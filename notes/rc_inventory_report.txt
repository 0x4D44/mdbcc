Byte-level rules the writer must reproduce:
- Emission order = SOURCE ORDER (with #include spliced inline), EXCEPT RT_STRING bundles are deferred to the very end. NOT the current type-tier order in res.rs:104.
- Every record lang=0x0000 (NOT res.rs's 0x0809 default — this is the BC4.5-era Borland default; must be the default for this profile).
- Mem flags: MENU/DIALOG/GROUP_ICON/STRING 0x1030; RT_ICON 0x1010 (MOVEABLE|DISCARDABLE, no PURE); BITMAP/RCDATA/VERSION 0x0030 (MOVEABLE|PURE).
- Header: type then name, each FFFF+ord or UTF-16LE NUL string (names emitted UPPERCASE as written in source), pad to DWORD, then DataVersion u32 0, mem u16, lang u16, Version u32 0, Characteristics u32 0. Data padded to DWORD before next record.
- ICON statement => TWO records: RT_ICON (#3) with a GLOBAL sequential ordinal name (1..6 in source order) emitted FIRST, then RT_GROUP_ICON (#14) with the source name. RT_ICON payload = the .ico file's image bytes (at ICONDIRENTRY.dwImageOffset, length dwBytesInRes; 766-22=744 for MD.ICO). GRPICONDIR payload (20 B) = idReserved 0, idType 1, idCount 1, then width/height/colorCount from the ICONDIRENTRY (20 20 10 00) but wPlanes/wBitCount taken from the EMBEDDED BITMAPINFOHEADER (01 00 04 00 — the .ico dir entry itself says 0,0), dwBytesInRes, nID u16. Inline 'hex' icon bodies are a complete .ico file image — same conversion.
- BITMAP payload = file bytes minus the 14-byte BITMAPFILEHEADER, length computed from the header: (bfOffBits-14) + biSizeImage — NOT filesize-14 (DOWNBUTT.BMP/UPBUTT.BMP have 14 trailing junk bytes: 396 on disk, 368 in res). Inline bitmap bodies: same stripping (TB_MAINWIN 4918->4904).
- RCDATA file payload = file verbatim.
- VERSIONINFO = standard Win32 UTF-16 VS_VERSIONINFO tree (wLength/wValueLength/wType triplets, 52-byte VS_FIXEDFILEINFO, nested StringFileInfo/StringTable/String, DWORD padding); VALUE's comma-separated extra "\0" strings concatenate into the value.

- CONFIRMED PE32 BUG at pe_writer.rs:4326: `let dd_off = opt_hdr_off + 112 + 2 * 8;` — 112 is the PE32+ DataDirectory base. The function never reads the optional-header Magic. In a PE32 (magic 0x10B) the directories start at opt_hdr_off+96, so Resource is at +112; writing at +128 lands on DataDirectory[4] (Certificate Table) — Resource stays zero AND the security dir is corrupted. SizeOfInitializedData (+8) and SizeOfImage (+56) offsets are coincidentally identical in PE32/PE32+, so the dd base is the only fix needed (read Magic, base = 96 for 0x10B, 112 for 0x20B).
- mdlink CLI (src/bin/mdlink.rs:76-101): inputs are only .lib → Input::Archive, else Input::CoffBytes. NO .res/.rc handling. link/mod.rs:356-361: Input::ResFile returns LinkError::Internal "not yet supported". So today there is NO route to get a .rsrc into the mdlink-linked PE32 railc.exe.
- pe_writer::build_rsrc (pe_writer.rs:2115) / emit_rsrc (2197): builds the 3-level tree from typed RcUnit collectors; id-entries ONLY (write_resource_directory always called with named=0, pe_writer.rs:2257/2269/2282) — no named directory entries, no ICON/BITMAP/RCDATA/GROUP_ICON/VERSION types, one language per resource. Needs generalising to flat (type, name-or-ordinal, lang, data) entries — exactly what a parsed .res file yields.
