# One-Stop Build Config Design

Status: SIGNED-OFF.

Arthur approved this design in-thread on 2026-06-12.

## Goal

Add a Cargo.toml-inspired project build path for mdbcc so a user can run one command from a project root and build a small C/C++ Windows program with sources, resources, objects, and libraries declared in a local config file.

The motivating shape is mdtpw: a simple project manifest in the repo root, discovered by walking upward, with paths resolved relative to the manifest.

## Evidence Reviewed

### mdtpw

Reviewed read-only in `C:\language\mdtpw`.

Key precedent:

- `mdtpw.toml` uses one `[package]` table.
- Invoking `mdtpw` with no positional Pascal source walks upward from the current directory to find `mdtpw.toml`.
- Explicit positional source input bypasses TOML mode.
- The parser is a small hand-rolled TOML subset: one package table, key/value lines, strings, arrays, comments, and hard validation.
- Unknown keys, duplicate keys, duplicate tables, wrong types, bad enums, and malformed arrays are hard errors.
- Paths in the manifest resolve relative to the manifest parent directory.
- Resources can be `.rc` or `.res`; `.rc` inputs are compiled before linking.
- Tests exercise discovery, parent discovery, no-config errors, positional bypass, CLI overrides, resource handling, parser validation, and subsystem behavior.

### mdbcc

Reviewed in `C:\language\mdbcc`.

Current relevant shape:

- `bcc` at `src/main.rs` is a Borland-style single-translation-unit compiler driver.
- `bcc` currently rejects multiple source inputs and suggests `bcc -c` followed by `mdlink`.
- `mdlink` accepts `.obj`, `.lib`, and `.res` inputs and links with `link::Input`.
- `mdrc` compiles `.rc` to `.res`, including a `--profile brc32|bc45` option.
- `compile_to_object_with_target_defines` can compile source files into object bytes.
- `SearchPathResolver` and `DefaultResolver` support include directory resolution.
- `compile_to_pe_with_rc_defines` already applies `bcc -D` definitions to direct single-source resource compilation.
- `link::auto_subsystem` already detects `WinMain` and selects the Windows subsystem for direct PE compilation.
- The code generator supports object files without an entry point, so multi-source project builds are feasible.

## User Surface

Add a new binary named `mdbcc`.

Why not change `bcc`:

- `bcc` has an existing Borland-compatible role and usage surface.
- Project build mode is not the same job as single-source compiler compatibility.
- Keeping `bcc`, `mdlink`, `mdrc`, and `mdar` unchanged avoids surprising existing users.

Accepted v1 commands:

```powershell
mdbcc
mdbcc --config path\to\mdbcc.toml
mdbcc --help
mdbcc --version
```

Rules:

- `mdbcc` with no arguments searches upward from the current directory for `mdbcc.toml`.
- `mdbcc --config PATH` uses that manifest directly. The project root is the manifest parent, not the process working directory.
- `-h` aliases `--help`; `-V` aliases `--version`.
- Positional source arguments are rejected in v1. Explicit source compilation remains the job of `bcc`.
- Build override flags such as `-o`, `-I`, `-D`, `--target`, and `--subsystem` are rejected in v1. Users should edit `mdbcc.toml` or use the lower-level tools.
- There are no CLI/TOML merge or precedence rules in v1 because there are no build overrides.

This deliberately diverges from mdtpw's override support. mdtpw had an existing single binary that owned both source and project mode. mdbcc already has separate low-level tools, so v1 keeps the project runner manifest-only.

## Config File

Filename: `mdbcc.toml`

Schema:

```toml
[package]
name = "hello"
sources = ["main.cpp", "util.cpp"]
output = "hello.exe"
target = "win64"
subsystem = "console"
include_dirs = ["include"]
defines = ["FEATURE_X", "WINVER=0x0400", "EMPTY="]
resources = ["resource/app.rc", "resource/version.res"]
resource_profile = "brc32"
objects = ["prebuilt.obj"]
libs = ["support.lib"]
```

Required:

- `sources`: non-empty array of source file paths.

Optional:

- `name`: default output stem when `output` is omitted. If both are omitted, use the first source stem.
- `output`: executable path. Default `<name>.exe`.
- `target`: `win64` or `win32`. Default `win64`, matching current mdbcc defaults.
- `subsystem`: `console`, `windows`, or `gui`. If omitted, auto-detect from compiled and prebuilt object entry symbols.
- `include_dirs`: include search paths for C/C++ compilation.
- `defines`: preprocessor definitions applied to C/C++ compilation and `.rc` resource compilation.
- `resources`: `.rc` or `.res` inputs. `.rc` files are compiled before linking.
- `resource_profile`: `brc32` or `bc45`. Default `brc32`.
- `objects`: prebuilt `.obj` inputs.
- `libs`: `.lib` archives.

`defines` syntax matches the existing `-D` convention:

- `NAME` defines `NAME` to `1`.
- `NAME=value` defines `NAME` to `value`, splitting at the first `=`.
- `NAME=` defines `NAME` to the empty string.
- Empty define strings are hard errors.
- Duplicate define names are resolved by the last array entry, matching map-style resource define behavior.

## TOML Subset And Validation

Supported subset:

- UTF-8 input only.
- Blank lines and `#` comments are allowed.
- Exactly one `[package]` table is required.
- Key/value pairs must appear under `[package]`.
- Keys are bare identifiers.
- Values are double-quoted strings or single-line arrays of double-quoted strings.
- Empty arrays are syntactically allowed, but fields that require values reject them during validation.
- Trailing array commas, empty middle array elements, malformed strings, inline tables, dotted keys, nested tables, multiline strings, and unquoted strings are rejected.

Hard validation errors:

- Missing `[package]`.
- Duplicate `[package]`.
- Any table other than `[package]`.
- Duplicate package keys.
- Unknown package keys, preferably with a spelling suggestion when the edit distance is small.
- Wrong value types.
- Missing `sources`.
- Empty `sources`.
- Empty string entries in path arrays.
- Empty `name`, `output`, `target`, `subsystem`, or `resource_profile` strings.
- Invalid `target`, `subsystem`, or `resource_profile` enum values.
- Source paths whose extension is not accepted by the current compiler source rules.
- Resource paths that are not `.rc` or `.res`.
- Object paths that are not `.obj`.
- Library paths that are not `.lib`.
- Duplicate normalized entries within `sources`, `resources`, `objects`, or `libs`.

## Path Policy

Definitions:

- `manifest_path` is the loaded `mdbcc.toml`.
- `manifest_dir` is `manifest_path.parent()`.
- Relative manifest paths resolve against `manifest_dir`.

Input paths:

- Relative input paths are resolved from `manifest_dir`.
- Absolute input paths are accepted for read-only inputs: `sources`, `include_dirs`, `resources`, `objects`, and `libs`.
- Relative input paths that contain `..` are normalized before duplicate checks. They are allowed because they are read-only, but diagnostics should print the normalized display path.

Output paths:

- Relative `output` paths resolve from `manifest_dir`.
- Absolute `output` paths are rejected in v1.
- Relative `output` paths that escape `manifest_dir` after lexical normalization are rejected.
- The output parent directory is created if needed.

Generated intermediates:

- Generated object and resource files always live under `manifest_dir\target\mdbcc`.
- Config fields cannot move generated intermediates outside that directory.
- Generated file names must be deterministic and collision-resistant.
- Use a stable index plus a sanitized normalized path plus a stable path hash, for example `0000-src_app_main-6f2a7c91.obj` and `0000-resource_app-91d4bc03.res`.

## Build Flow

1. Discover and load `mdbcc.toml`.
2. Parse and validate the manifest.
3. Resolve paths against `manifest_dir`.
4. Create `target\mdbcc\objects` and `target\mdbcc\resources` under `manifest_dir`.
5. Compile each source to an object file:
   - Use `compile_to_object_with_target_defines`.
   - Use `Target::Win64` or `Target::Win32` from the config target.
   - Use `SearchPathResolver` when `include_dirs` is non-empty.
   - Write generated objects using the deterministic naming policy.
6. Compile each `.rc` resource to `.res`:
   - Use the existing resource compiler library path used by `mdrc`.
   - Apply `defines` to resource compilation.
   - Use `resource_profile` to select BRC32-style or BC45-style output.
   - Write generated resources using the deterministic naming policy.
   - Pass configured `.res` files through as linker inputs.
7. Read configured `objects` and `libs`.
8. Select the linker subsystem:
   - If `subsystem` is present, use it as an explicit override.
   - If `subsystem` is omitted, scan generated and configured object files with the existing entry-symbol logic. If any object indicates Windows/GUI, use Windows; otherwise use console.
   - Libraries are not used for auto-subsystem detection in v1.
9. Link all object, resource, and library inputs using `link::link`.
10. Print a concise build summary with config path, target, subsystem, output path, and input counts.

The first implementation should rebuild all configured sources and resources each run. Incremental rebuild logic is intentionally out of scope.

## Linker Validation

Because the v1 schema accepts prebuilt `objects` and `libs`, machine validation belongs in the linker, not only in project mode.

Design requirement:

- `link::link` should reject any decoded object or archive member whose COFF machine does not match `LinkOpts.machine`.
- The error should include enough context to identify the offending input and show expected versus actual machine.
- Project tests should cover mismatched configured `.obj` and `.lib` inputs.

This is useful beyond `mdbcc` because `mdlink -m32 some_x64.obj` should also fail clearly.

## Code Shape

Expected touched files:

- `Cargo.toml`: add the `mdbcc` binary and bump package version from `0.2.0` to `0.3.0`.
- `Cargo.lock`: update package version if Cargo rewrites it.
- `src/bin/mdbcc.rs`: CLI entry point for project mode.
- `src/project.rs` or `src/project/mod.rs`: project feature module.
- `src/link/...`: linker machine mismatch validation.
- `src/lib.rs`: expose the project module and any shared parsing helpers needed by tests or CLIs.
- `tests/project_config.rs`: integration tests for discovery, parsing, path resolution, multi-source build, resources, target selection, and errors.
- `wrk_docs/...`: this design document.
- `wrk_journals/...`: task journal.

Implementation boundaries:

- Keep pure config parsing/validation testable without filesystem writes or subprocesses.
- Keep build orchestration separate from parser state.
- Reuse or centralize existing parsing behavior for target, subsystem, resource profile, and `-D` define strings where practical.
- Do not move broad CLI behavior into library APIs unless the project runner needs it.

## Acceptance Criteria

CLI:

- `mdbcc --help` documents project mode, `--config`, and manifest-only v1 behavior.
- `mdbcc --version` prints the package version.
- Unknown options fail clearly.
- Positional source arguments fail clearly and point users to `bcc`.
- Build override flags fail clearly and point users to `mdbcc.toml` or the low-level tools.

Discovery and paths:

- Running `mdbcc` in a directory containing `mdbcc.toml` builds the declared project.
- Running `mdbcc` in a child directory discovers a parent `mdbcc.toml`.
- `--config` uses the given manifest even when the current directory is elsewhere.
- Missing config produces a clear error.
- Relative paths resolve from `manifest_dir`, not the process working directory.
- Relative output path escape is rejected.
- Absolute output path is rejected.
- Generated intermediates are written under `manifest_dir\target\mdbcc`.

Parser and schema:

- Missing package, duplicate package, unknown table, duplicate keys, unknown keys, wrong types, malformed arrays, trailing array commas, invalid enum values, missing `sources`, empty `sources`, empty string path entries, unsupported extensions, and duplicate normalized inputs are tested.
- `defines` tests cover bare, valued, empty-valued, duplicate-name, and empty-string cases.

Build behavior:

- Multi-source projects compile and link successfully.
- Include dirs and defines are applied to C/C++ compilation.
- `defines` are applied to `.rc` compilation.
- `.rc` resources compile and link; `.res` resources pass through.
- Omitted `subsystem` auto-detects a `WinMain` project as Windows/GUI.
- Explicit `subsystem` overrides auto-detection.
- Generated files with same-stem inputs from different directories do not collide.

Target and linker:

- `target = "win64"` builds a PE32+ x86-64 executable.
- `target = "win32"` compiles Win32 objects, links a PE32 I386 executable, and uses image base `0x00400000`.
- The Win32 project test should inspect PE machine, optional header magic `0x10B`, and image base. It should run the executable when the host supports PE32 execution.
- Mismatched configured `.obj` and `.lib` inputs produce clear machine mismatch errors.

Regression:

- Existing `bcc`, `mdlink`, `mdar`, and `mdrc` tests continue to pass.

Validation after implementation:

```powershell
mdtimeout 120 cargo fmt
mdtimeout 120 cargo clippy
mdtimeout 120 cargo test -q
```

## V1 Non-Goals

Not in v1:

- Positional source mode for `mdbcc`.
- CLI build overrides or TOML/CLI merge semantics.
- Build profiles.
- Globbing.
- Build scripts or pre/post hooks.
- Workspaces or manifest inheritance.
- Dependency graphs or library build graphs.
- Environment-variable expansion.
- Incremental dependency tracking.
- Configurable generated-intermediate directories.
- Linker knobs such as custom entry point, image base, stack size, heap size, map files, or subsystem version.
- Separate `resource_defines`; `defines` applies to both C/C++ and `.rc` in v1.

## Review Results

Three read-only reviewers examined the draft, then performed one refutation pass over the combined findings. No critical findings were reported.

Findings folded into the design:

- Subsystem default: changed from default `console` to omitted means auto-detect, with explicit override support.
- CLI grammar: v1 is manifest-only. Only `--config`, help, and version are accepted.
- Define semantics: specified exact `-D` grammar and made `defines` apply to both C/C++ and `.rc`.
- Parser gates: added a validation matrix for duplicate keys/tables, missing package, malformed arrays, bad enums, empty values, unsupported extensions, and duplicate inputs.
- Path policy: specified output containment, absolute output rejection, generated intermediate location, and input path behavior.
- Linker validation: added link-level machine mismatch requirement for objects and archive members.
- Win32 acceptance: strengthened to end-to-end compile/link/header validation.
- Generated naming: specified deterministic collision-resistant naming for generated objects and resources.
- Scope control: added explicit v1 non-goals.
- Module boundaries: kept as design pressure rather than a prescribed file layout; parser/config/build seams are required.

One reviewer argued auto-subsystem could be dropped as extra policy. I am not dropping it because the current direct compiler path already auto-detects `WinMain`; a project manifest should not regress that behavior silently.
