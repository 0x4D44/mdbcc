## Context anchor

S1 closed today. mdbcc emits COFF `.obj` files with Borland-style C++
mangling; `mdlink` reads COFF + OMF + `.lib` archives + `.def` stubs;
the two-file C++ project compiles end-to-end as PE32+ (Win64 only).
**All x86-64.** Three architectural facts pin the work S2 has to do:

- `src/codegen.rs` (7809 LoC) hard-codes Win64: every `self.emit(&[…])`
  call carries an REX-prefixed AMD64 instruction stream baked-in as a
  raw `&[u8]` literal (e.g. `emit_riprel(&[0x48, 0x8D, 0x05], …)` for
  `lea rax, [rip+disp32]`). Around 800 distinct byte-literals are
  scattered across the file — see §3 for the encoder-table census.
- `src/link/pe_writer.rs` (3092 LoC) writes Machine = `0x8664`, Magic =
  `0x020B` (PE32+), 64-bit ImageBase, `.pdata`/`.xdata`-based SEH. Every
  one of those is wrong for 32-bit.
- `src/coff.rs` (1392 LoC) reserves `Machine::I386` but the encoder's
  reloc translator always calls `RelocKind::to_amd64()` (line 879). The
  i386 retarget is two days of work plus a relocation-kind table.

Each of T4's three sub-truths (x86 codegen + Win32 ABI + 32-bit object
& image format) sits in a different module. S2's design has to keep
the existing x64 stripe byte-identical (locked by `tests/o1_byte_iden
tity.rs`, 88 SipHash baselines) while introducing a parallel x86 path
that runs end-to-end. The work breaks naturally into sub-phases that
can run as parallel subagents — see §9.

## §1 — Goals + non-goals

### §1.1 — In-scope (the T4 dissolve)

After S2 closes, **the same C source `compile_to_object()` accepts MUST
build through `mdbcc -c -m32 foo.cpp` to a COFF i386 `.obj`, then
through `mdlink -m32 foo.obj kernel32.lib -o foo.exe` to a runnable
Win32 PE that exits with the same code as `bcc32 + tlink32`.** The
exit gate is O12 source-to-behaviour vs bcc32 across the 88-program
portable corpus.

Concretely S2 must produce:

- **Encoder**: a table-driven x86 instruction emitter that backs both
  the existing Win64 codegen (after retarget — see §4 trait pivot)
  and a new Win32-x86 codegen. The table is the single source of
  truth; a future disassembler can read it in reverse.
- **Codegen retarget**: split the per-target encoding+ABI surface
  behind a `Target` trait. Win64's `Target` impl is a behaviour
  preserving refactor; Win32's `Target` impl is new. The shared
  AST-walk + scoping + SEH-scope-collection plumbing stays common.
- **Win32 ABI** in `codegen/abi.rs`: `__cdecl`, `__stdcall`,
  `__fastcall` (Borland's variant — see §6), `__pascal` (optional —
  Q-Pascal in §11). Names decorated to bcc32 convention.
- **COFF i386 retarget** in `src/coff.rs`: Machine value, reloc-type
  map, symbol type field nuances (function symbols still use
  IMAGE_SYM_TYPE_FUNCTION; no real divergence here).
- **PE32 writer** in `src/link/pe_writer.rs`: Magic-flip, 32-bit
  optional header, no `.pdata`/`.xdata` requirement, optional `.reloc`
  base-relocation section because PE32 default `ImageBase = 0x400000`
  collides with the system loader's expectations more than PE32+'s
  `0x140000000` does.
- **fs:[0] SEH machinery** in a new `src/codegen/seh3.rs` plus a
  module-wide personality stub: per-try `push EXCEPTION_REGISTRATION`
  / `pop` pairs, one synthesised handler per program (callable via
  `fs:[0]` chain) that walks the same scope-table-shaped LSDA the
  x64 path already emits in `eh.rs`.
- **Driver wiring**: `-m32` (or `-mtarget=x86_win32`) drives target
  selection; without it, x64 path stays the historical default.

### §1.2 — Explicitly out of scope

The May-26 plan §S2 names these as "later stones"; the HLD pins them
because they tempt scope creep:

- **Real headers** — S3. S2's corpus uses the same `#include`-free /
  stub-header style the 88 fixtures use today.
- **OWL / ClassLib / response tables** — S5+. S2 does not need
  `_USERENTRY`/`CALLBACK` macros, only the calling conventions they
  expand to.
- **Win16 NE format** — explicitly retired by the May-26 plan (§0,
  out-of-scope). PE32 only.
- **DPMI / Win32s / VBX** — all retired by the May-26 plan.
- **`-m32 -mdll`** — DLL output is S8 long-tail; S2 emits `.exe` only,
  same as S1c.
- **`-O1`/`-O2` optimisation modes** — we have one optimisation level
  ("none, careful"); S2 stays at that bar.
- **Floating-point `long double`** — Borland uses Intel 80-bit. We
  promote to `double` (64-bit IEEE) on x86 today; that stays. Real
  `long double` is filed under S8.

The 88 e2e fixtures **keep their x64 byte-identity stripe**. S2 adds a
**parallel x86 byte-identity stripe** (Q-Corpus in §11 picks the
fixture-tagging mechanism). The two stripes do not share SHA-256
baselines; they share fixture *sources*.

## §2 — The `Target` trait surface

> **IMPLEMENTATION NOTE (2026-05-28, Decision-1c.2).** The generic
> `impl Gen<'s, T: Target>` design in §2.1 below was **deferred** during
> S2b.1. The shipped code keeps `Gen<'s>` non-generic and carries a
> `TargetKind` enum (runtime tag) instead — the generic refactor touches
> ~80 method signatures and the regression risk to the 88 SipHash x64
> baselines was judged too high for the available budget. The `Target`
> trait below is implemented as-specified (see `src/codegen/target.rs`)
> and remains the per-target contract; only the *dispatch mechanism* is
> a runtime branch on `TargetKind` rather than monomorphisation. Future
> work may re-attempt the generic form. Rationale:
> `wrk_journals/2026.05.27 - JRN - S2 drive (32-bit x86 backend).md`
> Decision-1c.2. **Read §2.1 as design-intent, not as the shipped shape.**

The Win64 codegen lives in `Gen<'s>` (the per-function state object,
`src/codegen.rs:?:state-decl`) plus the helper modules
(`abi.rs`/`expr.rs`/`stmt.rs`/`decl.rs`/`cpp.rs`/`object.rs`). Today
every byte the codegen emits is x64-specific; today's ABI constants
live as `pub(crate) const` items in `codegen/abi.rs`. S2 introduces
a `Target` trait that owns *every* per-target divergence:

```rust
// src/codegen/target.rs (NEW)

/// Per-target codegen + ABI surface. One impl per (architecture, OS,
/// calling-convention-default) tuple. Two impls today:
/// - WIN64 — current Microsoft x64 ABI on PE32+ (the historical path).
/// - WIN32 — Win32-x86 ABI on PE32 (S2's new path).
///
/// `impl Gen<'s, T: Target>` carries `T` as a generic parameter (NOT
/// `Box<dyn Target>`) so the encoder's hot path inlines. Every method
/// here is a leaf — they take parameter-by-value and return small
/// fixed-size data (bytes, register numbers, flags). The trait has no
/// associated state, no `&self` mutability; impls are zero-sized
/// markers ("phantom types").
pub trait Target: 'static {
    // -- Architecture facts ---------------------------------------------

    /// Pointer / GPR width in bytes (8 for x64, 4 for x86).
    fn ptr_bytes() -> u32;

    /// COFF machine value for `Object.machine`.
    fn coff_machine() -> coff::Machine;

    /// PE optional-header Magic (0x020B / 0x010B).
    fn pe_magic() -> u16;

    /// Number of integer arg registers (4 for Win64, 0 for cdecl-Win32,
    /// 2 for fastcall-Win32 — see also `int_arg_regs` for the per-conv
    /// detail). This is the *default* convention used by the codegen
    /// when no `__cdecl`/`__stdcall`/`__fastcall` keyword overrides;
    /// for Win64 it is 4 unconditionally.
    fn int_arg_reg_count_default() -> usize;

    /// Per-positional integer arg register encoding bytes for the
    /// SPILL (callee-side incoming-arg store into the locals frame).
    /// Returns an empty slice if the slot is on the stack. The slice
    /// is the *prefix* — the emit site appends `disp32` (the locals-
    /// frame offset). Mirrors today's `ARG_SPILL[]` table.
    fn arg_spill_prefix(slot: usize, conv: CallConv) -> &'static [u8];

    /// Per-positional integer arg register encoding bytes for the
    /// LOAD (caller-side stack-temp into argN register).
    fn arg_load_prefix(slot: usize, conv: CallConv) -> &'static [u8];

    /// Per-positional FP arg register encoding (Win64 = xmm0..xmm3;
    /// Win32 = none — all FP args go on stack). Empty slice when the
    /// slot has no register assignment for this conv.
    fn fp_arg_load_prefix(slot: usize, conv: CallConv) -> &'static [u8];
    fn fp_arg_spill_prefix(slot: usize, conv: CallConv) -> &'static [u8];

    // -- Aggregate ABI classification -----------------------------------

    /// How an aggregate parameter is passed. Win64: §6.1 + abi.rs
    /// classify_struct_for_win64 (sizes 1/2/4/8 → InReg, else HiddenPtr).
    /// Win32 cdecl/stdcall: caller pushes a copy of the aggregate on
    /// stack (`ByValueOnStack(size_padded_to_4)`); the callee reads
    /// directly. Win32 fastcall: tiny structs may ride EAX/EDX but the
    /// rules are convention-specific (TODO Q-Fastcall).
    fn classify_aggregate(size: usize, conv: CallConv) -> AggClass;

    // -- Caller-cleanup / callee-cleanup behaviour ----------------------

    /// Who frees the stack-passed arguments after the call:
    /// - `Caller` — `add esp, N` after the call (cdecl, Win64).
    /// - `Callee` — callee returns via `ret N` (stdcall, fastcall on
    ///   stack-passed tail, pascal).
    fn stack_cleanup(conv: CallConv) -> StackCleanup;

    // -- RIP-relative vs direct addressing ------------------------------

    /// True for x64 (lea rax, [rip+disp32] → fixup REL32). False for
    /// x86 (lea eax, [imm32] → fixup ADDR32). Determines both the
    /// encoder ModR/M choice and the COFF RelocKind the converter
    /// emits for cross-section refs.
    fn rip_relative() -> bool;

    // -- SEH model ------------------------------------------------------

    /// Which SEH style this target uses. The codegen collects scope
    /// tables uniformly (`TryScope` in `eh.rs`); the target decides
    /// how to materialise them at emit time.
    fn seh_kind() -> SehKind;

    // -- Encoder dispatch into the table --------------------------------

    /// Look up the byte encoding for a logical instruction shape.
    /// Defaults to `crate::codegen::encoder::EMITTERS_X64` /
    /// `EMITTERS_X86` per impl; centralises so callers do not match
    /// on `Target` themselves. See §3 for the table schema.
    fn encode(op: Op, ops: &[Operand]) -> Result<Encoded, EncodeError>;
}
```

### §2.1 — Where dispatch happens

The codegen is generic over `T: Target`. Every emit-time decision that
diverges between x64 and x86 routes through a `T::method()` call. At
monomorphisation time the compiler stamps out two copies of `impl Gen`
— one with `T = Win64` constants inlined, one with `T = Win32`. Cost
analysis:

- The `T::method` calls are static; LLVM inlines them at `-O1` and
  better. Dispatch overhead at runtime = zero.
- Binary-size cost = two copies of every `impl Gen` method. The
  current `Gen` is ~6500 LoC of methods; doubling that doubles the
  monomorphised code in mdbcc.exe. At today's tree depth that adds
  ~150 KB to the release binary, which is fine.
- Compile-time cost = ~10-15% slower `cargo build`, measured at the
  S1a precedent (we doubled some generics there and saw ~12%).
  Acceptable.

The alternative — `Box<dyn Target>` — buys nothing because the
encoder is in the hot path of every emit; we'd pay a virtual call
per byte emitted. Reviewer judgment: generic, not dyn.

```rust
pub struct Win64;
impl Target for Win64 {

    fn arg_spill_prefix(slot, _conv) -> &'static [u8] {
        crate::codegen::abi::ARG_SPILL[slot]
    }
    // … 9 more methods, each lifting a current Win64 constant ...
    fn rip_relative() -> bool { true }
    fn seh_kind() -> SehKind { SehKind::TableX64 }
}

// src/codegen/target/win32.rs (NEW)
pub struct Win32;
impl Target for Win32 {
    fn ptr_bytes() -> u32 { 4 }
    fn coff_machine() -> coff::Machine { coff::Machine::I386 }
    fn pe_magic() -> u16 { 0x010B }
    fn int_arg_reg_count_default() -> usize { 0 } // cdecl default
    fn arg_spill_prefix(slot, conv) -> &'static [u8] {
        match conv {
            CallConv::Cdecl | CallConv::Stdcall => &[],
            CallConv::Fastcall => abi_x86::FASTCALL_SPILL[slot],
            CallConv::Pascal   => &[],
        }
    }
    fn rip_relative() -> bool { false }
    fn seh_kind() -> SehKind { SehKind::Fs0Chain }
}
```

The dispatch site lives at `impl Gen<'s, T>` definition: today's
`Gen<'s>` becomes `Gen<'s, T = Win64>` with a default type parameter
so the existing single-target consumers keep working without source
changes. Multi-target callers (e.g. the new `compile_to_object_for`
in S2.x) name the target explicitly: `compile_module::<Win32>(tu)`.

### §2.3 — Stateful state object lifts unchanged

`Gen` holds the per-function emission state (`code: Vec<u8>`,
`riprefs`, `calls`, etc.). None of those fields are target-specific.
The `Gen` struct stays exactly as it is in `codegen.rs:1100+`; only
its `impl` block becomes generic.

## §3 — Instruction-table schema

The current emitter pattern in `codegen.rs` is:

```rust
// codegen.rs:1720
fn emit_riprel(&mut self, opcode: &[u8], target: RipRef) {
    self.emit(opcode);
    let at = self.here();
    self.emit(&[0, 0, 0, 0]);
    self.riprefs.push(RipReloc { at, target });
}

// call site, codegen.rs:1623
self.emit_riprel(&[0x8B, 0x0D], RipRef::Data(save_idx));
self.emit_riprel(&[0x48, 0x8D, 0x05], RipRef::Data(save_idx));
self.emit_riprel(&[0x48, 0x8D, 0x05], RipRef::Vtable(rec_id));
// … ~800 more …
```

The bytes are baked into call sites verbatim. The encoder is the
caller — we tell `emit` exactly which bytes to emit. **Decision-1
(Arthur ratified, brief)**: replace this with a **table-driven
encoder**. The table is the single source of truth, callers say *what*
they want, the table tells them *how* to encode it.

### §3.1 — Schema

```rust
// src/codegen/encoder/table.rs (NEW)

/// One row of the encoding table. Read-only; no allocation.
#[derive(Debug)]
pub struct Pattern {
    /// Logical operation (mov / lea / call / ret / push / pop / jcc / …).
    pub op: Op,
    /// Operand shapes this row matches. Position-significant.
    pub operands: &'static [OperandKind],
    /// Architecture flag — picks x64-only / x86-only / both rows.
    pub arch: ArchSet,
    /// REX-prefix policy: 0 = none, REX_W = 0x48 always, …
    pub rex: RexPolicy,
    /// Opcode bytes. Variable length 1-3 (most x86 ops are 1-2).
    pub opcode: &'static [u8],
    /// ModR/M template (None when there is no ModR/M byte; e.g. RET).
    /// When `Some(b)`, the encoder OR-merges the `reg` and `rm` fields
    /// from the operand registers at emit time.
    pub modrm: Option<ModRMTemplate>,
    /// Where the displacement lands and how big it is. None for no
    /// displacement; Disp8 for [reg+disp8]; Disp32 for [reg+disp32]
    /// (and for RIP-relative on x64); ImmAddr32 for x86 absolute
    /// `[disp32]`. Determines the COFF RelocKind the converter picks.
    pub disp: DispKind,
    /// Immediate operand emission. None / Imm8 / Imm16 / Imm32 / Imm64.
    pub imm: ImmKind,
}

#[derive(Debug, Clone, Copy)]
pub enum Op {
    Mov, Lea, Call, Ret, Push, Pop, Jcc(u8), Jmp,
    Add, Sub, Xor, And, Or, Cmp, Test, Imul,
    Movsd, Movss, Addsd, Subsd, Mulsd, Divsd, Ucomisd, Cvtsi2sd, Cvttsd2si,
    Int3, Nop,
    // ~ 60 mnemonics total; the AST never references opcodes by name —
    // it routes through Op + Operand[].
}

#[derive(Debug, Clone, Copy)]
pub enum OperandKind {
    /// Specific register (rax, eax, al — encoder picks register encoding).
    Reg(RegClass, RegId),
    /// Any register of a given class (for table rows that handle the
    /// register-to-register variant generically).
    AnyReg(RegClass),
    /// Memory: [base + disp32]. base is encoded; disp32 comes from
    /// the operand at emit time.
    Mem(RegClass /* base */, DispKind),
    /// Memory: [base + index*scale + disp32] (SIB).
    MemSib(RegClass, RegClass, ScaleKind, DispKind),
    /// Absolute [disp32] — x86 only; encoder picks the ModR/M `disp32-only`
    /// form (mod=00, rm=101 on x86; on x64 this is RIP+disp32).
    MemAbs,
    /// RIP-relative [rip+disp32] — x64 only. Encoder emits mod=00 rm=101.
    MemRipRel,
    /// Immediate of given width.
    Imm(ImmWidth),
    /// Relative-32 displacement (E8 call rel32 / E9 jmp rel32). Encoder
    /// emits 4 zero bytes; emit site records the fixup site index.
    Rel32,
}

#[derive(Debug, Clone, Copy)]
pub enum RegClass {
    Gpr8, Gpr16, Gpr32, Gpr64, Xmm,
    /// "Segment-register slot" — for `mov reg, fs:[0]` and friends.
    Seg,
}

#[derive(Debug)]
pub struct ModRMTemplate {
    /// `mod` field: 0/1/2/3 (00=mem-no-disp, 01=mem+disp8, 10=mem+disp32,
    /// 11=reg).
    pub mod_field: u8,
    /// `reg` field: filled at emit time from the destination operand.
    /// Set to `RegOrOpcodeExt::FromOperand(0)` to mean "take the operand
    /// at position 0", or `RegOrOpcodeExt::Fixed(n)` for opcode-extension
    /// rows (e.g. `add reg, imm32` uses /0; `sub reg, imm32` uses /5).
    pub reg_field: RegOrOpcodeExt,
    /// `rm` field: filled from the second operand (when mod=3) or the
    /// memory operand's base register (when mod=0/1/2).
    pub rm_field: RegOrOpcodeExt,
}

#[derive(Debug, Clone, Copy)]
pub enum DispKind { None, Disp8, Disp32, ImmAddr32 }
#[derive(Debug, Clone, Copy)]
pub enum ImmKind { None, Imm8, Imm16, Imm32, Imm64 }
#[derive(Debug, Clone, Copy)]
pub enum ArchSet { X64Only, X86Only, Both }
#[derive(Debug, Clone, Copy)]
pub enum RexPolicy {
    /// No REX prefix even on x64.
    None,
    /// Always emit REX.W=1 (0x48) on x64; nothing on x86.
    W,
    /// Conditional — depends on register operand width (`Gpr64` ⇒ W=1,
    /// otherwise nothing). The encoder computes from operands.
    Auto,
}
```

### §3.2 — How the encoder picks a row

```rust
pub(crate) fn encode(arch: ArchSet, op: Op, ops: &[Operand])
    -> Result<Encoded, EncodeError>
{
    static TABLE: &[Pattern] = &PATTERN_TABLE;

    let mut best: Option<&Pattern> = None;
    for row in TABLE.iter()
        .filter(|r| r.op == op)
        .filter(|r| r.arch.matches(arch))
        .filter(|r| r.operands.len() == ops.len())
    {
        if row.operands.iter().zip(ops.iter()).all(|(k, o)| k.matches(o)) {
            // Pick the first matching row (table ordering is significant —
            // narrower forms come first).
            best = Some(row); break;
        }
    }
    let row = best.ok_or(EncodeError::NoMatchingRow(op, ops.to_vec()))?;
    row.emit(ops)
}
```

The table is **statically constructed** as a Rust `&'static [Pattern]`
in `src/codegen/encoder/patterns.rs`. ~250-400 rows for the full
mnemonic set we need. Static `const` means `cargo check` validates
the schema at compile time; rustfmt keeps it readable.

### §3.3 — Five worked examples

**Example 1 — `mov rax, [rbp+disp32]` (x64 only):**

```rust
Pattern {
    op: Op::Mov,
    operands: &[
        OperandKind::Reg(RegClass::Gpr64, RegId::ANY),
        OperandKind::Mem(RegClass::Gpr64, DispKind::Disp32),
    ],
    arch: ArchSet::X64Only,
    rex: RexPolicy::W,
    opcode: &[0x8B],
    modrm: Some(ModRMTemplate {
        mod_field: 0b10,
        reg_field: RegOrOpcodeExt::FromOperand(0),
        rm_field:  RegOrOpcodeExt::FromOperand(1),
    }),
    disp: DispKind::Disp32,
    imm:  ImmKind::None,
},
```

Emits: `48 8B <ModR/M> <disp32>`. For `mov rax, [rbp+0x10]`:
ModR/M = `10_000_101` = `0x85`, disp32 = `0x00000010`. Bytes:
`48 8B 85 10 00 00 00`. Matches today's hand-rolled `[0x48, 0x8B, 0x85]`
+ `emit_disp32(0x10)` exactly.

**Example 2 — `mov eax, imm32` (both x64 + x86):**

```rust
Pattern {
    op: Op::Mov,
    operands: &[
        OperandKind::Reg(RegClass::Gpr32, RegId::ANY),
        OperandKind::Imm(ImmWidth::Imm32),
    ],
    arch: ArchSet::Both,
    rex: RexPolicy::None,
    opcode: &[0xB8],
    modrm: None,
    // Opcode-register encoding: row's opcode byte (`0xB8`) is OR'd
    // with the register number (0..7) at emit time. The encoder
    // detects this from a special `RegOrOpcodeExt::OpcodeReg` flag.
    disp: DispKind::None,
    imm:  ImmKind::Imm32,
},
```

For `mov ecx, 42`: `0xB8 | 0x01 = 0xB9`, then `2A 00 00 00`. Bytes
`B9 2A 00 00 00`. Same encoding for x64 and x86.

**Example 3 — `call rel32` (both):**

```rust
Pattern {
    op: Op::Call,
    operands: &[OperandKind::Rel32],
    arch: ArchSet::Both,
    rex: RexPolicy::None,
    opcode: &[0xE8],
    modrm: None,
    disp: DispKind::None,
    imm:  ImmKind::None,
    // Rel32 emits 4 zero bytes; emit site records the fixup offset
    // for the caller to push into `CallSite::at`.
},
```

Bytes: `E8 00 00 00 00`. The 4-byte rel32 is patched at link time
(REL32 reloc).

```rust
        mod_field: 0b00,
        reg_field: RegOrOpcodeExt::FromOperand(0),
        rm_field:  RegOrOpcodeExt::Fixed(0b101), // [disp32]-only
    }),
    disp: DispKind::Disp32, // same wire field; COFF reloc differs
    imm:  ImmKind::None,
},
```

The wire bytes for `lea eax, [imm32]` on x86 are identical to `lea
rax, [rip+disp32]` on x64 minus the REX prefix — same ModR/M `mod=00
rm=101 reg=N`, same disp32 slot. **What differs is the relocation
type** the converter emits in the COFF reloc table:

- x64: `IMAGE_REL_AMD64_REL32` (`RelocKind::Rel32`).
- x86: `IMAGE_REL_I386_DIR32` (`RelocKind::Addr32` — see §4) because
  x86 has no RIP-relative; the address is absolute.

The encoder's `Encoded` return includes both the bytes and the kind of
fixup the disp32 slot wants. The converter routes that into the
correct COFF RelocKind per `Target::coff_machine()`.

**Example 5 — `ret` (both, no operands):**

```rust
Pattern {
    op: Op::Ret,
    operands: &[],
    arch: ArchSet::Both,
    rex: RexPolicy::None,
    opcode: &[0xC3],
    modrm: None,
    disp: DispKind::None,
    imm:  ImmKind::None,
},
// Variant: ret imm16 (for stdcall callee-cleanup)
Pattern {
    op: Op::Ret,
    operands: &[OperandKind::Imm(ImmWidth::Imm16)],
    arch: ArchSet::X86Only, // stdcall is Win32; Win64 has no equivalent
    rex: RexPolicy::None,
    opcode: &[0xC2],
    modrm: None,
    disp: DispKind::None,
    imm:  ImmKind::Imm16,
},
```

`ret` → `C3`. `ret 8` → `C2 08 00`. Trivial. The stdcall row is x86-
only because Win64 has only one calling convention and it cleans the
stack at the caller.

### §3.4 — Backing both x64 and x86 from one table

Several encodings are byte-identical between x64 and x86 (e.g. `mov
ecx, imm32` is `B9 ...` on both). For these, `arch = Both` and the
row is shared. Where x64 needs a REX prefix and x86 does not, the
`RexPolicy` controls the prefix emission per-target. Where the
opcodes diverge (e.g. `mov rax, [rbp+disp32]` on x64 vs `mov eax,
[ebp+disp32]` on x86 — opcode `8B` is shared but REX makes the first
operand 64-bit), the encoder picks the same opcode row but emits
REX.W only on x64.

The reverse map (disassembler-side) is mechanical: enumerate rows
filtered by `arch`, build a `BTreeMap<opcode_prefix, &Pattern>` once.
That's S8 work; the table is the contract.

### §3.5 — Table contents — what we don't have today

The 88 fixtures exercise a closed set of mnemonics. A census of
`codegen.rs` byte-literals (next paragraph for the methodology)
catalogs the encodings we actually use:

- 8 `mov` variants (reg/reg, reg/mem [rbp+disp32], mem/reg [rbp+disp32],
  reg/imm32, reg/imm64, mem/imm32, reg/mem [rip+disp32], mem/reg [rip+disp32]).
- 5 `lea` variants.
- 2 `call` variants (rel32, indirect).
- 6 `add`/`sub` variants.
- 8 conditional jumps (`jcc`).
- The full SSE2 scalar set (12 instructions in `abi.rs:MOVSD_*`
  through `CVTTSD2SI_*`).
- `push rbp` / `pop rbp` / `sub rsp, imm32` / prologue/epilogue.

Census methodology: `cargo expand src/codegen.rs | grep '0x[0-9A-Fa-f]'`
plus eyeballing the 6500-LoC method body. Estimated 60 distinct
mnemonics, ~250 rows in the table once both x64 and x86 variants land.
The S2a subagent does the actual census during implementation.

### §3.6 — File location + module split

```text
src/codegen/encoder/
   mod.rs         — public encode() entry; ergonomic helper builders
   patterns.rs    — the table (250-400 rows, ~1500 LoC mostly comment)
   table.rs       — Pattern / OperandKind / RegClass struct defs
   regs.rs        — RegId enum + register-number map per arch

```

```rust
self.emit(MOVSD_XMM0_FROM_RBP);
self.emit_disp32(off);
```

with:

```rust

    Operand::reg(Xmm0),

```

The migration is mechanical, can be done in one tick (S2a.3 in §9),
and is byte-identical for the 88 e2e Win64 fixtures (locked by the
existing SHA-256 stripe).

## §4 — i386 COFF extension

`src/coff.rs` is largely architecture-neutral by construction; the
only AMD64-coupled paths are the relocation-type map (line 879:
`r.kind.to_amd64()`) and the machine number (line 904-908). S2c flips
the dispatch by `Object.machine`:

### §4.1 — Relocation-type retarget

```rust
// src/coff.rs — proposed delta
impl RelocKind {
    fn to_wire(self, machine: Machine) -> Result<u16, CoffError> {
        match machine {
            Machine::Amd64 => Ok(self.to_amd64()),
            Machine::I386  => self.to_i386(),
        }
    }
    fn to_i386(self) -> Result<u16, CoffError> {
        match self {
            RelocKind::Addr64    => Err(CoffError::RelocKindUnsupported(self, Machine::I386)),
            RelocKind::Addr32    => Ok(IMAGE_REL_I386_DIR32),
            RelocKind::Addr32nb  => Ok(IMAGE_REL_I386_DIR32NB),
            RelocKind::Rel32     => Ok(IMAGE_REL_I386_REL32),
            RelocKind::SectionIx => Ok(IMAGE_REL_I386_SECTION),
            RelocKind::SecRel32  => Ok(IMAGE_REL_I386_SECREL),
        }
    }
}
```

i386 reloc type constants (PE/COFF spec §5.2.2):

| Constant                       | Value  | Meaning                              |
|--------------------------------|--------|--------------------------------------|
| `IMAGE_REL_I386_DIR32`         | 0x0006 | Absolute 32-bit VA                   |
| `IMAGE_REL_I386_DIR32NB`       | 0x0007 | 32-bit RVA (no base)                 |
| `IMAGE_REL_I386_REL32`         | 0x0014 | 32-bit relative (call/jmp rel32)     |
| `IMAGE_REL_I386_SECTION`       | 0x000A | 16-bit section index (debug)         |
| `IMAGE_REL_I386_SECREL`        | 0x000B | 32-bit section-relative offset       |

The notable absence: **no `IMAGE_REL_I386_ADDR64`.** x86 has no 64-bit
pointers; any `RelocKind::Addr64` in an i386 Object is a hard error.
Today the `Addr64` consumers are vtable slots (Phase B,
`build_vtables`) and the typeinfo base RVA. For x86 vtable slots
become `Addr32` (absolute 32-bit pointer; PE32 has ImageBase fixed at
`0x400000`, so the absolute VA fits in 32 bits). For typeinfo
base-RVA fields, `Addr32nb` (RVA) already fits in 32 bits.

### §4.2 — Symbol record diffs (none, really)

The 18-byte symbol record format is identical between AMD64 and I386
COFF. The `Type` field uses the same `IMAGE_SYM_TYPE_FUNCTION = 0x20`
on both. `StorageClass` values are unchanged. The only divergence in
practice is that some legacy toolchains used to special-case I386
file/function aux records (`.bf`/`.ef` debug info); mdbcc doesn't
emit those today, so no change.

The `IMAGE_FILE_HEADER.Characteristics` field: i386 COFF objects MAY
set `IMAGE_FILE_32BIT_MACHINE (0x0100)` in the Characteristics field
of an i386 *image* file header, but in an object-file context this
field is conventionally `0`. mdbcc's COFF writer keeps it `0` for
both targets. No change.

### §4.3 — How the codegen converter (`src/codegen/object.rs`) adapts

Today's `Module → Object` converter emits e.g. `Addr64` for vtable
slots:

```rust
// src/codegen/object.rs (current shape)
relocs.push(Reloc {
    offset: vtbl_offset_in_section + 8 * slot_index,
    symbol: target_function_symbol_index,
    kind: RelocKind::Addr64,
});
```

After §4.1's `to_wire(machine)` flip, the converter consults
`Target::coff_machine()` to pick `Addr64` vs `Addr32` for vtable slot
relocations. The converter becomes:

```rust
let pointer_reloc = if T::ptr_bytes() == 8 {
    RelocKind::Addr64
} else {
    RelocKind::Addr32
};
relocs.push(Reloc {
    offset: vtbl_offset + T::ptr_bytes() * slot_index,
    symbol: target_function_symbol_index,
    kind: pointer_reloc,
});
```

This is one of three `T::ptr_bytes()`-sized fields in the converter:
vtable slots (relocations + section data layout); typeinfo entries
(may shrink, but the layout is RVA-only — see §4.4); the global
`ptr_str` field for `T *g = "lit";` patterns (today 8 bytes of
zeroes in `.data`, becomes 4 bytes on x86).

### §4.4 — Per-target image-byte differences for the same source

A `static const char *msg = "hello";` global, the 88-fixture corpus
exercises this. On x64, `.data` holds 8 zero bytes; mdlink patches in
the 64-bit absolute address of `"hello"` in `.rdata`. On x86, `.data`
holds 4 zero bytes; mdlink patches in the 32-bit absolute address
(absolute, because PE32's `ImageBase = 0x400000` is fixed — see §5).
The COFF reloc for this field is `Addr64` on x64 and `Addr32` on x86.

The vtable entries similarly: each slot is a pointer; 8 bytes on x64,
4 bytes on x86. `Module.vtables[i].slots` is `Vec<String>` of
function symbols, target-neutral; the converter walks `T::ptr_bytes()`
to compute slot offsets.

The typeinfo entries (Phase H4b RVA-pair encoding) are RVA-based and
fit in 32 bits on both targets; no change.

## §5 — PE32 writer extension

`src/link/pe_writer.rs:1580-1700` writes the PE32+ image. The
extension is largely "everywhere the file says PE32+, branch on
target". The two-target writer becomes:

### §5.1 — Optional-header divergence

| Field                       | PE32+ (x64)        | PE32 (x86)        |
|-----------------------------|--------------------|-------------------|
| `Magic`                     | `0x020B`           | `0x010B`          |
| `SizeOfOptionalHeader`      | `0xF0` (240)       | `0xE0` (224)      |
| `BaseOfData`                | not present        | `u32` (post `BaseOfCode`) |
| `ImageBase`                 | `u64` (0x140000000)| `u32` (0x400000)  |
| `SizeOfStackReserve`        | `u64`              | `u32`             |
| `SizeOfStackCommit`         | `u64`              | `u32`             |
| `SizeOfHeapReserve`         | `u64`              | `u32`             |
| `SizeOfHeapCommit`          | `u64`              | `u32`             |

PE32 = 224-byte optional header; PE32+ = 240-byte. Both include the
128-byte (16 × 8) data-directory array.

### §5.2 — Section alignment + image base

PE32 default `ImageBase = 0x00400000` (4 MiB). With our 4 KiB section
alignment, this puts `.text` at RVA `0x1000` (file `0x400`), exactly
as PE32+ does today. No change in section ordering. Section
characteristics flags are identical (same `IMAGE_SCN_*` bits).

### §5.3 — No `.pdata`/`.xdata` requirement

x64 SEH is table-driven: `.pdata` (RUNTIME_FUNCTION array) + `.xdata`
(UNWIND_INFO) — required for **every function with a non-leaf
prologue** on Win64 (Windows uses the unwind tables for stack
walking, debugger backtraces, etc.). On x86 there is no equivalent;
SEH is fs:[0]-based and entirely per-function, not table-driven.
PE32 has no DataDirectory[3] / IMAGE_DIRECTORY_ENTRY_EXCEPTION.

The PE32 writer simply does not emit `.pdata`/`.xdata` sections.
`Module.funcs[i].try_scopes` is consumed by the SEH3 lowering (§7)
inline into `.text`, not by a separate section.

### §5.4 — `.reloc` base-relocation section

x64 PE32+ images with our fixed `ImageBase = 0x140000000` can request
"no relocations" (PE flag `IMAGE_FILE_RELOCS_STRIPPED` + empty
`.reloc`); if the loader can't honour the requested ImageBase, the
image loads fail. mdbcc-emitted x64 PEs work this way today.

PE32 images with the default `ImageBase = 0x400000` typically need a
`.reloc` section because the loader may relocate them if 0x400000 is
taken. Practically, the loader honours the requested ImageBase for
console + GUI EXEs in most cases, so a minimum-viable PE32 can also
strip relocations (set `IMAGE_FILE_RELOCS_STRIPPED` = 0x0001 in
Characteristics). **S2d takes the same approach as today's x64**:
fixed ImageBase, RELOCS_STRIPPED, no `.reloc` section. Simpler;
matches today's contract.

If WOW64 refuses to load the image (we'll know quickly from O12
runtime tests), S2d falls back to emitting `.reloc`. Filed as
Q-Reloc in §11.

### §5.5 — Subsystem version

PE32 historically uses MajorSubsystemVersion 4 (Win95 / NT 3.51 era).
The 88 fixtures only need to run on Win11 x64 via WOW64. Pin
MajorSubsystemVersion = 4 (per Microsoft's recommendation for
WOW64-targeted PEs that should also run on NT 4 / Win98 — gratuitous
but matches Borland's choice; bcc32-built PEs ship with 4.0).

### §5.6 — Where the writer splits

## §6 — Win32 ABI representation

`src/codegen/abi.rs` today encodes Win64 only. S2b extends it with the
Win32 conventions. The bcc32 4.52 RTL default per `_DEFS.H` is
`__cdecl`; OWL response-tables use Borland-specific `__fastthis`
(deferred); Win32 API callbacks use `__stdcall` via `CALLBACK` /
`WINAPI` macros in `WINDEF.H`.

### §6.1 — The four conventions

| Convention   | Args                        | Stack cleanup | Name decoration              |
|--------------|-----------------------------|---------------|------------------------------|
| `__cdecl`    | All on stack, right-to-left | Caller        | `_foo`                       |
| `__stdcall`  | All on stack, right-to-left | Callee (`ret N`) | `_foo@N` (N = arg bytes)  |
| `__fastcall` | First 2-3 in regs, rest on stack right-to-left | Callee | `@foo@N` (leading `@`)|
| `__pascal`   | All on stack, left-to-right (!!) | Callee | `FOO` (uppercase)         |

### §6.2 — `__cdecl` — the workhorse

Stack layout at call site (caller-side, before `call`):

```
esp+0   arg0  (rightmost arg PUSHed last → at lowest address)
esp+4   arg1
esp+8   arg2
…
```

Args pushed right-to-left, so positional arg 0 ends up at `[esp+0]`
inside the callee. Caller emits `add esp, N` after the call to clean
up. Name decoration: leading underscore (`_foo`). Matches Borland's
`extern "C"` and matches the existing S1b mangling convention for
C-linkage symbols (`borland_c_symbol` in codegen/cpp.rs).

### §6.3 — `__stdcall`

Same arg-passing as cdecl (all on stack, right-to-left); difference
is who cleans:

- Caller: just `call foo`, no `add esp, N` after.
- Callee: `ret N` where N = total arg bytes.

Name decoration: `_foo@N` where N = decimal arg-byte count. So
`__stdcall void f(int, int)` mangles as `_f@8`. `__stdcall int
GetCommandLineA(void)` mangles as `_GetCommandLineA@0`. We already
need this for §5's import table entries — kernel32.dll exports
match the `@N` form.

### §6.4 — `__fastcall` — Borland vs Microsoft

**This is the divergence point Arthur warned about.** Microsoft's
fastcall (the only one defined by the AMD64-pre-era Microsoft spec
and adopted by lld/clang) passes the first two integer args in `ECX`
and `EDX`; rest on stack. Borland's fastcall passes the first **three**
integer args in `EAX`, `EDX`, `ECX` (note the order — EAX first,
not ECX) and is incompatible with Microsoft's at the byte level.

Name decoration also diverges:

- MS fastcall: `@foo@N` (leading + trailing @).
- Borland fastcall: `@foo` (leading @ only; no trailing).

**Honest assessment**: this is from secondary sources and the brief
hints; **not confirmed from a Borland source dump**. The verification
path is mechanical: at S2b.1 start, compile a sample with `bcc32 -3
-DUSE_FASTCALL` and dump the OMF with the existing
`tests/support/omf_walker.rs` reader. The PUBDEF symbol name +
the LEDATA instruction bytes for the function body settle it.

**Mitigation if wrong**: the convention table is a single
function (`Target::arg_load_prefix(slot, conv)`). Changing the
encoding for `__fastcall` is a one-file edit. The encoder table doesn't
care. Filed as Q-Fastcall in §11.

### §6.5 — `__pascal` — defer or include?

`__pascal` reverses arg order (left-to-right push), callee cleans
with `ret N`. Used pre-OWL in the Borland universe (Win16 OWL 1.x
called Windows API as `__pascal`); in 32-bit OWL 2.x it's almost
extinct. The Win32 BCC `_DEFS.H` aliases `_RTLENTRYF = __pascal` only
under `__PAS__` (which is off by default; never set in our corpus).

Recommendation: **skip in S2b; add in S5 if OWL needs it**. The
encoder + ABI machinery is designed for one-line extension; adding
`__pascal` later costs little. Q-Pascal in §11.

### §6.6 — Where the convention comes from (source attribution)

The AST `ast::Function` struct gains a `calling_conv` field:

```rust
// src/ast.rs (proposed delta)
#[derive(Debug, Clone)]
pub struct Function {
    pub name: String,
    pub ret: Type,
    pub params: Vec<(String, Type)>,
    pub c_linkage: bool,                   // S1b.3 (already exists)
    pub variadic: bool,
    pub const_method: bool,
    pub calling_conv: Option<CallConv>,    // S2 (NEW); None => target default
    // … existing fields …
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum CallConv {
    Cdecl, Stdcall, Fastcall, Pascal,
}
```

The parser learns to recognise the four keywords (`__cdecl`,
`__stdcall`, `__fastcall`, `__pascal`) as **declaration specifiers**.
Borland accepts both leading-underscore variants (`_cdecl`, `_stdcall`,
…) and double-underscore variants; both parse to the same `CallConv`.
The keyword can sit in any of the three positions C++ allows:
between the return type and function name, before the type, or
inside a function pointer (`int (__stdcall *fp)(int)`).

For the codegen, when `function.calling_conv` is `None`, the target
default applies (Win64: always Win64 ABI; Win32: cdecl). When it's
`Some(conv)`, the codegen + mangler honour it.

### §6.7 — Caller-side marshalling

The existing `marshal_args` in `codegen.rs` walks parameters from
position 0 → N. For Win32 conventions it inverts the order: pushes
args N-1 → 0 (for cdecl/stdcall/fastcall) or 0 → N-1 (for pascal).
Pseudo-Rust:

```rust
fn marshal_args_win32<T: Target>(
    &mut self,
    args: &[ArgValue],
    conv: CallConv,
) {
    let reg_args = match conv {
        CallConv::Cdecl   => 0,
        CallConv::Stdcall => 0,
        CallConv::Fastcall => 3,  // Borland's variant — Q-Fastcall
        CallConv::Pascal  => 0,
    };
    // For Borland fastcall: first 3 ints → EAX, EDX, ECX.
    for slot in 0..reg_args.min(args.len()) {
        // Emit per Target::arg_load_prefix(slot, conv).
        self.encode(Op::Mov, …);
    }
    // Stack args.
    let stack_args = &args[reg_args.min(args.len())..];
    let stack_iter: Box<dyn Iterator<Item = &ArgValue>> = match conv {
        CallConv::Pascal => Box::new(stack_args.iter()),
        _ => Box::new(stack_args.iter().rev()),
    };
    for arg in stack_iter {
        // push arg
        self.encode(Op::Push, …);
    }
    self.encode(Op::Call, &[Operand::rel32(callee)])?;
    // Caller cleanup for cdecl.
    if conv == CallConv::Cdecl {
        self.encode(Op::Add, &[Operand::reg(Esp),
                               Operand::imm32(stack_args.len() * 4)])?;
    }
}
```

The actual implementation lives in `codegen/abi.rs` / `expr.rs`; this
sketch is illustrative.

### §6.8 — Name decoration ↔ mangler interaction

The Borland C++ mangler in `codegen/cpp.rs` (S1b.3) decorates with
leading `@` (C++ overload) or `_` (C-linkage). For S2:

- `extern "C"` + `__cdecl`  → `_foo`
- `extern "C"` + `__stdcall` → `_foo@N` (N = arg bytes)
- `extern "C"` + `__fastcall` → `@foo` (Borland's no-trailing-N variant)
- C++ + any conv → `@<chain>$q<types>` (the calling conv does NOT
  appear in the mangled name for C++ symbols; it's part of the symbol's
  ABI signature, not its identity).

The mangler logic in `codegen/cpp.rs::borland_c_symbol` extends to
consult `calling_conv` for the C-linkage path; the C++ path is
unchanged. Q-Mangle in §11 confirms the `@N` suffix details for
stdcall (need empirical confirmation from bcc32 emitted OMF).

## §7 — fs:[0] SEH design

x86 SEH (often called SEH3 to distinguish from x64 SEH and SEH4) uses
a thread-local linked list of `EXCEPTION_REGISTRATION` records rooted
at `fs:[0]`. Each function's prologue pushes one record onto the chain;
the epilogue pops it. The chain walks bottom-up at exception time.

### §7.1 — `EXCEPTION_REGISTRATION` layout

```c
struct EXCEPTION_REGISTRATION {
    struct EXCEPTION_REGISTRATION *prev;  // [esp+0]
    void (*handler)(EXCEPTION_RECORD*,    // [esp+4]
                    EXCEPTION_REGISTRATION*,
                    CONTEXT*,
                    void*);
    // — Some C++ runtimes append:
    int scope_index;                       // [esp+8]
    int padding;                           // [esp+12]
    // — Then user-defined fields per scope-index table.
};
```

mdbcc's record is the minimal 8-byte form (prev + handler). Borland
and MSVC both extend it with a scope-index field for catch-block
dispatch; we follow the MSVC convention (8-byte base + 8 bytes scope
state). The scope state for catch handlers is computed from the
existing `TryScope` machinery in `eh.rs`.

### §7.2 — Per-function prologue/epilogue

Today's x64 prologue:
```text
55                         push rbp
48 89 E5                   mov rbp, rsp
48 81 EC ??                sub rsp, imm32
```

x86 prologue with SEH (per HLD `seh3.rs` design):
```text
55                         push ebp
89 E5                      mov ebp, esp
68 [handler RVA]           push imm32        ; handler function ptr
64 FF 35 00 00 00 00       push fs:[0]       ; prev pointer
64 89 25 00 00 00 00       mov fs:[0], esp   ; install new record
81 EC ??                   sub esp, imm32    ; locals
```

Epilogue (when SEH installed):
```text
64 8F 05 00 00 00 00       pop fs:[0]        ; restore prev (8 bytes
                                              ; from chain pop)
83 C4 04                   add esp, 4        ; drop handler-ptr slot
89 EC                      mov esp, ebp
5D                         pop ebp
C3                         ret
```

Functions without try blocks skip the SEH installation; their
prologues are 4 bytes shorter and the chain-pop is omitted. The
target's `seh_kind()` controls whether the prologue emits the SEH
installation at all.

### §7.3 — Personality / handler function

Today's x64 personality function (`build_personality_function` in
`eh.rs:324`) is a 384-byte chunk of hand-emitted x64 that the PE
writer's `.xdata` references. It implements the search-phase
dispatch for `EXCEPTION_MDBCC_INT` and `EXCEPTION_MDBCC_CLASS`.

For x86, we synthesise an **analogous module-wide handler** named
`__mdbcc_seh3_handler`:

```c
// Conceptual; actual implementation is hand-emitted x86 in
// src/codegen/seh3.rs::build_seh3_handler.
EXCEPTION_DISPOSITION __mdbcc_seh3_handler(
    EXCEPTION_RECORD *er,
    EXCEPTION_REGISTRATION *frame,
    CONTEXT *ctx,
    void *dc)
{
    // 1. Check exception code (mdbcc int / class only).
    // 2. Read scope_index from frame->scope_index.
    // 3. Walk the function's scope table (an array of (try_begin,
    //    try_end, handler, policy) records pointed to by the
    //    handler-ptr slot pushed at prologue + 4; see below).
    // 4. For matching scopes, set up RAX as the personality
    //    function expects (int value / buffer pointer) and unwind to
    //    the catch handler PC via RtlUnwind.
    // 5. For non-matching, return ExceptionContinueSearch.
}
```

**Critical structural decision**: the *handler-pointer* the prologue
pushes is NOT the personality function directly — it's a per-function
**handler descriptor** that contains:

```c
struct mdbcc_seh3_handler_desc {
    void *personality;       // points at __mdbcc_seh3_handler
    int scope_count;
    struct mdbcc_seh3_scope {
        int try_begin_off;   // function-relative offsets
        int try_end_off;
        int handler_off;
        int policy_code;     // Int / ByRef class_id / ByPtr class_id / Cleanup
        int catch_type_data; // per-policy auxiliary (vtable RVA for class catches)
    } scopes[];
};
```

The descriptor lives in `.rdata` (one per function with try blocks).
Each function's prologue does `push imm32` of the descriptor address;
the system loader patches the imm32 to the descriptor's absolute VA
via `IMAGE_REL_I386_DIR32`. The handler function reads the descriptor
through frame+4 (the slot just below the prev pointer).

This is the standard Borland / MSVC x86 SEH3 pattern. It looks
different from x64 because x86 has no `.xdata` — the handler
descriptor lives inline as a .rdata blob that the prologue references.

### §7.4 — How scope-table emission shares code with x64

The existing `Module.funcs[i].try_scopes` (a `Vec<TryScope>` from
`eh.rs`) is target-neutral. Today the x64 path lowers it to `.xdata`
scope records (via `pe_writer::build_xdata`). For x86, a new
`src/codegen/seh3.rs::emit_handler_descriptor(&CompiledFn) -> Vec<u8>`
walks the same `try_scopes` and emits the x86 descriptor format into
`.rdata`.

The `Target::seh_kind()` method dispatches at converter time:

- `SehKind::TableX64`: `Module.funcs[i].try_scopes` → `.pdata` +
  `.xdata` (as today).
- `SehKind::Fs0Chain`: `Module.funcs[i].try_scopes` → `.rdata`
  handler-descriptor blob, plus inline SEH installation in each
  function's prologue.

The collected scope tables are identical; only the lowering differs.
This is the trait-driven payoff.

### §7.5 — Real Borland OWL `xthrow.cpp` compatibility

The brief mentions `xthrow.cpp` (Borland's RTL exception-throw
helper). Borland's runtime exception throw on x86 calls
`RaiseException(EXCEPTION_BORLANDCXX, …)` after setting up a
"throw object" record. Our personality function recognises the
mdbcc-specific exception codes (`EXCEPTION_MDBCC_INT = 0xE0000001`,
`EXCEPTION_MDBCC_CLASS = 0xE0000002`); to interop with Borland's
RTL we'd need to also recognise Borland's code (`0xEEEEEEEE`-ish per
external dumps, **unverified — empirical step in S5**).

For S2 we **stay with our own codes** (the 88 fixtures don't link
Borland's RTL). When S5 builds OWL from source, the `xthrow.cpp`
runtime calls our `__throw` helper instead of Borland's; we control
both ends of the throw and our codes work end-to-end.

If S5 needs to *receive* a Borland-RTL-throw (e.g. some OWL
internal calls `RaiseException` directly), we extend the personality
function — one more `cmp eax, 0xBORLANDCODE` branch. Bounded.

## §8 — Sub-phase ordering + parallelism map

The S2 work splits into five sub-phases; the dependency graph
allows parallelism:

```
         S2a (encoder)
                |
                ↓
S2c (i386 COFF) ─┬─→ S2b (Win32 ABI) ─→ S2e (SEH3) ─→ S2-exit
                |                       ↑
                └─→ S2d (PE32 writer) ──┘
```

Concretely: S2a (encoder table-build) and S2c (i386 COFF retarget)
can dispatch as parallel subagents on day 1 — they touch disjoint
files (codegen/encoder/ + coff.rs respectively). When both return,
S2b (Win32 ABI in codegen/abi.rs) and S2d (PE32 writer in
link/pe_writer.rs) dispatch in parallel. S2e (SEH3) closes last
because it depends on all the others.

| Sub-phase | Name                                | Inputs                | LoC estimate | Oracle gate                                           |
|-----------|-------------------------------------|-----------------------|-------------:|-------------------------------------------------------|
| S2a       | Table-driven encoder                | This HLD              | ~1500 LoC    | All 88 x64 fixtures byte-identical (SipHash stripe)   |
| S2b       | Win32 ABI in codegen/abi.rs         | S2a                   | ~1200 LoC    | `__cdecl` corpus subset: 30 int-only fixtures compile + run |
| S2c       | i386 COFF (retarget RelocKind)      | This HLD              | ~400 LoC     | New `tests/coff_i386_format.rs`: round-trip + lld-link accepts |
| S2d       | PE32 writer                          | S2c                   | ~800 LoC     | Hello-world int main exits 42 as native i386 PE32     |
| S2e       | x86 SEH (fs:[0] chain)               | S2b + S2d             | ~2200 LoC    | EH test corpus rebuilt as x86: try/throw/catch passes |
| S2-exit   | O12 88-fixture corpus               | All above             | ~200 LoC     | ≥80 / 88 corpus fixtures match bcc32 reference exit + stdout |

Total LoC delta: ~6000 (codebase grows from ~30000 to ~36000). Per
S1c precedent the coverage stripe will dip ~1-2 pp at S2 close;
re-baseline in S3 when real headers add their own tests.

Parallel dispatch is feasible per S1b precedent — S1b.2 / S1b.3
ran concurrently and both came back green. The S2c / S2a parallel is
even safer because they're in completely disjoint trees.

## §9 — Oracle plan

### §9.1 — O12 source-to-behaviour vs bcc32 (the headline)

`tests/oracle_o12_x86_runtime.rs` (new). Per fixture from the 88-fixture
corpus that's tagged "x86" or "both" (Q-Corpus in §11 picks the
mechanism):

1. Compile source with `bcc32 + tlink32` → reference PE.
2. Compile source with `mdbcc -m32 -c + mdlink -m32` → mdbcc PE.
3. Run both on Win11 x64 via WOW64.
4. Compare:
   - Exit codes match exactly.
   - Stdout matches (whitespace-tolerant compare; some printf
     formatting differences are acceptable).

Pass when ≥80 / 88 fixtures match. The remainder is flagged for
investigation. Skip loudly if the bcc32 oracle is absent.

### §9.2 — O14-Half-A finally lights up

S1c.6 implemented OMF reading but couldn't actually link OMF → PE
because the PE writer was AMD64-only. Task #35 in the S1 close
journal explicitly defers the O14-A runtime gate to S2.

With S2d in place, O14-Half-A is:

`tests/oracle_o14_omf_to_pe_runtime.rs`: bcc32-compiled `.obj` (OMF
i386) → `mdlink -m32` → PE → runs → exit matches bcc32+tlink32
reference. **This is the killer oracle.** No more "we can't drift
silently from Borland" hand-waving.

### §9.3 — O1 byte-identity stripe forks

- **x64 stripe (existing)**: 88 SipHash baselines in
  `tests/o1_byte_identity.rs` continue to lock the Win64 path. S2
  must not break these.
- **x86 stripe (new)**: `tests/o1_x86_byte_identity.rs` adds a parallel
  stripe of 88 SipHash baselines for `mdbcc -m32` compiled binaries.
  Re-bless workflow same as the existing stripe.

The fixture sources are shared. The build commands differ. The
SipHash baselines are independent.

### §9.4 — Corpus tagging

`tests/corpus_tags.rs` (new — see Q-Corpus in §11). Each fixture is
tagged "x64", "x86", or "both":

```rust
const CORPUS_TAGS: &[(&str, &[Arch])] = &[
```

## §10 — Risk register

Per May-26 plan §7 (R1-R12) + S1b/S1c HLDs (R13-R20). New risks
specific to S2:

- **R21 — Borland `__fastcall` divergence from MS**. The
  EAX/EDX/ECX-first-three vs ECX/EDX-first-two distinction may be
  wrong in my understanding (see §6.4). **Mitigation**: empirical
  verification at S2b.1 start; rectifying is a one-file edit.
- **R22 — fs:[0] chain corruption under abnormal exits**. The
  prologue installs the SEH record; the epilogue pops it. If
  abnormal control flow (longjmp, alloca followed by stack
  overflow, `return` from inside a `try` body that bypasses
  cleanup) leaves the chain corrupted, the next exception walks
  garbage. **Mitigation**: S2e includes a `tests/seh3_corruption_
  edge_cases.rs` test suite (longjmp, nested try, exception in
  destructor, etc.). MSVC's runtime handles this by being defensive
  in the handler; we follow the same pattern.
- **R23 — pointer-size assumptions in the test harness**. The 88
  e2e tests assume `sizeof(int) == 4` (true for both x64 and x86 on
  Windows) but ALSO sometimes implicitly assume `sizeof(void*) ==
  8`. If a fixture does `printf("%p", &x)` and asserts stdout
  content, the x86 build differs from x64 (`0x0019ff34` vs
  `0x000000fdb8b6f9c0`). **Mitigation**: corpus tagging excludes
  pointer-format fixtures from the x86 oracle; ~18 of 88 will be
  x64-only-tagged per §9.4.
- **R24 — Variadic-int promotion differences**. C promotes `short`
  to `int` on call; on x86 `int` is 4 bytes, on x64 with our model
  also 4 bytes. **Same width**. No risk.
- **R25 — Long division / `__ftol` helpers**. bcc32's RTL provides
  `__ftol` for double → long conversion; on x86 it's a call into the
  helper. mdbcc inlines `cvttsd2si` on x64. For x86 we need to either
  (a) emit `cvttsd2si` (works on x86 too with SSE2) or (b) match
  bcc32 by emitting a call to `__ftol`. **Recommendation**: stay
  with `cvttsd2si` for byte-identity with x64; OK because SSE2 is
  required for Win11 x64 anyway and WOW64 supports SSE2 in 32-bit
  processes.
- **R26 — Multiple PE writers diverge**. Two parallel PE writers
  (`write_pe32_*` + `write_pe32plus_*`) risk one moving forward
  without the other. **Mitigation**: shared helpers for DOS stub,
  section-header emission, data-directory layout. ~70% of the PE
  writer is shared; per-target is just optional header + reloc
  emission.
- **R27 — Encoder table regression risk**. Replacing 800 hand-rolled
  byte literals with a table risks subtle off-by-one (wrong ModR/M,
  missing REX, etc.). **Mitigation**: S2a.2 is "drive Win64 codegen
  entirely through the new table, all 88 e2e SipHash baselines stay
  green". This is the regression lock; if a single byte shifts it
  fails immediately.
- **R28 — SEH and EH testing infrastructure on WOW64**. We need to
  actually run i386 EH code on Win11 x64 (via WOW64). WOW64's SEH
  implementation has some known quirks (no STATUS_HALT propagation
  semantics, restricted continuation contexts). **Mitigation**: S2e
  test suite runs against WOW64; differences from native NT 4 SEH
  semantics are documented as expected.

## §11 — Open questions for Arthur (Q-list)

**Q-Table — Encoder format**: ratify the inline-`const` Rust-array
choice over alternatives:
- TOML / build-script (parsing at `build.rs` time, generating Rust
  source) — pro: easier to edit non-programmers; con: opaque to
  `cargo check` until generated, breaks IDE jump-to-def.
- Builder DSL (procedural macro emitting the table) — pro: type-safe
  construction; con: macro complexity is high and review-unfriendly.

**Recommendation**: inline Rust `const` arrays. Matches house style
(`WIN32_IMPORTS`, `SECTION_NAMES`, …); editable in any Rust IDE;
trivially diffable. The macro-based / TOML-based approaches buy
nothing over a well-structured Rust file.

**Q-Corpus — fixture tagging**: should the existing 88 fixtures
**auto-rebuild** as x86 (corpus implicitly doubles to 176 SHA-256
baselines, with x86 builds expected to diverge from x64 on the
~18 pointer-format / size_t fixtures) or should fixtures be
**manually tagged** "x64" / "x86" / "both" per §9.4 with explicit
oracle runs only over `x86`-tagged fixtures?

**Recommendation**: manual per-fixture tagging. The 18 pointer /
%p / size_t fixtures are not "x86 is broken" — they're "x86 produces
different stdout from x64 for principled reasons, which is fine".
Auto-rebuild would produce noisy false failures. Manual tagging is
~50 lines of tag table.

**Q-Fastcall — empirical confirmation**: do you confirm that
Borland's `__fastcall` differs from MS's (EAX/EDX/ECX vs ECX/EDX), and
that we'll derive the actual encoding empirically at S2b.1 start
(compile sample with bcc32, dump OMF, observe)?

**Recommendation**: yes, derive empirically. The encoding lives in a
single `Target` method; rectifying is a 5-line edit.

**Q-Pascal — `__pascal` in S2 or defer to S5?** §6.5 recommends
deferring (no in-scope corpus references it). OWL 2.5 may or may not.
Honest answer: OWL 2.5 uses macros like `_USERENTRY`/`CALLBACK` that
expand to `__cdecl` / `__stdcall` on Win32; `__pascal` is essentially
extinct.

**Recommendation**: defer. S5 brings it back if needed.

**Q-Driver — `-m32` flag or `mdbcc32` binary?** Borland shipped two
binaries (`bcc.exe` for DOS/Win16, `bcc32.exe` for Win32). We can
mirror that (`mdbcc32` separate binary) or use a flag (`mdbcc -m32`).

**Recommendation**: single binary with `-m32` flag. Easier to maintain;
the dispatch lives in `main.rs` and routes to the same
`compile_to_object<T>` for both targets.

**Q-Reloc — emit `.reloc` section?** §5.4 recommends matching the
existing Win64 contract (fixed ImageBase, RELOCS_STRIPPED, no
`.reloc`). If WOW64 refuses to load `ImageBase = 0x400000`, fall
back to emitting `.reloc`. **Recommendation**: skip in S2; revisit
if O12 runtime tests show load failures.
