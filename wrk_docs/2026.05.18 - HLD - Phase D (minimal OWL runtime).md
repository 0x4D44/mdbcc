# HLD — Phase D: Minimal OWL runtime v1 ("Hello OWL window")

Date: 2026-05-18. Status: DESIGN (Phase A/B/C landed; impl-ready).
Roadmap: `wrk_journals/2026.05.17 - PLAN - OWL Windows roadmap.md`
(**Phase D section is authoritative scope**; obeys decisions
**D-1** reimplement a faithful OWL subset in Borland-dialect C++
compiled by mdbcc, **D-2** classic non-template OWL 2.5, **D-3**
oracle = O6 GUI-liveness + screenshot, no Borland-OWL behavioural
differential). Charter:
`wrk_journals/2026.05.18 - PLAN - Goal loop charter.md`.
Depends on Phase A (>4-arg Win64 stack ABI, `&func`/`RipRef::Func`,
indirect call), Phase B (vtables / virtual dispatch / virtual dtor),
Phase C (multi-DLL imports, subsystem-2 + `WinMain` stub, intrinsic
`<windows.h>`, `WIN32_IMPORTS`/`emit_win32_call`, O6 harness). All
reused; **none modified** except the small, in-style table/header/
harness growths Phase C explicitly reserved for Phase D.

## Why

Phase C made a GUI Win32 PE *buildable and runnable* (it loads,
imports USER32, shows a `MessageBoxA`, exits cleanly under O6). It
deliberately shipped **no window class, no message loop, no OWL**.
Phase D is the first *real OWL milestone*: an unmodified Borland-API
source

```cpp
#include <owl/applicat.h>
#include <owl/framewin.h>
class TMyApp : public TApplication {
public:
  TMyApp() : TApplication() {}
  void InitMainWindow() {
    SetMainWindow(new TFrameWindow(0, "Hello OWL"));
  }
};
int OwlMain(int /*argc*/, char* /*argv*/[]) {
  return TMyApp().Run();
}
```

compiles with `mdbcc`, and the resulting Win64 PE opens a real
top-level framed window on Windows 11 and exits cleanly when closed.
Per **D-1** the `owl/*.h` headers and the OWL runtime are *our own*
faithful Borland-public-API subset, **written in the Borland-dialect
C++ mdbcc already compiles** — there is no external OWL object to
link; the runtime is just more translation-unit C++. Per **D-3** the
GUI layer's only oracle is O6 liveness + an `mdscreensnap` golden;
the language features *under* OWL (classes, vtables, fn-pointers,
the Win64 ABI) stay fully O1/O2/O3-validated from Phases A/B and are
**not re-derived here**.

Non-negotiable constraint, identical in form to Phase A/B/C: **the
console path stays byte-identical**. O1 `tests/end_to_end.rs` (88,
authoritative) stays green and byte-identical; every Phase D addition
fires *only* when an OWL/GUI program is compiled (a console program
defines no `WinMain`/`OwlMain`, includes no `owl/*.h`, references no
new USER32 symbol ⇒ provably unchanged `.idata`, stub, and image).

## Current capabilities to build on (read 2026-05-18, grounded)

Phase D is **codegen-complete on the language side** — it adds *no*
new codegen feature. It is almost entirely (a) OWL C++ source we
author and (b) the small Win32-surface growths Phase C pre-scoped.

### Language / codegen (Phase A/B — reused verbatim, NOT changed)
- **Virtual dispatch & vtables** (Phase B, `src/codegen.rs`): a
  polymorphic class gets a hidden vptr at offset 0; `p->m(a)` on a
  virtual `m` lowers to `mov rax,[this]; mov rax,[rax+slot*8]; call
  rax`; virtual dtor takes a slot; ctor stores the vtable via
  `RipRef::Vtable` (`src/codegen.rs:147`,`:180`). This *is* the
  TApplication/TWindow `virtual InitMainWindow`/`HandleMessage`
  mechanism — no new work.
- **Function pointers + address-of-function**: `Type::Func`, `&func`
  / bare-function-name materialised via `RipRef::Func`
  (`src/codegen.rs:144`) as `lea reg,[rip+disp32]`; indirect call
  `emit_indirect_call` (`src/codegen.rs:1604`) reuses the Win64
  register+>4-arg-stack marshalling. This is exactly how the static
  `WndProc`'s address is handed to `RegisterClassExA` and how
  Windows' indirect call back into it is ABI-correct.
- **>4-arg Win64 ABI** (`emit_call`/`emit_indirect_call`): args 1-4
  in RCX/RDX/R8/R9, args ≥5 at `[rsp+32+8*(i-4)]`, 16B-aligned
  frame, 32B shadow (Phase A). `CreateWindowExA` = 12 args — already
  covered and three-way O2/O3-locked by `tests/corpus/portable/manyargs.c`.
- **Struct/Record types & member access** exist (`parser.rs` `Record`,
  field offsets; `gen_addr` on field/`->`). **Struct-by-value
  params/returns are NOT supported** (`src/codegen.rs:468-470`,
  `:1055-1057` hard error "struct/union by value is not yet
  supported"). *Every* Win32 struct API Phase D needs
  (`RegisterClassExA(&wc)`, `GetMessageA(&msg,…)`,
  `CreateWindowExA(…)`, `DispatchMessageA(&msg)`) takes a
  **pointer** to the struct — so this limitation does not bite
  Phase D. Recorded so D does not accidentally rely on by-value.

### Win32 substrate (Phase C — the two seams Phase D grows)
- **`WIN32_IMPORTS`** (`src/pe.rs:80-94`): the 6 KERNEL32 symbols
  (must stay first/in order — console byte-identical golden) +
  `("MessageBoxA","USER32.dll")`. `is_win32_import` (`src/pe.rs:102`)
  is the shared source of truth. `used_dlls`/`used_symbol`
  (`src/pe.rs:131`,`:159`) emit a DLL descriptor **iff a
  `RipRef::Import` references one of its symbols** (or it is
  `STUB_DLL`=KERNEL32) — so appending USER32/GDI32 symbols here is
  *dormant for a console program* (no reference ⇒ no descriptor ⇒
  `.idata` byte-identical; locked by `tests/pe_imports.rs`).
- **Win32 call path**: `gen_call` → `is_win32_import(name) &&
  !TU-defines-it` → `emit_win32_call` (`src/codegen.rs:1575-1576`,
  `:1934`) emits `emit_riprel(&[0xFF,0x15], RipRef::Import(name))`
  (indirect `call [rip+IAT]`), args via the Phase-A path. **Adding a
  symbol to `WIN32_IMPORTS` is the *entire* mechanism for calling a
  new Win32 API** — no per-API codegen. Override rule: a user (or
  OWL-runtime) function of the same name wins (falls through to the
  normal unit call) — same precedent as libc.
- **Intrinsic `<windows.h>`** (`src/pp.rs:56-77`, `WINDOWS_H`):
  `UINT/DWORD/BOOL`, `HANDLE/HWND/HINSTANCE/HMODULE/HMENU` (=`void*`,
  8), `LPSTR/LPCSTR`, `WPARAM`(u64)/`LPARAM`(i64)/`LRESULT`(i64),
  empty `WINAPI/CALLBACK/WINAPIV`, `CONST`, `MB_*`. Resolved only
  for the literal `windows.h` (`src/pp.rs:92-94`); every construct is
  plain `typedef`/object-macro the parser already handles. **No
  structs** (`MSG`/`WNDCLASSEXA`/`POINT`/`RECT`), **no `WM_*`/`WS_*`/
  `CW_USEDEFAULT`/`SW_*`/`IDC_*`/`CS_*`** yet — Phase C deferred
  these to Phase D "added there with their members when codegen can
  use them" (`src/pp.rs:54` comment; Phase C HLD §Deferred).
- **GUI entry stub** (`src/pe.rs:512-533`, `GUI_STUB_LEN=0x28`):
  `WinMain` detected by `compile_module` (`src/codegen.rs:347-358`,
  `Entry::GuiWinMain`); stub passes `hInstance=IMAGE_BASE`,
  hPrev=0, lpCmdLine=0, nCmdShow=1 (SW_SHOWNORMAL), `call WinMain`,
  `mov ecx,eax`, `call [rip+ExitProcess]`. **`hInstance` == the PE
  image base** is a *load-bearing fact* for Phase D (see D2).
- **No global constructors / no CRT init** (confirmed:
  `compile_module` only emits *constant* global initializers,
  `src/codegen.rs:330-336`,`:410`; the GUI stub is the entire CRT —
  "no atexit, no global ctors-via-CRT", Phase C HLD §C2). **This is
  the single hardest Phase D design constraint** and is resolved in
  D3 *within* D-1..D-3 scope (no escalation).
- **O6 harness** (`tests/gui.rs`): structural half (always-on,
  headless-safe — parses subsystem==2 + import descriptors/ILT) +
  liveness half (desktop-gated, `FindWindowA` by exact caption →
  `PostMessageA(WM_CLOSE)` → bounded `WaitForSingleObject`, watchdog
  `TerminateProcess`, RAII `ProcHandle` backstop). Phase D extends
  this file with an OWL-app analogue (a *real* `CreateWindowExA`
  window, not a `MessageBoxA`).

## Design

Phase D = **the OWL runtime (Borland-dialect C++ we author) + the
two Win32 seams it forces open + a real message loop + the WndProc
thunk→instance dispatch + O6-for-OWL**. Five design sub-areas
(D-a … D-e) then increment sequencing (D1..D6). Every sub-area is
the *smallest* faithful subset that runs the hello-window; every one
is dormant for a console program (byte-identical regression as
Phase A/B/C).

### D-a — Win32 surface growth (the Phase-C seams, `src/pe.rs` + `src/pp.rs`)

**(1) `WIN32_IMPORTS` (USER32) — only the hello-window set.**
Append, after `MessageBoxA`, *exactly* the symbols the OWL runtime
emits for one framed window with a working close — no speculative
surface (house style; Phase C §Deferred said "appends the rest of
the USER32/GDI32 set *when its codegen emits them*"):

```
("RegisterClassExA","USER32.dll"), ("CreateWindowExA","USER32.dll"),
("ShowWindow","USER32.dll"),       ("UpdateWindow","USER32.dll"),
("GetMessageA","USER32.dll"),      ("TranslateMessage","USER32.dll"),
("DispatchMessageA","USER32.dll"), ("DefWindowProcA","USER32.dll"),
("PostQuitMessage","USER32.dll"),  ("LoadCursorA","USER32.dll"),
("SetWindowLongPtrA","USER32.dll"),("GetWindowLongPtrA","USER32.dll"),
```

That is the irreducible set: register a class (`RegisterClassExA`),
make the window (`CreateWindowExA`), show it (`ShowWindow` +
`UpdateWindow`), pump (`GetMessageA`/`TranslateMessage`/
`DispatchMessageA`), default-handle (`DefWindowProcA`), quit on
destroy (`PostQuitMessage`), a cursor so the class is well-formed
(`LoadCursorA`), and the instance-map primitives
(`Set`/`GetWindowLongPtrA`, see D-c). **No `GDI32`** — a blank
`WS_OVERLAPPEDWINDOW` needs no painting (the default class
background brush erases it); GDI is Phase E/G (explicit deferral).
`GetModuleHandleA` is already used by the GUI stub's design space
(KERNEL32, no new DLL) — the runtime uses the stub-provided
`hInstance` instead (D2), so it is *not* added unless the runtime
actually emits it. **Dormancy:** a console program references none
of these ⇒ `used_dlls` still yields `["KERNEL32.dll"]` ⇒ `.idata`
byte-identical (the `tests/pe_imports.rs` golden is the executable
proof, unchanged).

**(2) Intrinsic `<windows.h>` growth (types/constants half).**
Phase C's `WINDOWS_H` body grows by the structs+constants the OWL
runtime's own C++ names (it is *data*, not a code change — same
mechanism Phase C proved; the parser already does `struct{…}`,
`typedef`, object macros). Add **only** what the runtime source
references:

- Structs (members in the exact Win64 layout; pointers passed by
  `&`, never by value — matches the struct-by-value limitation):
  - `POINT { LONG x, y; }`, `RECT { LONG left,top,right,bottom; }`
    (`typedef long LONG;` — LLP64 `long`==32, `parser.rs`).
  - `MSG { HWND hwnd; UINT message; WPARAM wParam; LPARAM lParam;
    DWORD time; POINT pt; }` (natural Win64 offsets; the loop only
    reads/writes whole `MSG` via `&msg`).
  - `WNDCLASSEXA { UINT cbSize; UINT style; WNDPROC lpfnWndProc;
    int cbClsExtra; int cbWndExtra; HINSTANCE hInstance; HICON
    hIcon; HCURSOR hCursor; HBRUSH hbrBackground; LPCSTR
    lpszMenuName; LPCSTR lpszClassName; HICON hIconSm; }`.
- Typedefs: `typedef void* HICON; typedef void* HBRUSH; typedef
  void* HCURSOR;` `typedef LRESULT (CALLBACK* WNDPROC)(HWND,UINT,
  WPARAM,LPARAM);` (`CALLBACK` is already empty — one Win64 ABI;
  the fn-pointer typedef is exactly Phase A's `Type::Func` form).
  `typedef __int64 LONG_PTR;` / `LRESULT`-shaped for the
  `SetWindowLongPtr` API.
- Constants (object macros): `WM_DESTROY 0x0002`, `WM_CLOSE 0x0010`,
  `WM_CREATE 0x0001`, `WS_OVERLAPPEDWINDOW 0x00CF0000`,
  `WS_VISIBLE 0x10000000`, `CW_USEDEFAULT 0x80000000`,
  `SW_SHOWNORMAL 1` (alias `SW_SHOW 5`), `IDC_ARROW 32512`,
  `GWLP_USERDATA -21`, `COLOR_WINDOW 5`, `CS_HREDRAW 0x0002`,
  `CS_VREDRAW 0x0001`. **Exactly these** — no `WM_PAINT`/menu/
  dialog/`WS_CHILD` (Phase E/G). `CW_USEDEFAULT` is `0x80000000`
  (the documented Win32 value; passed as an `int` arg — fits the
  existing int ABI).

Scope discipline (verbatim house style): the header grows by the
*set the hello-window OWL source literally names and no more*; every
addition maps to a parser construct already exercised; `windef.h`/
`winuser.h` aliases added only if an `owl/*.h` `#include`s them.

### D-b — `owl/*.h` public API surface + the OWL runtime (Borland-dialect C++, **compiled by mdbcc**, per D-1)

The runtime is **not Rust and not a code change** — it is C++ source
files mdbcc compiles like any TU. Two questions: *where do they
live* and *what shape*.

**Provisioning the headers/runtime (the one real packaging
decision, made here — not a fork).** mdbcc must find `<owl/...>`.
Reuse the **exact Phase-C intrinsic-header mechanism**: extend
`DefaultResolver::resolve` (`src/pp.rs:90`) so a system include whose
name starts `owl/` resolves to a built-in body (a `const` table of
`(name, bytes)` next to `WINDOWS_H`, same pattern, same determinism).
The OWL **runtime implementation** (the non-inline bodies:
`TApplication::Run`, the message loop, `TWindow::Create`, the static
`WndProc`) is provided as an **intrinsic OWL implementation TU
prepended to the user's source** when any `owl/*.h` is included
(a single `const OWL_RUNTIME: &[u8]` C++ blob, concatenated ahead of
the user TU by the driver — mdbcc is single-TU, so "link the OWL
runtime" = "compile it in the same TU"; this is the minimal,
in-style realisation of D-1 and needs *no linker*). Rationale: keeps
D-1's "real app source unmodified" (the app just `#include
<owl/applicat.h>` as on Borland) without inventing a multi-TU/lib
system (counter-goal; not needed for v1). The body is plain
Borland-dialect C++ within the Phase-A/B subset.

> Honest note: bundling the runtime as an intrinsic prepended TU
> (vs. a real `owl.lib`) is a *simplification*, not a fidelity loss
> for v1 — the *source the app sees* is byte-for-byte the Borland
> public API. A real separable library is a later concern (Phase I
> if a target app needs separate compilation); recorded as an
> explicit deferral, **not** an Arthur fork (D-1 already chose
> "reimplement a subset compiled by mdbcc"; this is just *how*).

**Class shapes (classic non-template OWL 2.5, D-2; minimal faithful
subset).** Single inheritance only (Phase B supports exactly that;
OWL-2.5 MI/mixins are a Phase-B-flagged deferral — not needed for
the hello-window). vptr-at-0 from Phase B gives the virtual dispatch
for free.

- **`TModule`** — base of `TApplication`. Holds `HINSTANCE hInstance;`
  Public API as Borland: ctor, `HINSTANCE GetInstance() const`.
  Minimal: it exists so `TApplication : public TModule` matches the
  real hierarchy and `hInstance` lives in the right place.
- **`TApplication : public TModule`** —
  - data: `TWindow* MainWindow;` (raw pointer; OWL-2.5 owns it).
  - `TApplication(const char* name=0)` — stores name; sets
    `hInstance` from the **global app instance** (see D3 init).
  - `virtual bool InitApplication()` — default returns true.
  - `virtual bool InitInstance()` — default: calls
    `InitMainWindow()`, then `MainWindow->Create()` and
    `MainWindow->Show(SW_SHOWNORMAL)`. Returns success.
  - `virtual void InitMainWindow()` — **default empty; the app
    overrides it** (the hello app's one override) to
    `SetMainWindow(new TFrameWindow(0,"…"))`.
  - `void SetMainWindow(TWindow* w)` — `MainWindow = w;`.
  - `virtual int Run()` — `InitApplication(); InitInstance();` then
    **the message loop** (see D-d); returns `msg.wParam`.
  - `int MessageLoop()` — the `GetMessageA`/`TranslateMessage`/
    `DispatchMessageA` pump, factored so `Run` is small.
- **`TWindow : public TStreamableBase`** — *no* streamable base in
  v1 (TStreamable is OWL persistence, deep + unneeded); `TWindow` is
  the polymorphic root we need:
  - data: `HWND HWindow; TWindow* Parent; const char* Title;
    const char* WndClassName;`
  - `TWindow(TWindow* parent, const char* title=0)` — stores;
    `HWindow=0`.
  - `virtual ~TWindow()` — virtual dtor (Phase B); v1 body trivial
    (the window is destroyed by Windows on close; no `DestroyWindow`
    needed for the single main window — recorded).
  - `virtual const char* GetClassName()` — returns a fixed class
    name (e.g. `"OWLWindow"`); `TFrameWindow` may override.
  - `virtual void GetWindowClass(WNDCLASSEXA& wc)` — fills `wc`
    (style `CS_HREDRAW|CS_VREDRAW`, `lpfnWndProc=&StaticWndProc`,
    `hInstance`, `hCursor=LoadCursorA(0,IDC_ARROW)`,
    `hbrBackground=(HBRUSH)(COLOR_WINDOW+1)`, `lpszClassName=
    GetClassName()`, `cbSize=sizeof(WNDCLASSEXA)`, rest 0). Virtual
    so `TFrameWindow`/Phase-E subclasses can customise — faithful to
    OWL.
  - `bool Register()` — idempotent `RegisterClassExA(&wc)` (ignore
    "class already exists" — standard OWL behaviour; v1 may just
    register unconditionally and rely on Windows' benign re-register
    error, recorded).
  - `virtual bool Create()` — `Register()`, then
    `HWindow = CreateWindowExA(0, GetClassName(), Title,
    WS_OVERLAPPEDWINDOW, CW_USEDEFAULT,CW_USEDEFAULT,
    CW_USEDEFAULT,CW_USEDEFAULT, Parent?Parent->HWindow:0, 0,
    hInstance, this)` — **`this` is passed as the
    `lpCreateParams`/`lParam`** so the static thunk can bind
    HWND→`TWindow*` (D-c). Returns `HWindow!=0`.
  - `void Show(int cmd)` — `ShowWindow(HWindow,cmd);
    UpdateWindow(HWindow);`.
  - `virtual LRESULT WindowProc(UINT msg, WPARAM w, LPARAM l)` —
    the **instance** dispatcher: `WM_DESTROY ⇒ PostQuitMessage(0);
    return 0;` else `return DefWindowProc(msg,w,l);` (the OWL
    public virtual a Phase-E response-table sits on top of — v1
    handles only `WM_DESTROY`, everything else defaults).
  - `virtual LRESULT DefWindowProc(UINT msg, WPARAM w, LPARAM l)` —
    `return DefWindowProcA(HWindow,msg,w,l);` (virtual, as OWL).
- **`TFrameWindow : public TWindow`** — for v1 a thin specialisation:
  ctor `TFrameWindow(TWindow* parent, const char* title)` →
  `TWindow(parent,title)`; may override `GetClassName()` →
  `"OWLFrame"`. (Real OWL `TFrameWindow` adds client-window/menu/
  accelerator/decoration plumbing — **all deferred to Phase E/G**;
  v1 `TFrameWindow` *is* a plain framed top-level window, which is
  exactly the hello milestone.)
- **`OwlMain`** — Borland's OWL entry (replaces `WinMain`/`main`).
  Provided by the runtime: an actual `int WinMain(HINSTANCE,
  HINSTANCE,LPSTR,int)` (Phase-C-detected ⇒ subsystem 2 + GUI stub,
  *reused unchanged*) whose body sets the global app instance/
  hInstance (D3) then `return OwlMain(0, 0);` (argc/argv = 0/NULL in
  v1 — `lpCmdLine` is already NULL from the Phase-C stub; real
  `GetCommandLineA`/argv is the same explicit deferral Phase C
  made). The **user writes `OwlMain`**, never `WinMain` — matching
  Borland exactly, so app source is unmodified.

All of the above is within the Phase-A/B C++ subset: single
inheritance, virtual methods/dtor, `new`, raw pointers, member
functions, `&function`, fn-pointer typedef, struct pointers. **No
templates, no exceptions/TXOwl, no member-fn-pointers, no
response-table macros** (D-2 + Phase E). If a needed construct turns
out to be outside the subset, that is an *implementation* finding
for the D-d/D-e increment, not an architectural fork (the subset was
chosen by D-2 precisely to avoid forks).

### D-c — The WndProc static-thunk → instance dispatch (the heart of Phase D)

A window class needs a `static LRESULT CALLBACK WndProc(HWND,UINT,
WPARAM,LPARAM)` (a *free function* address — Windows calls it
indirectly). It must recover the `TWindow*` for that `HWND` and
invoke the **virtual** `WindowProc`.

**ABI correctness (why a normal mdbcc function is a valid
`WNDPROC`).** mdbcc emits exactly one calling convention: standard
**Win64** (RCX/RDX/R8/R9 then stack, 32B shadow, 16B-aligned `rsp`
at `call`, callee-cleanup, return in RAX) — Phase A, three-way
O2/O3-validated. The Win64 `WNDPROC` signature *is*
`LRESULT(HWND,UINT,WPARAM,LPARAM)` = 4 register args, 8-byte
integer/pointer each, 8-byte return — i.e. **exactly what an mdbcc
4-arg function already emits**. There is no `__stdcall` name
decoration in x64 (`CALLBACK`/`WINAPI` are empty `#define`s,
correct for Win64 — Phase C §Deferred recorded this so D would not
reintroduce a 32-bit assumption). When `USER32!DispatchMessageA`
calls our thunk, it pushes a return address and enters with
`rsp` 16-aligned-minus-8 and 32 bytes of caller shadow — the
**exact contract every mdbcc-emitted call site already satisfies and
every mdbcc prologue already assumes** (Phase A's invariant). The
thunk's address is materialised by Phase A `&StaticWndProc`
→`RipRef::Func` (`lea`/stored into `WNDCLASSEXA.lpfnWndProc`); the
linker fills its text RVA exactly as for any function pointer. ⇒
**No new ABI, no thunk codegen — a plain `static` member/free
function is a conformant WNDPROC by construction.** (Asserted by O6
actually letting Windows call it; a wrong ABI faults on the first
message.)

**HWND → `TWindow*` map mechanism — decision: `SetWindowLongPtrA`/
`GWLP_USERDATA`, NOT a global table.** Rationale, reconciled with
*no global constructors*:
- A global side table (`std::map`-like) would need either a global
  object with a constructor (mdbcc has **none** —
  `src/codegen.rs:410`) or a mutable global with first-use init +
  its own allocation. `GWLP_USERDATA` is **per-window storage
  Windows itself provides** — zero global state, no ctor, no
  allocation, O(1), and is *precisely the classic OWL/Petzold
  mechanism*. It is strictly less machinery → the house-style
  choice.
- **Binding sequence (the subtle part), handling that early
  messages arrive before `CreateWindowExA` returns:**
  1. `Create()` passes `this` as the last `CreateWindowExA` arg
     (`lpParam`). Windows delivers it in `WM_NCCREATE`/`WM_CREATE`
     via `((CREATESTRUCT*)lParam)->lpCreateParams`.
  2. The static `StaticWndProc(hwnd,msg,w,l)`:
     - If `msg==WM_NCCREATE` (or `WM_CREATE`): `self =
       (TWindow*)((CREATESTRUCTA*)l)->lpCreateParams;`
       `SetWindowLongPtrA(hwnd, GWLP_USERDATA, (LONG_PTR)self);`
       `self->HWindow = hwnd;` then fall through to dispatch.
     - Else: `self = (TWindow*)GetWindowLongPtrA(hwnd,
       GWLP_USERDATA);`
     - If `self`: `return self->WindowProc(msg,w,l);` (the **Phase-B
       virtual call** — recovers the most-derived override).
     - If `self==0` (messages strictly before `WM_NCCREATE`, e.g.
       `WM_GETMINMAXINFO`): `return DefWindowProcA(hwnd,msg,w,l);`
       (the standard, correct OWL pre-binding behaviour — never a
       null deref).
  - This needs a `CREATESTRUCTA` shape. **Minimal addition to
    `WINDOWS_H`:** only the fields up to and including
    `lpCreateParams` — Win64 layout is `lpCreateParams` at offset 0
    of `CREATESTRUCTA` (it is the *first* member of the Win32
    `CREATESTRUCTA`), so the runtime can read
    `*(void**)l` equivalently; we still declare the struct honestly
    for readable OWL source. (`WM_NCCREATE 0x0081` constant added.)
- **Why not store in `cbWndExtra`/window words:** `GWLP_USERDATA` is
  simpler (no class-extra-bytes bookkeeping), is what OWL 2.5
  actually uses, and keeps the class registration trivial. Chosen.

**Init of the "global app instance" without global ctors (D3 — the
other no-global-ctor reconciliation).** `TApplication`/the runtime
need *one* process-wide pointer: the current `TApplication*` (so
`TWindow` can reach `hInstance`; OWL exposes `::GetApplication()`).
mdbcc has no global ctor — but it **does** support a *constant*
global initializer (`static TApplication* OwlApp = 0;` is a constant
`0` ⇒ legal, `src/codegen.rs:330-336`). The pointer is **assigned at
first use / at `TApplication` construction**, not via a ctor of a
global object:
- `static TApplication* OwlApp = 0;` (constant init — allowed).
- `TApplication::TApplication(...)` body does `OwlApp = this;` and
  sets `hInstance` from the **PE image base** — Phase C's GUI stub
  passes `hInstance == IMAGE_BASE` and *that equals
  `GetModuleHandle(NULL)`* (a no-resource EXE's module handle **is**
  its image base). The runtime's `WinMain` already has `hInstance`
  as its first parameter (the stub supplies it); it stores it into
  `OwlApp`/`TModule::hInstance` *imperatively in `WinMain`'s body*
  before calling `OwlMain`. **No global constructor anywhere** — all
  state is set by ordinary executed statements on the
  already-running call path. This is a *design decision within
  D-1..D-3* (the roadmap explicitly delegates "we control the OWL
  source so we choose a mechanism mdbcc supports"); it is **not** an
  Arthur fork.

> This is the crux risk and it is *closed by construction*: the only
> process-global is a constant-initialised null pointer, written by
> the first executed statement of `WinMain`/`TApplication::ctor`;
> per-window state lives in Windows' own `GWLP_USERDATA`. mdbcc's
> missing global-ctor feature is therefore **never exercised** by
> the OWL runtime — Phase D does not need it and does not add it.

### D-d — Message loop correctness, re-entrancy, teardown

- **The loop** (in `TApplication::MessageLoop`, ordinary C++ the
  Phase-A ABI compiles):
  ```cpp
  MSG msg;
  while (GetMessageA(&msg, 0, 0, 0)) {   // 0 ⇒ WM_QUIT, FALSE
      TranslateMessage(&msg);
      DispatchMessageA(&msg);            // ⇒ USER32 calls our thunk
  }
  return (int)msg.wParam;
  ```
  `GetMessageA` returns 0 **only** on `WM_QUIT`, ≠0 otherwise (the
  documented contract); the loop exits exactly on `WM_QUIT`. `&msg`
  is a stack `MSG` passed by pointer (no struct-by-value — within
  the limitation). `msg.wParam` read via the `MSG` struct fields
  (member access exists).
- **Teardown chain (close → clean exit), end to end:** user closes
  the frame → Windows posts `WM_CLOSE` → our `WindowProc` does *not*
  special-case `WM_CLOSE` ⇒ `DefWindowProcA` ⇒ default destroys the
  window → Windows sends `WM_DESTROY` → `WindowProc` does
  `PostQuitMessage(0)` → `GetMessageA` next returns 0 → loop exits →
  `Run` returns `msg.wParam` (0) → `WinMain` returns it → Phase-C
  stub `mov ecx,eax; call ExitProcess` → **clean process exit code
  0**. Every arrow is a mechanism that already exists (Phase C stub)
  or is one of the D-a USER32 imports.
- **Re-entrancy / nested dispatch:** `DispatchMessageA` calls our
  thunk *synchronously on the same stack*; the thunk may itself
  cause sends (e.g. `WM_NCCREATE` during `CreateWindowExA`, which
  runs **inside `Create()`**, before the loop even starts). The
  design is re-entrant-safe because: (a) the thunk holds **no
  shared mutable global** (instance state is per-HWND in
  `GWLP_USERDATA`, recovered fresh each call); (b) each mdbcc call
  frame is independent (Phase A frames are ordinary, re-entrant);
  (c) the `WM_NCCREATE`-before-`Create()`-returns case is explicitly
  handled (bind from `lpCreateParams`, set `HWindow` *in the thunk*
  so even messages arriving before the `CreateWindowExA` assignment
  see a valid `self`). No recursion bound is needed for v1 (no app
  message pumping inside handlers; that is Phase E).
- **Single window, single class:** v1 registers one class and one
  main window; no `DestroyWindow` bookkeeping, no multi-window
  lifetime. Closing the only window quits the app (standard). All
  multi-window/owned-popup logic is Phase E (explicit deferral).

## Regression (console path byte-identical — the central invariant)

Every Phase D addition is **dormant for a console program**, by the
same mechanism Phase A/B/C proved (executably, not by assertion):
- **D-a (1) `WIN32_IMPORTS` USER32 rows:** `used_dlls`/`used_symbol`
  (`src/pe.rs:131`,`:159`) emit a DLL descriptor *only* if a
  `RipRef::Import` references its symbol. A console program
  references none ⇒ `["KERNEL32.dll"]` ⇒ `.idata` byte-identical ⇒
  `tests/pe_imports.rs` golden unchanged (the executable proof).
- **D-a (2) `<windows.h>` struct/constant growth:** the body only
  materialises if the source `#include <windows.h>`; an unused
  typedef/struct/macro emits **zero bytes** (parser-only). A console
  program is unaffected; even one that includes it but uses nothing
  new is byte-identical.
- **D-b `owl/*.h` + runtime prepend:** the OWL runtime TU is
  prepended **only when an `owl/*` header is included**; a console
  program includes none ⇒ the runtime is not compiled in ⇒ zero
  bytes, byte-identical. (The intrinsic-resolver branch is gated on
  the `owl/` name prefix exactly as `windows.h` is gated on its
  literal name.)
- **D-c/D-d:** pure OWL-source / USER32-call behaviour; no codegen
  change ⇒ nothing a console program emits can differ.
- **No new codegen feature, no new `RipRef` variant, no ABI
  change** ⇒ the determinism guard + O1 88-e2e + the unchanged
  `pe_imports` golden are the executable proof, identical in form to
  the PE-layout fix and Phases A/B/C.

## Risks (honest)

1. **Callback ABI (Windows → our `WndProc`).** A wrong shadow-space
   / alignment / return-register assumption ⇒ the first dispatched
   message faults. *Mitigation:* mdbcc emits standard Win64 and the
   Win64 `WNDPROC` *is* a 4-arg Win64 function — argued above as
   correct **by construction** (no special thunk), and the same
   property is already exercised by Phase A's callback corpus
   (qsort-shaped callback invoked by a helper, three-way O2/O3). O6
   liveness is the end-to-end proof (Windows really calls it; a bad
   ABI crashes → non-clean exit → O6 FAIL). Residual: low; this is
   the most-load-bearing assumption, called out as such.
2. **Instance-map without global ctors.** The crux. *Mitigation:*
   chosen mechanism (`GWLP_USERDATA` + bind in `WM_NCCREATE` from
   `lpCreateParams`) uses **Windows' own per-window storage and
   zero process-global mutable state**; the one process-global is a
   *constant-initialised null pointer* set by the first executed
   statement of `WinMain` — mdbcc's missing global-ctor feature is
   never exercised. The pre-`WM_NCCREATE` null-`self` window is
   explicitly handled (`DefWindowProcA`, never a null deref). Closed
   by construction; D3 isolates and proves it before the full
   runtime.
3. **Message-loop testability / headless.** A GUI loop has no
   stdout; CI may be headless. *Mitigation (carried verbatim from
   the proven Phase-C O6 split):* the **structural half is
   always-on and rigorous** (subsystem + the exact USER32 symbol
   set + console-golden-unchanged — strong, headless-safe); the
   liveness half self-skips loudly with no visible window station;
   a non-modal window (unlike the MessageBox) does not even block
   its own process, so the watchdog is pure backstop. We never
   assert liveness we did not observe.
4. **The screenshot oracle is weak.** `mdscreensnap` golden cannot
   prove correct message handling/layout — only "a titled framed
   window of about the right shape appeared". *Mitigation:* stated
   verbatim in the doc + test header (D-3 honesty); it is a coarse
   tripwire, **not** conformance; the language *under* OWL stays
   fully O1/O2/O3-validated (Phases A/B); Phase I real-app is the
   acknowledged heavier follow-up. Not papered over.
5. **Scope size — Phase D is large.** OWL even as a subset + a
   message loop + the thunk + header growth is the biggest phase so
   far. *Mitigation:* the strict minimal subset driven by **one
   concrete hello-window** (every class/method/symbol/constant is
   "named by the hello source or cut"); the **D1→D6 increment
   ladder isolates each risk** (substrate, then raw window, then
   thunk, then runtime, then full app) so each lands as one small
   reviewed green commit and a failure is localised — not a
   big-bang. If an increment cannot go green in 2 tries the charter
   says stop/journal/hand back (no half-state).
6. **OWL runtime hits a Phase-A/B subset edge.** Authoring the
   runtime in mdbcc's C++ subset may surface an unsupported
   construct (e.g. an initialiser form, a cast). *Mitigation:* the
   subset was chosen by D-2 to avoid this; any edge is an
   *implementation* finding fixed by simplifying the OWL source
   (we own it, D-1) or a tiny scoped codegen fix on the strong
   O1/O2/O3 path — **not** an architectural fork. Surfaces early
   (D3/D4 compile the runtime before the full app).
7. **Concurrent agents on `src/pe.rs`/`src/pp.rs`.** Same hot files
   as in-flight work. *Mitigation (charter):* apply on a
   confirmed-clean tree; each increment small/atomic; do not
   refactor unrelated code; retry-on-foreign-build-error rather
   than fix others' code; the `WIN32_IMPORTS`/`WINDOWS_H` growths
   are append-only (low collision).
