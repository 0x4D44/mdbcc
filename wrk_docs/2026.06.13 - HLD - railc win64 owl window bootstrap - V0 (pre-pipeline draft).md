# RailC Win64 OWL Window Bootstrap

## Context

The repeatable Win64 source-stack link now produces a PE32+ RailC executable, but the bounded smoke exits before a visible window with `0xC0000374` in `ntdll.dll`. The previous `_init_heap` access violation and missing `CTL3D32.dll` loader dependency are resolved.

The next risk is not a narrow linker problem. The source-built stack is compiling BC45/OWL Win32-era code as native Win64, and the window bootstrap path still contains hard 32-bit assumptions.

## Evidence

- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE\WTYPES.H:131` defines `WPARAM` as `UINT`.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE\WTYPES.H:143` defines `LPARAM` as `LONG`.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE\WTYPES.H:149` defines `LRESULT` as `LONG`.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE\WINUSER.H:5917` declares `SetWindowLongA(HWND,int,LONG)` and the header has no `SetWindowLongPtrA`/`GWLP_WNDPROC` native path.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\OWL\OWL.CPP:68` installs the per-window thunk with `SetWindowLong(hWindow, GWL_WNDPROC, uint32(thunk))`.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\OWL\OWL.CPP:77` defines the Win32 `TInstanceThunk` as executable x86 data bytes.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\OWL\WINDOW.CPP:900` recovers `this` from Borland's `_EAX` pseudo-register.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\OWL\WINDOW.CPP:248`, `:292`, `:294`, and `:991` use the same 32-bit `SetWindowLong`/`GetWindowLong` window-procedure path.
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE\OWL\SIGNATUR.H:458` aliases `LRESULT_WPARAM_LPARAM_Sig` to `I32_U_I32_Sig`, and `DISPATCH.CPP` dispatchers carry `lParam` as `int32`. This is likely the second wall after the window bootstrap itself.

The project already has a safer model in its generated minimal OWL surface: `C:\language\mdbcc\src\pp.rs:552` stores the object pointer with `SetWindowLongPtrA(..., GWLP_USERDATA, (LONG_PTR)self)` and dispatches through a static WNDPROC.

## Constraints

- Do not edit `C:\language\mdbcc\wrk_oracle` in place. Keep oracle sources as evidence.
- Do not apply a global typedef rewrite to every target. PE32 still needs BC45-compatible 32-bit message types.
- The whole Win64 source slice must compile against the same message-width view. Mixing 32-bit and pointer-sized `WPARAM`/`LPARAM` declarations across archive members would make the C++ ABI incoherent.
- Preserve `TWindow` object layout unless a later failure proves it must change. The existing fields already include `WNDPROC DefaultProc` and private `WNDPROC Thunk`, so the bootstrap can be replaced without adding fields.

## Recommendation

Use a Win64-only workspace overlay for the RailC source-slice build. The overlay should be selected by the harness/build configuration, not by mutating BC45 sources. It should provide pointer-sized Windows message types and replace the OWL per-instance executable thunk with a static dispatcher plus `GWLP_USERDATA`.

This is preferable to a low-address allocation trick or a compiler special case. The current x86 thunk bytes cannot be correct native x64 code, and the `uint32(thunk)` cast loses information before USER32 sees the value. Any solution that tries to preserve that shape would be fragile by construction.

## Implementation Slice

1. Add a Win64 overlay include directory, selected only for the `-m64` RailC source-slice harness.
2. Provide wrapper headers for the smallest native ABI surface:
   - define `UINT_PTR`, `LONG_PTR`, `WPARAM`, `LPARAM`, and `LRESULT` as pointer-sized under the overlay;
   - expose `GWLP_USERDATA`, `GWLP_WNDPROC`, `SetWindowLongPtrA`, and `GetWindowLongPtrA`;
   - include the original BC45 headers after predefining the guarded message typedefs, so unrelated declarations still come from the oracle headers.
3. Add a target marker such as `-D__MDBCC_WIN64__=1` to the Win64 harness or select the overlay by include path/member source. Do not redefine the compiler's BC45-compatible predefines globally yet.
4. Generate patched build-local copies of `OWL.CPP` and `WINDOW.CPP` for the Win64 harness, or use small overlay source replacements with the same archive member names. The patch should be exact and reviewable:
   - `CreateInstanceThunk(TWindow*)` returns a single static dispatcher WNDPROC, not allocated executable data;
   - `FreeInstanceThunk(WNDPROC)` is a no-op for the static dispatcher;
   - `StdWndProc(HWND,uint,WPARAM,LPARAM)` recovers `TWindow*` through `GetWindowLongPtrA(hwnd, GWLP_USERDATA)` and then calls `ReceiveMessage`;
   - `InitWndProc` sets `GWLP_USERDATA` before installing the static dispatcher with `SetWindowLongPtrA(..., GWLP_WNDPROC, ...)`;
   - `TWindow::SubclassWindowFunction`, alias teardown, and `GetWindowPtr` use pointer-sized get/set paths.
5. Rebuild the Win64 harness and rerun the bounded smoke. If the process reaches window creation and fails later, keep that as a new frontier instead of stacking broader dispatch changes immediately.

## Second-Stage Risk

After the window-procedure path is pointer-safe, OWL response dispatch is likely to expose another pointer-width layer:

- `SIGNATUR.H` still names `LRESULT_WPARAM_LPARAM_Sig` as `I32_U_I32_Sig`.
- `DISPATCH.H` and `DISPATCH.CPP` use `int32` for `LPARAM`-carrying dispatchers.
- `COMPAT.H` preserves Win16-style `uint16 WParam` and `uint32 LParam`.

Do not fix all of that preemptively. First prove that the static WNDPROC/bootstrap change moves the runtime smoke past the current `0xC0000374` failure. Then widen the dispatch signatures only for messages that actually route pointer-bearing payloads through the response-table machinery.

## Acceptance Checks

- Existing non-ignored tests still pass.
- The ignored Win64 source-stack link harness still passes and writes the trace under `C:\language\mdbcc\wrk_probe\railc_source_slice_win64_link\build`.
- The Win64 import table contains `SetWindowLongPtrA` and `GetWindowLongPtrA` for the OWL window path and does not reintroduce `CTL3D32.dll`.
- A bounded smoke no longer exits before any visible top-level window for the same `0xC0000374` reason. A later failure is acceptable if it is a new, better-localized frontier.
