# HLD — mdbcc Win64 array-new/delete cookie fix (V2)

> **Status: DRAFT (V2) — pending sign-off.** team-design pipeline (proportionate: a small, well-localized codegen
> fix). V1 = authored draft from a debugger-confirmed diagnosis + a 3-reader UNDERSTAND brief. **V2 folds in the Codex
> external review** (gpt-5.5, decorrelated): its 10 findings clustered on ABI *precision* (alignment, cookie width,
> overflow, predicate completeness) and *scope* (split the ctor-loop widening; formally scope the allocator model;
> expand tests) — none refuted the fix. V2's central response (D6): **reuse/mirror `gen_new_array`'s EXACT cookie
> protocol**, so symmetry with `gen_delete` holds *by construction* and the fix inherits `gen_new_array`'s
> alignment/width/overflow behavior and its 18 passing tests. Plus: the allocator model is formally scoped (D7), the
> co-located ctor-loop widening is split into a separate tested Part 2 (D8), and the test matrix is expanded (O1).
> The UNDERSTAND brief also corrected the originating diagnosis: the bug is **target-agnostic** (i386 has the identical
> latent mismatch), and **no delete-side change** is needed (the entire fix is in the producer).

## Problem

The source-built **Win64** RailC exe heap-corrupts (`0xC0000374` STATUS_HEAP_CORRUPTION) at startup, **before any
window**, at `wrk_oracle/.../CLASSLIB/VECTIMP.H:159` `delete[] Data;` in `TVectorImpBase<T,Alloc>::Resize` (a BIDS
container growing its array during streamable-class registration via global constructors).

Root cause is an **array-cookie contract mismatch** between the array-new producer and the array-delete consumer,
for one cell: a **class element** (`array_needs_cookie` = ctor **or** dtor) allocated via the **allocator-placement**
form `new(*this)T[n]`:
- **Producer** `gen_placement_new_array` (`src/codegen.rs:14540-14674`) is target-agnostic and **never writes a
  cookie**: it requests exactly `count*elem_size` bytes from `operator new[](size, alloc)` and returns `payload == block`.
- **Consumer** `gen_delete` array path **honors `array_needs_cookie`** on both targets: for a class element it reads
  the count at `*(uN*)(payload-cookie)` and `HeapFree`s `payload-cookie` (Win64: 8 bytes, `:15055/:15137`; i386: 4
  bytes, `:14775-14781/:14824/:14898`).
- Because the block had no cookie, `delete[]` reads heap-header garbage as the element count, runs that many
  destructors, then frees `payload-cookie` (8/4 bytes **before** the real allocation) → heap corruption.

`array_needs_cookie` (`:15223-15236`, = Record has ctor OR dtor) is target-independent, so the i386 allocator-placement
class-element path is **identically broken — just latent** (the OWL bootstrap exercises the Win64 image). A Win64-only
fix would leave i386 latently broken; **the producer fix repairs both at once.**

## Cookie truth table (authoritative; the fix's invariant)

Cookie size = `target_ptr_bytes()` (i386=4, Win64=8); count at `block+0`; payload = `block+cookie`; delete reads/frees
`payload-cookie`. **Symmetry invariant:** for any element type, `(producer payload − block)` MUST equal
`(consumer freed-ptr − payload offset)` — i.e. 0 for cookie-less, `cookie` for cookie'd.

| New form | element | i386 NEW→DEL | Win64 NEW→DEL | status |
|---|---|---|---|---|
| scalar `new T` | any | none→none | none→none | OK (untouched) |
| **A** global `new T[n]` | trivial | none→none | none→none | OK |
| **A** global `new T[n]` | class | 4@blk+0,p=blk+4 → p-4 | 8@blk+0,p=blk+8 → p-8 | OK — **reference layout** (locked by `tests/cpp_new_array.rs`, 18 tests) |
| **B** alloc-placement `new(alloc)T[n]` | trivial | none→none | none→none | OK |
| **B** alloc-placement `new(alloc)T[n]` | **class** | none→**expects p-4** | none→**expects p-8** | **MISMATCH** (i386 latent; Win64 = the active crash) |
| **C** raw-buffer `new(voidptr)T[n]` | any | none→N/A | none→N/A | OK (caller owns; no `delete[]`) |

**The fix makes B-class reproduce the A-class reference layout.**

## Design

### Governing principle (D6, the Codex response): mirror `gen_new_array`'s EXACT cookie protocol
The fix must reuse the **same cookie protocol** the already-correct reference producer `gen_new_array` uses — same
predicate (`array_needs_cookie`), same prefix size, same `block+0` count store of the same width, same `payload =
block+prefix` offset, same `count*elem_size + prefix` size arithmetic. **Prefer factoring the shared cookie logic into
one helper** that both `gen_new_array` and `gen_placement_new_array`'s allocator form call (cleaner, and impossible to
drift); if a clean factor isn't feasible, mirror `gen_new_array` byte-for-byte. **Consequence:** symmetry with the
(unchanged) `gen_delete` holds *by construction* for every element type, and the fix automatically inherits
`gen_new_array`'s alignment, cookie-store/load width, overflow behavior, and `array_needs_cookie` completeness — all of
which are already locked by the 18 `tests/cpp_new_array.rs` tests. This dissolves the Codex precision findings:
- **Alignment (Codex #1):** the prefix is exactly what `gen_new_array` uses (= `target_ptr_bytes`, so `payload` is
  8-aligned on Win64 / 4-aligned on i386). Over-aligned (>pointer) element types are **out of scope** — they are not
  supported by the existing ABI and not used by the BIDS containers (which hold pointers / small records). State and
  test this constraint; do not invent alignment rounding that would diverge from `gen_new_array`/`gen_delete`.
- **Cookie store/load width (Codex #3):** the producer stores exactly the width `gen_delete` reads — `u64` at
  `block+0` on Win64, `u32` on i386 (= `target_ptr_bytes`). Guaranteed by mirroring `gen_new_array`.
- **Size overflow (Codex #4):** use `gen_new_array`'s size arithmetic verbatim (whatever it is); do not introduce a
  divergent computation.
- **Predicate completeness (Codex #5):** because new and delete consult the **same** `array_needs_cookie`, the fix
  **cannot introduce a mismatch** regardless of whether `array_needs_cookie` perfectly classifies implicit/virtual/
  base destructors — both sides always agree. (Any incompleteness in `array_needs_cookie` is a *pre-existing*
  dtor-completeness concern shared with `gen_new_array`/`gen_delete`, not introduced here; O1 adds a dtor-via-member/
  base regression to exercise it, but it is not a blocker for this fix.)

### The change

**Single change site: `gen_placement_new_array` (`src/codegen.rs:14540-14674`), the ALLOCATOR (non-ptr, non-array
placement) form only.** When `array_needs_cookie(ty)` is true (via the shared helper of D6):
1. **Gate on `array_needs_cookie(ty)`**, not the local `ctor.is_some()` (`:14593`). `array_needs_cookie` = ctor **or**
   dtor; a **dtor-only** class must also get a cookie (else it reproduces the mismatch in a second variant).
2. **Grow the allocation:** request `count*elem_size + cookie` bytes from `operator new[]` (the `alloc_call` size arg,
   `:14573/:14578-14590`), where `cookie = self.target_ptr_bytes()`. Otherwise writing the cookie + n elements overruns
   the block.
3. **Write the cookie:** store the element `count` at `block+0` (target-width store).
4. **Return `block+cookie`** as the payload — both the construction-loop base and the expression value
   (`:14615/:14626-14627/:14669-14670`) become `block+cookie`, not `block`.

This mirrors the already-correct reference producers — `gen_new_array` (Win64: store `:15431-15435`, payload=block+8
`:15439`) and `gen_new_array_i386` (store `:15758`, payload=block+4 `:15762`). Use `self.target_ptr_bytes()`
throughout — **do not hardcode 8** — so one change fixes both targets.

### Two parts, landed as separate commits (D8, the Codex #7 response)
- **Part 1 — cookie symmetry (the heap-corruption fix; the headline).** Steps 1–4 above. This alone clears
  `0xC0000374` (O4). It MUST land with a correct payload base (`block+prefix`).
- **Part 2 — co-located Win64 ctor-loop 64-bit widening (correctness ≥ 4 GB; separately tested).** The class-ctor
  construction loop (`:14639-14664`) emits **32-bit-only** encodings (`xor eax,eax`; `cmp eax,[ebp-n]`;
  `mov ecx,imm32`/`mul ecx`; `add eax,[ebp-payload]`; `inc dword [ebp-iter]`) — 32-bit pointer arithmetic on
  `payload`/`this` that truncates heap addresses ≥ 4 GB on Win64 (works today only because `HeapAlloc` returns
  sub-4 GB). Since Part 1 rewrites the payload-base computation flowing through this loop, widen it to 64-bit on Win64,
  mirroring `gen_new_array`'s REX-prefixed ctor loop (`~:15441+`), with a **targeted codegen test asserting 64-bit
  address arithmetic** (the loop uses REX.W / 64-bit `imul`/`add`). Splitting it keeps Part 1's review surface minimal
  while still fixing the latent defect in code we're already touching.

**Count single-eval:** the class path evaluates `count` twice (in `alloc_call` for the byte size, and to drive the
ctor loop). Spill `count` once and reuse it for the byte size, the cookie store, and the loop bound, to avoid a 3-way
divergence (the bound is side-effect-free in practice, but the cookie store makes a single canonical value mandatory).

**Explicitly NOT changed (must stay byte-identical):** `gen_delete` (both targets — it already frees `payload-cookie`
via `HeapFree`; **no delete-side change**), `gen_new_array` / `gen_new_array_i386` (the reference producers),
`gen_global_alloc_op` / the allocator `operator new[]` intrinsic (`:14688+`; the cookie is synthesized **around** the
call, never inside the operator — `TStandardAllocator::operator new[](size,Alloc&)` forwards to `::operator new[](sz)`
= raw `HeapAlloc` with no private header, `CLASSLIB/ALLOCTR.H:47-49`, so freeing `HeapFree(block)` is correct), scalar
`new`/`delete`, the raw-buffer placement form (caller-owned), and trivial-element arrays (cookie-less on both sides).

## Acceptance criteria / test oracles (definition of done for /team-build)
- **O1 — NEW differential roundtrip oracle matrix (tests-first; the tests that would have caught this; Codex #9):**
  `C* p = new(alloc)C[n]; … delete[] p;` exercising the BIDS allocator-placement form, built and **run** on **both
  -m32 and Win64**, exit-code-differential vs the `cl`/`bcc32` oracle. Each must currently **fail** on Win64
  (`0xC0000374`) / be heap-unsafe on i386, and **pass on both** after the fix, with ctor/dtor side-effect counters
  proving exactly `n` constructions and `n` destructions (right count from the right cookie). Variants:
  (a) **ctor + dtor**; (b) **dtor-only** (no user ctor — covers the `array_needs_cookie` vs `ctor.is_some()` gap);
  (c) **implicit non-trivial dtor via a member/base** with a dtor (covers the predicate-completeness concern, Codex #5);
  (d) **larger count** (e.g. `n` ≥ 64) so the dtor loop / size arithmetic isn't only exercised at `n=3` (Codex #9);
  (e) a **second alloc+free after the `delete[]`** to force heap-validation of the freed block. Trivial-element and
  raw-buffer-placement cases stay cookie-less (negative controls).
- **O2 — Symmetry assertion:** for the allocator-placement class array, the cookie-distance read `*((size_t*)p - 1) == n`
  succeeds (payload−block == cookie), exactly as `cpp_new_array.rs` asserts for global `new[]`.
- **O3 — Regression green:** all **18** `tests/cpp_new_array.rs` (global `new[]`/`delete[]` cookie + EH) and the S4
  `TArrayAsVector<long>` oracle (`tests/oracle_s4_classlib.rs`) stay green on both targets — proving the reference
  producers/consumers and trivial-element arrays are untouched. The full non-ignored suite stays green.
- **O4 — Runtime wall cleared:** `tests/railc_source_slice.rs::railc_source_built_dependency_slice_links_win64` no
  longer classifies the exe as `SmokeOutcome::HeapCorruption` (`0xC0000374`) — expect `WindowAppeared` or a NEW,
  better-localized frontier (the deferred WNDPROC/dispatch wall). Once stable, flip the O3 known-gap arm to `panic!`.
- **O5 — No i386 regression:** the 32-bit RailC self-host remains byte/behaviour-stable (the differential + S4 oracles
  guard this; the producer change is symmetric).

## Residual risks
1. **Allocator model — formally scoped (Codex #2, D7).** This fix is scoped to the **BIDS allocator model**: an
   allocator-placement `operator new[](size, Alloc&)` that bottoms out at the raw `::operator new[](sz)` = `HeapAlloc`
   base **with no private bookkeeping header** before `block`, so the unchanged `gen_delete`'s `HeapFree(payload-prefix)`
   frees the exact allocation base. This holds for `TStandardAllocator` (`CLASSLIB/ALLOCTR.H:47-49`, forwards cleanly).
   **team-build MUST verify** the concrete allocator type(s) the bootstrap containers bind to forward cleanly; if any
   allocator inserts its own header (so the heap base ≠ `block`), a cookie-only fix is insufficient *for that allocator*
   and it is out of scope (journal it, do not improvise a general allocator-delete-routing change). Note: general
   C++ `delete[]` is only well-formed against the standard allocation form anyway; BIDS pairs `new(alloc)T[n]` with an
   ordinary `delete[]` precisely because its allocator forwards to the global heap.
2. **Co-located 64-bit ctor-loop widening** adds encoding work (REX prefixes, 64-bit `imul`/`add`). Mirror
   `gen_new_array`'s proven loop; if it destabilizes, land the cookie fix first (correct payload base) and split the
   widening to an immediate follow-up — but do not leave a half-32-bit payload computation.
3. **EH / partial-construction.** `gen_placement_new_array` has no cleanup landing pad today (documented leak on a
   throwing element ctor). The cookie change does not alter EH; **constraint for any future placement cleanup pad:** it
   must `HeapFree(block)` = `payload-cookie`, not `payload`.
4. **The next frontier after O4.** Clearing `0xC0000374` likely exposes the deferred WNDPROC/int32-dispatch wall
   (wall 2). That is expected and acceptable (O4 passes on a new, better-localized frontier).

## Decision log
- **D1 — Fix the producer, not the consumer.** `gen_delete` already frees `payload-cookie` correctly; making
  `gen_placement_new_array` write the matching cookie restores symmetry with the smallest change. Rejects the
  originating journal's "route delete[] to operator delete[]" as unnecessary and riskier (UNDERSTAND brief).
- **D2 — Target-agnostic (`self.target_ptr_bytes()`), fixing both i386 and Win64.** `array_needs_cookie` is
  target-independent, so i386 is identically (latently) broken; one symmetric change repairs both. (Corrects the
  journal's "i386 matched" claim.)
- **D3 — Gate on `array_needs_cookie(ty)` (ctor OR dtor), not `ctor.is_some()`** — covers dtor-only classes.
- **D4 — Mirror the global-`new[]` reference layout** (count@block+0, payload=block+cookie) so the unchanged
  `gen_delete` reads the right place.
- **D5 — Fix the co-located 64-bit ctor-loop widening** because the same lines are being rewritten — superseded in
  packaging by D8 (landed as a separate, independently-tested Part 2 rather than folded into Part 1).
- **D6 — Mirror `gen_new_array`'s exact cookie protocol (prefer a shared helper).** Makes symmetry with `gen_delete`
  hold by construction and inherits the reference path's alignment/width/overflow/predicate behavior + its 18 tests.
  This is the central response to Codex's precision findings (#1/#3/#4/#5/#10) — the fix does not invent a new layout,
  it reuses the proven one.
- **D7 — Formally scope to the BIDS allocator model** (allocator forwards to raw `HeapAlloc`, no private header), with
  a team-build verification step; allocators with private headers are out of scope (Codex #2). The journal's
  "route delete[] to operator delete[]" idea is rejected as unnecessary and riskier (no delete-side change at all).
- **D8 — Two commits: Part 1 (cookie symmetry = the `0xC0000374` fix) + Part 2 (Win64 ctor-loop 64-bit widening,
  separately tested)** — keeps Part 1's review surface minimal while still repairing the co-located latent defect
  (Codex #7).
