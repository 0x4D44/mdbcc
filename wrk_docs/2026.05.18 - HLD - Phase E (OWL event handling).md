# HLD — Phase E: OWL event handling (response tables + EV_* + message cracking + TDC/TPaintDC)

Date: 2026-05-18. Status: DESIGN (Phase A/B/C/D landed; impl-ready).
Roadmap: `wrk_journals/2026.05.17 - PLAN - OWL Windows roadmap.md`
(**Phase E section is authoritative scope**; sits on top of the proven
D5 OWL milestone — `wrk_docs/2026.05.18 - HLD - Phase D (minimal OWL
runtime).md`). Charter: `wrk_journals/2026.05.18 - PLAN - Goal loop
charter.md`. Depends on Phase A (>4-arg Win64 stack ABI, `&func` /
`RipRef::Func`, indirect call), Phase B (virtual dispatch + vtables +
virtual dtor), Phase C (multi-DLL imports, subsystem-2 + `WinMain`
stub, intrinsic `<windows.h>`, `WIN32_IMPORTS`/`emit_win32_call`),
Phase D (the OWL runtime in `OWL_RUNTIME_H` with `TWindow`'s static
`OwlStaticWndProc` thunk → `GWLP_USERDATA` → virtual `WindowProc`
dispatch). All reused; **none modified** outside the small, in-style
table/header/runtime growths Phase D explicitly reserved for Phase E.

## Why

Phase D made a real OWL app *open a framed window and exit cleanly*
on Windows 11 — `TFrameWindow` + `TMyApp::InitMainWindow` +
`OwlMain` + the `GetMessageA`/`TranslateMessage`/`DispatchMessageA`
pump all interlock through `TWindow`'s virtual `WindowProc`. It
deliberately shipped **only `WM_DESTROY`** (`src/pp.rs:325-331`): the
public Borland API for *handling events* — `DECLARE_RESPONSE_TABLE` /
`DEFINE_RESPONSE_TABLE1` + `EV_WM_*` macros + the message-cracker
`EvX(...)` signatures + `TPaintDC` for drawing — is **the next OWL
milestone**. Phase E is the first time mdbcc compiles an OWL app
that actually *responds* to user input: an unmodified Borland-API
source like

```cpp
#include <owl/applicat.h>
#include <owl/framewin.h>
#include <owl/dc.h>

class TMyWin : public TFrameWindow {
public:
  TMyWin(TWindow* parent, const char* title)
    : TFrameWindow(parent, title), ClickCount(0) {}
  void EvLButtonDown(UINT modKeys, TPoint& pt);
  void EvPaint();
  void EvDestroy();
  int ClickCount;
  DECLARE_RESPONSE_TABLE(TMyWin);
};
DEFINE_RESPONSE_TABLE1(TMyWin, TFrameWindow)
  EV_WM_LBUTTONDOWN,
  EV_WM_PAINT,
  EV_WM_DESTROY,
END_RESPONSE_TABLE;
```

compiles with `mdbcc`, opens a window, draws text on `WM_PAINT` via
`TPaintDC`, increments `ClickCount` on each left-click, and exits
cleanly on close. Per **D-3** (carried) the GUI layer's oracle stays
the honestly-weaker O6 (structural half always-on rigorous; liveness
half desktop-gated, watchdog-bounded); **the language features under
the response table — virtuals, fn-pointers, RAII, casts — stay
fully O1/O2/O3-validated from Phase A/B and are NOT re-derived here**.

Non-negotiable constraint, identical in form to Phase A/B/C/D: **the
console path stays byte-identical**. O1 `tests/end_to_end.rs` (88,
authoritative) stays green and byte-identical; every Phase E
addition fires *only* when an OWL/GUI program is compiled (a console
program defines no `WinMain`/`OwlMain`, includes no `owl/*.h` or
`<windows.h>`, references no new USER32/GDI32 symbol ⇒ provably
unchanged `.idata`, stub, and image — `tests/pe_imports.rs` is the
executable proof, unchanged).

## Current capabilities to build on (read 2026-05-18, grounded)

Phase E is **codegen-complete on the language side** — it adds *no*
new codegen feature on the primary path. It is (a) C++ source in
the OWL runtime header that mdbcc already compiles + (b) a couple
of pre-scoped Win32-surface growths + (c) an extension of the
existing O6 harness.

### Language / codegen (Phase A/B/D — reused verbatim, NOT changed)
- **Virtual dispatch + vtables** (Phase B, `src/codegen.rs:147`,
  `:180`): a polymorphic class gets a hidden vptr at offset 0;
  `p->m(a)` on a virtual `m` lowers to vtable-indexed indirect
  call; virtual dtor takes a slot. **This is the dispatch
  mechanism Phase E chooses** for `EvX` handlers (see D1 below) —
  no new codegen.
- **The `OwlStaticWndProc` thunk** (`src/pp.rs:333-347`) already
  routes *every* OS message through `self->WindowProc(m, w, l)`
  after recovering `self` from `GWLP_USERDATA`. Phase E sits
  entirely *on top of* that virtual call — it does not change
  the thunk.
- **Function pointers / `&func`** (Phase A, `src/codegen.rs:144`,
  `RipRef::Func`): used by the runtime to wire `WNDPROC` into
  `WNDCLASSEXA`. Phase E does **not** newly use these for `EvX`
  handlers (no `EvX` is ever address-taken in mdbcc's lowering —
  the response table compiles to **C++ virtual overrides**, not
  to a static table of function pointers; see D1).
- **Member function pointers are NOT supported by mdbcc today**
  (verified — `Grep -i "member.*function.*pointer|memberfn|::\*"`
  returns no implementation; only the *concept* appears in the
  plan-of-record and the carried backlog). The plan-of-record
  explicitly notes "Needs member function pointers (here or
  folded into A)". **Phase E's mechanism choice deliberately
  side-steps this gap** (see D1) so that Phase E does not become
  a codegen project disguised as a runtime project.
- **`if`/`else` chains, not `switch`** — confirmed Phase D Tick 11
  finding: `Keyword::Switch`/`Case`/`Default` are lexed but the
  parser has **no `switch` rule** (`Grep "Switch|Case|Default"
  src/parser.rs` ⇒ 0 matches). The Phase-D `OwlStaticWndProc`
  already uses `if (m == WM_NCCREATE)` and `WindowProc` uses
  `if (msg == WM_DESTROY)` — Phase E reuses this pattern. The
  response-table dispatch is therefore an `if (msg == EV) return
  self->EvX(...);` chain inside the *parent class's*
  `WindowProc` override, not a `switch`.

### Win32 substrate (Phase C/D — the two seams Phase E grows)
- **`WIN32_IMPORTS`** (`src/pe.rs:80-116`): 6 KERNEL32 + 13 USER32
  symbols today (the Phase-D hello-window set, *including*
  `Set`/`GetWindowLongPtrA`). **No `GDI32` yet** (`src/pe.rs:103`
  comment: "No GDI32 — a blank `WS_OVERLAPPEDWINDOW` needs no
  painting; GDI is Phase E/G"). Phase E E2 adds `BeginPaint` +
  `EndPaint` (USER32 — *not* GDI32, see D3); Phase E E3 adds
  **`TextOutA` (GDI32.dll)** — **the first GDI32 symbol in mdbcc**,
  exercising the multi-DLL `.idata` path beyond two DLLs for the
  first time (the C1b multi-descriptor mechanism was *built* for
  this; one more DLL is *data*, not a code change — `used_dlls`
  already iterates the table for any descriptor whose symbol is
  referenced). Console dormancy unchanged: a program that
  references none of these still yields `used_dlls ==
  ["KERNEL32.dll"]`.
- **Intrinsic `<windows.h>`** (`src/pp.rs:70-162`, `WINDOWS_H`):
  has `UINT/DWORD/BOOL/HDC/HWND/HBRUSH/HCURSOR/HICON/...`,
  `POINT/RECT/MSG/WNDCLASSEXA/CREATESTRUCTA`, `WM_CREATE/
  WM_DESTROY/WM_CLOSE/WM_QUIT/WM_NCCREATE`, the `WS_*`/`CS_*`/
  `SW_*` constants, `WNDPROC` typedef. **Phase E grows it by**:
  `WM_PAINT 0x000F`, `WM_LBUTTONDOWN 0x0201`, `WM_MOUSEMOVE
  0x0200`, `WM_LBUTTONUP 0x0202`, `WM_COMMAND 0x0111`, `WM_KEYDOWN
  0x0100`, `MK_*` modifier-key bits, the `PAINTSTRUCT` struct
  (Win64 layout); plus a `TextOutA` declaration is **not**
  needed — like libc and `RegisterClassExA`, the call is
  recognised by name through `WIN32_IMPORTS`, no header
  declaration required.
- **Intrinsic `OWL_RUNTIME_H`** (`src/pp.rs:215-354`): the
  single self-contained TU prepended to any user program that
  includes `<owl/*.h>` (gated by the `owl/` prefix in
  `DefaultResolver::resolve`, `src/pp.rs:385-387`). **All Phase
  E runtime additions go here** — `TPoint` struct, `TDC`/
  `TPaintDC` classes, the `EV_WM_*` and `DECLARE_/DEFINE_
  RESPONSE_TABLE` macros, the per-event `virtual void EvX(...)`
  slots on `TWindow`. **No new codegen feature is needed** — the
  header growths are plain Borland-dialect C++ in the Phase-A/B
  subset (single inheritance, virtuals, member functions, ctor/
  dtor — exactly what `TWindow`/`TFrameWindow` already use).
- **The B-7/B-8/B-9 backlog** (`wrk_journals/2026.05.17 - JRN -
  Roadmap to OWL.md:219-235`) is the carried Phase-E prep:
  - **B-7**: `TWindow::Create()` drops `RegisterClassExA` /
    `CreateWindowExA` return values silently. v1's single
    hello-window does not surface it; v2 multi-window apps in
    Phase E (when an `EvCommand` creates a child) will. Folded
    into E2 (alongside `TPaintDC` because both touch
    `TWindow::Create`'s neighbourhood).
  - **B-8**: `_OwlApp` (`src/pp.rs:260`) is set in
    `TApplication::TApplication()` but currently unread. Phase E
    consumes it for `GetApplication()` public OWL accessor (a
    common pattern in event handlers reaching back to the app);
    if no E1..E4 handler needs it, the recommendation is
    **remove** it rather than carry dead state (house style: no
    speculative state).
  - **B-9**: parser does not check that the user's `OwlMain`
    signature matches the runtime's forward prototype (`int
    OwlMain(int, char**)`). v1 papered over with Phase A's
    4-args-in-regs. Phase E's `DEFINE_RESPONSE_TABLE` macro
    shapes may surface prototype/definition mismatches more
    broadly. Folded into E5 sweep, scoped tight (a
    prototype-vs-definition param-type check on `OwlMain` only,
    or **leave deferred** as the house-style "no speculative
    abstraction" — recommendation in E5).

## Design

Phase E = **the EV_*/response-table mechanism (an `if`-chain
dispatch over per-event virtuals) + the message-cracker `EvX`
signatures + `TPaintDC`/`TDC` RAII + a default-fallback path
through `DefWindowProc` + a click-driven O6 extension**. Five
design sub-areas (E-a … E-e), then increment sequencing
(E1..E5). Every sub-area is the *smallest faithful subset* that
exercises the chosen events; every one is dormant for a console
program (byte-identical regression as Phase A/B/C/D).

### E-a — The EV_*/response-table mechanism decision (the central choice)

The plan-of-record explicitly delegates this: *"DECLARE/DEFINE_
RESPONSE_TABLE + EV_* macros lowered to a mechanism mdbcc
supports (member-fn-ptr table or virtual dispatch — decide & doc)"*
(`PLAN - OWL Windows roadmap.md:113-117`). Two candidate
mechanisms, both faithful to the Borland *public* API (the user
writes the canonical `EV_WM_PAINT` / `DEFINE_RESPONSE_TABLE1`
text — both options are byte-for-byte source-compatible from the
app's side; the difference is **what the macros expand to**):

**Option (a) — Member-fn-ptr table (authentic OWL internals).**
`DEFINE_RESPONSE_TABLE1(TMyWin, TFrameWindow)` would expand to a
*static const array of `{msg_id, &TMyWin::HandlerMethod}` pairs*
+ a virtual `WindowProc` that walks the array and `(this->*p)()`
the chosen handler. **Requires new codegen for member-function
pointers including the implicit `this`-adjustment ABI** —
non-trivial (Itanium-like member-fn-ptr ABI is two words wide,
encodes virtual vs non-virtual, encodes the `this`-adjust delta;
single-inheritance simplifies it but it is *still* a codegen
feature mdbcc has never emitted, and the plan-of-record explicitly
calls this gap out: *"Needs member function pointers (here or
folded into A)"*). It is the OWL purist's choice.

**Option (b) — Virtual dispatch (smallest change).** Each
`EV_WM_X` expands to nothing at the user-class level *directly*
(it is a marker in the response table); the per-event virtual
slot is **declared once on `TWindow` itself** (`virtual void
EvPaint() {}`, `virtual void EvLButtonDown(UINT modKeys,
TPoint& pt) {}`, …) with empty defaults. The user class
declares `void EvPaint();` etc. *without `virtual`* (the
`virtual` is inherited from `TWindow` — Phase B already supports
that, vindicated by the D5 hello app). `DEFINE_RESPONSE_TABLE1
(TMyWin, TFrameWindow)` expands to a `TMyWin::WindowProc`
override whose body is an `if`-chain over the *enumerated*
EV_WM_* messages, each branch calling the corresponding virtual
`EvX(...)` (which the most-derived class has overridden), and
whose fallthrough is `return TFrameWindow::WindowProc(msg, w,
l)` (the *parent class link* the second macro arg captures).
**Uses Phase B virtuals only — no new codegen.** Trade-off:
adds N virtual slots to `TWindow`'s vtable (vtable bloat
proportional to the v1 EV_WM_* set, not to the user's
overrides). For v1's set (§E-b: 7 events) that is **+7 vtable
slots** — bounded, small, paid once.

**Decision: Option (b) — virtual dispatch.** Rationale:
1. **Smallest change** — Phase E becomes a *header growth*, not
   a codegen project. The D5 milestone already proved this exact
   pattern works across the OS callback boundary (the
   `WindowProc` virtual is dispatched through the vptr from
   `OwlStaticWndProc` after `GWLP_USERDATA` recovery — Phase B's
   vtables already drive the entire OWL message loop).
2. **(a) burns a codegen feature on a runtime-internal
   optimisation that does not gate any program's correctness.**
   The *public OWL API* — the macros the app writes — is
   identical under both options. (a) would replicate Borland's
   internal *implementation choice* (which was made in 1994 in
   part to reduce vtable size on 16-bit Windows when vtables
   lived in CS); on Win64 with cheap RAM and one-vptr-per-object
   that motivation is dead.
3. **The vtable bloat is bounded and observable.** N = 7 in v1.
   We measure it in E1's structural test (`sizeof(TWindow)` and/
   or the vtable's slot count — see TDD §E1) so any future
   growth is visible. A user class with 0 overridden EvX still
   has the +7 inherited slots — that is the cost we accept.
4. **(a) becomes a future B-N codegen item if it earns its
   keep.** Recorded explicitly: **B-10 (Phase E backlog) —
   member-function pointers as a general codegen feature.**
   Promoted *if and only if* a target app (Phase I) genuinely
   needs them (e.g. a non-virtual callback registry, a generic
   visitor) — not added speculatively for OWL when (b) already
   delivers OWL semantics.

Honest note: (b) is a *simplification*, not a fidelity loss for
v1. The *source the app sees* is byte-for-byte the Borland
public API. A real implementation difference would surface
only via reflection / size of a hypothetical
`TResponseTableEntry` — neither of which any OWL app inspects
at runtime. The macros' *names* (DECLARE_RESPONSE_TABLE etc.)
are preserved verbatim; only their *expansion* differs from
Borland's. This matches D-1's licence ("we control the OWL
source so we choose a mechanism mdbcc supports while keeping
the public macro API").

### E-b — `DECLARE_/DEFINE_RESPONSE_TABLE` + the v1 `EV_WM_*` set

**Per-event virtuals on `TWindow` (in `OWL_RUNTIME_H`).** v1 ships
the **minimal set the Phase-E O6 test actually exercises**, no
speculative surface (house style; same discipline as the D-a
USER32 set):

| Event | Virtual slot (signature) | Cracking |
|---|---|---|
| `WM_CREATE` | `virtual bool EvCreate(CREATESTRUCTA& cs);` | `cs = *(CREATESTRUCTA*)l` |
| `WM_DESTROY` | `virtual void EvDestroy();` | (no args) |
| `WM_PAINT` | `virtual void EvPaint();` | (no args; handler constructs `TPaintDC`) |
| `WM_LBUTTONDOWN` | `virtual void EvLButtonDown(UINT modKeys, TPoint& pt);` | `modKeys = (UINT)w; pt.x = LOWORD(l); pt.y = HIWORD(l);` |
| `WM_LBUTTONUP` | `virtual void EvLButtonUp(UINT modKeys, TPoint& pt);` | same as above |
| `WM_MOUSEMOVE` | `virtual void EvMouseMove(UINT modKeys, TPoint& pt);` | same as above |
| `WM_COMMAND` | `virtual void EvCommand(UINT id, HWND hCtl, UINT notifyCode);` | `id = LOWORD(w); notifyCode = HIWORD(w); hCtl = (HWND)l;` |
| `WM_KEYDOWN` | `virtual void EvKeyDown(UINT vkey, UINT repeatCount, UINT flags);` | `vkey = (UINT)w; repeatCount = (UINT)l & 0xFFFF; flags = (UINT)(l >> 16);` |

That is **8 virtuals** (slight expansion of the 7 in the §E-a
trade-off summary: `WM_LBUTTONUP` is cheap and the natural pair of
`WM_LBUTTONDOWN`; counted as one bloat unit). All defaults are
empty bodies (no-op), so `EvX` virtuals without an override
contribute zero observable behaviour — same idea as the v1
default `TApplication::InitMainWindow()` (`src/pp.rs:235`).

**The macros (in `OWL_RUNTIME_H`).** Borland's OWL response
tables are *function-like* preprocessor macros — mdbcc's `pp.rs`
already supports function-like macros (`Macro::Func {params,
variadic, body}`, `src/pp.rs:414`, `:682`, `:833`). The
expansion shape:

```cpp
#define DECLARE_RESPONSE_TABLE(cls) \
    virtual LRESULT WindowProc(UINT msg, WPARAM w, LPARAM l)

#define DEFINE_RESPONSE_TABLE1(cls, base) \
    LRESULT cls::WindowProc(UINT msg, WPARAM w, LPARAM l) {

#define EV_WM_PAINT       if (msg == WM_PAINT)       { this->EvPaint();                                                                       return 0; }
#define EV_WM_DESTROY     if (msg == WM_DESTROY)     { this->EvDestroy();    PostQuitMessage(0);                                              return 0; }
#define EV_WM_LBUTTONDOWN if (msg == WM_LBUTTONDOWN) { TPoint _p; _p.x = (LONG)(short)((l) & 0xFFFF); _p.y = (LONG)(short)(((l) >> 16) & 0xFFFF); this->EvLButtonDown((UINT)(w), _p); return 0; }
#define EV_WM_LBUTTONUP   if (msg == WM_LBUTTONUP)   { TPoint _p; _p.x = (LONG)(short)((l) & 0xFFFF); _p.y = (LONG)(short)(((l) >> 16) & 0xFFFF); this->EvLButtonUp((UINT)(w), _p);   return 0; }
#define EV_WM_MOUSEMOVE   if (msg == WM_MOUSEMOVE)   { TPoint _p; _p.x = (LONG)(short)((l) & 0xFFFF); _p.y = (LONG)(short)(((l) >> 16) & 0xFFFF); this->EvMouseMove((UINT)(w), _p);   return 0; }
#define EV_WM_COMMAND     if (msg == WM_COMMAND)     { this->EvCommand((UINT)((w) & 0xFFFF), (HWND)(l), (UINT)((w) >> 16)); return 0; }
#define EV_WM_KEYDOWN     if (msg == WM_KEYDOWN)     { this->EvKeyDown((UINT)(w), (UINT)((l) & 0xFFFF), (UINT)((l) >> 16)); return 0; }
#define EV_WM_CREATE      if (msg == WM_CREATE)      { CREATESTRUCTA *_cs = (CREATESTRUCTA *)(l); if (this->EvCreate(*_cs)) return 0; else return -1; }

#define END_RESPONSE_TABLE \
    return base_WindowProc(msg, w, l); }
```

Two design decisions in those macro bodies:

1. **`END_RESPONSE_TABLE` calls a parent-class link, not the
   second arg of `DEFINE_RESPONSE_TABLE1` directly.** Why: mdbcc's
   parser does not currently parse a *qualified* method call like
   `TFrameWindow::WindowProc(msg, w, l)` (it does parse `Tag::name`
   for declarations but the call form in expression position is
   not exercised — verifying parser support is an *E1 finding*,
   not an architectural assumption). The minimal workaround is to
   emit a **non-virtual member helper** on `TWindow` —
   `LRESULT base_WindowProc(UINT m, WPARAM w, LPARAM l) { return
   DefWindowProcA(HWindow, m, w, l); }` — and have
   `END_RESPONSE_TABLE` call `this->base_WindowProc(...)` (an
   ordinary method call, well-trodden). Honest: this short-
   circuits the chained parent-class behaviour Borland's OWL
   would give (in real OWL, `DEFINE_RESPONSE_TABLE1(TMyWin,
   TFrameWindow)` chains *through* `TFrameWindow::WindowProc`
   first, and only *then* falls to `DefWindowProc`). For v1 this
   has **no observable effect** because `TFrameWindow` has *no*
   response table of its own and `TWindow::WindowProc` already
   calls `DefWindowProcA` (`src/pp.rs:325-331`). Promoted to
   **B-11 (Phase E backlog) — true parent-class
   `WindowProc` chaining via qualified-call syntax** if a Phase-I
   target app overrides `TFrameWindow::WindowProc` (none of the
   v1 hello/click apps do).
2. **The `EV_WM_LBUTTONDOWN` cracker uses sign-extended `short`
   casts** — matches Win32's documented signed-coordinate
   semantics (negative x/y when the mouse drags outside the
   client area). The `(short)` cast is a parser-already-tested
   construct (Phase D's `LONG_PTR` cast chain in
   `OWL_RUNTIME_H::Create` is the precedent). If `short` is not
   yet a `decl_specifier` arm (verify in E1 with a
   smallest-reproducer compile; not asserted blind), fall back
   to a manual mask + branch (`((int32_t)l) & 0x8000 ? ... :
   ...`) — recorded as an *E1 finding* path, not a fork.

**Scope discipline (verbatim house style):** the `EV_WM_*` set
grows only when the Phase E O6 oracle literally names them. v1
ships *exactly* the 8 above. `WM_RBUTTONDOWN`, `WM_CHAR`,
`WM_TIMER`, `WM_HSCROLL`/`WM_VSCROLL`, `WM_SIZE`, etc. are
**deferred** (no test exercises them; the macro shape is
trivial to extend later — adding an `EV_WM_RBUTTONDOWN` is
copy-paste of the LBUTTON version).

### E-c — Message cracking detail (per-event)

The Win32 `WPARAM/LPARAM` packing for each v1 message:

- `WM_PAINT`: w=0, l=0 (no args; the handler must construct a
  `TPaintDC` itself — §E-d).
- `WM_LBUTTONDOWN`/`UP`/`WM_MOUSEMOVE`: w = `MK_*` modifier-key
  bits (`MK_LBUTTON 0x0001`, `MK_RBUTTON 0x0002`, `MK_SHIFT
  0x0004`, `MK_CONTROL 0x0008`, `MK_MBUTTON 0x0010`); l =
  `MAKELPARAM(x, y)` with x/y as **signed** 16-bit ints (negatives
  legal). Crack: `pt.x = (LONG)(short)(l & 0xFFFF); pt.y =
  (LONG)(short)((l >> 16) & 0xFFFF);` (the sign-extending `short`
  cast — see §E-b decision 2).
- `WM_COMMAND`: w-low = control/menu ID, w-high = notification
  code, l = HWND of the control (or 0 for menu). Crack:
  `id = LOWORD(w); notifyCode = HIWORD(w); hCtl = (HWND)l;`.
- `WM_KEYDOWN`: w = virtual-key code (`VK_*`), l-low = repeat
  count, l-high = scan code + flags. Crack via mask/shift as
  in the macro body above.
- `WM_CREATE`: w = 0, l = `CREATESTRUCTA*`. Crack: dereference
  via `*(CREATESTRUCTA*)l` and pass by reference. **Note**:
  this *aliases* the same `lpCreateParams` that `WM_NCCREATE`
  uses (`src/pp.rs:336-340`); Phase D's thunk consumes
  `lpCreateParams` in `WM_NCCREATE` and `WM_CREATE` simply
  passes the struct through to the user. Return value: `false`
  from `EvCreate` ⇒ creation aborts (returns `-1` from
  `WindowProc`); `true` ⇒ proceed (returns 0).
- `WM_DESTROY`: w=0, l=0. The macro **also** posts
  `WM_QUIT` (`PostQuitMessage(0)` *after* the user's
  `EvDestroy()` returns) — this preserves Phase D's clean exit
  chain (a user `EvDestroy` that does *nothing* still results
  in `WM_QUIT` ⇒ loop exit). If a user app wants to *prevent*
  exit (multi-window scenarios in Phase E v2), the right hook
  is `EvClose` (NOT in v1; deferred — same scope-discipline as
  the EV_WM_* set).

`LOWORD`/`HIWORD` are intentionally **not** added to
`<windows.h>` — the inline masks (`(w) & 0xFFFF`, `(w) >> 16`)
inside the `EV_WM_*` macros are mechanical and avoid yet
another macro layer. Decision is *taste*, recorded; if a real
target app names `LOWORD`/`HIWORD` in user code, add them then
(no speculative abstraction).

### E-d — `TDC`/`TPaintDC` RAII (the new GDI-touching classes)

**`TPoint`** — a tiny value-like struct (NOT polymorphic; no
vptr) added to `OWL_RUNTIME_H` *before* the `EV_*` macros that
reference it. Mirrors Borland's OWL `TPoint`:
```cpp
struct TPoint { LONG x; LONG y; };  // Win64-aligned, 8 bytes
```
**Not a class** (no methods; struct keyword to avoid Phase-B's
"polymorphic-derived-of-base-with-data-but-no-virtuals" guard
that bit D4). It is *passed by reference* (`TPoint& pt`) to
event handlers — struct-by-value remains unsupported
(`src/codegen.rs:468-470`, `:1055-1057`), so the by-reference
discipline is preserved from Phase D.

**`TDC`** — a thin base wrapping an `HDC` (the OWL public
parent of `TPaintDC`; `TClientDC`, `TScreenDC`, etc. derive
from it but are **out of v1 scope**):
```cpp
class TDC {
public:
    HDC GetHDC() const { return hdc; }
    void TextOut(int x, int y, const char *s, int len) { TextOutA(hdc, x, y, s, len); }
protected:
    HDC hdc;
    TDC() { hdc = 0; }
    virtual ~TDC() {}
};
```
- `TextOut` calls `TextOutA(GDI32.dll)` — **the new GDI32
  import** (E3). Phase B's mechanism (`is_win32_import` →
  `emit_win32_call` → indirect call through IAT) handles this
  with zero new codegen; `WIN32_IMPORTS` simply gains
  `("TextOutA", "GDI32.dll")`. **Console dormancy unchanged**
  (program references no GDI32 ⇒ `used_dlls` excludes GDI32 ⇒
  byte-identical `.idata`; `tests/pe_imports.rs` golden
  unchanged — locked by the same C1a/C1b mechanism that already
  proved this argument with the USER32 additions).
- `TDC` is polymorphic (virtual dtor) — derived classes
  (`TPaintDC`) need their own dtor to run. Phase B handles this.
- **What about `TClientDC`?** A `TClientDC` (uses `GetDC`/
  `ReleaseDC` rather than `BeginPaint`/`EndPaint`, drawn from
  outside `WM_PAINT`) is the natural OWL counterpart to
  `TPaintDC`. **Deferred** — the v1 Phase E oracle exercises
  drawing *inside* `EvPaint`, not the asynchronous-redraw case.
  Recorded as **B-12 (Phase E backlog) — `TClientDC` + the
  `GetDC`/`ReleaseDC` USER32 pair** if a Phase-I app needs it.

**`TPaintDC`** — RAII over `BeginPaint`/`EndPaint`:
```cpp
class TPaintDC : public TDC {
public:
    HWND hwnd;
    PAINTSTRUCT ps;
    TPaintDC(TWindow& w) {
        hwnd = w.HWindow;
        hdc = BeginPaint(hwnd, &ps);     // sets this->hdc (TDC base)
    }
    virtual ~TPaintDC() {
        EndPaint(hwnd, &ps);
    }
};
```
- The `TWindow&` ctor signature matches Borland's. Phase B
  vptr-install at the end of the ctor sets `TPaintDC`'s vtable
  (the polymorphic Phase-B path; D5 already exercises this
  pattern for `TFrameWindow`).
- The dtor runs at scope exit (`{` `}` block in `EvPaint`) —
  Phase B's RAII auto-dtor is the proven mechanism (verified by
  Phase B's `tests/virtual.rs` dtor-order assertions). A user's
  `EvPaint` writes:
  ```cpp
  void TMyWin::EvPaint() {
      TPaintDC dc(*this);
      dc.TextOut(20, 20, "Hello, OWL!", 11);
      // dc goes out of scope ⇒ ~TPaintDC ⇒ EndPaint
  }
  ```
- **`BeginPaint`/`EndPaint` are USER32, NOT GDI32** — verified
  against the Win32 docs (and the Win16 reference: `USER`
  ordinals 39/40). The `HDC` they yield is then used with
  `GDI32` functions (`TextOutA`, etc.). E2 therefore adds *only*
  USER32 symbols (no GDI32 yet); E3 is the first GDI32
  addition. Splitting this across two increments isolates the
  multi-DLL .idata growth from the RAII class infrastructure.
- `PAINTSTRUCT` is added to `WINDOWS_H`:
  ```c
  struct tagPAINTSTRUCT {
      HDC  hdc;
      BOOL fErase;
      RECT rcPaint;
      BOOL fRestore;     // reserved
      BOOL fIncUpdate;   // reserved
      BYTE rgbReserved[32];  // 32 bytes per Win32 docs
  };
  typedef struct tagPAINTSTRUCT PAINTSTRUCT;
  ```
  with the standard Win64 layout. **The `BYTE` type and array
  member need parser support**: `BYTE` is `unsigned char`
  (already supported via `typedef unsigned char BYTE;` — add
  to `WINDOWS_H`). Fixed-size array members (`BYTE x[32]`) are
  already used in mdbcc's parser? — **verify in E2**. If not,
  the workaround is to widen the reserved space with named
  scalars (`DWORD r0,r1,r2,r3,r4,r5,r6,r7;` = 32 bytes), which
  is an array-of-bytes substitute that does not need
  array-member parsing. Recorded as an **E2 finding** path —
  do not assume; smallest-reproducer compile is the oracle.

### E-e — Default behaviour fallback

For every `EV_WM_*` macro instance in a user's response table,
**only the corresponding message is matched**. All other
messages fall through the `if`-chain to `END_RESPONSE_TABLE`,
which `return this->base_WindowProc(msg, w, l);` (the
parent-link helper, §E-b decision 1) — which is
`DefWindowProcA(HWindow, msg, w, l)`. *Behaviour is exactly the
same as Phase D's `WindowProc`* for unmatched messages (already
verified working through O6).

**Honest about the dispatch path:**
- A user class with *no* response table (the D5 hello app)
  inherits `TWindow::WindowProc` from `OWL_RUNTIME_H`, whose
  body handles `WM_DESTROY` and falls to `DefWindowProcA`. v1
  Phase D behaviour is preserved.
- A user class with a response table **overrides
  `WindowProc`** (via the macro expansion). Its handlers fire
  for matched messages; everything else goes through
  `base_WindowProc` → `DefWindowProcA`. Note: `WM_DESTROY`
  posted by a user's response table goes via the
  `EV_WM_DESTROY` cracker, which **also calls
  `PostQuitMessage(0)`** — so the clean-exit chain (Phase D
  §D-d teardown) is preserved by *both* paths: the
  base-class default (`TWindow::WindowProc`) and the
  response-table dispatch.
- **Diamond risk: a user class with a response table that
  *omits* `EV_WM_DESTROY` would never post `WM_QUIT` and the
  loop would hang.** This is a real footgun. *Mitigation*:
  document it in the OWL header comment (the v1 hello-OWL
  precedent that says "include `EV_WM_DESTROY` if you have a
  response table") and rely on the watchdog in the O6 liveness
  test to catch the hang. Recorded as **B-13 (Phase E
  backlog) — auto-route `WM_DESTROY` to `PostQuitMessage`
  even without `EV_WM_DESTROY`**; small fix (have
  `base_WindowProc` post the quit when `msg == WM_DESTROY`
  before defaulting). For v1 we leave it explicit because the
  Phase-E O6 test *does* `EV_WM_DESTROY` and the principle
  "the user named it ⇒ the user owns it" is clearer.

### E-g — Console byte-identical regression (the central invariant, unchanged from C/D)

Every Phase E addition is **dormant for a console program**:
- **`<windows.h>` constant/struct growth (E1, E2)**: the body
  resolves only if a TU `#include <windows.h>`; any console
  program (no such include) ⇒ zero bytes emitted (parser-only
  artifact). Even a console program *that does* `#include
  <windows.h>` but uses no new constant emits zero bytes (the
  constants are object-macros; unused macros emit nothing).
- **`WIN32_IMPORTS` USER32/GDI32 growth (E2, E3, E4)**:
  `used_dlls`/`used_symbol` (`src/pe.rs:153`, `:181`) emit a
  DLL descriptor *only* if a `RipRef::Import` references its
  symbol. A console program references none ⇒ `["KERNEL32
  .dll"]` ⇒ `.idata` byte-identical ⇒ `tests/pe_imports.rs`
  golden unchanged (the executable proof, mechanical).
- **`OWL_RUNTIME_H` macro/class growth (E1, E2, E3)**: the
  whole OWL runtime body is gated on `owl/` prefix in
  `DefaultResolver::resolve` (`src/pp.rs:385-387`). A console
  program includes no `owl/*.h` ⇒ zero new bytes.
- **No new codegen feature, no new `RipRef` variant, no ABI
  change** ⇒ the determinism guard + O1 88-e2e + the unchanged
  `pe_imports`/`pe_layout` goldens are the executable proof,
  identical in form to Phases A/B/C/D. The byte-identical
  claim is *enforced by the unchanged golden tests*, not
  merely prose.

## Risks (honest)

1. **Macro-heavy headers stress the preprocessor.** OWL's
   `DECLARE_/DEFINE_RESPONSE_TABLE` + `EV_WM_*` are
   function-like / object-like preprocessor macros — mdbcc's
   `pp.rs` claims to support both (`Macro::Func {params,
   variadic, body}`, `:414`), and the existing intrinsic
   `WINDOWS_H` already uses object macros heavily (`WM_*`,
   `WS_*`, etc. — D1 proved this). *Mitigation*: the v1
   macros above use **only** the constructs `pp.rs` already
   exercises — function-like macros with a single named arg
   (`DECLARE_RESPONSE_TABLE(cls)`) and *object* macros
   (`EV_WM_*` take no args — they expand to literal `if`
   blocks). **No `__VA_ARGS__`, no `#` stringize, no `##`
   paste** are needed for v1. If a real OWL header needs
   them (e.g. for `EV_COMMAND(id, member)`), they are
   already supported per `pp.rs` doc comment; verify when
   Phase G needs `EV_COMMAND` proper. E1 is the empirical
   gate — a `DECLARE_RESPONSE_TABLE` + `EV_WM_DESTROY` user
   class either compiles or it does not.
2. **Vtable bloat from N `EvX` virtual slots on `TWindow`.**
   N = 8 in v1; every `TWindow` instance pays +8 vtable
   slots even with zero overrides. *Mitigation*: measure in
   E1's structural test (assert the vtable slot count;
   `sizeof(TWindow)` itself is unchanged because the vptr is
   one pointer regardless of vtable length — the *vtable*
   global is what grows). N stays *bounded* — extensions are
   gated by Phase-I app needs, never speculative. If Phase G
   adds `EV_COMMAND` properly with control-ID dispatch, the
   per-command callbacks should NOT consume vtable slots (a
   command-table-on-the-class is the right shape there;
   recorded as a Phase-G design constraint, not a v1 risk).
3. **The no-global-ctors gap remains.** Phase E's new state
   (vtables for `TPaintDC`, `TDC`, the `_OwlApp` if E5
   wires `GetApplication()`) are all either (a) const-init
   pointer/struct globals (vtable arrays are *pure
   const-data* — verified by Phase B/D5 already), or (b)
   per-instance state set imperatively in ctors. **No
   process-global object constructors are added.** v1
   carries this discipline from D-c verbatim.
4. **`switch` is still not parsed.** The response table
   *dispatch* uses an `if`-chain (the macro expansion in
   §E-b shows this), so v1 does not need `switch`. User
   handlers like `EvCommand` that need to discriminate by
   `id` must also use `if`-chains. *Mitigation*: documented
   in the OWL header comment as a known limitation;
   `switch` is recorded as a future parser feature
   (low priority — `if`-chains compile and run identically
   for small N). Not Phase-E-blocking.
5. **GDI32 multi-DLL imports — the third DLL.** E3 is the
   first time mdbcc emits a `.idata` with *three* DLLs
   (KERNEL32 + USER32 + GDI32). C1b's `emit_idata` was
   designed for k descriptors (`k = groups.len() as u32`,
   `src/pe.rs:237`) — exercised by 1 and 2 today, but k=3
   is new bytes. *Mitigation*: E3's structural test asserts
   the GDI32 descriptor + `TextOutA` ILT entry, and the
   PE-layout `tests/pe_layout.rs` tripwire (section
   alignment / size invariants) still covers correctness of
   the larger .idata. C1b's pure serializer is k-agnostic by
   construction (descriptors are emitted in a loop, ILT/IAT
   per group, etc.) — verified by `emit_idata` reading. Low
   residual risk.
6. **`SendMessageA` synchrony and the click test.** E4
   relies on `SendMessageA` being *synchronous* — the
   sender blocks until the WndProc returns. Win32
   semantics guarantee this only for *same-thread* sends; a
   cross-thread `SendMessageA` queues into the receiving
   thread's window and waits for it to process. The test
   harness sends from a different process; the OS still
   marshals correctly and waits, but a slow-painting
   handler could in principle delay. *Mitigation*: v1's
   `EvLButtonDown` is a trivial counter increment + a
   memory write; no painting, no allocation. Bound the
   wait with the existing `proc.wait(5000)` ms harness
   timeout (carried from C4/D5). If a future test exercises
   slow handlers, switch to `PostMessageA` + a small sleep
   + observable side effect.
7. **B-7/B-8/B-9 fold-ins.** Three review-tracked backlog
   items land in Phase E:
   - **B-7** (E2): natural fit — `TWindow::Create()`
     gains a `RegisterClassExA` return check while we are
     touching the runtime header for `TPaintDC`. Smallest
     change: `if (RegisterClassExA(&wc) == 0) return false;`
     before `CreateWindowExA`. Low risk.
   - **B-8** (E5): decide and act. Either remove `_OwlApp`
     (if no E1..E4 handler consumed it — likely, since v1
     hello-click does not need `GetApplication()`), OR
     add a `TApplication* GetApplication() { return
     _OwlApp; }` free function and write one test that
     uses it. **Recommendation: remove**; reinstate when a
     handler genuinely needs it (no speculative state).
   - **B-9** (E5): the parser laxity is real but
     low-impact (Phase A's reg-passing papers over it).
     *Recommendation: leave deferred* — write a one-line
     note in the OWL header about the expected signature
     and rely on link errors / silent UB if the user
     diverges. A scoped fix (param-type match on
     definitions referenced by a forward prototype) is a
     parser change with broader regression surface than
     Phase E should take. Call out to Arthur in E5
     review if the recommendation is challenged.
8. **Scope size.** Phase E is **smaller than Phase D**
   because (a) no new codegen, (b) the OWL runtime
   skeleton already exists, (c) the O6 harness exists.
   The bulk is: 8 `EvX` virtuals + 8 macros + `TPoint` +
   `TDC` + `TPaintDC` + 2 USER32 imports + 1 GDI32
   import + ~6 new constants + 2 new O6 tests. **No
   `src/codegen.rs` change, no `src/parser.rs` change**
   on the primary path; the only `src/*.rs` change is
   the table growth in `src/pe.rs` (one row per import)
   and the body growths in `src/pp.rs` (`WINDOWS_H`,
   `OWL_RUNTIME_H`) — `src/codegen.rs` and `src/parser.rs`
   are **untouched by Phase E**. This is the smallest
   meaningful OWL milestone after D5 and reflects the
   plan's "phase by phase, smallest reviewed green
   commit" discipline.
9. **Concurrent agents on `src/pe.rs`/`src/pp.rs`.** Same
   hot files as Phase C/D. *Mitigation* (carried from D's
   risk #7, charter §"Multi-agent environment"): apply on
   a confirmed-clean tree; each E1..E5 increment small/
   atomic; do not refactor unrelated code; the
   `WIN32_IMPORTS` and `WINDOWS_H`/`OWL_RUNTIME_H` growths
   are append-only (low collision risk).
