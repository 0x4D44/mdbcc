# HLD — Phase B: virtual functions, vtables, virtual destructors

Date: 2026-05-18. Status: DESIGN (Phase A landed; impl-ready).
Roadmap: `wrk_journals/2026.05.17 - PLAN - OWL Windows roadmap.md`.
Depends on Phase A (`RipRef::Func`, indirect `call` marshalling) — both
reused directly here.

## Why
OWL *is* virtual dispatch (TWindow/TApplication event handling). The
single biggest C++ gap. Pure portable C++ ⇒ fully O1/O2/O3-validated
(bcc32 5.5.1 fully supports virtual functions).

## Current implementation (read 2026-05-18, grounded)
- Methods mangled `Tag::name` in `sigs.funcs`; called via `emit_call`
  with `lead = this` (rcx). **`method_target` (codegen.rs:818) is
  STATIC dispatch**: walks the single-inheritance base chain, picks the
  most-derived class defining `name`. Phase B makes virtual methods
  *dynamic*.
- Single inheritance only; **base subobject at offset 0**, `this` needs
  no adjustment; base fields are flattened into the derived `Record`
  (scratchpad slice 13). `Record { base: Option<usize> }`.
- ctors/dtors exist; RAII auto-dtor at scope exit; base ctor/dtor
  chaining exists. `parser` only *skips* `virtual` in the base-clause —
  member `virtual` is not parsed.

## Object model (single inheritance; we own the ABI — Itanium-like)
- A class is **polymorphic** iff it or a base declares any `virtual`
  member (incl. virtual dtor).
- Polymorphic class ⇒ hidden **vptr at offset 0** (8 bytes), before all
  data members. Single inheritance + base-at-0 ⇒ the derived reuses the
  base's offset-0 vptr slot (one vptr per object). **Record-layout pass
  must reserve 8 at offset 0 and shift every data-member offset by 8
  when a class is polymorphic** (base flattening must keep exactly one
  vptr at 0, not duplicate). Non-polymorphic classes are unchanged ⇒
  the 88 O1 e2e stay byte-identical (same regression argument as
  Phase A).
- **vtable** per polymorphic class: ordered slots = base virtuals in
  declaration order, then this class's new virtuals; an override (same
  name + param types, single-inheritance) replaces the inherited slot.
  Emitted read-only; each slot is a function address ⇒ **reuse Phase
  A `RipRef::Func`** per slot (linker fills text RVAs). Modelled as a
  synthesized per-class global ("vtable symbol") in `.rdata`/`.data`;
  the ctor does `lea rax,[rip+vtbl]; mov [this+0],rax`.
- **ctor**: after base-ctor chaining, store *this class's* vtable into
  `[this+0]` (standard observable semantics: base ctor sees base
  vtable, derived ctor overwrites).
- **virtual call**: `recv.m(a)` / `p->m(a)` where `m` is virtual ⇒
  `mov rax,[this]; mov rax,[rax + slot*8]; call rax` — i.e. reuse
  Phase A's indirect-call register+stack marshalling with the callee
  loaded from the vtable instead of `lea RipRef::Func`. Non-virtual
  methods keep the existing direct `call Tag::m`.
- **virtual destructor**: a virtual dtor takes a vtable slot; `delete p`
  where `p`'s static class has a virtual dtor dispatches the dtor
  through the vptr (so `delete (Base*)d` runs `Derived::~Derived` then
  chains to base) — reuses the `delete` path + virtual dispatch.
- **pure virtual** `= 0` ⇒ abstract: instantiating it (`T v;`/`new T`)
  is a clear `CodegenError`; the slot points at a "pure virtual called"
  trap stub (never silently wrong — house style).
- Deferred (explicit, OWL-survey-gated): multiple/virtual inheritance
  (OWL 2.5 uses some mixin MI — revisit when genuine OWL headers are
  surveyed in Phase 0), RTTI/`dynamic_cast`, covariant returns,
  `virtual` operator/`this`-adjusting thunks.

## Parser changes
- Parse `virtual` on member declarations/definitions (currently only
  base-clause-skipped). Record per class: method → {virtual?, pure?
  (`= 0`)}. Class-body collector already exists; add the two flags.

## Codegen / linker changes
1. Record layout: vptr slot at offset 0 for polymorphic classes; shift
   data members +8; base-flatten keeps one vptr.
2. Per-polymorphic-class vtable: deterministic slot order
   (base-first, declaration order; overrides replace). Synthesize a
   read-only "vtable global" of 8-byte slots, each a `RipRef::Func`
   (or a small new `RipRef::Vtable`/reuse Data) → linker writes text
   RVAs. ctor injects `lea`+store of the vptr after base-ctor chain.
3. `method_target` / MethodCall codegen: if resolved method is
   virtual, emit the vtable indirect dispatch (reuse Phase A
   `emit_indirect_call` marshalling with a vtable-slot callee) instead
   of the direct mangled `call`. `delete`/dtor path: virtual dtor ⇒
   dispatch through vptr.
4. Determinism: vtable contents/order are a pure function of
   declaration order (no HashMap iteration into bytes — same discipline
   verified in Phase A).

## Risks (honest)
- The subtle part is vptr-at-0 vs base-at-0 flattening + the +8
  data-member offset shift; every field access/sizeof/struct-copy must
  see the shifted layout. Mitigation: non-polymorphic byte-identical
  regression (88 e2e) + dedicated virtual tests + three-way O2/O3.
- Vtable-in-`.rdata` is the only new linker infra; mirrors Phase A's
  `.data` global + `RipRef::Func` (low risk, proven mechanism).
- MI deferral may bite genuine OWL 2.5 (mixins) — flagged for the
  Phase 0 OWL-source survey to re-scope precisely (don't pre-build it;
  CLAUDE.md: no speculative abstraction).
