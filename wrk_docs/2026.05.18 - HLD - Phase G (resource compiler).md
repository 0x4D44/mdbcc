## Purpose

Phase G enables real OWL apps to ship menus, dialogs, accelerator
tables, and string tables via the standard `.rc` toolchain: an
mdbcc-compiled program calls `LoadStringA` / `LoadMenuA` /
`LoadAcceleratorsA` / `DialogBoxParamA` and the OS retrieves them
from the PE's `.rsrc` section, identical to what `link.exe` or
`ilink` would produce. Prerequisite for Phase I's OWL `TDialog` /
`TMenu` classes. Smaller-scoped than Phase H (no codegen changes; a
self-contained `.rc` front-end + one more `build_*` helper in
`src/pe.rs`) ⇒ parallelisable with Phase F per the roadmap. Real
brc32/brcc32 binaries are present at `wrk_tools/BCC55/Bin/` ⇒ the
**byte-exact .res differential** is *available*, not stubbed.

## Scope-in / scope-out

**In (v1):** `.rc` grammar subset = `STRINGTABLE`, `MENU` /
`MENUEX`, `ACCELERATORS`, `DIALOG` / `DIALOGEX`, plus `LANGUAGE`
and `#define`-style symbolic constants. `.res` binary writer. PE
`.rsrc` section (three-level Type→Name→Lang resource tree, DWORD-
aligned data block, data-directory[2] = RESOURCE). Runtime imports:
`LoadStringA`, `LoadMenuA`, `LoadAcceleratorsA`, `DialogBoxParamA`,
`EndDialog`, `TranslateAcceleratorA`. CLI: auto-detect a sibling
`foo.rc` for input `foo.c`/`foo.cpp` (single-pass, integrated).

**Out (G-future; not speculatively shipped):** `BITMAP` / `ICON` /
`CURSOR` (file-format heavy, `.bmp`/`.ico` parsing + RT_GROUP_ICON
indirection; not on the critical path) — **G-future-1**.
`RT_VERSION` (cosmetic) — **G-future-2**. `RT_MANIFEST` (Common
Controls v6 / DPI; v1 dialogs use classic controls) —
**G-future-3**. `DLGTEMPLATEEX` (the *extended* dialog template
with `dwHelpID`; classic `DLGTEMPLATE` suffices for Borland-era
OWL) — **G-future-4**. General `#include "windows.h"` inside `.rc`
— **G-future-5** (see Open Question 2). Non-ASCII UTF-8 source —
**G-future-6**.

## Increments G1..G6 (smallest-first, independently green-committable)

Per charter: each increment ends green, clippy-clean, committable;
O1 `tests/end_to_end.rs` (88) byte-identical throughout (no

### G1 — `.rc` lexer/parser scaffolding (STRINGTABLE only)

New module `src/rc/{mod,lexer,parser}.rs`. Lexer recognises `.rc`
tokens (identifiers, integers, quoted strings, keywords:
`STRINGTABLE`/`BEGIN`/`END`, comma/braces). Parser produces an
in-memory `RcModule` containing one `Resource::StringTable { entries:
Vec<(u16, String)> }`. **No codegen, no PE change.**

- **RED**: `tests/rc_parse.rs` — parse a minimal STRINGTABLE; assert
  AST shape; assert errors on malformed input.
- **GREEN**: ~150-300 LoC across `src/rc/*`.
- **Regression**: `src/rc/*` is dead code for non-resource TUs ⇒ O1
  e2e byte-identical.

### G2 — `.res` binary writer + brc32 differential (**the central oracle**)

New `src/rc/res.rs` writes `RcModule` → Win32 `.res` byte stream.
For STRINGTABLE only initially. `.res` records carry
`(DataSize, HeaderSize, Type, Name, Lang, … , Data)`; strings are
**UTF-16LE counted strings** (Risk 3 — the #1 byte-diff source).

New test `tests/rc_res.rs`: fixed corpus under `tests/corpus/rc/`
(3-5 small inputs). Per input:

1. mdbcc in-process: `.rc` → `mdbcc_res: Vec<u8>`.
2. brc32 (`wrk_tools/BCC55/Bin/brc32.exe`, 69 KB — confirmed
   present): `brc32 -r -fo out.res input.rc` (`-r` = compile to
   .res only, don't bind to .exe).
3. **Assert byte-identical**; on mismatch, structural diff helper
   reports the first divergent field.

**brc32 vs brcc32**: `brc32.exe` (resource shell) and `brcc32.exe`
(dedicated compiler) produce equivalent `.res` for our v1 inputs;
we use `brc32 -r`. If a divergence is found, prefer `brcc32`.

**Fallback** (no brc32 in CI): per-corpus hand-rolled goldens with
a `// TODO oracle brc32` marker — same `Option<Brc>` pattern as
`bcc()` in `tests/support/mod.rs:496-508`. brc32 *is* present in
our sandbox ⇒ exercised, not theoretical.

### G3 — PE `.rsrc` section emission

Extend `src/pe.rs` with
`fn build_rsrc(module: &Module, rsrc_rva: u32) -> Result<Rsrc,
CodegenError>` mirroring `build_idata` (`src/pe.rs:375`): pure
layout core; module-driven wrapper; an `Rsrc` struct carrying
`image: Vec<u8>` + `dir_rva` + `dir_size`. The three-level resource
tree (Type → Name → Lang → DataEntry) is the Win32-canonical
encoding; DataEntry RVAs are patched once `rsrc_rva` is pinned
(same shape as `build_data`'s string-RVA rebase at
`src/pe.rs:712-715`).

**Section placement**: `.rsrc` appended *after* `.data` (last
section, characteristics `0x4000_0040` = INITIALIZED_DATA | READ).
**Section table grows from 4 to 5 entries iff the TU emits
resources**; otherwise stays 4 (gated on
`module.resources.is_empty()` — the byte-identical regression
boundary).

**Data-directory[2] = RESOURCE**: `src/pe.rs:794-801` today fills
only `dirs[1]` (Import) and `dirs[12]` (IAT). G3 adds
`dirs[2] = (rsrc.dir_rva, rsrc.dir_size)` *iff* resources present;
zero otherwise.

`WIN32_IMPORTS` += `LoadStringA` (USER32), `GetModuleHandleA`
(KERNEL32 — verify if already present from Phase D).

- **Structural test** `tests/pe_rsrc.rs`: minimal mdbcc program
  with one STRINGTABLE ⇒ `.rsrc` at index 4; `NumberOfSections =
  5`; section alignment correct; dirs[2] non-zero;
  dirs[12] (IAT) unchanged.
- **Positive smoke**: an mdbcc program calls
  `LoadStringA(GetModuleHandleA(NULL), 1, buf, 256); puts(buf);`,
  runs on Windows 11, prints the embedded string — executable
  proof the loader parses `.rsrc`.
- **Regression**: O1 e2e (88) byte-identical (no test program
  embeds resources; `NumberOfSections == 4`; dirs[2] zero).

### G4 — MENU + ACCELERATORS

Extend G1's parser + G2's writer with `MENU` (tree of
`MENUITEM "text", id [, flags]` and `POPUP "text" BEGIN ... END`
records) and `ACCELERATORS` (flat array of
`{WORD fVirt, WORD key, WORD cmd, WORD pad}` with `fVirt & 0x80`
marking the terminator).

`WIN32_IMPORTS` += `LoadMenuA`, `LoadAcceleratorsA`,
`TranslateAcceleratorA` (USER32). `<windows.h>` += `MF_*` menu
flags, `FVIRTKEY`/`FSHIFT`/`FCONTROL`/`FALT` accelerator flags.

**O6 positive test** `PROG_G4_MENU` (extends `tests/gui.rs` per
Phase E §E-f precedent): mdbcc-built program embeds a MENU (one
"File" popup, one "Exit" item id=IDM_EXIT) and an ACCELERATORS
table; in `WinMain`, calls `LoadMenuA(hInstance, 1)` and
`LoadAcceleratorsA(hInstance, 1)`; `printf("MENU=%p ACCEL=%p\n",
hMenu, hAccel)`. Test asserts both handles **non-null** —
loader-visible proof `.rsrc` carries parseable MENU/ACCEL records.

Visual on-screen menu rendering is a Phase-I (`TMenu` class)
concern; G4's oracle is *handle non-null*, the loader oracle.

### G5 — DIALOG / DIALOGEX (heaviest piece)

`DLGTEMPLATE` binary layout = `{style, dwExtendedStyle, cdit, x, y,
cx, cy, menu, windowClass, title [, pointsize, typeface]}` followed
by `cdit × DLGITEMTEMPLATE` records, **each DWORD-aligned** (Risk
1 — the #1 dialog-fails-to-load failure mode). v1 `.rc` grammar
supports: `DIALOG` with `STYLE`/`CAPTION`/`FONT` statements; the
control set `PUSHBUTTON`/`DEFPUSHBUTTON`/`LTEXT`/`EDITTEXT` (the
minimum for a v1 OK/Cancel dialog).

`WIN32_IMPORTS` += `DialogBoxParamA`, `EndDialog` (USER32);
`SendMessageA` reused from Phase E E4.

**O6 positive test** `PROG_G5_DIALOG`:
1. Embeds a trivial DIALOG (one `DEFPUSHBUTTON "OK"`, id=IDOK=1).
2. `WinMain` calls `DialogBoxParamA(hInstance, 1, NULL, DlgProc,
   0)`.
3. `DlgProc` handles `WM_INITDIALOG` (return TRUE) and `WM_COMMAND`
   (`if LOWORD(wParam) == IDOK then EndDialog(hwnd, 0)`).
4. Harness (same `extern "system"` FFI block as Phase D5/E4, in
   `tests/gui.rs:215-231`, extended): find dialog by caption;
   `PostMessageA(hwnd, WM_COMMAND, IDOK, 0)` from a separate
   thread; wait for process exit within the existing 5s
   watchdog; assert exit-code 0.
5. Stdout assertion: `printf("DIALOG_RETURN=%d\n", ret)` — dialog
   completed cleanly (not watchdog-killed).

**New files (G3-G5):** `tests/pe_rsrc.rs`; extensions to
`tests/gui.rs` (`PROG_G4_MENU`, `PROG_G5_DIALOG` — *extended*, not
forked, per Phase E precedent).

**Modified (additive only):**
- `src/pe.rs` — `build_rsrc` (~80-120 LoC, mirrors `build_idata`);
  section table 4→5 iff resources present; `dirs[2]` populated when
  resources present; `WIN32_IMPORTS` rows for the new symbols.
- `src/pp.rs` — `WINDOWS_H` += `MF_*`/`FVIRTKEY`/`IDOK` object-
  macros (dormant if unused; same shape as Phase C/D constant
  growth).
- `src/lib.rs` — `pub mod rc;` export.
- `src/main.rs` — sibling-`.rc` auto-detect (CLI choice justified
  below).

**Module placement — new `src/rc/*`, not sibling of
`src/parser.rs`**: `.rc` grammar is disjoint from C/C++ (different
tokens, different keywords, no shared AST). Folding into
`src/parser.rs` would double the file and conflate grammars. The
`src/pp.rs` `DefaultResolver` (`src/pp.rs:458-490`) already
distinguishes intrinsic bodies (`WINDOWS_H`, `OWL_RUNTIME_H`) — a
parallel pattern for `.rc` fits cleanly as its own module called
by the driver. House style: one grammar per module.

**CLI — auto-detect sibling `.rc`**: input `foo.c` ⇒ look for
`foo.rc` in the same dir; if present, compile both in one pass.
Justification: zero flag drift; matches Borland's `bcc32` driver
UX; single-pass keeps the library surface symmetric (one input ⇒
one .exe). Rejecting `--rc <path>`: speculative abstraction; add
only when a Phase-I app needs unusual build layouts.

## brc32 differential (central Phase-G oracle)

`wrk_tools/BCC55/Bin/brc32.exe` (69 KB, present). Invocation in
`tests/rc_res.rs`: `brc32 -r -fo <out.res> <input.rc>` (`-r` =
compile to `.res` only). Byte-for-byte comparison vs mdbcc's
in-process writer; structural diff on mismatch. Every resource
kind shipped in G1-G5 has a corpus entry that survives this
differential. **The only Phase-G test that exercises a real
third-party resource compiler**; without it, our `.res` could be
silently malformed in ways the OS loader tolerates but other tools
reject. Fallback: per-corpus hand-goldens with `// TODO oracle
brc32` marker if brc32 is absent.

## Risk register

1. **DWORD alignment between resource entries.** Loader expects
   every `IMAGE_RESOURCE_DATA_ENTRY` payload and `DLGITEMTEMPLATE`
   on a DWORD boundary; padding with zero. *Mitigation*:
   `align_to_dword` helper at every layout step (mirrors
   `align_up` in `src/pe.rs`); `tests/rc_res.rs` byte-diff vs
   brc32 catches drift mechanically. *Impact if missed*: dialog
   silently fails to load.
2. **DLGTEMPLATEEX deferral.** Modern `.rc` tends to emit
   DLGTEMPLATEEX (extended; `dwHelpID`, per-control help). v1
   ships only classic `DLGTEMPLATE` — sufficient for Borland-era
   OWL (DLGTEMPLATEEX is ~2002 / CC v6, post-dating OWL). Parser
   errors loudly on the extended form (`unsupported: DIALOGEX
   with version > 1`); never silently wrong. Recorded as
   G-future-4.
3. **Unicode strings in .res from ASCII source (#1 byte-diff
   source).** STRINGTABLE / MENU / DIALOG strings are stored as
   **UTF-16LE counted strings** in `.res`/`.rsrc`, even when `.rc`
   source is ASCII. `LoadStringA` / `LoadMenuA` get ANSI strings
   *only because* the OS transcodes on demand; on-disk bytes are
   Unicode. v1 supports ASCII-7 only (the corpus); non-ASCII UTF-8
   transcoding is G-future-6.
4. **Language ID default.** `LANGUAGE 0x09, 0x01` (LANG_ENGLISH +
   SUBLANG_ENGLISH_US ⇒ 0x0409) if no `LANGUAGE` statement. Per-
   resource overrides supported. v1 corpus uses the default.
5. **`.rsrc` placement.** Inserting between `.rdata` and `.data`
   would shift `.data`'s RVA and break every existing golden.
   Design appends `.rsrc` *after* `.data` ⇒ zero drift for the
   88-program corpus (which stays at `NumberOfSections = 4`).
6. **brc32 absence in CI.** Same problem `bcc()`-Option solved
   for bcc32 (`tests/support/mod.rs:496-508`); `tests/rc_res.rs`
   uses the identical pattern (`brc32()` returns `Option<Brc>`;
   tests skip gracefully if absent). Hand-golden fallback is the
   durable baseline.

## Open questions (genuine)

1. **Default code page** for ANSI transcoding from UTF-16:
   **Windows-1252** (Borland-era default) vs UTF-8 / 65001
   (modern). *Recommendation: 1252* — we target Borland-era app
   compatibility and the brc32 differential will *fail* if we
   diverge from brc32's CP assumption. Academic for v1 (corpus is
   ASCII-7); needs Arthur's call iff a Phase-I app uses non-ASCII
   menu text.
2. **`#include` inside `.rc`**: real Borland `.rc` commonly
   `#include <windows.h>` for `IDOK`/`WM_COMMAND`/`WS_*` symbols.
   Two options:
   - (a) Route `.rc` through `src/pp.rs`: full fidelity but couples
     `.rc` to the C header system (most of `<windows.h>` is
     nonsense to an `.rc` compiler).
   - (b) **`#define`-only subset internal to the `.rc` parser**:
     parser handles `#define NAME value` and hard-codes a small
     symbol table of common constants (`IDOK`/`IDCANCEL`/`MF_*`/
     `WS_*`) — mirrors Phase C's intrinsic-resolver model
     (`src/pp.rs:69`).
   - *Recommendation: (b)*; promote to (a) only if Phase-I forces
     it (G-future-5).
3. **Integrated vs standalone CLI**: (a) separate `mdrc` binary
   emits `.res`, consumed by `mdbcc -r foo.res`; (b) **integrated,
   auto-detect sibling `.rc`**. *Recommendation: (b)* — minimises
   user surface, matches Borland's single-driver UX, keeps
   library + binary symmetric (one input ⇒ one .exe). A `-rc`
   flag is added only if a real build layout needs it.
