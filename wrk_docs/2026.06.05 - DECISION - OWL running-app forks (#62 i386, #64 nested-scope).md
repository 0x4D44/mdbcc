## FORK #62 — target i386 (PE32), not win64, for the OWL apps

### Evidence (concrete, not theorised)
`SOURCE/OWL/WINDOW.CPP:885-900`:
```cpp
// per-window thunk. 'this' ptr is setup in register(s) by the thunk before
// StdWndProc is called.
StdWndProc(HWND, uint msg, WPARAM wParam, LPARAM lParam)
{
  return ((TWindow*)_EAX)->ReceiveMessage(msg, wParam, lParam);
}
```
OWL recovers the C++ `this` from the **`_EAX`** pseudo-register. `CreateInstanceThunk(TWindow*)`
(WINDOW.CPP:39, 199) generates a small piece of **x86 machine code** per window that
loads `this` into EAX, then jumps to `StdWndProc`, which reads it back via `_EAX`.

### Why win64 cannot represent this
- `_EAX` is a Borland **i386** pseudo-register (the 32-bit accumulator). The x64 ABI
  passes args in RCX/RDX/R8/R9 and has no "EAX holds `this`" convention — there is no
  faithful win64 lowering of `_EAX`.
- The instance thunk is hand-emitted **x86** instructions; an x64 thunk would be
  different machine code AND a different calling convention.

### The decisive point
The goal is **"behaviour matching the bcc32-built reference."** `bcc32` IS the 32-bit
Borland compiler — the reference binaries are 32-bit (PE32, i386). So "matching bcc32"
*inherently* means producing 32-bit code. A 32-bit PE32 **runs natively on Win11 x64
via WOW64** (the OS's built-in 32-bit subsystem — this is how the overwhelming majority
of legacy Windows apps run on x64 today), satisfying "runs natively on Win11 x64."
**The goal's own terms point at i386.** The win64 default was mdbcc's sensible choice
for a *modern* target; it is simply the wrong target for *this* conformance goal.

### Options
- **A (RECOMMENDED): target i386/PE32 for the OWL build.** mdbcc already has `-m32`
  (i386 PE32 emission) and the i386 path is **not speculative — it is a proven, oracle-
  tested base.** Empirically RE-VERIFIED this session: `mdbcc -m32 | mdlink -m32` produces
  a genuine **PE32 (Intel i386) executable that runs natively on Win11 x64 via WOW64** and
  returns the correct result for free-function calls, method calls (`this`), **C++ virtual
  dispatch through a base pointer, and `new`/`delete`** — the exact primitives OWL's window
  message routing depends on. `tests/i386_run.rs` already locks this with **101 run-tests**
  (incl. `i386_virtual_dispatch_base_ptr`: Animal/Dog/Cat polymorphism + virtual dtor +
  heap), each **diffed against the BCC 4.52 oracle** when present.
  (Caveat worth noting for whoever drives this: the i386 target requires `-m32` on BOTH
  `mdbcc` AND `mdlink`; mdlink defaults to Amd64, so an i386 object linked without `-m32`
  yields a malformed PE32+ that runs i386 bytes as x64 — silently wrong, not a crash at
  link. Auto-detecting machine from the COFF header would remove this footgun.)
  Prerequisites are concrete, non-architectural engineering once the target is chosen —
  the largest is **#28** (i386 throw/EH codegen — currently win64-only; OWL is exception-
  heavy: TXOwl etc.). A few smaller codegen paths are also currently win64-only and were
  explicitly deferred for i386 as built (placement/array-new of class types, the
  record-return-by-hidden-pointer ABI incl. the new virtual-call lead). Bounded follow-ons,
  not open-ended unknowns — a multi-increment effort on a VALIDATED foundation, not a leap.
- **B (NOT recommended): stay win64, rewrite the dispatch** (e.g. a HWND→`this` map via
  `SetWindowLongPtr`, as modern OWL/MFC ports do). This **diverges from the real BC45
  source** and would not be "recompiling real Borland C++ 4.52 source" nor guaranteed to
  match bcc32 behaviour. It defeats the PLAN's premise.

### If A: the concrete path to a running app
1. Confirm i386 as the OWL target (this decision).
2. Complete #28 (i386 EH codegen) — the only large non-architectural prerequisite.
3. Compile WINDOW.CPP + the OWL runtime objects in i386 (the `_EAX`/thunk now legal).
4. Link (mdlink) + run + behaviour-diff against the bcc32 HELLOAPP.EXE.

## FORK #64 — nested-class scoping vs the flat class model

### Evidence
Every streamable OWL class uses `DECLARE_STREAMABLE`, which defines a **nested**
`class Streamer`. mdbcc's record model is **FLAT**: it collapses `Outer::Inner` to the
innermost tag `Inner`. So `TButton::Streamer`, `TEdit::Streamer`, `TScrollBar::Streamer`,
… all collapse to one tag `Streamer` and collide. `GetObject()` (defined per-Streamer to
return `cls*`) then resolves to the wrong class, producing the **"no member named X"**
cluster:
- BUTTON.CPP:137 `is >> GetObject()->IsDefPB;`
- EDIT.CPP:838 `is >> GetObject()->Validator;`
- …~8-10 files (CHECKBOX, COMBOBOX, GROUPBOX, SCROLLBAR, STATIC, LISTBOX, …).

### Options
- **A (full): nested-class-qualified scoping** — track each nested class's enclosing
  class so `Outer::Inner` keeps its qualification and the Streamers stop colliding. A
  real refactor of the record/tag model; correct and general; touches a lot.
- **B (narrow, RECOMMENDED FIRST): context-resolve `GetObject()`** to the enclosing
  streamable class when compiling an out-of-line `X::Streamer::Read/Write`. Requires the
  parser to record the enclosing streamable class for a Streamer's out-of-line methods
  (it currently flattens that away). Smaller; unblocks the whole "no member" cluster;
  escalate to A only if other nested-scope collisions surface beyond Streamer.

### Recommendation
Take **B** first (cheap unblock of ~8-10 files); keep **A** as the fallback if nested
scoping bites elsewhere. (#64's blast radius is "compile breadth," not "can an app run" —
so it is lower-urgency than #62 for the *running-app* goal, but it is the single largest
remaining breadth cluster.)
