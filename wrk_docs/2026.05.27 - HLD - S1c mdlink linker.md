## Context anchor

S1b closed with mdbcc producing real COFF `.obj` files
(`bcc -c hello.c` → 155-byte .obj, lld-link accepts, exit-code matches).
**All of single-TU linking still happens inside `pe::write_pe_with_rsrc`**
on the in-process `Module` shape; the COFF file is a side-product, not yet
the production pipeline. S1c is the architectural fork: replace `pe.rs`
with `mdlink`, which consumes the COFF `Object` IR (from mdbcc) and OMF
`.obj` (from bcc32, per Decision-1A), plus libraries, and emits a PE.

After S1c, the pipeline forks once and converges once:

```
source ─► tokens ─► AST ─► Module ─► coff::Object ─► mdlink::link ─► PE
                                                          ▲
                                              OMF .obj ───┤   library .lib
                                              .def ───────┤   .res (RC output)
```

`compile_to_pe` becomes `compile_to_object + mdlink::link_single`. The
88 e2e tests + 17 determinism fixtures keep working because the path is
end-to-end equivalent (per Arthur's Q2 ratification: keep
`compile_to_pe` as a Rust API; only the `bcc` CLI shells to `mdlink`
when no `-c` is given). The test net catches regressions during the
port.

## §1 — Architecture

### §1.1 — Crate layout

mdlink lives in two places:

1. **Library** — `src/link/` (a new module tree). Public from `lib.rs`
   alongside `coff`, `compile`, etc.
2. **Binary** — `src/bin/mdlink.rs`, a thin CLI wrapper over the library.

```rust
// src/lib.rs — proposed delta
pub mod ast;
pub mod codegen;
pub mod coff;
pub mod compile;
pub mod eh;
pub mod lexer;
pub mod link;       // NEW — the linker library
pub mod parser;
pub mod pe;         // RETAINED through S1c.2; deletion or stub recommended
                    // at S1c.11 close (Q-Pe in §10)
pub mod pp;
pub mod rc;

pub use compile::{compile_to_object, compile_to_pe, CompileError};
pub use link::{link, link_single, LinkError, LinkOpts, Input};
```

The `src/link/` tree breaks down as:

```
src/link/
   mod.rs        — Public API: link, link_single, LinkOpts, LinkError, Input
   pe_writer.rs  — PE32+ writer (ported from src/pe.rs)
   resolve.rs    — Symbol resolution (CALLs and externs → defining symbol)
   merge.rs      — Section concatenation + RVA assignment
   reloc.rs      — Patch sites; computes final values per RelocKind
   idata.rs      — Import table synthesis (current pe.rs::build_idata)
   pdata.rs      — .pdata / .xdata layout for x64 SEH
   rsrc.rs       — .rsrc merge (port of pe::build_rsrc + multi-input merge)
   crt.rs        — Startup stub synthesis (.text$startup), global ctor walking
   omf.rs        — OMF .obj reader (lifted from tests/support/omf_walker.rs +
                   FIXUPP)
   archive.rs    — .lib archive reader (MS ar-style)
   defparse.rs   — .def file parser
```

Roughly ~3500 LoC total estimate (~2074 ported from pe.rs + ~1500 new for
multi-Object/OMF/archive/CRT). See §9 for the per-phase breakdown.

**Naming.** I deliberately picked `src/link/` over `src/mdlink/`:
- `link` is the noun the rest of the codebase already uses (the linker
  step in `compile.rs`'s docstring is called "the link step").
- `mdlink` is the binary name (Borland precedent: TLINK32 the binary, but
  the function in code is just "link").
- Matches `coff` / `eh` / `pp` / `rc` short module names already in tree.

### §1.2 — Public API signatures

```rust
// src/link/mod.rs

/// One input to the linker. Each variant carries the bytes plus a label
/// for diagnostic messages.
pub enum Input<'a> {
    /// In-memory COFF Object (used by `link_single` / `compile_to_pe`).
    Object(&'a coff::Object),
    /// On-disk COFF `.obj` bytes (mdbcc-produced or other COFF producer).
    CoffBytes { name: String, bytes: Vec<u8> },
    /// On-disk OMF `.obj` bytes (bcc32-produced). Decoded by `link::omf`.
    OmfBytes { name: String, bytes: Vec<u8> },
    /// On-disk static-library archive (MS `!<arch>\n` format). Members
    /// are pulled in on-demand to satisfy undefined externals.
    Archive { name: String, bytes: Vec<u8> },
    /// On-disk .def file (parsed; honoured for EXPORTS/NAME/STACKSIZE).
    DefFile { name: String, text: String },
    /// On-disk .res file (RC compiler output; merged into `.rsrc`).
    ResFile { name: String, bytes: Vec<u8> },
}

/// Linker options.
#[derive(Debug, Clone)]
pub struct LinkOpts {
    /// IMAGE_FILE_MACHINE_*. Today Amd64 only; I386 dormant.
    pub machine: coff::Machine,
    /// Subsystem: Console (3) or Gui (2).
    pub subsystem: Subsystem,
    /// Entry-point symbol. None = auto-select (CRT-startup-aware: pick
    /// `mainCRTStartup` if defined, else `main`, else `WinMain`).
    pub entry: Option<String>,
    /// ImageBase — fixed default for determinism (0x1_4000_0000), matches
    /// current pe.rs. Setting other values is supported but not exercised.
    pub image_base: u64,
    /// Stack reserve / commit; defaults match current pe.rs.
    pub stack_reserve: u64,
    pub stack_commit: u64,
    /// Heap reserve / commit; defaults match current pe.rs.
    pub heap_reserve: u64,
    pub heap_commit: u64,
    /// Whether to synthesise the CRT startup stub. True for a real EXE
    /// link; false for tests that link only their own startup.
    pub synthesise_crt: bool,
    /// Treat warnings as errors. Default false.
    pub warnings_as_errors: bool,
}

pub enum Subsystem { Console, Gui }

/// Linker error. Reports ALL unresolved externals (not just the first)
/// before failing — mirrors lld-link / link.exe diagnostics.
#[derive(Debug)]
pub enum LinkError {
    UnresolvedExternals(Vec<String>),
    DuplicateSymbol { name: String, first: String, second: String },
    BadInput { source: String, reason: String },
    Coff(coff::CoffError),
    Omf(link::omf::OmfError),
    PeOverflow { what: &'static str },
    Internal(String),
}

/// Single-TU shortcut: link one in-memory Object plus the synthesised
/// CRT startup into a PE. Used by `compile_to_pe` (the in-process fast
/// path that keeps the 88 e2e tests green).
///
/// This is `link(&[Input::Object(obj)], opts)` with the auto-default
/// LinkOpts pinned: console subsystem when `main` is defined, GUI when
/// `WinMain` is defined; CRT synthesis on.
pub fn link_single(
    obj: &coff::Object,
    opts: &LinkOpts,
) -> Result<Vec<u8>, LinkError>;

/// Multi-input link. Entry point for `mdlink foo.obj bar.obj -lc -o
/// foo.exe` and for any future multi-TU caller.
pub fn link(
    inputs: &[Input<'_>],
    opts: &LinkOpts,
) -> Result<Vec<u8>, LinkError>;
```

`link_single` is the lossless shortcut that preserves the 88 e2e
byte-identity invariants: it goes through the same `link` machinery but
with a pre-baked Input set of size 1 plus the synthesised startup. The
shortcut exists so that `compile_to_pe` does not need to construct an
Input slice and round-trip the Object through serialisation.

### §1.3 — `compile_to_pe` after S1c

```rust
// src/compile.rs (post-S1c)
pub fn compile_to_pe_with_rc(
    src: &[u8],
    file_name: &str,
    resolver: &dyn IncludeResolver,
    rc_unit: Option<&RcUnit>,
) -> Result<Vec<u8>, CompileError> {
    let object = compile_to_object_with(src, file_name, resolver)?;
    let opts = LinkOpts {
        machine: coff::Machine::Amd64,
        // Auto-pick subsystem from the Object: if `WinMain` is defined,
        // GUI; if `main` is defined, Console. (The Object exposes the
        // defined external symbols; the auto-pick lives in mdlink.)
        subsystem: link::auto_subsystem(&object),
        entry: None,                // mdlink picks mainCRTStartup
        image_base: 0x1_4000_0000,
        stack_reserve: 0x100000,
        stack_commit: 0x1000,
        heap_reserve: 0x100000,
        heap_commit: 0x1000,
        synthesise_crt: true,
        warnings_as_errors: false,
    };
    let exe = link::link_single(&object, &opts)?;
    // .rsrc merge: when rc_unit is Some, mdlink takes a synthesised
    // .res-equivalent Input (or we add an Input::RcUnit variant that
    // carries the parsed in-memory RcUnit, avoiding the .res emit
    // detour). The synthesis path is described in §2.5.
    let exe = if let Some(rc) = rc_unit {
        link::merge_rsrc_unit(exe, rc)?
    } else {
        exe
    };
    Ok(exe)
}
```

The seam matches the existing pipeline: compile produces an Object, the
linker produces a PE. The `rc_unit` parameter stays in `compile.rs` for
API compatibility (the 88 e2e + GUI tests already pass an `RcUnit` here
when a sibling `.rc` is found by the driver).

### §1.4 — `bcc foo.cpp` (no -c) after S1c lands

Per Arthur's Q2 (S1b.1 HLD): the Rust API stays in-process. The CLI
behaviour:

| Command                       | Behaviour                                  |
|-------------------------------|--------------------------------------------|
| `bcc -c foo.cpp` (today)      | `compile_to_object` → `.obj` (no change)   |
| `bcc foo.cpp` (no -c, today)  | `compile_to_pe` → `.exe` (in-process)     |
| `bcc foo.cpp` (no -c, post-S1c) | `compile_to_object` → `link_single` → `.exe` (in-process, **shells to mdlink only when multi-input**) |
| `bcc foo.cpp bar.cpp` (post-S1c) | Shells to `mdlink` (multi-input — out of `bcc`'s sweet spot, but recognised so user is not confused) |
| `mdlink foo.obj bar.obj -o foo.exe` | Standalone linker invocation |

**Recommendation**: `bcc foo.cpp` (single .cpp) **stays in-process** —
calls `compile_to_object` then `link::link_single` directly. This keeps
the 88 e2e fixtures green without a process-spawn dependency. Multi-file
`bcc foo.cpp bar.cpp` can be implemented later (S1c.10 or deferred to
S8); honest answer: a multi-file build should use mdlink directly. The
job of `bcc` is "compile one .cpp"; the job of `mdlink` is "link N
.obj/.lib/.res".

This means `bcc` never shells out to `mdlink` in the common case. The
"two CLI behaviours" Q2 spoke of are:
- bcc CLI: compile + link (in-process, single .cpp)
- mdlink CLI: link only (file inputs only)

Filed as Q-Bcc in §10 for Arthur's ratification — supervisor's
recommendation is the above.

## §2 — Linking algorithm

The link proceeds in seven passes; each pass is sequential and the
result of each is total-order deterministic.

### §2.1 — Pass 1: ingest

Each `Input` is decoded into a common intermediate `Module` (NOT to be
confused with `codegen::Module`; rename to `LinkInputModule` or similar
during S1c.5 to avoid the collision):

```rust
struct LinkInputModule {
    source: String,                          // diagnostic name
    sections: Vec<LinkInputSection>,         // copies of input sections
    symbols: Vec<LinkInputSymbol>,           // copies of input symbols
}

struct LinkInputSection {
    /// Canonical section name (after splitting off any COMDAT `$disc`).
    /// `.text$Foo` → "text" with comdat_key="Foo".
    canonical_name: SectionKind,
    /// Original full name (".text$Foo") — retained for diagnostics.
    raw_name: String,
    comdat_key: Option<String>,
    data: Vec<u8>,
    bss_size: u32,
    relocs: Vec<LinkInputReloc>,
    align: u32,                              // from IMAGE_SCN_ALIGN_*BYTES
    characteristics: u32,
}

enum SectionKind {
    Text,
    Data,
    Rdata,
    Bss,
    Pdata,
    Xdata,
    Drectve,                                 // honoured during pass 2
    CrtXcu,                                  // .CRT$XCU — ctor pointers
    CrtXcz,                                  // .CRT$XCZ — end sentinel
    CrtXcl,                                  // .CRT$XCL — beg sentinel
    Other(String),                           // pass-through (e.g. .debug$S)
}

struct LinkInputSymbol {
    name: String,
    section_ref: ResolvedSectionRef,         // Section(idx)/Undefined/Abs
    value: u32,
    storage: Storage,                        // External / Static / WeakExt
    is_function: bool,
    comdat: Option<ComdatLeader>,            // when this is a COMDAT leader
}
```

**COFF inputs.** `coff::Object::read` is the existing decoder. The
LinkInputModule construction is a direct mapping.

**OMF inputs.** §3 spells out the OMF→LinkInputModule mapping. The
existing `tests/support/omf_walker.rs` provides the record decoder; §3
adds FIXUPP decoding (relocations) and LIDATA/LEDATA payload assembly.

**Archives.** §4 spells out the ar format and member iteration. Each
member is itself a COFF or OMF Object; the archive reader produces
LinkInputModules on demand.

**.def files.** §6. Most directives become metadata for the link
descriptor (`opts.exports` etc.); EXPORTS in particular drives DLL
output (S8 not S1c — see §7).

**.res files.** Per HLD §1.4, mdlink merges a .res into the output's
`.rsrc`. The current `rc::RcUnit` is also an Input form (avoids a .res
serialise/deserialise round-trip for the in-process path).

### §2.2 — Pass 2: symbol resolution

Build the global symbol table:

```rust
struct GlobalSymbol {
    name: String,
    defining_input: usize,                   // index into LinkInputModule
    defining_section: usize,                 // section within that input
    value: u32,                              // offset in section
    storage: Storage,
    comdat: Option<ComdatLeader>,
}
```

Algorithm:

1. Walk every input's symbol table. For each EXTERNAL definition (not
   UNDEFINED), insert into a `BTreeMap<String, GlobalSymbol>`.
2. **Duplicate handling.**
   - Both are non-COMDAT → `DuplicateSymbol` error.
   - First is COMDAT (Selection::Any) → keep the first; discard the
     second's section (entire .text$Foo gets pruned).
   - First is WEAK_EXTERNAL; second is strong → second wins.
   - Both are WEAK_EXTERNAL → first wins (insertion order).
   - SELECT_SAME_SIZE / EXACT_MATCH: enforce constraint; error on
     violation.
   - SELECT_LARGEST: the one whose section's data is longer wins.
3. **Associative COMDATs.** A `.xdata$Foo` with selection
   `SELECT_ASSOCIATIVE` to `.text$Foo` is pulled in iff `.text$Foo` is
   pulled in. The associative bookkeeping happens here (the symbol is
   conditional on its leader).
4. **Pass 2b — resolution.** For each undefined external in every
   input, look it up in the global table. If unresolved:
   - First try library archives (§4 algorithm) — pull in any member
     defining the missing symbol; loop until quiescent.
   - If still unresolved after archive scan → collect into a
     `BTreeSet<String>` of unresolved names. Fail at end of pass with
     `LinkError::UnresolvedExternals(all of them)`. Lld-link calls this
     "unresolved external symbol _foo"; mdlink mirrors the line format.

The pass collects but does not yet emit. Output: the resolved
`GlobalSymbol` set plus a `BTreeSet<(input_ix, section_ix)>` of "live
sections" (the COMDAT-pruning made some sections unreachable).

### §2.3 — Pass 3: section merging + RVA assignment

Group live sections by `SectionKind`:

```rust
struct OutputSection {
    kind: OutputSectionKind,
    contributions: Vec<SectionContribution>,
    rva: u32,                                // assigned in pass 3
    file_offset: u32,                        // assigned in pass 3
    raw_size: u32,
    virt_size: u32,
    characteristics: u32,
}

struct SectionContribution {
    input_ix: usize,
    input_section_ix: usize,
    offset_within_output: u32,
}
```

Algorithm:

1. **Group**: walk live sections; group by `SectionKind`. Within a group,
   contributions are sorted by `(input_ix, input_section_ix)` for total
   ordering (input order matches the link command line). `.CRT$XCU`
   contributions are sorted **lexicographically by raw_name** so the
   compiler's `.CRT$XCU.001`, `.CRT$XCU.002`, etc. interleave correctly
   — this matches MSVC's behaviour and is what `_initterm` walks at
   runtime.
2. **Concatenate**: within each output section, pad each contribution to
   the section's alignment (max of all contributions' alignments —
   typically 16 for .text, 8 for .data/.rdata, 4 for .pdata/.xdata).
   Record the offset.
3. **Assign output section order**: deterministic. Pin order:
   `.text → .CRT (CRT$XCL → CRT$XCU → CRT$XCZ stitched) → .rdata →
   .data → .pdata → .xdata → .idata → .rsrc → .reloc (S8)`.
   `.bss` follows `.data` (uninitialized data; SizeOfRawData = 0).
   Match cl /link's canonical ordering.
4. **Compute RVAs**: each output section's RVA is
   `align_up(prev_end, SECT_ALIGN)`. Same rule pe.rs uses today;
   identical layout for single-TU inputs except where new sections
   (CRT, .reloc) intervene.
5. **Compute file offsets**: `align_up(prev_end_file, FILE_ALIGN)`.

### §2.4 — Pass 4: relocation processing

Every reloc in every live section gets its 4-or-8-byte field patched.
The reloc kinds (from `coff::RelocKind`):

```text
ADDR64   bytes[off..off+8] = (image_base + target_rva).to_le_bytes()
ADDR32   bytes[off..off+4] = (image_base + target_rva as u32).to_le_bytes()
ADDR32NB bytes[off..off+4] = target_rva.to_le_bytes()
REL32    bytes[off..off+4] = ((target_rva as i32) - (reloc_site_rva + 4 + implicit_disp)).to_le_bytes()
SECTION  bytes[off..off+2] = output_section_index.to_le_bytes() (1-based)
SECREL   bytes[off..off+4] = (target_value - target_section_rva).to_le_bytes()
```

`reloc_site_rva` = `section.rva + contribution.offset_within_output +
reloc.offset`. `target_rva` = `defining_section.rva + symbol.value` (or
the IAT slot RVA for `__imp_<name>`-named symbols — see §2.5).

**OMF relocations.** §3.4 details FIXUPP decoding; each FIXUPP maps to
one of the same RelocKind enum values. The unified pipeline means
COFF-RELOC and OMF-FIXUPP are processed identically after §3's bridge.

**Failure modes.** Relocations referencing pruned-COMDAT sections (we
chose another TU's copy) are silently retargeted to the survivor; the
survivor must define the same symbol (it does by ODR). Relocations
where `target_value + addend` overflows 32 bits (rare for x64 RIP-rel)
return `LinkError::PeOverflow`.

### §2.5 — Pass 5: IAT / .idata synthesis

Collect every undefined external whose name starts with `__imp_`. This
is the MSVC convention (and the one mdbcc emits — Q4 ratified in S1b.1
HLD). Group by source DLL.

mdbcc's contribution to "which DLL" is the `WIN32_IMPORTS` map in
current `pe.rs`. That map moves to `src/link/idata.rs` (the symbol→DLL
table) and is extended for any new symbol mdbcc or user code references.

For library-supplied imports (e.g. `__imp__printf` from the CRT
library), the library will instead be a real static .lib that defines
`printf` — no IAT entry, just an in-image function call. The IAT
synthesis is only for OS-provided DLL imports.

Algorithm (port of pe.rs::build_idata, generalised):

1. Collect imports: walk the global symbol table for UNDEFINED externals
   named `__imp_*`. Strip the prefix to get the real Win32 symbol name.
   Group by DLL using the WIN32_IMPORTS table.
2. Emit `.idata`:
   - IMAGE_IMPORT_DESCRIPTOR array (one per DLL + null term).
   - Per-DLL ILT (by-name thunks, null-terminated).
   - Per-DLL IAT (identical thunks, null-terminated).
   - Hint/name table (`<hint:u16=0><name><NUL>`, padded to even length).
   - DLL name strings (null-terminated).
3. Each `__imp_<name>` symbol's IAT slot RVA is recorded; relocations
   against `__imp_<name>` resolve to that RVA (this is what
   `call qword ptr [rip+disp]` patches in pe.rs::build_text today).

Symbols imported but not listed in `WIN32_IMPORTS` → `LinkError`. Same
hard error as `pe::used_dlls` today.

### §2.6 — Pass 6: .pdata / .xdata layout (x64)

x64 SEH requires `.pdata` (RUNTIME_FUNCTION array) and `.xdata`
(UNWIND_INFO). For multi-input programs:

1. Concatenate every input's `.pdata` contribution (already in output
   section assembly from pass 3). The OS expects entries sorted by
   `BeginAddress` ascending — sort the merged .pdata.
2. Concatenate every input's `.xdata` contribution. Relocations
   (Addr32nb) inside .pdata already point at the right offsets within
   the merged .xdata (the relocs were patched in pass 4 against the
   defining input's .xdata contribution offset, which became its
   placement within the merged .xdata).
3. Personality function references: every try-bearing function's
   `UNWIND_INFO.ExceptionHandler` is an Addr32nb against the personality
   function symbol. For mdbcc-only links the personality function is
   the synthetic one mdbcc embeds (`PERSONALITY_FN_NAME` in eh.rs).
   For mixed mdbcc/bcc32 links the personality function comes from
   whichever input defines it; if both define it (collision), it's a
   DuplicateSymbol error unless one is COMDAT.

For the single-TU case, the merged .pdata and .xdata are identical to
what pe.rs::build_pdata/build_xdata produce today (modulo the fact that
in pe.rs they're computed from `Module.funcs` directly, while here
they're a side-product of relocation processing — same bytes either
way).

### §2.7 — Pass 7: .rsrc merge

For RC compiler output (.res files), each `.res` is decoded into a
sequence of typed resources. For multi-input links with multiple .res
files, resources are merged:

- Same (type, name, language) triplet across two inputs → error
  ("duplicate resource"). lld-link does the same; cl /link merges
  silently with last-wins, which is dangerous and we don't replicate.
- All triplets across all inputs → assembled into one `.rsrc` per the
  existing `pe::build_rsrc` algorithm (which is type-grouped, sorted by
  (type, name)).

For the in-process `RcUnit` path (the existing test path), the
`compile_to_pe_with_rc` wrapper passes the unit directly; only one
input contributes resources, so there's no merge — port verbatim.

The .rsrc section emits as a self-contained block (single output
section, no relocations across other sections). Same shape as today.

### §2.8 — Entry point selection

`PE.OptionalHeader.AddressOfEntryPoint` points at the CRT startup stub
(`mainCRTStartup` for console, `WinMainCRTStartup` for GUI, plus
`_DllMainCRTStartup` for DLL — DLL deferred to S8). The CRT startup
itself walks `.CRT$XCU` then calls `main`/`WinMain`.

For the single-TU mdbcc path today, pe.rs synthesises a tiny inline
stub that does the equivalent of `mainCRTStartup` minus the
`.CRT$XCU` walk (no global ctors in today's tests because no
`Foo g;` test fixture exists yet). mdlink ports this stub but extends
it to:

1. Call `GetCommandLineA` (KERNEL32) for argv (today's stub passes
   nothing; argv is `(0, NULL)`).
2. Parse argc/argv from the command line (a tiny C routine in
   `src/link/crt.rs`'s assembled blob, or — Q-CRT in §10 —
   imported from Borland's RTL once that lib is built; for S1c we
   bake it).
3. Call `_initterm(&__xc_a, &__xc_z)` — walks the `.CRT$XCU` array.
4. Call `main(argc, argv, envp)` or `WinMain(...)`.
5. Call destructors (atexit chain).
6. Call `ExitProcess(retval)`.

The CRT skeleton is detailed in §5.

## §3 — OMF reading (Decision-1A)

bcc32 4.52 emits OMF; for the O14 oracle to be a round-trip (bcc32 OMF
→ mdlink → PE), mdlink must read OMF. The OMF walker in
`tests/support/omf_walker.rs` (734 LoC, S1b.6) decodes
LNAMES/SEGDEF/PUBDEF/EXTDEF/COMDEF/COMDAT records but skips FIXUPP and
LIDATA/LEDATA. mdlink can't skip those — they carry section data and
relocations.

### §3.1 — Lift strategy

Move (don't copy) `tests/support/omf_walker.rs` to `src/link/omf.rs`.
Reasons:

- Same set of records mdlink and the O13 oracle need.
- Same std-only / no-extra-deps house style.
- Keeping the walker in tests/ forces awkward re-imports from src/.
- The O13 oracle (`tests/oracle_o13_coff_parity.rs`) will re-import
  from `mdbcc::link::omf` instead of `tests::support::omf_walker`.
  Mechanical change.

`tests/support/omf_walker.rs` becomes a thin re-export shim:
```rust
pub use mdbcc::link::omf::*;
```

Or, simpler, delete it and update the import in the O13 oracle to
`use mdbcc::link::omf as omf_walker;`.

### §3.2 — Additional records to decode

The walker decodes LNAMES, SEGDEF, PUBDEF, EXTDEF, COMDEF, COMDAT, and
MODEND. For mdlink we add:

- **LEDATA** (`0xA0/0xA1`) — Logical Enumerated Data: raw section
  payload at a specified offset within a SEGDEF. Each LEDATA contributes
  a `(seg_idx, offset, bytes)` triple to the assembled segment.
- **LIDATA** (`0xA2/0xA3`) — Logical Iterated Data: same as LEDATA
  but the bytes are run-length compressed. Decompress into the same
  segment buffer.
- **FIXUPP** (`0x9C/0x9D`) — Fixups: relocations against the most
  recently emitted LEDATA/LIDATA. One FIXUPP record carries multiple
  fixups; each fixup has:
  - Location type (low byte / offset16 / offset32 / etc.)
  - Data record offset (within the LEDATA/LIDATA we're modifying)
  - Frame reference (which thing the fixup is "from" — usually a
    segment, group, or external)
  - Target reference (which thing the fixup points at)
  - Optional target displacement
- **THEADR** (`0x80`) — Translator Header: source file name. Decode and
  retain for diagnostics; not used for linking.
- **COMENT** (`0x88`) — Comment record: ignored except for the
  Borland-specific class A0 ("OMF extensions") subclasses that carry
  link-time directives. Most are ignorable; document the few we honour.

The FIXUPP→RelocKind mapping (for 32-bit OMF, which is what bcc32
emits for Win32; mdbcc targets Win64 so this is somewhat moot, but
mdlink needs to read what bcc32 emits):

| OMF Location | OMF Mode | Maps to             |
|--------------|----------|---------------------|
| Offset16     | Segment-relative | (16-bit; ignored — we're not loading 16-bit OMF) |
| Offset32     | Self-relative    | `RelocKind::Rel32`  |
| Offset32     | Segment-relative | `RelocKind::Addr32` |
| Pointer48    | (anything)       | (16:32 far ptr; ignored — Win32 doesn't need it) |
| LinearOffset32 | Segment-relative | `RelocKind::Addr32` |

For x64 we'd need Offset64 fixups; bcc32 4.52 doesn't emit them
(targets Win32-x86 only). The OMF reader rejects machine mismatches:
if a Win64 link receives a Win32 OMF .obj, the link fails with a
clear error rather than silently mangling. Mixed-architecture links
are not supported in any case (mdlink rejects on machine mismatch
between any two inputs).

### §3.3 — COMDEF semantics

Borland COMDEF (communal) is "weak BSS" — a symbol that exists in
multiple TUs, all definitions agree on type and size, the linker picks
one and discards the rest. Maps cleanly to COFF COMDAT SELECT_ANY:

- Allocate one BSS-sized section per first COMDEF appearance.
- Subsequent COMDEF for the same name: discard.
- An EXTDEF for a COMDEF name resolves to the kept copy.

mdlink internalises COMDEF as "make a synthesised .bss COMDAT
section, attach a symbol at offset 0, treat as if it were a normal
COFF COMDAT". §2.2 pass 2 then handles the deduplication uniformly.

### §3.4 — COMDAT semantics

bcc32 COMDAT (`0xC2/0xC3`) is essentially the same as COFF COMDAT:
"this section is a deduplication candidate; pick one across all TUs".
The walker decodes name and offset; mdlink needs the attribute byte
(selection: pick-any, no-dup, same-size, etc.) and the section bytes.

OMF COMDAT names the underlying section via its `public_name_idx`
(LNAMES). The data follows the header; FIXUPP records that follow
apply to the COMDAT's data, not to a prior LEDATA. mdlink tracks the
"current data context" to route FIXUPPs correctly.

Selection mapping:

| OMF COMDAT attribute | COFF Selection equivalent |
|---------------------|---------------------------|
| 0 (no match)        | `NoDuplicates`            |
| 1 (pick-any)        | `Any`                     |
| 2 (same-size)       | `SameSize`                |
| 3 (exact-match)     | `ExactMatch`              |

§2.2's COMDAT handler is selection-agnostic; this mapping is purely
about preserving the input's semantics.

### §3.5 — Records mdlink does NOT decode

| Record | Why skip |
|--------|----------|
| LINNUM (0x94/0x95) | Source line-number debug info; deferred to S8 |
| MODEND (0x8A/0x8B) | Already terminates the walk (the walker handles) |
| EXTDEF (B/A) qualified | Standard EXTDEFs are decoded; qualified-symbol EXTDEFs (CPP class names) are rare and the existing walker handles them via the standard path |
| GRPDEF (0x9A/0x9B) | Group definitions; bcc32 emits a single DGROUP that mdlink can ignore (Win32 PE has no grouping) |
| FIXEXT / FIXLOG | OS/2-specific; not relevant |
| Borland-extended COMENT classes other than A0 link directives | Brand-specific debug info |

Records skipped without warning (their length tells us how to advance
the cursor). An unknown record type triggers a soft warning to stderr
in debug builds, silent in release; only structural errors (bad
length, truncated body) cause hard failure.

### §3.6 — What might bite us

- bcc32's Win32 OMF uses **segment-name semantics** that don't always
  map to canonical PE sections. bcc32 emits `_TEXT` (class CODE) for
  .text, `_DATA` (class DATA) for .data, `_BSS` (class BSS) for .bss.
  mdlink's OMF reader maps segment-name + class to canonical
  SectionKind via a small table; unknown combinations get
  SectionKind::Other and are passed through verbatim.
- COMDAT data offset (`enum_data_offset` in §3.4) can be non-zero,
  indicating the data continues a previous COMDAT of the same name.
  Continuation COMDATs are essentially append operations on the same
  logical section. Rare in real bcc32 output; honour but document.
- bcc32 occasionally emits "16-bit" SEGDEF (`0x98`) for 32-bit
  segments when the segment fits in a 64 KB window. The walker handles
  the variant; FIXUPP needs to detect "this is conceptually 32-bit
  data even though SEGDEF is the 16-bit form".
- FIXUPP **frame methods**: F0 (frame is a segment) and F4 (frame is
  determined from the target) are common. F2 (frame is a group) maps
  through GRPDEF; if mdlink ignores groups, F2 fixups would need
  reinterpretation. **Mitigation**: when bcc32 emits a group-frame
  fixup, we look at the group's members; if all members are the same
  segment (bcc32's DGROUP is typically _DATA + _BSS + _CONST), we
  rewrite the fixup as segment-relative. Document failure mode in code.

If we hit any OMF feature we can't decode, fail loudly with the
offending record-type byte + offset. **Never silently miscompile.**

## §4 — Static library (.lib) format

MS-style ar archives.

### §4.1 — File structure

```
"!<arch>\n"                          (8-byte magic)
member-header                        (60 bytes)
member-data
[member-header]                      ...
[member-data]
```

Each member-header is 60 ASCII bytes:

```
[0..16]   Name (space-padded; long names use "/<index>")
[16..28]  ModificationDate (space-padded decimal; ignored — set 0)
[28..34]  OwnerID (space-padded; ignored)
[34..40]  GroupID (space-padded; ignored)
[40..48]  Mode (space-padded octal; ignored)
[48..58]  Size (space-padded decimal; MEMBER DATA SIZE)
[58..60]  "`\n" (back-tick newline magic)
```

Member data is `Size` bytes; padded with a single `\n` if `Size` is
odd (so the next header is aligned to 2 bytes).

### §4.2 — Special members

MS-archive convention pins the first two members as:

1. **"/"** — First Linker Member. Symbol index using big-endian u32s
   (legacy from Unix archives).
2. **"/"** (again) — Second Linker Member. Symbol index using
   little-endian u32s with a more efficient layout: number of members,
   array of member offsets, number of symbols, array of u16 indices
   into the member array, string table of symbol names.

mdlink uses **the second linker member only** (it's what every modern
.lib actually relies on). For format-spec compliance the first member
is skipped if present; we read it for index validation if Arthur wants
the belt-and-braces but it's the same data twice.

3. **"//"** — Longnames Member. Holds member names that don't fit in
   the 16-byte slot; named members like `/123` use the offset 123 into
   this member's bytes for the actual name.

### §4.3 — Symbol resolution

When pass 2 has collected all undefined externals after walking all
explicit inputs, it iterates:

1. Take an undefined external `_foo`.
2. Look up `_foo` in each archive's second-linker-member symbol index.
   First hit wins (matches link.exe / lld-link).
3. Locate the offending member: the index gives an offset into the
   archive; the member at that offset is read as a fresh
   LinkInputModule (via §3 for OMF or `coff::Object::read` for COFF).
4. Add the new LinkInputModule to the input set. Its EXTERNAL
   definitions enter the global symbol table; some of them resolve
   prior undefined externals. Some of its own undefined externals may
   be NEW undefined externals.
5. Loop until no more changes in one full pass.

This is the classic "one-pass" linker behaviour: an undefined external
pulled in might itself depend on something not yet pulled in. The
correctness invariant is "no unresolved external at end of loop"; the
loop terminates because every iteration either pulls in a fresh
member (bounded by total archive size) or makes no progress (terminates).

**Linker corner case**: an archive member that defines TWO symbols, only
one of which is needed, drags the OTHER definition in too. This is the
"all-or-nothing" rule; users who care about this granularity use
COMDAT (each function in its own section). mdlink does this correctly
because LinkInputModule is a unit; symbol-table population happens
once per module.

### §4.4 — Archive-from-COFF vs Archive-from-OMF

Both formats use the same ar wrapper. mdlink detects the member format
by sniffing the first byte:
- `0x80` (THEADR): OMF
- First two bytes match an `IMAGE_FILE_MACHINE_*` value: COFF

Borland's static libraries on the CD (`\BC45\LIB\*.LIB`) are OMF
internally. mdlink's archive reader handles both transparently — the
member loader dispatches based on the sniff.

## §5 — CRT skeleton

The CRT (C Runtime) startup glue lives in `src/link/crt.rs`. mdlink
synthesises a small `.text` contribution (think of it as an internal
"crt.obj") containing the startup function plus the .CRT$XCL/XCZ
sentinel symbols.

### §5.1 — Synthesised inputs

When `opts.synthesise_crt == true`, mdlink prepends a synthetic
LinkInputModule named `<crt-stub>` to the input set. It contributes:

- `.text` section containing the startup function (~100-200 bytes of
  hand-assembled x64 code).
- `.CRT$XCL` empty section with one symbol `__xc_a` at offset 0 — the
  beginning sentinel.
- `.CRT$XCZ` empty section with one symbol `__xc_z` at offset 0 — the
  end sentinel.
- EXTERNAL `__imp_GetCommandLineA`, `__imp_ExitProcess`,
  `__imp_GetStdHandle`, `__imp_WriteFile`, `__imp_GetProcessHeap` etc.
  (the existing pe.rs WIN32_IMPORTS stub set, plus
  `__imp_GetCommandLineA` for argv parsing).
- EXTERNAL `main` (or `WinMain` per subsystem).

The startup function (in pseudo-code; the real assembly lives in
`crt.rs` as a `const STUB_BYTES: [u8; N]` with relocations
documented):

```text
mainCRTStartup:
    sub rsp, 0x28                            ; shadow + 16-align
    call GetCommandLineA                     ; rax = LPCSTR cmdline
    mov rcx, rax                             ; (cmdline)
    call _parse_argv                         ; rax = argc, rdx = argv**
    mov ecx, eax                             ; argc → arg0
    mov rdx, [rsp+...]                       ; argv → arg1
    xor r8, r8                               ; envp = NULL
    call _initterm                           ; walks .CRT$XCU
    call main                                ; user main(argc, argv, envp)
    mov ecx, eax                             ; argc → ExitProcess arg
    call ExitProcess
    int 3                                    ; unreachable

_initterm:                                   ; (start: rcx, end: rdx)
    ; for (p = start; p < end; ++p)
    ;     if (*p != NULL) (*p)();
    ; (the .CRT$XCU array is u64* of ctor function pointers)
    push rbp / sub rsp, 0x10                 ; standard mdbcc prologue (for SEH)
    ; ... loop body ...
    add rsp, 0x10 / pop rbp / ret

_parse_argv:                                 ; (cmdline: rcx)
    ; trivially tokenise on whitespace; quote handling deferred to S8.
    ; bake-in: argc + argv** in static buffer ___argv_buf
    ; (the per-process argv buffer; 8 KB ought to be enough for anyone)
    ...
```

**Critical**: the startup function MUST follow the mdbcc prologue
shape (`push rbp; mov rbp,rsp; sub rsp,imm32`) because the same
`.pdata`/`.xdata` machinery describes it. Any future codegen change
to the standard prologue must update the startup stub in lockstep.
Document this co-evolution constraint in crt.rs.

### §5.2 — .CRT$XCU layout

Global ctor pointers are emitted by mdbcc when it sees `Foo g;` with a
non-trivial ctor (the codegen path doesn't exist yet — filed for a
later S1 tick that adds global-ctor lowering). Each TU contributes one
`.CRT$XCU.<symbol>` section containing an 8-byte function pointer to
its ctor wrapper.

The merge in pass 3 concatenates `.CRT$XCU.*` contributions in
lexicographic order (matches MSVC); the result is a contiguous array of
`void (*)(void)` pointers between `__xc_a` (start) and `__xc_z` (end).

`_initterm(&__xc_a, &__xc_z)` walks this array at startup, invoking
each non-null pointer in order.

### §5.3 — What mdlink provides vs what gets pulled from a library

The Borland CD has `\BC45\SOURCE\RTL\SOURCE\STARTUP\COMMON32\STARTUP.C`
(real Borland CRT startup) and `\BC45\SOURCE\RTL\SOURCE\STARTUP\WIN32\
C0NT.ASM` (assembly CRT startup for Win32 console). The full Borland
CRT is ~903 .C + ~206 .ASM files — too much for mdlink to bake in.

**Division of labour**:

| What | Where | Why |
|------|-------|-----|
| `mainCRTStartup` / `WinMainCRTStartup` stub | mdlink crt.rs | Bake — every link needs it; tiny |
| `_initterm` (walks .CRT$XCU) | mdlink crt.rs | Bake — tiny |
| `argv` parsing (basic, quote-unaware) | mdlink crt.rs | Bake — small, S1c-needs-it-now |
| `printf` / `malloc` / `free` | linked from a library | Real Borland source (S5) or stub (S1c) |
| `__chkstk` (stack probe) | linked from a library | Compiler intrinsic; emit `__chkstk` references from codegen, link from CRT |
| `_atexit` chain | linked from a library | Per-program dtor list |
| `_setjmp` / `_longjmp` | linked from a library | Borland's RTL provides |

For S1c specifically: mdlink bakes its own minimum
(`mainCRTStartup`, `_initterm`, `_parse_argv`). The 88 e2e tests do
NOT use `Foo g;` global ctors, do NOT use argv (every `main` is
`int main(void)`), and don't need printf via a library (mdbcc's
codegen still inlines `printf` to a WriteFile call). So the baked stub
is sufficient for everything S1c needs to make green.

When S5 builds the real Borland RTL as `crt.lib`, mdlink will accept
its `mainCRTStartup` as a defined symbol; the synthesised stub becomes
the fallback (its symbol is WEAK_EXTERNAL so a real definition wins).
Filed as a forward-compatibility seam.

### §5.4 — Subsystem-specific stubs

| Subsystem | Stub name           | Calls            | Args to user fn          |
|-----------|---------------------|------------------|--------------------------|
| Console   | `mainCRTStartup`    | `main`           | `argc, argv, envp`       |
| GUI       | `WinMainCRTStartup` | `WinMain`        | `hInstance, hPrevInstance=NULL, lpCmdLine, nCmdShow=SW_SHOWNORMAL` |
| DLL       | `_DllMainCRTStartup`| `DllMain`        | `(hinst, reason, reserved)` — S8 |

For GUI, mdlink also synthesises imports for `GetModuleHandleA` (to
fetch hInstance) — or, matching today's pe.rs trick, bakes
`hInstance = ImageBase` because ImageBase is fixed and the EXE's
module handle equals its image base. The current pe.rs uses this
trick to avoid the `GetModuleHandleA` import; mdlink preserves it for
the GUI stub.

## §6 — .def file parser

Per HLD §1.4 (S1b): minimum viable parser. Recognise the directives;
honour only those needed for S1c (i.e. effectively none — they all hit
deferred S8 paths). Filed as `src/link/defparse.rs`.

### §6.1 — Grammar (subset)

```
def-file        ::= statement*
statement       ::= NAME app-name [ BASE = number ]
                  | DESCRIPTION quoted-string
                  | STACKSIZE number [ , number ]    ; reserve, commit
                  | HEAPSIZE  number [ , number ]
                  | EXPORTS export-entry+
                  | IMPORTS import-entry+
                  | SECTIONS section-flags+          ; ignored
                  | VERSION number . number          ; ignored
                  | LIBRARY library-name             ; (DLL output; ignored S1c)
                  | comment                          ; (; or #)
export-entry    ::= symbol [ = mangled-symbol ] [ @ ordinal ]
                                [ NONAME ] [ PRIVATE ] [ DATA ]
import-entry    ::= [ ext-name = ] module-name . internal-name
                  | [ ext-name = ] module-name . @ ordinal
```

### §6.2 — What S1c honours

- `STACKSIZE n [, m]` — overrides `opts.stack_reserve` / `_commit`.
- `HEAPSIZE n [, m]` — overrides `opts.heap_reserve` / `_commit`.
- `NAME app-name` — informational, written into the PE's
  `OptionalHeader.MajorImageVersion` field? Actually no — Borland's
  TLINK32 just used it for `.map` file labelling. mdlink stores but
  doesn't emit anywhere.
- Everything else: parsed for syntactic validity (error on malformed
  input) but unused.

### §6.3 — What S1c defers

- `EXPORTS`: only meaningful for DLL output (S8). Parser accepts; values
  stored in `LinkOpts.exports`; DLL output path consults them. S1c
  emits .exe only, so EXPORTS is effectively informational.
- `IMPORTS`: per-line import override (equivalent of `-l` with
  ordinal). mdbcc's WIN32_IMPORTS table is the source of truth; .def
  IMPORTS would shadow it. Defer to S5+ when real .def files appear.

## §7 — DLL output (defer to S8)

Per the May-26 plan §4.S8: DLL output is "long tail". S1c emits .exe
only. The architectural seam is:

```rust
enum OutputFormat { Exe, Dll }   // LinkOpts.output_format, S8 adds Dll
```

For DLL output (S8+):
- `PE.OptionalHeader.AddressOfEntryPoint` → `_DllMainCRTStartup`.
- Export table synthesis from `.drectve` directives + .def EXPORTS.
- Different IMAGE_FILE_HEADER characteristic bits (IMAGE_FILE_DLL).
- Different entry stub (DllMain semantics — reason codes etc.).
- Same `.idata` / `.pdata` / `.xdata` machinery.

The S1c implementation pins `output_format = Exe` and rejects DLL
attempts with `LinkError::Internal("DLL output is S8 work")`. S8 lifts
this restriction by adding `dll.rs`. No churn elsewhere because the
seam isolates it.

## §10 — Open questions for Arthur (Q-list)

**Q-Bcc — `bcc foo.cpp` (no -c) post-S1c**: shell out to mdlink, or
stay in-process? §1.4 recommends **stay in-process for single-file
invocations**; spawn mdlink only when invoked with multiple inputs.
This keeps the 88 e2e tests green without a process-spawn dependency.
Multi-file `bcc foo.cpp bar.cpp` is rare today and can be deferred
to S8 (with the `bcc` CLI rejecting multi-file with a clear
"use mdlink for multi-file links" message). **Recommendation:
in-process single, defer multi-file**.

**Q-Pe — delete pe.rs or keep as stub?** §1.5 recommends **delete at
S1c.11**. Counter-argument is to keep it as `pub use crate::link::
pe_writer::*;` for back-compat. Since the crate is internal (only
in-tree consumers) and the only call sites are inside the crate, the
stub adds confusion. **Recommendation: delete**.

**Q-Cli — option convention.** mdlink should accept what flavour of
options?
- **GNU-style**: `mdlink --subsystem=console --entry=main foo.obj -o
  foo.exe`. Familiar to Rust/Cargo users; matches lld-link's
  `--`-prefixed alternates.
- **MSVC-style**: `mdlink /SUBSYSTEM:CONSOLE /ENTRY:main foo.obj
  /OUT:foo.exe`. Matches link.exe / lld-link's primary syntax; user
  who came from `cl /link` finds it familiar.
- **Borland-style**: `mdlink -Tpe -Sc -ofoo.exe foo.obj`. Matches
  TLINK32 syntax; nobody alive uses it but it would match the
  "look-and-feel of bcc32" goal.

**Recommendation**: GNU-style as primary, MSVC-style aliases for the
common options (`/SUBSYSTEM`, `/ENTRY`, `/OUT`). The Borland-style
mode is filed as S8+ "if real bcc32 makefiles need it".

**Q-CRT — bake or import?** §5.3 proposes mdlink bakes its own
`mainCRTStartup` + `_initterm` + `_parse_argv` for S1c. Counter-
argument: the real Borland CRT (when S5 builds it) becomes
authoritative; mdlink's baked stub is the fallback. **Recommendation:
bake for S1c; mark the symbols WEAK_EXTERNAL so a real CRT
definition wins when linked in S5+**. This is a forward-compatible
seam.

**Q-Default-Libs — implicit kernel32.lib?** Today pe.rs's
WIN32_IMPORTS table inlines the IAT entries; no library is consulted.
mdlink could keep this convention (bake the IAT entries) OR require
the user to pass `kernel32.lib` (extracted from the SDK). **Recom-
mendation: keep the baked WIN32_IMPORTS for S1c** — it's
the smallest dependency footprint, matches today's behaviour, and
the user can override by linking a real `kernel32.lib` later.

**Q-Mangling-Reach — emit Borland mangling for C functions too?**
S1b §3.6 noted mdbcc only invokes the Borland mangler for overload
sets; plain C functions stay un-mangled. For mdlink's mixed link with
bcc32, mdbcc's C function `void foo(void)` would emit `_foo` (extern
"C" convention; matches bcc32). For C++ free functions without
overloads, mdbcc emits `foo` (no leading underscore). bcc32 emits
`@foo$qv` (full C++ mangling). S1b.7 RED 3 closed the externs side
(extern declarations get mangled); definitions still don't. **Question:
is closing the definitions side an S1c task or deferred to S3/S4?**
**Recommendation: defer**; the O13 oracle (which compares symbol sets)
catches the divergence, and the S1c mixed-link test (§8.5) uses extern
"C" on both sides explicitly to sidestep it.

## §11 — Risk register update

Per May-26 plan §7 (R1-R12) + S1b HLD §7 (R13-R16). New risks /
disposition changes from S1c:

- **R8 (TLINK32 quirks) — DEMOTED**: mdlink replaces TLINK32 entirely;
  TLINK32 is consulted only for the reference build in O14-Half-A. Its
  quirks no longer matter for emitted bytes. R8 stays on the register
  as "Borland's idiomatic OMF emissions may bite the OMF reader" — but
  it's much narrower scope.
- **R10 (multi-TU symbol resolution) — CRYSTALLISED in S1c.4/S1c.5**.
  Mitigation: the two-file program test (§8.4) gates S1c.4; the COFF
  loader test (§8.5) gates S1c.5; the library test (§8.6) gates S1c.7;
  each is a small, focused fixture that surfaces resolution bugs early.
  Plus the O13 oracle continues to catch symbol-set divergence.
- **R15 (pe.rs 2074-LoC reshape) — DISCIPLINE**: S1c.2 is the
  pure-shuffle commit (all 880 tests green throughout, no semantic
  change). S1c.3 is the first semantic-change commit. Same atomic
  discipline as S1a.
- **R17 — OMF FIXUPP edge cases bite multi-input link**. Borland's
  fixup record format has many variants; our reader will only have
  been validated against the O13 fixture set (small, predictable
  source). Real Borland source may exercise FIXUPP modes the reader
  doesn't handle. **Mitigation**: hard-fail with the offending byte
  + offset; never silently miscompile. Add fixtures iteratively as
  we hit gaps in S5+.
- **R18 — CRT stub assembly bytes co-evolve with codegen prologue
  shape**. The mdbcc `push rbp; mov rbp,rsp; sub rsp,imm32` is
  baked into both `read_prolog_alloc` and the CRT stub bytes; any
  future codegen change to the prologue requires a synchronised
  update of crt.rs. **Mitigation**: the same `read_prolog_alloc`
  helper validates the CRT stub's prologue at link time; mismatch
  → hard error.
- **R19 — Re-blessing the 88 SipHash baselines at S1c.3 may mask a
  silent bug**. The expected PE-byte shift makes the SipHash
  comparison opaque to "did anything that shouldn't have changed
  change". **Mitigation**: at S1c.3 commit, the diff between the
  old PE and the new PE must be ONLY in (a) startup-stub
  contribution (now `mainCRTStartup` + `_initterm` + `_parse_argv`
  instead of the inline 18-byte stub), (b) new `.idata` entries
  (`GetCommandLineA`), (c) new `.CRT$XCL/XCZ` sentinel sections.
  Manually verify section-by-section diff on one fixture; document
  the expected delta in the commit message.
- **R20 — Static library archive format has historical quirks**.
  GNU vs BSD vs SysV `ar` variants exist; MS-format is the standard
  on Windows but has its own subspecies (symbol-index endianness,
  long-name handling). **Mitigation**: mdlink reads only MS-format
  archives (what cl /link emits and what Borland's TLIB produces).
  Format detection is by the `!<arch>\n` magic; we don't claim
  GNU/BSD compatibility.

Carried risks unchanged: R13 (mangling completeness, still ~95% post-
S1b.7), R14 (COMDAT vs COMDEF — crystallises in S1c.6 when mdlink
consumes both), R16 (determinism in OBJ writer — addressed by Vec
ordering throughout).
