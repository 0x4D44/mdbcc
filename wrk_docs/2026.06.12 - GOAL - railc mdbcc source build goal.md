# RailC mdbcc Source-Build Goal

Date: 2026-06-12

## Goal

Make RailC build without the Borland compiler toolchain, on a path that can later produce a native 64-bit executable.

The immediate goal is not "make the current `mdbcc.toml` link RailC today". The immediate goal is to replace the old dependency chain in stages, proving one boundary at a time.

## Background

The old working RailC build depends on:

- RailC source and resources.
- Borland C++ compiler and linker.
- Borland resource compiler.
- Borland startup/CRT objects and libraries.
- OWL and ClassLib/BIDS binary libraries.
- Windows import libraries.
- `RAILC.DEF`.

For 64-bit, the old Borland binary libraries and startup objects are not viable target dependencies. They are 32-bit artifacts and keep us tied to the old ABI. We should treat them as reference/oracle material, not as the architecture we are trying to preserve.

## Strategy

Pursue two concrete stepping stones:

1. RailC compile-only, Win32.
2. Source-built OWL/ClassLib dependency slice, Win32.

Only after those are under control should we aim at a 64-bit RailC executable.

This order keeps the problem testable. RailC compile-only isolates mdbcc's C++ front-end and 32-bit codegen against the application source. Source-building OWL/ClassLib then avoids the likely trap of trying to match Borland's binary C++ ABI exactly.

## Milestone 1: RailC Compile-Only, Win32

Objective:

- Compile every RailC translation unit to Win32 object files using `mdbcc`.
- Use RailC source from `C:\language\railc`.
- Use existing Borland/OWL headers as header inputs only.
- Do not link yet.
- Do not invoke Borland `BCC32.EXE`, `TLINK32.EXE`, or `BRC32.EXE`.

RailC translation units from the current legacy recipe:

- `RAILC.CPP`
- `DEPARTUR.CPP`
- `LOCOYARD.CPP`
- `ARRIVALS.CPP`
- `FINISH.CPP`
- `ABOUT.CPP`
- `STARTUP.CPP`
- `START.CPP`
- `CONFIGUR.CPP`
- `LAYOUT.CPP`
- `SELECTOR.CPP`
- `PLATFORM.CPP`
- `TOOLBAR.CPP`
- `TOOLBUTT.CPP`
- `STATBAR.CPP`
- `SECTION.CPP`
- `PLATDATA.CPP`
- `ovlpdata.cpp`
- `ROUTES.CPP`
- `LOCOS.CPP`
- `TIMETABL.CPP`

Acceptance criteria:

- A repeatable command compiles all listed RailC translation units to Win32 COFF objects with `mdbcc`.
- The command has a clear pass/fail summary per translation unit.
- No Borland compiler or linker executable is invoked.
- All failures are attributable to specific mdbcc language, preprocessor, header-compatibility, or codegen gaps.
- When the milestone is complete, all RailC translation units compile cleanly enough to produce object files.

Expected work:

- Add or adapt a compile-only RailC harness.
- Fix mdbcc parser/preprocessor/codegen gaps in the order they block translation units.
- Keep each compiler fix small and covered by focused tests in mdbcc.

## Milestone 2: Source-Built OWL/ClassLib Dependency Slice, Win32

Objective:

- Build the OWL/ClassLib/BIDS code needed by RailC from source using `mdbcc`.
- Target Win32 first, not Win64.
- Avoid linking RailC against old Borland binary OWL/ClassLib libraries as the target architecture.

Source locations currently available as reference/input:

- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\OWL`
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\CLASSLIB`
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\SOURCE\RTL\SOURCE`
- `C:\language\mdbcc\wrk_oracle\bc452\BC45\INCLUDE`

Acceptance criteria:

- The RailC-required OWL/ClassLib source slice compiles to Win32 objects or libraries with `mdbcc`.
- The build does not depend on `OWLWF.LIB`, `BIDSF.LIB`, or other old Borland binary C++ libraries as final link inputs.
- Any remaining old-world dependencies are explicitly categorized, for example startup/CRT, import libraries, resource compiler behavior, `.def` handling, or help/resource packaging.
- The dependency slice is documented well enough that expanding it is mechanical rather than guesswork.

Expected work:

- Discover the OWL/ClassLib source files actually pulled in by RailC.
- Build only the needed slice first; avoid importing or porting the entire tree prematurely.
- Add missing mdbcc support for Borland C++ constructs surfaced by OWL/ClassLib.
- Decide case by case whether to preserve behavior, stub a narrow compatibility surface, or remove unused legacy behavior.

## Not Goals Yet

- Full 64-bit RailC executable.
- Full OWL port.
- Full Borland C++ ABI compatibility with old binary libraries.
- Rewriting RailC's UI architecture.
- Replacing RailC resources/help packaging beyond what is needed to unblock compile/source-build steps.
- Preserving old Borland binary libraries as the final architecture.

## Later Goal: 64-Bit RailC

After RailC and its OWL/ClassLib dependency slice are source-built in Win32 mode, move the same source-built stack to Win64.

Likely additional work:

- Pointer-size and handle-size cleanup.
- Old `near`, `far`, `huge`, and `PASCAL` compatibility decisions.
- Win64 calling convention and structure layout changes.
- Replacement startup/CRT pieces.
- Import and resource/linker behavior for Win64.

## Key Risks

- Borland C++ dialect features in RailC or OWL may be deeper than RailC alone exposes.
- OWL/ClassLib may assume 32-bit pointer and message-packing behavior in many places.
- Mixing mdbcc-generated RailC objects with Borland binary C++ libraries is likely to fail on ABI details; this should remain diagnostic only.
- Rebuilding too much OWL too early could turn a focused compiler-porting effort into an unbounded framework port.
- Rewriting RailC to avoid OWL might eventually be sensible, but doing that before we understand the compiler gaps would destroy useful evidence.

## Decision Log

- Chose a 32-bit intermediate target because RailC and OWL were originally Win32, and it separates compiler compatibility from pointer-size migration.
- Chose RailC compile-only as the first milestone because it provides the smallest useful feedback loop.
- Chose source-built OWL/ClassLib as the second milestone because it moves us toward 64-bit and avoids depending on old Borland binary C++ ABI compatibility.
- Deferred old-binary-library linking to diagnostic use only.

## Current Acceptance Evidence

- Milestone 1 is covered by `tests/railc_compile_only.rs`. The explicit command `mdtimeout 900s -- cargo test --release -q --test railc_compile_only -- --ignored --nocapture` compiled all 21 RailC translation units to Win32 COFF objects with `mdbcc`; result: 21 pass, 0 fail.
- Milestone 2 is covered by `tests/railc_source_slice.rs`. The explicit command `mdtimeout 1200s -- cargo test --release -q --test railc_source_slice -- --ignored --nocapture` rebuilt the RailC-needed dependency slice from workspace sources and linked `railc_slice.exe` with source-built archives; result: RailC 21 objects, OWL 65 members, streams 48 members, BIDS 11 members, RTL 207 members, executable size 9,030,144 bytes.
- The source slice is pinned in `tests/corpus/railc/source_slice.tsv`: OWL 65 members, streams 48 members, BIDS 11 members, RTL 207 members. The normal test `railc_source_slice_manifest_maps_to_workspace_sources` validates that the pinned member list maps to workspace sources.
- The ignored source-slice build links with `mdlink --trace-archives` and verifies that the source-built archives pull exactly the pinned member set. Expanding the slice is mechanical: regenerate a trace, update the fixture, validate source mapping, then rerun the ignored source-slice build.
- The remaining old-world pieces are now explicit: Win32 target mode, RailC resources through `mdrc --profile bc45`, the current mdbcc runtime/shim pieces in the RTL archive, the local `C:\language\railc` corpus used as an input, and release-built mdbcc tools under `target\release`.
- The Win64 compile-only dependency-slice spike is now repeatable through `tests/railc_source_slice.rs`. The explicit command `mdtimeout 1200s -- cargo test --release -q --test railc_source_slice railc_source_built_dependency_slice_compiles_win64 -- --ignored --nocapture` compiled the same source-built stack to AMD64 COFF objects; result: RailC 21 objects, OWL 65 members, streams 48 members, BIDS 11 members, RTL 207 members.

## Win64 Spike Evidence

- A narrow compile-only spike was run for the 21 RailC application translation units with `target\release\bcc.exe -c -m64 -D__WIN32__`, using the RailC root and BC45 include directory. Generated evidence is under `wrk_probe\railc_win64_compile_only`.
- Initial result: 14 translation units produced AMD64 COFF objects and 7 failed.
- The `TDialog(parent, name)` blocker was reduced by adding Win64 by-value record user-defined conversion support for cases like `LPSTR -> TResId`. The focused regression is `win64_cstr_to_by_value_class_user_defined_conversion`.
- The x64 polymorphic-secondary-base blocker was reduced by adding Win64 this-adjusting thunks for secondary vtables (`sub rcx, off; jmp target`) and by omitting those leaf tail-jump thunks from x64 unwind tables. Focused regressions:
  - `win64_mi_polymorphic_second_base_new_and_virtual_dispatch`
  - `win64_mi_secondary_thunk_with_eh_metadata`
  - `amd64_object_omits_unwind_rows_for_secondary_vtable_thunks`
- This does not complete secondary-base RTTI. `s4_mi_plus_rtti_secondary_base_dynamic_cast_known_gap` records the current runtime gap: secondary-base construction/dispatch works, but `dynamic_cast<D*>(B2*)` through a secondary vtable still returns null under mdbcc while bcc32 returns 20.
- The Win64 data-bearing shared-virtual-base blocker was reduced by enabling the existing Stage-3 single-shared-vbase machinery for Win64. The focused regression is `win64_fstream_shaped_data_bearing_virtual_base_diamond`, which mirrors the `fstream : fstreambase, iostream` shape and proves shared `ios` state through all three base paths.
- Current result: all 21 RailC application translation units produce AMD64 COFF objects with `target\release\bcc.exe -c -m64 -D__WIN32__`.
- The pinned 331-member source-built dependency slice was then run as a Win64 compile-only spike. Initial result was `SUMMARY ok=351 fail=1`; the only blocker was `OWL/WINDOW.CPP` using Borland's `_EAX` register pseudo-variable in `StdWndProc`.
- The `_EAX` blocker was reduced by making the existing pseudo-variable machinery target-width: functions that reference `_EAX` now spill entry RAX/EAX before parameter spills, and `_EAX` has pointer-width integer type for casts such as `((TWindow*)_EAX)`. The focused AMD64 object regression is `amd64_eax_pseudovar_compiles_as_entry_rax`; the existing i386 runtime regression remains `i386_eax_register_pseudovariable`.
- Current result: all 352 Win64 compile-only objects are produced for the source-built stack: RailC 21, OWL 65, streams 48, BIDS 11, RTL 207. Generated evidence is under `wrk_probe\railc_source_slice_win64_compile_only`, and the repeatable ignored harness writes its summary under `wrk_probe\railc_source_slice_win64_compile_only\build\summary.txt`.
- The Win64 source-built dependency objects were archived into source-built libraries under `wrk_probe\railc_source_slice_win64_link`: OWL 65 members, streams 48 members, RTL 207 members, BIDS 11 members.
- The first Win64 source-stack link spike exposed record/reference-to-handle conversion gaps rather than archive format issues. Focused fixes added:
  - record/ref-to-record argument marshalling through conversion operators for direct, virtual, and indirect calls;
  - compatible conversion-operator results for already-known call signatures, e.g. `TModule::operator HINSTANCE()` feeding a `HANDLE` callback;
  - vtable-slot parameter signatures so pure virtual declarations still marshal `TDC&`/`Base&` arguments correctly when no concrete `sigs.funcs` entry exists;
  - x64 on-demand imports for the `lstr*` family used by the source-built stack.
- Focused regressions added during the link spike include `ref_record_argument_to_scalar_param_uses_conversion_operator`, `ref_record_argument_to_function_pointer_scalar_param_uses_conversion_operator`, `compatible_conversion_operator_result_feeds_function_pointer_param`, `constructor_scalar_param_uses_record_conversion_operator_on_win64`, `pure_virtual_reference_param_uses_slot_signature_for_marshalling`, and `unused_synth_copy_ctor_does_not_reference_private_member_copy_ctor`.
- The Win64 source-stack link spike is now repeatable through `tests/railc_source_slice.rs`. The explicit command `mdtimeout 1200s -- cargo test --release -q --test railc_source_slice railc_source_built_dependency_slice_links_win64 -- --ignored --nocapture` rebuilt the AMD64 source objects, source-built archives, and `mdrc --profile bc45` resources, then linked `railc_source_slice_win64.exe`; result: RailC 21 objects, OWL 65 members, streams 48 members, BIDS 11 members, RTL 207 compiled members, executable size 12,468,736 bytes.
- The Win64 archive trace check now treats the old 32-bit heap/startup path as intentionally replaced in native links: `MEMORY_COMMON32_GETMEM.C.o`, `MEMORY_COMMON32_HEAP.C.o`, `MEMORY_COMMON32_REALLOC.C.o`, `MEMORY_WIN32_VIRTMEM.C.o`, and `MISC_WIN32_PLATFORM.C.o` are compiled as part of the pinned slice but are not pulled into the Win64 executable.
- The regenerated PE import table contains `KERNEL32.dll`, `GDI32.dll`, `USER32.dll`, `COMDLG32.dll`, `WINMM.dll`, and `SHELL32.dll`. It does not import `CTL3D32.dll`, `VirtualAlloc`, or `VirtualFree`; the native allocation surface is satisfied through `GetProcessHeap`, `HeapAlloc`, and `HeapFree`.
- A bounded runtime smoke against `wrk_probe\railc_source_slice_win64_link\build\railc_source_slice_win64.exe` still fails before a visible top-level RailC window appears. The process exits with `0xC0000374`; Windows logs `Application Error` for `ntdll.dll`, exception code `0xc0000374`, fault offset `0x0000000000117555`.
- The previous `_init_heap` access violation caused by Borland's 32-bit `HEAP.C` free-list layout is resolved by the process-heap shim and by keeping `HEAP.C` out of the Win64 link. The current runtime blocker is a deeper native Win64 ABI/runtime issue, not the missing CTL3D DLL and not the old heap startup initializer.

## Next Concrete Step

Decide the Win64 Windows compatibility strategy before broad implementation. The evidence points at old BC45/OWL 32-bit assumptions that need a deliberate design: pointer-sized `WPARAM`, `LPARAM`, and `LRESULT`; a Win64 replacement for OWL's x86 `CreateInstanceThunk`/`StdWndProc` path; and `SetWindowLongPtrA`/`GWLP_WNDPROC` usage instead of truncating a window-procedure pointer through `uint32`/`SetWindowLong`. This is no longer a narrow linker shim; it is the next architecture decision for making the source-built PE32+ executable run.
