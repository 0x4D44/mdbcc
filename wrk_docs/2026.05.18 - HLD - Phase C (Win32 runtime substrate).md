# HLD — Phase C: Win32 runtime substrate

Date: 2026-05-18. Status: DESIGN (Phase A/B/B-1 landed; impl-ready).
Roadmap: `wrk_journals/2026.05.17 - PLAN - OWL Windows roadmap.md`
(Phase C section is authoritative scope). Charter:
`wrk_journals/2026.05.18 - PLAN - Goal loop charter.md`.
Depends on Phase A (Win64 >4-arg stack ABI — `CreateWindowEx`/`MessageBoxA`
are multi-arg) and Phase B (vtables — the OWL substrate that lands *on top*
of this in Phase D). Both reused, neither changed here.

## Why
OWL apps are GUI Win32 programs: they link many DLLs (`USER32`, `GDI32`,
`KERNEL32`, …), enter at `WinMain`, and run under subsystem 2 (GUI). The
compiler today emits **only** a console (subsystem 3) PE that imports
**exactly six `KERNEL32` functions** and enters via a fixed `main`-calling
stub. Phase C is the narrow PE-writer + driver generalisation that makes a
GUI Win32 program *buildable and runnable at all* — nothing OWL-specific,
no message loop, no window classes (that is Phase D). The language features
underneath stay on the strong O1/O2/O3 path; the GUI surface gets a new,
honestly-weaker oracle **O6**.

The non-negotiable constraint: **the console path stays byte-identical**.
O1 `tests/end_to_end.rs` (88 tests, authoritative) must remain green and
unchanged; every Phase C addition is gated on "fires only when a Win32/GUI
program is compiled", reusing the exact byte-identical-regression argument
proven in the PE-layout fix, Phase A and Phase B.

## Current implementation (read 2026-05-18, grounded)

### PE writer — single-DLL, kernel32-centric, console-only
- `IMPORTS: [&str; 6]` (`src/pe.rs:75`) is a hard-coded `KERNEL32`-only
  list: `ExitProcess, GetStdHandle, WriteFile, GetProcessHeap, HeapAlloc,
  HeapFree`. `ExitProcess` must stay index 0 (the entry stub calls it).
- `build_idata` (`src/pe.rs:92`) builds **one** `IMAGE_IMPORT_DESCRIPTOR`
  + a null terminator (`desc_size = 2*20`, `src/pe.rs:97`), `dll_name =
  b"KERNEL32.dll\0"` (`src/pe.rs:93`), one ILT and one IAT of `n+1` 8-byte
  by-name thunks (`src/pe.rs:98-101`), one hint/name blob per import
  (`src/pe.rs:106-116`), one DLL name. `iat_slot: HashMap<&'static str,
  u32>` maps every import name → its IAT-slot RVA (`src/pe.rs:151-154`).
  The whole `.idata` is `descriptors | ILT | IAT | hint/name | dll`.
- Data directories: only `dirs[1]` = Import table and `dirs[12]` = IAT are
  set, both from the single `idata` (`src/pe.rs:514-516`).
- Entry stub (`STUB_LEN = 0x12`, `src/pe.rs:269`; built at
  `src/pe.rs:294-304`): `sub rsp,0x28; call main; mov ecx,eax;
  call [rip+ExitProcess]; hlt`. `main_off` is looked up by the literal
  name `"main"` (`src/pe.rs:288-290`); missing ⇒ `CodegenError`. The IAT
  cell for the stub's `call` is `idata.iat_slot["ExitProcess"]`
  (`src/pe.rs:291`).
- Subsystem is the literal `b.u16(3)` = `WINDOWS_CUI` (`src/pe.rs:504`).
  `AddressOfEntryPoint = text_rva` (the stub, `src/pe.rs:489`).
- `RipRef::Import(name)` is resolved in `build_text` by
  `idata.iat_slot.get(name)` → unknown ⇒ `CodegenError("unknown import
  '{name}'")` (`src/pe.rs:324-328`). Other `RipRef` arms (`Str`, `Data`,
  `Func`, `Vtable`) already exist (`src/pe.rs:329-352`).
- `RipRef::Import` is `&'static str` (`src/codegen.rs:133`) — only string
  *literals* in codegen can name an import today.
- Section count is the literal `4` (`src/pe.rs:475`, `:609`) and
  `NumberOfSections` field; `.idata` is one section.
- A regression lock already exists: `exact_sect_align_boundary_no_spurious_page`
  (`src/pe.rs:692`) and the `tests/end_to_end.rs` 88 + `differential.rs`
  `mdbcc_determinism` byte-stability guard.

### Codegen — imports are emitted as fixed `RipRef::Import` literals
- All imports are emitted by codegen as `emit_riprel(&[0xFF,0x15],
  RipRef::Import("…"))` with a **string literal**: `GetStdHandle`/
  `WriteFile` in the printf/puts path (`src/codegen.rs:2193`, `:2202`,
  via `emit_write_buf`), `GetProcessHeap`/`HeapAlloc` in `new`
  (`src/codegen.rs:1946`, `:1951`), `GetProcessHeap`/`HeapFree` in
  `delete` (`src/codegen.rs:2014`, `:2019`). There is **no** general
  "call an arbitrary imported function by name" path.
- Call dispatch (`gen_call`, `src/codegen.rs:1515`): `printf`/`puts` →
  `gen_io_builtin`; `is_builtin(name)` (libc intrinsics, `:1624`) →
  `gen_libc`; overload → mangled `emit_call`; named fn-ptr →
  `emit_indirect_call`; else `emit_call(name,…)` which emits an
  **`E8` rel32** + `CallSite{at,callee}` (`src/codegen.rs:1920-1923`)
  resolved by `offsets[callee]` in `build_text` (`src/pe.rs:312-318`).
  An undefined call is a **link error** (`src/pe.rs:313`). There is no
  symbol→DLL table — an unknown name is *always* a unit-function call
  that then fails to link.
- `is_builtin` = `libc_ret(name).is_some() && !defined-in-TU`
  (`src/codegen.rs:1624`); `libc_ret` (`src/codegen.rs:2688`) is the
  closed list of libc intrinsics. This is the exact pattern Phase C
  generalises for Win32: a name table + a "TU may override it" guard.
- `compile_module` (`src/codegen.rs:256`) builds `Module { funcs,
  globals, vtables, record_count }` (`src/codegen.rs:184-192`); there is
  no place that records "which imports were used" or "is this a GUI app".

### Driver — one TU → one console PE, no mode selection
- `compile_to_pe_with` (`src/compile.rs:62`): lex → `pp::preprocess` →
  `Parser::parse` → `codegen::compile_module` → `pe::write_pe`. No
  subsystem/entry choice anywhere.
- `src/main.rs` parses `-o`/`--dump-tokens`/input; no subsystem flag, and
  none is wanted (subsystem is *detected*, not flagged — house style: no
  speculative knob).

### Preprocessor — system headers stub to empty
- `DefaultResolver::resolve` (`src/pp.rs:47`): every `<...>` system header
  (known or unknown) resolves to **empty bytes** (`src/pp.rs:49-60`).
  Intrinsics need no declarations: libc names are recognised by codegen,
  not by a header. `<windows.h>` therefore *already* "resolves" (to
  nothing) — what is missing is (a) the types it would declare and (b)
  the symbol→DLL knowledge.
- Type parsing: `decl_specifiers` only accepts built-in keywords; an
  unknown type name is `error_here("expected a type")`
  (`src/parser.rs:348-349`) **unless** it is a registered `typedef`
  (`src/parser.rs:200`, `:250`, `register_typedefs` `:1119`). `long`
  is LLP64 32-bit; `__int64`/`long long` = 8 (`src/parser.rs:339-365`).
  So Win32 typedefs (`HWND`, `UINT`, …) must reach the parser as real
  `typedef`s, exactly like a user `typedef unsigned char byte;`
  (`src/parser.rs:2235` test).

### Oracle harness — C-only, no GUI probe
- `tests/support/mod.rs`: `mdbcc_run` compiles in-process and runs the
  PE under a 10 s wall timeout (`run_with_timeout`, `:199`), capturing
  stdout/exit. O2 writes `t.c` and builds with `cl /nologo /MT`
  (`msvc_build_run`, `:396-413`); O3 writes `t.c` and builds with
  `bcc32` (`bcc32_ref`, `:516`). **Both reference arms hard-code a
  `.c` extension and C-mode compilation** — this is backlog **B-4**
  (it forces `virtual.c` off the 3-way; a C++ corpus file cannot be
  fed to `cl`/`bcc32` as C). `compare` (`:94`) is a pure stdout+exit
  equivalence relation; there is no window/liveness notion.
- `corpus_files(sub)` (`:564`) discovers `*.c` in `tests/corpus/<sub>`;
  `parse_skip` (`:156`) reads `// oracle: skip[...]` directives. The
  O2/O3 tests are `#[cfg(windows)]` in `tests/differential.rs`.

## Design

Five sub-areas (C1–C5) plus sequencing (C6). Each is the **smallest**
change that satisfies the Phase C scope; every one is dormant for a
console program (byte-identical regression argument, as Phase A/B).

### C1 — Multi-DLL import directory (`src/pe.rs`)

**Goal.** Replace the single hard-coded `KERNEL32` descriptor with N
descriptors (one per DLL actually imported), driven by which imports the
module used, with a built-in Win32 symbol→DLL table. The six existing
`KERNEL32` imports must serialise to **byte-identical `.idata`** for any
program that uses only them (i.e. every current program).

**Symbol→DLL table (the "minimal intrinsic `<windows.h>` half 1").**
A `const` table in `src/pe.rs` (single source of truth, deterministic,
no HashMap-into-bytes):

```
// (symbol, dll) — minimal, Phase-C scope only. Ordered.
WIN32_IMPORTS: &[(&str, &str)] = &[
    // KERNEL32 — the existing six MUST stay first and in this order so
    // the .idata for console programs is byte-identical.
    ("ExitProcess","KERNEL32.dll"), ("GetStdHandle","KERNEL32.dll"),
    ("WriteFile","KERNEL32.dll"),   ("GetProcessHeap","KERNEL32.dll"),
    ("HeapAlloc","KERNEL32.dll"),   ("HeapFree","KERNEL32.dll"),
    // USER32 — Phase C GUI minimum (MessageBoxA for O6; the rest are
    // the irreducible Phase-D set, added only when codegen can emit
    // them — do NOT pre-populate speculatively, house style).
    ("MessageBoxA","USER32.dll"),
];
```

Only `MessageBoxA` is added in Phase C (it is all O6 needs). Phase D
appends `RegisterClassA`/`CreateWindowExA`/`DefWindowProcA`/… *when its
codegen emits them* — not before (no speculative abstraction).

**`.idata` generalisation.** Generalise `build_idata` to:
1. Determine the **used import set** in deterministic order (see C1's
   "what is used" below). For a console program this is exactly the
   current six in the current order.
2. Group used symbols by DLL, preserving table order both across DLLs
   and within a DLL. Only DLLs with ≥1 used symbol get a descriptor.
3. Emit `k+1` `IMAGE_IMPORT_DESCRIPTOR`s (k = #DLLs, +null terminator):
   `desc_size = (k+1)*20`. Layout becomes
   `descriptors | per-DLL ILT | per-DLL IAT | hint/name | dll names`.
   Each descriptor's `OriginalFirstThunk`/`FirstThunk` point at that
   DLL's ILT/IAT sub-array (each null-terminated), `Name` at its DLL
   string. `iat_slot: HashMap<&str,u32>` still maps **every** used
   symbol → its IAT-slot RVA (unchanged contract for `build_text`).
4. `dirs[1]` = (first descriptor RVA, `desc_size`); `dirs[12]` = (IAT
   block start, total IAT size across all DLLs) — the IAT directory
   may legitimately span multiple DLLs' contiguous IAT sub-arrays.

**Byte-identical proof for the console path.** If the used set is exactly
the six `KERNEL32` symbols in table order, then: k=1, `desc_size=2*20`
(same), one DLL `"KERNEL32.dll\0"` (same), one ILT + one IAT of `n+1`
thunks in the same order (same), same hint/name blob order. Every byte
of `.idata`, every RVA, `SizeOfImage`, and the entry stub's
`iat_slot["ExitProcess"]` are unchanged ⇒ the whole PE is byte-identical.
This is *locked by a test* (C1 TDD below), not merely argued.

**What is "used".** Today `RipRef::Import` is `&'static str` and the
*only* importable names are the six baked into codegen. Phase C keeps the
import set **static and conservative**: `build_idata` includes a DLL's
symbols iff codegen could emit them. Concretely, the used set is computed
by scanning every `CompiledFn.riprefs` for `RipRef::Import(name)` and
mapping each through `WIN32_IMPORTS`. A symbol that codegen emits but is
absent from `WIN32_IMPORTS` is a hard `CodegenError` ("import 'X' has no
known DLL") — never silently wrong. (Pre-pass at `func_offsets`/layout
time, before `.idata` is sized; cheap, deterministic.) Result: a
console-only program's scan yields exactly the six (any program that calls
`new`/`printf`), the *same* six the current code hard-codes.

**`RipRef::Import` widening.** To let C2/C3 emit arbitrary Win32 calls,
`RipRef::Import(&'static str)` is widened to `RipRef::Import(String)`
(mirrors `RipRef::Func(String)`, the proven Phase-A precedent). All six
existing call sites pass string literals → `.to_string()`; no emitted
byte changes (the variant only carries a name used at link time). This
is the single codegen-type change Phase C needs; it is additive in spirit
(same discriminant, owned string) and covered by the determinism guard +
O1 byte-identical lock.

### C2 — Subsystem selection + WinMain entry stub (`src/pe.rs`)

**Detection (driver-side fact, computed in codegen, carried on `Module`).**
A TU is a **GUI app** iff it defines a function named `WinMain` (the
classic Win32 GUI entry; `WinMainCRTStartup` is the CRT's internal name
and is *not* user-written — we synthesise its behaviour in the stub, so
detecting `WinMain` is sufficient and minimal). Detection: in
`compile_module`, set `Module.entry: Entry` where

```
enum Entry { ConsoleMain, GuiWinMain }   // default ConsoleMain
```

`GuiWinMain` iff `sigs.funcs` (or overloads) contains `WinMain` **and**
it is *not* also defining `main` differently — if a TU defines *both*
`main` and `WinMain`, that is ambiguous: **hard `CodegenError`** ("a
translation unit defines both `main` and `WinMain`"), never a silent
guess (house style). A console program has no `WinMain` ⇒ `ConsoleMain`
⇒ everything below is byte-identical.

**Entry stub.** `build_text` branches on `module.entry`:
- `ConsoleMain` (unchanged, byte-identical): the current `STUB_LEN=0x12`
  stub calling `main`, exit code = `main`'s return (`src/pe.rs:294-304`).
- `GuiWinMain`: a stub that synthesises `WinMainCRTStartup` minimally:
  call `GetModuleHandleA(NULL)` for `hInstance` *(adds
  `GetModuleHandleA`→`KERNEL32` to the used set — KERNEL32 already a
  descriptor, no new DLL)*, pass `hInstance, NULL (hPrevInstance),
  "" (lpCmdLine), SW_SHOWNORMAL=1 (nCmdShow)` per the `WinMain` ABI
  (4 args, all register, Win64), `call WinMain`, `mov ecx,eax`,
  `call [rip+ExitProcess]`, `hlt`. The `lpCmdLine` pointer may be a
  NULL (0) in v1 — Phase C's O6 app does not read it; a real
  `GetCommandLineA` is a Phase-D refinement, explicitly deferred.
  Stub length is a second `const` (`GUI_STUB_LEN`); `func_offsets`/the
  `.text` vsize pre-pass (`src/pe.rs:406`, `:212`) must use the
  *selected* stub length — the always-on size-divergence check
  (`src/pe.rs:447-453`) already fails loudly if they disagree, so a
  wrong constant cannot ship a silently-unloadable PE.
- Subsystem field: `b.u16(if gui {2} else {3})` (replaces the literal
  `3` at `src/pe.rs:504`). Console ⇒ still `3`, byte-identical.
- `AddressOfEntryPoint = text_rva` unchanged (stub is still first in
  `.text`); only the stub's *contents* and length differ for GUI.

**Why a synthesised stub, not a CRT.** We own the whole pipeline (the
point of the project); there is no `WinMainCRTStartup` object to link.
The stub is the *entire* Phase-C CRT for GUI: hInstance + cmdshow +
call + exit. No atexit, no global ctors-via-CRT (mdbcc has no global
ctor mechanism yet; that is a known gap owned elsewhere, not Phase C).

### C3 — Minimal intrinsic `<windows.h>` (types half)

C1 supplies the *symbol→DLL* half. The *types* half: a GUI source writes
`HWND`, `UINT`, `WPARAM`, `LPARAM`, `HINSTANCE`, `LPCSTR`, … and
`int WINAPI WinMain(HINSTANCE,HINSTANCE,LPSTR,int)`. Today these are
unknown type names ⇒ parse error (`src/parser.rs:348`).

**Mechanism — a built-in header *body*, not a code change.** The
existing intrinsic model is "system header resolves to bytes the
preprocessor then lexes/parses". libc resolves to *empty* because libc
names are recognised in *codegen*. Win32 *types* cannot be recognised in
codegen (they are type names the *parser* needs). The minimal, in-style
solution: `DefaultResolver::resolve` returns, **for `windows.h` only**, a
small fixed byte string of `typedef`s + a `WINAPI`/`CALLBACK`/`APIENTRY`
macro, instead of empty:

```
typedef unsigned int   UINT;
typedef unsigned long  DWORD;          /* LLP64: long==32 (parser.rs:364) */
typedef int            BOOL;
typedef void          *HANDLE;
typedef HANDLE         HWND;           /* opaque handles == void*  */
typedef HANDLE         HINSTANCE;
typedef HANDLE         HMODULE;
typedef HANDLE         HMENU;
typedef char          *LPSTR;
typedef const char    *LPCSTR;
typedef unsigned __int64 WPARAM;       /* Win64 sizes: 8 bytes      */
typedef          __int64 LPARAM;
typedef          __int64 LRESULT;
#define WINAPI                          /* calling-conv is a no-op:  */
#define CALLBACK                        /*  we have ONE Win64 ABI    */
#define APIENTRY
#define CONST const
```

Every construct here is **already supported** by the parser:
`typedef … name;` flows through `register_typedefs` (`src/parser.rs:1119`,
test `:2235`); object-like `#define` is fully supported (the pp already
does object macros). `void*`-sized handles + `__int64`-sized
`WPARAM/LPARAM/LRESULT` match the Win64 ABI and the parser's existing
sizes (`src/parser.rs:339`,`:364`). **No parser or codegen change** — the
header body is data. It lives as a `const &str` in `src/pp.rs` next to
`DefaultResolver`, returned only for the literal name `windows.h`
(`windef.h`/`winuser.h`/`winbase.h` may alias to the same body or empty
— add only if a Phase-C/O6 source `#include`s them; do not pre-add).

**Scope discipline.** Only the handful of types the O6 app + a Phase-D
"hello window" will name. Not `RECT`/`MSG`/`WNDCLASS` structs yet —
those are Phase D/G (`MSG`/the message loop) and are added there, with
their members, when codegen can use them. Phase C ships the *minimum*
that makes a `MessageBoxA` GUI app parse. `MessageBoxA` itself needs **no
declaration** — like libc, the call is recognised by name in codegen
(C1's used-set scan picks it up); `<windows.h>` is only for the *types*
in the program's own signatures.

**Codegen call path for `MessageBoxA` (and arbitrary Win32).** Add a
minimal extension to `gen_call` (`src/codegen.rs:1515`): after the
libc/overload/fn-ptr checks and before the default unit-call
`emit_call`, if `name` is in `WIN32_IMPORTS` and the TU does **not**
define it itself (same `!self.sigs.funcs.contains_key` guard as
`is_builtin`, `src/codegen.rs:1624`), marshal args via the **existing
Phase-A register+stack path** and emit
`emit_riprel(&[0xFF,0x15], RipRef::Import(name.into()))` (an indirect
`call [rip+IAT]`, exactly how `WriteFile` is already called at
`src/codegen.rs:2202`). Argument marshalling reuses `emit_call`'s slot
logic verbatim — refactor the marshalling tail of `emit_call` so the
import path and the `E8` path share it (DRY; small, mirrors how
`emit_indirect_call` already parallels `emit_call`). No new ABI. Return
value is in EAX/RAX like every other call. A Win32 symbol the TU
overrides falls through to the normal unit-call path (user wins —
identical to the libc-override rule).

### C4 — Oracle O6 (GUI liveness) — `tests/gui.rs`

O6 is **honestly weaker** than the O1/O2/O3 stdout differential: a GUI
app has no stdout to diff, and there is no Borland-OWL behavioural
reference (D-3). O6 asserts only **liveness**: the app builds, launches,
creates a real top-level window, can be dismissed programmatically, and
exits cleanly within a timeout. It is a *tripwire*, not a conformance
oracle — documented as such (matches the roadmap's explicit honesty).

**The app (hand-written, in the test, not the corpus).** A ~5-line C
program is the smallest thing that exercises the *entire* Phase C
substrate end to end:

```c
#include <windows.h>
int WINAPI WinMain(HINSTANCE hI, HINSTANCE hP, LPSTR cmd, int show) {
    return MessageBoxA(0, "mdbcc-o6-body", "mdbcc-o6-title", 0);
}
```

This forces: C3 types parse (`HINSTANCE`/`LPSTR`/`WINAPI`); C2 detects
`WinMain` → subsystem 2 + GUI stub; C1 emits a `USER32` descriptor +
`MessageBoxA` IAT slot; Phase-A ABI passes 4 args; the PE loads and runs
on Windows 11. `MessageBoxA(…, MB_OK=0)` creates a **modal dialog** with
a known title.

**The probe (Rust, std-only, no new deps).** `tests/gui.rs`,
`#[cfg(windows)]`, reusing `tests/support` (`mdbcc_compile`, `work_dir`,
`run_with_timeout`-style timing):
1. Compile the app in-process with `mdbcc_compile`; assert it produced a
   PE (a Phase-C codegen/PE red surfaces here, not as a hang). Sanity-
   assert the **subsystem byte == 2** and an `.idata` descriptor names
   `USER32.dll` by parsing the PE bytes directly (a *strong, cheap*
   structural check that does not depend on a GUI session — this is the
   part of O6 that is as rigorous as the rest of the suite).
2. Spawn the exe (`Command::spawn`, detached, no stdin).
3. From the test process, find the window by **exact title**
   `"mdbcc-o6-title"`: poll `FindWindowA(NULL, "mdbcc-o6-title")` (a
   `MessageBoxA` is a real top-level window with the title as its
   caption) for up to ~5 s, 50 ms cadence. The Win32 calls
   (`FindWindowA`, `PostMessageA`/`SendMessageA`, `WaitForSingleObject`,
   `GetExitCodeProcess`) are declared via a tiny `extern "system"`
   block in `tests/gui.rs` (Rust FFI to `user32`/`kernel32`); **no new
   crate dependency** (matches the std-only constraint; `windows`/`winapi`
   crates are *not* added).
4. Dismiss it: `PostMessageA(hwnd, WM_CLOSE, 0, 0)` (a message box
   honours `WM_CLOSE` → returns `IDCANCEL`; `WM_CLOSE` is more robust
   than synthesising a button click and needs no child-window walk).
5. `WaitForSingleObject(process, 5000)`; assert it signalled (not
   timed out — a hang is a **FAIL**, the test kills the process and
   fails), then `GetExitCodeProcess` is a defined value (the
   `MessageBoxA` return; we assert it is *not* `STILL_ACTIVE` and not a
   crash `STATUS_*` code via the existing `is_crash_code` from
   `tests/support`).

**Headless / no-session self-skip.** CI or a Session-0 service has no
interactive window station; `FindWindowA` would never find the dialog
and the test would falsely fail. O6 **self-skips loudly** (the
established pattern: `o2_active`/`o3_active` in `tests/support/mod.rs`,
and the SKIP-print style in `tests/differential.rs`) when no interactive
desktop is available. Detection: `GetProcessWindowStation` +
`GetUserObjectInformationW(UOI_FLAGS)` → if not `WSF_VISIBLE`, or a
cheap "can I create+find my own probe window" pre-check fails, print
`"[O6] SKIP: no interactive window station (headless) — structural
checks still ran"` and **still keep the step-1 structural assertions**
(subsystem==2, USER32 descriptor present). That keeps O6 contributing
*real* signal even headless: the rigorous half (PE structure) always
runs; only the liveness half is desktop-gated. This split is the honest
mitigation for "O6 is weaker + headless CI" — we never claim liveness we
did not observe, and we never lose the structural guarantee.

**Honesty statement (verbatim in the doc + the test header).** O6 proves
"a GUI Win32 PE mdbcc emitted loads, shows a titled top-level window, and
exits cleanly when asked". It does **not** prove the window's contents,
layout, or message handling are correct — that has no automated oracle
without a Borland-OWL reference (D-3). `mdscreensnap` golden + a real
target app (Phase I) are the heavier follow-ups; Phase C deliberately
ships only the tripwire.

### C5 — Backlog B-4 fold-in: harness C++ mode (optional Phase C sub-item)

Phase C already touches the PE writer and (via O6) the oracle harness, so
this is the cheapest moment to clear **B-4** (charter: "fold B-4 in when
Phase C touches the PE writer / oracle harness"; it restores
`virtual.c`'s 3-way that Phase B could not complete).

**Design (minimal, opt-in, additive).** Extend `tests/support/mod.rs`:
- A new directive `// oracle: lang cpp` parsed by an extended
  `parse_skip`-sibling (`parse_lang`) — same first-15-lines scan, same
  pure-function + unit-test discipline as `parse_skip`
  (`tests/support/mod.rs:156`, unit-tested at `:692`).
- `msvc_build_run` / `bcc32_ref` / `bcc32_accept` take the language: C++
  ⇒ write the temp file as `t.cpp` and pass the C++-mode flag — `cl`
  infers C++ from `.cpp` (or pass `/TP`); `bcc32` infers from `.cpp` (or
  pass `-P`). mdbcc is language-agnostic in-process (already compiles the
  C++ subset). Default (no directive) is unchanged ⇒ **every existing
  corpus file and all current differential behaviour is byte-for-byte
  identical** (the `.c`/C path is the untouched default branch).
- Then add `// oracle: lang cpp` to a `tests/corpus/portable/virtual.c`

## Regression (console path byte-identical — the central invariant)

Every Phase C addition is **dormant for a console program**:
- C1: used-set scan of a console program = the six KERNEL32 symbols in
  table order ⇒ k=1, identical descriptor/ILT/IAT/hint-name/dll bytes ⇒
  identical `.idata`, RVAs, `SizeOfImage`, stub IAT cell. (Locked by the
  C1 golden test.)
- C2: no `WinMain` ⇒ `Entry::ConsoleMain` ⇒ the exact current
  `STUB_LEN=0x12` stub + subsystem `3`. Zero byte change.
- C3: `<windows.h>` body only materialises if the source `#include`s it;
  a console program that doesn't is unaffected (and even if included,
  unused typedefs emit no bytes — they are parser-only).
- C5: the C path is the untouched default; `.c` corpus + all current
  differential runs are byte-for-byte unchanged.
- `RipRef::Import(&'static str)→String` carries a name used only at link
  time; emitted bytes are identical (determinism guard + O1 lock prove
  it). This is the same additive-variant argument as Phase A's
  `RipRef::Func`.

The argument is *identical in form* to the one proven in the PE-layout
fix, Phase A and Phase B; O1's 88 e2e + the determinism guard + the new
C1 golden are the executable proof.

## Deferred (explicit — no speculative abstraction)

- **Message loop, `RegisterClassA`/`CreateWindowExA`/`DefWindowProcA`,
  `WndProc` thunk, `MSG`/`WNDCLASS` structs** — Phase D. C1's
  `WIN32_IMPORTS` and C3's header grow there, *driven by codegen that
  actually emits them*.
- **Real `GetCommandLineA`/argv, `atexit`, global ctor/dtor via a CRT,
  STARTUPINFO** — not Phase C; the GUI stub is the minimal CRT
  (hInstance + cmdshow + call + exit). cmdLine is NULL in v1.
- **Import-by-ordinal, delay-load, forwarders, bound imports, `.tls`,
  exception/SEH directories, resources (`.rsrc`)** — out of scope;
  Phase G owns resources, others are not needed for OWL v1.
- **`mdscreensnap` golden, real target-app conformance** — Phase I; O6
  is deliberately only the liveness tripwire.
- **A `-subsystem` / `-mwindows` driver flag** — *not added*: subsystem
  is detected from `WinMain`, not flagged (house style: no knob without
  a need). Revisit only if a real app needs an override.
- **`stdcall`/`__stdcall` name decoration & calling convention** — we
  have exactly one Win64 ABI; `WINAPI`/`CALLBACK` are `#define`-empty.
  Correct for Win64 (no `@N` decoration in x64); recorded so Phase D/E
  does not reintroduce a 32-bit assumption.
- **C5 if time-boxed out** — cleanly stays backlog B-4; never a
  half-applied state.

## Risks (honest)

1. **Import-directory correctness.** Multi-descriptor `.idata` is the
   highest-risk change: a wrong ILT/IAT/hint-name offset yields a PE the
   loader silently refuses or that faults on first Win32 call.
   *Mitigation:* the C1 golden byte-identical lock (console path can't
   regress, executably), the multi-DLL structural test (offsets/overlap/
   `SizeOfImage`), the existing always-on `.text` size-divergence hard
   error (`src/pe.rs:447`), and O6 actually loading+running a 2-DLL PE
   on Windows 11. Keep the layout order
   `descriptors|ILT|IAT|hint/name|dll` (same shape as today, just
   per-DLL sub-arrays) to minimise the delta.
2. **Subsystem regression.** A mistake in C2 detection or the GUI-stub
   length could corrupt the console stub or `SizeOfImage`. *Mitigation:*
   `Entry::ConsoleMain` is the literal current code path (no behavioural
   change for it); the C2 regression test pins the exact console stub
   bytes; the always-on size pre-pass/emit divergence check
   (`src/pe.rs:447-453`) hard-errors if a stub-length constant is wrong
   (cannot ship silently-unloadable). The `both main and WinMain` →
   hard error removes the only ambiguous case.
3. **O6 is weaker than a stdout differential, and headless CI.** No
   Borland-OWL reference exists (D-3); a GUI app has no diffable stdout.
   *Mitigation (honest, not papered over):* O6 is explicitly only a
   *liveness tripwire*; its **rigorous half (PE-structure assertions:
   subsystem==2, USER32 descriptor, IAT slot) runs even headless** and
   is as strong as the rest of the suite; the *liveness half* self-skips
   loudly with a clear message when no window station exists (exactly
   the `o2_active`/`o3_active` precedent). We never assert liveness we
   did not observe. The language features *under* the GUI stay fully
   O1/O2/O3-validated (Phase A/B). `mdscreensnap` + Phase I are the
   acknowledged heavier follow-ups, deliberately out of Phase C.
4. **`<windows.h>` body drift / over-reach.** Hand-written typedefs
   could mis-size a type vs the Win64 ABI (e.g. `long`-vs-`__int64`),
   or scope-creep into Phase-D structs. *Mitigation:* the C3 `sizeof`
   tests pin `WPARAM/LPARAM/LRESULT/HWND == 8`; the body is the bare
   minimum to parse the O6 app (no `MSG`/`WNDCLASS`); every type maps to
   a parser size already exercised by libc/dialect corpus.
5. **`RipRef::Import` widening churn.** Touching all six call sites +
   the pe.rs match arm. *Mitigation:* mechanical `.to_string()` at six
   literals + one arm (mirrors Phase A's `RipRef::Func` exactly);
   determinism guard + O1 byte-identical lock catch any emitted-byte
   drift; it is the minimal enabler for arbitrary Win32 calls (the
   alternative — keeping `&'static str` — cannot express a
   program-derived import name).
6. **Concurrent agents on `src/pe.rs`/`src/codegen.rs`.** Phase C edits
   the same hot files as in-flight work. *Mitigation:* per the charter,
   apply on a confirmed-clean tree, keep each increment small and
   atomic, do not refactor unrelated code, retry-on-foreign-build-error
   rather than fixing others' code.
