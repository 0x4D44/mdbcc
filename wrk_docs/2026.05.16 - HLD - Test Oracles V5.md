- **V3→V4 (this round):** the build-health guard counted only
  *build/launch* failures, so a wired-up-but-wrong toolchain (`cl`
  builds+runs but mis-behaves) would flood **false FAILs blamed on
  mdbcc** through the FAIL channel — closed by (a) a **known-answer
  probe** (harness asserts Rust-computed expected bytes over a

  reference-suspect FAIL-rate guard**. Minors: dialect parse-smoke is a
  tripwire only (mdbcc silently drops unknown constructs); 8 MiB
  overflow ⇒ WARN-then-EXCLUDE; advisory pair is now {reference cmdline}
  vs {+`/O2`} so one arm *is* the compared reference; printf directive
  must match result signedness; stale §4.4 cross-refs fixed.
- **V4→V5 (this round):** V4's blanket "≥25% FAIL ⇒ reference-suspect
  WARN, never a clean red blamed on mdbcc" was the *dual* defect — it
  auto-exonerated a broad genuine mdbcc regression as the reference's
  fault, defeating O2's purpose. Fixed by **gating that guard on the
  known-answer probe** (which is `cl`-only, so it discriminates):
  probe GREEN + broad FAIL ⇒ **hard red attributed to mdbcc** with a

## 1. Purpose

Define the minimum oracle set that makes the autonomous build loop
trustworthy, and pin down *exactly* what "behaviourally equivalent" means
so a differential cannot manufacture false signal or sit silently green.
Quality stance (CLAUDE.md): solve the problem at hand, no speculative
abstraction, no migration/rollback, **no feature flags, minimal env vars**.

## 2. Environment (probed 2026-05-16)

- MSVC installed: `vswhere.exe` at the standard path → VS Community,
  `vcvars64.bat` + `cl` x64 present. `cl` is **not** on `PATH`.
- No Borland/Embarcadero compiler installed.
- `.gitignore` ignores `target/ target_ci/ bin/ obj/ venv/ .venv/ env/
  *.tmp *.log` — it does **not** ignore `wrk_tools/` or `wrk_corpus/`.

## 3. Oracle catalogue (compact)

| ID | Oracle | Proves | Gating | When |
|----|--------|--------|--------|------|
| O1 | Existing hand-expected e2e (`tests/end_to_end.rs`) | End-to-end correctness vs hand-computed values | **yes, authoritative** | live |
| O2 | Differential vs MSVC `cl` over a small on-disk corpus | Semantic equivalence on portable C | yes, when `cl` usable | v1 |
| O3 | Differential/acceptance vs a real Borland compiler | Correctness of the *Borland dialect* | yes, when present | v3 (setup-gated) |
| O5 | x64 structural-decode sanity of emitted `.text` | Bytes are well-formed x64 (not semantics) | yes | v2 |

O1 stays the **authoritative gate** and is **not deleted or migrated**.
O2 augments it. Perf/compile-time is a **non-goal** (one print if ever
wanted; never gated — naïve codegen, "run" not "run fast"). No O4/O6.

Why O3 matters (settled; Arthur acquires binaries): MSVC structurally
cannot compile authentic Borland source, so for dialect code MSVC is not a
valid reference — only a real Borland compiler is. bcc64 (Win64) =
behavioural; bcc32-5.5 (Win32) = front-end acceptance via `bcc32 -c`.
Detail deferred to v3 when a binary is actually in `wrk_tools/`.

## 4. O2 — the only new oracle built in v1

### 4.1 Corpus is NEW files, not a retrofit
The ~120 e2e program invocations are Rust string literals/fragments
(several per test); there is no on-disk corpus, and an extractor for our
own test file would be fragile overengineering. Instead:

- `tests/corpus/portable/*.c` — small, hand-authored complete TUs in the
  **mdbcc ∩ MSVC** intersection: deterministic, input-free, UB-free,
  avoiding mdbcc's known gaps (§4.5).
- `tests/corpus/dialect/*.c` — Borland-dialect programs. MSVC is excluded
  for these by construction; they are O3-only. In v1 they still get a
  **front-end parse-smoke** (mdbcc compiles them; assert it does not
  error/panic — no behavioural claim) so the project's core-value area
  has *some* automated pressure before bcc64 exists. This is a
  crash/parser-error **tripwire only**: mdbcc silently drops unrecognised
  constructs (e.g. `asm`), so a green parse-smoke is explicitly *not*
  evidence the dialect feature is supported (the §6 coverage line says
  `dialect-smoke (tripwire)` to avoid overstating it).
- `tests/end_to_end.rs` (O1) is untouched and remains authoritative.

### 4.2 Reference build
`cl /nologo /MT <src> /Fe:<out>` in a per-invocation dir
`target/oracle/<pid>_<n>/` (avoids `*.obj` collisions under parallel
`cargo test`). `/MT` (static CRT) so `ref.exe` is self-contained. No
`/EHsc` (no exceptions in scope), no `/O2` (codegen comparison is a
non-goal).

### 4.3 `cl` discovery + representative probe (no env var we define, no flag)
Locate `vswhere.exe` at its known path → resolve `vcvars64.bat`. Capture
its env with `cmd /c "\"<vcvars64>\" >NUL 2>&1 && set"`, keep only lines
matching `^[A-Za-z_][A-Za-z0-9_()]*=`, split on the **first** `=`, cache
in a `OnceLock`. Success criterion = a **known-answer probe build**:
`#include <stdio.h>\nint main(void){ printf("%d %u %lld\\n", -7,
4294967295u, 4294967295LL); return 7; }` built with the **exact §4.2
command line and flags**, then run — the harness asserts the
**Rust-computed** expected bytes `-7 4294967295 4294967295\n` (after
§4.4.3 normalisation) **and** exit 7. A fixed-string probe would only
prove include/lib *resolution*; asserting a sign/width/64-bit answer the
harness computes itself also catches a toolchain that is *wired up but
wrong* (mismatched UCRT, bad SDK). Bitness is implied by a working x64
stdio exe (the `VSCMD_ARG_TGT_ARCH=x64` check is a cheap defensive note,
not the gate). Three loud states: `cl ACTIVE`, `SKIP: cl not found`,
`SKIP: cl found but environment unusable`.

**Health guards** (a broken toolchain must never present as a green O2;
a sound toolchain's FAILs must not be auto-exonerated). With `cl`
ACTIVE — note the known-answer probe is `cl`-only, so it discriminates:
a wired-but-wrong `cl` **fails** the probe, a broken mdbcc **passes**
it:
- if **0** non-skip corpus files were successfully compared ⇒ loud WARN
  (compared nothing), not green;
- if a large fraction of non-skip files **fail to build/launch**
  (≥25%) ⇒ loud WARN (toolchain broken);
- a large fraction of *compared* files **FAIL** (≥25%) is gated on
  probe state:
  - probe was **GREEN** (toolchain proven sound by the same
    `cl`/flags) ⇒ this is a **hard red O2 result attributed to
    mdbcc**, with a triage banner ("broad O2 disagreement; probe
    GREEN → investigate mdbcc first; per-file §4.5 UB triage before
    final sign-off"). It is **not** downgraded to a toolchain WARN —
    auto-exonerating a broad mdbcc regression here would defeat O2's
    whole purpose (it exists to cover exactly the sign/width/UB-adjacent
    space O1's hand-expected set does not).
  - probe **degraded/flaky**, or the build/launch guard is also
    tripping ⇒ `WARN: reference-suspect — triage toolchain before
    trusting O2 FAILs` (the toolchain is demonstrably unstable, so the
    FAILs are not trustworthy as mdbcc signal).

### 4.4 Equivalence is defined as
A corpus program **passes** iff, for mdbcc's exe and `ref.exe`:

1. **Primary observable is stdout, not the exit code.** Corpus programs
   compute a result and report it via `printf("%d\n", r)` / `%u` etc.,
   then `return 0;`. This recovers full-range coverage (negative, >255,
   unsigned) through a channel where mdbcc and the MSVC CRT are
   byte-equivalent post-normalisation, and removes exit-code-range
   ambiguity. (Rationale: constraining `main`'s return to 0–125 would
   gut O2 and contradict O1, which deliberately returns -7/255/0x7FFFFFFF
   to test sign/width — O1 keeps that coverage; O2 routes it via stdout.)
   The print directive **must match the result's signedness** (`%d` for
   signed, `%u` for unsigned) — a mismatched directive makes *both* sides
   emit the same wrong text and yields a false PASS.
2. **Exit code** is still compared, as the `i32` from
   `std::process::ExitStatus::code()` on *both* sides (never mixed with
   `u32`); normally 0. `None` (killed/no code): only mdbcc ⇒ **FAIL**;
   both ⇒ **EXCLUDE**. Crash codes (high byte `0xC0`/`0x80`,
   Windows `STATUS_*`): mdbcc-only ⇒ **FAIL**, both ⇒ **EXCLUDE** — two
   crashes are *not* agreement.
3. **stdout** captured as **raw bytes (no string decode), read bounded
   (8 MiB; overflow ⇒ `WARN: <file> output-overflow — likely
   miscurated`, then EXCLUDE)**; compared byte-equal **after** stripping
   a `\r` immediately preceding each `\n` on *both* streams (MSVC CRT
   text-mode `\n`→`\r\n` vs mdbcc raw `WriteFile`). No other
   normalisation. Documented blind spot: O2 cannot catch a
   newline-encoding bug — O1's byte-exact check still can.
4. **stderr**: **not** in the pass/fail tuple (CRT-vs-no-CRT asymmetry);
   captured for failure diagnostics only.

### 4.5 Mandatory corpus filters (else the differential lies)
- **mdbcc printf gap**: no `%`-directive with flags/width/precision/length
  modifiers (mdbcc ignores them today → `"%5d"` diverges). A real mdbcc
  gap O2 should later drive fixing, not just curation.
- **Deterministic, input-free, UB-free.** UB/impl-defined exclusion is
  **hand-curated**: a leading `// oracle: skip <reason>` excludes a file.
  This is the **sole primary UB gate**; no automated UB analysis is
  attempted (explicit non-goal).
- **Advisory only** (not an exclude, not an exoneration): also build a
  second reference at the §4.2 command line **plus `/O2`** (so the §4.2
  build itself is one arm — the WARN describes the artifact actually
  compared); if the two disagree, emit
  `WARN: <file> reference-unstable — hand-curate`. It does **not**
  auto-EXCLUDE and **never** exonerates mdbcc. Rationale: `/Od`==`/O2`
  does *not* imply "no UB" (hardware/layout-deterministic UB —
  div/overflow/shift, mdbcc's weakest paths — agrees across MSVC modes),
  and `/Od`≠`/O2` does *not* imply UB (opt-sensitive but defined code).
  So a surprising O2 FAIL must be triaged for UB **before** being
  attributed to mdbcc; the WARN just flags candidates for the human.
- (bcc32-5.5 only, v3) exclude pointer-size-observing programs (Win32
  ptr=4 vs our Win64 ptr=8).

### 4.6 Execution robustness
Every child runs under a fixed **10 s wall-clock timeout**; exceeded ⇒
kill ⇒ mdbcc-only = FAIL, both = EXCLUDE. A **reference** launch failure
or recognised AV-quarantine of a freshly written file is retried **once**,
then reported as a distinct "reference failed to launch" state — never
conflated with a behavioural disagreement. An **mdbcc-exe** launch/crash
is reported on **first occurrence and never retried** (retrying could mask
a nondeterministic mdbcc crash as a pass — fail toward exposing mdbcc).

## 5. O5 — structural-decode sanity (v2, honest scope)

Linear-decode the whole `.text` with `iced-x86` (`[dev-dependencies]`
only; Arthur pre-approved; never linked into the shipping binary). Assert
**(a)** zero `INVALID` instructions and **(b)** decoded boundaries exactly
tile `[0, text.len())` (no gap/overlap/undecodable tail). Whether to also
range-check `rel32` targets is decided **when O5 is built (v2)**, not
pre-committed here.

Honest claim (recorded so the loop never over-trusts it): O5 proves bytes
are **well-formed x64**, *not* the **intended/semantically correct**
instructions — a typo'd-but-legal opcode passes O5 and is caught only
behaviourally. Unique value: catching truncated/garbage/out-of-bounds
emission on a path O1/O2 don't take. Precondition: valid only while
`.text` is pure code (true today; revisit if jump tables land in `.text`).

## 6. Engineering (simple, concrete, no premature abstraction)

- **No `Reference` trait/struct.** v1 is a concrete `fn msvc_ref(src) ->
  RunOutcome` + discovery helper. A second real reference (bcc) → extract
  a shared shape *then* (two concrete impls is the minimum to design an
  interface; one is not).
- One module `tests/differential.rs` + a small support module. Corpus =
  directories globbed; only metadata convention is `// oracle: skip
  <reason>`. No manifest/schema/stdin DSL.
- **Self-skip, never silently green.** Every run prints a one-line
  coverage summary (e.g. `oracles: O1 ACTIVE | O2 SKIP(cl env unusable) |
  dialect-smoke (tripwire)`). **O1 is the authoritative gate at all
  times**; O2/O3 only add signal. "Zero external differential oracles
  active" and the §4.3 compared-nothing / build-launch / reference-suspect
  breaches are loud WARNs, not green; a §4.3 probe-GREEN broad-FAIL is a
  hard red attributed to mdbcc (not a WARN).
- Artifacts under `target/oracle/` (already git-ignored).
- **Precondition (must precede any tool/corpus acquisition):** add
  `wrk_tools/` and `wrk_corpus/` to `.gitignore` (today neither is
  ignored; without this, acquired BCC binaries and copyrighted Borland
  sample sources would be committed).

## 7. Non-goals / recorded pushbacks (do not re-litigate)

- No machine-code comparison vs MSVC/BCC (optimiser noise).
- Perf/compile-time never gated; not designed here.
- MSVC is not a reference for Borland-dialect source; `dialect/` is
  O3-only, MSVC-excluded by construction; a future BCC disagreeing with
  MSVC on dialect code is **expected**, not "UB to exclude".
- No named triangulation model: "all *available* references must agree"
  is the whole rule.
- The `/Od`-vs-`/O2` check is **advisory only** — never an automated UB
  verdict, exclude, or mdbcc exoneration (§4.5).
- O5 is structural sanity only — not a codegen-correctness oracle.
- No automated UB analysis; the corpus is curated.

## 10. Open risks (accepted, watched — not blockers)

- bcc64 free standalone availability is intermittent and outside our
  control; O3 (the dialect oracle — the project's core value) may stay
  unbuilt. Fallback if it persists: bcc32-5.5 *behavioural* (Win32,
  pointer-size programs filtered). Until then, the v1 `dialect/`
  parse-smoke is the only automated dialect pressure — weak but real.
- Defender may quarantine freshly written unsigned exes under O2 churn;
  recommend a documented Defender exclusion for `target/oracle/`;
  launch-failure is a distinct retried state for the reference side only.
- Sandbox network availability for acquiring tools/corpus is unconfirmed;
  verify before scheduling v3 work.
