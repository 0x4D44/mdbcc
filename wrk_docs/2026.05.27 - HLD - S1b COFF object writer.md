## Context anchor

Today (post-S1a, 7547 LoC `codegen.rs` + 5 helper modules) the pipeline
is `compile.rs::compile_to_pe_with_rc` →
`codegen::compile_module(&TranslationUnit) -> Module` → `pe::
write_pe_with_rsrc(&Module, Option<&RcUnit>) -> Vec<u8>` (a PE32+ image).
Everything is in-process; there is no on-disk intermediate. To make
multi-TU work, S2's `-m32` switch, S5's "build OWL from source", S6's
sample apps, and S7's 64-bit retarget all possible, we have to break
the pipeline at the codegen↔pe seam, persist what crosses it as a COFF
`.obj` file on disk, and have a separate linker (`mdlink`, S1c) merge
N `.obj` files plus libraries into a PE.

## §1 — Boundary redesign

### §1.1 — What codegen.rs hands to pe.rs today

The current boundary is the `Module` struct (`src/codegen.rs:170-199`)
plus the four secondary types it transitively owns. Verbatim from the
source:

```rust
// src/codegen.rs:170
pub struct Module {
    pub funcs:       Vec<CompiledFn>,
    pub globals:     Vec<GlobalData>,
    pub vtables:     Vec<VtableImage>,
    pub record_count: usize,
    pub entry:       Entry,           // ConsoleMain | GuiWinMain
    pub typeinfo:    Vec<TypeInfoEntry>,
    pub eh_buffer_size: usize,
}

// src/codegen.rs:106
pub struct CompiledFn {
    pub name:        String,           // mangled (Borland-flavour H5)
    pub code:        Vec<u8>,          // raw x86-64 bytes
    pub calls:       Vec<CallSite>,    // E8 rel32 fixups
    pub riprefs:     Vec<RipReloc>,    // RIP+disp32 fixups
    pub strings:     Vec<Vec<u8>>,     // local string-literal pool
    pub fp_literals: Vec<u64>,         // promoted to globals
    pub try_scopes:  Vec<TryScope>,    // EH scope tables (eh.rs)
}

// src/codegen.rs:80 — every fixup site classifies as one of:
pub enum RipRef {
    Import(String),    // IAT slot (Win32 DLL symbol)
    Str(usize),        // string literal, local index
    Data(usize),       // module global, by index
    Func(String),      // address of another unit function
    Vtable(usize),     // class vtable by record id
}
```

`Module` is **emit-coupled, not link-coupled**: it carries unresolved
intra-TU references (vtable record-ids, string indices, function names)
that pe.rs resolves during `write_pe_with_rsrc`. The whole pipeline is
single-TU; nothing in `Module` admits an external (cross-TU) symbol.

pe.rs consumes `Module` in `write_pe_with_rsrc` (line 1382) by:
1. Laying out 4–5 sections (`.text`/`.idata`/`.rdata`/`.data`,
   optionally `.pdata`/`.xdata`/`.rsrc`) at fixed RVAs.
2. Iterating `module.funcs` and patching every `CallSite::at` with the
   computed `rel32` to the callee, every `RipReloc::at` with the
   computed `disp32` to the resolved target (IAT slot / `.rdata` string
   / `.data` global / function RVA / vtable RVA).
3. Building `.idata` from the `WIN32_IMPORTS` table and the union of
   names referenced by `RipRef::Import`.
4. Synthesising `.pdata`/`.xdata`/personality-function plumbing when
   `try_scopes` is non-empty (`build_xdata` / `build_pdata`,
   `read_prolog_alloc` validates the literal prologue bytes).
5. Synthesising `.rsrc` from the optional `RcUnit`.

### §1.2 — The new boundary: `Object`

Introduce a new IR type `Object` that is the COFF-shaped, linker-facing
view of one translation unit. Minimal sketch (only what COFF actually
needs):

```rust
// src/coff.rs (new) — IR + writer
pub struct Object {
    pub machine: Machine,              // x86_64 today; Machine::I386 in S2
    pub sections: Vec<Section>,
    pub symbols:  Vec<Symbol>,
    pub strtab:   StringTable,         // owned, deduped
    pub directives: Vec<u8>,           // `.drectve` contents (linker hints)
}

pub enum Machine { Amd64, I386 }       // I386 dormant until S2

pub struct Section {
    pub name:   SectionName,           // .text / .data / .rdata / .bss /
                                       // .pdata / .xdata / .drectve OR
                                       // a COMDAT name like ".text$Bar::m"
    pub data:   Vec<u8>,               // bss: empty; SizeOfRawData==0 path
    pub bss_size: u32,                 // for IMAGE_SCN_CNT_UNINITIALIZED
    pub relocs: Vec<Reloc>,
    pub characteristics: u32,          // IMAGE_SCN_* (set per kind)
    pub comdat: Option<Comdat>,        // selection code + leader symbol idx
}

pub struct Reloc {
    pub offset:   u32,                 // VirtualAddress in section
    pub symbol:   u32,                 // SymbolTableIndex
    pub kind:     RelocKind,           // mapped to IMAGE_REL_AMD64_* on write
}

pub enum RelocKind {
    Addr64,    // ADDR64       — vtable slots, absolute globals
    Addr32,    // ADDR32       — 32-bit absolute (rare in x64)
    Addr32nb,  // ADDR32NB     — RVA (e.g. .pdata RuntimeFunction fields)
    Rel32,     // REL32        — E8 call rel32 + RIP-relative call/lea
    SectionIx, // SECTION      — 16-bit section index (debug info)
    SecRel32,  // SECREL       — 32-bit section-relative offset (debug)
}

pub struct Symbol {
    pub name:     SymName,             // 8-byte slot or strtab offset
    pub value:    u32,
    pub section:  SectionRef,          // 1-based or UNDEFINED/ABSOLUTE/DEBUG
    pub kind:     SymKind,             // function | static-data | extern
    pub storage:  StorageClass,        // EXTERNAL | STATIC | WEAK_EXTERNAL
    pub aux:      Vec<AuxRecord>,      // section-def aux, weak-extern aux
}

pub enum SymName {
    Short([u8; 8]),     // when name.len() <= 8
    Long(u32),          // strtab offset (post-write fixup)
}

pub enum AuxRecord {
    SectionDef { length: u32, num_relocs: u16, checksum: u32,
                 number: u16, selection: ComdatSelect },
    WeakExtern { tag: u32, characteristics: u32 },
    // File and FunctionDef aux records: not needed until S8 (debug).
}
```

Field-by-field justification of minimality:

- **No `.idata`-related fields.** Imports go to the linker as plain
  EXTERNAL symbols (`UNDEFINED` section), and the linker resolves them
  via `.idata` synthesis. mdbcc loses zero capability here; the
  `WIN32_IMPORTS` whitelist moves to mdlink.
- **No `.rsrc` fields.** `.rsrc` is a per-image construct: the resource
  compiler (already in `src/rc/`) emits resources, and mdlink merges
  them per binary. mdbcc compilation of a .cpp produces no `.rsrc`.
- **No entry-mode field.** `ConsoleMain` vs `GuiWinMain` is a per-image
  property determined by which `main`/`WinMain` is *defined* in the
  final link set, not per-TU. mdlink picks the entry stub.
- **`directives` is `Vec<u8>`** rather than a structured type because
  `.drectve` is one or more whitespace-separated command-line
  fragments (`-defaultlib:libcmt`, `-export:foo`); mdbcc emits very
  few today (none, in fact). One `Vec<u8>` is the smallest seam.

Total surface area: ~50 LoC of types vs ~200 LoC for `Module` +
friends today, because COFF's external-symbol indirection collapses
the `RipRef`/`CallSite` duality. Every fixup becomes a `Reloc` over a
symbol index.

### §1.3 — How the existing PE writer retargets

The design recommends **path (b): move the PE writer into `mdlink`.**
Rationale:

- pe.rs's whole reason for existing — laying out an image, resolving
  every reference, synthesising .idata/.pdata/.xdata/.rsrc — IS the
  linker job. Keeping it in mdbcc forces a second "object decoder"
  layer between the new Object IR and the unchanged pe.rs, which is
  pure incidental complexity.
- The current `pe.rs` reaches into codegen-private types
  (`crate::codegen::RipRef`, `crate::codegen::Entry`,
  `crate::codegen::TypeInfoEntry`). After S1b, those types no longer
  cross the codegen↔world boundary; they're a codegen-internal
  implementation detail. Forcing pe.rs to import them is wrong.
- mdlink will need to do the same .idata / .pdata / .xdata / .rsrc
  synthesis for multi-TU programs as pe.rs does today for single-TU.
  Reusing the same code is the cleanest answer.
- The historical bytes of single-TU programs CAN be reproduced
  end-to-end if mdlink's PE writer is a port of today's pe.rs with
  the front-end changed from "consume Module" to "consume one or more
  Objects + library archives". The 88 e2e fixtures, `pe_imports.rs`,
  `pe_layout.rs`, `pe_rsrc.rs`, and `o1_byte_identity.rs` (88
  SipHash baselines) are all preserved by running them through
  `mdbcc -c | mdlink` end-to-end — provided mdlink picks the same
  default subsystem/entry/imports/section order.

Counter: **path (a) — pe.rs stays in mdbcc, called by a thin mdlink
that decodes Objects back to Module** — is technically cheaper to
prototype (no port of pe.rs) but trades long-term clarity for short-
term diff size. Reviewer judgment: path (b). Estimated extra port
cost: small (pe.rs is ~2074 LoC; ~80% is mechanical move + adapt;
~20% needs slight reshaping for multi-Object input). Filed for Arthur
in §6 as Q1.

### §1.4 — Public-API delta

After S1b lands, the crate's lib.rs surface changes minimally:

```rust
// src/lib.rs (proposed)
pub mod ast;
pub mod codegen;
pub mod coff;       // NEW — Object IR + COFF writer
pub mod compile;
pub mod eh;
pub mod lexer;
pub mod parser;
pub mod pp;
pub mod rc;
// pe stays in tree for one or two ticks for backward-compat;
// removed when mdlink is the single image producer.
pub mod pe;

pub use compile::{CompileError, compile_to_object};  // NEW entry
pub use compile::{compile_to_pe};                    // retained
```

`compile.rs` grows one new function:

```rust
pub fn compile_to_object(
    src: &[u8],
    file_name: &str,
    resolver: &dyn IncludeResolver,
) -> Result<coff::Object, CompileError>;
```

Existing `compile_to_pe` stays (it becomes a wrapper:
`compile_to_object` → `mdlink::link_single` → `Vec<u8>`) for one tick
so the 88 e2e tests + 17 determinism fixtures don't have to be
rewritten in lockstep with the boundary move.

`src/main.rs` (the `bcc` driver) acquires a `-c` flag:

```text
bcc [--dump-tokens] [-c] [-o <out>] <file.c|file.cpp>
   without -c: produces <out>.exe via in-process link (today's path).
   with    -c: produces <out>.obj (COFF) and exits — no link step.
```

When `mdlink` lands in S1c, `bcc <file.c>` (no `-c`) shells out to
`mdlink` to produce the final PE; the in-process fast path is
removed. Q2 in §6 asks Arthur to ratify "always go through obj/link"
vs "keep in-process as a fast path".

## §2 — COFF write specification

This section spells out every byte mdbcc-COFF emits, for x86_64
(`IMAGE_FILE_MACHINE_AMD64 = 0x8664`). Source for the structures:
Microsoft PE/COFF spec §4 (object files) — captured in this session.

### §2.1 — File-level layout

```
+------------------------------------+
| IMAGE_FILE_HEADER       20 bytes   |
+------------------------------------+
| IMAGE_SECTION_HEADER[N] 40 bytes ea|   N = section count
+------------------------------------+
| Section data (raw bytes per sec)   |   concatenated, no alignment
+------------------------------------+
| Relocations per section            |   12 bytes per IMAGE_RELOCATION
+------------------------------------+
| COFF symbol table                  |   18 bytes per IMAGE_SYMBOL
+------------------------------------+   (including aux records)
| String table                       |   4-byte size LE + null-term names
+------------------------------------+
```

IMAGE_FILE_HEADER:
- `Machine = 0x8664` (Amd64)
- `NumberOfSections = N`
- `TimeDateStamp = 0` (determinism; never the real time)
- `PointerToSymbolTable = offset` (computed)
- `NumberOfSymbols = symbol count incl. aux records`
- `SizeOfOptionalHeader = 0` (none in object files)
- `Characteristics = 0` (object files: no `IMAGE_FILE_EXECUTABLE_IMAGE`)

### §2.2 — Sections we emit

| Section     | Characteristics                                                        | Purpose                                          |
|-------------|-------------------------------------------------------------------------|--------------------------------------------------|
| `.text`     | CNT_CODE \| MEM_EXECUTE \| MEM_READ \| ALIGN_16                          | Function bytes                                   |
| `.data`     | CNT_INITIALIZED_DATA \| MEM_READ \| MEM_WRITE \| ALIGN_8                  | Mutable globals (`int g = 5;`)                   |
| `.bss`      | CNT_UNINITIALIZED_DATA \| MEM_READ \| MEM_WRITE \| ALIGN_8                | Zero-init globals (`int g;`)                     |
| `.rdata`    | CNT_INITIALIZED_DATA \| MEM_READ \| ALIGN_8                              | String literals, vtables, typeinfo, FP literals  |
| `.pdata`    | CNT_INITIALIZED_DATA \| MEM_READ \| ALIGN_4                              | RUNTIME_FUNCTION entries (one per function)      |
| `.xdata`    | CNT_INITIALIZED_DATA \| MEM_READ \| ALIGN_4                              | UNWIND_INFO blobs                                |
| `.drectve`  | LNK_INFO \| LNK_REMOVE                                                   | Linker directives (default libs, exports)        |

COMDAT variants for templates, inline-method definitions, vtables of
exported classes, and the synthesised copy-ctor (`build_synth_copy_ctor`,
cpp.rs:274):

| Section pattern   | LNK_COMDAT | Selection      | Used for                              |
|-------------------|------------|----------------|---------------------------------------|
| `.text$<symbol>`  | yes        | SELECT_ANY     | Inline / template instantiations      |
| `.rdata$<class>`  | yes        | SELECT_ANY     | Per-class vtable image                |
| `.rdata$xt$<cls>` | yes        | SELECT_ANY     | Per-class typeinfo entry              |
| `.xdata$<symbol>` | yes        | SELECT_ASSOCIATIVE → .text$<symbol> | Per-COMDAT EH info |
| `.pdata$<symbol>` | yes        | SELECT_ASSOCIATIVE → .text$<symbol> | Per-COMDAT pdata    |

The `.text$<sym>` naming convention follows the MSVC / lld-link
de-facto convention: the `$` splits the canonical merge key
(`.text`) from the COMDAT discriminator (`<sym>`), so the linker
folds duplicates across TUs by the discriminator. mdbcc + bcc32
emit-side conventions differ (BCC's OMF uses COMDEF for the same
deduplication purpose, see §3.4); we use the MSVC convention because
our consumer is MSVC-COFF linkers (mdlink, lld-link, link.exe).

### §2.3 — Symbol table layout

Per-symbol shape (`IMAGE_SYMBOL`, 18 bytes):

```
[0..8]   Name           — short slot OR (Zeroes=0; Offset=strtab idx)
[8..12]  Value          — function: 0 (overridden by reloc base); data:
                           offset within section
[12..14] SectionNumber  — 1-based section index OR
                          0 = UNDEFINED (extern reference)
                         -1 = ABSOLUTE (vs an immediate)
                         -2 = DEBUG (compiler-emitted)
[14..16] Type           — 0x20 for functions, 0 otherwise
[16]     StorageClass   — EXTERNAL(2), STATIC(3), WEAK_EXTERNAL(105)
[17]     NumberOfAuxSymbols
```

Symbol emission order (deterministic, byte-identity-friendly):

1. One STATIC section-definition symbol per emitted section (in
   section-header order). Each carries one Aux Format 5 record:
   `Length = section data size`, `NumberOfRelocations`,
   `CheckSum = 0` (we don't bother — mdlink doesn't need it),
   `Number / Selection` for COMDATs only.
2. One EXTERNAL symbol per function defined in this TU (mangled name).
   `Value = offset within .text`, `SectionNumber = .text idx`,
   `Type = 0x20`. No aux record.
3. One STATIC symbol per inline private storage (string literal RVA
   stubs, FP literals, vtables, typeinfo). Internal names mdbcc
   generates uniquely (`.Lstr.<fn>.<idx>`, `.Lflit.<bits>`,
   `.Lvtbl.<rec>`, `.Lxt.<rec>`).
4. One EXTERNAL undefined symbol per cross-TU reference (referenced
   functions not defined here, externs, imports). `SectionNumber = 0`,
   `Value = 0`. Imports are encoded as undefined externals named
   `__imp_<symbol>` to match the MS convention for IAT references
   (mdlink sees `__imp_ExitProcess` and synthesises the IAT slot).

Aux-record-count discipline: COFF's strict rule is "the immediately
following N entries are auxiliary records belonging to this symbol".
Order in our table:

- Section symbols: 1 aux (Format 5).
- Weak externals (rare; for inline functions where the linker should
  pick from any TU that defines the same): 1 aux (Format 3).
- Function symbols: 0 aux (we don't emit Function-Definition aux
  records; those are for `.bf`/`.ef` debug info that we don't have).

### §2.4 — Relocations per section

Today every patch site in `build_text` (pe.rs:633) becomes a
relocation in COFF. The mapping is mechanical:

| Today (pe.rs)                                | Becomes (COFF reloc)            |
|----------------------------------------------|----------------------------------|
| `CallSite::at` (`E8 rel32` to unit function) | `REL32` against function symbol |
| `RipRef::Import` (call/lea via IAT)          | `REL32` against `__imp_<name>` extern |
| `RipRef::Str` (lea string)                   | `REL32` against `.Lstr.*` static |
| `RipRef::Data` (mov global)                  | `REL32` against `.Ldata.*` static OR data symbol |
| `RipRef::Func` (lea funcptr)                 | `REL32` against function symbol |
| `RipRef::Vtable` (lea vtable)                | `REL32` against `.Lvtbl.*` static (or COMDAT) |
| vtable slot (abs function address)           | `ADDR64` against function symbol |
| typeinfo entry (vtable RVA)                  | `ADDR32NB` against vtable symbol |
| `.pdata` RUNTIME_FUNCTION.BeginAddress       | `ADDR32NB` against function symbol |
| `.pdata` RUNTIME_FUNCTION.EndAddress         | `ADDR32NB` against function symbol + size |
| `.pdata` RUNTIME_FUNCTION.UnwindInfoAddress  | `ADDR32NB` against `.xdata` symbol |
| `.xdata` ExceptionHandler RVA                | `ADDR32NB` against personality fn |
| `.xdata` scope-table BeginAddress / EndAddr  | `ADDR32NB` against function sym |
| `.xdata` scope-table HandlerAddress          | `ADDR32NB` against function sym |
| `.xdata` typeinfo table base RVA             | `ADDR32NB` against `.Lxt.*` sym |
| global pointer-to-string (`ptr_str` field)   | `ADDR64` against `.Lstr.*` static |

mdbcc today bakes vtable slots, typeinfo entries, and global string
pointers as ABSOLUTE addresses using a fixed `IMAGE_BASE` (the same
trick `ptr_str` uses; see codegen.rs:141 and pe.rs:528). In COFF
those become **`ADDR64` relocations against the target symbol**, and
the linker resolves them once `ImageBase` is known. This is a strict
generalisation; the resulting bytes after linking are identical for
the same `ImageBase`.

`REL32_1..5` (offsets `+1..+5` from the next-byte default) are
**not used** by mdbcc — every RIP-relative emit puts the disp32
immediately before the next instruction. Reserved in the writer's
enum but never emitted; the unit test asserts emission only uses
`REL32`. Future codegen optimisations that fuse a constant-pool
load with an immediate may want them; deferred.

`ABSOLUTE` (0) is never emitted — it's the "no-op" reloc.

### §2.5 — String table policy

A symbol's name occupies the 8-byte slot directly iff
`name.len() <= 8`. Otherwise the 8-byte slot is `00 00 00 00 | u32
offset-into-strtab`, and the name is written to the string table
(null-terminated). The string table itself starts with a 4-byte LE
size field (including the size field itself) and contains concatenated
null-terminated strings.

Deduplication: dedup names by content (a `HashMap<String, u32>`
populated during symbol-table construction). Borland-mangled names
average ~12 bytes (e.g. `@Bar@m$qi` = 9 bytes, `@Bar@$bctr$qv` =
13 bytes), so most user functions hit the strtab path. Internal
mdbcc names (`.Lstr.*` etc.) are short enough to fit ~half the time;
dedup is still worth it.

### §2.6 — `.drectve` content

mdbcc emits an empty `.drectve` by default. When the source contains
explicit `__declspec(dllexport)` (Phase S3+ feature; reserved here),
we emit `-export:<mangled>`. When the source contains `extern "C"`
function definitions, no directive is needed — the mangling logic
(§3) already produces the underscore-prefixed C name.

The Borland-default-library directive (`-defaultlib:cw32.lib` etc.)
is NOT mdbcc's job — mdlink decides what libraries are pulled in
based on its own command line + the entry-point selection. Putting
it in `.drectve` would couple every emitted .obj to a specific link
recipe and break the multi-link-target promise S2/S7 needs.

### §2.7 — COMDAT / linkonce encoding

For each function or data symbol that should fold across TUs (template
instantiations, inline member functions, vtables, typeinfo,
synthesised copy ctors), mdbcc emits:

1. A dedicated section `.text$<sym>` (or `.rdata$xt$<class>`, etc.) —
   one COMDAT section per fold group.
2. The section header gets `IMAGE_SCN_LNK_COMDAT` set.
3. Two symbols at offset 0 of the COMDAT section: a STATIC
   section-definition symbol (the COMDAT leader) carrying the
   selection code in its aux record, followed by an EXTERNAL symbol
   with the actual mangled name (visible to the linker for dedup).
4. Per the COFF spec the leader symbol's selection code is
   `IMAGE_COMDAT_SELECT_ANY` (2) — "pick any one definition; discard
   the rest". This is the right choice for template instantiations
   and inline functions where C++ ODR guarantees all definitions are
   equivalent.

Associative COMDATs (`.xdata$<sym>` / `.pdata$<sym>` for the EH
plumbing of a COMDAT function) use `IMAGE_COMDAT_SELECT_ASSOCIATIVE`
(5) and point to the `.text$<sym>` section index in the aux's
`Number` field. When the linker drops the `.text$<sym>` copy, the
associated `.xdata`/`.pdata` is dropped in lockstep — no orphan
unwind data.

mdbcc 4.5-era source (BCC 4.52 we target) predates `inline`-in-the-
language-as-such with linkage-fold semantics. The practical use:
class-body member functions (`class Foo { int x() { return 1; } };`)
get folded — that's idiomatic Borland code. Templates (S4) will be
the major user.

## §3 — Borland name mangling

This section derives Borland's C++ mangling from observed `.obj`
output. All samples produced this session by:

```
wrk_oracle/bc452/BC45/BIN/BCC32.EXE -c -Iwrk_oracle/bc452/BC45/INCLUDE <src>
```

OMF symbol extraction: a 100-line Python parser walks the OMF record
stream, decoding LNAMES (0x94), SEGDEF (0x96/0x97), PUBDEF/LPUBDEF
(0x90/0x91/0xB6/0xB7), EXTDEF (0x8C/0xB4), COMDEF (0xB0/0xB8), and
COMDAT (0xC2/0xC3) records. Symbol names are length-prefixed ASCII
strings inside the record body.

### §3.1 — Symbol shape

Borland's mangler emits names with this anatomy:

```
@ <qualified-name> $ <quals?> q <type-encoding>
```

- Leading `@` for any C++ symbol (free function with overloads, all
  members, all special operators). Plain extern-C functions get a
  leading `_` (Microsoft-conventional underscore-prefix-on-cdecl),
  e.g. `_main`, `_extc_fn`.
- `<qualified-name>` is the class chain joined by `@`:
    - free function `foo` → `foo`
    - member `Bar::m` → `Bar@m`
    - nested `Outer::Inner::get` → `Outer@Inner@get`
- `$` is the separator between the qualified name and the per-symbol
  qualifiers / argument-list marker.
- `<quals?>` are zero or more per-symbol qualifier characters:
    - `b...` — built-in special name follows (see §3.3)
    - `x` — `const` member function (trailing-`const`)
- `q` introduces the parameter type list. Every overloaded /
  qualified symbol has it. Followed by N type codes (one per
  parameter, no separators).

Examples (observed):

| Source                                  | Mangled                          |
|-----------------------------------------|-----------------------------------|
| `int foo(int, char*, double)` overload  | `@foo$qipcd`                      |
| `int Bar::m(int)`                       | `@Bar@m$qi`                       |
| `Bar::Bar()` (default ctor)             | `@Bar@$bctr$qv`                   |
| `Bar::Bar(int)`                         | `@Bar@$bctr$qi`                   |
| `Bar::Bar(const Bar&)` (copy ctor)      | `@Bar@$bctr$qrx3Bar`              |
| `Bar::~Bar()`                           | `@Bar@$bdtr$qv`                   |
| `Bar Bar::operator+(const Bar&) const`  | `@Bar@$badd$xqrx3Bar`             |
| `int Bar::read() const`                 | `@Bar@read$xqv`                   |
| `int& Bar::at(int)`                     | `@Bar@at$qi`                      |
| `int Bar::at(int) const`                | `@Bar@at$xqi`                     |
| `static int Bar::s_count()`             | `@Bar@s_count$qv`                 |
| `Bar* Bar::clone(const Bar&)`           | `@Bar@clone$qrx3Bar`              |
| `int Base::f()` (virtual)               | `@Base@f$qv`                      |
| `int Base::g(double, int)` (virtual)    | `@Base@g$qdi`                     |
| `int Outer::Inner::get() const`         | `@Outer@Inner@get$xqv`            |
| `void take_const_ptr(const int*)`       | `@take_const_ptr$qpxi`            |
| `void take_ptr_const(int* const)`       | `@take_ptr_const$qxpi`            |
| `void take_ref_const(const int&)`       | `@take_ref_const$qrxi`            |
| `void take_unsigned(unsigned long, short)` | `@take_unsigned$quls`          |
| `template<class T> T tfn(T)` w/ T=int   | `@tfn$qi`                         |
| `extern "C" int extc_fn(int)`           | `_extc_fn`                        |
| `int main()`                            | `_main`                           |

### §3.2 — Type codes (observed)

Single character per simple type:

| Code | Type                                |
|------|-------------------------------------|
| `v`  | `void`                              |
| `c`  | `char` (signed)                     |
| `s`  | `short`                             |
| `i`  | `int` / `long` (both 32-bit in BCC) |
| `l`  | `long` (also 32-bit; sometimes ambiguous w/ `i`) |
| `u`  | `unsigned` qualifier prefix (precedes int code) |
| `f`  | `float`                             |
| `d`  | `double`                            |

The `take_unsigned(unsigned long, short)` sample mangles as `quls`
which decomposes as `q`-list `u` (unsigned prefix) + `l` (long) +
`s` (short). So `u` is a qualifier prefix, not a standalone type.

Compound type modifiers (prefix-coded, recursive):

| Code | Meaning                              |
|------|--------------------------------------|
| `p`  | pointer-to                           |
| `r`  | reference-to                         |
| `x`  | `const` qualifier                    |
| `<N><name>` | user-defined type — `<N>` is the digit-string length of `<name>` (the unmangled class tag) |

Examples decompose:

- `qipcd` → `i`(int), `pc`(ptr-to-char), `d`(double)
- `qrx3Bar` → `r`(ref-to) `x`(const) `3Bar`(class `Bar`, length 3)
- `qpxi` → `p`(ptr-to) `x`(const) `i`(int) — i.e. `const int*`
- `qxpi` → `x`(const) `p`(ptr-to) `i`(int) — i.e. `int* const`
- `qrxi` → `r`(ref-to) `x`(const) `i`(int) — i.e. `const int&`

The qualifier order matters: `p` then `x` is "pointer to const", `x`
then `p` is "const pointer to". This matches C++ declarator semantics
read right-to-left.

### §3.3 — Special-name suffix codes (`$b...$`)

When the source name is an operator or a special function, Borland
substitutes a `$b<code>$` form for the bare name:

| Code     | Special name                |
|----------|-----------------------------|
| `$bctr$` | constructor (`Tag::Tag`)    |
| `$bdtr$` | destructor (`Tag::~Tag`)    |
| `$badd$` | `operator+`                 |
| `$bdele$`| `operator delete`           |
| `$bnew$` | `operator new`              |

These follow `@<class>@` for member operators and stand alone for free-
function operators. Observed pattern is `@Bar@$badd$xqrx3Bar` —
class `Bar`, op `+`, const method, takes `const Bar&`.

Additional `$b...$` codes (not observed this session, conjectured
from pattern + need): `$bsub$` (-), `$bmul$` (*), `$bdiv$` (/),
`$bmod$` (%), `$basg$` (=), `$beql$` (==), `$bneq$` (!=), `$blt$` (<),
`$bgt$` (>), `$ble$` (<=), `$bge$` (>=), `$band$` (&&), `$bor$` (||),
`$bnot$` (!), `$bcmp$` (~), `$blsh$` (<<), `$brsh$` (>>),
`$bsubs$` ([]), `$bcall$` (()), `$basgn$` (assignment operators like
`+=`/`-=` may have their own arm; not derived this session).

The trailing-`const` marker `x` for const member functions sits
**between the `$` and the `q`** when present: `$xqv` not `$qxv`.
This is empirically clear: `@Bar@read$xqv` is `int Bar::read()
const`, `@Bar@read$qv` would be the non-const variant.

### §3.4 — Vtable, typeinfo, COMDEF symbols

Observed in samples:

- `@$xt$3Bar` — typeinfo for class `Bar` (length 3, name `Bar`).
- `@$xt$p3Bar` — typeinfo for `Bar*`.
- `@$xt$1B`, `@$xt$1D` — typeinfo for `B` / `D` (length 1).
- `@Bar@3` — vtable for class `Bar` (the trailing `3` is the
  documented "vtable" sentinel; unrelated to type-encoding lengths).
- `@$bdele$qpv` — `operator delete(void*)`, emitted as an EXTDEF
  reference (the compiler doesn't define it; the RTL does).
- `__DestructorCountPtr`, `@__InitExceptBlock`, `__ftol`,
  `__turboFloat` — RTL helpers used by ctors/dtors and FP conversions.
  EXTERNAL references; mdlink will need stubs / a libc substrate.

COMDEF (`0xB0`) records carry communal (BSS-style) symbols — Borland
uses them for typeinfo + auto-generated destructors so duplicate TUs
that share the same class definition resolve to a single instance at
link time. Our COFF equivalent is COMDAT sections (§2.7).

### §3.5 — Derivation completeness

What's pinned by this session (high confidence):

- Type codes for `void`, `char`, `short`, `int`, `float`, `double`.
- `unsigned`/`pointer`/`reference`/`const` qualifier codes.
- User-type encoding (`<N><name>`).
- Member-function chain (`@Class@method`).
- Nested class chain (`@Outer@Inner@method`).
- Constructor/destructor special-names (`$bctr$`/`$bdtr$`).
- `operator+`, `operator new`, `operator delete` special-names.
- Trailing-`const` marker for member functions.
- `extern "C"` and plain-C functions: leading `_` prefix, no other
  mangling.
- Vtable and typeinfo naming (`@class@3` / `@$xt$<N><class>`).

What's NOT pinned (defer to S1b.4 implementation; iterate against
the bcc32 oracle as we encounter):

- The remaining `$b...$` operator codes (a dozen or so). Derive in
  S1b.4 by emitting one sample per operator and dumping. Bounded.
- Long/long long encoding (`__int64`). Likely `j` or `J` per Itanium
  parallel but unconfirmed; BCC 4.52 may not even support `long long`
  consistently (C89-era).
- Multiple-inheritance / virtual-base mangling. Defer to S4 because
  MI itself isn't implemented yet.
- Template parameter encoding. Templates produce instantiation-
  specific names; from `@tfn$qi` we see the instantiation looks like a
  plain function (the template parameter `T=int` is materialised into
  the parameter type code). Template-of-template or non-type
  template parameters: defer to S4.
- Function-pointer parameter encoding. Not observed.
- Reference-to-function encoding. Not observed.
- Array-as-parameter encoding (decays to pointer; same as `p`).

**Estimated completeness for what S1 needs**: ~75%. The remaining 25%
is operator zoo + edge cases. S1b.4 implementation phase will add the
oracle-driven derivation harness: for each unknown corner, write the
smallest .cpp source, run bcc32, inspect the OBJ, update the
mangling table. This is mechanical and bounded.

### §3.6 — Comparison to today's mdbcc mangling

Today mdbcc emits Itanium-flavoured codes (`f$ic` not `f$qic`); see
`codegen/cpp.rs::overload_symbol` (line 91). The mdbcc convention:

```rust
// codegen/cpp.rs:96
let mut s = format!("{base}$");
for (n, t) in params {
    if n == "this" { continue; }
    s.push_str(&type_code(t));
}
if const_method { s.push('K'); }
```

Key divergences from Borland:

- mdbcc uses `i` directly for `int`; Borland prefixes the q (`qi`).
- mdbcc separates with `$`; Borland uses `$q` after the optional
  per-symbol qualifier(s).
- mdbcc uses `K` for const; Borland uses `x` between `$` and `q`.
- mdbcc does NOT prefix class members with `@class@`; Borland does
  the `@class@member` chain.
- mdbcc does NOT emit `$bctr$`/`$bdtr$` for ctor/dtor — the source
  name `Tag::Tag` is mangled as-is.
- mdbcc does NOT emit a leading `@` or `_`.

**Implication**: switching mdbcc to Borland mangling is a
behaviourally-equivalent rename of every emitted symbol. Every
relocation site already references symbols by their mangled string,
so changing the mangling function changes both ends in lockstep.
But — it WILL invalidate the 88 e2e SipHash baselines in
`o1_byte_identity.rs` because emitted `.text`/`.rdata` bytes contain
no symbol names (just RIP-rel disp32 and absolute addresses), so
the SipHash byte image is unchanged — UNLESS the mangled name
shows up in an extern reference, which today's pre-link `Module`
shape doesn't expose. Actually: the SipHash is on the PE-final
bytes which do include the .idata strings (which are import names,
NOT user names); user names never reach the final PE in single-TU
builds. So the 88 baselines should survive a mangling rename.

(A careful audit during S1b.4 will confirm. If any baseline does
shift, we re-bless once; mangling change has to be a single
self-contained tick.)

## §4 — Test plan

### §4.1 — O13 oracle: COFF structural parity

`tests/oracle_o13_coff_parity.rs` (new). For each fixture:

1. Compile the source with mdbcc (in-process): produces an Object IR.
2. Serialise to COFF: produces `<tmp>/<name>.mdbcc.obj`.
3. Compile the same source with bcc32 (via `bcc_oracle`): produces
   `<tmp>/<name>.bcc.obj` (OMF).
4. Decode each — mdbcc's OBJ via the new COFF reader (mdlink's input
   path), bcc32's OMF via a minimal OMF reader (a 200-line walker
   like the dump_omf.py we used to derive the mangling).
5. Compare the **semantic content** (after format bridge): the set of
   external symbols, the set of section names + sizes, the set of
   relocations (by symbol name + offset + kind, not by raw bytes).
6. Pass iff:
   - Every PUBDEF in bcc32's OBJ has a matching EXTERNAL symbol in
     mdbcc's OBJ with the same mangled name.
   - Every EXTDEF in bcc32's OBJ that names a user function has a
     matching `SectionNumber=0` symbol in mdbcc's OBJ.
   - Section sizes within 1.5x of each other (allows for different
     codegen quality without flagging real divergence).

Skip loudly if the bcc32 oracle is absent (consistent with O2/O3).

**Fixture suite** (12 sources, progressively complex):

1. `o13_01_int_only.c` — `int main() { return 42; }` (no C++).
2. `o13_02_two_funcs.c` — `add(a,b)` + `main` (intra-TU call reloc).
3. `o13_03_global_int.c` — `int g = 5; int main() { return g; }`.
4. `o13_04_string_lit.c` — `puts("hi"); return 0;` (.rdata reloc).
5. `o13_05_extern_fn.c` — `extern int helper(int); main calls
   helper.` (UNDEFINED extern reloc).
6. `o13_06_cpp_overload.cpp` — two `add` overloads, one called.
7. `o13_07_cpp_class.cpp` — `Bar` with ctor/dtor/method.

### §4.2 — O14 oracle: link-equivalence (round-trip)

Per Decision-1A (S0 close-out journal): two halves.

- **Half A** (S1c-blocked): bcc32's OMF .obj reads through mdlink's
  ingest path → mdlink links to PE → runs → exit code matches the
  bcc32-original build. **Not in scope here**; the OMF reader is
  S1c work.
- **Half B** (S1b.4 close): mdbcc's COFF .obj links through
  `link.exe` or `lld-link` (the COFF format witness) → PE runs →
  exit code matches mdbcc's in-process single-TU build. This is
  the format-conformance gate.

Half B test: `tests/oracle_o14_msvc_link.rs`. Self-skips if neither
`link.exe` nor `lld-link.exe` is on PATH. Per fixture (same 12 as
O13): compile with mdbcc -c → invoke `lld-link /subsystem:console
<name>.obj kernel32.lib /out:<name>.exe /entry:main` → run → assert
exit code matches.

### §4.3 — `tests/coff_object_format.rs` — unit tests

Format-internal tests, no oracle dependency. Recommended approach:
**hand-rolled decoder, not an external crate.** Reasons:

- The decoder is ~150 LoC (file header + section header iter +
  reloc iter + symbol iter + strtab access). Comparable to the OMF
  walker. Hand-rolling matches the std-only, no-extra-deps house
  style (`bcc_oracle.rs` already exemplifies this with its inline
  SHA-256).
- The decoder doubles as mdlink's input path — having it as crate
  code avoids the dependency on the external `object` crate which
  would pull in `goblin` / `wasmparser` etc.

Tests:
- `roundtrip_empty_object`: empty Object writes + reads back
  unchanged.
- `roundtrip_single_function`: one function, no relocs.
- `roundtrip_function_with_call`: REL32 reloc resolves.
- `roundtrip_data_with_pointer`: ADDR64 reloc resolves.
- `roundtrip_comdat_function`: section flags + aux record encode
  correctly.
- `roundtrip_long_symbol_name`: strtab fallback.
- `symbol_dedup`: emitting two relocations against the same name
  reuses the same symbol index.
- `section_alignment`: each section's characteristics encode the
  right `IMAGE_SCN_ALIGN_*` bits.
- `validate_with_lld_link`: byte-write an Object → spawn lld-link
  (if available) → assert exit 0. Self-skips if lld-link absent.

### §4.4 — O1 byte-identity stripe extension

Add `o1_obj_byte_identity.rs`: for the 88 e2e fixtures, compile
twice with `mdbcc -c` and assert the produced `.obj` bytes are
identical (SipHash sweep, mirrors `o1_byte_identity.rs`).
Determinism is a hard requirement for content-addressable caching
in S1d/S5 OWL build progress tracking.

This is **stricter than the PE byte-identity stripe** because
TimeDateStamp + other compiler-version fields in the PE were
already zero-suppressed; the OBJ writer must do the same from day
one (`TimeDateStamp = 0`, symbol table ordering deterministic,
strtab dedup keyed by content, etc.).

### §4.5 — Mangling regression suite

`tests/borland_mangling.rs`: each row of §3.1's table becomes a
unit test that constructs a Function AST node and asserts mdbcc's
`borland_overload_symbol` produces the observed string. Goes red
during the mangling-rewrite tick; goes green when the rewrite
matches bcc32 exactly.

## §6 — Open questions for Arthur

**Q1 — PE writer location.** §1.3 recommends moving the PE writer
into mdlink (path b). Cheaper short-term: keep it in mdbcc and have
mdlink call it (path a). Decision needed before S1b.4 starts.

**Q2 — In-process single-TU fast path.** The May-26 plan §4.S1 says
the exit is "mdbcc -c foo.cpp produces COFF, mdlink links". Does the
in-process `compile_to_pe` path stay (driver auto-uses it for
single-TU compiles) or is it removed once mdlink exists? **Plan
language is ambiguous on this.** The pragmatic answer: keep
`compile_to_pe` for the 88 e2e tests so they keep working without a
mdlink dependency; mark `bcc <file.c>` without `-c` as "shell out to
mdlink, no in-process". One Rust API, two CLI behaviours.

**Q3 — Mangling derivation completeness.** §3.5 estimates 75% pinned,
25% to derive in S1b.7. The remaining 25% (operator zoo + edge cases)
is a bounded but possibly multi-tick effort. Acceptable to ship S1b
with §3 incomplete and close the gaps as encountered? Or block S1b
exit on §3 closure? **Recommendation**: ship incomplete; the O13
oracle is the contract that closes gaps incrementally.

**Q4 — `__imp_<symbol>` convention.** §2.3 proposes encoding imports
as undefined externals named `__imp_<symbol>` to match MS COFF
convention (mdlink synthesises the IAT slot from any `__imp_*`
reference). Borland's OMF uses an EXTDEF directly named `_FuncName`
with a fixup-type that tells TLINK32 it's an import. Our COFF
convention diverges from Borland's OMF here (deliberately). Is the
MSVC `__imp_` convention acceptable, or should mdlink instead read
ordinary externs and consult its own DLL table? **Recommendation**:
MSVC convention — works with lld-link / link.exe out of the box,
and our mdlink can read either. Confirm acceptable.

**Q5 — Empty `.drectve` policy.** §2.6 says we emit no default-lib
directive. For Borland-source builds, the link recipe is in
`make`/`bcc32.cfg`, not in `.obj` directives. Are we OK with
"defaultlib selection is the linker driver's job, never the .obj's"?
This makes mdbcc-produced objects portable across linkers (lld-link
vs mdlink vs link.exe). **Recommendation**: yes.

## §7 — Risk register update

Per May-26 plan §7 (R1-R12). New risks surfaced this design pass:

- **R13 — Borland mangling derivation is incomplete.** §3 covers
  ~75% of cases. Closure depends on O13 oracle iteration in S1b.7.
  **Mitigation**: oracle-driven — every unknown surfaces as a RED
  fixture; bounded by the number of distinct C++ source features we
  exercise. Worst case: a corpus source uses an operator we haven't
  derived, we add the rule, move on. Will not block S1 close-out
  because the gap is observable (RED test) rather than silent
  (miscompile).
- **R14 — COMDAT semantics drift from Borland's OMF COMDEF.** §3.4
  notes Borland uses COMDEF (commual symbols) where MSVC-COFF uses
  COMDAT sections. The two are not bit-equivalent; the test for
  semantic equivalence is "two TUs that define the same template
  instantiation link to one copy, not two". **Mitigation**: O13
  Half A (bcc32 OMF → mdlink) doesn't exist yet (S1c work). For
  Half B (mdbcc COFF → lld-link) the COMDAT semantics are
  spec-defined and well-tested in lld-link itself. The risk only
  bites when mdlink itself processes COMDAT from mdbcc and COMDEF
  from bcc32 in the same link — that's S1c+S5 territory.
- **R15 — `pe.rs`-move (Q1, path b) is a 2074-LoC reshape.** Even
  with the test corpus pinning behaviour, moving pe.rs from
  `src/pe.rs` to `src/bin/mdlink.rs` (or `src/link/mod.rs`) is a
  big mechanical churn. **Mitigation**: do the move as one
  pure-shuffle commit (S1c.1, deferred); only re-shape semantics
  in subsequent commits. Mirror the S1a discipline.
- **R16 — Determinism stripe expansion may surface latent
  non-determinism in the OBJ writer.** Symbol-table ordering is
  the prime suspect (HashMap iteration). **Mitigation**: design
  the writer to use Vec / IndexMap from the start. Audit every
  HashMap that touches emitted bytes during S1b.2 implementation.

Existing risks unchanged: R8 (TLINK32 quirks) is S1c, R9 (codegen
restructure) is closed by S1a, R10 (multi-TU symbol resolution)
crystallises during S1b.4 + S1c.
