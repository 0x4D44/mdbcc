## Goal prompt

Move mdbcc from "RailC works" to "mdbcc is a general, reproducible Borland/OWL
rebuild toolchain that can scale to more programs without losing correctness."

The headline is not raw speed yet. The next valuable outcome is proof that the
toolchain works beyond the one application that drove the closure. Performance
work should follow measured multi-app builds, not guesses.

## Current context

- RailC has crossed the sampled Win64 GUI parity line.
- The `build_bc45_libs --target win64` product path exists and produces Win64
  dependency libraries in `target/bc45-libs/win64/`.
- `BUGS.md` no longer has active open rows, but several important limitations

- There is active uncommitted work in the repo around Win64 RailC UI/calling:
  - `src/codegen.rs`: Win64 stack outgoing-shadow reservation around by-value

  - `wrk_owl_win64/DIALOG.CPP`: `WS_CLIPSIBLINGS` dialog paint-order fix.

## North-star acceptance

This goal is done when:

1. The current RailC Win64 product build issues are landed, tested, documented,
   and no longer sitting as dirty worktree state.
2. At least two additional small BC4.52 OWL example applications build and run
   through normal `mdbcc.toml` product mode on Win64.
3. The acceptance commands are reproducible from a clean checkout, or skip
   loudly with explicit prerequisites when proprietary/local fixtures are absent.
4. Build-time performance has a repeatable baseline over RailC plus the new
   sample apps, with per-phase timings recorded.
5. At least one measured performance bottleneck is improved without weakening
   byte-identity, runtime, or differential oracle coverage.
6. The first structural extraction from `src/codegen.rs` has landed
   byte-identically, reducing future collision risk.

- Uses ordinary OWL/BIDS/streams surfaces, not custom build machinery.

- Fix only the smallest root cause needed for the sampled app.

Acceptance:

- Each app launches and reaches a simple visible/interactive state.
- Failures are either fixed or logged honestly with a minimal repro.

### G4 - Optimize The Measured Bottleneck

G3 disproved the first header-cache hunch for the measured RailC/product
workload: codegen dominated. The first landed G4 slice therefore targets a
pre-emission codegen pass, not preprocessing.

Implemented first performance candidate:

- Precompute each function definition's final linker symbol once.
- Index inline definitions by that final symbol.
- Resolve extern-prototype/inline collision checks through the index instead of
  rescanning all TU items and re-mangling each candidate per prototype.
- Reuse the precomputed final symbol in the function-emission loop.

Remaining candidates only if future data points there:

- Header tokenize-once cache for guarded includes.
- Linker/archive symbol lookup hot spots.
- Object writer allocation/copy hot spots.
- Parser repeated lookup hot spots in large C++/OWL headers.

Acceptance:

- One targeted performance change lands with before/after timings.
- Correctness gates remain at least as strong as before.
- Any determinism or byte-output movement is explained and intentionally
  re-blessed, never hand-waved.

### G5 - Reduce Codegen Collision Risk

Start shrinking `src/codegen.rs` by extracting stable, already-tested regions.
Do this only after active correctness work is landed, because mechanical moves
inside dirty collision zones are expensive.

First extraction landed:

- Static-local symbol naming, guard-key naming, and static-local declaration
  collection now live in `src/codegen/statics.rs`.
- This is deliberately smaller than the ABI/EH candidates below: it proves the
  extraction workflow with low collision risk and existing static-local tests.

Good first extraction candidates:

- Reachability pruning helpers.
- Win64/i386 call ABI lowering and argument marshalling.
- EH lowering helpers.
- Struct-by-value and record-return helpers.
- printf/formatting intrinsics.

Rules:

- Extract one coherent region at a time.
- Preserve bytes unless the extraction deliberately fixes a bug.
- Run byte-identity and focused behavioral tests immediately.
- Do not refactor names or behavior casually while moving code.

Acceptance:

- One extraction lands with no behavior change.
- Future fixes have a smaller file/module surface to touch.

## Working rules

- Correctness remains the gate. A faster wrong compiler is worse than a slow one.
- Use real product paths early. Synthetic probes are for root cause, not final
  confidence.
- Keep each slice boring: one repro, one root cause, one fix, one validation
  story, one commit.
- Do not weaken or skip tests to get green.
- Do not chase parked architectural gaps unless a real sample app or oracle
  pulls them into scope.
- Treat non-RailC failures as signal, not distractions.
