# GOAL — Native Win64 RailC at full GUI parity

Date: 2026-06-14
Supersedes the "Later Goal: 64-Bit RailC" section of `2026.06.12 - GOAL - railc mdbcc source build goal.md`,
which is now substantially met (compile, link, and a rendering window are done — see Current Evidence).

## Goal

Drive the **source-built, mdbcc-compiled, native Win64 RailC** application — which today opens a real top-level
window — all the way to **full GUI parity with the proven 32-bit self-host**, and make that validated native-64 build
a **repeatable, first-class deliverable** of the toolchain.

"Full GUI parity" is concrete and means the Win64 RailC behaves like the 32-bit golden across the *same* sampled
surface the 32-bit self-host was validated on:
- the main frame window + menus, fully interactive;
- the ABOUT / CONFIG / FINISH dialogs open and function;
- the KINGSX child windows render and animate (the 720 / 3600-tick parity tiers);
- byte-identical resources (`railc.res`);
- differential GUI parity vs the 32-bit golden at the sampled tiers (capture-and-compare).

This is the completion of **Stone S7 (native 64-bit)**. It is deliberately *narrow*: finish the RailC we have on
Win64; do NOT broaden into the S8 toolchain long-tail (that is "Not Goals Yet").

paint* — message dispatch through OWL's response tables, dialogs, the child-window tree, and validating it all matches
the 32-bit golden.

## Strategy

Same frontier-by-frontier discipline that drove the i386 closure and the runtime wall: **each milestone is a testable
acceptance gate**, ordered so each lands as a complete, runnable unit, and the *observed runtime behaviour* (not just
"it links") is the metric. Reuse the machinery we already have rather than building new oracles:
- the **gui-parity capture harness** (`wrk_probe/gui_parity/capture_main_window_parity.ps1` + the Rust
  `find_window_by_pid`/`enum_pick_by_pid` smoke now in `tests/railc_source_slice.rs`) — extend it from "a window
  appeared" to "this window/dialog/child matches the 32-bit golden capture";
- the **byte-identical `railc.res` oracle** (`tests/rc_railc.rs`, salvaged 2026-06-13) — resources are already proven;
- the **differential vs the 32-bit golden** (the 32-bit self-host is the reference image; capture both, compare);
- **`mdscreensnap`** for visual verification at each tier.

Where a frontier needs a Win64-only ABI change, **reuse the Win64 overlay machinery already designed** in
`2026.06.13 - HLD - railc win64 owl window bootstrap.md` (the harness-selected `-m64` overlay for pointer-sized
`WPARAM`/`LPARAM`/`LRESULT` + the build-local patched OWL sources) — wall 1 didn't need the message-width half of it,
but wall 2 does, and the design is sitting ready.

## Milestones

### M1 — Wall 2: OWL response-dispatch pointer width (the int32 dispatch layer)
**Objective.** Make OWL's message dispatch pointer-safe on Win64 so messages whose `lParam` carries a pointer
(`WM_CREATE`/`WM_NCCREATE` `CREATESTRUCTA*`, `WM_GETMINMAXINFO` `MINMAXINFO*`, `WM_NOTIFY`, command routing, etc.) are
dispatched without truncation, and the main frame window is fully interactive (menus fire, the response tables route).
The known sites (from the wall-1 HLD's "second-stage risk"): `SIGNATUR.H:458` `LRESULT_WPARAM_LPARAM_Sig == I32_U_I32_Sig`,
`DISPATCH.H`/`DISPATCH.CPP` `int32` LPARAM dispatchers, `COMPAT.H` Win16 `uint16/uint32` params, and `TWindow::ReceiveMessage`/
`HandleMessage` widths.

**Acceptance.** A bounded interaction smoke drives the main window (post a menu command / a pointer-bearing message)
and asserts no truncation-class crash (`0xC0000005`) and the expected response; the existing O0–O3 gates stay green;
`railc.res` stays byte-identical. The runtime smoke advances from "window appears" to "window survives a dispatched
pointer-bearing message."

**Expected work / key constraint.** This is the **slice-wide message-width view** the wall-1 HLD deliberately deferred:
widening `WPARAM`/`LPARAM`/`LRESULT` in only a couple of TUs breaks the link (the non-virtual cross-TU-inlined
`ReceiveMessage`/`HandleMessage` mangling — proven in the wall-1 analysis). So M1 must apply the Win64 overlay
*coherently across the whole `-m64` slice* (the overlay header path the wall-1 HLD designed), or otherwise keep one
consistent ABI. Watch for further latent Win64 ABI bugs of the **same class as the array-cookie bug** (32-bit
assumptions in pointer/handle width) surfacing in the dispatch/streamable machinery.

### M2 — Dialogs (ABOUT / CONFIG / FINISH) via the `DWL_USER` path
**Objective.** The three RailC dialogs open and function on Win64. These use OWL's **separate** dialog-proc / `DWL_USER`
mechanism (not the `GWLP_USERDATA` window path wall 1 fixed) — `DIALOG.CPP` + the common-dialog TUs. The 32-bit
`SetWindowLong(DWL_USER, this)` truncates the `TDialog*` on Win64, exactly analogous to the wall-1 `GWLP_USERDATA` bug.

**Acceptance.** Each dialog opens from the main window, its controls are live, and OK/Cancel behave; capture-and-compare
vs the 32-bit golden dialog images (the GUI-parity harness already validated these on i386). No `0xC0000374`/`0xC0000005`.

**Expected work.** Port the `DWL_USER` path to `DWLP_USER` + `SetWindowLongPtrA` (build-local patched `DIALOG.CPP`, the
same overlay pattern as `wrk_owl_win64/`), and the common-dialog TUs as needed.

### M3 — KINGSX child windows + the full window tree
**Objective.** The KINGSX child windows (and any other RailC child/owned windows) render and animate natively, the full
window tree is constructed, and the app runs to the 720 / 3600-tick parity tiers without crashing.

**Acceptance.** The window tree matches the 32-bit golden (window classes/children present by enumeration), and the
animation runs to 720 and 3600 ticks; capture-and-compare at those tiers.

### M4 — GUI parity validation vs the 32-bit golden
**Objective.** Promote the smoke into a real **differential GUI-parity oracle**: drive the Win64 exe through the same
sampled surface the 32-bit self-host was validated on (main + ABOUT/CONFIG/FINISH + KINGSX @ 720/3600), capture, and
compare against the 32-bit golden captures.

**Acceptance.** The Win64 captures match the 32-bit golden at the sampled tiers (within the same tolerance the i386
parity used); `railc.res` byte-identical; the full O0–O4 + parity suite green and repeatable.

### M5 — Native-Win64 as a first-class, repeatable deliverable
**Objective.** The whole native-64 pipeline (compile → archive → resources → link → run → parity) is a single repeatable
acceptance test, ergonomic to run (a `cargo test` / a documented command), and the native-Win64 RailC build is a
first-class output of the toolchain alongside the 32-bit one. Fold into the concurrent "BC4.52 dependency libs as an
mdbcc deliverable" track where it composes.

**Acceptance.** One documented command builds-and-validates native Win64 RailC end-to-end to GUI parity; the result is
deterministic; the native-64 build is documented as a supported toolchain target.

## Not Goals Yet (explicitly deferred — these are the *other* ambitious directions, not this one)
- The S8 toolchain long-tail: CodeView/PDB debug info (would have saved this session's windbg detour — tempting, but
  not required for parity), DLL output, `__property`/`__closure`, BCC 5.x, a perf baseline.
- A *second*, larger native-Win64 OWL app (the generality proof point).
- Exhaustive (vs sampled) GUI parity; common-dialog Set-data-file select-success automation (a standing oracle limitation).
- Optimizing the Win64 codegen for speed/size.

## Key Risks
- **M1 is the hard one.** Slice-wide message-width widening must be ABI-coherent or the link breaks (the non-virtual
  cross-TU `ReceiveMessage`/`HandleMessage` mangling). The overlay design exists; applying it coherently is the work.
- **More cookie-class Win64 ABI bugs.** We just found one (array-new/`delete[]` cookie). The streamable/dispatch
  machinery is heavy template/container code; expect siblings (32-bit width assumptions). The new
  `tests/cpp_placement_new_array_cookie.rs` is one guard; add focused regressions as each surfaces.
- **The parity oracle is sampled, not exhaustive** (inherited from the i386 validation) — parity at the sampled tiers,
  not a proof of total equivalence. Acceptable, but stated.
- **Debuggability.** Without PDB/CodeView, future Win64 crashes need the `cdb` + `mdlink --map` workflow established this
  session (documented in the journals). If M-work bogs down in opaque crashes, S8's debug-info item may get pulled in.

## Decision Log
- **Chose parity over breadth.** Finish the native-64 RailC we have (S7) before broadening to the S8 toolchain
  long-tail or a second app — highest confidence, delivers a complete, validated milestone (a real native-64 OWL app).
- **Reuse existing oracles** (gui-parity capture, the byte-validated `railc.res`, the 32-bit golden as the differential
  reference) rather than building new validation machinery.
- **Reuse the wall-1 Win64 overlay design** for M1/M2's pointer-width changes — it was designed for exactly this and
  half-used already.
- **Frontier-by-frontier, runtime-behaviour as the metric** — the discipline that worked for the i386 closure and the
  runtime wall.
