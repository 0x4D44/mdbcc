# HLD — Test Oracles for mdbcc

Date: 2026-05-16
Status: Design (no code changed by this document)
Author: Claude (pair: Arthur)

## 1. Why this document

mdbcc's autonomous build loop is only as trustworthy as its oracles — the
machine-checkable encodings of "what correct looks like". Today the only
oracle is hand-authored expected values (exit code / stdout) on ~88 e2e
programs. That is genuinely strong (real Windows loader + CPU execute our
bytes) but its *breadth* is bounded by cases we thought to write, and there
is no independent reference. This HLD defines the full oracle set, the
priority order, and the explicit non-goals.

Quality stance (per CLAUDE.md): ruthlessly minimise scope, keep it simple,
no migration/rollback (dev sandbox), **no environment variables or feature
flags** — reference compilers are auto-discovered and tests self-skip when a
reference is absent.

## 2. Current environment (probed 2026-05-16)

| Tool | State |
|---|---|
| MSVC (`cl`) | Installed; `vswhere.exe` present at the standard path. `cl` not on PATH (needs `vcvars64`). |
| Borland/Embarcadero (`bcc32`/`bcc64`/`bcc32c`) | **Not installed.** No `C:\Borland`, no `C:\Program Files (x86)\Embarcadero`. |
| clang | Not on PATH. |

Implication: the MSVC differential is implementable now. Any BCC oracle is
**setup-gated** — it needs a BCC binary acquired first.

## 3. The BCC-oracle question (answered)

A BCC oracle is **not optional — it is the project-defining correctness
oracle**, for one structural reason: **MSVC cannot compile authentic Borland
source** (`<iostream.h>`, default-int, `near/far/huge`, Borland `asm`,
`__pascal`, BIDS, K&R). The entire purpose of mdbcc is the *Borland
dialect*; for dialect-specific code, MSVC is not a valid reference at all.
Only a real Borland compiler defines "what this Borland program does".

There are several free, runnable Borland compilers:

- **bcc32 5.5** — the classic free command-line compiler (Borland 2000).
  Original Borland front-end, targets **Win32 (32-bit PE)**. Best as a
  *front-end-acceptance* reference: "does the original Borland front-end
  accept this dialect?" If bcc32 5.5 rejects a sample it is not valid
  Borland; if it accepts and we reject, that is a front-end gap.
- **Embarcadero bcc64 (Clang-based)** — modern, free, **targets Win64**
  (same bitness as mdbcc → cleanest behavioral differential, no
  pointer-size divergence), and is Borland-dialect-aware. **Primary BCC
  behavioral reference.**
- bcc32c/bcc32x — clang-classic 32-bit; secondary, not needed initially.

Bitness nuance: bcc32 5.5 is Win32 (`sizeof(void*)`=4) vs our Win64 (=8),
so behavioral diffs are *legitimate* for any program that observes pointer
size — those must be filtered out of a bcc32-5.5 behavioral differential.
bcc64 has no such issue.

Caveat: even a real BCC cannot run the 16-bit DOS/Win16 samples
(OWL/TurboVision/BGI/`int86`) — those are structurally out of scope for
"run on modern Windows" regardless of oracle.

## 4. Oracle catalogue

| ID | Oracle | Proves | Reference | Gating | Status |
|----|--------|--------|-----------|--------|--------|
| O1 | Executable behavioural (existing) | End-to-end correctness vs hand-computed expected | hand values | yes | live (88 e2e) |
| O2 | Differential vs MSVC `cl` | Semantic correctness on portable C/C++ | `cl` | yes | design → build v1 |
| O3 | Differential vs real BCC | Correctness of the *Borland dialect* | bcc64 (behaviour), bcc32-5.5 (acceptance) | yes when present | design; setup-gated |
| O4 | BCC sample-corpus realism | Front-end swallows authentic period code | bcc64 / bcc32-5.5 | tiered | design; setup-gated |
| O5 | x64 decode-validity | Emitted bytes are legal x64; jumps/relocs in-bounds | iced-x86 | yes | design → build v1 |
| O6 | Perf & compile-time | Trend tracking only | cl/bcc | **no (non-gating)** | design; minimal |

### O2 — MSVC behavioural differential (primary correctness)
For each corpus program: build with mdbcc → `a.exe`; build with `cl /nologo
/EHsc` → `ref.exe`; run both with identical stdin; assert `(exit code,
stdout, stderr)` identical. Cheapest first move: **retrofit the existing 88
e2e programs through O2** — removes hand-expected fragility immediately and
surfaces real bugs/gaps where MSVC disagrees. Our LLP64 type model *mirrors
MSVC* (`long`=4, ptr=8) → far fewer spurious diffs than a gcc reference.

### O3 — BCC differential (primary *dialect* correctness)
Same harness, reference = bcc64 (behaviour) and bcc32-5.5 (front-end
acceptance: compile-success only, no run, Win32). Validates the
dialect-specific corpus that O2 structurally cannot.

### O4 — BCC sample corpus
Harvest the **console/computational subset** of shipped Borland samples.
Two tiers: (a) behavioural vs bcc64 where deterministic; (b) downgraded to
"parses + compiles + links" where interactive; (c) quarantine
OWL/TurboVision/BGI/DOS-int as structurally out of scope. Corpus is
copyrighted abandonware — acceptable in sandbox, kept out of git
(`wrk_corpus/`, git-ignored), never a build dependency.

### O5 — x64 decode-validity (cheap defence-in-depth)
Disassemble each emitted function's `.text`; assert every instruction
decodes as legal x64 and every intra-unit jump/reloc lands in-bounds.
Catches hand-assembled encoder typos on *untaken* paths (we now hand-emit a
lot: printf itoa, libc intrinsics) which O1/O2 miss. Use `iced-x86` as a
**dev-dependency** (correct, maintained) rather than hand-rolling a decoder.

### O6 — Perf & compile-time (NON-gating, deliberately)
mdbcc codegen is intentionally naïve (no regalloc, RBP-memory temps);
expect 10–50× slower than `cl /O2`. Gating on that yields a permanently-red,
noisy oracle, and "run *fast*" is an explicit non-goal — the goal is "*run*
on modern Windows". O6 records mdbcc/reference ratios and alerts only on
regression **vs. mdbcc's own history**, never vs. reference absolute.
Codegen optimisation is a separate future workstream, not smuggled in here.

## 5. Triangulation model

Portable corpus runs **mdbcc vs MSVC vs bcc64**:
- references agree, mdbcc differs ⇒ mdbcc bug (hard fail).
- references disagree ⇒ UB / implementation-defined ⇒ auto-exclude +
  annotate (this also validates the references themselves).
- mdbcc agrees with both ⇒ pass.

## 6. Required corpus filters (or the differential manufactures false fails)

1. **UB / nondeterminism gate**: uninitialised reads, pointer↔int casts,
   struct-padding reads, `rand`, time, PIDs, observed addresses. Curated
   corpus only; a one-line `// oracle: skip-reason` comment convention
   excludes a file with a recorded reason.
2. **Pointer-size filter** (bcc32-5.5 only): exclude programs that observe
   `sizeof(void*)` / pointer-int round-trips (Win32 ptr=4 vs our Win64=8).
3. Deterministic, self-contained, no-input programs in v1 (stdin support is
   a later, optional extension — YAGNI now).

## 7. Engineering design (simple, no env vars, no feature flags)

- **One harness, pluggable reference.** `tests/differential.rs` +
  `tests/support/` (plain Rust, no macros/DSL). A `Reference` is just a
  struct with `name`, `compile(src)->exe`, discovered by code.
- **Discovery, not configuration.**
  - `cl`: locate VS via the known `vswhere.exe` path → resolve
    `vcvars64.bat` → run it once, capture `set` output into a map cached in
    a `OnceLock`. We *read* the dev env vcvars produces; we define **no**
    env var ourselves.
  - `bcc64`/`bcc32`: probe conventional install dirs and a repo-local
    `wrk_tools/` (git-ignored) directory. No env var, no flag.
- **Self-skip when a reference is absent.** If a reference compiler is not
  found, its differential tests early-return after `eprintln!("SKIP: <ref>
  not found")` and pass vacuously. This keeps `cargo test` green on a box
  without that reference **without** a cargo feature or env toggle (honours
  the "no flags/env" constraint; correct for a dev sandbox).
- **Corpus = directories, no manifest.** `tests/corpus/portable/`,
  `tests/corpus/borland/`; harness globs them. Optional first-line
  `// oracle: ...` comment for skip/stdin metadata — minimal, no schema.
- **No migration/rollback, no back-compat.** Existing `end_to_end.rs`
  stays as O1; O2 is additive. If retrofitting e2e programs into the
  differential supersedes a hand-expected test, the hand-expected test is
  simply deleted (dev sandbox; no deprecation dance).
- **Artifacts** (built exes, captured output) go under `target/oracle/`
  (already git-ignored); never under `wrk_docs/`.

## 8. Explicit non-goals / pushbacks (recorded so they are not re-litigated)

- **No machine-code comparison vs MSVC/BCC.** `cl /O2` reorders/vectorises;
  byte/instruction diff is pure noise. "Codegen correctness" is fully
  captured behaviourally by O2/O3; structural sanity is O5's job.
- **Perf is never a pass/fail gate** (see O6).
- **MSVC is not a reference for raw Borland source** (cannot compile it);
  O3/O4 own that. O2 owns portable/controlled programs.
- **16-bit DOS/Win16 GUI samples are out of scope** for behaviour under any
  oracle (no DOS/Win16 on Win64). They may at most be front-end-acceptance
  cases against bcc32-5.5.

## 9. Staged delivery (minimal first — CLAUDE.md "minimise")

1. **v1 (build now):** harness skeleton with pluggable `Reference`;
   `cl` discovery via vswhere+vcvars; O2 retrofitted onto the existing e2e
   corpus; O5 decode-validity (high value vs our hand-asm). Self-skip if
   `cl` absent.
2. **v2:** O6 non-gating perf/compile-time numbers (print only).
3. **v3 (setup-gated):** acquire bcc64 (+ bcc32-5.5) into `wrk_tools/`;
   enable O3; triangulation on the portable corpus.
4. **v4 (setup-gated):** harvest BCC console sample corpus → O4 tiers.

## 10. Decisions (resolved 2026-05-16, Arthur)

1. **Acquire both** bcc64 (primary dialect behaviour reference) **and**
   bcc32-5.5 (front-end acceptance). Reality: bcc32-5.5 is archive-hosted
   and self-contained (likely obtainable); **bcc64 is account-gated and is a
   manual download Arthur performs** — its standalone-free availability is
   intermittent. Both are dropped into git-ignored `wrk_tools/`; O3/O4
   self-activate when present, self-skip otherwise. The harness is built
   reference-agnostic now so no code change is needed when binaries land.
2. **`iced-x86` accepted** as a `[dev-dependencies]` entry only (O5 is test
   code; never linked into the `mdbcc`/`bcc` mainline binary).
3. **Self-skip-when-absent confirmed.** Mitigation against a silently-rotting
   skipped oracle: every run prints a loud `SKIP: <ref> not found` line, and
   an always-on harness self-check compiles a known program with mdbcc twice
   and diffs it against itself — so the differential plumbing (build, run,
   capture, compare) is exercised on every `cargo test` even with zero
   external reference compilers installed.
