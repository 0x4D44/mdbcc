## 1. What "100% complete" means

The four-agent synthesis converged on two competing definitions:

- **(a) OWL-app conformance, three apps** (stage architect). 6-10
  months of subagent work past H. Concrete, measurable.
- **(b) Full Borland C++ 5.x dialect conformance** (literal reading
  of Arthur's "fully implement"). 3-5 years. No published bound on
  "the dialect" — every quirk is a tick.

This plan adopts a **hybrid**: stages J–N are option (a) (three
real OWL apps as the forcing oracle for everything Arthur's "OWL
Windows" North Star actually needs); stage O is the option-(b) tail
(features that *no* observed corpus exercises but which the dialect
spec calls out — `long double`, full RTTI, `wchar_t` end-to-end,
multiple inheritance, templates *if* an app needs them).

Honest framing: stages J–N have a measurable termination condition
(three apps build + launch + interact + clean-exit). Stage O is
**unbounded**, and we will only continue O while items remain that
either (i) a hypothetical near-future user has explicitly named or
(ii) the dialect spec lists and is easy enough to land cleanly. **If
the autonomous loop drifts into stage O speculation, kill it.**

## 4. Per-stage detail

### J — Phase-I prep (autonomous-feasible variant)

The original roadmap stalls here on "Arthur-only D-1." The devil's
advocate is right: **a one-day spike at tick 48 closes this**. We do
not need Arthur to acquire the perfect provenance-pinned OWL 2.5 app
to *start*; we need *any* real Borland C++ source to surface the gap
between mdbcc and reality. Autonomous-feasible procurement options:

1. **Synthetic OWL app (lowest risk)**: hand-write a ~500-line OWL
   2.5-style app that combines the major OWL idioms (TFrameWindow +
   TDialog + TMenu + response table + TPaintDC + at least one ctor
   that throws). The H10 review listed the patterns. This is 1-2
   ticks of subagent work; pure test/corpus addition; surfaces every
   cross-feature gap.
2. **Public Borland sample sources**: BCC55's `Examples/` or `Owl/`
   subdirectory if present; widely-archived OWL tutorials (e.g.,
   *Borland C++ Power Programming* book samples on archive.org).
   Provenance is weaker but adequate for an internal benchmark.
3. **Arthur supplies app #1**: the original D-1 path. Keep open as
   "fast-forward if Arthur picks one."

J adopts option 1 + option 2 in parallel:
- **Tick 48**: synthesise the cross-feature OWL idiom corpus
  (one ~500-line .cpp + matching .rc + matching headers).
  Compile-smoke through mdbcc. Categorise failures into the gap
  report.
- **Tick 49**: wire `cargo llvm-cov` into the supervisor gate.
  Coverage delta becomes a journal line per tick. Reviewer/implementer
  blind-spot mitigation: a one-line check per tick "did line
  coverage drop?" — if yes, surface to journal.
- **Tick 50**: add the cross-feature integration corpus
  (`tests/cpp_integration.rs`, ~15 fixtures per testing-strategy §3a).
  Closes H10 MINOR-3.
- **Tick 51**: write a fresh HLD for the first real K work item
  (lowest-effort gap from the J gap report).

J exit: gap report committed; coverage wired; cross-feature corpus
in place; K's first HLD ready.

Existing oracles (carry forward):
- **O1**: 88-program e2e (exit-code + stdout). Authoritative
  behavioural gate.
- **O2/O3**: MSVC `cl` / Borland `bcc32 5.5.1` differential.
- **O5** (planned): `iced-x86` linear decode.
- **O6**: GUI liveness via Win32 FFI.
- **Phase G byte-exact**: vs `brc32` over `.res`.
- **Reviewer process**: independent subagent at each phase boundary.

New oracles (from J onward):
- **O7 — gap-report determinism** (J): `mdbcc -c` over the OWL
  corpus produces a deterministic gap-report file; CI-locked.
- **O8 — app-build/runtime liveness** (K/L/M): each app reaches a
  green state; cross-corpus regression locked.
- **O9 — coverage delta** (J wired, ongoing): `cargo llvm-cov` line
  coverage tracked; drops surfaced per-tick.
- **O10 — cross-feature integration corpus** (J): closes H10
  MINOR-3.
- **O11 — determinism stripe** (N): 10 fixtures × 5 compiles ×
  identical SHA-256. Hardens H10 MINOR-9.

Rejected oracles (testing strategy §3f/g, §7):
- Lexer/parser fuzzing — wrong bug class for mdbcc.
- Fourth differential reference (clang/mingw-gcc).
- Snapshot tests of AST/IR.
- Mocks.
- bcc32-Win32 OWL behavioural diff (pointer-size mismatch).

**Testing charter (mandatory for every J–O tick)**:
1. O1 byte-identical for non-targeted features. SHA-256 sweep on
   touched paths before commit.
2. Every new feature ships with per-feature suite AND ≥1
   cross-feature integration test.
3. Every error path is explicit `CodegenError` with grepable phrase
   naming the originating stage.
4. External oracles self-skip loudly.
5. Reviewer process gates every Phase boundary.
6. Determinism stripe runs every tick.
7. Coverage drops are journal lines.

## 6. Devil's-advocate findings, retained as risk register

Cited per the testing charter as ongoing risks the loop must respect:

- **R-D1**: Speculative-feature-creep. Stage O is the trap. Gate:
  "no O work until N is signed off."
- **R-D2**: Self-graded corpus. Mitigation: J's cross-feature corpus
  + N's external app set replaces the 88-program oracle as the
  primary regression guard.
- **R-D3**: Reviewer/implementer shared blind spots. Mitigation:
  (i) coverage tracking (O9), (ii) Arthur reviews the SEH personality
  function once before N close-out, (iii) reviewer prompt explicitly
  asks "what would a human reviewer not familiar with this codebase
  spot?"
- **R-D4**: `src/codegen.rs` 6,400-line legibility risk.
  Mitigation: opportunistic mod-extract during any K/L/M tick that
  has spare subagent context; mandatory in N if not done.
- **R-D5**: Dialect-contract drift. Mitigation: each K/L/M app
  pinned to a specific BCC version (recorded in journal).
- **R-D6**: No user. The plan ships v1.0; whether anyone uses it is
  not the plan's problem. Acknowledged.
- **R-D7**: SEH undocumented-behaviour dependence. Mitigation:
  reviewer sign-off + a single Win11 23H2 + Win11 22H2 smoke test
  added in N.
- **R-D8**: Single-TU model collapses at multi-file app. Probable
  K item if any K app has more than one .cpp. Treated as architectural
  fork; surface to Arthur if encountered.
