# 2026.06.17 - JRN - G4 codegen final-symbol index

## Context

G3 showed that RailC/product time was dominated by codegen, not by the earlier
header-cache hunch. The serial RailC product baseline was ~68.0s wall, with
~61.1s summed `codegen` time.

The decisive anomaly was `ovlpdata.cpp`: 52 source lines, 15 templates expanded
to 1649 items, `compute_emitted` kept only 3 functions and 1 live record, but
the outer codegen phase still took ~3.9s. That shape pointed away from function
body emission and toward a full-TU pre-emission pass.

## Change

`src/codegen.rs::compile_module_for` now:

- precomputes each `Item::Func` final symbol once;
- builds `inline_by_final`, a final-symbol index of inline definitions;
- uses that index for extern-prototype/inline collision checks;
- reuses the precomputed final symbol in the later function-emission loop.

This replaces an O(extern prototypes x TU items) scan that repeatedly called
`final_symbol_for` / Borland overload mangling. Emitted order and output policy
are unchanged; this is a lookup/indexing optimization.

RailC serial wall is ~10.0x faster and summed codegen is ~48.8x lower. Default
parallel RailC wall is ~4.3x faster. The remaining serial RailC cost is now led
by preprocessing (~4.05s summed) rather than codegen (~1.25s summed).

## Notes

The next performance target has changed: after this slice, RailC serial summed
preprocess time is larger than summed codegen time. If G4 continues, revisit the
guarded-header tokenize-once cache with the new baseline rather than assuming
codegen is still dominant.
