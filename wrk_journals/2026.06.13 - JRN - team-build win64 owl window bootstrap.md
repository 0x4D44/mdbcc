## ⭐ KEY FINDING — the patch is correct but does NOT clear `0xC0000374` (wall 1 unmet; HLD premise wrong)

Full ignored run result (163.9s build + gates):
- **O0 ✅** railc=21 owl=65 streams=48 bids=11 rtl=207; clean PE32+ (12,357,120 B); trace + counts match.
- **O1 ✅** `403 named imports; *Ptr* present; no CTL3D32/VirtualAlloc/VirtualFree`.
- **O2 ✅** patched-object markers present; no residual truncating sites.
- **O3 ❌→ KNOWN GAP** the patched exe **still exits `0xC0000374` (heap corruption) before any window**.

**Analysis.** The WNDPROC-bootstrap patch is *correct and complete for what the HLD scoped* (it removes the
heap x86 thunk + the `SetWindowLong(uint32(thunk))` truncation + the `_EAX` recovery; O0/O1/O2 verify compile,
link, imports, and that the patched objects are used). But the `0xC0000374` crash is **unchanged** by it — and,
per the GOAL doc, was *already* unchanged by the heap-shim fix and the CTL3D fix. A crash that is invariant across
three unrelated fixes lives in a code path none of them touch: **upstream of the window bootstrap** (C++/RTL
startup or the heap allocator), *before* `StdWndProc` ever runs. So the HLD's root-cause premise (that the OWL
window bootstrap causes *this* `0xC0000374`) was **incorrect**. `0xC0000374` = `STATUS_HEAP_CORRUPTION`; prime
suspect is the **`wrk_rtlshim` process-heap allocator** (malloc/free over HeapAlloc/HeapFree with a 16-byte
alignment prefix — a classic header-corruption site), or another early RTL/global-ctor heap operation.

**Diagnosis attempted:** no x64 debugger in-env (cdb/windbg/drmemory absent; the only gdb is i386-Win32 and cannot
read the x64 PE — "File format not recognized"). So no backtrace was captured here. The finding rests on the
fault-stability argument above + the smoke's deterministic `0xC0000374` classification.

## 🔬 ROOT CAUSE FOUND (post-report, windbg/cdb installed per Arthur)
Installed WinDbg (`Microsoft.WinDbg`); used the bundled classic **`cdbX64.exe`** (headless). Relinked the exe with
`mdlink --map` (byte-identical) for symbol translation (no PDB emission). cdb caught the `c0000374`; backtrace:
```
ntdll!...heap error reporter...
ntdll!RtlAllocateHeap+0x2b5b
ntdll!RtlFreeHeap+0x2ba           <- HeapFree detected the corruption
railc_mapped+0x376e2a             <- our code freed a bad pointer
```
Map: VA `0x140376e2a` ∈ **`TVectorImpBase<…>::Resize`** (`wrk_oracle/.../CLASSLIB/VECTIMP.H:150-160`), one symbol after
`TStreamableTypes::TStreamableTypes`. So the crash is during **startup streamable-class registration** (global ctors
grow a BIDS vector), at `delete[] Data` in `Resize` — **before any window**, which is why it's invariant to the
OWL/heap-shim/CTL3D fixes and why the WNDPROC patch couldn't help.

**The actual defect — an mdbcc Win64 array-new/delete COOKIE MISMATCH:**
- `TVectorImpBase::Resize` does `T* temp = new(*this)T[sz]; … delete[] Data;` — allocator-placement array-new + `delete[]`.
- `gen_placement_new_array` (codegen.rs:14575-14593) compiles `new(alloc)T[n]` (class element) **COOKIE-LESS** — it
  calls `operator new[](n*sizeof(T), alloc)` and returns the raw block base (comment line 14576: "NO array cookie").
- `gen_delete` for a class array on **Win64** uses the **8-byte cookie** convention: count at `p-8`, and `HeapFree(p-8)`
  (codegen.rs:14723-14729). The i386 cookie path is gated `target == Win32 && array_needs_cookie` (14740-14746), so on
  i386 these allocator-new'd arrays stay **cookie-less on BOTH sides → matched → 32-bit RailC works**.
- On Win64 the cookie-less allocation meets the cookie-ful `delete[]` → `delete[]` frees `p-8` (8 bytes before the real
  block) → `RtlFreeHeap` sees a corrupt header → `STATUS_HEAP_CORRUPTION`.

**Scope:** this is a GENERAL Win64 C++ ABI bug — every BIDS/ClassLib container (`TVectorImp`/`TMIVectorImp`/… `new(alloc)T[n]`
+ `delete[]`) hits it; it blocks essentially any non-trivial Win64 OWL program, not just RailC. It is the true MDBCC-01
runtime wall.

**Fix direction (focused, NOT yet implemented — for Arthur's go-ahead):** reconcile the Win64 cookie convention between
allocator-placement array-new and array-delete. Cleanest: make `gen_placement_new_array`'s allocator form write the
8-byte cookie (alloc `n*sizeof(T)+8` via `operator new[]`, store `n`, return `p+8`) and route the matching `delete[]`
to the allocator's `operator delete[]` at `p-8` — i.e. give Win64 the cookie symmetry the i386 path already gets via
`array_needs_cookie`. Must keep the trivial-element and raw-buffer-placement (`new(voidptr)T[n]`) cases cookie-less,
and re-run the array-new/delete regressions on both targets.
