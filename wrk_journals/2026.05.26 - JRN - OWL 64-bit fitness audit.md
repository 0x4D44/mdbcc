## 2. MFP / Response-Table Storage (BLOCKER)

This is the core dispatch mechanism and the highest-priority blocker.

### Structure Definition (INCLUDE/OWL/EVENTHAN.H, lines 97–108)

`cpp
template <class T> class TResponseTableEntry {
  public:
    typedef void (T::*PMF)();

    union {
      uint          Msg;
      uint          NotifyCode;
    };
    uint            Id;
    TAnyDispatcher  Dispatcher;
    PMF             Pmf;
};
`

**Analysis:**
- **Win32 (32-bit pointer):** sizeof(PMF) typically 4 bytes (single-inheritance case) or 8 bytes (virtual inheritance). TResponseTableEntry<T> is ~16–20 bytes (4 + 4 + 4 + 4–8 padding).
- **Win64 (64-bit pointer):** sizeof(PMF) is 16 bytes (Microsoft ABI: MFP is offset + thunk address for virtual support). TResponseTableEntry<T> balloons to ~32–40 bytes. **Array layouts change; binary compatibility breaks.**

### Dispatch Architecture (INCLUDE/OWL/DISPATCH.H, line 39)

`cpp
typedef int32 _OWLFUNC (*TAnyDispatcher)(GENERIC&, TAnyPMF, uint, int32);
`

The TAnyDispatcher function pointer casts generic PMFs and calls them. On Win64, the PMF representation is incompatible; reinterpret-casting a Win64 PMF as Win32-sized PMF will silently truncate or misalign.

### Usage: 46 Files Declare Response Tables

All 46 files using DECLARE_RESPONSE_TABLE or DEFINE_RESPONSE_TABLE are affected:

- Core: APPLICAT.CPP, WINDOW.CPP, DIALOG.CPP, FRAMEWIN.CPP, DECFRAME.CPP, DECMDIFR.CPP
- Controls: BUTTON.CPP, CHECKBOX.CPP, COMBOBOX.CPP, EDIT.CPP, LISTBOX.CPP, SCROLLBA.CPP, SLIDER.CPP, RADIOBUT.CPP, STATIC.CPP, GAUGE.CPP, HSLIDER.CPP, VSLIDER.CPP, GROUPBOX.CPP
- Dialogs & Frames: DOCVIEW.CPP, EDITVIEW.CPP, CLIPVIEW.CPP, OLEMDIFR.CPP, OLEMETA.CPP, FLOATFRA.CPP, LAYOUTWI.CPP, GADGETWI.CPP, TINYCAPT.CPP
- OLE: OLEFRAME.CPP, OLEWINDO.CPP, OLEDLG.CPP, INSOBJ.CPP, OLEVIEW.CPP, PASTESPC.CPP, LINKS.CPP
- Misc: CONTROL.CPP, DOCMANAG.CPP, MDI*.CPP, FINDREPL.CPP, PRINTDIA.CPP, PRINTER.CPP, CHGICON.CPP, CHOOSECO.CPP, CHOOSEFO.CPP, EDITSEAR.CPP, VBXCTL.CPP, LISTVIEW.CPP, PREVIEW.CPP

**Severity: BLOCKER.** The response-table dispatch is OWL's core event-handling mechanism. Fixing this requires:
1. Redefining TResponseTableEntry to dynamically size based on __POINTER_WIDTH__ or Platform ABI.
2. Or rewriting dispatch to not store raw PMFs (use function indices + vtable lookup instead).

## 7. Instance Thunk Architecture (BLOCKER)

**Location:** SOURCE/OWL/OWL.CPP, lines 73–223.

OWL uses a **per-window instance thunk** to convert the static StdWndProc callback into a call to the member function TWindow::EventHandler(). This is necessary because Win32 window procs must be global functions, not C++ member functions.

### Win32 Implementation (lines 77–129)

`cpp
struct TInstanceThunk {
  char     Call;              // x86: 0xE8 (CALL)
  int      Offset;            // relative displacement
  PROC     WndProcPtr;        // pointer to StdWndProcInstance
  TWindow* Window;            // 'this' pointer
  char     Code[6];           // x86 code: POP ECX, MOV EAX,[ECX+4], JMP [ECX]
};
`

**Win32 behavior:**
- Thunk is allocated dynamically via 
ew TInstanceThunk.
- Win32 is "nice" about executable memory; this works.

**Win64 blocker:**
- Code offsets (Offset, the immediate in MOV EAX,[ECX+4]) assume 32-bit addressing.
- The Code[6] contains hardcoded x86 displacement; Win64 requires REX prefixes and 64-bit offsets.
- The layout assumes TWindow* is 4 bytes ([ECX+4]); on Win64 it's 8 bytes.
- Code page execution: modern Win64 DEP (Data Execution Prevention) requires thunks in executable code sections, not heap allocations.

### Win16 Implementation (lines 141–221)

Win16 thunks are even more complex, using GlobalAlloc, FP_SEG/FP_OFF macros (segment/offset addressing), and alias selectors. Entirely inapplicable to Win64.

**Severity: BLOCKER.** Options to fix:

1. **Redesign thunk mechanism:** Emit thunks into a code section at module load (e.g., via a DLL thunk table).
2. **Use Win64 API:** SetWindowSubclass or SetWindowLongPtr(GWL_USERDATA, (LONG_PTR)this) + static dispatch table.
3. **Virtual thunking:** Pre-allocate a dispatch table and use function indices instead of per-window thunks.

**Recommended for S7:** Adopt option 2 (SetWindowLongPtr + static dispatch table) — lowest risk, most compatible with Win64.

## 9. Severity Classification

### BLOCKER (requires design changes)

1. **Response-table MFP dispatch** (EVENTHAN.H) — Binary incompatible on Win64; PMF size changes.
2. **Instance thunk architecture** (OWL.CPP) — x86 asm + heap code allocation; incompatible with Win64.
3. **__far/
ear keywords** (NOXX.CPP, exception handling) — Win16 memory model; non-portable.

### PATCHABLE (mechanical edits)

1. **SetWindowLong → SetWindowLongPtr** (WINDOW.CPP, FRAMEWIN.CPP, DECFRAME.CPP, DIALOG.CPP, OWL.CPP) — 21 calls.
2. **Handle-to-int casts** (BRUSH.CPP, CHGICON.CPP, LISTBOX.CPP) — ~5–10 instances, mostly dead code.
3. **LPARAM cast to uint** (WINDOW.CPP:1066) — 1 critical instance.
4. **LPARAM ↔ LONG dispatcher casts** (DISPATCH.CPP) — 15 instances; likely OK but audit needed.

### ADVISORY (monitor; no changes required)

1. **MAKELONG / MAKELPARAM / LOWORD / HIWORD** (47 hits across 17 files) — Correct usage for 16-bit message parameters. Safe on Win64.
2. **sizeof(int) / sizeof(long)** (3 files) — Context-safe; no load-bearing assumptions.

## 10. Recommendation for S7 Scope

### Estimated effort for Win64 port:

| Task | Effort | Risk |
|------|--------|------|
| Patch SetWindowLong(Ptr) calls | 2–3 days | Low |
| Replace handle-to-int casts | 1–2 days | Low |
| Redesign instance thunk mechanism | 3–4 weeks | Medium (requires testing across all window classes) |
| Rewrite response-table MFP dispatch | 4–6 weeks | High (touches core event loop; regression risk) |
| Port exception handling (__far keywords) | 2–3 days | Low |
| **Total** | **6–8 weeks** | **Medium–High** |

### Most Important Read for Supervisor

**Top priority:** The **instance thunk mechanism** (OWL.CPP:73–223) and **response-table MFP dispatch** (EVENTHAN.H:97–108) are architectural blockers. Together they account for 50–60% of the porting effort.

**Recommendation:**
- **If porting OWL directly:** Plan 6–8 weeks for core changes, plus 2–3 weeks for testing/regression. Doable but not trivial.
- **If thunking is unacceptable:** Consider a **Win32-to-Win64 API compatibility layer** at the OWL boundary (e.g., emit Win32-compatible thunks on Win64 via a veneer layer), allowing OWL to run largely unchanged. This would defer deep porting to a future phase.
- **Lowest-risk path for S7:** Mechanical patches (SetWindowLongPtr, handle casts) first; defer thunk & MFP redesign to a Phase 2 if the supervisor prefers incremental progress.

The OWL 64-bit port is **feasible** but requires **design decisions** before S7 begins. Once the thunk + MFP approaches are locked, execution is straightforward.
