## Step 2 - Harden Windows GUI Test Execution

Problem:
- Normal parallel `cargo test` can schedule multiple interactive GUI liveness tests in `tests\gui.rs` at once.
- The tests use the same Windows desktop/window namespace and Win32 message APIs (`FindWindowA`, PID/window enumeration, `SendMessageA`, `PostMessageA`, child-window enumeration). That made the DDVT/STATTEST/CURSAPP/click-count probes intermittently fail under parallel load even when the same binary passed with `--test-threads=1`.

Implementation:
- Added a process-local `Mutex<()>` in `tests\gui.rs`.
- Each interactive GUI liveness test takes the guard after the `interactive_desktop()` gate and before writing/spawning the temporary executable.
- I initially guarded every process-launch test in `tests\gui.rs`, then applied review feedback and narrowed the guard back to true interactive GUI tests. Non-interactive resource/console launchers remain parallel.

Review:
- Independent review found no required changes.
- Applied the suggestion to keep the guard scope honest by removing non-interactive locks.
- Parked the stale/foreign caption-window hardening suggestion as a future improvement; this step targets same-binary parallel GUI cross-talk.

## Step 3 - File-Open Select-Success Oracle

Decision:
- Parked the select-success oracle instead of committing an unreliable GUI harness path.
- The current tracked acceptance already covers Set data file cancel, seeded alternate `.RCD` loads, saved-profile byte parity, and multiple exact GUI parity tiers.
- The untracked/ignored `wrk_probe` experiment tried the remaining obvious user-action paths, but none made the Windows common dialog return a successful selection in this session.

Evidence:
- Programmatically setting the common-dialog file-name control (`id=1148`) can put the intended `YORK.RCD` path into the edit field.
- `SendKeys.SendWait` is blocked in this session with `Access is denied`.
- Win32 `SendInput` failed in two ways while driving the dialog: first `ERROR_INVALID_PARAMETER` from a too-small INPUT layout, then `ERROR_ACCESS_DENIED` after the layout was corrected.
- UI Automation could locate the Open button but `InvokePattern` was unsupported for the target control in this dialog.
- `BM_CLICK`/posted OK closes the dialog, but both golden and mdbcc keep saving the original `KINGSX.RCD`, so treating that path as success would be a false oracle.
- The last focused command:
  - `mdtimeout 900s -- powershell -NoProfile -ExecutionPolicy Bypass -File .\wrk_probe\gui_parity\capture_child_windows_parity.ps1 -GoldenRun .\wrk_probe\gui_parity\golden_current_run -MdbccRun .\wrk_probe\gui_parity\golden_current_run -DataFile KINGSX.RCD -TimerTicks 30 -CompareSavedIni -ExerciseSetDataSelectPath .\wrk_probe\gui_parity\golden_current_run\YORK.RCD`
  - visual windows and saved profile parity remained exact between builds, but `GoldenSelectedDataFileSaved=False` and `MdbccSelectedDataFileSaved=False`.

Interpretation:
- This is not evidence of a golden-vs-mdbcc behavior split. Both builds behave identically under the failed automation.
- The honest next options are manual confirmation, a debugger/API hook around `GetOpenFileNameA`, or a deliberately instrumented app build. Those are outside the smallest useful post-self-host hardening slice.
