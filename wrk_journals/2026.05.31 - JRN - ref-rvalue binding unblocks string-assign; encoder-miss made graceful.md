## What shipped (3 commits, all gated: 88 byte-identity ×2 + full suite + clippy)

### 1. `ac4d630` — bind a value-rvalue argument to a `const T&` parameter (#8)
Binding an rvalue (a value-returning call, a method call, a binary expression)
to a reference parameter previously errored **"expression is not an lvalue"**:
every reference-marshalling site took the argument's address via `gen_addr`,
which rejects a prvalue. C++ permits binding such an rvalue to a `const T&` by
materialising a temporary.

- New `gen_ref_arg` helper centralises reference-argument marshalling. For an
  addressable (lvalue) arg → `gen_addr` (byte-for-byte the historical path); for
  an enumerated value-rvalue form (`Call`/`Binary`, and a `MethodCall` that is
  neither record- nor reference-returning) → evaluate the value into a fresh
  frame slot and leave that slot's address in rax (exactly what `gen_addr`
  produces for an lvalue, so every site captures it unchanged).
- The value temp must outlive the marshalling site (the callee may read the
  referent throughout the call), so it is NOT freed there — the next `alloc_tmp`
  would reuse its slot. New `deferred_ref_temps` counter reclaims them once at
  the function epilogue, keeping the `cur_tmp == 0` balance assertion.
- **Safe-by-construction**: only previously-erroring rvalue forms change; every
  lvalue binding still routes through `gen_addr`, and the frame reserves a fixed
  16 temps regardless of `cur_tmp` — no compiling program changes a byte.

### 2. `f4d0fdc` — route the i386 free-call path through `gen_ref_arg` too
The first commit converted SIX sites but missed a seventh: `marshal_args_cdecl`
(the i386 cdecl free/member path) bound a reference via `gen_addr` in its
non-UDC else-branch, so `-m32` still errored. Now all seven route through
`gen_ref_arg`; the only remaining `gen_addr(a)` is the `is_record`
struct-by-value path.
- Added RUN-verified tests on BOTH targets: `reference_param_binds_to_a_value_rvalue`
  (end_to_end / Win64) and `i386_reference_param_binds_to_a_value_rvalue`
  (i386_run / i386 + diff vs bcc32). Free-call, method-call (the `min` shape),
  and binary rvalue forms.

### 3. `<pending commit>` — encoder-miss → clean self-diagnosing error (robustness)
`encode()` ended in `.expect("encoder pattern miss")` — a PANIC whenever the
table has no row for an (op, operand-kinds) shape. New sticky `encode_miss`
flag (mirrors `tmp_overflow`): record the first miss (op + operand kinds via
`EncodeError`'s Display), emit nothing, and discard the function with a clean
`CodegenError` at the epilogue. Never panic — a missing encoding is unsupported
input, not a broken invariant. Byte-identity-safe (compiling functions never
hit the miss path). New test `i386_unsupported_encoding_is_clean_error_not_panic`
exercises the general path (`(long long)d` → `cvttsd2si r64, xmm`).

## The big result: `string::assign` is unblocked

The real BCC 4.52 RTL `string::assign` (ASSIGN.CPP) now COMPILES on both targets
and defines **`@string@assign$qr6stringuiui`** (and the 2-arg

STRING-RTL-link blocker.

Mechanism (the prior summary's diagnosis was partly off):

- Binding the `s.length()` rvalue to the template's `const T&` param was THE
  blocker. `new TStringRef(...)`, `delete`, and `throw(xalloc)` all codegen
  fine; the mangling was already correct (so #27 was a non-issue for `assign`).

## Addendum 3 — #24 cross-TU extern data (DONE, 0ff96f7) — a silent miscompile fixed

earlier mis-scoped as "too big for tonight". It was bounded once I found the
right shape, and the b12 discipline (gate + run + revert) made it safe to try.

**The bug (silent miscompile):** `extern int g;` was parsed identically to a
definition — the `extern` storage class was consumed and DISCARDED — so codegen
emitted a LOCAL zero `g` and reads used the TU's own slot. A program reading a
cross-TU extern global got **0, with no link error**. RUN-verified before/after.

**The fix (5 components, ast → linker):**
1. ast: new `Item::ExternGlobal { name, ty }` (avoids an `Item::Global` field
   ripple — only 2 exhaustive matches needed the new arm).
2. parser: capture storage-class `extern` (after the `extern "C"` check) →
   `extern T g;` with NO initializer becomes ExternGlobal; `extern T g = v;`
   stays a Global definition.
3. GlobalData: `is_extern` flag (6 construction sites, mechanical).
4. compile_module: ExternGlobal → register in sigs.globals (reads resolve via
   RipRef::Data) + push GlobalData{is_extern:true} (no def, no dynamic init).
5. object.rs: extern global → UNDEFINED EXTERNAL symbol, no `.data` bytes; and
   USER file-scope globals now have EXTERNAL linkage (was Static) so they are
   the visible defining side — `.`-prefixed internal globals stay Static.

**Verified:** cross-TU read 42 (was 0), cross-TU write 9, single-TU unchanged.
New test cross_tu_extern_data_reads_and_writes; updated parser unit test
plain_extern_is_undisturbed (it had codified the buggy extern-as-definition).
The External-linkage change aligns with C/bcc32 — o13/coff/two_file_link all
green. Static data members now get external linkage too (correct C++).

**Why it matters:** cross-TU data is broadly needed by the RTL (extern globals,
static members in non-defining TUs). Note: the string get_* are already provided

## Addendum 33 — S4.2(e): OWL 1.0 DDVT message dispatch implemented + RUN-verified (the 17-app lever).

   the `[ ... ]` expression (was: skip balanced brackets). WM_FIRST is `#define`d 0, so the

2. The index is recorded per-class (`ClassInfo::ddvt_handlers: Vec<(key, idx)>`).
3. After the class body (alongside `synthesize_base_chaining`), `synthesize_ddvt_windowproc`

   inherited WindowProc slot, so the runtime's static-thunk `self->WindowProc(m,w,l)` virtual
   call lands on it.
4. Runtime (OWL_RUNTIME_H): `struct TMessage { HWND Receiver; WPARAM WParam; LPARAM LParam;

## Addendum 52 — KEY FINDING: the oracle does NOT need a CRT; it OVER-EMITS `string` (reachability)

Root-caused (via temporary DBG in touch_record / the reachability worklist, reverted) WHY the
TArrayAsVector<int> oracle drags in the RTL string + libc/CRT, even though its RUNTIME path (allocate
int[], store, read) never touches string:

**The reachability analysis over-approximates and KEEPS the whole `string` class.** Three contributing
mechanisms, all in `compute reachable` (codegen.rs ~12340-12530):
1. `by_component` matches function references by NAME ONLY (not signature): a reachable reference to
   `operator==` / `operator+` / `operator<` (e.g. from the int-array's comparison machinery) pulls in
   EVERY overload of that name — including cstring.h's `friend operator==(const string&,const string&)`.
2. Those friend operators are emitted as ROOTS (the friend-def handler at parser.rs:1264 does NOT mark
   an in-class friend definition `inline`, though C++ gives it implicit inline/vague linkage). A root is
   always seeded reachable.
3. `touch_record` is CLASS-GRANULAR: touching the `string` tag keeps ALL its members + recurses its
   `TStringRef* p` field's class. So once `string` is named by any kept function, the entire string API
   (assign/append/find/compare/substring/regex operator()/...) is emitted, referencing the OUT-OF-LINE
   RTL string methods -> which need malloc/free/memmove/stricmp/_ctype/cin/cout/regex = the CRT.

DBG confirmed touchers: `operator+`, `operator<`, `operator<=`, `operator==`, `operator>` (the string
friend operators) each `via name=string`. NOT via a string value field (string is held by pointer).

**Implication: the oracle could LINK+RUN with NO CRT** if reachability stopped over-emitting `string`.
The faithful fix is a coordinated REACHABILITY-PRECISION effort (architectural — bigger than tonight):
  (a) mark in-class `friend` definitions `inline` (parser.rs:1264) — correct C++, makes them prunable;
  (b) BUT that requires reachability to track the `new`-expression -> `operator new[]` edge (a placement
      `new(v)T[]` calls the friend `operator new[](size_t,Alloc&)`; without the edge it wrongly prunes —
      proven: the (a)-only experiment broke e2e `placement_array_new_through_allocator_object`, reverted);
  (c) `by_component` (and `touch_record`) should be SIGNATURE/USE-precise so a reference to `operator==`
      keeps only the matching overload, not the string one; and touching a class should keep only
      ODR-used members, not the whole API (this is #16's deeper form).
All three interlock; doing (a) alone regresses, and even (a)+(b) leaves string touched by other
by_component name-collisions. This is the genuine "ODR-precise reachability / inline-on-demand" rework.
