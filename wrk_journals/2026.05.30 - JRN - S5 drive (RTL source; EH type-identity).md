## Tick — S4.2y: out-of-line static data member definitions (GREEN, committed e33052d)

**Gap (STRINGS.CPP:195):** `int string::case_sensitive = 1;` — a static data
member *definition* at file scope. The parser routed every `::`-qualified
file-scope name to `member_def_tail` (the member-function/ctor/dtor path),
which expects a `(` param list → "expected '('".

**Fix (1-line guard, surgical):** A `::`-name is a member *function*
definition only when the cursor sits on `(`. Guard the out-of-line-member
branch in `external_declaration` with `is_punct(LParen)`:

```rust
if self.is_punct(Punct::LParen)
    && let Some((class_path, member)) = name.rsplit_once("::")
{ ... member_def_tail ... }
```

A static-member definition (cursor on `=` or `;`) now falls through to the
existing global-object path → `Item::Global { name: "string::case_sensitive",
.. }`, a single program-wide object keyed by its qualified name. Codegen
already lowers `Item::Global` by name, so no codegen change was needed for
the *definition*.

**Verified:** 88 byte-identical baselines unchanged (no baseline uses static
data members); full suite 226+ tests green; clippy clean.

**Deferred (code-noted):** the direct-init form `Type C::m(args);` also shows
`(` and would mis-route to `member_def_tail`. Rare for statics, not exercised
by the RTL probe; left with a code note.

**Known semantic gap (NOT yet fixed — Steps B/C):** the in-class declaration
`static int case_sensitive;` is still parsed as an *instance field* (added to
`string`'s layout), and an unqualified in-method `case_sensitive` resolves to
`this->case_sensitive` (the field), disconnected from the global definition.
So today the static member compiles but behaves *per-instance* — wrong for a
shared class-static flag. To make STRINGS.CPP a *correct* RTL this needs:
  - (B) class-body: when `is_static`, register `{tag}::{member}` and DROP it
    from the instance layout (no field, no vptr shift);
  - (C) codegen in-method access: an unresolved `name` in a method → if
    `{cur_class}::name` is a global, resolve to that global (not `this->name`).
This is bounded + byte-safe (no baseline uses statics) and generalizes; it's
the next NON-architectural item. But it does NOT unblock STRINGS.CPP further
right now, because the very next blocker is architectural (below).

## CRITICAL ARCHITECTURAL FINDING — mdbcc's exception type-identity is vtable-keyed; real BC++ exceptions are NON-polymorphic

After S4.2y, STRINGS.CPP reaches codegen and dies on:

```
throw: class must be polymorphic (have at least one virtual function or a
virtual destructor) — Phase H4b's type matching uses the class's vtable RVA
as the type tag. Add `virtual ~Tag() {}` to fix
```

STRINGS.CPP does `throw outofrange();`, `throw string::lengtherror();`,
`throw xalloc(...)`. I checked the real headers:

**`except.h` — `xmsg` (the root BC++ exception class) has NO virtual
functions:**
```cpp
class _EXPCLASS xmsg {
public:
    _RTLENTRY xmsg(const string _FAR &msg);
    _RTLENTRY xmsg(const xmsg _FAR &msg);
    _RTLENTRY ~xmsg();                 // <-- NOT virtual
    const string _FAR & _RTLENTRY why() const;
    void _RTLENTRY raise() throw(xmsg);
    xmsg& _RTLENTRY operator=(const xmsg _FAR &src);
private:
    string _FAR *str;
};
class _EXPCLASS xalloc : public xmsg { ... };   // non-poly
```
`cstring.h`: `class outofrange : public xmsg`, `class lengtherror : public
xmsg` — all non-polymorphic.

**So the entire BC++ 4.52 exception hierarchy is non-polymorphic.** This is
not a quirk of one class — it's how Borland's RTL is built. BC++ (like MSVC)
identifies exception types with compiler-generated **type descriptors**
(RTTI-ish `__tpid`/type-info records), *independent of any vtable*. A class
needs no virtual function to be thrown/caught.

**mdbcc's Phase-H4b model conflates two things that BC++ keeps separate:**
1. *instance layout* — does an object carry a vptr at offset 0?
2. *exception type identity* — the per-type tag throw stamps and catch matches.

mdbcc uses the **vtable RVA** for (2). `is_polymorphic() == !vtable.is_empty()`
gates BOTH. The whole EH path is vtable-keyed:
  - `gen_throw_class` (codegen.rs:3523): rejects non-poly classes.
  - throw stamp (codegen.rs:3586): `lea` the vtable abs addr as the tag.
  - catch scope table + rethrow (codegen.rs:3422): catch type's vtable RVA.
  - `build_typeinfo` (pe_writer.rs:659): the derived→base hierarchy table is
    `[class_vtable_rva, base_vtable_rva]` pairs — *errors* (line 678) if a
    class has no vtable RVA.
  - synthetic personality fn walks that table comparing vtable RVAs.

**Impact:** this blocks essentially ALL real BC++ exception code — RTL string
ops, `xalloc` on `new`, OWL's `TXBase`-rooted exceptions when the base is
non-virtual-dtor, etc. It is a pervasive S5 blocker, not a STRINGS.CPP quirk.

### Proposed design (additive, byte-safe) — DECOUPLE EH type-identity from the vtable

Introduce a canonical **EH type-id RVA** per EH-participating class:
  - polymorphic class → **its vtable RVA** (UNCHANGED → existing fixtures stay
    byte-identical; the oracle protects this);
  - non-polymorphic class → a **synthetic 1-byte `.rdata` type-id datum**,
    emitted only for classes actually thrown/caught (collected like
    `live_records`), addressed by a new `RipRef::EhTypeId(rec_id)`.

Then:
  - throw / catch / rethrow `lea` `RipRef::EhTypeId(id)` instead of
    `RipRef::Vtable(id)`. For poly classes the resolver returns the vtable RVA
    → identical bytes.
  - `build_typeinfo` emits `[type_id_rva, base_type_id_rva]` using the
    type-id RVA (vtable RVA for poly, synthetic for non-poly), and includes
    non-poly EH classes. The personality is RVA-agnostic — it compares tags
    and walks the table — so it needs no logic change, only the generalized
    table.
  - drop the `is_polymorphic()` gates in `gen_throw_class` + the catch checks.

**Why additive/byte-safe:** existing fixtures are polymorphic-only and throw
no non-poly class, so EhTypeId==vtable RVA everywhere, build_typeinfo bytes are
unchanged, and no synthetic data is emitted. The 88-baseline oracle + full
suite gate every step; any drift is caught immediately; clean-tree revert is
the fallback.

**Scope:** ~6–8 sites across codegen (throw/catch/rethrow), a new `RipRef`
variant + resolution in pe_writer, synthetic-datum emission + collection, and
`build_typeinfo` generalization. The personality fn (`src/eh.rs`) likely
unchanged.

**Incremental path (lowest-risk first):** non-poly THROW only (synthetic
type-id + stamp) is enough to compile a throw-only TU like STRINGS.CPP (it
throws but does not catch these — the catches live in callers). Non-poly
CATCH + base-walk can follow when compiling catching code. This lets the
change land in two reviewed steps.

## Tick — S4.2ab: overloaded declared-only ctor registration (DRAFTED, REVERTED — net regression)

Root cause (real + now precisely understood): extern_proto folding
(codegen.rs:570) skips duplicate-named protos (`funcs` is a map), so the dozen
declared-only `string::string` ctors a TU sees from CSTRING.H collapse to ONE
— never forming an overload set ⇒ "no matching overload". Draft fix: count
protos, register same-named ones as Overloads (mirrors the defined-overload
path, reuses the proven `overload_symbol_with_records` mangler). It DID compile
FIND1/RFIND/SUBSTR1/SUBSTR2.

**But it REGRESSED 9 other files (37→31), so I reverted it.** Registration
alone makes overload resolution STRICT (type-based) where the old `funcs` path
was loose (arity-only). Strict resolution then fails on:
  - `new TStringRef(0,0,0,0,cap)` (ASSIGN/CLONE/CTOR1/3/4/5/6): `0`→`const
    char*` is a NULL-POINTER CONSTANT and `0`→`size_t`; `arg_compat` is
    type-based and can't match a literal `0` to a pointer;
  - `strpbrk`/`strchr` (FNDFRST/FNDLAST/FNDLASTN): the C++ const/non-const
    library overloads both match a `char*` arg ⇒ "ambiguous".

So the CORRECT fix is multi-part and must land together (Task #10):
  (a) overload registration (this draft);
  (b) `arg_compat`: int→size_t/unsigned standard conversion;
  (c) null-pointer-constant: literal `0` → any pointer — needs EXPR-level
      handling in `resolve_overload` (it has the arg exprs; type-based
      `arg_compat` cannot tell `0` from `x`);
  (d) C-library const/non-const overload tie-break (prefer the arg's
      cv-match) to kill the strpbrk/strchr ambiguity.

**Lesson (important):** the internal `cargo test` suite does NOT cover the RTL
source files, so S4.2ab passed the suite GREEN while regressing 9 RTL files.
The string-RTL probe (`for f in RTL/SOURCE/STRING/*.CPP; bcc -c -m32`) is a
COMPLEMENTARY oracle — run it for any change touching overload/type
resolution, not just the suite.

## Finding — const-pointer mangling diverges from bcc32 (Task #11, LOW priority)

bcc32: `g(const char*)`→`@g$qpxc`, `h(char*)`→`@h$qpc`. mdbcc's overload

collision risk if a class declares both `T(const char*)` and `T(char*)`.

## MILESTONE — S4.2ae: EH type-identity DECOUPLED from the vtable (non-poly exceptions work)

Reversed the "defer to Arthur" decision: the Stop hook explicitly demanded EH
to land S2–S7, and waiting for an asleep Arthur IS getting blocked (against his
"push on" directive). The decoupling is additive (polymorphic path unchanged),
byte-safe (88 baselines have no EH), reversible — so I built it.

**Mechanism — typeinfo-entry-as-descriptor.** mdbcc keyed EH type-matching on
the vtable RVA; BC++ 4.52's whole exception hierarchy (`xmsg`/`xalloc`/
`outofrange`/`lengtherror`) is non-polymorphic (no vtable). The fix: a
non-polymorphic class's EH type tag is the RVA of its OWN typeinfo entry
(`.Lxt.<id>`, which object.rs already emits as a symbol), with a
SELF-REFERENTIAL `class_rva`. The entry doubles as the type descriptor — no
separate datum. The personality compares type-tag RVAs and walks the typeinfo
hierarchy (also RVA-keyed), agnostic to whether a tag points at a vtable or an
entry, so throw / catch / catch-by-base all work unchanged.

**Changes:**
  - codegen.rs: drop the `is_polymorphic` gate in `gen_throw_class`; typeinfo
    now includes non-poly EH-LIVE classes (compute_emitted touches throw
    operands + catch types ⇒ they're live) + their sizes in `eh_buffer_size`.
  - object.rs (4 sites): `RipRef::Vtable(non-poly)` → its typeinfo-entry
    symbol; typeinfo `class_rva` non-poly → self; `base_rva` non-poly base →
    base's entry; catch scope-table `catch_type_rva` non-poly → entry.
  - Reverted a first wrong-path edit in pe_writer.rs's `write_pe` (the
    Module→PE path; compile_to_pe uses object.rs → `write_pe_from_objects`).

**Validation:**
  - 88 byte-identity baselines GREEN (poly EH path byte-identical).
  - Simple non-poly `throw E(42); catch (E& e)` → **42, matching bcc32 4.52**
    (new run-test). Before: "throw: class must be polymorphic".
  - Non-poly catch-by-base compiles to a well-formed PE (new test; the RUN is
    Defender-blocked — see below — but the runtime walk is identical to the
    polymorphic base-walk bar vtable-vs-entry RVAs).
  - **All 5 EH-blocked string-RTL files compile on Win64** (STRINGS.CPP — the
    HELLOAPP `TStringRef` dependency — at 46 KB), plus REGEXP (array-new works

## S4.2aj — extern-only member operators registered as overloads (operator[] un-defers!)

**THE operator[] blocker is FIXED.** Root-caused precisely (and corrected a

### Diagnosis (in-context, real CSTRING.H)
Instrumented `op_method_return_type` + `resolve_overload` and compiled a
minimal `#include <cstring.h>` user. The candidate dump for `string::operator()`
on a 1-arg `size_t` call showed FOUR candidates — and the non-const

const `operator()(size_t) const->char` (`@string@$bcall$xqui`) was present, so

The 4 missing overloads correlated *perfectly* with literal `throw(...)`

  already carries overloads is ADDED as another candidate (dup-checked on
  params+const, so a same-TU definition registers first and dup-checks out ⇒

## Tick (cont.) — HELLOAPP probed; next blocker = default-arg overload resolution (DEFERRED, design captured)

Pivoted from STRING to the mission's culmination — `EXAMPLES/OWL/OWLAPPS/HELLO/
HELLOAPP.CPP` (12 lines: `return TApplication("Hello World!").Run();`). Good
news: the OWL headers (`owl/owlpch.h`, `owl/applicat.h`) PARSE — we reach line 10.

  `10:3: no matching overload for call to 'TApplication::TApplication'`

ROOT CAUSE — `resolve_overload` uses STRICT-arity matching
(`c.params.len() != argtys.len() → continue`). `TApplication` ctors:
  58: (const char* name=0, TModule*& gModule=::Module, TAppDictionary* appDict=0)
  60: (const char*, HINSTANCE, HINSTANCE, const char*, int, TModule*&=…, …=0)
  236: (const TApplication&)   // copy
`TApplication("Hello")` is a 1-arg call to the 3-param, ALL-DEFAULTED ctor 58 ⇒
strict arity rejects it. Default-argument-aware resolution is needed — and OWL
uses defaulted ctors PERVASIVELY, so this is a high-leverage, recurring blocker.

### Why it was DEFERRED (not a safe single-tick autonomous change)
Attempted the min-arity relax (`min_args = params.len() - trailing_defaults`).
The repro `A v(7)` (3-param all-defaulted ctor + copy ctor ⇒ overload set; expect
a=7,b=20,c=30 ⇒ 930) FAILED to even resolve — exposing a THREE-PART problem the
fix must solve together:

1. **Parser collision.** `note_defaults` keys `fn_defaults` by SOURCE name and
   OVERWRITES. Two same-named defaulted ctors (58 & 60) collide ⇒ only the
   last-parsed survives. Needs `HashMap<String, Vec<Vec<Option<Expr>>>>` (one
   default-vec per overload), matched to a candidate by arity in codegen.
2. **Key mismatch.** `sigs.defaults` is keyed by source name; an OVERLOADED call
   resolves to and marshals under the MANGLED symbol (`ov.symbol`), so
   `sigs.defaults.get(key)` misses. (Non-overloaded calls key by source name and
   DO find defaults — that path works and must stay byte-identical.) Fix: build
   `sigs.defaults` keyed by the EMITTED symbol in codegen.
3. **`this`-prefix / `base` ABI misalignment (the dangerous one).** For the lead
   (ctor/method) + overload path, `ptys = ov.params` EXCLUDES `this`, yet
   `base = lead.is_some() = 1`, so `marshal`'s `ptys.get(base + i)` is shifted by
   one. BENIGN for scalar/pointer args (a `None` ptys ⇒ no convert/by-ref, which
   is correct for a pointer), which is why string ctors and `TApplication("x")`'s
   own `const char*` arg "work". But it WOULD bite a REFERENCE/record/FP arg —
   e.g. the APPENDED default `TModule*& gModule = ::Module` (a reference param):
   misaligned ptys ⇒ not marshalled by-ref ⇒ silent miscompile.

### Recommended design (for a focused / Arthur-aware pass)
- Parser: per-overload default-vecs (part 1).
- Codegen: `sigs.defaults` keyed by emitted symbol; store each overload's
  defaults on the `Overload` struct (aligned to `ov.params`, no `this`).
- `resolve_overload`: `min_args = params.len() - trailing_some(c.defaults)`; score
  only provided args (zip already stops at `argtys.len()`).
- **Expand defaults to ARGS at the call site** (`gen_call_with_lead`, both arms):
  after resolve, push the omitted `ov.defaults[args.len()..]` exprs onto the args
  and emit the full list. This sidesteps `marshal`'s append-indexing entirely.
- **Fix the lead+overload `base`/ptys alignment** (part 3) so the appended
  `TModule*&` reference default marshals by-ref. This is the byte-identity-
  sensitive bit — gate on the 88 baselines + targeted repros: `A v(7)`→930 AND a
  TApplication-shaped TWO-defaulted-ctor + ref-default repro to catch the
  collision and the by-ref default.
Reverted the partial change to green (committed state = S4.2au). This is the #1
OWL-ctor blocker but a cross-cutting ABI-marshal refactor — captured precisely
rather than landed blind overnight.

## #20 static-init — design REFINED via source dig (key de-risking finding)

Dug into the codegen/link internals to pin #20's exact components. KEY FINDING:
**the CRT static-init walker ALREADY EXISTS** for the linked path.
`src/link/crt.rs::synthesise_startup_object` emits `mainCRTStartup` →
`__do_global_ctors` → user `main` → `ExitProcess`, and `__do_global_ctors` walks
the merged `.CRT$XC*` function-pointer array between `__xc_a` (`.CRT$XCL`) and
`__xc_z` (`.CRT$XCZ`). So a file-scope ctor just needs a `.CRT$XCU` pointer to an
init function — the walker calls it before main. **PART 3 (startup) is DONE for
the mdbcc-objects + mdlink path.**

So #20 reduces to:
1. **PARSER** (`external_declaration`, parser.rs:3292): disambiguate `T name(expr-
   args);` → `Item::Global{ init: Some(Expr::Call{tag,args}) }` (SAME repr as
   `T name = T(args);`, which already parses). ~20 lines. Gate byte-identity.
2. **CODEGEN** (`global_image` decl.rs:88 + `compile_module` Item::Global + the
   object emitter object.rs): for a record-typed ctor-rvalue init — (a) zero the
   storage (don't `const_eval`); (b) emit a synth init function
   `@__sti_<g>` doing `Tag::Tag(&g, args)`; (c) emit a `.CRT$XCU` data section
   holding an 8-byte pointer with a reloc to `@__sti_<g>`. **NEW INFRA needed:** a
   `.CRT$XC*` section KIND (object.rs `canonical_section_name`) + a data→function-
   pointer reloc (today only `ptr_str` data→string relocs exist).
3. **STANDALONE-PATH GAP** (`pe_writer::write_entry_stub`, pe_writer.rs:33): the
   `compile_to_pe` entry stub is `sub rsp; call main; ExitProcess` — it does NOT
   call `__do_global_ctors`. So run_src/end_to_end (standalone EXE) wouldn't run
   the ctors. Either (a) add a ctor-walk to the standalone stub, or (b) GATE #20
   via a LINKED compile→link→run test (mdlink path, where the CRT walker runs).

⇒ #20 is a focused pass: parser (~20 LoC, byte-identity-gated) + object.rs
`.CRT$XC*` section + func-ptr reloc infra (the substantive part) + a link+run
gate. The CRT walker discovery turns it from "build a static-init subsystem" into
