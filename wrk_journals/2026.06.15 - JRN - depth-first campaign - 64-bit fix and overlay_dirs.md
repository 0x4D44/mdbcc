## 1. Step 1 — the 64-bit integer miscompile (DONE, `98115c4`)

The "unconfirmed hypothesis" was real and **four layers deep**. Found by
driving failing oracle tests down through the pipeline:

| Layer | Bug | Fix |
|---|---|---|
| Codegen | `gen_intop` emitted 32-bit opcodes for *all* widths | `gen_intop64` (REX.W: `shl rax,cl`, `cqo;idiv rcx`, …) |
| Operands | rhs truncated by `mov ecx,eax`; mixed int/ll not extended | `op64` width select + `extend_rax_to_64` |
| Typing | `expr_type` typed every literal **and** every integer-op *result* as `int` → 64-bit path never fired, nested results re-truncated | magnitude-based literal typing + result-width propagation + parser `Cast`-wrap for small `LL` literals |
| Sibling | unary `neg eax`/`not eax` had the identical 32-bit bug | width-aware `neg rax`/`not rax` |

**Symptoms confirmed exactly:** `x >> 32` returned the value unchanged
("lo==hi"); 64-bit divide used `cdq` not `cqo`; add/sub/mul lost carry across
bit 32. RailC survived only by avoiding u64 in hot paths.

**Debugging note (for the lessons file):** the bug masqueraded as fixed at the
codegen layer because every pure-literal test was *compensating* — the broken
32-bit `==` only inspected the low dword, which matched the broken arithmetic's
low dword. The fix only "took" once `expr_type` propagated 64-bit width so
`op64` fired and `extend_rax_to_64` stopped re-truncating nested results.
Lesson: a width bug needs the **type** to carry the width, not just the
instruction selector.

**Verification:** 17 oracle-checked cases in `tests/i64_ops.rs` (shift L/R,
signed/unsigned, div/mod/mul/add/sub, mixed-width promotion, compare, bitwise,
unary neg/not). Full suite: **75 suites, 1862 tests, 0 failures, 0 warnings.**
O1 byte-identity green (every new path gated on Win64 + 8-byte operands → i386
& 32-bit Win64 byte-identical; i386 263 tests unchanged).

**Residual gaps (logged in BUGS.md, deliberately scoped out):**
- B-02: an `LL`-suffixed literal in `0x8000_0000..=0xFFFF_FFFF` still types as
  `int` (mdbcc models that range as signed int; promoting it would change
  existing RailC behaviour).
- B-03: `const_eval` shift folding is signedness-blind (signed shift for
  unsigned). Codegen/runtime path is fixed; the *fold* path isn't.

## 3. Step 2 — generalize `-m64` (slice 1 DONE, `fa69d85`; remainder PAUSED)

**`fa69d85` — `overlay_dirs` manifest field.** Adds an `overlay_dirs` key to
`mdbcc.toml`, searched **before** `include_dirs`, so a target-specific header
shadows a same-named stock one. This lifts the Win64 overlay prepend (the
`include64/` ABI overlay: pointer-width `WPARAM`/`LPARAM`/`LRESULT` + `*Ptr`
thunk prototypes) out of the test harness into the production build driver —
the structural prerequisite for B-18 (build a Win64 app via `mdbcc.toml`
without test scaffolding). Empty by default ⇒ zero change for existing
manifests. Guarded by a new `project_config` e2e test (overlay header returns
40, stock returns 1 → overlay wins).

**Remaining for a full `-m64` target (NOT started):**
- `build_bc45_libs --target win64` → produce `mdowl64.lib` etc. reproducibly
  (currently hardcoded `-m32`).
- **Design fork (open):** where do the patched OWL Win64 sources live? Today
  they're hand-edited copies in `wrk_owl_win64/` (dev scratch). Options:
  (A) point `build_bc45_libs --target win64` at the scratch dir; (B) promote
  the overlay (headers + patched sources) into a tracked `overlay/win64/`.
- End-to-end: build RailC `-m64` via `mdbcc.toml`, diff objects vs the
  slice-test output.
