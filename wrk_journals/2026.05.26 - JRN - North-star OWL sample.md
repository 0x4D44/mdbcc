**Justification for DRAW over PRINTING (the only other clean candidate):**

PRINTING (201 LoC) is slightly smaller but exercises the OWL print subsystem (`TPrinter`, `TPrintout`, `TWindowPrintout` derived class with virtual `PrintPage`/`GetDialogInfo`/`HasPage`/`SetBanding` overrides, MM_ISOTROPIC mapping, page banding, scaling DC). That brings in printer dialog handling, banded device contexts, and the printer driver shim — a much taller stack for first-light. DRAW exercises a tighter, more S6-appropriate surface: TFrameWindow, mouse capture, TClientDC, file dialogs, response table, menu RC. The metafile/dialog pieces are independent OWL classes with no inter-dependence beyond OWL itself.

DRAW is the **smallest sample that exercises the canonical TFrameWindow + response table + .RC menu + EV_COMMAND triad** with no MI gap and no document/view framework.

## 3. OWL & C++ feature inventory of DRAW.CPP

### OWL classes referenced

- **`TApplication`** (subclassed as TDrawApp)
- **`TFrameWindow`** (subclassed as TDrawWindow; single inheritance path)
- **`TClientDC`** (instantiated; `new`/`delete`)
- **`TMetaFileDC`** (instantiated; `new`/`delete`)
- **`TMetaFilePict`** (stack-allocated; ctor + `PlayOnto`)
- **`TOpenSaveDialog::TData`** (nested-class member; `SetFilter`, `Flags`, `FileName`)
- **`TFileOpenDialog`** / **`TFileSaveDialog`** (temporary-object dialog Execute pattern)
- **`TPoint`** (passed by reference to mouse handlers)
- **`TRect`** (returned by `GetClientRect()` to size metafile playback)
- **`string`** (Borland pre-standard `cstring.h` class — used in `DisplayMessage`)
- Free function **`OwlMain(int, char**)`** (OWL entry-point shim)

### OWL response-table macros

```cpp
DECLARE_RESPONSE_TABLE(TDrawWindow);
DEFINE_RESPONSE_TABLE1(TDrawWindow, TFrameWindow)
  EV_WM_LBUTTONDOWN,
  EV_WM_LBUTTONUP,
  EV_WM_MOUSEMOVE,
  EV_WM_RBUTTONDOWN,
  EV_COMMAND(CM_RECORD, CmRecord),
  EV_COMMAND(CM_STOP,   CmStop),
  EV_COMMAND(CM_PLAY,   CmPlay),
END_RESPONSE_TABLE;
```

Four `EV_WM_*` window-message macros + three `EV_COMMAND(id, handler)` menu-command macros.

### TFrameWindow methods called

`SetCapture`, `ReleaseCapture`, `Invalidate`, `AssignMenu` (resource-name AssignMenu, not numeric), `UpdateWindow`, `GetClientRect`, `MessageBox`, `GetApplication`.

### C++ features the source uses

| Feature                                        | Status in mdbcc (per `2026.05.22 - JRN`) | Notes |
|------------------------------------------------|------------------------------------------|-------|
| Single inheritance (`: public TFrameWindow`)   | OK                                       | base path mdbcc supports.|
| Virtual functions overridden in derived class  | OK                                       | EvLButtonDown etc. dispatch via OWL response table — virtuals only inside OWL itself.|
| `const char far*` parameter declaration        | OK (`far` is treated as no-op on 32-bit)| Borland 16/32-bit dual-target source idiom.|
| Member-function out-of-line definition         | OK                                       | All Ev* / Cm* methods are out-of-line.|
| `new` / `delete` for class objects             | OK                                       | `new TClientDC(*this)`, `delete HoldDC`.|
| Reference parameter (`TPoint&`)                | OK                                       | mouse handlers.|
| Member of nested-class type (`TOpenSaveDialog::TData FileData;`) | **UNVERIFIED** — nested-class member layout has not been forced through mdbcc tests.|
| Temporary object execute pattern (`TFileSaveDialog(this, FileData, 0, "...").Execute()`) | **UNVERIFIED** — rvalue temp method dispatch on user-defined class.|
| `string` (Borland pre-standard CString) class with `c_str()` method | OK (per J-21 fixture).|
| `BOOL` / `UINT` / `HINSTANCE` typedefs         | OK                                       | from `<windows.h>` transitively.|

**No** templates, **no** multiple inheritance, **no** virtual base in user code, **no** operator overloading, **no** exception throw/catch, **no** RTTI / dynamic_cast, **no** namespaces, **no** STL.

### Known gaps vs mdbcc today

- **Inheritance from OWL itself**: TFrameWindow virtually inherits from TWindow (TFrameWindow : virtual public TWindow per OWL headers). DRAW does NOT spell out an explicit virtual-base init, so the compiler must implicitly emit a virtual-base init in the TDrawWindow ctor. mdbcc has not implemented virtual-base layout / virtual-base ctor init.
- **OWL response table template machinery**: `DEFINE_RESPONSE_TABLE1` expands to a `TResponseTableEntry<TDrawWindow>` table with member-function-pointer entries and dispatcher thunks (`v_U_POINT_Dispatch`, `v_Dispatch`). mdbcc does NOT support templates or member-function-pointer dispatch in this form.
- **Borland-extended pragmas / extensions**: `#include <owl\owlpch.h>` triggers `#pragma hdrignore SECTION` and `#pragma hdrstop` in OWL headers. mdbcc preprocessor does not implement these.
- **Massive include footprint**: `owl\owlpch.h` pulls in `windows.h`, all OWL machinery, and the BIDS containers. mdbcc has not been tested against the full Borland system-header surface.

These are the four big-ticket items between today's mdbcc and "DRAW builds with mdbcc". S6 will need each.

## 6. Disposition for S6

S6 (build the same DRAW.cpp with mdbcc + mdlink and run on Win11) is **a large but well-scoped jump from today's mdbcc**. The four big-ticket gaps blocking it:

1. **Virtual base classes (TFrameWindow : virtual public TWindow).** Without this, DRAW's `class TDrawWindow : public TFrameWindow` cannot lay out correctly; the ctor for TDrawWindow needs to chain through to TWindow via the virtual-base init path. Effort: **large** — requires layout reworking, vbtable emission, vbase offset adjustment. Per `2026.05.22 - JRN` line 273, this is explicitly Tier-4 / Stage-O work.

2. **C++ templates (response-table machinery).** `TResponseTableEntry<TDrawWindow>` is a class template; OWL also instantiates `Find` / `Dispatch` / `SearchEntries` over these. Without templates, the response-table macros expand to undeclared symbols. Effort: **very large** — likely the biggest single undertaking on the mdbcc roadmap.

3. **Member-function pointers (response-table entries) + their dispatcher thunks.** Each `EV_WM_LBUTTONDOWN` macro stores a `void (TDrawWindow::*)(UINT, TPoint&)` member pointer alongside a thunk address (`v_U_POINT_Dispatch`). Tick 71 (Apr 2026) landed virtual-mfp support; non-virtual mfp invocation through the response-table machinery should be close. Effort: **medium** if mfp infrastructure carries; **large** if the OWL template-thunk dispatch needs separate work.

4. **Borland-extended preprocessor (`#pragma hdrignore`, `#pragma hdrstop`).** `owlpch.h` uses these heavily. mdbcc currently treats unknown pragmas as no-ops (existing behaviour); needs validation that the OWL precompiled-header-like structure produces correct semantics without the actual pre-compilation.

**Estimated S6 effort (DRAW only):** 6–10 weeks of focused engineering, with templates being the gating item.

**Recommended S6 ordering:** virtual-base support FIRST (smaller, well-isolated, unlocks layout). Templates SECOND (the long pole). Then attempt the DRAW build and iterate on remaining link-time gaps from there.

**S6 sample-2 and sample-3 (medium/complex)** picks should be deferred until after the north-star is green; choosing them now risks premature commitment to a feature surface that turns out to be unreachable.

## 8. Surprises & open items

- **Surprise:** CD-shipped DRAW.EXE is 16-bit NE, not 32-bit PE. The CD ships the 16-bit pre-builds; rebuilding from source for 32-bit is mandatory and matches the COFF-only policy (per `2026.05.26 - JRN - BCC 4.52 CD inventory.md` §7 R8).
- **Surprise:** `bcc32 ... <file>.RES` does NOT pass the RES to TLINK32 as a resource; it tries to compile it as a source file (yields "Illegal character" errors). The correct pipeline is: bcc32 → link to .EXE; then brc32 to bind RES into the linked .EXE (post-link bind). The CD-shipped owlmake.gen uses this same order, so it's the canonical Borland 4.5 pattern.
- **Surprise:** `BRCC32 -32` is invalid; Win32 mode is default (use `-w32` to be explicit). `-30/-31` flags downgrade to Win 3.0/3.1 RES format.
- **Open:** PRINTING.CPP (201 LoC, also clean of MI) is a viable backup if S6 finds DRAW's metafile-DC path harder than expected. Both have menu RC + EV_COMMAND.
- **Open:** No screenshot was captured. When mdscreensnap gains an OWL-window-capture mode, a `Draw Away!` reference screenshot should be added to this journal for golden-image diffing in S6.
- **Open:** The DRAW.exe is statically linked at 108,544 bytes. A DLL build (`-tWD` + OWLDWF.LIB) would be smaller and exercise the OWL DLL surface; consider once S6 advances enough to make either flavour buildable.
