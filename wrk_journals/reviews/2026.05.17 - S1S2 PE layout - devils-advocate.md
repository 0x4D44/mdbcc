## Challenge 1 — Release-build silent corruption via compiled-out `debug_assert_eq!`

**Premise verified true:** `Cargo.toml` `[profile.release]` (opt-level 3, lto) does **not** set
`debug-assertions = true`. So `debug_assert_eq!(text.len() as u32, text_vsize)` (`src/pe.rs:368`)
and the stub-length / idata-offset asserts are **compiled out in release**. The test suite runs
debug, so the reconciliation between the pre-pass `text_vsize` (`src/pe.rs:338-339`) and the real
`build_text` output is **never checked in release** by any test.

**But the divergence is structurally impossible — proven, not asserted:**

- `write_pe(module: &Module)` (`src/pe.rs:329`) takes an **immutable** borrow. `build_text`
  (`src/pe.rs:221`) also `&Module`. Neither can mutate any `f.code`. No interior mutability
  (`CompiledFn` is plain `Vec<u8>`/`String`, `src/codegen.rs:146-153`).
- `f.code` is **finalized before `CompiledFn` is constructed**: `Gen::run` emits the whole body,
  then moves `self.code` into `CompiledFn` (`src/codegen.rs:439-445`). All `patch()` sites
  (`src/codegen.rs:475-478`, ~13 call sites) use `code[at..at+4].copy_from_slice` — **4-byte
  in-place overwrite, never a length change**. `compile_module` then only `funcs.push(cf)`
  (`src/codegen.rs:300`) — no further `code` touch. No insert/remove/splice/drain/resize on
  `code` exists anywhere (grep-confirmed).
- Pre-pass iterates `module.funcs`, sums `f.code.len()`, adds `STUB_LEN`. `build_text` iterates
  the **same** `module.funcs` in the **same** order, `cursor += f.code.len()` per func, appends
  each body verbatim (`t.extend_from_slice(&f.code)`), patches relocations in place (no resize).
  **No per-function alignment/padding/NOP-fill exists in `build_text`** that the pre-pass omits
  (the only padding in the whole file is `.idata` hint/name 2-alignment, internal to
  `build_idata`, not `.text`). The stub is a fixed `STUB_LEN=0x12` byte sequence,
  itself asserted (`src/pe.rs:253`) and unconditionally identical-length.

The pre-pass is an exact arithmetic mirror of the build. They cannot drift in the current code.

**DISMISSED (would-be BLOCKER, but the mechanism cannot fire).**
The reviewer's PRAISE on this point is correct.

**However — recommended hardening (MINOR, may be Stage 3):** the *only* thing protecting release
builds is a debug-only assert plus the discipline that nobody ever adds per-function alignment to
`build_text` without updating the pre-pass. That is exactly the kind of invariant that rots under
a future "align hot functions to 16 bytes" change — and it would produce a **release-only,
test-invisible, unloadable/again-overlapping exe** (`SizeOfImage` and `.idata` RVA computed from a
too-small `text_vsize`). The robust fix is one line and free: derive the layout from the **real**
build, not a parallel estimate. Concretely, in `write_pe`, build `.text` is currently done late
because it needs `idata`/RVAs which need `text_vsize` first — a true ordering constraint. Minimal
defensible options, in order of preference:
1. Replace the debug-only assert at `src/pe.rs:368` with an **always-on** check that returns
   `Err(CodegenError(...))` on mismatch (it is already in a `Result`-returning fn; cost is one
   `u32` compare, only when the structural invariant has been broken by a future edit). This
   converts a silent release miscompile into a loud compile error. **Do this — it is trivial and
   the asymmetry of consequences (free vs. shipping an unloadable exe) is overwhelming.**
2. (Heavier, not required) restructure so `text_vsize` is the length of an already-built
   stub-less body vector. Rejected as over-engineering for S1/S2.

Recommendation: apply option 1 (debug_assert → runtime `Err`) **before the S1+S2 commit** — it is
a 2-line change, removes the single largest latent-risk asymmetry in the diff, and the reviewer
should have flagged the release/debug assert gap rather than only praising the assert.

## Challenge 2 — Loads-but-crashes (stale RVAs into a still-loadable image)

Three sub-targets: `.rdata` string RIP targets, `.idata` import RIP/IAT, and the `.data`
pointer-to-string **absolute** value, all when emitted after a >4 KB `.text`.

**`.idata` + `.rdata` after big `.text`: genuinely exercised — DISMISSED.**
Important correction to the test/review prose: mdbcc's `printf` is **not** an imported `printf`.
`gen_io_builtin` lowers `printf` to inline `GetStdHandle`/`WriteFile` import refs
(`RipRef::Import`, `src/codegen.rs:1800,1809`) **plus** the format string via
`intern_string`/`RipRef::Str` (`src/codegen.rs:1784`). Both `pe_layout.rs` (`printf("sum=%d\n",
s)`) and `bigcode.c` (`printf("bigcode=%d\n", s)`) place that `printf` inside `main`, which is the
**last** function emitted (`tu.items` order, `src/codegen.rs:293-301`), hence physically after the
800 / 64 bloated functions. So a stale `.rdata` string RVA or a stale `.idata` IAT RVA computed
off the *old* fixed 0x2000/0x3000 would make `WriteFile` read garbage / the string print wrong /
the call fault — and `pe_layout.rs` asserts **exact** stdout (`assert_eq!(stdout,
"sum={sum}\n")`) and **exact** exit (`assert_eq!(exit, expected_exit)`) with the sum recomputed
independently in Rust. This is a real loads-but-miscompiles oracle for the `.rdata`+`.idata`
after-big-text case. The reviewer's PRAISE here is sound (its "imported printf" wording is
imprecise but the coverage it claims exists for a different reason).

**`.data` pointer-to-string ABSOLUTE value after big `.text`: UPHELD-CONCERN (severity MINOR).**
`build_data` (`src/pe.rs:189-207`) writes, for a `char *g = "..."` global, the **absolute**
8-byte value `IMAGE_BASE + rdata_rva + rdata.len()` (`src/pe.rs:198-201`). This is the *only*
absolute (non-RIP, non-loader-relocated) address the writer emits, and `DllCharacteristics=0` /
no reloc table means it is correct **only if `rdata_rva` is exactly right at load time** — there
is no `.reloc` safety net. **Neither new oracle has a single file-scope global** (verified: zero
globals in `bigcode.c`; `pe_layout.rs`'s generator emits none). The existing O1 suite *does*
cover this path (`tests/end_to_end.rs:848 string_global_and_printf`,
`:800 global_variable_state`) — but **only for small programs**, where `rdata_rva` is the
historical fixed `0x3000` and the regression-safety proof guarantees byte-identical output.
**The new code path — that same absolute formula when `rdata_rva` is dynamically shifted by a
large preceding `.text`/`.idata` — is exercised by nothing, anywhere.**

Severity is MINOR not MAJOR because the formula is sound *by the same construction* that the
large-`.idata`/`.rdata` RIP path uses (and that path **is** exercised large by `pe_layout.rs`):
`rdata_rva` is pinned before `build_data` appends (`src/pe.rs:346` then `:350`), `IMAGE_BASE` is
fixed, the recurrence is uniform. So this is a **coverage gap on a high-consequence path**, not a
demonstrated bug. But "reasoned correct + zero large-regime coverage on the only absolute address
in the binary" is exactly the residual the reviewer waved away too cheaply.

**Required:** add coverage of a `char *g = "..."` global **after a large `.text`** with an exact
stdout/exit assertion on the dereferenced string. Cheapest: extend `pe_layout.rs`'s
`big_program()` to also emit `char *tag = "T";` and `printf("%s%d\n", tag, s)` (the `%s` path is
already supported — `src/codegen.rs:1640-1658`), asserting the `T`-prefixed output. This converts
the largest uncovered loads-but-wrong-pointer path into a guarded one for ~4 lines.
**This can be Stage 3** *iff* Stage 3 is committed-to in writing and lands before any release
build is produced; otherwise pull it into S1/S2. It is not a commit blocker on its own.

## Challenge 3 — "Byte-identical for small programs": proven or asserted?

The reviewer's symbolic proof is **correct and I reproduce it**: for every section ≤ 0x1000,
`text_rva=align_up(0x400,0x1000)=0x1000`; `text_vsize ∈ [STUB_LEN .. 0x1000]` (min 0x12, never
0, so `idata_rva=align_up(0x1000+vsize,0x1000)=0x2000`); `rdata_rva=0x3000`;
`data_rva=align_up(0x3000+rdata.len(),0x1000)=0x4000`;
`size_of_image=align_up(0x4000+data_vsize,0x1000)` — identical to the historical formula. File
offsets, `SizeOfRawData`, `FILE_ALIGN`, `HEADERS_SIZE`, DOS/PE headers, section count (still 4),
raw padding are all size-independent and untouched by the diff (confirmed by reading the whole
`write_pe`). There is **no** realistic perturbation (SizeOfImage page, BaseOfCode, SizeOfCode,
section count, raw padding) for a ≤0x1000 program: every one of those is a pure function of the
same inputs reduced to the same constants.

**A literal old-vs-new byte-diff test is genuinely UNNECESSARY — DISMISSED.** The proof is total
(every emitted field traces to constants for the small case), and the 88 O1 behavioural tests
plus the `mdbcc_determinism` byte-equality guard already pin observable behaviour and
recompile-stability. A frozen-golden-bytes test would be **negative value**: it would (a) require
checking in a binary blob, (b) need regeneration on any *intentional* unrelated codegen change,
and (c) add maintenance cost exceeding the confidence it adds over the existing proof + 88 tests.
The reviewer correctly declined it; arguing for it would be cargo-culting.
One residual nuance the reviewer could have stated explicitly: the proof's *load-bearing
assumption* is `text_vsize ≥ 1` for the small case (so `align_up(0x1000+vsize,…)` rounds up to
0x2000, not stays 0x1000). That holds unconditionally because `STUB_LEN=0x12` and `main` is
mandatory — but it is the one place the small-case proof is non-obvious and deserved a sentence.
Not a defect.

## Challenge 4 — Determinism: proven or assumed?

I traced every map in the sizing/emission path:

- `idata.iat_slot: HashMap<&str,u32>` (`src/pe.rs:89`): **inserted** in `IMPORTS` array order
  (`src/pe.rs:151-154`); **only ever keyed-looked-up** for emission (`idata.iat_slot["ExitProcess"]`
  `src/pe.rs:240`; `idata.iat_slot.get(name)` `src/pe.rs:274`). **Never iterated.** The bytes that
  go into `.idata` come from the `hn_off` `Vec` and `IMPORTS` array loops (`src/pe.rs:131-154`),
  both fixed-order. No `collect()` from this map.
- `offsets: HashMap<&str,usize>` in `build_text` (`src/pe.rs:229`): inserted in `module.funcs`
  order, only `.get()`-looked-up for relocation targets. Never iterated for emission.
- `intern_string` (`src/codegen.rs:488-494`): dedup via `Vec::iter().position` — **order-stable
  Vec**, not a hash set. `strings` is a `Vec<Vec<u8>>`; `build_rdata` walks `module.funcs` then
  `f.strings` in order (`src/pe.rs:173-181`). Deterministic.
- `compile_module` uses HashMaps (`sigs.funcs`, `name_counts`, etc.) for **lookups only**;
  emission order is driven by `tu.items` (`src/codegen.rs:293`), a Vec in source order. No
  `.iter()`/`.collect()` over a `HashMap`/`HashSet` feeds any byte or size in the changed path
  (grep across `src` confirms no map iteration in pe.rs; codegen map iteration is `name_counts`
  for counting only, not emission).

**DISMISSED.** No nondeterministic iteration reaches output. The `mdbcc_determinism` guard
(`tests/differential.rs:264`) passes on merit, not luck — and crucially `bigcode.c` now feeds that
guard a *large* unit (string + imports + 64 funcs), strengthening it. Reviewer correct.

## Challenge 5 — Edge cases waved to "Stage 3"

`align_up(v,a) = v.div_ceil(a) * a` (`src/pe.rs:38-39`). **Exact-multiple is correct, verified
by definition** (not assumed): for `v` a multiple of `a`, `div_ceil` = `v/a` exactly (no
remainder, no +1), so `align_up(v,a)=v` — **no spurious extra page**. A section whose vsize is
exactly `k*0x1000` advances the next base by exactly `k` pages. The reviewer's reasoning holds;
I independently confirm via the integer identity. Coverage by test: none — but the property is a
one-liner and provably correct; an explicit test is **nice-to-have, legitimately Stage 3**.

Per-edge verdicts:

- **Zero functions / no `main`**: `compile_module` hard-errors "no 'main'"
  (`src/codegen.rs:287-289`) before `write_pe`; `build_text` also re-checks
  (`src/pe.rs:237-239`). `text_vsize` ≥ `STUB_LEN` always. Safe. Not a layout concern.
- **No imports**: `IMPORTS` is a fixed 6-element const array; `.idata` is never empty. N/A by
  construction (cannot occur).
- **No string literals / empty `.rdata`**: `push(0)` guard (`src/pe.rs:351-353`) runs **before**
  `data_rva` (`:359`) and before `rdata_vsize` (`:370`) — order is correct; degenerate section
  gets a valid 1-byte image and correctly-spaced following RVA. Verified by line order. Safe.
- **Empty `.data`**: same — `push(0)` (`src/pe.rs:354-356`) before `data_rva` (`:359`) and
  `data_vsize` (`:371`). But note the guard runs **after** `build_data`, so a ptr-string global
  has already appended to `.rdata` and `data_rva` correctly uses the post-append `rdata.len()`
  (`src/pe.rs:359`). Ordering is right. Safe.
- **Single function whose own body > 4 KB**: covered by the uniform recurrence; `pe_layout.rs`
  exercises aggregate >>4 KB `.text` but **not** a single >4 KB function body. The relocation
  math (`src/pe.rs:266,286-288`) is offset-based and size-agnostic, so this adds no new risk
  beyond aggregate-large `.text` which IS tested. Reasoned-safe; explicit test legitimately S3.
- **Large `.data` AFTER large `.text` (the genuinely-new multi-section interaction)**:
  **UPHELD-CONCERN (severity MINOR)** — same gap as Challenge 2's `.data` sub-point and the
  reviewer's own "Known gap #2". Tested by **nothing now** (zero globals in either oracle). The
  recurrence covers it *by construction* and is the same recurrence proven sound for large
  `.idata`/`.rdata` (which IS tested large), so this is a coverage gap, not a latent bug. Pull
  the fix forward **with** Challenge 2's suggested `char *tag` extension to `pe_layout.rs` — one
  change closes both. Stage 3 acceptable **only** under a written Stage-3 commitment landing
  before any release artifact.

No edge deferred to Stage 3 hides a *demonstrable* bug — but two ("large `.data` after large
`.text`", "the only absolute address in the binary, large-regime") are high-consequence,
zero-coverage paths that the reviewer dismissed with "covered by construction" a little too
breezily. They are correctly *reasoned*, dangerously *untested*.

## Challenge 6 — Was the code review too soft?

Mostly rigorous (the symbolic regression proof and data-dependency-ordering PRAISE are genuinely
good and I reproduced them). Three things APPROVE-WITH-NITS under-weighted:

1. **The debug/release assert asymmetry was praised, never risk-assessed.** The reviewer called
   `debug_assert_eq!` "exactly the right tool" without noting it is **compiled out in the only
   build that ships**, leaving a future-edit footgun with zero release coverage. A skeptical
   reviewer flags that the *guard itself* has no teeth in release. (→ Challenge 1, MINOR, fix now.)
2. **"`.data` pointer absolute value … correct" — verified only at the historical RVA.** The
   reviewer's verification item #4 checks the formula but not that it is *exercised in the
   large-RVA regime*; combined with "Known gap #2" this is the single highest-consequence
   untested path (the only non-relocated absolute address in the file). Should have been called a
   MINOR coverage gap, not folded into a "reasoned-correct, Stage 3" footnote. (→ Challenges 2/5.)
3. **The two oracles share a blind spot the reviewer noted only as a size-prose NIT:** *neither*
   has any global / any `.data`. The reviewer flagged the cosmetic "~26 KB vs ~132 KB" prose
   mismatch but not the substantive fact that the union of both oracles still has empty `.data`,
   so the new multi-section `.data`-after-large-`.text` interaction is wholly uncovered.

These are weighting/coverage-skepticism misses, not correctness errors in the review's reasoning.
The review is **adequate on correctness, under-rigorous on test-coverage skepticism** for the two
high-consequence paths above.

## RECOMMENDATION

`SAFE-TO-COMMIT` — with one trivial fix applied first and one coverage item that may be S3 under a written commitment:

- **MUST FIX BEFORE S1+S2 COMMIT (MINOR, ~2 lines):** replace the debug-only
  `debug_assert_eq!(text.len() as u32, text_vsize)` at `src/pe.rs:368` with an always-on
  `if text.len() as u32 != text_vsize { return Err(CodegenError(...)) }`. Free, removes the only
  latent release-only-unloadable-exe footgun in the diff. (Challenge 1.)
- **MUST DO IN S3 (MINOR) — or pull into S1/S2 if no written S3 commitment:** add a
  `char *g = "..."`-after-large-`.text` case with exact stdout/exit assertion (extend
  `pe_layout.rs` `big_program()` with `char *tag="T"; printf("%s%d\n",tag,s);`). Closes the only
  untested high-consequence path: the binary's sole non-relocated absolute address, and
  large-`.data`-after-large-`.text`, in the new dynamic regime. (Challenges 2 & 5.)
- **NICE-TO-HAVE S3:** explicit exact-`SECT_ALIGN`-multiple section test and a single->4 KB-body
  test. Proven-correct by construction; low value, legitimately deferrable.

The core fix is correct: the RVA recurrence is sound for arbitrary sizes, regression safety is
provably byte-exact, determinism is real (and strengthened by `bigcode.c`), and the
`.rdata`+`.idata`-after-large-`.text` failure mode is genuinely exercised with exact oracles.

## CLOSE-OUT (2026-05-17, fresh independent devil's-advocate)

### Ch.1 — CLOSED.
- The reconciliation is now `src/pe.rs:371-377`: `if text.len() as u32 != text_vsize { return
  Err(CodegenError(format!(... pre-pass ({}) ... emitted code ({}) ..., text_vsize, text.len()))) }`.
  (a) **No `debug_assert`/`assert` form of this check remains** — grep of `pe.rs` shows the only
  `debug_assert_eq!`s are three *unrelated* invariants (l.141 hint/name offset, l.253 stub length,

  (b) Returns via the function's real `Result` using `CodegenError` — the **same** type the rest
  of `pe.rs` uses (`build_text`'s duplicate-fn / undefined-callee / unknown-import errors); no
  panic, no `unwrap`, no bespoke type. Propagates `CodegenError -> CompileError::Codegen` via the
  existing `From` in `compile.rs:46`, so it surfaces as a `compile_to_pe` `Err` (not a process
  abort) in release.
  (c) Message carries **both** values (`text_vsize` and `text.len()`).
  (d) On the normal write path, not behind any `cfg` — placed right after the real `build_text`
  call (l.367) and before every dependent size/RVA, so a divergence is caught *before* a bad
  image is emitted, exactly where it can catch it.

  (off 526570) and `diverged from emitted code` (off 526595) are contiguously present in the
  **release** `target/release/bcc.exe` (profile = opt-level 3 + lto, `debug-assertions` unset).
  The guard is NOT compiled out and NOT dead-code-eliminated by LTO; it is reachable on the
  `write_pe` path. (The prior memo's "MUST FIX" is genuinely, not superficially, discharged.)

### Ch.2/5 — CLOSED, and the new oracle HAS TEETH.
- `tests/pe_layout.rs` now declares a **file-scope** `char *tag = "T:";` (l.75), 800 trivial
  functions (NFUNC=800 → `.text` ≫ 8 KB, well past the old ceiling), then
  `printf("%s%d\n", tag, s)` (l.86) — the `%s` after the large `.text`. It asserts **exact**
  stdout including the literal `TAG` bytes (`format!("{TAG}{sum}\n")`, l.99) and **exact** exit
  (l.103-110), with `sum` recomputed independently in Rust (`fval`).
- **Teeth verified by full codegen trace** (not trusted from prose):
  `tag` = `Expr::Var` → `expr_type` resolves it via `sigs.globals` to `Type::Ptr` (codegen.rs
  l.2152-2167). `gen_expr` (l.892-902): ptr is not Array/Record → `gen_addr` then `load_rax`.
  `gen_addr` for a global (l.721-723) emits `lea rax,[rip+g]` with **`RipRef::Data(idx)`** — the
  address of the `.data` 8-byte slot. `load_rax(Ptr)` (l.1191-1192) emits `mov rax,[rax]` — an
  8-byte dereference of that slot, loading the **absolute** value `IMAGE_BASE + rdata_rva + off`
  that `build_data` wrote (`pe.rs:198-201`). This is **provably the `.data` `ptr_str`
  absolute-address path**, NOT a RIP-relative-to-`.rdata` ref and NOT constant-folded:
  grep confirms codegen.rs has **no** const-fold / propagation pass (`const_fold|fold_const|
  propagat` → 0 hits); `Expr::Var` is never folded to an immediate/RIP literal anywhere.
- **No spurious pass.** With `.text` ≫ 8 KB the real `rdata_rva` ≥ 0x4000. A stale `0x3000`
  (old fixed) absolute pointer would land **inside `.idata`** (descriptor/ILT/IAT/hint-name
  bytes), so `%s` reads import-table garbage or faults — it cannot coincidentally spell
  `"T:"`+`\0`+`{sum}\n`. The string content is asserted exactly, so wrong pointer ⇒ wrong/garbage
  bytes ⇒ `assert_eq!` fails; a non-loading PE ⇒ `Command::output().expect("launch")` **panics**
  (hard RED). Confirmed empirically: `cargo test --release --test pe_layout` PASSES in 0.18 s in
  **release** (debug-asserts off) — the large-regime `.data`-absolute path actually loads and
  prints `"T:{sum}\n"`. The only uncovered high-consequence path the prior memo flagged is now
  guarded with an exact, teeth-bearing oracle, in S1/S2 (no S3-deferral risk).
- `bigcode.c` independently corroborates: it carries `char *tag = "T:"` + `printf("%sbigcode=%d
  \n", tag, s)` after 64 multi-stmt functions (>4 KB `.text`); it lives in `tests/corpus/
  portable/` with **no** `// oracle: skip*` directive (the only `skip` strings in the tree are
  unit-test fixtures in `support/mod.rs` and external-tool *self*-skips). So it flows through
  O2 (MSVC `cl`), O3 acceptance (`bcc32 -c`), O3 behavioural (`bcc32` Win32 run) and the

  int-only arithmetic bounded by `%1000`, `char*`+`%s` (no ptr/int-size divergence): truly
  portable across 32-bit bcc32 and 64-bit mdbcc.
