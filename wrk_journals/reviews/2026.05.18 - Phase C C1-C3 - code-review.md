## Strengths (genuinely solid — verified, not assumed)

1. **The multi-descriptor `.idata` layout is correct, well-formed, and
   deterministic.** `emit_idata` (`src/pe.rs:209-321`) lays out
   `descriptors | per-DLL ILT | per-DLL IAT | hint/name | dll names`
   with `desc_size = (k+1)*20` (k DLLs + null terminator), each
   descriptor's `OriginalFirstThunk`/`FirstThunk`/`Name` pointing at
   that DLL's own null-terminated ILT/IAT sub-array and DLL string,
   `dirs[1] = (import_dir_rva, desc_size)` and `dirs[12] =
   (iat_rva=rva(iat_block_off), iat_size)` legitimately spanning all
   DLLs' contiguous IAT sub-arrays (`src/pe.rs:750-751`). `iat_slot`
   maps each symbol to `rva(iat_off[gi]) + i*8` — its own per-DLL cell,
   distinct across DLLs because the sub-arrays are disjoint. The
   `multi_dll_idata_has_two_well_formed_descriptors` unit test
   (`src/pe.rs:1009`) independently proves: 2 real descriptors + a
   fully-zero 20-byte null terminator, per-DLL ILT==IAT each
   null-terminated, hint/name `<0u16><name><NUL>`, distinct slot RVAs
   (`s_a1 != s_a2 != s_b`), contiguity (`d1_ft == d0_ft + 3*8`), and
   determinism (`emit_idata(...).image == img` on re-run). The
   `win32_msgbox.rs` tests re-parse the descriptor array / ILT thunks
   from the *produced PE bytes* and confirm a real KERNEL32+USER32
   2-descriptor image. `NumberOfSections` stays `4`,
   `NumberOfRvaAndSizes` stays `16`, no `.reloc` — multi-DLL adds no
   section or directory. Correct for the no-ASLR fixed-base writer.

2. **The byte-identical-console regression claim holds under rigorous
   scrutiny and is executably enforced.** (a) `tests/pe_imports.rs`
   pins the **exact** `.idata` bytes (`GOLDEN_IDATA`, a literal
   169-byte array decoded and cross-checked: single KERNEL32
   descriptor + null term, one ILT + one IAT of 7 thunks, six
   hint/names, `KERNEL32.dll\0`) and the **exact** entry stub
   (`GOLDEN_STUB`) for both an import-bearing and a *zero-import*
   console program — the latter (`bare_program_still_emits_full_
   kernel32_idata`) specifically guards the "naive prune would shrink
   `.idata`" failure, and the golden was proven frozen across C1b→C3.
   (b) `used_dlls` always includes `STUB_DLL` (`KERNEL32.dll`) so a
   zero-import program still emits the full six. (c) C1b's
   `console_grouping_is_single_kernel32_group_of_six` pins one
   KERNEL32 group of the six in table order (no pruning). (d) C2's
   `ConsoleMain` arm of `build_text` and the `Subsystem` field are the
   *literal* historical bytes (`git show 553e4b5` confirms the console
   stub block is character-for-character the old code).  (e) C3's
   USER32 entry is dormant: `console_program_has_exactly_one_kernel32_
   descriptor_no_user32` asserts USER32 absent. (f) O1
   `tests/end_to_end.rs` is a true behavioural oracle (`status.code()`
   + captured stdout, `:33-57`), file byte-frozen since pre-Phase-C,
   88/88 green ⇒ observable console behaviour provably unchanged. The
   argument is identical in form to the Phase-A/B byte-identical proofs
   and is airtight.

3. **The `marshal_args` refactor is provably byte-identical for the
   unit-call path.** Diffing `git show 553e4b5:src/codegen.rs`'s
   `emit_call` body against the current `marshal_args` + `emit_call`:
   the pre-C3 `emit_call` body is, verbatim, `marshal_args`'s body
   (lines `let base = …` through `for _ in &slots { self.free_tmp() }`)
   followed by `self.emit(&[0xE8]); let at = self.here();
   self.emit(&[0,0,0,0]); self.calls.push(CallSite{at, callee:
   callee.to_string()})`. The new `emit_call` (`src/codegen.rs:1905`)
   calls `marshal_args(callee, lead, args, ptys_override)?` then emits
   that **exact same** `0xE8`/4-zero/`CallSite` tail. The only textual
   change inside the marshalling body is `callee → key` at two
   signature/default lookups (`self.sigs.funcs.get(key)`,
   `self.sigs.defaults.get(key)`), and `emit_call` passes `callee` as
   `key`, so every lookup, every `emit`, the `alloc_tmp`/`store_tmp`/
   `free_tmp` order, and the `max_stack_args` fold are byte-for-byte
   identical for any unit call. This is the same algebraic-equivalence
   proof class as Phase A's prologue proof; combined with the frozen O1
   88 + the structural goldens it is *sufficient* evidence (the O1
   suite executes real programs whose every byte of `.text` is
   exercised; a marshalling drift would change `.text` and fail e2e or
   the stub golden). `emit_indirect_call` was **not** touched by C3
   (`git diff 553e4b5 daa3f9f -- src/codegen.rs` shows only a pre-
   existing call-site context line), so the sibling correctness witness
   is unperturbed.

4. **`emit_win32_call` gets the Win64 ABI right for `MessageBoxA`.**
   `emit_win32_call(name, args)` (`src/codegen.rs:1928`) calls
   `marshal_args(name, None, args, None)` then
   `emit_riprel(&[0xFF,0x15], RipRef::Import(name))`. With `lead=None`
   ⇒ `base=0`; an import has no `sigs.funcs` entry and
   `ptys_override=None` ⇒ `ptys=None` ⇒ no defaults, no by-ref (every
   arg via `gen_expr`). For MessageBoxA's 4 args: `total = 4`, **not**
   `> 4` ⇒ `max_stack_args` untouched (correct: 4 args all in
   registers `rcx/rdx/r8/r9` via `ARG_LOAD[0..4]`). The 32-byte shadow
   space is reserved in the *caller's* frame (`frame_fixed =
   vars_bytes + ntemps*8 + 32`, `src/codegen.rs:517`); RSP is constant
   from the prologue (the only `push` in codegen is `0x55` push rbp —
   Phase A invariant, still true), so `[rsp+0..32]` is a valid shadow
   for the callee and 16-byte alignment holds (`frame = (… + 15) &
   !15`; OS entry rsp%16==8, push rbp→0, sub rsp,frame→0, the indirect
   `call` pushes ret → callee sees rsp%16==8). A hypothetical >4-arg
   Win32 call (e.g. `CreateWindowExA`) would correctly take the
   `total > 4` path and write `[rsp+0x20+8*(ri-4)]` — the proven
   Phase-A stack-arg ABI, now shared. `RipRef::Import` resolves to the
   symbol's IAT slot via `iat_slot` (`src/pe.rs:404-408`); identical
   shape to the already-proven `WriteFile`/`HeapAlloc` calls.

5. **C2's `hInstance = IMAGE_BASE` is sound and proven end-to-end.**
   `IMAGE_BASE = 0x1_4000_0000` (`src/pe.rs:31`), `b.u64(IMAGE_BASE)`
   as `ImageBase`, `DllCharacteristics = 0` (`src/pe.rs:740`: no
   DYNAMIC_BASE/ASLR), no `.reloc`, `NumberOfSections=4`. An EXE's
   `HMODULE` *is* its load base, and with a fixed `ImageBase` + no
   relocation directory + no `DYNAMIC_BASE` the loader always maps at
   `0x140000000`, so `mov rcx, IMAGE_BASE` (imm64) is the true module
   handle — the same fact `ptr_str` (`IMAGE_BASE + str_rva`,
   `src/pe.rs:368`) and the vtable image already exploit; internally
   consistent. `tests/winmain.rs::winmain_program_runs_and_returns_
   its_constant` **launches the generated subsystem-2 PE on the real
   Windows loader** and asserts exit code == 7 — the strongest possible
   proof: the OS accepts the GUI PE, the stub's 4-arg marshalling +
   `sub rsp,0x28` alignment + `call WinMain` + `mov ecx,eax; call
   [rip+ExitProcess]` all work. `both_main_and_winmain_is_a_clean_
   error` pins the ambiguity hard-error (message names both); the
   neither-entry path is the unchanged `no 'main' function defined`
   error. Subsystem plumbing is `match module.entry` → 3/2; console is
   the literal `3`.

6. **The intrinsic `<windows.h>` is LLP64-correct, scope-disciplined,
   and does not perturb non-windows.h includes.** `WINDOWS_H`
   (`src/pp.rs`) declares opaque handles as `void*` (8), `LPSTR=char*`,
   `LPCSTR=const char*` (parser treats `const` as a no-op qualifier so
   it decays to `char*` exactly as a real header would),
   `WPARAM=unsigned __int64`, `LPARAM=LRESULT=__int64` — all 8 bytes at
   Win64. Probe 1 **empirically confirms** the sizes
   (`WPARAM/LPARAM/LRESULT/HWND/HINSTANCE == 8`, `DWORD/UINT/BOOL ==
   4`) — `long` is correctly *not* used (LLP64 trap avoided; HLD risk
   #4 mitigated in fact). `DWORD=unsigned int` (not the HLD's
   `unsigned long`, but both are 4 at Win64 and `unsigned int` is
   unambiguous — an improvement). Resolution is gated `if system &&
   name == "windows.h"` *before* the `KNOWN` list with an early return
   (`src/pp.rs:91-94`), so other system headers and quoted
   `#include "windows.h"` (Probe 4: reads disk, `system==false`) are
   unaffected. No `MSG`/`WNDCLASS`/`RECT` (correctly deferred to Phase
   D). `MessageBoxA` needs no declaration (recognised by name in
   codegen, libc-style). The empty `WINAPI`/`CALLBACK`/`WINAPIV` is
   correct for the single Win64 ABI (no `@N` decoration in x64).

7. **`is_win32_import` is the exact structural mirror of `is_builtin`,
   single-source-of-truth, with the correct override precedent.**
   `src/codegen.rs:1680-1684` is `crate::pe::is_win32_import(name) &&
   !self.sigs.funcs.contains_key(name) &&
   !self.sigs.overloads.contains_key(name)` — character-identical in
   shape to `is_builtin` (`:1669-1673`). `pe::is_win32_import`
   (`src/pe.rs`) is the single table predicate shared between codegen
   (recognition) and the `.idata` scan (symbol→DLL) so the two can
   never disagree. `gen_call` routes it (`src/codegen.rs:1575`) after
   io/libc/overload/fn-ptr and before the default unit-call — exactly
   the HLD's specified order. Probe 3 confirms a user-defined
   `MessageBoxA` falls through (user wins). Unknown-import is a hard
   `CodegenError` ("import 'X' has no known DLL", `src/pe.rs:137`),
   with a second defense-in-depth error in `build_text`
   (`src/pe.rs:405-407`); never silently wrong.

8. **Determinism is fully preserved (no HashMap iteration into emitted
   bytes).** `used_dlls`/`used_symbol`/`grouped_imports` iterate
   `WIN32_IMPORTS` (a `const &[(&str,&str)]`, fixed order) and
   `module.funcs` (a `Vec`, source order); `emit_idata` iterates the
   ordered `groups`/`g.symbols` Vecs. `iat_slot: HashMap<String,u32>`
   is built by iterating those ordered groups and is **only ever
   `.get()`'d** in `build_text` — never iterated to produce bytes.
   `func_offsets`/`build_text` use the length-only cursor with
   `stub_len(module.entry)`. `idata_is_deterministic_across_compiles`
   plus the `multi_dll` test's re-run equality lock this. Same standard
   as the Phase-A/B determinism proofs.

9. **Tests are oracle-grade and honest about scope.** `winmain.rs`
   runs the GUI PE on the real loader (exit-code oracle); `pe_imports.rs`
   is a true byte-for-byte golden incl. the zero-import edge;
   `win32_msgbox.rs` re-parses the import directory from the produced
   bytes (the "rigorous half" the HLD promised) and explicitly,
   verbatim documents why the live MessageBoxA launch is deferred to
   C4/O6 (modal/blocking) — a documented deferral, not a silent gap.
   The C1b unit tests drive the multi-DLL path with a *synthetic*
   2-DLL group (deliberately not USER32, which is C3) — correct TDD
   sequencing.

### MINOR

- **MINOR-1 — The "B-2 backlog closed" claim is inaccurate;
  `emit_indirect_call` still duplicates the stack-arg-store sequence
  B-2 exists to de-duplicate.** The C3 commit message ("emit_call's
  arg-marshalling tail extracted to a shared `marshal_args` … —
  incidentally closes backlog B-2"), `wrk_journals/2026.05.18 - JRN -
  Goal loop progress.md:89`, and `… - PLAN - Goal loop charter.md:85`
  all state C3 closes B-2. But B-2 is defined in `wrk_journals/
  2026.05.17 - JRN - Roadmap to OWL.md:197` as: *"DRY the identical
  stack-arg store in `emit_call` **vs `emit_indirect_call`** into one
  `emit_arg_into_slot` … (guards against silent divergence)"*. C3
  extracted `marshal_args` shared between `emit_call` and the **new**
  `emit_win32_call` — it did **not** touch `emit_indirect_call`, which
  still contains a verbatim copy of the `i<4 ARG_LOAD[i]` /
  `[rsp+0x20+8*(i-4)]` stack-store sequence (`src/codegen.rs:1647-1656`,
  unchanged) that is byte-identical to the one now in `marshal_args`
  (`src/codegen.rs:1999-2014`). The exact silent-divergence B-2 guards
  against (`emit_call` and `emit_indirect_call` drifting under a future
  ABI change) is therefore **not** closed — and is arguably slightly
  worse, since the unit-call sequence now lives in `marshal_args` while
  `emit_indirect_call`'s lives inline, so an ABI tweak to `marshal_args`
  would fix the unit + import paths but still silently miss the
  indirect path. This is a **tracking-accuracy defect, not a code
  defect** (the duplicated code is correct and tested: calling 11/11).
  Note `emit_indirect_call` uses `i` directly as the Win64 arg index
  (no `lead`/`base`) whereas `marshal_args` uses `base + i`, so a
  literal extraction is mildly non-trivial — which is presumably why it
  was left — but then **B-2 must remain OPEN**, not be marked closed.
  Recommended: correct the journal/charter/commit-narrative to "C3
  DRY'd `emit_call`↔`emit_win32_call`; B-2 (`emit_indirect_call`
  divergence) remains open", or actually fold `emit_indirect_call` onto
  `marshal_args` (parameterising the arg-index base) and then close
  B-2 truthfully. Either is acceptable; silently leaving B-2 "closed"
  while the divergence persists defeats the backlog item's purpose.

- **MINOR-2 — No committed `sizeof` ABI-lock test for the intrinsic
  `<windows.h>` types, though the HLD's C3 TDD plan explicitly
  required one.** HLD line 459 ("C3 RED→GREEN … Assert `WPARAM`/
  `LPARAM` size 8 and `HWND` size 8 via a tiny `sizeof` program (Win64
  ABI lock)") and HLD risk #4's mitigation ("the C3 `sizeof` tests pin
  `WPARAM/LPARAM/LRESULT/HWND == 8`") both call for an executable size
  lock. `tests/win32_msgbox.rs` proves the types *parse and compile*
  and round-trips `(int)lr`/`(int)d`/`(int)b`, but **no committed test
  asserts the 8-byte/4-byte sizes**. The sizes are correct *by
  construction* (sourced from `__int64`/`void*`, which the parser
  already sizes at 8 — Probe 1 confirms empirically), so this is not a
  current correctness defect. But the dedicated oracle the HLD promised
  as the mitigation for risk #4 (a careless future `WINDOWS_H` edit
  changing `__int64`→`long`, silently making `LPARAM` 32-bit) is
  **absent** — and no other committed test would catch that regression
  (it would still parse and compile). Recommended: add the ~5-line
  `sizeof` regression (Probe 1 is a ready template) so the LLP64
  contract is locked, matching the HLD's own TDD plan.

### NIT

- **NIT-1 — `emit_idata`'s `for (gi, _g) in groups.iter().enumerate()`
  loops bind an unused `_g`.** `src/pe.rs` (the descriptor / ILT / IAT
  emission loops) iterate `groups.iter().enumerate()` but only use
  `gi`; `for gi in 0..groups.len()` would be marginally cleaner. Clippy
  is clean (the `_g` prefix suppresses the warning) and the intent is
  readable; purely cosmetic, no action needed.

- **NIT-2 — `used_dlls` performs an O(funcs·riprefs·table) validation
  scan and then `used_symbol` re-scans per DLL.** `used_dlls`
  (`src/pe.rs:131`) scans all riprefs for the unknown-import check,
  then the per-DLL loop calls `used_symbol` (another full rip-ref scan)
  per table DLL. For Phase-C program sizes (one or two DLLs, a handful
  of imports) this is trivially cheap and the determinism/clarity is
  worth it; noting only that if `WIN32_IMPORTS` grows to the full
  Phase-D USER32/GDI32 set this becomes O(DLLs · funcs · riprefs) —
  fold the membership into the single validation pass when Phase D
  expands the table. No action for Phase C.

- **NIT-3 — `console_grouping_is_single_kernel32_group_of_six` hard-
  codes the six symbol names.** `src/pe.rs:1100`-ish asserts
  `groups[0].symbols == vec!["ExitProcess", … "HeapFree"]`. This is
  the *intended* lock (it pins the byte-identical contract), correctly
  in-style with the golden; called out as reviewed-and-fine, not a
  defect — only noting that the same six names are now asserted in two
  places (here and implicitly via `GOLDEN_IDATA`), which is acceptable
  redundancy for a load-bearing invariant.

## Outstanding risks / notes for Arthur

1. **No BLOCKER/MAJOR — Phase C C1a–C3 is solid.** The PE/import-
   directory correctness (the HLD's "highest-risk change"), the
   byte-identical-console invariant, the `marshal_args` refactor, the
   GUI stub, and the intrinsic header are all correct and verified
   against every ground-truth oracle plus targeted probes.

2. **MINOR-1 is the one finding with real teeth and should be actioned
   in Phase C.** Not because the code is wrong (it is correct and
   tested) but because a backlog item that exists *specifically to
   prevent silent ABI divergence* is being reported as closed while
   the divergence it guards persists in `emit_indirect_call`. The
   cheapest honest fix is a one-line correction to the
   journal/charter/backlog (re-open B-2, re-scope the C3 narrative to
   "DRY'd emit_call↔emit_win32_call only"). Folding
   `emit_indirect_call` onto `marshal_args` is the thorough fix but is
   a separable change (mildly non-trivial: the arg-index `base`
   differs) and per house style ("smallest change") may legitimately
   stay backlog — *as long as it is tracked as open*.

3. **MINOR-2: the HLD-promised `sizeof` ABI lock is missing.** The
   types are correct today (empirically verified) but the regression
   tripwire for the LLP64 trap (HLD risk #4) does not exist in the
   committed suite. Adding it is ~5 lines and matches the HLD's own
   C3 TDD plan; recommended before Phase D grows `WINDOWS_H`.

4. **Documented deferrals are honest and explicit, not silent bugs.**
   `lpCmdLine = NULL` (HLD lines 240/504, scratchpad line 200), no
   real `GetCommandLineA`/argv, no `atexit`, no global ctors/dtors
   (HLD lines 254-255/503-504: "the GUI stub is the minimal CRT —
   hInstance + cmdshow + call + exit") are all explicitly recorded as
   Phase-D deferrals with rationale. C4 (O6 GUI liveness) and C5
   (optional B-4 C++ harness) are correctly out of this review's
   scope and tracked as next. The MessageBoxA live-launch deferral to
   C4/O6 is verbatim-documented in `win32_msgbox.rs`. None of these is
   a silent gap.

5. **O6 (C4) will carry the only live multi-DLL loader proof.** C3 is
   structural-only for MessageBoxA (correctly — modal/blocking).
   `tests/winmain.rs` already proves a subsystem-2 PE *loads and runs*
   on the real OS, but the 2-DLL (KERNEL32+USER32) image is only
   *structurally* validated until O6 actually launches it. This is the
   HLD's acknowledged, honest position (O6 is the liveness tripwire);
   noting it so the C4 review treats "a 2-descriptor PE the real
