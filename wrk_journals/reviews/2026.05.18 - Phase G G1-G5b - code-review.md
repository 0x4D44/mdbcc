## Cross-cutting observations

1. **The brc32 differential is real, exercised, byte-exact, and the chief Phase-G oracle.** `wrk_tools/BCC55/Bin/brc32.exe` (5.40, 69 KB, present) is invoked via `tests/rc_res.rs::Brc::compile` for every corpus entry; mismatch panics with a hex diff. This is the strongest Phase G safety net and it does what the HLD promised — verified by running the suite. **However**, the implementation has two real divergences from brc32 that the corpus doesn't exercise (see MAJOR-1, MAJOR-2). The "all 26 byte-exact" claim is true only over the chosen fixtures, which omit MF_GRAYED-style flags and DIALOGEX.
2. **Discipline of structural-then-runtime is faithfully honoured.** Each runtime gui test (`g3_runtime`, `g4_menu_runtime_loads_menu_from_rsrc`, `prog_g5_dialog_displays_and_dismisses`) has a sibling structural test that runs unconditionally and headless-safely (asserts subsystem, imports, `.rsrc` directory entries). The runtime test self-skips loudly if the desktop is headless / spawn fails / FindWindow misses. This mirrors Phase D5/E4 precedent exactly. The PROG_G5_DIALOG dismissal contract (RAII `ProcHandle::drop` watchdog + bounded `FindWindowA` poll + `Wait(5s)` post-`PostMessageA`) is the right model and the anti-hang discipline is preserved (re-read carefully — the watchdog is acquired *before* spawn-and-forget at line 3471–3479, so a child that crashes pre-window-creation triggers the `proc.exit_code() != STILL_ACTIVE` branch with a useful panic message).
3. **PE `.rsrc` two-offset-conventions trap is correctly handled.** `emit_rsrc` (`src/pe.rs:803-914`) clearly distinguishes section-relative offsets (`OffsetToData` in `IMAGE_RESOURCE_DIRECTORY_ENTRY`) from RVAs (`OffsetToData` in `IMAGE_RESOURCE_DATA_ENTRY`). `debug_assert_eq!` runs at each tier confirming the cursor matches the pre-computed offset. The hand-rolled byte oracle (`tests/pe_rsrc.rs::build_rsrc_byte_exact_for_one_entry_hi`) pins every byte for a known small input. Solid.
4. **WIN32_IMPORTS grouping is per-DLL not per-symbol.** `pe.rs:283-288` emits **every** `WIN32_IMPORTS` row whose DLL is used. So any program touching USER32 (e.g. just `MessageBoxA`) gets `LoadStringA`, `LoadMenuA`, `LoadAcceleratorsA`, `TranslateAcceleratorA`, `DialogBoxParamA`, `EndDialog` in `.idata` too — even when the source never calls them. I verified this empirically with a probe (`MessageBoxA`-only program; all six G3/G4/G5a USER32 symbols appear in the PE bytes). **The HLD/source comments describe this as "dormant for any program that does not reference them" which is misleading — they're dormant only for *console* programs that touch no USER32**. The `tests/pe_imports.rs` console golden lock is the only safety net; per-DLL grouping is documented at `src/pe.rs:272-276` as deliberate. Not a bug; a doc inaccuracy and source of `.idata` growth no GUI-side test catches. See MINOR-2.
5. **The "leave-it-green" O1 invariant is real.** `tests/pe_rsrc.rs::no_rc_pe_is_byte_identical_to_legacy_compile_to_pe` asserts the literal bytes of `compile_to_pe(src)` equal `compile_to_pe_with_rc(src, ..., None)`. Section count stays 4, `DataDirectory[2]==0`, no `.rsrc` header. The double-gate is correct: `rc_unit.map(...).unwrap_or_default()` covers `None`; `!rsrc_bytes.is_empty()` covers `Some(empty_unit)`. The 88-program e2e corpus is byte-identical end-to-end (mechanically — none of those TUs have a `.rc` to autodetect).
6. **Parser is generally lenient where brc32 is lenient (commas optional, case-insensitive keywords) and strict where brc32 fails (missing END, out-of-range ids, non-integer where integer expected).** Diagnostics include line/col and use the C-parser's `expected X, found Y` shape. This is good house style. **However**, the lenience extends to unknown identifiers in trailing-flag positions, which silently swallows MF_GRAYED / VK_F1-on-a-MENUITEM / etc. with no warning — see MAJOR-1.

### MAJOR (fix before close, doesn't block roadmap)

#### MAJOR-1 — `MENUITEM` and `POPUP` silently swallow trailing MF_* flags (e.g. `GRAYED`); writer emits flags=0, brc32 emits 0x0001 et al.

**File**: `src/rc/parser.rs:382-400` (`parse_optional_menuitem_flags` — returns 0 always; consumes any `Ident(_)` after a comma).

**Symptom**: empirically reproducible in two minutes. I ran:

```rc
100 MENU
BEGIN
  MENUITEM "Test", 200, GRAYED
END
```

- **mdbcc** emits the MENUITEM with flags=`0x0080` (just MF_END).
- **brc32 5.40** (verified by running `wrk_tools/BCC55/Bin/brc32.exe -r -foout.res test.rc`) emits flags=`0x0081` (MF_GRAYED=0x01 | MF_END=0x80).

The byte divergence: at `.res` offset 0x40 mdbcc writes `80 00`; brc32 writes `81 00`. The byte-exact differential corpus doesn't catch this because no corpus entry uses flag-bearing menuitems — the comment at `src/rc/parser.rs:344-347` explicitly acknowledges "the writer does not consume them yet (kept here so flag-tolerant sources parse cleanly; differential-equivalent to brc32's ignore-and-warn behaviour for flags it doesn't model)" — but that comment is wrong: brc32 does NOT ignore; it sets the flag bit. Runtime symptom: a user writes `MENUITEM "File", 200, GRAYED, INACTIVE`, expects the item to render grayed/inactive at runtime, gets a fully active item. The same defect applies to `POPUP "Help", GRAYED` (also parses `parse_optional_menuitem_flags`).

This is the exact failure mode Phase F's review caught as MAJOR-1 (silent-wrong int↔FP arg conversion); the symptom matches the "never silently wrong" central discipline being violated. The runtime never produces an error message; the byte diff is mechanical and visible only with an oracle the test suite doesn't exercise.

**Fix sketch** (~20 lines):

1. Recognise the MF_* flag keywords (`GRAYED`/`INACTIVE`/`CHECKED`/`MENUBARBREAK`/`MENUBREAK`/`HELP`) in `src/rc/lexer.rs::keyword_lookup` (matches the case-insensitive house style).
2. Change `parse_optional_menuitem_flags` to switch on those keywords and OR the appropriate MF_* bit into a `u16`, returning that.
3. The writer's `write_menu_items` already accepts a `flags` field on each `MenuItem::Item { flags, .. }` and OR's it with MF_END — so the writer is ready to consume the bits; the parser is the only site that needs to change.
4. Add a brc32-differential fixture under `tests/corpus/rc/menu_grayed.rc` exercising MF_GRAYED + MF_INACTIVE and a fixture covering POPUP with a flag.

The strictly-house-style alternative is to **reject unknown identifiers loudly** ("unsupported MENUITEM flag `GRAYED`"); v1 can defer setting the bit but should not silently drop it. Phase F's REX.W deferral in `convert` chose the strict-error path when the encoding was missing — the same precedent applies here.

**Severity rationale**: I rate this MAJOR (not BLOCKER) because (a) no existing test fails — there's no in-tree user affected; (b) the fix is mechanical and well-localised; (c) the writer side is ready for the bits. But it cannot be a MINOR because the primary user-visible symptom is silent semantic divergence from the third-party oracle Phase G is built around, on a syntactic form (`MENUITEM "File", 200, GRAYED`) that real `.rc` files commonly use. The byte-exact brc32 differential — the *central Phase G oracle* — is bypassed by the missing fixture and would catch the bug immediately if added.

#### MAJOR-2 — `DIALOGEX` is accepted by the parser, recorded as `is_ex=true`, and then silently emitted as a classic DLGTEMPLATE by the writer. HLD Risk 2 says "Parser errors loudly … never silently wrong."

**Files**: `src/rc/parser.rs:558-578` (parser accepts both `DIALOG` and `DIALOGEX` and records the difference on the AST); `src/rc/res.rs:386-427` (writer ignores `dlg.is_ex` and emits the classic 18-byte-header form unconditionally); `src/rc/mod.rs:191-196` (doc claims "writer rejects this — G-future-4"); `src/rc/res.rs:379-385` (doc claims "DIALOGEX is rejected at the writer boundary").

**Symptom**: empirically reproducible. I built and ran:

```rc
100 DIALOGEX 0, 0, 100, 50
BEGIN
END
```

The `parse()` call returns `Ok(RcUnit { ... DialogResource { is_ex: true, ... } })`. The `write_res()` call returns a `.res` whose DIALOG payload starts with `00 00 88 80` (= style 0x80880000) — i.e. the **classic DLGTEMPLATE first-u32 layout** (style), not the DLGTEMPLATEEX first-u32 layout (`0x0001FFFF` = signature `dlgVer=1` | `signature=0xFFFF`). The grep for any code that consults `is_ex`:

```
$ grep -rn "is_ex" src/
src/rc/mod.rs:195:    pub is_ex: bool,
src/rc/parser.rs:561:        let is_ex = match self.peek_kind() {
src/rc/parser.rs:697:                        is_ex,
```

Three sites: the AST field, the parser setting it, and the parser storing it. **Zero consumers**. The doc comments at `src/rc/mod.rs:192-195`, `src/rc/mod.rs:53`, `src/rc/res.rs:379-385`, and HLD Risk 2 all claim the writer rejects this — they are uniformly wrong about reality. The only test that touches it (`tests/rc_parse.rs::g5a_parse_dialogex_records_is_ex_flag`) asserts the flag is `true` on the AST, but no test asserts the writer rejects (nor that a stricter caller rejects).

Runtime symptom: a user writes a modern `.rc` with `DIALOGEX` (which is the common form post-2002), expecting DLGTEMPLATEEX semantics — DPI awareness via `dlgVer=1`, per-control `dwHelpID`, etc. mdbcc silently emits classic DLGTEMPLATE bytes. The Windows loader will accept the classic form and render a working dialog, so the user sees no immediate error — but any DLGTEMPLATEEX-only behaviour (extended help, per-control help ids) is silently dropped. This matches the "silent-wrong" failure mode the HLD explicitly committed to preventing.

**Fix sketch** (3 lines): at the top of `write_dialog_bytes` (`src/rc/res.rs:386`), add:

```rust
pub(crate) fn write_dialog_bytes(dlg: &DialogResource) -> Result<Vec<u8>, RcError> {
    if dlg.is_ex {
        return Err(RcError {
            message: "DIALOGEX (DLGTEMPLATEEX) is not supported in v1 — \
                      use DIALOG (classic DLGTEMPLATE) instead (G-future-4)".into(),
            line: 0, col: 0, // or thread through the source position
        });
    }
    // ... existing body
}
```

Propagate the `Result` up through `collect_dialogs` and the PE writer. (Alternatively, reject at parse time in `parse_dialog` — the HLD's preferred form, "Parser errors loudly". That's cleaner — drop the `is_ex` field from the AST entirely.) Then add a `tests/rc_parse.rs::g5a_dialogex_is_rejected` test asserting the error. The current `g5a_parse_dialogex_records_is_ex_flag` test goes away.

**Severity rationale**: MAJOR (not BLOCKER) for the same reasons as MAJOR-1: no existing test or user trips it; the fix is well-localised; the HLD already specifies the right design. But cannot be a MINOR — the documented contract ("never silently wrong") is broken in a way that will silently corrupt any future user's DIALOGEX-bearing `.rc`.

### MINOR (defer to backlog acceptable)

#### MINOR-1 — `.res` type-internal order claim "MENU(4) → DIALOG(5) → ACCEL(9) → STRINGTABLE(6)" is implemented but never byte-tested with all four types simultaneously

**File**: `src/rc/res.rs:104-173` (the writer hardcodes this ordering, with a folklore-busting comment about ACCEL preceding STRINGTABLE despite the descending-ordinal appearance); `tests/corpus/rc/` (no fixture combines all four resource types).

The closest coverage is `g5a_dialog_and_stringtable_coexist` (5→6 only) and `g4_menu_and_stringtable_coexist` (4→6 only). The non-obvious 9-before-6 part of the order — the entire "folklore-busting" claim — is asserted only in code comments and journal entries, never in a byte-exact differential against brc32. A future refactor that re-orders the writer's per-type loops would not trip any test.

**Fix sketch**: add a 5-line `tests/corpus/rc/all_four_types.rc` (one MENU, one DIALOG, one ACCEL, one STRINGTABLE) and a `g5a_all_four_types_emit_in_brc32_order` test in `tests/rc_res.rs` asserting the byte-exact diff. The brc32 oracle is already wired up — adding one fixture is trivial.

#### MINOR-2 — `WIN32_IMPORTS` per-DLL grouping means every G3/G4/G5a USER32 symbol is added to every existing GUI program's `.idata`; no test catches the drift

**File**: `src/pe.rs:277-290` (`grouped_imports`; per-DLL, not per-symbol). Comments at `src/pe.rs:153-160`, `:163-170`, `:174-181` say "USER32 is only emitted when used" / "dormant for any program that does not reference them" — these are misleading; "dormant" applies only to *console* programs that touch no USER32 at all.

Empirically: a `MessageBoxA`-only test program now contains `LoadStringA`, `LoadMenuA`, `LoadAcceleratorsA`, `TranslateAcceleratorA`, `DialogBoxParamA`, `EndDialog` strings in its PE (I checked via a `pe.windows(name.as_bytes()).any(|w| w == name)` probe). Every Phase D/E test program's `.idata` has grown silently with each Phase G increment. The `tests/pe_imports.rs` console golden lock catches **only** the KERNEL32-only case (`PROG_FULL` / `PROG_BARE`); there is no GUI golden lock.

**Fix sketch**: either (a) implement per-symbol pruning in `grouped_imports` (defer per the deliberate-non-optimization stance) or (b) add a `tests/pe_imports.rs::user32_full_set_byte_identical` lock that pins the full USER32 sub-image for a one-`MessageBoxA` program. Option (b) is cheaper and matches existing pattern.

#### MINOR-3 — Hand-golden fallback in `tests/rc_res.rs::compare` is dead code when brc32 is present in CI; hand-goldens could drift from brc32 unnoticed

**File**: `tests/rc_res.rs:101-119`. `compare()` always uses `brc.compile(oracle_src)` when `Brc::discover()` returns `Some`. In our sandbox brc32 is always present (`wrk_tools/BCC55/Bin/brc32.exe`), so the hand-goldens are only checked when running outside the sandbox. A future PR that bumps a constant in the writer could silently break the hand-golden without any CI test failing.

**Fix sketch**: assert that, when brc32 is present, the hand-golden matches brc32 *too* — e.g. add a `debug_assert_eq!(hand_golden, expected)` inside the `Some(brc)` arm. Cheap and prevents drift. Alternatively, treat the hand-goldens as documentation-only (delete them, accept brc32-required-in-CI).

#### MINOR-4 — `tests/rc_res.rs::Brc::compile` leaks the temp dir on panic or read error

**File**: `tests/rc_res.rs:56-79`. Cleanup at line 77 only runs on the happy path. A failing `assert!(status.success())` at line 71 or a failing `std::fs::read(&res_path)` at line 76 leaves the temp dir behind. Test discipline issue (the OS sweeps `temp_dir` eventually); add an RAII `Drop` guard on `dir` to remove it unconditionally. Five-line fix.

#### MINOR-5 — Sibling-`.rc` detection in `src/main.rs` has untested edge cases: input is a directory, sibling-rc file is unreadable, sibling-rc has UTF-8 BOM, input has no extension

**File**: `src/main.rs:85-95`. The path computation `Path::new(&path).with_extension("rc")` has several quirks I verified empirically:
- `bcc foo` (no extension) ⇒ looks for `foo.rc` — probably intended.
- `bcc foo.bar.c` ⇒ looks for `foo.bar.rc` — works as expected.
- `bcc .bashrc` ⇒ looks for `.bashrc.rc` (dotfile + `.rc`) — silly but harmless.
- `bcc foo.rc` ⇒ looks for `foo.rc` (same as input!) — would try to parse the input *as both* C and `.rc`, the C parse fails first.
- **Sibling `.rc` has UTF-8 BOM** ⇒ rc parser fails with `unexpected character 'ï'` (verified — diagnostic is poor but failure is loud).
- **Sibling `.rc` IS a directory** ⇒ `read_to_string` returns `Err`, treated as `None` (no sibling). Silent.
- **Sibling `.rc` is unreadable (permissions)** ⇒ same: silent no-rc.

Cases 6 and 7 are silent — a user who created `foo.rc` but accidentally as a directory (e.g. `mkdir foo.rc` then `touch foo.rc/file.rc`) would silently get an `.exe` with no resources. There's no CLI integration test for any of these.

**Fix sketch**: differentiate between "no sibling .rc exists" (silent no-op) and "sibling .rc exists but couldn't be read" (loud error). `match std::fs::metadata(&rc_path) { Ok(m) if m.is_file() => try_to_parse, Ok(_) => warn-and-bail-loud, Err(NotFound) => silent_None, Err(other) => loud_error }`. Add at least one CLI integration test (drive `main` via `std::process::Command`).

#### MINOR-6 — `parse_i16_with_label` silently wraps `u16` values > 32767 to negative `i16` via `as i16` cast; comment-only documentation, no test for the boundary

**File**: `src/rc/parser.rs:964-993`. The lexer doesn't recognise unary `-`, so source `-1` is impossible; the parser accepts the full `u16` range and wraps via `as i16`. A user writing `100 DIALOG 0, 0, 32768, 50` would silently get a dialog with `cx = -32768`. brc32 may or may not behave identically (untested in our corpus). The doc comment at lines 956-963 is honest but the boundary case isn't tested.

**Fix sketch**: either (a) add a brc32-differential fixture asserting the wrap matches brc32, or (b) tighten the parser to reject 32768..=65535 as out-of-range for "DIALOG x/y/cx/cy" (negative dialog coordinates are legitimate so this rules out half the i16 range; less attractive). Recommend (a).

#### MINOR-7 — Bundle math at id boundaries is correct but only one boundary (id=17 → bundle 2) is tested; id=0, id=15, id=65535 untested

**File**: `src/rc/res.rs:648-649` (`bundle_id = (id >> BUNDLE_SHIFT) + 1; slot = id & 0xF`). I verified empirically:
- id=0 → bundle 1, slot 0 (works; tests don't exercise).
- id=15 → bundle 1, slot 15 (works; untested).
- id=16 → bundle 2, slot 0 (works; untested).
- id=65535 → bundle 4096, slot 15 (works; untested). Max bundle is 4096, fits u16.

`stringtable_multibundle.rc` only covers id=1 + id=17 (a single boundary crossing). A subtle off-by-one in the bundle formula would not be caught at the edges. Cheap to add.

**Fix sketch**: append id=0 and id=65535 to an existing fixture, or add a `stringtable_id_boundaries.rc` covering all four.

## Empirical-findings spot-check

I verified three of the 28+ folklore-busting claims journaled across Tick 30/32/33:

1. **"Default DIALOG style = 0x80880000 (WS_POPUP|WS_BORDER|WS_SYSMENU), not WS_POPUP|WS_CAPTION|WS_SYSMENU"** — **VERIFIED**. `tests/rc_parse.rs::g5a_parse_dialog_empty` (line 431-443) asserts `d.style == DIALOG_DEFAULT_STYLE` and `mod.rs:253` defines `DIALOG_DEFAULT_STYLE = 0x8088_0000`. `tests/rc_res.rs::g5a_dialog_empty` (line 651-672) byte-exact diffs the dialog payload starting with `0x80880000` against the brc32 oracle. **Solid.**

2. **"MF_SEPARATOR (0x0800) NOT set by brc32 for `MENUITEM SEPARATOR`"** — **VERIFIED**. `tests/rc_res.rs::g4_menu_with_separator` (line 491-506) hand-codes the separator entry as `flags=0` (or MF_END when last) with id=0 and empty text, then diffs against brc32 via `compare()`. The byte-exact assert proves the writer agrees with brc32, neither sets MF_SEPARATOR=0x0800. **Solid.**

3. **".res resource type order with DIALOG present: MENU(4)→DIALOG(5)→ACCELERATORS(9)→STRINGTABLE(6) (NOT ascending — ACCEL precedes STRINGTABLE)"** — **PARTIALLY VERIFIED, key part NOT tested**. The MENU→STRINGTABLE 4-then-6 order is locked by `g4_menu_and_stringtable_coexist` (line 872). The DIALOG→STRINGTABLE 5-then-6 order is locked by `g5a_dialog_and_stringtable_coexist` (line 832). **But no fixture combines MENU+DIALOG+ACCEL+STRINGTABLE simultaneously**, so the truly folklore-busting part — ACCEL(9) emitted *before* STRINGTABLE(6) despite the descending-ordinal appearance — is never byte-exercised. The implementation is correct (the writer's tier order at `res.rs:115-173` hardcodes MENU→DIALOG→ACCEL→STRINGTABLE), but a refactor that reordered the writer's per-type loops would not trip any test. **This is MINOR-1.**

The other 25+ findings (ACCELERATORS default mem_flags = 0x0030 lacking DISCARDABLE; ^X cooks to `X - 0x40`; brc32's compiled-in default language = 0x0809 en-GB; brc32 OR's WS_CHILD|WS_TABSTOP into explicit per-control style; etc.) are individually tested through dedicated fixtures (e.g. `g4_accel_ascii_ctrl`, `language_default_when_unspecified`, `g5a_dialog_one_pushbutton`'s 0x50010000 assert). The journal-claim-to-fixture coverage is broadly faithful.

## Outstanding risks (post-fix)

Even after MAJOR-1 and MAJOR-2 are addressed, the residual Phase G risks are:

1. **Per-DLL `.idata` grouping means every existing test program imports the Phase G symbols whether it uses them or not** (MINOR-2). No GUI-side byte-identical golden exists; a future change to `WIN32_IMPORTS` could quietly bloat every GUI test's `.idata`. Add `tests/pe_imports.rs::user32_full_set_byte_identical`.
2. **brc32 absence handling is silent (hand-golden fallback)** (MINOR-3). Recommend either making brc32 required (panic when absent) or asserting hand-golden ≡ brc32 when present.
3. **STYLE accepts only numeric u32, not symbolic `WS_POPUP|WS_CAPTION|WS_SYSMENU`** (the G5b judgement call). Currently fails loudly with `expected integer for STYLE, found identifier WS_POPUP` — that's the right house-style behaviour and tested implicitly by PROG_G5_DIALOG choosing to omit STYLE. **Not a finding** — the error message is informative.
4. **DIALOG x/y/cx/cy wraps via `as i16` for values 32768..=65535** (MINOR-6). Boundary fixture would lock the behaviour.
5. **Sibling-.rc edge cases (directory, BOM, permissions)** (MINOR-5). CLI integration test missing.

## Recommendation

**REQUEST-CHANGES.** Phase G is well-engineered overall — the PE `.rsrc` two-offsets trap is correctly handled, the byte-exact differential against brc32 5.40 is real and exercised, the cross-thread dismissal harness for PROG_G5_DIALOG matches Phase D5/E4 precedent, the leave-it-green O1 invariant is preserved end-to-end. The HLD's design is followed in spirit on every increment, and the empirical brc32 oracle has surfaced a remarkable 28+ folklore-busting facts that are now encoded in code.

**However, two MAJOR findings violate the "never silently wrong" central discipline** that the HLD itself commits to (Risk 2 — "Parser errors loudly … never silently wrong"). MAJOR-1 (silent loss of MF_GRAYED / other MENUITEM flags) is the precise analogue of Phase F's MAJOR-1 (silent loss of int→FP arg promotion): a syntactic form real `.rc` files commonly use, a byte-exact divergence the third-party oracle would catch immediately, no test in the corpus to surface it. MAJOR-2 (DIALOGEX silently emits classic DLGTEMPLATE despite documentation everywhere claiming the writer rejects it) is a contract violation hiding behind a comment. Both fixes are small (~5-20 lines each plus one new corpus fixture each) and the brc32 oracle is already wired up to catch them.

Before Phase G is declared done: address MAJOR-1 (MF_GRAYED + brc32-differential fixture) and MAJOR-2 (DIALOGEX rejection at parser-or-writer boundary + test). Either MINOR-1 (all-four-types fixture) or MINOR-2 (GUI `.idata` byte-identical lock) is also worth landing in the apply-feedback increment because both prevent silent regressions in the *next* phase. The other MINORs and NITs can be triaged at leisure.

Once the two MAJORs land green, Phase G is a strong foundation for Phase I (OWL `TDialog`/`TMenu` wrapper classes consuming the `WIN32_IMPORTS` already in place) and a credible demonstration that the brc32-differential discipline scales to the heaviest format-encoding work mdbcc has done since the PE writer itself.
