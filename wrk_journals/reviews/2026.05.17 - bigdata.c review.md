# Review: tests/corpus/portable/bigdata.c

VERDICT: APPROVE-WITH-NITS

Skeptical review of the single-file large-`.data` durability oracle. The
already-green three-way differential (O2 `cl` + O3 `bcc32` 5.5.1 accept+
behaviour + `mdbcc_determinism`) is taken as given and NOT re-litigated.
Scope: silent-oracle-rot durability and latent UB/portability only.

Empirical confirmation (compiled `bigdata.c` via `mdbcc::compile_to_pe`,
parsed the section table; throwaway probe deleted, no git mutation, no
slow suite run):

| section | VirtualSize | Characteristics | meaning |
|---------|-------------|-----------------|---------|
| .text   | 0x410       | 0x60000020      | code |
| .idata  | 0xF9        | 0xC0000040      | printf import |
| .rdata  | 0x12        | 0x40000040      | format string |
| **.data** | **0x299B (10651 B ≈ 10.4 KB)** | **0xC0000040** | **CNT_INITIALIZED_DATA \| R \| W** |

`.data` VirtualSize **0x299B > 0x2000**, RawSize 10752 (bytes physically in
the file image — *not* zero-fill; a `.bss`-style section would carry
`CNT_UNINITIALIZED_DATA 0x80000080`). The blob lands in **initialized**
`.data`, placed after `.rdata`, with monotonically increasing RVAs across 4
sections — the intended "next-section-after-a-big-one" dynamic-layout regime
**is genuinely exercised today**. (Brief's claim #3 confirmed.)

## BLOCKER
_None._

## MAJOR

- **bigdata.c:33-39 + differential.rs:130/201 — Silent-oracle-rot:
  the large-`.data` regime is asserted ONLY transitively via stdout, and the
  blob is constant-foldable, so the regime can silently become vacuous while
  the test stays GREEN.**
  `grep bigdata` over every `*.rs` = **zero hits**. The only consumer is
  `corpus_files("portable")` → `compare(&md,&rf)`, which asserts **stdout
  equality only** (`"blob len=%u sum=%u\n"`). There is **no PE-header /
  VirtualSize oracle** for this file anywhere (`pe_layout.rs` uses a
  *generated* big-`.text` program, not bigdata.c).
  `blob` is a file-scope `static const char[]`, never address-escaped. `main`
  folds every byte into `sum` with a loop whose bound (`blob[i]!=0`) and
  recurrence (`sum*31u + byte & 0xFFFFu`) are **pure functions of compile-time
  constants with no runtime input**. A sufficiently strong optimizer is fully
  entitled to fold the entire loop to `printf(..., 10650u, <constant>)` and
  **dead-strip `blob` from `.data`**, collapsing `.data` back below the old
  ceiling. The printed stdout is **byte-identical** whether or not the array
  physically survives — so a future/stricter `cl`, a future `bcc32`, or (most
  realistically) **mdbcc itself gaining any constant-folding pass** would
  shrink `.data`, keep the differential GREEN, and silently void the very
  regression this file exists to lock. mdbcc is the system under test: the
  moment it learns to fold `sum*31+const`, *its* `.data` shrinks while cl/
  bcc32 stdout is unchanged ⇒ same stdout ⇒ still green ⇒ net no longer
  covers the dynamic-layout bug.
  The file comment's assertion *"neither `cl /O2` nor `bcc32 -O` can
  dead-strip it"* is **false in the general case** — it holds only for the
  *specific current versions* of these toolchains (a weak bcc32 5.5.1
  optimizer, no mdbcc optimizer), which is precisely what GREEN-TODAY cannot
  guarantee for the future. Net judgement: **AT-RISK (latent silent rot, not
  active today).**

  **Minimal hardening (priority order):**
  1. *Strongest & cheapest — assert the regime structurally.* Add a ~10-line
     Rust test (mirroring the existing `pe_layout.rs` pattern): compile
     `bigdata.c` via `compile_to_pe`, parse the `.data` section header, assert
     `VirtualSize > 0x2000` **and** `Characteristics &
     IMAGE_SCN_CNT_INITIALIZED_DATA != 0`. This enforces the property under
     test directly and survives *any* compiler (incl. mdbcc) gaining
     constant-folding. The regime should be asserted via the PE header, not
     inferred from stdout.
  2. *Source-only fallback* (if a structural test is undesired): make the
     consumed value depend on something **not known at compile time** so the
     fold is illegal — e.g. `volatile unsigned int seed = 0u;` read once into
     `sum` before the loop. Defined, fully deterministic (`+0`), keeps it a
     pure stdout oracle, but the opaque `volatile` read blocks the optimizer
     from precomputing the checksum, forcing the array to be read at runtime.
     (Avoid `argc`/`argv` seeding — risks perturbing the deterministic-stdout
     contract.)

  (1) is materially stronger; (2) is acceptable as a lighter touch. Either
  one closes the rot. This is a *latent* risk on a 1-file add-on, hence MAJOR
  (worth fixing) not BLOCKER (today's net is genuinely green and the regime
  *is* exercised by the current toolchains).

## MINOR

- **bigdata.c:13-15 — "Strict C89" is overstated for the string literal.**
  ISO C89 (§5.2.4.1) mandates implementations accept string literals only up
  to **509 characters** and objects up to **32767 bytes**. The blob is a
  **single ~10.6 KB string literal** — ~21× the strict-conformance literal
  minimum. The *object* (~10.6 KB) is comfortably within the 32767-byte limit,
  so object size is fine; it is specifically the **single-literal length**
  that is **not strictly conforming C89** (it relies on cl/bcc32 generously
  exceeding the mandated minimum, which they do). This does **not** affect
  this oracle's purpose — the only consumers are cl, bcc32 5.5.1 and mdbcc,
  all accept it, and the differential is GREEN — but the wording could
  mislead a future reader into treating this as a portable strict-C89
  specimen. Soften, e.g.: *"Targets cl/bcc32/mdbcc — not strict-ISO-C89: the
  single ~10.6 KB string literal exceeds C89's 509-char literal minimum (all
  three target compilers accept it; the object is within C89's 32767-byte
  limit)."* The rest of the strictness list (decls-before-stmts, slash-star
  comments, no C99/long long/stdint/VLA/sizeof/%p/time/rand) **is accurate**.

## NIT
_None._

## PRAISE

- **bigdata.c:34 — `(unsigned int)(unsigned char)blob[i]` is exactly right.**
  The `(unsigned char)` cast deliberately normalises to 0..255 *before*
  integer promotion, so the checksum is **invariant to plain-`char`
  signedness** (which is signed on all three target compilers). This is the
  single most common latent UB in checksum-style corpus code and it is
  correctly defended here.
- **bigdata.c:30-37 — width/overflow-clean by construction.** All arithmetic
  is `unsigned int` (`*31u`, `+...u`) masked `& 0xFFFFu`: defined wrap, result
  independent of `int`/`unsigned` width for any width ≥16 bits. No signed
  overflow, no shift UB, no `int`-width reliance. The brief's premise that
  stdout is genuinely model-independent (32-bit bcc32 vs 64-bit mdbcc) **holds
  on inspection**, not by luck.
- **Sanity all green:** no `// oracle:` skip directive (verified across the
  whole portable corpus); `sum/len/i` all initialised to `0u` before use (no
  uninitialised reads); no input/time/rand (deterministic); `printf` `%u %u`
  matches `unsigned int, unsigned int`; ends `return 0;`.

### Bottom line
The file does what it claims **for today's toolchains** and the regime is
empirically real (`.data` = 0x299B, initialized). It is mergeable as-is. The
one substantive concern is the MAJOR: GREEN-TODAY does not prevent the
large-`.data` regime from silently going vacuous if any consumer (most
plausibly mdbcc itself) gains constant-folding, because the regime is asserted
only via foldable stdout. Recommend the ~10-line structural `.data`-size
assertion (hardening option 1) before relying on this as a *permanent* lock;
absent that, soften the comment's "cannot dead-strip it" / "Strict C89"
claims so the file does not over-promise. None of this blocks the current
green net.

### 1. Hole truly closed? — CLOSED

The test asserts on the **actual produced image bytes**: `exe =
compile_to_pe(src)` (the real pipeline: lexer→pp→parser→codegen→`pe::write_pe`,
verified via `src/compile.rs:62`), then `section(&exe, b".data")` walks the
emitted PE's own section table. No recomputed/expected size, no stdout, for
the structural claim.

Every parsing offset verified against `src/pe.rs` (and cross-checked against
the writer's *own* internal test helper `sections()` at `src/pe.rs:591`,
which uses identical arithmetic):
- `PE_OFF=0x80` == writer `PE_OFF` (`pe.rs:36`); `PE\0\0` at 0x80 (`pe.rs:397`). ✓
- `coff = PE_OFF+4`; `NumberOfSections` is COFF u16 #2 → `coff+2` (Machine u16 first, `pe.rs:398-399`). ✓
- `SIZEOF_OPT=0xF0` == writer `SizeOfOptionalHeader` (`pe.rs:403`); COFF hdr = 20 B → section table at `PE_OFF+4+20+0xF0`. ✓
- `SECT_HDR_LEN=40` == `write_section_header` byte count (8+4+4+4+4+4+4+2+2+4). ✓
- In-header: name `0..8`, VirtualSize `+8` (`pe.rs:491-492`), Characteristics `+36` (final `u32`, `pe.rs:499`). ✓

Offsets are exact for *this* writer — not reading garbage. Asserts the RIGHT
section (`.data`, the one holding the large initialized global) with
`VirtualSize > 0x2000` AND `Characteristics & 0x40`
(IMAGE_SCN_CNT_INITIALIZED_DATA). `.data` is written with `0xC000_0040`
(`pe.rs:460-462`) so the CNT_INITIALIZED_DATA bit is structurally present and
the bit-test has teeth (would fail if the blob were ever routed to a
zero-fill section).

### 2. Teeth + optimizer-proof? — YES

The size is forced **structurally**, not incidentally. Traced the full
routing of `static const char blob[24000] = "..."`:
- Parser: explicit non-zero dimension wins — `maybe_initializer`
  (`parser.rs:1147-1149`) sets `len = if *n==0 {lit+1} else {*n}` ⇒ stays
  `Type::Array(char,24000)`; literal length is irrelevant. `Type::size()`
  = `1*24000` (`ast.rs:61`).
- Codegen: `global_image` (`codegen.rs:307-329`) allocs `vec![0u8; 24000]`,
  copies the 4096-byte literal prefix, leaves 4096..24000 zero-filled — **all
  24000 are real bytes in `GlobalData.bytes`**.
- Writer: non-`ptr_str` global → `build_data` does
  `image.extend_from_slice(&g.bytes)` (`pe.rs:204`); `.data` VirtualSize =
  24000 = 0x5DC0. **~3× margin over the 0x2000 threshold.**

No `.bss`/zero-fill escape hatch exists: the writer emits exactly 4 fixed
sections, `SizeOfUninitializedData = 0` (`pe.rs:412`); trailing zeros are
physically emitted into `.data`'s file image. `const` does NOT route to
`.rdata` — the `Item::Global` path is purely type-driven and ignores the
`const` qualifier; only pointer-to-string-literal globals (`ptr_str`) get the
8-byte-slot treatment, which `blob` is not. So the writer **cannot legally**
place this array in `.bss` or `.rdata`: no false-pass, no false-fail on a
legitimate layout.

Optimizer-proof reasoning: if a future mdbcc/cl/bcc32 constant-folded the
checksum and dead-stripped `blob`, the structural claim rests **solely** on
the parsed `.data` VirtualSize, which would collapse from 0x5DC0 to a few
bytes — the `vsize > 0x2000` assert FAILS immediately, regardless of stdout
staying byte-identical. This is exactly the silent-rot vector the MAJOR
identified, and it is now caught structurally. The foldable checksum/stdout
assertion is present too but is *additive* (proves load+correctness); the
durability claim does not depend on it.

### 3. Can the new test itself rot/flake? — LOW / acceptable

- Determinism: no time/rand/input; `COUNTER`+pid only name the temp exe;
  build is deterministic (`TimeDateStamp=0`, fixed ImageBase, no ASLR). The
  Rust checksum mirror (`pe_layout.rs:190-198`) iterates the identical
  byte sequence (pattern for `i<lit_len`, else 0) with matching
  `wrapping_mul(31).wrapping_add & 0xFFFF` ⇒ exact, not flaky.
- Structural claim does NOT rest on the foldable checksum (verified — the
  `vsize`/`chars` asserts run before and independently of the stdout check).
- Offsets: hard-coded but **correct and self-documenting**; they mirror
  `src/pe.rs` exactly and would only break on a deliberate PE-header redesign
  — at which point the writer's own `pe.rs` tests break in lockstep, so this
  is not silent rot. Acceptable brittleness (coupled to the format under
  test, by design).
- Subset: empirically PASSES — `static const char[24000]="..."` +
  decls-before-stmts `unsigned int` + `while` + `printf("%u %u")` compiles,
  loads, runs, and prints the exact mirrored checksum on mdbcc.
