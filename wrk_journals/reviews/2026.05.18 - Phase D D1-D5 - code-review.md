## Verdict: APPROVE (no BLOCKER, no MAJOR)

Phase D D1–D5 is correct, minimal, faithful to the HLD, and the
central claim — *"mdbcc has built and run a real OWL-based GUI app
end-to-end on modern Windows 11"* — is **executably enforced** by an
exit-code-`0` liveness test that I independently ran here and that
passed deterministically in ~0.19 s alongside nine sibling gui tests.

The architectural decisions vindicated by D5 are honest: the OWL
runtime as an intrinsic-prepended single-TU body (D4 `OWL_RUNTIME_H`)
sidesteps the absence of a linker; the `_OwlHInstance` "global"
trick (a constant-null pointer set imperatively by the first
statement of WinMain) sidesteps the absence of global constructors;
the `GWLP_USERDATA` per-HWND instance map sidesteps the absence of a
file-scope mutable side-table; the static `OwlStaticWndProc` thunk is
a conformant Win64 WNDPROC by construction (one ABI in x64 — Phase A's
4-arg + >4-arg stack ABI gives precisely the signature Windows
requires when it indirectly calls back). Every one of those four
elisions is honest engineering: not workarounds, but design choices
that survive scrutiny.

The console byte-identical invariant — Phase D's central regression
target — **holds**. The committed goldens in
`tests/{pe_imports,pe_layout,end_to_end}.rs` were **not re-blessed**
in any of the six Phase-D commits; an independent
`git log --follow --oneline` shows zero Phase-D entries on those
files. The new `o6_d4_console_program_unchanged_after_owl_runtime`
locks the same invariant structurally for the new `owl/` resolver
branch.

All findings are MINOR/NIT. The strongest is a soundness gap in the
liveness path's failure mode: a silent runtime failure (e.g. a
`RegisterClassExA` that returns 0) would cause `FindWindowA` to
time out and the test to *self-skip rather than fail* — a known
trade-off of any "tripwire" oracle, called out honestly by the HLD,
but worth recording so it cannot be forgotten when D5 is the
milestone marker. Two B-tracked compiler gaps surfaced honestly by
D4 (B-6 `bool` deferral; the TModule virtual dtor matching real OWL)
are deferrals, not silent wrongness.

## Strengths (load-bearing)

### S1. The D3 crux is genuinely well-designed.

The static `OwlStaticWndProc` thunk + `GWLP_USERDATA` instance map +
virtual `WindowProc` dispatch is the load-bearing interlock of Phase D
— and the design is sharp:

- **`GWLP_USERDATA` instead of a side-table** sidesteps the absence
  of global constructors. The HLD §Risks #2 calls this "closed by
  construction" and it is: the only file-scope mutable state the
  runtime touches is `_OwlHInstance` and `_OwlApp`, both **constant-
  null-initialised pointers** that codegen handles via the existing
  `global_image` zero-fill path (`src/codegen.rs:395-417` — Some(e) →
  `const_eval` → `to_le_bytes` for a literal `0`). No runtime ctor
  required.

- **The static thunk is a free function** of signature `LRESULT
  CALLBACK OwlStaticWndProc(HWND, UINT, WPARAM, LPARAM)`. Because
  `CALLBACK` is the empty macro in `<windows.h>` and Win64 has **one**
  ABI, this signature is byte-compatible with what Windows expects
  when it dispatches via `lpfnWndProc`. The HLD §D-c proof is correct
  by construction in x64: there is no `@N` decoration, no stdcall vs.
  cdecl ambiguity.

- **The 12-arg `CreateWindowExA` call** in `TWindow::Create`
  (`src/pp.rs:307-310`) exercises Phase A's >4-arg Win64 stack ABI
  (4 args in `rcx/rdx/r8/r9` + 8 stack slots). The 12th arg
  `lpCreateParams = this` survives the OS call into the WndProc
  intact (the OS just copies it into `CREATESTRUCTA::lpCreateParams`
  in user memory before calling the thunk). The D3 test
  (`o6_d3_thunk_dispatches_via_vtable_to_clean_exit`) is the
  empirical proof: a `MyWindow` stack-allocated in `WinMain` reaches
  its derived `HandleMessage` override across the OS callback edge,
  and posts `WM_QUIT` on `WM_DESTROY` → exit code exactly 0.

- **The `WM_NCCREATE` binding** is correct: pull
  `(TWindow*)CREATESTRUCTA::lpCreateParams` from `LPARAM`, store
  `h` into `self->HWindow`, `SetWindowLongPtrA(h, GWLP_USERDATA,
  (LONG_PTR)self)`. The `WM_NCCREATE` message then falls through to
  the `self != 0` branch and dispatches to `TWindow::WindowProc(
  WM_NCCREATE, ...)`, which falls through to `DefWindowProcA(
  HWindow, msg, w, l)`. `DefWindowProcA` returns nonzero (TRUE) for
  `WM_NCCREATE`, which is what Windows requires to continue window
  creation. Correct.

- **The null-self fallback** (`if (self != 0) ... else return
  DefWindowProcA(h, m, w, l);`) covers pre-WM_NCCREATE messages
  (e.g. `WM_GETMINMAXINFO`) that Windows can deliver before the
  binding. Standard OWL behaviour.

### S2. The OWL_RUNTIME_H itself is minimal and faithful.

`src/pp.rs:215-322` — the 209-line `OWL_RUNTIME_H` body is honest
OWL 2.5 non-template surface, only what hello-OWL needs:

- `TModule { HINSTANCE hInstance; ctor; virtual ~TModule; GetInstance; }`
  — the virtual dtor satisfies mdbcc's "polymorphic-derived-from-
  base-with-data-no-virtuals" guard. The HLD's note that this also
  matches real OWL is accurate.
- `TApplication : public TModule` with `MainWindow`,
  `InitMainWindow`, `SetMainWindow`, `Run`, virtual dtor.
- `TWindow { HWND HWindow; TWindow *Parent; const char *Title; ctor;
  virtual ~TWindow; virtual GetClassName; virtual Create; virtual
  WindowProc; Show; }`.
- `TFrameWindow : public TWindow` — thin v1 specialiser.
- `OwlMain(int, char**)` — declared, expected to be defined by the
  user TU.
- `int WINAPI WinMain(HINSTANCE hI, ...)` — the runtime owns this,
  reads `hI` into `_OwlHInstance`, calls `OwlMain(0, 0)`. Phase-C's
  `Entry::GuiWinMain` detection fires on this definition → subsystem
  2 + the GUI stub is reused verbatim.

The runtime is a single self-contained header guarded with
`_OWL_RUNTIME_INCLUDED` so a user TU may freely `#include
<owl/applicat.h>` AND `<owl/framewin.h>` (canonical Borland idiom)
without redefining classes. The `owl/` prefix gate in
`DefaultResolver::resolve` (`src/pp.rs:385-387`) keeps every byte of
the runtime dormant for non-OWL TUs.

### S3. The watchdog/RAII test infrastructure cannot hang.

Every D2/D3/D5 liveness test reuses C4's `interactive_desktop()` /
`ProcHandle` RAII / `TerminateProcess` watchdog / `skip()` /
`TempExe` machinery verbatim (no duplication). I traced every
failure path:

| Path | Action | Bound |
|---|---|---|
| `compile_to_pe` fails | `panic!` (test fail, no child to clean up) | — |
| `interactive_desktop()` false | `skip()` and return | — |
| `fs::write` to temp fails | `skip()` and return | — |
| `Command::spawn` fails | `skip()` and return | — |
| `OpenProcess` fails | `terminate_child(child)` + `skip()` | `Child::kill` + `Child::wait` |
| `FindWindowA` poll exhausts deadline | `proc.terminate()` + `proc.wait(3000)` + `skip()` | 4 s + 3 s |
| `PostMessageA` fails | `proc.terminate()` + `proc.wait(3000)` + `skip()` | 3 s |
| `proc.wait(5000)` returns false | `proc.terminate()` + `proc.wait(3000)` + `skip()` | 5 s + 3 s |
| Test panics at any point | `ProcHandle::Drop` → if `STILL_ACTIVE` → `terminate()` + `wait(2000)` + `CloseHandle` | 2 s |

Total worst-case per test: well under 20 s. Empirical: **gui suite
total 0.16 s for 10 tests including 4 desktop-gated liveness probes**.
The `std::mem::forget(child)` after `OpenProcess` is correct: the
`std`-owned handle leaks until cargo test exits, but the
`ProcHandle`'s independent handle (via `OpenProcess` with
`PROCESS_TERMINATE | SYNCHRONIZE | PROCESS_QUERY_INFORMATION`) is
RAII-closed on drop, so the child is reliably reaped. The local-drop
order in every live test is correct: `proc` (declared later) drops
first → terminate + wait + close → then `tmp` (declared earlier)
drops → remove file (which is no longer locked because the process
has exited).

### S4. Honest deferrals, tracked.

The journal explicitly notes:

- **B-6**: `bool` keyword is lexed (`Keyword::Bool`) but not
  accepted by `decl_specifiers` as a type. The runtime uses
  `BOOL = int` from `<windows.h>` instead. The HLD did NOT promise
  `bool` as a type; this is a real compiler gap, surfaced honestly
  by D4, deferred with a backlog ID.
- **`TModule` virtual dtor**: this satisfies Phase B's
  "polymorphic-derived-from-base-with-data-no-virtuals" guard and
  *also* matches real OWL. Not a workaround.
- **mdscreensnap golden**: I confirmed by inspecting the local
  `mdscreensnap.exe --help` that it provides capture only — no
  compare/golden infra. The HLD §D-3 itself describes the
  screenshot golden as a "coarse" oracle; exit-code-0 liveness is
  the primary D5 oracle. The deferral is honest.

### S5. Bonus rigour: the structural half of every liveness test runs unconditionally.

`o6_d5_hello_owl_compiles_to_gui_pe`,
`o6_d3_thunk_instance_window_compiles_to_gui_pe`,
`o6_d2_raw_window_compiles_to_gui_pe_importing_user32_set`,

### BLOCKER — none.

I looked hard at the D3/D4/D5 interlock, the OWL_RUNTIME_H impls,

### MAJOR — none.

### MINOR

#### MINOR-1 — A silent OWL runtime failure (e.g. `RegisterClassExA` returning 0) does not fail the liveness test; it self-skips.

Repro path:

1. If `OwlStaticWndProc` were ever broken (wrong ABI, wrong cast
   chain), `RegisterClassExA` would still succeed (it does not
   validate `lpfnWndProc`), but `CreateWindowExA` would NOT — the
   OS calls the WndProc on `WM_NCCREATE`, the broken thunk returns
   FALSE / crashes, `CreateWindowExA` returns NULL.
2. The runtime ignores the `CreateWindowExA` return value (it is
   stored into `HWindow`, but `Create()` only returns its non-NUL-
   ness as `BOOL`). `Run()` ignores `Create()`'s return value.
3. The message loop runs with no top-level window → no `WM_QUIT`
   ever arrives → `GetMessageA` returns 1 indefinitely.
4. The liveness test's `FindWindowA` poll times out after 4 s →
   the test branches into `proc.terminate(); proc.wait(3000);
   skip(...)`. The test **self-skips**, it does not fail.

This is a soundness gap, not a hang: the watchdog still kills the
child. But it means D5's "exit code 0" assertion can be silently
bypassed under a future regression that doesn't actually post a
window. Two mitigations are worth considering:

- (cheap) Have the D5 liveness probe call
  `GetExitCodeProcess` after the FindWindowA timeout and assert
  it is NOT `STILL_ACTIVE` (i.e. the child died on its own) and
  that the exit code is non-zero — turning the silent skip into
  an explicit `"D5 child never showed a window; exit code {…}"`
  failure.
- (cheaper) The structural test
  `o6_d5_hello_owl_compiles_to_gui_pe` already locks the
  USER32 import set; this catches structural drift but not
  runtime-OS interactions.

This is honestly a property of any "tripwire" oracle (the HLD §C4
calls liveness "honestly weaker than the O1/O2/O3 differential")
and is not a regression vs. the C4 baseline. Filing as MINOR because
D5 is the milestone marker and the bar deserves to be raised.

Files:
- `tests/gui.rs:1515-1521` (D5)
- `tests/gui.rs:745-750` (D2, same shape)
- `tests/gui.rs:1090-1095` (D3, same shape)

#### MINOR-2 — `OwlStaticWndProc` reads `self` uninitialised on the non-WM_NCCREATE branch.

`src/pp.rs:289-296`:

```c
LRESULT CALLBACK OwlStaticWndProc(HWND h, UINT m, WPARAM w, LPARAM l) {
    TWindow *self;
    if (m == WM_NCCREATE) {
        ...
        self = (TWindow *)cs->lpCreateParams;
        ...
    }
    self = (TWindow *)GetWindowLongPtrA(h, GWLP_USERDATA);   // (*) always overwrites
    ...
}
```

The read at `(*)` makes the previous unconditional `self =`
write inside the `WM_NCCREATE` arm dead-store-ish (and on the non-
`WM_NCCREATE` path, `self` was uninitialised before this line).
mdbcc does not warn (no clippy here), real C compilers would
flag it. Harmless because the write inside the `if` is followed by
the unconditional re-read on the very next line that overwrites it.

Suggested cleanup: initialise `self = 0;` at declaration, or restructure
to a single `if/else` so the read is on a known-initialised path.
Non-blocking; documenting because the HLD claims the runtime is "no
hacks" — initialising the local is a one-token tidy-up that lifts the
"any C reader" bar.

#### MINOR-3 — `RegisterClassExA` and `CreateWindowExA` return values are dropped silently in the runtime.

`src/pp.rs:286-310` (`TWindow::Create`):

```c
RegisterClassExA(&wc);            // result discarded
...
HWindow = CreateWindowExA(...);   // stored, but Create() only returns
                                  //   HWindow != 0 — never checked at call site
```

On a real second-instance call (e.g. a Phase E child window of a
different class), `RegisterClassExA` might fail and silently leave
the class unregistered. `CreateWindowExA` returns NULL and the
`Create()` BOOL is the user's only hint. The current single-window
hello-OWL never exercises this, but anything Phase E adds (multi-
window apps, secondary classes) needs to surface the failure path.
Filing as MINOR because D5 ships green, but it's a real shape for
Phase E to inherit. Not actionable in Phase D.

#### MINOR-4 — `_OwlApp` is set but never read by the runtime.

`src/pp.rs:248`: `TApplication *_OwlApp = 0;` is declared.
`src/pp.rs:269`: the `TApplication` ctor does `_OwlApp = this;`.

No code in `OWL_RUNTIME_H` actually reads `_OwlApp`. It is dead
state for D4/D5. The HLD §D-b implies it is provided for Phase E
(callbacks that need to find "the app" — message cracking, IPC,
DDE). Filing as a NIT-shaped MINOR because the runtime carries a
mutable global with zero readers — small surface for accidental
divergence later. Trivial to keep; trivial to remove until Phase E
actually needs it.

### NIT

#### NIT-1 — `OwlStaticWndProc` redundantly dispatches `WM_NCCREATE` to `self->WindowProc`.

`src/pp.rs:289-300`: on `WM_NCCREATE`, the thunk binds `self` via
`GWLP_USERDATA` and then falls through to the unconditional
`self = GetWindowLongPtrA(...); if (self != 0) return
self->WindowProc(...)`. This means `WM_NCCREATE` is dispatched to
the virtual `WindowProc` which falls through to `DefWindowProcA(
HWindow, msg, w, l)`. Functionally correct (DefWindowProcA does
return TRUE for WM_NCCREATE), but the OWL idiom is usually to
handle WM_NCCREATE entirely in the thunk and return TRUE without
calling the virtual. The current shape is fine; documenting
because it differs from textbook OWL/Petzold.

#### NIT-2 — `OwlMain` is declared in the header but not strictly required to be there.

`src/pp.rs:251`: `int OwlMain(int argc, char **argv);` is a
forward prototype. The parser accepts prototypes and discards
them (`src/parser.rs:1190-1192`), so it costs nothing, but the
parser does not enforce signature match between the prototype and
the user's definition. A user TU that wrote `void OwlMain(void)`
would compile, and then the runtime's `OwlMain(0, 0)` call would
pass two args to a no-arg function. Phase A's calling convention
mostly papers over this (4-arg-in-regs is robust), but it's a
latent correctness shape that Phase E will eventually want to
tighten.

#### NIT-3 — `D5_USER32_REQUIRED = D4_USER32_REQUIRED` aliasing is correct but rebinds without comment.

`tests/gui.rs:1391`: `const D5_USER32_REQUIRED: &[&str] =
D4_USER32_REQUIRED;`. The aliasing is intentional (the D5 user TU
emits no USER32 calls directly — all imports come from the
unchanged D4 runtime), and the comment on the constant is clear.
Pure stylistic; could just inline-use `D4_USER32_REQUIRED` in the
`o6_d5_hello_owl_compiles_to_gui_pe` assertion loop.

## Outstanding risks for Phase E

The HLD's Phase-E preview (event tables, response tables, message
cracking) is where the current minimalism will need to grow. Three
real load-bearing risks the D4 surface does not yet address:

### R1. `DECLARE_RESPONSE_TABLE` / `DEFINE_RESPONSE_TABLE` — member-function pointers.

Borland-OWL response tables are implemented as static tables of
`{message, member-function-pointer}` entries. mdbcc has NO
member-function pointer support (no `&Class::method` type/AST/
codegen, no thunk emission). Phase E must either:

- (a) emulate response tables with a `switch`-style dispatch in
  the runtime — but mdbcc has no `switch` parser rule
  (`Keyword::Switch` is recognised but no `parse_switch`), so
  Phase E may need to add a `switch` parser before it can add
  response tables. The D2 fixture works around this with `if`
  chains; OWL response tables would be a much bigger if-cascade.
- (b) add member-function pointer support (a significant Phase B
  extension — typed pointers, thunk vs. direct call discipline,
  PMI codegen).
- (c) define a smaller "mdbcc-OWL" subset that does message
  handling via virtuals only (`TWindow::WindowProc` switch on
  `msg` in the user override). Workable for a hello-OWL but
  diverges from Borland-OWL idiom.

The HLD §D-2 ("classic non-template OWL 2.5") leaves this open;
Phase E should resolve.

### R2. Macro-heavy OWL headers.

Real Borland-OWL headers use heavy pre-processor macros
(`DECLARE_RESPONSE_TABLE`, `EV_WM_*`, `EV_COMMAND`, etc.). The
intrinsic `OWL_RUNTIME_H` body bypasses this by hand-rolling the
runtime in mdbcc's plain-C++ subset. Phase E either:

- keeps hand-rolling (low ceiling for real-OWL portability), or
- extends the intrinsic to include the macro definitions and
  ensures `src/pp.rs`'s preprocessor can chew the macro
  expansion (currently very capable — the lib's 61 tests include
  variadic / token-pasting / `__LINE__` / nested cases — but the
  EV_* macros tend to use ##/# in ways worth probing).

### R3. The "no compiler change" wins compound — but Phase E almost certainly breaks the streak.

D1–D5 added zero compiler features (only data growth + an
intrinsic header). Phase E (event handling) is unlikely to
preserve this: at minimum, real response tables need either
member-function pointers (codegen) or a `switch` parser rule
(parser). The journal should set expectations: Phase E is where
the compiler grows again, and it should be sequenced as carefully
as Phase A/B/C with one-feature-per-commit + green-bar gates.

### R4. The console byte-identical lock is now load-bearing for every Phase-D+ commit.

The `owl/` resolver gate (`src/pp.rs:385-387`) is one line of
defense: any path-prefix bug (e.g. `name.starts_with("owl")` —
missing the slash — would match `owl_unrelated.h`) would emit the
209-line OWL body for some unrelated user header and silently bloat
the console PE. The current strict-`owl/` prefix is correct, but
the byte-identical golden lock (`tests/pe_imports.rs`) is the only
catch. Any Phase-E change touching `DefaultResolver::resolve` must
keep this golden frozen.

### R5. MINOR-1 (silent runtime failure → self-skip) becomes load-bearing in Phase E.

Phase E's response tables are far more likely to have a subtle
runtime bug than D4's hand-rolled minimal runtime. The
"FindWindowA-timeout → skip" branch on the D5 path should be
upgraded to a hard failure before Phase E lands — see MINOR-1's
suggested mitigation.

## Conclusion

Phase D D1–D5 is a real milestone, honestly enforced. mdbcc — a
compiler that fits in single-digit thousands of Rust lines and has no
linker — compiles unmodified Borland-OWL-shape source
(`TApplication` subclass + `OwlMain`) to a Win64 PE that opens a real
top-level window on Windows 11 and exits cleanly with code 0. The
test that proves this ran here, on the development machine,
deterministically, in 0.19 s alongside nine sibling gui tests, with
the entire 217-test suite green and clippy clean.

The architectural elisions (intrinsic-prepended single-TU runtime;
constant-null-init globals + first-statement-imperative-store;
`GWLP_USERDATA` per-HWND instance map; static-thunk WNDPROC as a
plain Win64 4-arg function) are each correct and each chosen for the
right reason — to fit inside what the existing compiler already
supports, rather than expanding it speculatively. The MINOR findings
are all suggestions, not defects.

The journal's claim of "no compiler change" for D2–D5, and "pure
data growth" for D1+D4, holds up to file-by-file inspection. The
byte-identical-console regression is locked structurally (the new
`o6_d4_console_program_unchanged_after_owl_runtime`) and
byte-for-byte (the unmodified `tests/pe_imports.rs` golden). The
"interactive desktop" liveness machinery is provably bounded —
total worst-case per test under 20 s; empirical 0.19 s for ten.

Approve for merge.
