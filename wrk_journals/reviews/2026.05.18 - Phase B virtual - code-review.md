## Verdict: REQUEST-CHANGES (one BLOCKER; ABI core is otherwise sound)

The vtable/layout/dispatch core is correctly designed and faithfully
encoded: vptr-at-0, the +8 data-member shift, base-first slot ordering,
override resolution, the `.rdata` vtable image, virtual dispatch
register/clobber discipline, virtual-destructor-through-base, the
abstract-instantiation guard, the byte-identical non-polymorphic
regression, and determinism are all correct and verified. **However,
there is one real Phase-B correctness BLOCKER**: a polymorphic
constructor that takes an early `return` (or that makes a virtual call
within its own body) never installs the vptr, because the vptr store is
emitted only on the function's fall-through path in `Gen::run`. This is
not theoretical — it is reproduced below with a clean program that
silently miscompiles to the wrong answer, and a sibling program that
**crashes with an access violation**. It must be fixed in Phase B.

A separate pre-existing defect (early `return` in a destructor body
skips the appended base-destructor chain call) is *not* introduced by
Phase B but lands squarely in Phase B's headline domain (virtual-dtor
ordering) and is recorded as MAJOR with proof.

## Strengths (genuinely solid — verified, not assumed)

1. **The vtable ABI is correctly designed and encoded.** vptr reserved
   at `[0,8)` and data members shifted +8 only when `polymorphic`
   (`parser.rs:1962-1970` `layout`); single-inheritance base re-lay
   reproduces base offsets with one shared vptr (no duplication —
   `parser.rs:640-647`). Slot order is base-virtuals-first then this
   class's new virtuals in declaration order, override matched by `key`
   (name, or `"~"` for the dtor) replacing the inherited slot's `sym`
   (`parser.rs:602-619`). Virtual dispatch is the textbook
   `mov rax,[rcx]; mov rax,[rax+slot*8]; call rax`
   (`codegen.rs:1037-1045`) with RCX (`this`) provably preserved across
   the two loads (neither touches RCX), arguments evaluated to temps
   *before* any register load (arg eval cannot clobber a live reg),
   and the >4-arg path reusing Phase A's exact `[rsp+0x20+8*(g-4)]`
   marshalling (`codegen.rs:1024-1031`). `B1`–`B8` (weighted,
   position-observable) and Probes 3/5/6 confirm dispatch, override
   binding, inherited-slot retention, the 3-level chain and the
   synthesized default ctor are all correct.

2. **The byte-identical non-polymorphic regression claim holds under
   scrutiny.** Every Phase-B layout/codegen change is gated on
   polymorphism: `layout`'s `align`/`size` seed only changes when
   `polymorphic` is true (`parser.rs:1969-1970` — non-poly keeps
   `align=1, size=0`); `vtables` are synthesized only for
   `rec.is_polymorphic()` (`codegen.rs:336-344`) so a program with no
   virtuals produces **zero** new `.rdata` bytes and no RVA drift
   (`pe.rs:223-227` skips when `module.vtables` is empty; the `is_empty
   ⇒ push 0` degenerate-section guard is unchanged); the ctor vptr
   store is gated on `r.is_polymorphic()` (`codegen.rs:536-541`); the
   virtual-call / virtual-delete paths are gated on a non-empty vtable
   (`codegen.rs:1273`, `:1986`). The 88 O1 e2e + 15 differential +
   2 pe_layout pass, empirically confirming no perturbation of the
   non-polymorphic surface. Same regression argument class as Phase A,
   and it is airtight.

3. **Determinism is fully preserved.** `vtables` is built by iterating
   `sigs.records` (a `Vec`, declaration order) — `codegen.rs:337`;
   per-slot symbols come from `rec.vtable` (a `Vec` built by the parser
   in declaration order, `parser.rs:602-619`). `func_offsets`
   (`pe.rs:209-220`) iterates `module.funcs` (Vec) with a length-only
   cursor; `build_vtables` (`pe.rs:226-249`) iterates `module.vtables`
   (Vec) and resolves symbols via `offsets.get` (lookup only). The two
   `HashMap`s (`offsets`, the `idata` map) are never *iterated* to
   produce bytes. `record_count` indexes `vtable_rvas` by record id (a
   dense `Vec<u32>`), not by hash order. No HashMap iteration feeds
   emitted bytes anywhere in the diff. Vtable contents/order are a pure
   function of declaration order, as the HLD requires.

4. **The `func_offsets` pre-pass is correctly justified and
   self-checking.** It mirrors `build_text`'s cursor exactly (offsets
   depend only on code lengths, never relocations), so baking absolute
   function addresses into vtable slots before `.text` exists is sound;
   the existing always-on `build_text` divergence check (`pe.rs:~445`,
   unchanged) still guards the whole pipeline. Duplicate-function and
   undefined-slot-symbol cases are clean `CodegenError`s
   (`pe.rs:213-215`, `:240-244`), and a vtable referenced but not
   emitted is a clean error (`pe.rs:343-351`) — house style honoured.

5. **The abstract-instantiation guard is complete for the value cases.**
   `is_abstract()` (`ast.rs`, any slot with empty `sym`) is checked for
   every local/param of class type (`codegen.rs:456-470`, iterating the
   `locals` map which includes params) and for `new T`
   (`codegen.rs:1929-1938`). Pointers/refs to abstract classes are
   correctly allowed (not `Type::Record`). Pure slot ⇒ `0` in
   `.rdata` (`pe.rs:236-238`); the "an abstract class can never be
   instantiated so a pure slot is never dispatched" argument is valid
   *given the guard is complete* — and it is, for declarable instances.
   `B9` confirms the clean error with an `abstract`/`pure virtual`
   message.

6. **Virtual-destructor-through-base is correct.** `delete p` where the
   static pointee has a `"~"` slot loads the **runtime** vptr and
   dispatches `[vptr + dslot*8]` (`codegen.rs:1986-1994`); single
   inheritance keeps `dslot` stable so static-slot == dynamic-slot;
   `delete (Base*)d` therefore runs `Der::~Der`, which chains to
   `Base::~Base` via the parser-appended base-dtor call. `B4` (virtual)
   and `B5` (non-virtual contrast — static `E8` retained) both pass.
   The derived→base ordering is correct *as long as the derived dtor
   body falls through* (see MAJOR-1 for the early-return hole, which is
   pre-existing).

7. **The `Tag::Tag` ctor-detection heuristic is sound for this subset.**
   `f.name.split_once("::")` with `tag == m` (`codegen.rs:536-537`):
   C identifiers cannot contain `:`, so the only `::`-bearing names are
   compiler-mangled (`Tag::method`, `Tag::~Tag`, `Tag::operator@`). A
   free function has no `::` ⇒ `split_once` returns `None` (safe). An
   `operator+` method ⇒ `m="operator+" != tag` (safe). A method named
   exactly like its class *is* the constructor in C++ (correct). It
   also matches the synthesized empty-default and base-chaining ctors
   (both `Tag::Tag`) — which is exactly what we want (they must install
   the vptr). No free-function/operator collision exists.

8. **Test design is oracle-grade.** Weighted, position-observable sums
   (`*100`, `*10`) make the dispatched-to implementation observable so a
   slot-order or wrong-binding bug cannot pass silently; `B6` reads
   members back through a virtual method to prove the +8 shift is
   applied consistently; `B4`/`B5` use printf-order as a dtor-ordering
   oracle; `B9` asserts the abstract error. The deferral of the C++
   differential corpus (harness compiles `.c` as C; tracked B-4) is
   honest and explicit, and `virtual.c` is still parse-smoked as a
   tripwire.

## Findings

### BLOCKER

- **BLOCKER-1 — A polymorphic constructor that does not fall through
  never installs the vptr (silent miscompile / crash).**
  `src/codegen.rs:531-548` (the vptr store in `Gen::run`) is emitted
  **once, on the function's fall-through path only**, after
  `for s in &f.body { self.gen_stmt(s)? }`. `Stmt::Return`
  (`codegen.rs:706-722`) emits `emit_all_dtors()` + `epilogue()`
  (`leave; ret`) and diverts control — it never reaches the vptr store.
  Consequences, both **empirically reproduced**:
  - **Early `return` in a ctor → object has no vptr.**

    ```cpp
    class Shape { public: virtual int area(){ return 0; } };
    class Sq : public Shape { int s; public:
      Sq(int x){ s=x; if (x>0) { return; } s=999; }
      virtual int area(){ return s*s; } };
    int main(void){ Sq q(3); Shape* p; p=&q; return p->area(); }
    ```

    C++ requires `9`. **mdbcc produces `0`** — `[this+0]` is
    uninitialised stack, `p->area()` dispatches through garbage. Silent
    wrong answer (here it happened not to fault; in general it is UB).
  - **Any virtual call inside a ctor body dispatches through an
    uninitialised vptr** (because the store is *after* the body):

    ```cpp
    class P { public: int x; P(){ x = this->v(); }
              virtual int v(){ return 1; } };
    class Q : public P { public: virtual int v(){ return 9; } };
    int main(void){ Q q; return q.x; }
    ```

    C++ requires `1` (inside `P::P` the dynamic type is `P`). **mdbcc
    crashes with `0xC0000005`** (access violation): `mov rax,[rcx]`
    reads garbage at `[this+0]`, `call [rax+slot*8]` jumps into the
    void. Hard crash on a textbook construct.

  This is *the* load-bearing Phase-B invariant ("most-derived wins;
  the vptr is always installed") and it is violated for any ctor that
  is not strictly straight-line-fall-through. The HLD's own claim —
  "synthesize an empty default ctor so the vptr is *always* installed"
  — is defeated the moment a user ctor has an `if (...) return;` (very
  common in OWL/Win32 ctors that bail on a failed resource acquire).
  In-ctor virtual calls (also common in OWL base-class init) are
  *always* wrong, not just on early return, because the store is
  unconditionally emitted after the whole body.

  Root cause: the vptr store is positioned as a single epilogue-adjacent
  emission rather than (a) at ctor *entry*, immediately after base-ctor
  chaining and before the user body — which is the standard Itanium
  ordering and also makes in-ctor virtual calls resolve to the correct
  (current-class) override — and (b) on every return path.
  **The standard fix is to install the vptr at the *start* of the ctor
  body (after the base-ctor call, before member-inits/user statements),
  not at fall-through.** That single repositioning fixes both the
  early-return case and the in-ctor-virtual-call C++ semantics
  simultaneously, and removes the fall-through-only fragility entirely.
  Must be fixed and covered by a RED→GREEN test (early-return ctor +
  in-ctor virtual call) before Phase B is accepted.

### MAJOR

- **MAJOR-1 — Early `return` in a destructor body skips the appended
  base-destructor chain (pre-existing; lands in Phase B's domain).**
  `src/parser.rs:805-819` (`dtor_full_body`) builds a flat
  `Vec<Stmt>` = `[user body ... , ExprStmt(Base::~Base(this))]`. The
  base-dtor chain call is a *trailing statement*; an early `return` in
  the user dtor body makes it dead code, so `~Base` never runs.
  Reproduced (Probe 4, virtual): `delete (Base*)new Der()` with
  `~Der(){ if (k) { printf("~Der\n"); return; } }` prints `~Der\n`
  only — `~Base` is dropped. Probe 7 shows the **non-virtual** dtor has
  the identical defect, proving this is **pre-existing**, not introduced
  by Phase B (same root cause as BLOCKER-1's control-flow model, but in
  the parser's statement-appending rather than codegen's
  fall-through-only emission). It is recorded here as MAJOR because
  Phase B's headline guarantee is "virtual destructor runs Derived::~
  then chains to Base::~", and a one-line `if (..) return;` in a real
  OWL dtor silently breaks base teardown (leaks / double-free of base
  resources). Symmetric fix to BLOCKER-1: base-dtor teardown must run on
  *every* exit path (it belongs to the same return-diversion machinery
  as `emit_all_dtors`/scope exit, not to a trailing AST statement).
  Recommend fixing within Phase B since it is the same control-flow bug
  class and directly undermines the Phase B oracle's intent; at minimum
  it must be an explicit tracked backlog item with a failing test, not
  left implicit.

### MINOR

- **MINOR-1 — Unqualified call to a class's own (virtual or not) method
  from inside a method/ctor body is a hard `CodegenError` (pre-existing
  limitation, but it amputates most of Phase B's value for OWL).**
  Probes 2 and 8: `int use(){ return v(); }` and `P(){ x = v(); }`
  both fail with `CodegenError("call to undefined function 'v'")`. The
  parser sets `cur_class`/`fn_locals` for member bodies
  (`parser.rs:697-714`) but an unqualified `v()` is lowered as a free
  `Expr::Call{name:"v"}`, not rewritten to `this->v()` /
  `MethodCall{recv:this}`; codegen then cannot find a free function
  `v`. This is pre-existing (not a Phase B regression — `B8`'s
  *non-virtual* probe fails identically) and the committed `B1`–`B9`
  sidestep it by always calling through an explicit receiver
  (`p->area()`, `b.f()`, `q.plain()` where `plain` calls `v()` — wait:
  `B8` `nonvirtual_method_calls_virtual_on_this` *passes* because
  `plain(){ return x + v(); }` … this works only because `x` and `v`
  resolve via the member path there; the failing case is a *standalone*
  `return v();`). Net: OWL is saturated with unqualified virtual
  self-calls (`Paint()`, `SetupWindow()`, `GetWindowClass()` called
  from base methods without `this->`). Phase B's dispatch is correct,
  but it is largely unreachable from idiomatic OWL code until
  unqualified member-call resolution lands. Strongly recommend
  promoting this to an explicit, tracked, high-priority backlog item
  (it is arguably the real blocker for *using* Phase B in Phase 0+,
  even though it is not a Phase-B-introduced defect) — and verifying
  whether any committed `virtual.rs` test actually exercises an
  unqualified virtual self-call (none does; `B8` uses `v()` inside
  `plain()` which currently compiles only because of the specific
  member-resolution path — this should be confirmed and a dedicated
  RED test added when MINOR-1 is addressed).

- **MINOR-2 — `delete` of a null pointer dereferences `[null]` for the
  vptr load.** `src/codegen.rs:1989-1994`: the virtual-dtor path emits
  `mov rcx,[rbp-p]; mov rax,[rcx]` unconditionally; `delete (T*)0`
  therefore faults instead of being the C++-required no-op. The
  non-virtual path (`:1996-2004`) has the same pre-existing property
  (unconditional dtor call + `HeapFree`), so this is not a Phase-B
  regression, but the virtual path adds a *second* unconditional null
  deref (the vptr load) ahead of `HeapFree`. Low priority (no test or
  OWL pattern depends on `delete nullptr` yet) but worth a tracked note;
  a single `test rcx,rcx; jz skip` around the dtor+free would make
  `delete`-of-null safe for both paths.

- **MINOR-3 — `recv_record_id` cannot see through a reference-typed
  receiver *expression* (only a reference *variable*).**
  `src/codegen.rs:955-963`: it matches `Type::Record` / `Type::Ptr` but
  not `Type::Ref`, and `Type::decay()` does **not** peel `Ref`
  (`ast.rs:140-146`). The common case works only because `expr_type`
  for an `Expr::Var` of reference type pre-unwraps `Ref(inner)=>inner`
  (`codegen.rs:2555-2558`), so `B& b; b.f()` yields `Record` (why `B2`
  passes). But a receiver whose `expr_type` legitimately returns
  `Type::Ref(Record)` without the `Var` unwrap (e.g. a function
  *returning* `T&`, then `getRef().f()`) would return `None` →
  **silent static dispatch instead of virtual**. Out of the
  single-inheritance happy path the tests cover; latent, surfaces with
  ref-returning accessors (plausible in OWL). Cheap robustness fix: add
  a `Type::Ref(inner)` arm to `recv_record_id` mirroring the `Var`
  unwrap. Record as tracked.

### NIT

- **NIT-1 — `is_polymorphic()` is re-derived by a linear `records`
  scan inside `Gen::run` for every function.** `codegen.rs:538-541`
  does `self.sigs.records.iter().position(|r| r.tag.as_deref() ==
  Some(tag) && r.is_polymorphic())` on every emitted function (not just
  ctors — the `split_once`/`tag==m` guard short-circuits non-ctors
  first, so it is correct, just mildly wasteful). Fine for current
  program sizes; noting only that once BLOCKER-1 moves the store to
  ctor entry this lookup should move with it and could reuse the
  record id already known at ctor synthesis. No action required now.

- **NIT-2 — `VtableImage.slots: Vec<String>` clones every mangled
  symbol.** `codegen.rs:340` `rec.vtable.iter().map(|s|
  s.sym.clone()).collect()`. Harmless (small, build-time), and keeps
  `VtableImage` decoupled from `Record` lifetimes — a reasonable
  tradeoff, called out as reviewed-and-fine.

- **NIT-3 — `tests/corpus/portable/virtual.c` is `#include <stdio.h>`
  + C++ but lives under `corpus/portable/` where the harness compiles
  `.c` as C.** The header comment documents this clearly and B-4 tracks
  the C++ harness mode; the file is still parse-smoked. Correct as a
  tripwire; no action. (Noting: once B-4 lands, `Rect` has no explicit
  ctor *and* a non-trivial base with a vtable — a good
  synthesized-ctor-installs-vptr differential case; ensure it is
  retained.)

## Outstanding risks / notes for Arthur

1. **BLOCKER-1 is the gate.** The vtable ABI itself is correct and
   well-tested; the defect is purely *when* the vptr is written
   (fall-through only) rather than *what* is written. The fix is
   well-understood and localized (install at ctor entry, after
   base-ctor chaining, before the user body — the standard ordering),
   and it simultaneously corrects in-ctor virtual-call semantics. It
   must ship with a RED→GREEN test covering (a) an early-`return` ctor
   and (b) an in-ctor virtual call. Until then Phase B silently
   miscompiles / crashes on idiomatic constructors.
2. **MAJOR-1 and MINOR-1 are pre-existing but Phase-B-critical.** The
   early-return-skips-base-dtor (MAJOR-1) and unqualified-member-call
   (MINOR-1) defects are not introduced by this commit, but both strike
   directly at Phase B's purpose (virtual-dtor ordering; OWL virtual
   self-dispatch). They should be explicitly tracked as high-priority
   backlog with failing tests — not left implicit — and MAJOR-1 is
   cheap enough (same control-flow machinery as BLOCKER-1) to be worth
   folding into the Phase B fix.
3. **The committed oracle is green but has a coverage hole.** No
   `virtual.rs` test exercises an early-return ctor, an in-ctor virtual
   call, or a standalone unqualified virtual self-call. The suite's
   greenness does not imply Phase B is correct for these — the probes
   prove it is not. Recommend the apply-feedback pass add these as
   permanent RED→GREEN regressions so the gap cannot reopen.
4. **Differential C++ mode (B-4) remains deferred.** The O1
   `tests/virtual.rs` oracle is the only authoritative virtual check;
   `virtual.c` is parse-smoke only. Accepted as documented, but it
   means the BLOCKER would not have been caught by the differential
   harness either — the O1 hand-oracle is doing all the work and it
   has the coverage hole in (3).

## Conclusion

The Phase B object model — vptr-at-0, +8 shift, base-first slot order,
override resolution, `.rdata` vtable image, indirect dispatch,
virtual-destructor-through-base, abstract guard, byte-identical
non-polymorphic regression, determinism — is correctly designed,
faithfully implemented, and verified against all six ground-truth
oracle suites plus reproduction probes. **One BLOCKER prevents
acceptance**: the constructor vptr store is emitted only on the
fall-through path, so any constructor with an early `return` silently
miscompiles and any in-constructor virtual call crashes; both are
empirically reproduced. Fixing it (install the vptr at ctor entry after
base-ctor chaining) is localized and also corrects in-ctor virtual
semantics. One pre-existing MAJOR (early-return drops the base-dtor
chain) and one pre-existing MINOR (unqualified member-call resolution)
land in Phase B's domain and must be explicitly tracked with failing
tests. **REQUEST-CHANGES**: fix BLOCKER-1 in Phase B; fold in MAJOR-1
if practical; track MINOR-1/2/3 with regression tests.

## Apply-feedback outcome (2026-05-18, implementer)

- **BLOCKER-1 (ctor vptr only on fall-through) — FIXED.** Root-cause
  fix, not a patch: a parser-injected `Stmt::SetVptr(id)` is placed
  immediately *after* the base-ctor call and *before* the member-inits
  / user body in every ctor-body producer (`ctor_full_body`,
  `synthesize_base_chaining`, the polymorphic empty-default ctor). It
  therefore runs (a) after base construction so the most-derived
  vtable wins, (b) before any user statement so it executes on **every**
  exit path incl. early `return`, and (c) before in-ctor virtual calls
  so they dispatch correctly (also resolves the in-ctor MINOR). Codegen
  emits **nothing** for `SetVptr` on a non-polymorphic record, so the
  88 O1 e2e stay byte-identical (verified). The buggy fall-through
  block in `Gen::run` was removed. New RED→GREEN tests:
  `early_return_constructor_still_installs_vptr` (=205) and
  `virtual_call_inside_base_constructor_resolves_to_base` ("10\n") —
  these close the review's coverage-hole MINOR-1 for the ctor path.
- **MAJOR-1 (early `return` in a (v)dtor skips the base-dtor chain) —
  TRACKED, not fixed (backlog B-5).** Confirmed PRE-EXISTING and *not
  Phase-B-introduced* (the non-virtual dtor has the identical defect).
