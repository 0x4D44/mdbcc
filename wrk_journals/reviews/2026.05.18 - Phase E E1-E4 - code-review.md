## Verdict: APPROVE (no BLOCKER, no MAJOR)

Phase E E1–E4 is correct, minimal, and faithful to the HLD's central
mechanism choice (Option (b): virtual-dispatch lowering, **not**
member-fn-ptr tables). The central claim — *"a real OWL app with a
response table responds to a synthetically-injected user-input event,
mutates state, and reports the count on clean exit"* — is **executably
enforced** by `o6_e4_click_owl_counts_lbuttondowns_via_response_table`
that I independently ran here, where three cross-thread `SendMessageA(
hwnd, WM_LBUTTONDOWN, ...)` calls produce three deterministic
`"CLICK k\n"` lines plus the `"CLICKS=3\n"` summary, with exit code
exactly 0, in ~0.22 s alongside seventeen sibling gui tests.

The mechanism-choice decision is sharp: the HLD §E-a Option (b) is
faithfully realised — every `EV_WM_X` macro expands to an `if (msg ==
X) { ...crack WPARAM/LPARAM...; this->EvX(...); return 0; }` block
inside the user's `cls::WindowProc` override, and `END_RESPONSE_TABLE`
falls through to `this->base_WindowProc(msg, w, l)` which calls
`DefWindowProcA(HWindow, ...)` directly. Member-function pointers were
**not** introduced; the codegen surface is unchanged. The 8 Ev*
virtuals land in `TWindow`'s vtable as inherited slots — same Phase-B
machinery D5 already proved across the Win32 callback boundary.

The "no compiler change" invariant — Phase E's strongest discipline
claim — **holds** to file-by-file inspection: `src/{ast,parser,
codegen,compile,lib,lexer,main}.rs` show **zero deltas** across all
five commits (`git diff --stat 0a8dbc7^..4c49ae3 -- src/{ast,parser,
codegen,compile,lib,lexer,main}.rs` is empty). Only `src/pe.rs` (data
table growth in `WIN32_IMPORTS`) and `src/pp.rs` (intrinsic-header
body growth in `WINDOWS_H` + `OWL_RUNTIME_H`) are touched, with
`tests/gui.rs` extended for fixtures + harness. The console
byte-identical invariant — Phase E's central regression target —
**also holds**: `tests/pe_imports.rs` (the 169-byte `GOLDEN_IDATA`
console lock) shows `git log --follow` only `df4f7c8` (C1a, file
creation), zero Phase-E entries. `tests/pe_layout.rs` and
`tests/end_to_end.rs` are equally untouched by Phase E.

All findings are MINOR/NIT. The strongest is a **HLD-implementation
drift on `EV_WM_CREATE` semantics**: the HLD documented bool-style
return (`true=continue creation`, `false=abort`) but the actual macro
returns `(LRESULT)this->EvCreate(cs)` directly and the default
`EvCreate` returns `int` (with the `0` happy path that, by Win32 raw
semantics, means "continue" — so the default works by accident).
Phase E ships no test that exercises `EV_WM_CREATE`, so this cannot
surface as a runtime bug in Phase E itself; logging as MINOR because
Phase F+ event handlers WILL use `EV_WM_CREATE` and the doc/impl
divergence will trip a real user. A second MINOR is that the HLD's
**"vtable slot count observability"** commitment (HLD §E-a Decision
3, "we measure it in E1's structural test") was **not honored** — no
test asserts `sizeof(TWindow)` or the vtable slot count, so silent
EvX growth in Phase F+ will not be caught.

## Strengths (load-bearing)

### S1. The HLD §E-a mechanism choice is honored faithfully.

`src/pp.rs:429-441` — the eight EV_WM_* macros each expand to an
`if (msg == X) { ...crack...; this->EvX(...); return 0; }` block
that lands inside `cls::WindowProc` (via `DEFINE_RESPONSE_TABLE1`'s
opening `{`). `END_RESPONSE_TABLE` is `return
this->base_WindowProc(msg, w, l); }` — closing the brace and
falling through to the non-virtual helper. This is **exactly** the
HLD §E-a Option (b) design:

- `EV_WM_DESTROY` additionally calls `PostQuitMessage(0)` after the
  user's `EvDestroy()` returns, preserving Phase D's clean-exit
  chain (a user `EvDestroy` that does nothing still results in
  `WM_QUIT` ⇒ loop exit).
- `EV_WM_LBUTTONDOWN`/`UP`/`MOUSEMOVE` use `(int)(short)(l &
  0xFFFF)` and `(int)(short)((l >> 16) & 0xFFFF)` to extract
  signed 16-bit screen coordinates from the packed LPARAM — the
  HLD §E-c sign-extension contract. `WPARAM` (mouse modifier keys)
  is unpacked as `(UINT)w`. The signature passed to the EvX virtual
  is `(UINT modKeys, int x, int y)` rather than the HLD-spec
  `TPoint& pt` — an honest simplification the commit message
  surfaces ("no-TPoint simplification") that avoids a struct-by-
  reference parameter ABI question.
- `EV_WM_COMMAND` unpacks `id = LOWORD(w)`, `notifyCode = HIWORD(w)`,
  `hCtl = (HWND)l` — matches the Win32 contract.
- `EV_WM_KEYDOWN` unpacks `vkey = (UINT)w`, `repeatCount = LOWORD(l)`,
  `flags = HIWORD(l)` — matches.

Member-function pointers are **not** added: a grep of all source
shows zero `::*` syntax, zero member-fn AST nodes. The HLD Option
(a) authentic-OWL path is recorded as **B-10** in the backlog, NOT
silently added.

### S2. `base_WindowProc` is the honest workaround for the missing qualified-call-in-expression grammar.

`src/pp.rs:305`: `LRESULT base_WindowProc(UINT m, WPARAM w, LPARAM l)
{ return DefWindowProcA(HWindow, m, w, l); }` — a non-virtual member
helper. The HLD §E-b decision 1 explains why: mdbcc's parser does
**not** accept `TFrameWindow::WindowProc(msg, w, l)` in an expression
position (qualified-call-in-expression is a parser gap). The minimal
workaround emits a same-class method `base_WindowProc` that
`END_RESPONSE_TABLE` can call via the standard `this->`-method-call
syntax.

The HLD's claim that this is "**functionally identical** in v1
because `TFrameWindow` does not override `WindowProc`" is **subtly
wrong** for one message — `WM_DESTROY`. `TWindow::WindowProc`
(`src/pp.rs:400-406`) handles `WM_DESTROY` by calling
`PostQuitMessage(0)` before returning 0. `base_WindowProc`
unconditionally calls `DefWindowProcA`, which does NOT call
`PostQuitMessage`. So a user class with a response table that
**omits** `EV_WM_DESTROY` would fall through `END_RESPONSE_TABLE` →
`base_WindowProc` → `DefWindowProcA` → no `WM_QUIT` ever → message
loop hangs.

This is exactly the **B-13 footgun** the HLD §E-e and §Risks #8
warn about: "*a user class with a response table that omits
EV_WM_DESTROY would never post WM_QUIT and the loop would hang*". The
HLD records it as a backlog item, the watchdog catches it in tests,
and every Phase E test fixture (E1, E2, E3, E4) includes
`EV_WM_DESTROY`. Honest deferral, documented in the runtime header
comment. Promoted to **MINOR-1** below because the HLD's "functionally
identical" language deserves a precise WM_DESTROY caveat.

### S4. The first FUNCTIONAL runtime oracle in Phase E (E3) is rigorous.

`tests/gui.rs:2293-2459` — `o6_e3_paint_owl_runs_and_emits_painted_via_response_table`
is the first test in mdbcc that asserts a Win32 GUI app's response-
table-dispatched handler actually ran by checking captured stdout.
The chain it proves:

1. `compile_to_pe(PROG_E3_PAINT_OWL)` — compiles a `TFrameWindow`
   subclass with `DECLARE_RESPONSE_TABLE` + `EV_WM_PAINT` +
   `EV_WM_DESTROY`, an `EvPaint` that does `TPaintDC dc(*this);
   dc.TextOut(10,10,"…"); printf("PAINTED\n");`.
2. Subsystem-2 (GUI) PE.
3. Headless gate up front (`interactive_desktop()`) — skips loudly
   on Session-0/headless.
4. Spawn with `Stdio::piped()` for stdout capture.
5. Reader thread drains the pipe to EOF.
6. `FindWindowA("MdbccE3Paint")` polled ≤4 s.
7. `PostMessageA(WM_CLOSE)` → 4-layer teardown chain through
   `DefWindowProcA` → `WM_DESTROY` → `EV_WM_DESTROY` macro →
   `EvDestroy()` (no-op) → `PostQuitMessage(0)` → loop exits →
   `ExitProcess(0)`.
8. `proc.wait(5000)` bound.
9. Assert exit code exactly 0 (deterministic teardown chain;
   non-zero would be a crash or broken teardown).
10. Assert captured stdout **contains `"PAINTED\n"`** at least once.

The HLD's WM_PAINT-reliability claim (HLD §E-f E3 step 3: "the *first*
`WM_PAINT` will have fired by then [because] Windows sends `WM_PAINT`
as part of the create+show+update sequence") is documented in the
test's doc-comment (`tests/gui.rs:2270-2276`): `TApplication::Run`
calls `MainWindow->Show()` → `ShowWindow` → `UpdateWindow`, and
`UpdateWindow` SYNCHRONOUSLY sends `WM_PAINT` to the window proc
**before** `GetMessageA` is entered. This is correct per MSDN: 
*"UpdateWindow function … sends a WM_PAINT message directly to the
window procedure of the specified window, bypassing the application
queue"* — bypassing-the-queue is the synchronous-by-construction
guarantee. So `EvPaint` (and its `printf`) fires **before** the
harness's `PostMessageA(WM_CLOSE)` can race. The PAINTED-stdout
assertion is therefore reliable, not racy.

### S5. The E4 click oracle's `SendMessageA` synchronization claim is correct.

`tests/gui.rs:2598-2798` — `o6_e4_click_owl_counts_lbuttondowns_via_response_table`
injects N=3 synthetic clicks via cross-thread `SendMessageA(hwnd,
WM_LBUTTONDOWN, 0, lparam)` from the Rust test harness. The
synchrony claim documented at `tests/gui.rs:2481-2488` is:

> "PostMessageA is async (queues the message, returns immediately);
> SendMessageA across threads/processes blocks until the receiving
> thread's window proc processes the message and returns. That
> synchrony lets us deterministically count three dispatches: three
> sequential SendMessageA calls produce three sequential
> EvLButtonDown invocations before we move on to
> PostMessageA(WM_CLOSE)."

This is correct per the MSDN `SendMessage` documentation: *"If the
specified window was created by a different thread, the system
switches to that thread and calls the appropriate window procedure.
Messages sent between threads are processed only when the receiving
thread executes message retrieval code. The sending thread is blocked
until the receiving thread processes the message."* The OWL exe is
already running its `GetMessageA`/`DispatchMessageA` pump in
`TApplication::Run`, so the cross-process sent message is delivered
inline. Three sequential `SendMessageA` calls produce three sequential
EvLButtonDown invocations (each one running
`g_clicks=g_clicks+1; printf("CLICK %d\n", g_clicks)` to completion
before the next is delivered). The assertion that the captured stdout
contains exactly `"CLICK 1\n"`, `"CLICK 2\n"`, `"CLICK 3\n"`, and
`"CLICKS=3\n"` is therefore not racy.

### S7. The watchdog/RAII test infrastructure cannot hang (E3/E4 reused C4/D2/D3/D5/E3 verbatim).

Every E3 and E4 liveness path I traced reuses the proven machinery —
the `interactive_desktop()` headless gate, `ProcHandle` RAII +
`TerminateProcess` watchdog, `FindWindowA` bounded poll (4 s), the
`proc.wait(5000)` exit-signal bound, the `proc.wait(3000)`

captured stdout and the exit code — does not silent-skip.

The reader-thread stdout drainage (`tests/gui.rs:2348-2353`,
`:2681-2686`) is a one-shot `read_to_end` on the pipe whose write
end the child holds; when the child exits, the kernel closes the
write end, `read_to_end` returns, and the thread joins. No
synchronization primitive needed; no hang surface added.

#### MINOR-1 — The HLD's "`base_WindowProc` is functionally identical [to `TFrameWindow::WindowProc`] in v1" claim is wrong for `WM_DESTROY`.

`src/pp.rs:305`: `base_WindowProc(m, w, l) { return
DefWindowProcA(HWindow, m, w, l); }`.

`src/pp.rs:400-406`: `TWindow::WindowProc(msg, w, l)` handles
`WM_DESTROY` by calling `PostQuitMessage(0)` (and then returning
`0`), and falls to `DefWindowProcA` for everything else.

The two functions differ for `WM_DESTROY`: a real
`TFrameWindow::WindowProc` (which would inherit `TWindow::WindowProc`,
since `TFrameWindow` doesn't override) **would post WM_QUIT** on
WM_DESTROY before defaulting; `base_WindowProc` does **not**.

Consequence: a user class with a response table that **omits**
`EV_WM_DESTROY` would fall through `END_RESPONSE_TABLE` →
`base_WindowProc(msg, w, l)` → `DefWindowProcA(HWindow, WM_DESTROY,
…)` → no `WM_QUIT` ever posted → `GetMessageA` returns nonzero
indefinitely → message loop hangs.

The HLD §E-e §Risks #8 calls this out honestly as the **B-13
footgun**, and the v1 design choice is "trust the user to include
`EV_WM_DESTROY`". Every E1/E2/E3/E4 test fixture **does** include
`EV_WM_DESTROY`, so the footgun cannot bite in Phase E itself; the
watchdog catches it if it ever does. The MINOR is the **HLD
documentation drift**: the HLD §E-b decision 1 should say
"functionally identical in v1 EXCEPT for `WM_DESTROY` — see B-13"
rather than the unqualified "functionally identical".

Files:

- `src/pp.rs:400-406` (`TWindow::WindowProc` body, the contrast)
- `wrk_docs/2026.05.18 - HLD - Phase E (OWL event handling).md:336-358`

#### MINOR-3 — `EV_WM_CREATE` macro semantics drift from the HLD's stated bool convention; harmless in Phase E (no test exercises it), but a real footgun for Phase F+.

The HLD §E-c says:

> "`WM_CREATE`: w = 0, l = `CREATESTRUCTA*`. Crack: dereference via
> `*(CREATESTRUCTA*)l` and pass by reference. Return value: `false`
> from `EvCreate` ⇒ creation aborts (returns `-1` from
> `WindowProc`); `true` ⇒ proceed (returns 0)."

The HLD §E-b macro proposal:

```c
#define EV_WM_CREATE      if (msg == WM_CREATE) { CREATESTRUCTA *_cs = (CREATESTRUCTA *)(l); if (this->EvCreate(*_cs)) return 0; else return -1; }
```

The **actual** macro (`src/pp.rs:439`):

```c
#define EV_WM_CREATE if (msg == WM_CREATE) { CREATESTRUCTA *cs_; cs_ = (CREATESTRUCTA *)l; return (LRESULT)this->EvCreate(cs_); }
```

Two divergences from the HLD spec:

1. **Pointer not reference.** The HLD's `EvCreate(CREATESTRUCTA& cs)`
   is realised as `EvCreate(CREATESTRUCTA *cs)` (`src/pp.rs:304`) —
   pointer not reference. This matches the cracker's `(CREATESTRUCTA
   *)l` cast naturally and avoids by-reference ABI surface. Honest
   simplification, surfaced in the E1 commit message ("Cracking
   signatures use `int x, int y` rather than `TPoint& pt` for v1").
2. **No bool-vs-int translation.** The HLD's spec was `bool`
   semantics ("true = continue, false = abort"); the macro
   short-circuits to `return (LRESULT)this->EvCreate(cs_)` —
   passing the int return value DIRECTLY to Win32. Win32's
   raw `WM_CREATE` return semantics are: `0` (or any non-negative)
   = continue, `-1` = abort. So the runtime behaviour is Win32-
   native, not the HLD's bool spec.

The default `EvCreate` returns `0` (`src/pp.rs:304`), which under
Win32 raw semantics means "continue creation" — the right default,
by accident. A user override returning `1` (HLD's `true`) means
"continue" (correct). A user override returning `0` (HLD's `false`)
means **"continue"** in Win32 — **opposite of the HLD's stated
abort intent**.

Phase E ships **no test** that uses `EV_WM_CREATE` or overrides
`EvCreate`, so this drift cannot surface as a runtime bug in Phase
E itself. The B-6 (`bool` keyword not a type) workaround is what
forced the int return type. The MINOR is twofold:

- The HLD prose committed to a bool semantic that the implementation
  inverted. Either the HLD should be amended to say "int: 0=continue,
  -1=abort (Win32 native)" or the macro should translate (e.g.
  `return this->EvCreate(cs_) ? 0 : -1;`). The current shape is the
  worst of both — looks bool-ish at the call site, runs as raw
  Win32, no comment in the macro to flag the divergence.
- A Phase F+ user (writing per the HLD spec, returning `false` to
  mean "abort") will silently get "continue" instead. This is the
  exact "no automated oracle for a future divergence" problem
  MINOR-2 highlights at the vtable level.

Files:
- `src/pp.rs:304` (`EvCreate` default `return 0;`)
- `src/pp.rs:439` (the macro's `return (LRESULT)this->EvCreate(cs_);`)
- HLD §E-b decision (the bool-spec prose) and §E-c (the
  "false ⇒ aborts" prose)

Recommended fix (small): change the macro to `return
this->EvCreate(cs_) ? 0 : -1;` to honor the HLD's spec. Or,
preferred: amend the HLD to say "int: 0=continue, -1=abort
(Win32-native)" and put a `/* int: 0=continue, -1=abort (Win32 raw
semantics, B-6 workaround) */` comment on the EvCreate default and
the macro. Either path matches the implementation to the
documentation.

#### MINOR-4 — Vtable bloat is +8 on TWindow even for non-OWL polymorphic uses (no impact in Phase E; flag for Phase F+ scope).

Every polymorphic user of `TWindow`, even a class that overrides
zero EvX virtuals, now carries +8 inherited vtable slots (the
EvX virtuals). The runtime cost is one vtable per `TWindow`-derived
class (a one-time global, not per-instance), so the absolute cost
is small. But:

- A Phase-I app's `TFrameWindow`-derived `TMyWin` with a
  `TDialog`-derived `TAboutBox`-derived class would carry the
  full 8-slot EvX set into the about-box, even though about-boxes
  typically don't need EvLButtonDown, EvMouseMove, etc. — pure
  vtable carry. The HLD §Risks #2 calls this out: "every TWindow
  instance pays +8 vtable slots even with zero overrides", with
  the mitigation "measure in E1's structural test" — see MINOR-2
  (the measurement wasn't done).

Not a Phase E bug; flagging because the HLD committed to making it
observable and that commitment was not honored (MINOR-2's twin).

## Outstanding risks for Phase F+

### R1. The `EvCreate` int-vs-bool divergence (MINOR-3) is the most likely real footgun.

Phase F is the first plausible time a target app's `EV_WM_CREATE`
handler returns `0` to mean "abort" per the HLD spec — and gets
"continue" in Win32. Should be fixed in E5 review (either macro
translation or HLD amendment), well before any real handler is
ported.

### R2. Phase F+ message handlers WILL exercise more `EV_*` shapes; v1 macros use no `__VA_ARGS__` / `#` / `##`, but Phase G needs `EV_COMMAND(id, member)`.

The HLD §Risks #1 already flagged: v1 macros are object-like or
single-arg function-like, no token-pasting or stringizing. Phase G's
control-ID-specific `EV_COMMAND(IDM_FILE_NEW, CmFileNew)` will need
`##` to mangle the member name + ID, **AND** member-function pointer
syntax (`&TMyWin::CmFileNew`) — i.e. the deferred B-10 codegen
feature. The HLD records this as a Phase-G boundary, not E5.

### R3. `TClientDC` (and `GetDC`/`ReleaseDC`) is the next likely GDI gap.

The HLD §B-12 deferred `TClientDC` because v1's E3 paint oracle
draws inside WM_PAINT (`TPaintDC` covers that). Any Phase-I OWL app
that does asynchronous redraw outside WM_PAINT will hit it. Adding
`GetDC`/`ReleaseDC` USER32 rows + `TClientDC` follows the same
shape as E2's BeginPaint/EndPaint addition — copy-paste.

### R4. `switch` parser gap remains (HLD §Risks #4).

Every per-event virtual is currently `void EvX(...)` with `if`-chain
discrimination if the user wants to differentiate by an inner ID
(e.g. `EvCommand` switching on `cmdId`). Real OWL handler code
tends to switch on these. Not Phase-E-blocking; will surface as a
quality-of-life gap when Phase G adds `EV_COMMAND(id, member)`.

### R5. The "every OWL TU imports GDI32 even if it doesn't draw" pattern (commit 18c9070 design note) is a real Phase-I forward problem.

A Phase I survey of real Borland OWL apps will hit OWL apps that
don't paint at all — pure dialog wrappers, command-only apps, etc.
Those will currently pull in TextOutA/BeginPaint/EndPaint imports
they don't use, bloating the IAT. The deferral is honest ("Per-method
dead-code-elimination would change this; deliberately deferred —
house style 'no speculative optimization'"), but Phase I should
revisit whether to add per-method DCE before shipping a Phase I
demo binary. Recorded for the Phase I scope review, not Phase F.

### R6. MINOR-2 (vtable observability) will let silent slot-count drift slip through Phase F+ extensions.

If Phase F (or G) adds 3 more EvX virtuals (`EvRButtonDown`,
`EvRButtonUp`, `EvChar`) without a test asserting the slot count,
the bloat is invisible. Fixing this in E5 — adding the slot-count
oracle the HLD §E-a Decision 3 committed to — would close the gap
before Phase F has a chance to grow.

## Conclusion

Phase E E1–E4 is a real Phase milestone, honestly enforced. mdbcc —
already proven (Phase D D5) to compile a real OWL app that opens a
window and exits cleanly — now compiles a real OWL app that
**responds** to a synthetically-injected user-input event, dispatches
it through a response-table-defined virtual handler, mutates
observable state, and reports the count on clean exit with code 0.
The Phase-E milestone oracle
(`o6_e4_click_owl_counts_lbuttondowns_via_response_table`) ran here,
deterministically, in ~0.22 s alongside seventeen sibling gui tests,
with the full 225-test suite green and clippy clean.

The architectural decisions are correct and minimal:

- **Mechanism choice (HLD §E-a Option (b)).** Virtual-dispatch
  lowering of `EV_WM_*` macros — each one expands to an
  `if (msg == X) { ...crack...; this->EvX(...); return 0; }` block
  inside the user's `cls::WindowProc` override. Member-function
  pointers are not introduced; codegen is unchanged.
  `END_RESPONSE_TABLE` falls through to a non-virtual
  `base_WindowProc` helper that calls `DefWindowProcA` — the
  honest workaround for the missing qualified-call-in-expression
  parser grammar (HLD §E-b decision 1).
- **TPaintDC RAII (HLD §E-d).** `BeginPaint` in ctor, `EndPaint`
  in virtual dtor, by-reference `TWindow&` binding (Phase B-proven
  for derived → base ref).
- **First GDI32 row (HLD §E-f E3).** `TextOutA` added to
  `WIN32_IMPORTS` with no codegen change; the C1b multi-descriptor
  `.idata` machinery handles k=3 by construction; structurally and
  on-OS-loader proven by the E3 structural test plus the E3/E4
  liveness tests.
- **No compiler change** (HLD's central discipline). `src/{ast,
  parser,codegen,compile,lib,lexer,main}.rs` are byte-identical
  pre/post Phase E. Phase E is **pure data growth** in `src/pe.rs`
  + intrinsic-header body growth in `src/pp.rs` + test growth in
  `tests/gui.rs`. **Verified by `git diff --stat`.**
- **Console byte-identical** (HLD §E-g). `tests/pe_imports.rs`
  (the 169-byte GOLDEN_IDATA console lock) was not re-blessed in
  any of the five commits (`git log --follow --oneline` shows
  exactly one commit, `df4f7c8`, the C1a creation). The console
  invariant is enforced by an unmodified golden, not by silent
  re-capture.
- **Anti-hang machinery** is comprehensive: every E3/E4 liveness
  test reuses C4/D2/D3/D5 watchdog/RAII verbatim; total worst-case
  per test is well under 20 s; empirical gui suite is 0.22 s for
  18 tests including 4 desktop-gated liveness probes that **launch
  real GUI processes and synchronously inject cross-thread Win32
  messages**.
- **Synchrony claims are correct.** `UpdateWindow` synchronously
  sends `WM_PAINT` per MSDN (bypassing the application queue);
  cross-thread `SendMessageA` blocks until the receiving thread's
  WindowProc returns. Both are well-known Win32 guarantees that
  the E3 and E4 oracles rely on, and the code does rely on them
  correctly (no spurious sleeps, no polling for stdout, no race
  surface).

The MINOR findings are all documentation drift or one missed HLD
commitment, not implementation defects. The strongest one (MINOR-3,
the `EV_WM_CREATE` int-vs-bool divergence) is harmless in Phase E
itself but will trip a real handler in Phase F+ — recommended fix in
E5 review. The HLD's vtable-observability commitment (MINOR-2) being
unmet is the second priority; the Phase D pattern of "structural
test catches silent growth" deserves a slot-count assertion before
Phase F starts adding EvX virtuals.

Approve E1–E4 for merge. Recommendations for E5 review:

1. Either fix the EV_WM_CREATE macro to translate `bool→0/-1` as
   the HLD specified, OR amend the HLD §E-c to "int: 0=continue,
   -1=abort" and put a one-line comment on the macro + the
   EvCreate default explaining the Win32-native semantic. **Pick
   one** (MINOR-3).
2. Add a structural assertion of TWindow's vtable slot count to
   close the HLD §E-a Decision 3 commitment (MINOR-2).
3. Decide-and-act on B-8 (remove `_OwlApp` or add
   `GetApplication()` — recommend remove per HLD §B-8 since no
   E1..E4 handler consumed it).
4. Decide-and-act on B-9 (leave deferred per HLD recommendation
   unless a Phase F+ regression surfaces it).
5. Decide whether to amend the HLD's "functionally identical"
   prose for `base_WindowProc` to add the WM_DESTROY caveat
   (MINOR-1).
