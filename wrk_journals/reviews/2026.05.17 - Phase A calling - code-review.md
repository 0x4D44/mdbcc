## Strengths (genuinely solid)

1. **Byte-identical regression claim is rigorously sound.** Verified
   against the committed prologue (`git show HEAD:src/codegen.rs`,
   ~l.421): the old code already emitted `48 81 EC` + a **4-byte
   `u32`** immediate (always imm32, never imm8) and a per-param
   `ARG_SPILL[i]` + `(-off).to_le_bytes()` loop. The new code
   (`codegen.rs:442-462`) emits the identical opcode+imm bytes, takes
   the `i < 4` branch with byte-for-byte identical spill encoding, and
   the `run` re-patch (`codegen.rs:470-477`) overwrites the same 4
   bytes with the **same value** when `max_stack_args == 0`
   (`io_out.max(8*0) == io_out`, and
   `frame == (frame_fixed + io_out + 15) & !15` is algebraically
   identical to the old `(vars + ntemps*8 + 32 + outgoing + 15) & !15`).
   The diff is purely additive on the new branches. ≤4-param /
   io-only functions are provably unchanged — same argument class as
   the PE-layout regression proof. This is the single most important
   correctness property and it is airtight.

2. **The load-bearing "no push/pop" invariant is real and exploited
   correctly.** The only `push` machine instruction emitted anywhere
   in codegen is `0x55` (push rbp) in the prologue; there is no
   `push`/`pop`/`pushf` elsewhere — every temporary lives at
   `[rbp-off]`. Therefore `rsp` is constant between prologue and every
   `call`, which is exactly what makes the `[rsp + 0x20 + 8*(i-4)]`
   outgoing-arg store (`codegen.rs:1688-1691`, `:1391-1395`) and the
   `[rbp + 16 + 8*i]` incoming-param load (`codegen.rs:455-461`)
   correct. The HLD's invariant analysis is borne out by the code.

3. **16-byte alignment at `call` is preserved.** `frame = (.. + 15)
   & !15` is always a 16-multiple; OS entry `rsp%16==8`, `push rbp`
   → `%16==0`, `sub rsp,frame` keeps `%16==0`. `frame_fixed =
   vars_bytes + 160` (160 = 16*8 + 32, both 16-aligned; `vars_bytes`
   8-aligned) and `outgoing` is an 8-multiple, so the round-up is
   correct. Deferred frame sizing does not perturb alignment.

4. **Indirect-call register/callee marshalling order is correct.**
   `emit_indirect_call` (`codegen.rs:1340-1399`) evaluates all args to
   temps first, then the callee pointer **last** into its own temp
   (cannot be clobbered by arg evaluation), then loads arg registers,
   then `load_tmp(fp)` into RAX, then `FF D0 call rax`. The RAX clobber
   during stack-arg stores precedes the fp→RAX load, so it is benign.
   This mirrors `emit_call`'s lead/`this` discipline — consistent.

5. **Temp allocator balance is exact.** `emit_indirect_call` allocs
   `N` (slots) + 1 (fp); frees fp then `N` — net zero. The
   `debug_assert_eq!(self.cur_tmp, 0)` at end of `run`
   (`codegen.rs:478`) is a real oracle that would catch imbalance in
   the test build (and all suites are green).

6. **Determinism fully preserved.** The new `RipRef::Func` arm
   (`pe.rs:284-291`) only does `offsets.get(...)`. `offsets` is a
   HashMap but is *built* by iterating `module.funcs` (a Vec, source
   order) with a layout cursor; it is never iterated to produce bytes.
   `sigs.funcs` is likewise lookup-only. `max_stack_args` is a
   deterministic max-fold over emission order. No HashMap iteration
   feeds emitted bytes anywhere in the diff. The `RipRef::Func`
   relocation math (`text_rva + off`, then shared
   `disp = target_rva - next_rva`) is identical in shape to
   `RipRef::Data` — correct rip-relative `lea`.

7. **Test design is strong.** Weighted sums
   (`a + b*2 + c*3 + ...`) make every argument *position* observable —
   a single mis-slotted stack arg changes the result, so a stack-ABI
   bug cannot pass silently. `many_args_and_printf_in_same_function`
   directly exercises the `max(io_out, 8*max_stack_args)` interaction
   the HLD flagged as a risk. `nested_call_passes_more_than_four_args`
   covers a >4-arg call inside a >4-arg callee. The portable corpus
   is strict-C89, deterministic, flag-free — appropriate for the
   three-way O2/O3 oracle. Honest, oracle-grade tests.

8. **Deferrals are honest and explicit.** Member-function pointers
   (this-adjustment ABI) are clearly out of scope and routed to
   Phase E in the HLD; struct-by-value through an indirect call is a
   clean error (`codegen.rs:1359-1365`), not silently wrong — matches
   house style ("error clearly, never silently wrong").

## Findings

### MINOR

- **`expr_type` of a fn-ptr *variable* call returns `int`
  unconditionally** — `src/codegen.rs:2353-2364`
  (`Expr::Call` arm). When `fp` is a function-pointer variable,
  `fp(x)` parses as `Expr::Call{name:"fp"}` (parser `primary`,
  `parser.rs:1808`). `expr_type` for `Expr::Call` looks up
  `self.sigs.funcs.get("fp")` (None for a variable) and falls back to
  `Type::int()`. The *value* path is correct (`gen_call` reroutes to
  `emit_indirect_call`, RAX holds the right bytes), but the *static
  return type* is wrong whenever the fn-ptr does not return `int`
  (e.g. `char *q = fp(); /* later */ *q` would mis-scale, or
  `long r = fp();` mis-widen). Note the asymmetry: the
  `(*p)(x)` / `tbl[i](x)` form lowers to `Expr::CallPtr`, whose
  `expr_type` (`codegen.rs:2374-2382`) **does** correctly return the
  pointee's `ret`. Only the bare-ident-named-fp-variable form is
  wrong. Not exercised by Phase A's int-returning corpus, so no test
  regression, but a latent correctness gap that will bite the first
  non-`int`-returning callback (plausible in OWL/Win32:
  `LRESULT (*)(...)`, `HWND (*)(...)`). Suggested fix: in the
  `Expr::Call` arm, before the `Type::int()` fallback, if the name
  resolves to a local/global of `Ptr(Func{ret,..})`, return `*ret`
  (mirroring the `CallPtr` arm / the `gen_call` shadow check at
  `codegen.rs:1317-1328`). Low-risk, additive, and removes the
  asymmetry.

- **Release-mode temp overflow is silent stack corruption (pre-existing,
  aggravated by Phase A)** — `src/codegen.rs:535-540`. `alloc_tmp`
  guards `cur_tmp <= max_tmp` with `debug_assert!`, which is compiled
  out in release. On overflow in release, `temp_base + (idx+1)*8`
  addresses **past the 128-byte (`ntemps*8`) reserved temp region**,
  silently clobbering adjacent frame storage — not a clean
  `CodegenError`. This is a pre-existing property of the temp
  allocator (unchanged by Phase A), but Phase A *raises* peak temp
  pressure: `emit_call`/`emit_indirect_call` hold all `N` arg slots
  (plus `fp`) simultaneously across the load loop, and nested
  many-arg calls stack these. The HLD explicitly defers
  "nested many-arg calls vs the 16-temp budget", so the deferral is
  honest, but the *failure mode* (silent corruption vs hard error) is
  worth recording. Suggested (out of Phase A scope, track separately):
  promote the overflow guard to a real `Result`/`CodegenError` so a
  pathological program fails loudly instead of miscompiling.
  Acceptable to defer for Phase A given the documented scope, but it
  should be an explicit tracked item, not left implicit.

### NIT

- **A libc/intrinsic name shadowed by a local fn-ptr is not reroutable**
  — `src/codegen.rs:1309-1311` vs `:1317`. `gen_call` checks
  `is_builtin(name)` (→ `gen_libc`) *before* the function-pointer
  shadow check. A local `int (*memcpy)(...)` called as `memcpy(...)`
  would take the intrinsic path, not the indirect path. This is an
  extreme edge case (shadowing a libc name with a same-named local
  fn-ptr), consistent with the existing builtin-priority precedent,
  and absent from any plausible OWL/Win32 code. Record as a known
  limitation; no action needed for Phase A.

- **`emit_indirect_call` duplicates the stack-arg store sequence from
  `emit_call`** — `src/codegen.rs:1380-1395` vs `:1685-1692`. The
  `mov rax,[rbp-t]; mov [rsp+0x20+8*(i-4)],rax` (and the `i < 4`
  `ARG_LOAD[i]`) blocks are byte-identical between the two functions.
  Minor duplication; a shared `fn emit_arg_into_slot(reg_idx, tmp)`
  would DRY it and guarantee the two paths can never diverge in the
  ABI encoding. Optional, low value now (both are tested and
  identical); worth a note so a future ABI tweak updates both.

- **`param_type_list` parameter names are parsed and silently
  discarded** — `src/parser.rs:966-989`. Correct for a type-only
  context and documented in the doc-comment; noting only that array
  parameters decay via `ty.decay()` (correct: `int a[]` → `int*`),
  and `void`-only is special-cased correctly. No issue — called out
  as reviewed-and-fine.
