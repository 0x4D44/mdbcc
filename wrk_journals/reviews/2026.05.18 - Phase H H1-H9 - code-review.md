### MAJOR (fix before close, doesn't block roadmap)

#### MAJOR-1 — `Expr::Str { wide: true }` is silently demoted to a narrow byte-string by the parser; H9's wide-string concat tests only verify the LEXER's rejection of mismatched narrow+wide, masking the fact that wide strings have no end-to-end semantics

**Files**: `src/parser.rs:1418` (initializer Str arm) and `src/parser.rs:2117-2125` (primary Str arm); `src/lexer.rs:499-528` (`lex_string` correctly carries the `wide` flag on the token); `tests/cpp_string_concat.rs` (7 tests, NONE test that a wide string survives parsing as wide).

**Symptom**: The H9 implementation's adjacent-concat loop in `lex_string` correctly handles `L"abc" L"def"` at the lexer, producing one `Str { bytes: …, wide: true }` token. But BOTH parser sites that consume `TokenKind::Str` discard the `wide` field via `if let TokenKind::Str { bytes, .. } = …` — the `..` silently drops the `wide` bit. The resulting `Expr::Str(bytes)` has no encoding marker. A user's `wchar_t* s = L"hello";` would silently treat the literal as a narrow `char[6]`, which is the wrong type AND the wrong byte layout (a wide string should be 12 bytes of UTF-16, not 6 bytes of UTF-8). The lexer-side `wide: true` machinery is decorative.

**Verification** (read-only): `grep -rn "wide" src/parser.rs` returns 0 hits, confirming the parser is wide-blind. The H9 `tests/cpp_string_concat.rs` "wide" tests are inside the lexer's unit tests (lines 920-1010 of `src/lexer.rs`) and verify only that the lexer correctly merges or rejects — they do not run through the parser end-to-end with a wide-string-typed destination.

The HLD §H9 explicitly said "Mixing wide and narrow fragments is an error per C standard." That's faithfully implemented at the lexer. But the silent narrow-demotion-on-parse means *any* successful wide-string parse is also wrong. The HLD's "smallest H increment" framing is true for the lexer-only fix, but the wide-string feature it nominally supports has a downstream gap.

**Fix sketch** (two options, ~5 lines each):

- **Strict** (recommended): at the parser sites, reject `TokenKind::Str { wide: true, .. }` with a clean diagnostic ("wide string literals (L\"...\") are not yet supported; use narrow strings — wide is H-future"). The lexer's wide-handling becomes correct-for-rejection. Add a `tests/cpp_string_concat.rs::wide_string_rejected_at_parse` test.
- **Lenient** (defer): record the `wide` flag on `Expr::Str` and route through codegen; emit UTF-16 byte sequences. Substantially more work (requires `wchar_t` type handling, printf %S, etc.) — best left as H-future-8.

**Severity rationale**: I rate this MAJOR (not BLOCKER) because (a) no in-tree user is affected (no test writes `L"..."`), (b) the fix is mechanical, (c) the HLD anticipated wide-vs-narrow as an error case so the right design exists. But it cannot be a MINOR because the user-visible symptom is precisely "the compiler silently emits the WRONG TYPE and the WRONG BYTES" — the exact "never silently wrong" violation Phase F's review and Phase G's review both penalised at MAJOR. Direct analogue to Phase G's MAJOR-2 (DIALOGEX accepted at parser, silently emitted as classic DLGTEMPLATE at writer).

#### MAJOR-2 — SEH runtime (H4a+H4b) has narrow test coverage that misses several runtime-critical cases that Phase-I OWL `TXOwl` hierarchies will trip

**Files**: `tests/cpp_exceptions.rs` (29 tests total — 16 parser/error + 4 structural + 9 runtime). The 9 runtime tests (t17–t25) cover: bare int catch, nested try, cross-frame throw, no-throw fall-through, class-by-ref, derived-catches-base, by-pointer, first-match-wins, deep 4-level hierarchy. None of the following are tested.

**Cases the SEH runtime is silently UNTESTED on:**

1. **Throw during constructor.** A `class C { public: C(int x) { if (x<0) throw 42; }` invoked as `C c(-1);` — the object is partially constructed. If C also has fields with their own ctors, those fields' dtors must NOT run on unwinding past `c`. The current implementation has no notion of "partially constructed object" — `track_dtor` would never have been called for `c`, so the no-dtor side is correct by omission; but a class C with a base would have the base's ctor run before C's body throws — the base's dtor should run. Not tested.

2. **Throw during destructor.** `~Foo() { throw 9; }` — the dtor itself throws. Standard says this terminates if already in unwinding, but it's a runtime concern for Phase-I OWL where destructor-throws are common in resource-cleanup paths.

3. **Throw across function-pointer indirect call.** `void (*fp)(void) = boom; try { fp(); } catch (int e) { ... }` — the `call [rax]` (or `call rax`) instead of `call rel32`. The personality function is location-agnostic and should handle this, but it's never exercised.

4. **Throw across virtual-method dispatch.** `try { ptr->virtual_method(); } catch (...) { … }` — the call goes through `call [rax+disp]`. Same as case 3 but through vtable.

5. **Explicit-rethrow `throw e;`** (with caught exception captured by name). `catch (int e) { ... ; throw e; }` should be supported via the existing throw path; t18 nests this case (`throw e1 + 1;`) BUT the rethrow-the-same-value pattern is closer to a real OWL idiom. Not directly tested.

6. **Two same-level catch clauses with bases matching different chains.** `try { throw D(); } catch (A1 &) {} catch (A2 &) {}` where D derives from BOTH A1 and A2 — impossible under single inheritance (H4b model), so the test gap may be unreachable. But two unrelated base catches `catch (Base1 &) {} catch (Base2 &) {}` with `throw Base1Derived()` should match Base1 → not Base2. The first-match-wins test t24 only covers int-vs-class, not two-class-types.

7. **Empty catch body** (legal C++). `catch (int e) {}` — the no-decl path. Not tested.

8. **Throw within a deeply-nested try.** 5+ levels of nested try/catch in a single function. Not tested; HLD risk #2 calls scope-table format "intricate."

**Verification** (read-only): `grep -E "ctor.*throw|dtor.*throw|fp.*throw|indirect.*throw|callptr.*throw" tests/cpp_exceptions.rs` returns 0 substantive matches. Comments and section headers do not exercise the code paths.

**Fix sketch**: Add 4-6 of these as runtime tests in `tests/cpp_exceptions.rs::runtime`. Each is ~15-25 lines. Cases (1), (2), (3), (5) are the highest-value for Phase-I. The infrastructure (run_src, assert exit code) is already in place — pure additions.

**Severity rationale**: MAJOR because the SEH runtime is the largest H risk per the HLD's own risk register, and Phase I (OWL apps) is the explicit forcing function for cases the H4a/H4b runtime currently does not exercise. Failures will surface as `STATUS_BAD_FUNCTION_TABLE` process-kills, not clean diagnostics. Each missing test is silent today (the program doesn't exist) but will become a debug-painful runtime crash on the first Phase-I app that hits it. Not a BLOCKER because no in-tree user is affected and the fix is purely additive (no implementation change needed for cases 1, 3, 4, 5, 7, 8 — they may already work).

#### MINOR-1 — H5 does not handle trailing-const on member functions, so the canonical OWL container pattern `T& operator[](int)` + `const T& operator[](int) const` is unreachable

**File**: `src/parser.rs:198-218` (`decl_specifiers` accepts `const` but trailing-const after `)` is not parsed); empirically verified by compiling `int get() const { return v; }` and seeing the loud diagnostic `expected '{'` at the `const` position.

The HLD §H5 explicitly cited this pattern: *"every container's `T& operator[](int)` plus const overload"*. mdbcc errors LOUDLY on the trailing `const` rather than silently misparse — that is the right house-style behaviour given the deferral, but the deferral means a real OWL container can't be written without textual surgery. Mitigation: parse the trailing `const` and add it to the mangling scheme (e.g. `foo$iK` where K denotes const-method). One-day fix; defer to Phase I if no app needs it.

#### MINOR-4 — H7 chained `a = b = c` when operator= returns BY VALUE (not by reference) silently misuses the return value as an address in the rare `(a = b) = c` lvalue-context

**File**: `src/codegen.rs:2651` (`Expr::Assign { lhs, .. } if self.has_op_method(lhs, "operator=")? => self.gen_expr(e)?`).

When operator= returns `V&` (the typical case), `gen_expr(e)` leaves the address in RAX — gen_addr correctly returns that address. When operator= returns `int` or `V` (by value), `gen_expr(e)` leaves the value in RAX. The gen_addr arm then treats RAX as an address. If the user writes `(a = b) = c` where `operator=` returns by value, `(a = b)` is not a true lvalue under C++ semantics either — but mdbcc silently accepts the syntactic form and emits a memory store through a garbage address.

Mitigation: in the gen_addr arm, check the return type of the looked-up `operator=` and reject if not a reference. Five-line fix. The H7 brief explicitly said "Don't insert a self-check; user code is responsible" — that's about self-assign, but this is about non-lvalue chaining, a different concern. Verified the chained test (`op_assign_chained` line 393) uses `V& operator=` only.

#### MINOR-5 — H6's `gen_new_array` reads `mul rcx` output only from RAX, silently truncating on `n * elem_size > 2^64`, AND signed-int `n` < 0 sign-extends to ≈2^64 → silent allocation failure → NULL cookie write → AV

**File**: `src/codegen.rs:4886-4888` (`mul rcx` emitted but `rdx:rax` upper word discarded). The journal's "byte count can exceed 4 GB" comment correctly anticipates the 32-bit case but the 64-bit case is not bounded.

Empirically: `int n = -1; int* a = new int[n];` would compute `0xFFFFFFFFFFFFFFFFu * 4 + 8` in `rdx:rax`, RAX = `0xFFFFFFFFFFFFFFF0`, HeapAlloc fails, NULL returned, cookie write at `[NULL]` → AV. Not the worst (it crashes loudly), but the diagnostic is a Windows AV, not a clean error.

Mitigation: before the mul, check if `n` is < 0 (CL emits `cmp rax, 0; js .negative_count_error`) and bail loudly. Or check `rdx == 0` after the mul. Five-line fix. Track as MINOR; no in-tree test hits it.

#### MINOR-6 — H6 array-construction has NO exception-safety cleanup; if ctor of element K throws, elements 0..K-1 leak (no dtor calls, no HeapFree)

**File**: `src/codegen.rs:4914-4954` (`gen_new_array` ctor loop). The loop is a plain forward iteration with no try/catch wrapper. If element 5 of `new T[10]` throws inside `T::T()`, elements 0–4 are constructed and then leaked when the throw unwinds past the loop — the `HeapAlloc`-returned block also leaks (the `block` tmp goes out of scope before any cleanup runs).

Standard says half-constructed array MUST destroy [0..K-1] in reverse order and free the block. C++03 §5.3.4. This is a real OWL pattern (a TString array construction can throw if HeapAlloc fails in element K's body). Mitigation: emit a per-element try/catch via the existing SEH machinery — substantial work, defer to H-future-8.

#### MINOR-7 — H4b shared `.mdbcc_eh_buffer` is sized to the largest polymorphic class in the TU; a multi-threaded program would race on the global buffer

**Files**: `src/codegen.rs:587-596` (`compile_module` allocates one global buffer sized to max-polymorphic-class), `src/codegen.rs:2269-2285` (gen_throw_class memcpys into `.mdbcc_eh_buffer`). Comment at line 2173 honestly notes "mdbcc runs single-threaded so one buffer suffices."

Mitigation: TLS-allocated buffer; defer to H-future-9 since OWL message-loop is single-threaded.

## Recommendation

**APPROVE-WITH-NITS.** Phase H is the largest single phase in the project (9 implementation commits across ast/parser/codegen/pe/lexer; ~4000 LoC of new logic; the project's first SEH runtime; the project's first member-overload mangler; the project's first byte-cookie heap layout). The execution quality is high across every increment I cross-checked — Win64 struct ABI correctness (3/5/6/7 hidden-pointer trap honoured); SEH personality function byte-exact against the 5 fixed integration bugs the journal disclosed; class-hierarchy walking via tyinf is mathematically clean (current = base_of(current) reaches 0 cleanly on a non-polymorphic base); operator overload resolution faithfully reuses Phase A free-fn machinery; H8 closes a genuine pre-existing silent miscompile (`{ int x; { int x = 2; } }` collapsed to one slot) with the minimum AST disruption (zero — codegen-only).

The two MAJOR findings are not in the SEH plumbing but in the SURROUNDING coverage discipline:
- **MAJOR-1** (wide-string parse-time silent narrow demotion) is the third "parser accepts but downstream silently drops" finding in three phases (Phase F's MAJOR-1, Phase G's MAJOR-1+MAJOR-2). The project has a recurring pattern of cleanly-engineered lexer/AST capability that downstream consumers ignore. Each individual instance is small; the pattern is worth a process change — every new AST field should have a `compile_error!` defence in every consumer until a real implementation lands.
- **MAJOR-2** (SEH runtime coverage misses several Phase-I-likely cases) is the natural consequence of an aggressively-time-boxed H4a+H4b. The 9 runtime tests are well-chosen but the missing cases (exception during ctor/dtor, throw across function pointer, explicit rethrow of caught value by name, deeply nested try, two-base-catches at one level) are exactly what an OWL test would hit first.

Before Phase H is declared done, I would address MAJOR-1 (add the parser-side wide-string rejection; the H9 lexer infrastructure is already correct) and add 3-5 of the MAJOR-2 cases (each is ~15-25 lines). MINOR-3 (cross-feature tests) is the highest-leverage backlog item for Phase-I forward-defence; one or two well-chosen cross-product programs would prevent many integration surprises. The other MINORs and NITs can be triaged at leisure.

Once MAJOR-1 and the highest-value MAJOR-2 cases (cases 1, 3, 5 — ctor-throws, throw-via-funcptr, explicit-rethrow) land green, Phase H is a strong foundation for Phase I. The combined A-G-H stack now covers: integer arithmetic + control flow + functions (A), virtual dispatch + single inheritance (B), Win32 imports + entry points (C/D), event/paint runtime (E), floating point (F), .rc resources (G), and the C++ maturation language features (H). The roadmap's "8 of 9 phases" is no longer a stretch — it's a credible claim. Phase I (a real OWL app) is the remaining forcing function, and the only one I can defend with confidence is "the H test suite has rehearsed enough of the language for a TXOwl-style exception hierarchy to compile."
