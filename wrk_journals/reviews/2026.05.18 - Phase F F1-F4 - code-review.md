## Verdict: REQUEST CHANGES — 1 MAJOR (silent-wrong int↔FP arg/cast conversions); 0 BLOCKER

The Phase F vertical slice is impressively well-engineered: every SSE2 encoding I cross-verified against Intel SDM Vol 2 is byte-correct (a non-trivial achievement — `ucomisd` is `66` not `F2`, `xorpd` is `66` not `F2`, `cvttsd2si r64` is the `F2 48 0F 2C C0` form, etc., all right); the Win64 positional ABI handles the slot-skip rule for `(int,double,int,double)` correctly; the FP literal pool is deterministic (bit-pattern interned, insertion-order); the dtoa algorithm is right for every dyadic-rational test input; nothing in `src/pe.rs` or the PE writer's emitted bytes changes for a pure-integer program (the console `pe_imports` byte-identical golden still passes); clippy is clean; all 191 declared tests pass.

However, there is ONE house-style violation that fails the "never silently wrong" bar and is reproducible in two minutes: **`marshal_args` does not call `convert(arg_type, param_type)` between `gen_expr(arg)` and the FP spill, so passing a non-FP argument to an FP parameter silently spills whatever uninitialised garbage happens to be in `xmm0`.** Empirically, `double f(double x){return x*2.0;} int main(void){return (int)f(42);}` compiles cleanly, runs, and returns **0 (not 84)** — the canonical "never silently wrong" failure mode that Phase F sets out to avoid. A secondary thread of the same defect: `convert` itself, for `Type::Int{bytes:8}` ↔ `Type::Float`, emits only the 32-bit `cvtsi2sd xmm0,eax` / `cvttsd2si eax,xmm0` forms, silently truncating `long long ↔ double` casts (`(double)(long long)0x100000000` silently produces 0; `(long long)1.5e10` silently produces an int32-saturated value). Both are deferred in the HLD (F-5/F-9) as honest precision limits — but a deferral that prints "0" instead of "84" for the most idiomatic C-style call (`f(42)` to a `double` param) is not honest deferral; it is silent UB at the boundary the user is most likely to hit. The HLD's §F-e explicitly says marshal_args inserts the FP promotions automatically ("Same site, same shape — one extra typed branch"), which is the fix.

The MAJOR is fixable with ~5 lines (insert a `convert` call inside the `marshal_args` non-by_ref arm, mirror in `emit_indirect_call` and `emit_virtual_call`). The structural / encoding / FP-ABI / dtoa-rounding parts of Phase F are otherwise correct and idiomatic. The DESIGN HLD is excellent (acknowledges every relevant Intel SDM nuance, the Win64 positional-not-greedy rule, and the dyadic-rational test discipline).

## Findings — MAJOR (should fix in Phase F; if not, must be tracked as a backlog item)

### MAJOR-1 — `marshal_args` does NOT call `convert` between argument evaluation and FP spill; silent wrong values when an int (or any non-FP type) is passed to a `Type::Float` parameter

**File**: `src/codegen.rs:2522-2553`, `src/codegen.rs:2148-2168` (`emit_indirect_call`), `src/codegen.rs:1290-1311` (`emit_virtual_call`).

**Symptom**: empirically reproducible in two minutes; I ran:

```c
double f(double x) { return x * 2.0; }
int main(void) { return (int)f(42); }
```

mdbcc compiles cleanly, runs, returns **0** instead of **84**. The root cause is straightforward: `marshal_args` (line 2530) does `gen_expr(a)` (which leaves a 32-bit int in eax for the int argument), then chooses the spill based on the *declared param type* (`is_fp` flag from `ptys[base+i].is_float()` at line 2536 = `true`), then calls `store_tmp_xmm0(t)` at line 2549. **`xmm0` was never written** between `gen_expr` and `store_tmp_xmm0`. Whatever uninitialised garbage was in xmm0 (typically 0.0 for a freshly-started function, but adversarially anything from the previous SSE2 expression in the same function) is what the callee sees. The callee then multiplies that garbage by 2.0 and returns it.

The HLD §F-e explicitly anticipates this: *"Function arg matching (`marshal_args`) — if a `float` arg is being passed to a `double` parameter, insert `cvtss2sd` after evaluating the arg and before the load; same for the reverse and for integer/FP. Today `marshal_args` already does some implicit narrowing for integer args of mismatched size (via `eax`-truncation); Phase F adds the FP counterpart cases. **Same site, same shape** — one extra typed branch."* But the F3 implementation skipped this branch. Worse, **F3's commit message claims the path is correct** (and the existing F3 tests pass because every test passes either a `double` literal/variable to a `double` param or an int to an int param — none exercise the int → double automatic-promotion case that ordinary C code naturally generates).

This is the exact failure mode Phase F's "never silently wrong" discipline sets out to prevent: a user writes `f(42)`, the compiler accepts it without error, the runtime produces a wrong answer with no diagnostic. Compare to the variadic-printf-arg case where `printf("%f", 1)` is rightly rejected with a clean error in `gen_fp_arg_into_tmp` — the non-variadic-FP-arg case lets the bug through silently.

**Fix sketch** (~5 lines):

```rust
// In marshal_args, between gen_expr(a) and the alloc_tmp/store_tmp_xmm0 step,
// after computing is_fp:
let at = self.expr_type(a)?;
let pt = ptys.as_ref().and_then(|p| p.get(base + i)).cloned();
if let Some(pt) = &pt {
    self.convert(&at, pt)?;   // leaves int in eax / FP in xmm0 per `to`'s domain
}
// (existing store_tmp / store_tmp_xmm0 dispatch already routes correctly
// because it consults is_fp = pt.is_float()).
```

The same insert is needed in `emit_indirect_call` (line 2155 onward) and `emit_virtual_call` (line 1298 onward). For variadic (no `ptys`), the existing `expr_type(a).is_float()` fallback correctly keeps the bytes as-is (since variadic FP args are passed as-is, no promotion).

**MAJOR-1 trailer — `convert` itself emits only 32-bit forms for int64 ↔ FP, silently truncating `long long` casts**: `src/codegen.rs:2041-2046`. `convert` unconditionally emits `cvtsi2sd xmm0,eax` (32-bit, treats eax as int32) and `cvttsd2si eax,xmm0` (32-bit, writes only eax). For `Type::Int{bytes:8}` (a `long long`), the upper 32 bits are silently lost. Empirical repro (built and run, deleted):
- `(double)(long long)0x100000000` produces `0.0` (high 32 bits dropped, low = 0).
- `(long long)1.5e10` produces an int32 indefinite `0x80000000` then `movsxd rax,eax` = `0xFFFFFFFF80000000`.

The HLD §F-e explicitly calls for the REX.W form `F2 48 0F 2C /r` for `(long long)d` and the matching `F2 48 0F 2A /r` for `(double)(long long)`. The dtoa already encodes `F2 48 0F 2C C0` correctly (line 3393) — so the encoding is known good; it just isn't routed from `convert`.

**Fix sketch** (~3 lines in `convert`):

```rust
if from.is_integer() && to.is_float() {
    if from.size() == 8 {
        self.emit(&[0xF2, 0x48, 0x0F, 0x2A, 0xC0]);   // cvtsi2sd xmm0, rax
    } else {
        self.emit(CVTSI2SD_XMM0_EAX);                  // 32-bit form, existing
    }
    return Ok(());
}
if from.is_float() && to.is_integer() {
    if to.size() == 8 {
        self.emit(&[0xF2, 0x48, 0x0F, 0x2C, 0xC0]);   // cvttsd2si rax, xmm0
        return Ok(());                                  // already in rax; no widen needed
    }
    self.emit(CVTTSD2SI_EAX_XMM0);                     // 32-bit form, existing
    from = Type::Int { bytes: 4, signed: true };
}
```

If the maintainer prefers to defer the int64 ↔ FP case to a future increment, the strict house-style fix is to **emit a clean `CodegenError`** for `from.size() > 4` (or `to.size() > 4`) — never silently lose bits. The HLD F-9 backlog records the *unsigned* case; the signed case is not currently called out, so this is a real omission either way.

**Severity rationale**: I rate this MAJOR rather than BLOCKER because (a) every existing test passes (no in-tree user is affected today), (b) the fix is mechanical and small, (c) the HLD explicitly calls for the fix at the right site so the design intent already documents what to write. But it cannot be a MINOR or a "tracked backlog" because the **primary user-visible symptom** (a plain C call `f(42)` to a `double` param silently returning 0) directly violates the "never silently wrong" central discipline that Phase F itself asserts. Address before Phase F is declared done.

### MINOR-1 — dtoa integer-part overflow saturates silently for `|x| ≥ 2^63` after scaling

**File**: `src/codegen.rs:3393` (`cvttsd2si r64,xmm0` after the `*10^prec + 0.5` scale step).

Empirical repro (deleted): `printf("%f", 1e20)` prints `"9223372036854.775808"` — visibly wrong, but no compile-time or runtime diagnostic. The `cvttsd2si r64` on an out-of-range double saturates to Intel "indefinite integer" `0x8000000000000000`, which the dtoa then treats as a regular unsigned scaled integer and divmods through the digit loop.

The HLD F-5 acknowledges this and accepts "visibly wrong but never silent UB" for v1. Honest deferral. Not a blocker for v1 (test corpus chooses tame inputs), but worth tracking explicitly in the backlog and possibly worth a runtime guard before the cvttsd2si — `comisd xmm0, [rip+max_pos_for_cvtsi64]; ja overflow_branch` — that emits an inline "overflow\n" message and aborts. Cost: a few opcodes per `%f` call. Cheap honesty.

### MINOR-4 — `%.0f` for negative zero round-trip: implementation choice not documented in HLD or tests

**File**: `src/codegen.rs:3460-3467` (sign-prepend branch), `tests/printf_format.rs::printf_f_zero` (only tests `+0.0`).

Empirical: `printf("%f", 0.0 * -1.0)` (runtime-produced `-0.0`) prints `"-0.000000"` — matches cl/bcc32 default behaviour (the IEEE sign bit is preserved). Good. But this is a real semantic choice that is NOT exercised in `tests/printf_format.rs` (only `+0.0` literal is tested) and the HLD §F-h only said "pick the simpler". Recommend adding one assertion to `printf_f_zero`:

```rust
let src = "#include <stdio.h>\n int main(void){ double a=0.0; double b=-1.0; \
           printf(\"%f\", a*b); return 0; }\n";
assert_eq!(out(src), "-0.000000");
```

so a future change to the dtoa cannot silently flip this behaviour without tripping the oracle.

### MINOR-5 — Variadic FP gate (`gen_fp_arg_into_tmp`) message says "cast it explicitly" but does not mention that variadic with the right type does NOT get auto-promoted to double

**File**: `src/codegen.rs:3235-3238`. The error text is `"printf '%f': argument is not floating-point (cast it explicitly, e.g. `(double)x`)"` — fine — but it does not surface the underlying C99 rule that variadic float-typed args are auto-promoted to double. Today this is benign (mdbcc's `printf` is `gen_io_builtin`, not a real variadic call), but if F-7 ever lands real variadic, this gate becomes load-bearing and the message should reflect "in variadic context".

### MINOR-6 — `float_token` allocates 8 tmps; documented as "5 buffer + ptr + len + sign" which is correct, but no static check guards the 16-tmp budget against multiple %f in one printf

**File**: `src/codegen.rs:3322-3324`, `src/codegen.rs:843-851`. The `tmp_overflow` flag in `Gen` only fires if `cur_tmp > max_tmp = 16`. A single `%f` spec allocates 9 (`fv` + 8 from `float_token`) — within budget. Two sequential `%f` calls free between them, so peak is still 9. But a `printf("%f %f\n", a, b)` is two separate `%f` dispatches — each frees its tmps before the next starts (`fmt_float_spec` ends with 8× `free_tmp` at line 3322). The order is correct. Not a defect; just an observation that the budget *would* fire cleanly if violated. Nothing to fix.

## Findings — NIT (cosmetic / for future cleanup)

### NIT-1 — Comment at `src/codegen.rs:3538-3539` is stale

`// Phase F-1: typing only — every site that would lower an FP value still returns CodegenError until F2 lands.` This was true in F1 but no longer in F2-F4. Strip the F1 caveat.

### NIT-2 — `_b1` through `_b4` in `float_token` mute the unused-binding warning rather than documenting why the bindings exist

`src/codegen.rs:3339-3342`: the `_b1..=_b4` allocations are load-bearing (they reserve consecutive 8-byte slots adjacent to `b0`), but the leading underscore suggests "I don't care about the return value". A short comment `// reserve consecutive 8-byte slots for the right-to-left buffer; addresses derived from b0+8*N` would document the intent. Trivial.

### NIT-3 — `xorpd xmm1,xmm1` in the `LogNot` arm uses inline-bytes instead of a const

`src/codegen.rs:1475`. The other `xorpd xmm0,xmm0` has `XORPD_XMM0_XMM0` const; the `xmm1` form (`66 0F 57 C9`) is inlined as a magic byte string. For consistency, define `const XORPD_XMM1_XMM1: &[u8] = &[0x66, 0x0F, 0x57, 0xC9];` next to `XORPD_XMM0_XMM0` at `src/codegen.rs:564`. Optional.

### NIT-4 — The dtoa's `inf`/`nan` text uses inline-bytes too

`src/codegen.rs:3490,3492,3494` (inf) and `emit_special_text(b"nan", ...)` (nan, called at line 3479). The `inf` path is inlined byte-by-byte because of the conditional minus prefix; the `nan` path goes through `emit_special_text`. Consistent enough. No action.

### NIT-5 — `compile_module` synthesises `.flit.<fn>.<i>` globals but the `<fn>` portion can contain `::` for mangled methods

`src/codegen.rs:402`. `format!(".flit.{}.{}", f.name, i)` will produce names like `.flit.Foo::bar.0` for a method that takes an FP literal. The leading `.` guarantees no C-identifier collision, and the PE writer doesn't validate symbol-name characters (these are internal indices). Fine in practice. Could optionally sanitize for cleanliness if `objdump`-friendliness becomes important.

## Outstanding risks (post-fix)

After fixing MAJOR-1 (the int↔FP arg/cast `convert` insert + REX.W for int64 ↔ FP), the remaining risks for Phase F v1 are:

1. **Dtoa rounding for non-dyadic-rational inputs at the precision boundary.** Today's test corpus is dyadic-rational so `scale + 0.5 + truncate` matches cl/bcc32. For adversarial inputs (e.g. `printf("%.17f", 0.1)`) the v1 path will diverge — and the v1 cap of precision ≤15 mostly contains this. The honest deferral is documented (HLD F-6). Recommend: add a "round-half-to-even" test input (e.g. `0.5` at `%.0f` ⇒ MSVC default is "0", round-half-up is "1") and document which behaviour mdbcc chose so a future change can't silently flip it.
2. **Integer-overflow path of the dtoa** (MINOR-1) — visibly wrong for `|x| > 2^53` or so after scaling, never silent UB.
3. **`float` 4-byte storage rides 8-byte movsd path** — F-future polish, no test pressure today; round-trips through memory could lose the upper 4-byte garbage if external code observed.
4. **NO test asserts module-determinism of `.flit.*` globals across compiles** — the implementation is correct (insertion-order Vec), but a regression test would defend against a future "let's add a HashMap shortcut" PR.

## Conclusion

Phase F is the largest compiler-feature increment since Phase A: ~1500 lines of new logic across AST/parser/codegen, the first SSE2 codegen path, the first FP function-arg ABI, and the first hand-emitted dtoa in mdbcc. The execution quality is high on every front I cross-checked — SSE2 encodings, Win64 positional ABI, FP literal pool, expr_type promotion, variadic-FP rejection, dtoa structure for the chosen inputs. The "no PE writer change" central regression target is preserved; clippy and the full test matrix (191 declared green + 1 ignored) are clean.

The single MAJOR finding is fixable in ~5 lines at the documented HLD §F-e site, and one of the two ~3-line fixes for int64 ↔ FP. Before Phase F is declared done, please address MAJOR-1 (both parts) so that ordinary C-style calls like `f(42)` to a `double` parameter, and casts like `(double)(long long)x`, no longer silently produce wrong values. The other findings are MINOR / NIT and can be triaged at leisure.

Once MAJOR-1 is fixed, Phase F is a strong foundation for F5 (the `pad_field` refactor, %g/%e, the `cvtsd2ss`/`cvtss2sd` for genuine `float`) and a real demonstration that the "incremental compiler-feature" approach taken since Phase A scales to substantial vertical slices without compromising the byte-identical regression argument.
