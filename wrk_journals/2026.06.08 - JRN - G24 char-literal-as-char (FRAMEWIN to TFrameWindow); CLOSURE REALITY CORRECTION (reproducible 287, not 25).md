## G24 (2975cd0) — char literal types as `char`, not `int`

A C++ char literal `':'` has type `char`. mdbcc lowered char literals to
`Expr::Int` (type `int`), so an overload set with char-family parameters tied:
for `string(':')`, `string(char)` / `string(signed char)` /
`string(unsigned char)` ALL needed an int→1-byte conversion → "ambiguous call
to overloaded 'string::string'". OWL **FRAMEWIN.CPP**'s `title += ':'` triggered
exactly this — `string` has no `operator+=(char)`, so the char must construct a
`string`, and the char-family ctors were indistinguishable.

Fix: a new `Expr::Char(i64)` AST variant, distinct from `Expr::Int` **only** in
static type (`Int{bytes:1, signed:true}`). Codegen + constant-folding treat it
identically to `Int(value)` (byte-identical `mov eax, imm32` load), so this is a
pure overload-resolution / typing change with no codegen-byte impact:
- `ast.rs` Expr::Char; `parser.rs` char-token→Expr::Char, `const_eval` +
  `refresh_expr_record_types`; `codegen.rs` gen_expr (load), expr_type +
  rg_expr_type (→char), temp-materializable, array-new count;
  `template.rs` type_of_expr (`f('a')`→`T=char`); `decl.rs` global FP init.

**Gate (full, per the standing G15 lesson):** full suite exit 0; clippy 0; OWL
compile sweep **83→84** (FRAMEWIN flips to OK, **zero new failures**);
char-semantics RUN (arithmetic / switch-case labels / compare / ternary all ==
bcc32, rc=95); new RUN test `i386_char_literal_selects_char_overload` == bcc32.
**Effect:** TFrameWindow's parameterized ctors (`@TFrameWindow@$bctr…`) now
RESOLVE — they are absent from the unresolved set (a railc-direct symbol).

Byte-identity safety confirmed: the "88 byte-identity" tests
(`o1_obj_byte_identity_cli` etc.) are mdbcc-vs-mdbcc **determinism** checks, not
frozen-snapshot locks — a deterministic codegen change cannot break them; the
bcc32-oracle parity tests can only improve (the fix removes a spurious narrowing
`movsx`, matching bcc32). Suite green confirms both.
