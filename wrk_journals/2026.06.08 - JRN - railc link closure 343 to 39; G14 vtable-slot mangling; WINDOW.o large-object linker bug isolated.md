## The OWL-global thunks: a WINDOW.o large-object LINKER bug (NOT a compiler gap)

Chased exhaustively. OWL.CPP **does** define the Win32 thunks
(`-D__WIN32__` ⇒ `BI_PLAT_WIN32` via classlib/compiler.h's
`_Windows`+`__FLAT__` chain, both predefined by mdbcc; the preprocessed body is
the `new TInstanceThunk` Win32 form, not the 16-bit `far`/`MK_FP` one). Proven
defined: `scw.o + OWL.o` (2 objects) **resolves** SetCreationWindow AND
CreateInstanceThunk.

But in the full link they're unresolved — even with OWL.o **explicit** and
present exactly once (lib rebuilt without OWL.o to rule out duplicate-fold).
Bisected to the cause:

- `scw.o + OWL.o` → thunks RESOLVE.
- `scw.o + OWL.o + DC.o` / `+ GDIOBJEC.o` / `+ APPLICAT.o` → still RESOLVE.
- `scw.o + OWL.o + WINDOW.o` → **UNRESOLVED** — and not just WINDOW.o's refs:
  even scw.o's OWN direct `SetCreationWindow` reference goes unresolved, i.e.
  **adding WINDOW.o drops OWL.o's definitions entirely.**

WINDOW.o is the LARGEST OWL object (284 KB ≈ 2× OWL.o/DC.o). It links fine
alone. So: **a large object (WINDOW.o) corrupts the symbol resolution of
co-linked objects** — a per-object scale limit (section-index / symbol-count /
reloc-count field width) in either the COFF writer (mdbcc emits a subtly-bad
object past some size) or mdlink's decode/merge. This is the highest-value next
target: it's a LINKER/COFF bug (no byte-identity-baseline risk), and it likely
gates more than the 5 thunks once large OWL objects participate.

**WdebugMETHOD for the next arc**: decode WINDOW.o vs DC.o section/symbol/reloc
counts; diff against any u16/u8 field in `src/coff.rs` (writer) and
`src/link/*` (reader). The trigger is size-correlated and WINDOW.o-specific.
