# 2026.06.05 — S6: trivial copy/SLICE base-init → bitwise subobject copy (COMPAT.CPP flips)

Commit: **f3746f0** (17th increment of the S6 drive). Files: `src/codegen.rs`
(+57), `tests/end_to_end.rs` (+21). Full gate green (238 e2e + 88 byte-identity

## The gate

Re-probing the failing OWL corpus, three files had a *hard-fatal* (non-deferred)
"no matching overload for call to a CONSTRUCTOR":

- COMPAT.CPP  → `TXOwl::TXOwl`
- COMMDIAL.CPP → `TDialog::TDialog`
- BITMAPGA.CPP → `TDib::TDib`

(The much larger "no matching overload" cluster was POLLUTED: most entries are
inside `note: deferred N inline function(s) [...]` brackets — non-fatal; even
APPLICAT.CPP, which compiles, emits them. Only the three bare `error:` lines are
real gates.)

COMPAT was the cleanest. Its two `TXOwl(` call sites:
- `:63  TXOwl(MapStatusCodeToString(statusCode))` — a `string` rvalue → the
  `TXOwl(const string&, unsigned=0)` ctor. **This resolves fine** (proven by
  reproA2: a static-member-fn string rvalue in a mem-init, with both ctors
  present, compiles).
- `:70  TXOwl(src)` where `src` is `const TXCompatibility&` (a DERIVED class) —
  a base SLICE-copy. **This is the gate.**

## Narrowing (the asymmetry)

Minimal repros pinned the exact trigger — neither ctor alone fails, only both:

| repro | class shape | `X(src)` slice-copy |
|-------|-------------|---------------------|
| B  | `X(unsigned=0)` (1 ctor) | **compiles** (wrongly — see below) |
| B3 | `X(const string&,unsigned=0)` only | compiles |
| B4 | `X(unsigned,int*=0)` only | compiles |
| **B2** | BOTH (2 ctors) | **ERRORS** "no matching overload for 'X::X'" |
| C  | base B has a copy ctor + 2 ctors | compiles (flat-model: B's copy-ctor
field flattens into X ⇒ X gets a synth copy ctor) |

Root cause: a copy/slice ctor call resolves against `Sigs::overloads[Tag::Tag]`,
which **does not contain the implicit copy ctor**. The derived-to-base ref check
in `resolve_overload` (codegen.rs:9825) only matches an *existing* candidate, so
with 2+ user ctors there is nothing to match `src` against.

The ASYMMETRY: with ONE ctor the class lives in `sigs.funcs` (method_target
5728-5764), whose arity-only path **skips the type check** and silently accepts
`X(src)` by picking the wrong ctor (a latent miscompile that *compiles*). With
2+ ctors it lives in `sigs.overloads` → strict `resolve_overload` → hard error.

`needs_synthesis` (codegen.rs:1338) only inspects a class's OWN fields, so a
class whose copy-ctor-bearing member is INHERITED through an *opaque* RTL base
gets no synth copy ctor. TXOwl : TXBase : xmsg — xmsg is opaque in mdbcc's view
(its `string` does not flatten in), so TXOwl is trivial-modeled ⇒ matches B2,
not C. That is why COMPAT fails where a normal derived-copy would not.

## The fix

In `gen_call_with_lead`'s lead-less ctor-CHAINING path, after the S4.2b0
re-resolve on `[src]` fails, a new last-resort block detects the trivial
copy/slice and emits a **bitwise subobject copy** (`emit_struct_copy`) instead
of erroring — mdbcc's existing model for `copy_ctor_symbol == None` (a plain
record). Guard (all must hold; very narrow):

- `args.len() == 2` (a parser-injected `Tag::Tag(this_ptr, src)`),
- `name` is a ctor (`last_component(c) == m`),
- `Tag` is in `overloads` (so the `funcs` 1-ctor path stays byte-identical),
- `copy_ctor_symbol(Tag) is None` (no user/synth copy ctor — a TRIVIAL copy),
- `src` IS-A `Tag` (`base_offset_to(src_id, Tag)` is `Some(off)`).

Emit: dest (`this`, already base-offset-adjusted) → tmp; `gen_ref_arg(src)`
→ address; `lea` by `off` to the Tag subobject; `rdx=src, rcx=dest`;
`emit_struct_copy(sizeof Tag)`.

Scalar/string args (TXOwl's line 63, `TXOwl(unsigned)`) are NOT records IS-A
TXOwl ⇒ the block is skipped ⇒ those keep resolving normally. RUN-verified by
`derived_copy_ctor_slices_base_with_two_ctors_no_copy_ctor` (d2 bitwise-slices
d1's X subobject; returns 24).

## Addendum 2 — S2e (i386 EH) is ~70% LANDED, not "unimplemented" (RUN-verified)

Probed the S2e tail (#28) directly instead of trusting the stale "unimplemented"
label. Finding: the i386 fs:[0] SEH-3 scheme (`build_seh3_handler` + the Win32
try-scope install) is IMPLEMENTED and CORRECT for scalar throws. RUN-verified on
Win11 x64 / WOW64 (`mdbcc -m32 | mdlink -m32`, then execute):
- `throw 42; catch(int)` → **42** ✓
- non-throwing `try` normal path → **7** ✓
- `throw 99` ACROSS a function call (real stack UNWIND through a frame) → **99** ✓

So the hard part (the personality function + fs:[0] unwind through call frames)
already works in i386. The ONLY remaining gap is **class** throws: `throw E(5);
catch(E&)` hits "no encoder pattern for Mov [Gpr64,Gpr64]" because `gen_throw_class`
(codegen.rs:4525) is entirely win64-hardcoded (RIP-relative buffer/vtable lea,
reg64/mem64, rcx/rdx/r8d/r9 RaiseException ABI). The port is precisely scoped in
#28: a `gen_throw_class_i386` behind `target==Win32` (win64 untouched ⇒ byte-
identical) using the existing i386 absolute-DIR32 address helper (~codegen.rs:3251),
the already-target-agnostic `emit_struct_copy`, and a `__stdcall` RaiseException
push-sequence. ONE unknown to settle first: whether the i386 SEH-3 handler already
decodes the `EXCEPTION_MDBCC_CLASS` + 2-arg array for catch-by-ref/ptr matching, or
only the scalar path — if not, the handler's class-dispatch joins the increment.

Why scoped-not-coded here: EH is the worst place for a rushed, partially-verified
change (b12 — silent unwinding corruption passes smoke tests). The class-throw port
+ its RUN-verification (throw/catch/unwind/by-ref/by-ptr) + settling the handler
unknown needs fresh budget to do with rigor; starting it at a long turn's tail
would risk an uncommittable, under-verified EH state. The discovery itself —
**S2e is scalar-complete incl. cross-call unwind; only class-throw codegen remains,
fully scoped** — is the durable progress, and it materially shrinks #28 (and thus
the S2-closure gap) from "big unknown" to "one well-understood codegen port".

## Addendum 3 — IMPLEMENTATION BLUEPRINT for i386 class-EH (byte-level, ready to type)

Designed the full subsystem to the byte. Three coordinated pieces; all-or-nothing
(a codegen-only partial regresses today's clean "not supported" error into a
runtime terminate, so they ship together). All primitives confirmed to exist.

### Piece 1 — `gen_throw_class_i386` (codegen.rs; new fn beside gen_throw_class)
Dispatch: add at gen_throw_class top → `if self.target==TargetKind::Win32 { return
self.gen_throw_class_i386(expr, et); }`. The fn (mirrors gen_throw_int's Win32 path
+ gen_throw_class's buffer/args structure; `alloc_tmp`=8B slots so ONE tmp holds the
4-byte-packed 2-elem args array — i386 ExceptionInformation slots are 4B, not 8B):
```
peel et -> (rec_id, rec_size, RecSrc);  validate id; rec_size<=eh_buffer_size();
buf_idx = globals[EH_BUFFER_NAME];
match src: AddrOf=>gen_addr(expr), Deref=>gen_expr(expr);  src_tmp=alloc_tmp; store_tmp(src_tmp)
// memcpy obj -> buffer (emit_struct_copy wants ecx=dest, edx=src):
emit[0xB9]; reloc Addr32 Data(buf_idx)            // mov ecx, offset buffer
emit[0x8B,0x95]; emit_disp32(-src_tmp)            // mov edx, [ebp-src_tmp]
emit_struct_copy(rec_size)
// 4-byte-packed args array in one 8B tmp: [0]=vtable RVA, [1]=&buffer:
args=alloc_tmp
emit[0xB8]; reloc Addr32 Vtable(rec_id); emit[0x89,0x85]; emit_disp32(-args)      // [ebp-args]   = &vtable
emit[0xB8]; reloc Addr32 Data(buf_idx);  emit[0x89,0x85]; emit_disp32(-args+4)    // [ebp-args+4] = &buffer
// __stdcall RaiseException(EXCEPTION_MDBCC_CLASS, 0, 2, &args):
emit[0x8D,0x85]; emit_disp32(-args)               // lea eax,[ebp-args]
emit[0x50]; emit[0x6A,0x02]; emit[0x6A,0x00]; emit[0x68]+EXCEPTION_MDBCC_CLASS    // push eax,2,0,code
emit_riprel([0xFF,0x15], RipRef::Import("RaiseException"))  // target-aware: Addr32 on Win32
encode(Ud2); free_tmp x2
```
(`emit`/`here`/`emit_disp32`/`riprefs.push(RipReloc{at,target})` per the prologue + gen_throw_int patterns. RipRef in .text -> Addr32/DIR32 on Win32 per to_object.)

### Piece 2 — prologue registration record (codegen.rs:2592 block)
For a try with a CLASS catch, push 2 EXTRA fields FIRST so they land at
[regptr+16]=kind, [regptr+20]=expected-type-RVA — leaving [regptr+8]=pad,
[regptr+12]=frame (and ALL int-only-try byte output) UNCHANGED ⇒ byte-identical
baselines. KEY SNAG found: the prologue runs BEFORE the body, so the catch's
class_record_id (hence its Vtable RVA) is not yet known. Resolution: (a) a body
PRE-SCAN (like `fn_has_seh`) sets `fn_class_catch: Option<usize>` (the catch's
record id); (b) push an imm32 PLACEHOLDER for the type field + record its position
(new `seh_type_patch`), and register the `RipRef::Vtable(id)` reloc POST-body in
run's tail (mirroring `seh_pad_patch`). Only emit the 2 extra pushes when
`fn_class_catch.is_some()`.

### Piece 3 — a SEPARATE `build_seh3_class_handler` (eh.rs; NEW fn, do NOT edit the int one)
REFINEMENT (found while wiring): editing `build_seh3_handler`'s int flow to insert a
class branch necessarily moves its int-match `jne` displacement → a byte-identity
RISK if any i386 `try` program is baselined. AVOID entirely by adding a NEW handler
`build_seh3_class_handler` that class-catch functions install (Piece 2's prologue
pushes ITS VA via `RipRef::Func(SEH3_CLASS_HANDLER_NAME)` instead of the int one).
The int handler + every int-only prologue are then byte-for-byte UNTOUCHED ⇒ the
whole subsystem is byte-additive. Emit the new handler conditionally (mirror the
`funcs.push(build_seh3_handler())` at codegen.rs:1801, gated on "≥1 function has a
class catch"). The class handler is a fresh copy of the int handler's skeleton with:
`cmp ecx, EXCEPTION_MDBCC_CLASS; jne continue_search;` flags test; TYPE GATE
`edx=[ebp+12]`(regptr), `esi=[eax+0x14]`(thrown type RVA), `cmp esi,[edx+20]`
(expected), `jne continue_search`; DELIVER `ecx=[eax+0x18]`(buffer ptr); then the
SAME stash([edx-4])/RtlUnwind/reload/`eax=buffer`/`jmp pad` transfer. The catch pad
is already target-agnostic (stores EAX into the catch slot; for by-ref/by-ptr EAX =
buffer pointer — correct). MINIMAL = exact-type match (non-poly BC++ xmsg); base-
chain typeinfo walk is a follow-on. Because only class-catch functions install this
handler, the int-only-frame false-positive concern is moot.
