Update:
- Arthur explicitly allowed access to `..\mdtpw`, so I reviewed it read-only.
- mdtpw's real pattern is one `[package]` table, upward discovery from current directory, no TOML mode when an explicit source is supplied, relative paths resolved from the manifest parent, hard parser errors for unknown or wrong-typed keys, and a small hand-rolled TOML subset rather than a dependency.
- I revised the mdbcc design to follow that shape more closely.
- The one intentional divergence is a new `mdbcc` project runner instead of changing `bcc`, because `bcc` is the Borland-compatible single-source compiler front end and should not quietly become a project build tool.
- The current design resists profiles, globs, build scripts, resource defines, environment expansion, and incremental dependency tracking. It includes only fields that map directly to existing mdbcc tools: sources, output/name, target, subsystem, include dirs, defines, resources, objects, and libs.

Emotional temperature:
- Calmer now that the sibling precedent is concrete. My remaining discomfort is schema fossilization: once a manifest field exists, it becomes expensive to correct. The best defense is to keep the first version boring, explicit, and heavily tested.

Update:
- Ran three read-only adversarial reviewers: UX/compatibility, implementation/testability, and simplicity/scope.
- All three reported no critical findings.
- The combined findings then went through a short refutation round with the same reviewers.
- Surviving findings: default subsystem should not regress WinMain auto-detection, CLI grammar must be exhaustive, define semantics must be exact, parser gates need to be explicit, path policy must be precise, configured prebuilt object/lib machine mismatches need clear errors, Win32 needs end-to-end validation, and generated object/resource naming needs a real collision policy.
- Weakened findings: exact module/file split should be implementation guidance rather than hard architecture, resource define handling is a clarity decision, and scope exclusions were partly present but needed sharper text.
- I revised the HLD accordingly. The biggest design choices now are manifest-only `mdbcc` v1, omitted `subsystem` means auto, `defines` applies to both C/C++ and `.rc`, absolute outputs are rejected, generated intermediates always stay under `target\mdbcc`, and `link::link` should own machine mismatch validation.

Emotional temperature:
- Productively tense. The review did what it was supposed to do: it turned several fuzzy "we'll figure it out" areas into hard contracts. I am especially glad the subsystem issue was caught before code; silently breaking WinMain projects would have been an avoidable own goal.
