# RailC Win64 OWL Window Bootstrap

Update:
- Resumed after the repeatable Win64 source-stack link and bounded smoke failure.
- Reconfirmed there is no workspace `AGENTS.md` and the working tree still contains the broader RailC source-build campaign changes.
- Inspected the BC45/OWL window bootstrap rather than editing it immediately.
- Confirmed the key 32-bit assumptions:
  - `WTYPES.H` defines `WPARAM` as `UINT`, and `LPARAM`/`LRESULT` as `LONG`.
  - `WINUSER.H` exposes `SetWindowLongA(HWND,int,LONG)` but no pointer-sized `SetWindowLongPtrA` path.
  - `OWL.CPP` builds a heap object containing x86 instruction bytes and installs it with `SetWindowLong(..., uint32(thunk))`.
  - `WINDOW.CPP` recovers `this` from `_EAX`, and also uses `SetWindowLong`/`GetWindowLong` for `GWL_WNDPROC`.
  - `SIGNATUR.H` and `DISPATCH.CPP` still describe several `LPARAM`/`LRESULT` response-table paths as `int32`.
- Wrote the design checkpoint to `wrk_docs\2026.06.13 - HLD - railc win64 owl window bootstrap.md`.
- Recommended a Win64-only workspace overlay/source-slice selection rather than editing `wrk_oracle` or adding a compiler special case.

Current thinking:
- The best first implementation slice is not "port OWL to 64-bit". It is narrower: give the Win64 RailC harness pointer-sized Windows message typedefs and replace OWL's per-instance executable thunk with a static WNDPROC plus `GWLP_USERDATA`.
- `TWindow` already stores `DefaultProc` and `Thunk` as `WNDPROC`, so the object shape can probably stay stable for this slice.
- `CreateInstanceThunk` can return the static dispatcher, `FreeInstanceThunk` can become a no-op, and `StdWndProc` can recover `TWindow*` from `GetWindowLongPtrA(hwnd, GWLP_USERDATA)` before calling `ReceiveMessage`.
- `InitWndProc`, `SubclassWindowFunction`, alias teardown, and `GetWindowPtr` are the call sites that must stop truncating WNDPROC pointers through `uint32`.

Remaining risks:
- The current runtime failure is still only localized to "before a visible window, heap-corruption exit"; the proposed overlay may move the crash without fully fixing runtime.
- The response-table dispatcher layer is probably the next wall because many dispatch functions still carry `LPARAM` as `int32`.
- A global header rewrite would be a bad move. It would touch too much ABI surface at once and make failures harder to attribute.

Emotional temperature:
- I am impatient to try the static-dispatcher overlay because it is the first shape that feels technically honest. I am also wary: this is exactly the kind of legacy framework port where a small-looking typedef change can fan out through every member-function pointer signature. The frustration is that the current crash says "heap corruption", but the strongest source evidence points at callback ABI and pointer truncation. That mismatch is uncomfortable, and it is why I want the next change to be a small, reversible harness overlay with crisp smoke evidence.
