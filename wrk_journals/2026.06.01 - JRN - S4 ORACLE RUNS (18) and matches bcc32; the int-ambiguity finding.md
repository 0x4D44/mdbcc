## The keystone was already committed: `cc07168` (type-aware operator reachability)

The prior session's last commit — type-aware operator reachability — is what
lands this. Before it, `collect_reach_edges` recorded an operator *name* for
**every** binary op / subscript / assignment in the oracle, and `by_component`
(name-only) then pulled **every overload** of that operator across all included
headers — including `cstring.h`'s `string` friend `operator+/==/<<`, which
dragged in the whole `string` API → RTL → libc/CRT. Oracle string-dep count: 32.

`cc07168` makes the reachability typer **aggressive but bounded**: it records an
operator name *only when an operand is provably a record* (`rg_record_id` over a
conservative expression typer with base-chain field/`operator[]`-return
lookup). The oracle's operands are all `int`/`long`/pointer arithmetic, so **no
spurious operator names are recorded**. Result: string-dep 32 → 6, oracle.o
44 KB → 27 KB. The 6 residual undefined symbols are all **dead DATA externs**
(`string::case_sensitive`, `…::resize_inc`, … + CRT globals `_ctype`,
`_osversion`, …) that the parse-time over-approx kept alive but no emitted code
references.

## Why it now LINKS alone (and (B) dead-extern pruning is not needed for the RUN)

`mdlink oracle.o -o s4.exe` succeeds with **no other objects**. The decisive
fact: mdlink **zero-resolves undefined DATA externs** (treats them like C common
symbols), so the 6 dead data externs cost nothing — they are never read (dead
code). The reason 32 deps blocked the link earlier but 6 do not: the 32 included
**function** externs (e.g. `@TStringRef@$bctr$qcui`), and an undefined *function*
extern cannot be zero-resolved (it is code). The typer severed exactly those
function deps. So **the typer alone makes the oracle self-contained enough to
link**; the planned part-(B) "dead-extern pruning" in the object writer is a
cleanliness improvement, **not** a prerequisite for the RUN. (I drafted (B),
hit an E0308, reverted it — the RUN does not need it. Tree stays at `cc07168`.)

## THE FINDING: bcc32 4.52 itself CANNOT compile `TArrayAsVector<int>`

The PLAN's literal oracle uses `<int>`. When I built the bcc32 reference to get
the "matching bcc32" evidence, **bcc32 rejected it**:

```
Error …\classlib\arrays.h 197: Ambiguity between
  'TDArrayAsVectorImp<…,int>::Detach(const int &)' and
  'TDArrayAsVectorImp<…,int>::Detach(int)'
  in function …::Destroy(const int &)
```

This is a real defect in **Borland's own classlib** for scalar `int`. ARRAYS.H
185–202:

```cpp
int Detach( const T& t ) { return Data.Detach(t); }              // 185
int Detach( int loc )    { return Data.Detach(ZeroBase(loc)); }  // 190
int Destroy(const T& t)  { return Detach(t); }                   // 197  <-- ambiguous when T=int
int Destroy(int loc)     { return Detach(loc); }                 // 200
```

With `T=int`, `Detach(const int&)` and `Detach(int)` become an ambiguous pair
for an `int`/`const int&` argument, and `Destroy(const int&)`'s call to
`Detach(t)` cannot resolve. The classlib was written for object/pointer element
types (`Detach(const TPoint&)` vs `Detach(int)` are distinguishable); `<int>`
collapses them. **There is no bcc32 reference exe for `<int>` — so "matching
bcc32" is literally unsatisfiable for the PLAN's literal oracle.**

mdbcc *accepts* `<int>` and runs it to the intuitively-correct 18 (verified) —
i.e. mdbcc is more permissive here. That divergence does NOT bite the real PLAN
goal: the actual BC45 library/OWL source never instantiates `TArrayAsVector<int>`
(it uses object/pointer element types). Whether to add bug-for-bug
ambiguity-rejection compatibility is an **Arthur decision** (filed; my
recommendation: no — it is a classlib defect, not behaviour worth matching).

### The faithful repair: `<long>`

The ambiguity is **`int`-specific** (the 2nd overload is literally `Detach(int)`).
Any non-`int` arithmetic type avoids it. `<unsigned>` hits a *different* ambiguity
deeper in `TMCVectorImp` (187), but **`<long>` and `<double>` compile cleanly
with bcc32**. `<long>` preserves the integer-arithmetic semantics of the oracle,
so it is the faithful oracle that *both* compilers build:

| oracle                     | bcc32 4.52      | mdbcc (win64)   |
|----------------------------|-----------------|-----------------|
| `TArrayAsVector<int>`      | **REJECT** (amb)| accept → 18     |
| `TArrayAsVector<long>`     | **18**          | **18**  ← MATCH |
| `TArrayAsVector<double>`   | 18              | (untested)      |
| `TArrayAsVector<unsigned>` | REJECT (amb 187)| —               |

### The bug — quoted `#include "dir\file.h"` of a real `-I` header silently stubbed to EMPTY
`SearchPathResolver::resolve` tried the era-stubbing `DefaultResolver` FIRST for
quote includes. That fallback stubs every unknown header to empty (it never

source uses pervasively) → resolved to an EMPTY body → vectimp.h's

And NO "cannot open" diagnostic (the stub returned `Some(empty)`) — a silent
miscompile of the include graph. The `<...>` arm never hit this because system
includes search real `-I` dirs first.

Fix: for quote includes, try the real local file (TU base dir) then real `-I`
dirs BEFORE the stubbing fallback — mirroring the `<...>` arm. Genuinely-absent
headers still stub (leniency preserved). Verified: preprocessed STREAMBL.H now
carries 8 `TISVectorImp`/`TMISVectorImp` decls (was 0); the parse-acceptance

### The TIME.CPP bug — a stale (size:0) record layout defeats overload resolution
`TIME.CPP:95` `BuildLocal(endMarch.Previous(SUNDAY)+7, 2)` failed with "no matching
overload for operator+". Reduced to: `endMarch.Previous((DayTy)0) + 7` FAILS but
`TDate p = endMarch.Previous((DayTy)0); p + 7` WORKS. A `MDBCC_TRACE_OVL` probe in
`resolve_overload` was decisive:
- rvalue operand argty = `Record{id:6, size:0, align:1}` (a size:0 STUB)
- lvalue operand argty = `Record{id:6, size:4, align:4}` (complete)
- candidate param = `Ref(Record{id:6, size:4})`

Root: `TDate Previous(DayTy) const;` is declared INSIDE the still-incomplete TDate
body, so its return type was captured as a `size:0` record. `expr_type`'s MethodCall
arm returns `ov.ret` VERBATIM for an OVERLOADED method (codegen.rs ~12123) — the
stub — whereas a NON-overloaded method falls to `funcs.get` (~12128) which holds the
COMPLETED type (the `complete_record_sizes(&f.ret,…)` at ~2101). `arg_compat` compares
records by full equality (id+size+align, cpp.rs:419), so a size:0 arg matches NO
completed param ⇒ spurious no-match. (`Previous` is overloaded — `Previous(const
char*)` + `Previous(DayTy)`, date.h:91-92 — which is why it hit the `ov.ret` path; a
single-overload synthetic refused to reproduce.)

Fix: complete record sizes in `resolve_overload`'s argtys via the existing
`complete_record_sizes(&t, &self.sigs.records)`. **Provably byte-safe**: a
correctly-sized arg re-reads the same size (unchanged); only a stale size:0 stub is
corrected — and a stub matches nothing today, so completion can only turn a spurious
no-match into the right match, never alter an existing resolution. The 88 baselines
confirm: byte-identical.

**Result: CLASSLIB/TIME.CPP now compiles cleanly (rc=0)** — its only blocker. CLASSLIB

## Addendum 14 (2026-06-04) — function-local static with a RUNTIME initializer (init-once guard); LOCALECO compiles

LOCALECO's remaining blocker was `static int WINAPI (*compareStringA)(...) =
(TCompareStringA)::GetProcAddress(::GetModuleHandle("kernel32"), "CompareStringA");`
— a function-local `static` with a RUNTIME initializer. mdbcc's local-static path
(codegen.rs ~944) const-evaluated the init via `global_image` and ERRORED on a
non-constant (the no-name "global initializer must be a constant", decl.rs:90).

Implemented the standard init-once-guard (C++ §6.7, init-on-first-reach). Three
sites + a helper:
1. compile_module static-local loop: `match global_image`; on Err (non-constant
   init) zero the `.slocal.*` storage AND register a guard int `.sguard.<fn>.<var>`.
2. Per-function Gen setup: map a synthetic `static_locals` key
   `static_guard_key(v)` (`\u{1}sguard.<v>`, can't collide with an identifier) ->
   the `.sguard.*` global, so the body can reference it via `Expr::Var`.
3. Body `Stmt::Decl{is_static:true,..}` (was a no-op): for a runtime-init static,
   SYNTHESIZE and `gen_stmt` `if (guard==0){ name=<init>; guard=1; }`. `name`
   resolves to `.slocal.*`, the guard key to `.sguard.*` (both via static_locals →
   the existing `lea [rip+g]` path). Guard-gated (not value-gated), so a
   GetProcAddress that returns NULL is not retried — matches bcc32.

All three use the SAME discriminator (`global_image` fails) so they stay in sync.
Byte-safe: a CONSTANT-init static takes the Ok path (no synthesized code, no guard)
⇒ identical to before; only previously-ERRORING runtime-init statics get new code,
so no baseline is touched (confirmed: 88 baselines green). The body recomputes the
discriminator per static decl (cheap) rather than threading state.

RUN-verified: `int counter=0; int next_id(){return ++counter;} int get(){ static
int id=next_id(); return id; } main{ a=get(); b=get(); return a*10+b; }` -> 11
(id initialised once; would be 12 if re-run). Stable across processes. Test:
`static_local_with_runtime_initializer_runs_once`.

Effect: **CLASSLIB/LOCALECO.CPP compiles (rc=0)** — CLASSLIB 18/27. General feature

## Addendum 16 (2026-06-04) — parenthesised functional-cast parse fix (GADGETWI/GAUGE)

From the OWL parse cluster (deterministic, reducible — unlike the heterogeneous,
non-reproducing lvalue one-offs which I probed and set aside). GADGETWI:209 /
GAUGE:145 `int((long(units)*h + u/2)/u)` failed "expected ')'". Minimal trigger:
`(long(5))/2` (a PARENTHESISED functional cast followed by a binary op);
`long(5)/2` (no wrapping paren) was fine.

Root: `peek_is_type_after_lparen` returned `true` UNCONDITIONALLY for a bare
type keyword (and struct/union/enum/class), skipping the cast-SHAPE check the
typedef/tag (Ident) branch already did. So `(long(...)` committed to a C-cast
`(long)…`, `type_name()` parsed `long`, then `expect ')'` hit `(` -> error. A
functional cast has the type followed by `(`, not a cast close.

Fix: unify all three branches to walk the type-specifier sequence (built-in
keyword run / `struct Tag` / `::`-qualified typedef-or-tag), then the SHARED
cv-quals + `*`/`&` tail, then REQUIRE `)`. A type NOT followed by (ptr/ref then)
`)` ⇒ the parens hold an expression. Byte-safe: this only turns currently-FAILING
inputs (`(type(…))…`) from cast→paren-expr; every shape the keyword branch
accepted before (`(int)`, `(unsigned long)`, `(int*)`, `(const char*)`,
`(struct Foo*)`) still ends in `)` ⇒ still a cast. Confirmed: 88 byte-identity
baselines unchanged. Preserves the documented `(Flags & mask)` / `(ios::in|out)`
expression cases.

RUN-verified: `(long(50))/2` -> 25; the GADGETWI shape `int((long(10)*12 +
8/2)/8)` -> 15. GADGETWI.CPP + GAUGE.CPP cleared the paren error (further blockers
remain). Test: `parenthesized_functional_cast_then_operator_parses`. Gate: 88
baselines x2 + full suite + clippy — all green. (DOCTPL qualified member-fn-ptr
