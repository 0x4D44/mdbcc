# JRN — M3: native Win64 RailC starts a game and the KINGSX layout animates

Date: 2026-06-14
Milestone: M3 (KINGSX child windows + full window tree, runs to the 720/3600-tick tiers)

## TL;DR
**The source-built, mdbcc-compiled, native Win64 RailC runs a full game.** cmd 100 (Game>Start) opens the
TStart dialog, OK starts the simulation, and the King's Cross (KINGSX) track layout renders and animates
deterministically — clock 7:21 at tick 720, 10:21 at tick 4320 (exactly 3 game-hours over 3600 ticks),
platform signals evolving — surviving 720 + 3600 = 4320 driven `WM_TIMER` ticks with **no crash**. The M3
"does the game even run on Win64" frontier is cleared.

## How the game is driven (reused from the proven 32-bit parity harness)
The 32-bit i386 closure built `wrk_probe/gui_parity/capture_child_windows_parity.ps1`, which drives RailC
deterministically. Reused that exact mechanism for Win64 (`wrk_probe/owl_win64_smoke/game_start_probe.ps1`):
1. **Run dir**: copy `KINGSX.RCD` (the timetable data) + the win64 exe; patch the exe's `"RAILC.INI"`
   string → `".\RC.INI"`; write an `RC.INI` with `Data file name=<KINGSX.RCD>`, `Timer speed=3`,
   `Enable delay=0` (deterministic, no wall-clock waits).
2. **Start**: `WM_COMMAND 100` (CMMnuFilNew) → wait `#32770` "Prepare to start" (TStart) → `WM_COMMAND IDOK`.
3. **Layout**: wait for the child window of class **"Layout Class"** (TLayout = `DisplayHan`, a child of the
   main frame — found via EnumWindows + EnumChildWindows, not top-level).
4. **Ticks**: `SendMessageTimeout(layout, WM_TIMER, wParam=ID_TIMER=2100, ...)` N times — deterministic,
   bypasses the real 100 ms `SetTimer`. The game clock advances purely as a function of tick count.

## What this exercises (all green on Win64)
- TStart dialog (same DWL_USER path proven for ABOUT/CONFIG in M2) — opens + OK.
- `TLayout::EvTimer` (LAYOUT.CPP:188) → `HandleTimeChange()` — the **full simulation core** (loco/timetable
  scheduling, platform assignment, the heavy per-tick work) runs without a Win64 ABI fault across 4320 ticks.
- `TLayout::Paint` → `UpdateDisplay` (LAYOUT.CPP:239/246) — the KINGSX track rendering (DrawSection /
  DrawPlatform, float scaling, GDI pen/bitmap work) draws the complete layout: platforms 1-10/UB/LY, the
  UF/DF/US/DS lines, junction crossings, signal indicators, the LED clock, Arrival/Departure delay displays.
- Deterministic advance: 720 ticks → 7:21, +3600 ticks → 10:21. Identical tick→clock cadence is the
  precondition for differential parity vs the golden.

## M3/M4 differential parity vs the BC4.5 golden — PIXEL-PERFECT (outside one golden bug)

Built `wrk_probe/owl_win64_smoke/game_parity.ps1`: starts BOTH the BC4.5 golden and the native Win64 exe,
drives the IDENTICAL deterministic tick sequence into each layout, captures the "Layout Class" child at
tiers 720 and 3600, pixel-compares.

**Determinism fix (critical).** `CMMnuFilNew` arms a real 100 ms `SetTimer` after the TStart OK, which
contaminates the injected-tick count (the two processes start at different wall-clock instants -> different
real-tick totals -> the clock drifts: golden 7:22 vs win64 7:28 in the first run). Fix: queue
`CM_MNUFIPAUS` (101) right behind the TStart `IDOK` so the pause's `KillTimer` runs immediately after
`SetTimer`, before the first 100 ms real tick (R=0). `EvTimer` has no `GamePaused` guard, so injected
`WM_TIMER` ticks still drive the simulation. => state is a pure function of injected tick count.

**Result (deterministic, identical at both tiers):**
```
tier 720 : 704x369  total diff 1938/259776 (0.746%)  outside-delay-LED-region: 0 px (0.0000%)
tier 3600: 704x369  total diff 1938/259776 (0.746%)  outside-delay-LED-region: 0 px (0.0000%)
```
The **entire KINGSX layout — track sections, junctions, the LED clock, platform 1-10/UB/LY indicators,
the UF/DF/US/DS lines — is PIXEL-IDENTICAL to the BC4.5 golden** at both the 720 and 3600 tick tiers. The
only differing region (1938 px, byte-stable across tiers) is the two Arrival/Departure delay LED boxes,
where the **golden exhibits its documented blank-delay-box GDI bug** (LAYOUT.CPP:630 — HTimeSym selected
into two DCs -> StretchBlt from an empty 1x1 DC -> blank boxes) and the **win64 build renders the LED
digits correctly** (the source carries the fix). So win64 is, if anything, *more* correct than the golden.

**Float parity confirmed.** The track sections are positioned by float scaling
(`SetXScaleFactor(float(right)/850.0)`). win64 matches the golden's track pixels EXACTLY -> win64 float
math agrees with the original Borland golden. (A diff vs the stale Jun-11 32-bit mdbcc build showed a ~1px
offset on every track edge — that build predates the recent `f91163b` width-correct float load/store fix;
it is not a clean reference. The BC4.5 golden is the stable reference and win64 matches it.)

**This clears M3** (KINGSX animates to 720 and 3600 without crashing; layout matches the golden) **and the
core of M4** (differential capture-and-compare at the sampled tiers, pixel-identical within a documented,
golden-bug exclusion). Driver + oracle: `wrk_probe/owl_win64_smoke/game_parity.ps1` (gitignored tooling).
