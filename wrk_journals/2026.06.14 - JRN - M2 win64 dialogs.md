## Empirical findings (differential vs the 32-bit golden)

- **Main-window WM_COMMAND routing WORKS on Win64.** Posting `WM_COMMAND 300/301` to the main frame
  (class `Main_Window_Class`, title "Rail Control") toggles the Arrivals/Departures windows off — so the
  response table routes and command handlers fire. (Note: the main frame class is `Main_Window_Class`, NOT
  `OwlWindow` — the wall2 probe / O3 gate were targeting the first PID window, often a KINGSX child; the
  resize-storm part still validly exercised wall 2, but the menu-command part was largely inert. TODO: point
  the O3 battery at `Main_Window_Class`.)
- **All 4 KINGSX windows (Arrivals/Departures/Platforms/Locoyard) are created at startup** as top-level
  windows (enabled in the INI) — 5 visible top-level windows before any interaction.
- **The dialogs FAIL to open on Win64.** Posting `WM_COMMAND 999` (About) / `201` (Config) → handler runs
  (routing works) but **no dialog window appears**; the process survives.
- **Differential:** the SAME source on the **32-bit** `railc_slice.exe` → posting 999 makes a **`#32770`**
  (standard Windows dialog class) window appear = the About dialog. So this is a genuine Win64-only failure.

## Dialog path (from RailC + OWL source)

`CMMnuHeAbot` → `GetApplication()->ExecDialog(new TAbout(this,"AboutBox"))` → `TDialog::Execute()` →
`TDialog::DoExecute()` → `DialogBoxParam(*GetModule(), Attr.Name, parentHWnd, (DLGPROC)(FARPROC)StdDlgProcInstance, Attr.Param)`
(DIALOG.CPP:~395). Modal. `Execute()` throws `IDS_WINDOWEXECUTEFAIL` if `DialogBoxParam` returns -1; the throw
is swallowed by `GetApplication()->SuspendThrow/ResumeThrow` → no dialog, process survives. **This matches the
observed symptom exactly: `DialogBoxParam` is returning -1 (cannot create the dialog box).**

## Ruled out
- **DLGPROC truncation.** `TProcInstance` (GEOMETRY.H:243) stores `FARPROC Instance` (64-bit) and the Win32
  ctor is `Instance = FARPROC(p)` — no truncation. `operator FARPROC()` returns it full-width.
- **Resources.** `railc.res` is byte-identical (rc_railc test); the dialog templates (ABOUTBOX/CONFIG/FINISH)
  are present and the 32-bit build loads them fine.
- **Command routing / dispatch.** Confirmed working (300/301 toggle windows).

## ROOT CAUSE (instrumented, 2026-06-14) — `CallWindowProc(DialogWndProc, WM_INITDIALOG)` hangs

Instrumented overlay `DIALOG.CPP` + `WINDOW.CPP` with a Win32 file-logger (`wrk_probe/owl_win64_smoke/`:
`instr_dialog.py`, `fast_relink.sh` for ~5s recompile-one-object + relink). Drove the About dialog (post
`WM_COMMAND 999`) and traced the message flow. The dialog window (`#32770`) **is created but stays HIDDEN**
(`vis=False`, style `0x84C800C4` — no `WS_VISIBLE` bit) and the process hangs (modal loop running, killed by
the probe). Exact chain captured in the log:

```
Execute.enter → Execute.RegisterOK → Execute.beforeDoExecute     ← Register + child-register OK
DoExecute.inst/parent/dproc                                       ← args valid (hInstance, parent HWND, DLGPROC)
dlgproc.msg 48 <hDlg>          (WM_SETFONT — the dialog's first message; OWL subclasses here)
stdwp 272 <hDlg>              (WM_INITDIALOG → StdWndProc; proc is now StdWndProc after subclass)
recv272.enter                 (TWindow::ReceiveMessage(WM_INITDIALOG))
wp272.enter                   (TWindow::WindowProc)
wp272.beforeDefWP             (no OWL response-table handler for WM_INITDIALOG → fall to DefWindowProc)
defwp.ENTER 272               (TWindow::DefWindowProc body entered)
defwp272.wparam <focusHWND>   (args valid: wParam=focus control HWND, lParam=0, DefaultProc in USER32 range)
defwp272.lparam 0
defwp272.defproc <USER32 addr>
   ← HANG: ::CallWindowProc(DefaultProc, hDlg, WM_INITDIALOG, ...) never returns (no afterDefWP),
            StdDlgProc is never re-entered for 272, the dialog is never shown.
```

**Mechanism.** OWL's `StdDlgProc`, on the dialog's first message (WM_SETFONT), calls the (wall-1-patched)
`TWindow::SubclassWindowFunction()` → installs the **shared static `StdWndProc`** as the dialog's
`GWLP_WNDPROC` and captures the old proc (the `#32770` USER32 `DialogWndProc`) as `DefaultProc`. So
WM_INITDIALOG routes `StdWndProc → ReceiveMessage → WindowProc → (no handler) → DefWindowProc →
::CallWindowProc(DefaultProc=DialogWndProc, WM_INITDIALOG)`. **That `CallWindowProc` into USER32's
DialogWndProc hangs on Win64** (args are all valid; it never reaches the `StdDlgProc` DLGPROC call inside it).

**Ruled out:** DLGPROC truncation (`TProcInstance` stores `FARPROC` full-width); resources (FindResource finds
AboutBox/CONFIG/FINISH in BOTH the Win64 and 32-bit exes, same sizes 462/812/550); command routing (300/301
toggle KINGSX windows fine); `Register()`/child-register (both log OK); virtual-base dispatch (`defwp.ENTER`
proves `TWindow::DefWindowProc` is entered; both TDialog AND TFrameWindow are `virtual public TWindow` and the
main window works). **Differential:** the 32-bit `railc_slice.exe` shows the About dialog (`#32770`, vis) on
the same source — Win64-only.

**Why 32-bit works but Win64 hangs (hypothesis):** on 32-bit the OWL subclass installs a per-window
*executable thunk* as the proc; on Win64 (wall-1) it installs the *shared* `StdWndProc`. USER32's
`DialogWndProc(WM_INITDIALOG)`, driven through the subclassed proc, loops/blocks on Win64 — likely the dialog
manager's focus / UI-state setup re-entering the subclassed proc in a way the shared dispatcher doesn't
satisfy. This is the **DWL_USER frontier** the wall-1 HLD anticipated: dialogs need their own `this`-recovery
(`DWLP_USER`) and must NOT subclass the dialog window proc — keep USER32's `DialogWndProc` as the window proc,
let `StdDlgProc` (the DLGPROC) recover `this` and route via `DialogFunction`.

## Fix direction (M2 — not yet implemented)
Port `StdDlgProc` to the Win64 **DWL_USER path** in an overlay `DIALOG.CPP`:
- Do **not** call `SubclassWindowFunction()` for the dialog (don't replace `GWLP_WNDPROC`); keep USER32's
  `DialogWndProc` as the window proc so the dialog manager's WM_INITDIALOG/show works.
- Recover/store the `TDialog*` via `SetWindowLongPtrA/GetWindowLongPtrA(hDlg, DWLP_USER)` (full pointer width;
  DWLP_USER = 16 on Win64 vs 8 on Win32 — but the API constant handles that), instead of the
  `GetWindowPtr`/`DlgCreationWindow`/subclass dance.
- Verify the response-table routing (EV_COMMAND IDOK/Cancel, e.g. TConfigur::CmOk) still works through
  `DialogFunction` without the subclass — read `DialogFunction` (DIALOG.CPP:186-230) to confirm it routes
  non-init messages to the response table; if it relies on the subclass, a hybrid is needed.
- Acceptance: posting 999/201 makes a `#32770` window appear `vis=True`; OK/Cancel behave; no hang/AV;
  differential vs the 32-bit golden capture.

## UPDATE — the WM_INITDIALOG hang is FIXED; the About dialog now DISPLAYS ✅

The deferred-subclass idea works, with one addition (an explicit show). Implemented in an overlay
`DIALOG.CPP` (recipe in `wrk_probe/owl_win64_smoke/fix_dialog.py`). The working `StdDlgProc` change:

```c
  if (DlgCreationWindow && !dialog && msg != WM_CANCELMODE && msg != WM_ENABLE) {
    DlgCreationWindow->HWindow = hDlg;
    dialog = DlgCreationWindow;
    // Win64 M2: the wall-1 static-dispatcher subclass makes USER32 DialogWndProc(WM_INITDIALOG)
    // hang when re-entered via ::CallWindowProc. Handle WM_INITDIALOG while the dialog manager
    // still owns the window proc (-> EvInitDialog -> SetupWindow, no hang), then explicitly show
    // the (manager-created-hidden) dialog and subclass it for response-table routing.
    if (msg == WM_INITDIALOG) {
      bool _r = dialog->DialogFunction(msg, wParam, lParam);
      ::ShowWindow(hDlg, SW_SHOW);          // manager created it hidden & doesn't show it on Win64
      dialog->SubclassWindowFunction();
      DlgCreationWindow = 0;
      return _r;
    }
  }
```

**Verified:** posting `WM_COMMAND 999` now makes the About `#32770` dialog appear **`vis=True`**
(`style 0x94C800C4`, WS_VISIBLE set), 3/3 runs; the modal loop runs idle (CPU 0 ms — confirms the hang
is gone, the dialog was merely created hidden). Two empirical facts that unlocked this:
1. Deferring the subclass past WM_INITDIALOG lets `EvInitDialog → SetupWindow` complete (the
   `CallWindowProc(DialogWndProc, WM_INITDIALOG)` round-trip never happens).
2. On Win64 the dialog manager creates the modal dialog HIDDEN and does **not** auto-show it after
   WM_INITDIALOG (no WM_SHOWWINDOW observed) — so OWL must `ShowWindow` it explicitly.

## Remaining M2 work (NOT yet fixed)

  1/2 → `EndDialog` → `DestroyWindow`) crashes with an access violation. WM_CLOSE leaves it open (normal —
  dialogs dismiss via the command path). Instrumented dismiss trace (StdWndProc for WM_COMMAND/WM_DESTROY/
  WM_NCDESTROY + `~TWindow` enter):
  ```
  dsm.stdwp 273 <dlg>     (WM_COMMAND IDOK to the dialog, via the subclassed StdWndProc)
  dsm.stdwp 2   <child>   (WM_DESTROY to a CHILD window — reaches StdWndProc, so it's subclassed)
  dsm.stdwp 130 <child>   (WM_NCDESTROY to the child)
     ← crash; `~TWindow` (OWL teardown) is NEVER entered.
  ```
  So the crash is in **USER32's window destruction** (EndDialog→DestroyWindow tearing down the dialog +
  its child controls through the subclassed `StdWndProc`/`DefWindowProc`→`CallWindowProc(DialogWndProc)`
  path), *before* OWL's `~TWindow`. A child control's WM_DESTROY/WM_NCDESTROY reaching StdWndProc means the
  controls got subclassed too (Ctl3d auto-subclass or the OWL path); the subclassed-proc teardown ordering
  faults on Win64. Prime suspects: the wall-1 subclass-teardown restoring `GWLP_WNDPROC` on an
  already-half-destroyed window, or `CallWindowProc(DialogWndProc, WM_NCDESTROY)` with a stale `DefaultProc`.
- **Config (201) does not show.** `TConfigur` creates OWL child controls (`TRadioButton`/`TCheckBox`) in
  its ctor; `SetupWindow → CreateChildren` constructs them. About (no OWL child controls) shows; Config
  doesn't — a child-window construction / control-subclass issue on Win64.
- **Likely needs Step 2 (the int32 dispatch widening: DISPATCH.H/CPP, SIGNATUR.H)** for the command/
  notification/owner-draw paths these exercise — the M1-deferred frontier.

## UPDATE 3 — the About dialog FULLY WORKS (open + close + reopen) ✅✅

Two more findings closed the loop:
1. **The subclass approach is fundamentally broken on Win64.** Forwarding default processing to USER32's
   `DialogWndProc` via `::CallWindowProc(DefaultProc, …)` hangs for WM_INITDIALOG *and* crashes for
   WM_NCDESTROY (traced: the entire OWL handling completes, then the crash is inside DialogWndProc's
   completion, before `DoExecute` returns). The deferred-subclass only dodged WM_INITDIALOG; destroy still hit it.
2. **The DWL_USER path (no subclass) eliminates both.** Recover the `TDialog*` from `GWLP_USERDATA` (stored on
   the first message), leave USER32's `DialogWndProc` as the window proc throughout, and route via
   `DialogFunction`. Dialog opens (manager shows it normally — no explicit ShowWindow needed), no hang, no crash.

Two more fixes made it fully functional:
- **OK/Cancel close.** Without the subclass, OWL's response table (`EV_COMMAND(IDOK,CmOk)`) is bypassed and
  **DefDlgProc does NOT auto-EndDialog** (the DLGPROC must). So route IDOK/IDCANCEL in `DialogFunction` to the
  virtual `CmOk()`/`CmCancel()` (which call `::EndDialog`). Now Esc→IDCANCEL and Enter→IDOK both close.
- **Control-HWND truncation** (independent wall-2 fix, WINDOW.CPP): `EvCommand(LOWORD(wParam), (HWND)(uint)lParam, …)`
  truncated the notifying control's HWND to 32 bits → control commands mis-route. `(uint)` → full `lParam`.

**Verified (About dialog):** opens reliably (8/8); closes via **Enter** (IDOK→CmOk, 4/4) and **Esc**
(IDCANCEL→CmCancel); **3/3 open→close→reopen cycles, app survives**. No hang, no crash. This is the M2
dialog *mechanism* solved.

## UPDATE 4 — Config FIXED too: the SetWindowLongPtrA-return truncation ✅✅✅

Root-caused Config's child-control crash: `TWindow::SubclassWindowFunction` captures the subclassed control's
prior window proc as `DefaultProc` from **`SetWindowLongPtrA`'s return**. `mdwin64thunk.h` deliberately
declared **no prototype** for it (trusting mdbcc's Win32-import recognition to return full pointer width) —
but mdbcc treats the un-prototyped call as **implicit-int** and truncates the *return* to a **signed 32 bits**.
A USER32 BUTTON proc (`0x00007FF9_xxxxxxxx`) thus became `0xFFFFFFFF_xxxxxxxx` (traced: DefaultProc hi = -1) →
`::CallWindowProc(DefaultProc, …)` faults → `0xC0000005` (5/5). Harmless for the install calls (return
ignored) and for the main window (uses `GetProcAddress`, not the subclass path), so it only bit subclassed
predefined controls — i.e. dialogs with OWL child controls (TConfigur's radios/checkboxes).

**Fix:** declare `extern "C" LONG_PTR __stdcall SetWindowLongPtrA(HWND,int,LONG_PTR);` (+ Get) in
`mdwin64thunk.h`. DefaultProc hi → `0x7FF9` (real USER32 address); Config opens + closes (Esc + Enter, 3/3),
no crash; About unaffected. This is a **fundamental fix for all subclassed controls**, not just Config.

**Verified:** Config (201) opens + closes via Esc(IDCANCEL) and Enter(IDOK); About (999) still opens + closes
(no regression). Both RailC dialogs now function on native Win64.

## M2 visual parity: About side-images (EvPaint on the DWL_USER path) — RESOLVED

**Gap:** the DWL_USER path (no OWL subclass) means the response table never runs, so `TAbout::EvPaint`
(the two steam-loco / DMU side bitmaps, `ABOUT.CPP:59`, drawn with raw Win32 `BeginPaint`/`BitBlt`) never
fired. Win64 About showed the template content (icon, text, OK) but was missing both train images vs the
32-bit golden.

**First attempt (WRONG):** route *every* handled message through `Find`/`Dispatch` in `DialogFunction`.
This blanked the dialog (intercepted messages the dialog manager needs) → narrowed to a `WM_PAINT`-only
route. That fixed About's images but **regressed O5: Config crashed `0xe0000002`** (an uncaught throw, not
an AV). It opened fine under PrintWindow capture (which sends `WM_PRINT`, not `WM_PAINT`) but died under
real on-screen painting.

**Root cause (traced, not guessed):** a `WM_PAINT` on a plain dialog (`TConfigur`, no paint override)
resolves up the response table to **`TDialog::EvPaint` → `DefaultProcessing()`** (`DIALOG.CPP:145`), which
throws on a no-subclass dialog. `TAbout::EvPaint` is safe (raw GDI, no DefaultProcessing). An `MDBCC_M2_TRACE`
build logged the matched response-table entry per paint: TAbout → entry `…616`, every plain dialog →
TDialog's entry `…808`.

**Fix (zero hardcoding):** in the `WM_PAINT` case, dispatch **only when the concrete dialog overrides
EvPaint below TDialog**. Discriminate by comparing the *virtual* `Find()` (most-derived entry) against the
implicit-this **`TDialog::Find()`** (devirtualised by mdbcc, exactly like RailC's `TFrameWindow::Paint()`
base calls — note `this->TDialog::Find()` does NOT devirtualise: mdbcc only static-binds the implicit-this
qualified form). Entries equal → inherits `TDialog::EvPaint` → let `DefDlgProc` paint (no throw). Entries
differ → a real override (`TAbout`) → safe to `Dispatch`. Verified by trace: About `…616 ≠ …808` (dispatch),
Config `…808 = …808` (skip).

**Result:** Win64 About now renders both train side-images (full visual parity with the golden), Config
paints normally via `DefDlgProc`, and the O5 gate stays green. One self-contained edit to the `DIALOG.CPP`
overlay's `DialogFunction`; no app source touched.

**mdbcc codegen note (for a focused regression later):** the explicit-this qualified virtual call
`this->Base::Virt()` is emitted as a *virtual* dispatch (does not static-bind to `Base::Virt`); only the
implicit-this form `Base::Virt()` devirtualises. Worth confirming + filing.
