### J-5 — `gen_new_array` overflow + negative count guards

Three layers, in order from cheapest to runtime:

1. **Compile-time constant-negative**: if `count` is `Expr::Int(n)`
   with `n < 0` (or the parser-raw `Unary{Neg, Int(n)}` form — the
   parser does no constant folding at parse time, so `-5` arrives as
   `Unary{Neg, Int(5)}`), reject with
   `"new T[n]: array count is negative ({n})"`. Source-pinned
   diagnostic; no runtime trap on the path the compiler can see.
2. **Runtime negative-`n` guard**: after spilling and reloading the
   count, emit `test rax,rax ; jns +2 ; ud2` (`48 85 C0 79 02 0F 0B`,
   7 bytes). SF=1 (top bit set) falls into `ud2`; non-negative skips
   the trap. Catches `int n=-5; new T[n];` cleanly:
   STATUS_ILLEGAL_INSTRUCTION (0xC000001D) instead of the original
   "near-2^64 unsigned mul → HeapAlloc returns NULL → AV at cookie
   write" path.
3. **Runtime overflow guard**: only when `elem_size != 1`, after the
   `mul rcx` (unsigned 64-bit multiply, sets CF=1 iff the 128-bit
   product exceeds 64 bits), emit `jnc +2 ; ud2` (`73 02 0F 0B`,
   4 bytes). Truncated-product allocation collapses to an immediate
   fault rather than under-allocation + later AV.

Total codegen overhead: 7 + 4 = 11 bytes per `new T[n]` site (when
`elem_size != 1`; 7 bytes for `T[1]`/`char[]`). The 88 e2e fixtures
do NOT exercise any `new T[n]` path, so O1 byte-identity is
preserved (verified: `cargo test --test end_to_end` 88/88 green
unchanged).

## Tick 52 — 2026-05-23 — J-7 bare `throw;` (rethrow) inside catch

**Goal**: close J-7 (H3-era reject phrase still in tree). Lift the

catch handler, keep rejection outside any catch with a clearer
diagnostic phrase.

**Touch surface**: `src/codegen.rs`, `tests/cpp_exceptions.rs`, this
journal, the gap-report queue.

### Design

Added a per-function `catch_contexts: Vec<CatchCtx>` stack on `Gen`.
Entry holds `{kind: CatchKindLow, value_off: i32}` where:
- `CatchKindLow::Int` — slot holds the thrown int (low 32 bits of
  the 8-byte spill).
- `CatchKindLow::Class { class_record_id }` — slot holds the
  buffer-pointer the personality function delivered to the handler.
  The catch's static type id feeds args[0] (vtable absolute address)
  on rethrow.

`gen_try` decides per clause:
- If the catch body contains a bare `throw;` (any depth — scan via
  `catch_body_rethrows` / `stmt_rethrows` helpers, NOT recursing into
  nested catches' bodies because their rethrows belong to the inner
  catch), push a `CatchCtx`.
- For named catches: reuse the existing param slot — no extra
  instructions emitted. Pre-J-7 named-catch programs are
  byte-identical.
- For anonymous catches: spill RAX into a fresh tmp at the landing
  pad (8-byte `mov [rbp-tmp], rax`). Without J-7's tmp spill, the
  caught value would be unrecoverable since `gen_try`'s existing
  spill-into-slot logic only fires for `name: Some(_)`.

`Stmt::Throw(None)` arm now peeks `catch_contexts.last()`:
- Empty → `CodegenError("'throw;' (rethrow) is only valid inside a
  'catch' block; no current exception to re-raise")`.
- Non-empty → `gen_rethrow(ctx)`:
  - `Int`: `RaiseException(EXCEPTION_MDBCC_INT=0xE0000001, 0, 1,
    &slot)`, `&slot` = `lea r9, [rbp-value_off]`. Same shape as
    `gen_throw_int` but no fresh eval — the value is already in the
    slot.
  - `Class`: build a 2-`ULONG_PTR` args array `[vtable_abs(T),
    buffer_ptr]` (T = catch's static type), `RaiseException(
    EXCEPTION_MDBCC_CLASS=0xE0000002, 0, 2, &args)`. Same shape as
    `gen_throw_class` but no memcpy — the buffer is already
    populated by the original throw.

`ud2` follows each call for symmetry with the value-throw paths.

## Tick 55 — 2026-05-23 — G-1 / G-4 inline member fn returning own class

**Goal**: close G-1 (and G-4 for free) — inline class member functions
that return / use the enclosing class type now compile and run
correctly. Predicted to share a root cause; confirmed during
investigation.

**Touch surface**: `src/parser.rs` (end-of-parse AST sweep);
`tests/owl_integration.rs` (flipped 2 regression-locking tests,
added 2 robustness tests). Codegen UNTOUCHED.

**Root cause confirmed (both gaps)**: when a `class Tag { … Tag
method(…) { … } … }` body is parsed, the parser walks members one
member at a time. The class's record id is allocated up-front (so
the tag is in scope for self-references), but `self.records[id]`
keeps `size: 0, align: 1` until **after** the closing `}` (when
`layout()` is called). An inline member function whose return type,
`this` pointee, or local `Tag r;` is the enclosing class therefore
captures the **stale** `Type::Record { id, size: 0, align: 1 }` on
its `Function::ret` / `Function::params[].1` / `Stmt::Decl::ty`.
The out-of-line counterpart resolves the type via `decl_specifiers`
**after** the class body closes — so its cache is already correct.
Downstream consequences of the stale cache:

- **G-1 ("empty struct by value")**: `Gen::new(f, …)` checks
  `f.ret.is_record() && f.ret.size() == 0` and rejects (codegen.rs

**Root cause confirmed (both gaps, single fix)**: in `gen_binary`
(`src/codegen.rs:3908`), the overloaded-binop path did:

```rust
if let Some(m) = self.overloaded_binop(op, lhs)? {
    let this_e = Expr::Unary { op: UnOp::Addr, expr: Box::new(lhs.clone()) };
    return self.gen_call(&m, &[this_e, rhs.clone()]);
}
```

This calls `gen_call_with_lead(name, None, …)` — `lead=None` ⇒ NO
`prepare_record_return_call` / `complete_record_return_call`
machinery is invoked. For a `Point operator+(Point&)` (InReg(8) per
`classify_struct_for_win64`), the callee packs the 8 struct bytes
into RAX and returns. Without the complete step, **no result buffer
is materialised** — RAX holds the packed-bytes value, not an
address. Downstream consumers then see:

- **G-2** (`Expr::Assign { lhs: c, rhs: Binary { … } }`): the
  Assign record-copy path (codegen.rs:3556+) calls
  `gen_addr(rhs)`. `gen_addr` has no `Expr::Binary` arm ⇒ falls
  through to "expression is not an lvalue".
- **G-3 compile-time** (`Expr::Member { base: Binary { … }, … }`):
  `gen_member_addr` calls `gen_addr(base)`. Same fall-through.
- **G-3 runtime** (`marshal_args` arg-by-value path for an
  `Expr::Binary` returning a record): `gen_expr(a)` ⇒ `gen_binary`
  emits the call, leaving the packed bytes in RAX. Then
  `lower_struct_arg` treats RAX as the source struct's *address*
  and copies 8 bytes from `[rax]` (where `rax = packed value, e.g.
  0x0000000600000005`) — reads from an unmapped address ⇒
  STATUS_ACCESS_VIOLATION 0xC0000005 (unix-style exit 139).

**Fix (3 edit sites in src/codegen.rs)**:

1. **`gen_binary`** (~line 3908): rewrite the overloaded-binop path
   to build an `Expr::MethodCall` (via the existing
   `build_op_method_call` helper, same shape used by `Expr::Index`

   `Expr::MethodCall` arm of `gen_expr` (line 3729+) already calls
   `prepare_record_return_call` + `complete_record_return_call`, so
   record-returning op+ inherits the full ABI handling — InReg
   returns are materialised into a result buffer, HiddenPtr returns

   op+ paths (D5 OWL response-table demos, all pre-tick-56 J-21
   fixtures) keep their byte-identical code shape.
2. **`gen_addr`** (~line 2851): widen the
   `Expr::Call | Expr::MethodCall` record-returning arm to also
   accept `Expr::Binary`. When the binary's `expr_type` is a record
   (only happens for an overloaded op returning a class), delegate
   to `gen_expr` (which now materialises the buffer per #1) and the
   buffer address ends up in RAX as `gen_addr`'s lvalue contract
   requires. Non-record binaries (int + int, etc.) fall into the
   catch-all "not an lvalue" arm below — preserves pre-tick-56
   diagnostic for `(3 + 4).x`.
3. **`record_call_result_size`** (~line 3342): add an `Expr::Binary`
   arm gated by `overloaded_binop` returning Some. This lets

## Tick 57 — 2026-05-23 — J-9 aggregate initializers `{…}` (block scope)

**Goal**: close J-9 — `int a[5] = {1,2,3,4,5};`, `Point p = {3,4};`,

### Design

**AST**: `Expr::InitList(Vec<Expr>)`. Nested aggregates are nested
InitLists. Trailing comma is consumed at parse and does not appear
in the AST. Out-of-init-context use is a clean CodegenError (the
parser only emits it after `=` in a declarator initialiser).

**Parser** (`maybe_initializer` ~line 1486): after `=`, peek for `{`;
if present, parse `init_list()`. `init_list()` consumes `{`, then
comma-separated assignment expressions OR nested `init_list`s
(branch on `{`), allowing a trailing comma, then `}`. Unsized array
length `Type::Array(elem, 0) → Type::Array(elem, list.len())` is
resolved at the same site so the codegen sees a finalised type.

**Codegen** (`gen_init_list_into_slot`): zero the entire slot
up-front (covers partial-init holes + struct padding in one move,
which the standard requires zero), then per-element store at
`off - i*elem_size` (array) or `off - field.offset` (record).
Excess items reject with a clear "too many initializers for …"
diagnostic. The per-element helper (`gen_init_element`) handles
three cases: nested InitList → recurse; char-array element with
a string literal → reuse the existing `emit_array_init` byte-copy;
record element → reuse the existing struct-copy idiom; scalar →
`gen_expr` + `convert` + `store_to_local`.

**Rejection sites** (3): `gen_expr` (use of InitList in non-init
position), `expr_type` (no inherent type), `global_image` (file-

for J-9b).

## Tick 58 — 2026-05-23 — J-10 v1 invoke user-defined copy ctors

**Goal**: partial-close J-10. v1 scope: invoke user-declared
`Tag(const Tag&)` (and pre-standard `Tag(Tag&)`) at by-value-pass
and by-value-return sites instead of the silent `memcpy`. Full
memberwise synthesis stays J-10b.

**Touch surface**: `src/codegen.rs` (`Sigs::copy_ctor_symbol` helper;
`lower_struct_arg` reshaped to take `&Type` + InReg-with-copy-ctor
rejection; HiddenPtr-pass copy-ctor branch; HiddenPtr-return
copy-ctor branch in `Stmt::Return`; memberwise-deferral guard in
`compile_module` pass 1); `src/parser.rs` (auto-invoked ctor now
emitted as `MethodCall` rather than `Call`, AND skipped when an
`=` initialiser is present); `tests/cpp_copy_ctor.rs` new suite
(9 tests).

### Design

- **Detection** (`Sigs::copy_ctor_symbol(rec_id) -> Option<String>`):
  a copy ctor has params (post `this` stripping) `[Ref<Record { id:
  rec_id }>]`. Look up `Tag::Tag` first in the overload set, then
  in the unique-ctor `funcs` map (where `params[0]` is `this` and
  `params[1]` is the user param). Returns the mangled symbol or
  `None`. `const Tag&` and `Tag&` both lower to
  `Type::Ref(Record { … })` at the AST boundary (`const` is
  consumed and discarded by `decl_specifiers`); single helper
  catches both forms.

- **HiddenPtr pass site** (`lower_struct_arg`'s HiddenPtr arm):
  RCX = `&dest_buf` (statically known RBP offset), RDX = source
  pointer (already in RAX from `gen_expr`); direct `call <ctor>`
  via `RipRef`-style intra-unit call; post-call `lea rax,
  [rbp+dest_disp]` re-derives the dest for the standard spill
  path. No tmps allocated; the by-value-region accounting stays
  identical to the memcpy path so frame size is unchanged. For
  classes with NO copy ctor the existing `emit_struct_copy`
  byte-by-byte memcpy fires verbatim ⇒ byte-identical for every
  pre-tick-58 program.

- **HiddenPtr return site** (`Stmt::Return` record arm, HiddenPtr
  branch): symmetric. RDX = source (`&local`, in RAX from
  `gen_expr`), RCX = `*[rbp-hr]` (caller's result buffer, the
  hidden first arg). `call <ctor>` and then `mov rax, [rbp-hr]`
  to return the buffer pointer per Microsoft convention. NO copy
  ctor ⇒ existing `emit_struct_copy` path byte-for-byte.

- **InReg defensive rejection**: a class size ∈ {1,2,4,8} with a
  declared copy ctor errors loudly — InReg unconditionally packs
  the bytes into the positional GPR, so the copy ctor's `this`
  pointer has nowhere valid to point. Grep-pinned phrase
  `"InReg-classified class with a copy ctor is not supported"`.
  Real-world classes with copy ctors are virtually all larger.

- **Memberwise-deferral guard** (`compile_module`, after vtable
  rebuild): walk every record's fields; for any class-typed (or
  array-of-class-typed) member whose nested class has a copy ctor
  AND whose containing class does NOT, return a clean compile
  error with Grep-pinned phrase
  `"memberwise synthesis is deferred to J-10b"`. v1 chooses
  safety: never silently miscompile the outer's memcpy that would
  skip the inner's copy ctor. J-10b's brief is to synthesise the
  outer's chained copy ctor automatically.

- **Parser auto-invoke as MethodCall**: the `Foo a;` auto-invoke

## Tick 60 — 2026-05-23 — J-15 array-new exception safety (DEFERRED, test-locked)

**Goal**: close H10 review MINOR-6 — `new T[N]` whose K-th ctor throws

**Touch surface**: `tests/cpp_new_array.rs` (one new test),

### Investigation outcome — DEFER

The personality function (`src/codegen.rs::build_personality_function`,
918-1187) is a pure search-phase handler: it dispatches on the
exception code, walks the scope table looking for a try-range +
type-match, and on match calls `RtlUnwindEx` to deliver control to a
catch landing pad. There is NO cleanup-scope path — no
`handler_kind = TERMINATION`, no "call this thunk on the way past",
no continuation-of-search after an action. The `CatchPolicy` enum
has three variants (`Int`, `ByRef`, `ByPtr`); the scope-table
emission format (`build_xdata`) and the personality function are
locked to those three.

Approach A (extend the personality function with a Cleanup variant
that the scope table can carry, the personality function recognises
on PC-range match, invokes a generated landing pad for, and continues
search after) requires:
- `CatchPolicy::Cleanup { landing: u32 }` AST + AST-walker updates.
- `build_xdata` write-out of a fourth `catch_kind` byte.
- `build_personality_function` recognition + action path (read entry's
  handler RVA, set up RtlUnwindEx with `er` cleared of the catch-side
  ReturnValue, transfer control, then on landing-pad-return resume
  scope-table walk for the SAME exception so a downstream catch fires).
- A generated landing pad inside `gen_new_array` that reads the
  in-flight iter counter (stack slot), calls dtors in reverse, then
  `HeapFree`s the block, then returns to the personality function.
- New scope-table layout invariant: cleanup scopes ALWAYS come before
  catch scopes in walk order, so a cleanup runs before its enclosing
  catch.

Realistic estimate: 150-250 LoC across `src/codegen.rs` +
`src/pe.rs` + new scope-table version bump (which trips the H4b
`pe_imports` byte-identity test unless guarded). The
PE-byte-identity assertions in `pe_imports.rs` may also need
re-blessing depending on whether the typeinfo/scope-table layout
changes for try-bearing functions. This is multi-tick work.

Approach B (synthesise a `try { … } catch (...) { dtor chain; throw;
}` around the ctor loop, leveraging the existing personality
function) fails because mdbcc has no catch-all yet (`catch (...)`
is not a parser construct nor a `CatchPolicy` variant). Adding it
just to use it here would be ~80 LoC of parser + AST + codegen
extension on its own.

**Honest decision**: defer to J-15b. The fix shares ENTIRE machinery
with J-11b (base/member partial-construction dtor chain, tick 59's
deferral). Both want a cleanup-scope personality function extension;
both want generated landing pads. Implementing them together is
the right unit of work — separately would be twice the bookkeeping
for the same internal API.

## Tick 61 — 2026-05-23 — J-10c copy-init at declaration `T x = y;`

**Goal**: close J-10c — invoke the user copy ctor at the `T x = y;`
declaration site for class type `T`. Tick 58 covered by-value pass
and by-value return; this tick covers the remaining copy-init site
that tick 58 explicitly deferred (filed implicitly under J-10c in

**Touch surface**: `src/codegen.rs` (`Stmt::Decl` record-typed init
arm — new copy-ctor branch); `tests/cpp_copy_ctor.rs` (4 new tests).

### Investigation (probe before fix)

A throwaway probe test confirmed today's behaviour: `T x = y;` for
a class with a copy ctor compiles cleanly but **silently memcpys**
the bytes (option 1 from the brief). Counter stays 0, `b.v` equals
`a.v` rather than `a.v + 1`. No double-construct, no error — the
parser already skips the auto-default-ctor when an `=` initialiser
is present (tick 58's fix). So the surface gap is exactly: the
memcpy path in `Stmt::Decl`'s record arm needs to invoke the copy
ctor instead when the target class has one.

### Design

`Stmt::Decl { ty, init: Some(e), … }` where `ty.is_record()`:

1. If `ty` is `Type::Record { id }` AND `Sigs::copy_ctor_symbol(id)
   == Some(sym)` AND the source `e` does NOT have its own
   record-call result buffer (`record_call_result_size(e) == None`):
   invoke `T::T(&local_slot, &source)`. Direct call via `RipRef::Func`-
   style intra-unit CallSite (the same shape as tick 58's pass-site
   and return-site copy-ctor invocations). No tmps allocated; RAX
   from `gen_addr(e)` flows straight into RDX, then RCX = `lea
   [rbp-off]` for the local slot.
2. Otherwise (class with no copy ctor, OR source is a record-
   returning call / overloaded-binop record rvalue): fall through
   to the existing `emit_struct_copy` byte-by-byte memcpy path,
   verbatim.

The gate on `record_call_result_size(e).is_none()` is the
load-bearing design choice. Tick 58 already invokes the copy ctor
at the return site, populating the caller's result buffer with a
copy-constructed object. For `T x = make_t();` we want **one**
copy total, not two — letting the Decl-site memcpy the already-
copy-constructed bytes into the local slot is correct (no extra
ctor invocation, semantics match pre-C++17 NRVO-permitted copy
elision). The existing test `class_with_copy_ctor_invoked_on_by_
value_return` expects counter=1 for `Foo r = make_foo(5);` — the
gate preserves that.

## Tick 62 — 2026-05-23 — J-14 v1 member-function pointers (non-virtual)

**Goal**: close J-14 v1 — parse, type, and lower **non-virtual**
member-function pointers (MFPs). Cover the three v1 surfaces:
MFP type (`int (Foo::*p)(int)`), MFP address-of (`&Foo::method`),
and MFP call (`(obj.*p)(args)` / `(ptr->*p)(args)`). Reject virtual
MFPs with a Grep-pinned deferral phrase (J-14b).

**Touch surface**: `src/ast.rs` (new `Type::MemFn`, new
`Expr::AddressOfMember` / `Expr::CallMemberPtr`); `src/parser.rs`
(MFP declarator + `&Class::method` unary + `.*`/`->*` postfix);
`src/codegen.rs` (typing + call lowering + virtual rejection);
`tests/cpp_mfp.rs` (6 tests).

### Investigation (probe before fix)

Read the existing fn-pointer machinery (Phase A `Type::Func`,
`Expr::CallPtr`, `&func` decay) — the MFP path mirrors it byte-for-
byte with two deltas: (i) a hidden `this` setup in RCX before the
indirect call, (ii) a `class_id` carried on the type so the
construction site can detect virtuals. Confirmed the lexer already
emits `Punct::DotStar` and `Punct::ArrowStar` (line 100 of
`lexer.rs`) — no lexer work needed.

### Design

**AST**:
- `Type::MemFn { class_id, ret, params }` — 8 bytes, align 8, mangled
  as `M<class_id>_F<typecodes>_` for overload-resolution uniqueness.
  `decay()` is a no-op (MFPs don't decay).
- `Expr::AddressOfMember { class, method }` — produces an 8-byte MFP
  value. Codegen emits `lea rax, [rip+sym]` via `RipRef::Func`.
- `Expr::CallMemberPtr { recv, ptr, args, arrow }` — indirect call
  with `this` from `recv` (`&recv` for `.*`, `recv` for `->*`) and
  function address from `ptr`. Args shift by one positional slot
  (RCX = `this`).

**Parser**:
- MFP declarator: new arm BEFORE the existing `(*ptr)(...)` fn-ptr
  path. Pattern-match `( Ident :: * [name] )` where Ident is a known
  class tag. ~30 LoC.
- `&Class::method`: new arm at the top of `unary()` BEFORE the
  generic `&` Addr path. Pattern-match `& Ident :: Ident` where
  Ident is a known class tag. ~20 LoC.
- `.*` / `->*`: new arm in `postfix()` BEFORE the existing
  `.`/`->` arm. Produces `CallMemberPtr` with **empty args** as
  a partial. The existing `LParen` (CallPtr) arm in `postfix` then
  detects a partial CallMemberPtr by `args.is_empty()` and fills
  in the call's args instead of wrapping with `CallPtr`. This two-
  stage shape works because `(obj.*p)(3)` parses as:
  primary → `LParen` → `expr()` parses `obj.*p` → `RParen`; then
  back in outer postfix, the `(3)` hits the LParen arm which sees
  the pending CallMemberPtr and merges. ~25 LoC net.

**Codegen**:
- `Type::MemFn` size/align = 8. `load_rax(MemFn)` loads 8 bytes
  (added to the existing `Type::Ptr(_) | Type::Int { bytes: 8 }`
  arm). `store_at_rcx`'s size-dispatched store handles 8 bytes
  unchanged.
- `Expr::AddressOfMember`: lookup the resolved method's symbol via
  the new `member_target_symbol` helper, then emit
  `lea rax, [rip+sym]` (RipRef::Func). Virtual targets are rejected
  inside `resolve_member_for_mfp` with the J-14b deferral phrase.
- `Expr::CallMemberPtr`: new `gen_member_ptr_call` helper. Same
  shape as `emit_indirect_call_with_lead` (build slots, save fn
  pointer to a tmp, load arg regs, `call rax`) but with `this`
  loaded first into RCX and explicit args shifted by one slot.
  ~80 LoC for the helper.

### Virtual-MFP rejection

In `resolve_member_for_mfp`: after looking up the class by tag,
check `records[class_id].vtable` for any entry with the matching
key. If found ⇒ error with the J-14b deferral phrase. This catches
the test `j14_mfp_virtual_method_rejected_with_grep_pin` cleanly
at compile time (no AST machinery for 16-byte virtual MFPs; v1 is
deliberately simple).

### Overloaded MFPs (v1 simplification)

For an overloaded method, `resolve_member_for_mfp` returns the
**first** registered overload candidate (matches `method_target`
precedence). Explicit signature-based disambiguation at the
`&Tag::name` site is filed for a future tick — the test
`j14_mfp_overloaded_method_picks_first` exercises the single-
overload case (no ambiguity in v1).

### Honest framing

- **Simplifying assumptions made**: (a) the first overload
  candidate wins at `&Tag::name`; (b) the MFP equality `==` works
  for same-module addresses because the high 32 bits of the
  function address agree (cmp_set uses 32-bit `cmp` — adequate for
  the test, a known limitation for cross-module compares); (c)
  only `(obj.*p)(args)` and `(ptr->*p)(args)` immediate-call forms
  are supported — a bare `obj.*p` value (e.g. passed to a
  function) would leave a partial CallMemberPtr in the AST that
  reaches codegen and produces a clear error.
- **Virtual MFPs (J-14b)**: real C++ ABIs use a 16-byte MFP for
  virtuals (function ptr + this-adjustment offset + vtable index).
  v1 stays simple and rejects with a Grep-pinned phrase. The
  rejection is at the `&Foo::virtual_method` construction site,
  so the type system never sees an MFP value that *might* be
  virtual — every MFP at runtime is guaranteed to be an absolute
  function address.
- **Multiple inheritance**: the brief explicitly defers this. Our
  records have at most one base, and the base subobject is at
  offset 0, so the `this`-adjustment offset is always 0 in mdbcc's
  v1 — even if it had a slot in our MFP layout, it would be
  unused.
- **Pointer-to-data-member**: out of scope per brief. Different
  ABI shape (offset, not address), not needed for any v1 idiom.

### Honest gaps remaining

- **J-14b** (virtual MFPs): test-locked at the rejection phrase.
  Implementing requires (a) widening the MFP storage to 16 bytes
  conditional on whether the target was virtual at construction —
  but the *value* can come from anywhere, so the safer route is
  always-16-byte MFPs and a runtime dispatcher (vtable lookup if
  the function ptr is actually a slot index, direct call if it
  isn't). Wraps to ~150 LoC parallel work.
- **Pointer-to-data-member** (`int Foo::*`): different feature,
  same syntactic family. Filed for a later focused tick.
- **MFP-typed function parameters / returns**: should "just work"
  via the regular 8-byte-value marshalling, but no v1 test
  exercises it.

## Tick 64 — 2026-05-23 — J-13 v1 variadic user functions

**Goal**: close J-13 v1 — free variadic functions
(`int sum(int n, ...) { va_list ap; va_start(ap, n); … }`) work
end-to-end. Two ABI surfaces:
1. **Callee side** — `<stdarg.h>` resolves to an intrinsic header
   declaring `typedef char *va_list;`; `va_start`/`va_arg`/`va_end`
   are *codegen intrinsics* (recognised directly in the parser, NOT
   preprocessor macros). The variadic-function prologue spills
   RCX/RDX/R8/R9 into the caller-allocated home space at
   `[rbp+16..+40]` so `va_start(ap, last)` can compute
   `ap = rbp + 16 + 8*(last_index+1)` and walk a contiguous slot
   array; stack args ≥ position 4 sit immediately after at
   `[rbp+48..]`, so the same `ap += 8` loop works uniformly.
2. **Caller side** — when a call site's resolved callee name is in
   the new `sigs.variadic` set, an FP argument at positional slot
   0..3 is emitted into BOTH the positional XMM and the
   corresponding GPR (Win64 §A.5.1.2). Non-variadic callees stay
   byte-identical (the set is empty in every pre-tick-64 program ⇒
   the O1 88 e2e regression contract holds).

**Touch surface**: `src/ast.rs` (+41 LoC — `Function::variadic`
field, `Expr::VaStart`/`VaArg`/`VaEnd`); `src/parser.rs` (+163 LoC
— `param_list` returns `(params, variadic)`, six call-site updates
to thread the bit + reject variadic ctors/member-fns, parse-time
recognition of the three `va_*` intrinsics in `primary`, a new
`variadic_protos` HashSet to fold prototype-declared variadic onto
the matching definition's AST); `src/codegen.rs` (+282 LoC —
`Sigs::variadic` HashSet, prologue home-space spill, two new Gen
fields `variadic_named`/`is_variadic`, two new lowerings
`gen_va_start`/`gen_va_arg` (~80 LoC each), caller marshalling
gains a `callee_variadic && arg_is_fp && ri<4` extra GPR-load arm,
plus codegen-side rejections for variadic + record-return);
`src/pp.rs` (+19 LoC — `STDARG_H` const + resolver gate);
`tests/cpp_variadic.rs` (+292 LoC, 12 tests including 2 cl
differentials).

### Investigation (probe before fix)

Read `param_list` (already advances past `...` and breaks — the
flag was just thrown away), the function prologue
(`Gen::run`, lines 1738-1813 — spills named params to local slots
in DFS order; can be extended without touching the local-slot
layout), and `marshal_args` (the variadic-callee FP-AND-GPR rule
slots cleanly into the existing FP-loaded-into-xmm path). Looked
at `pe::is_win32_import` to confirm there's no
`HashSet::contains`-style precedent that closes over Sigs from a
free function — the `sigs.variadic` HashSet is read from the
emit loop via `self.sigs.variadic.contains(key)` which is the
same shape `self.is_builtin` uses, so the codegen layering stays
consistent.

### Design

**AST**:
- `Function::variadic: bool` — set to `true` by `param_list` when
  `...` was consumed. Defaults to `false` everywhere a `Function`
  is constructed without an explicit param list (synthesised
  ctors/dtors, the synthesised default-ctor-for-polymorphic-no-
  ctor path, base-chaining ctors/dtors — none of these can be
  variadic so the flag is always `false`).
- `Expr::VaStart { ap, last_name }` — `last_name` is captured as a
  raw String, NOT a Var expression, because `va_start`'s second
  argument MUST be the unaltered name of a parameter; a generic
  expression there would defeat the lookup. The parser enforces
  this at parse time with a clean diagnostic.
- `Expr::VaArg { ap, ty }` / `Expr::VaEnd { ap }`.

**Parser**:
- `param_list` returns `(Vec<(String, Type)>, bool)`. Every caller
  destructures the tuple; non-free-function sites (ctors/dtors,
  member fns) reject `variadic == true` with a clear scope-limit
  diagnostic. Free-function prototypes that declare variadic store
  the name in `variadic_protos`; the final `parse()` pass folds
  those bits onto any matching Function definition (so an extern
  declaration's variadic bit reaches the codegen).
- `primary` recognises `va_start`/`va_arg`/`va_end` BEFORE the
  generic `Ident(name) LParen` arm — they intercept the parens
  and parse a TYPE for `va_arg`'s second operand
  (via `type_name()`, mirroring `sizeof(T)`).

**Codegen**:
- New `Sigs::variadic: HashSet<String>` populated once by
  `compile_module` from the items pass. Looked up at every call
  site via `sigs.variadic.contains(key)`.
- `Gen::new` rejects variadic + HiddenPtr-return (the implicit
  RCX hidden-result-pointer would collide with the home-space
  layout `va_start` depends on) and variadic + zero-named-params
  (no `last` for `va_start` to anchor against). Captures
  `variadic_named: Vec<String>` (the source-order parameter
  names) and an `is_variadic: bool` flag.
- `Gen::run` adds, BEFORE the existing named-param spill, a four-
  iteration loop that emits the home-space spill via
  `ARG_SPILL[0..4]` with positive disp32 offsets 16/24/32/40 —
  *only* when `is_variadic` is true. The existing local-slot
  spill is untouched ⇒ the body sees parameter values at exactly
  the same locations they had pre-tick-64.
- `gen_va_start(ap, last_name)`: look up `last_name`'s position in
  `variadic_named`; emit `lea rax, [rbp + 16 + 8*(idx+1)]`; then
  the usual `gen_addr(ap); mov [rcx], rax` store-through-lvalue
  shape.
- `gen_va_arg(ap, ty)`: load current `ap` into rax, save; add 8;
  write the new ap back via `gen_addr(ap)`; load `*(T*)cur` into
  the correct result register (sized integer load with sign/zero
  extend for 1/2/4/8 byte int, `movsd xmm0, [rax]` for FP).
- `gen_va_end`: no-op (intentionally — the Win64 va_list is a
  bare `char*`, no heap state).
- `marshal_args`: the existing FP-into-xmm path gains, when
  `callee_variadic` is true, a second emit:
  `mov <gprI>, [rbp-t]` — the temp slot already holds the IEEE-
  754 bit-pattern from the `store_tmp_xmm0` above, so a plain GPR
  load suffices; no `movq xmm→gpr` detour needed.

  "hidden-result-pointer + va_list home-space layouts would
  collide" so the error is greppable.
- **`va_arg` with a record type**: rejected — small structs travel
  in registers and bigger ones by hidden pointer, with subtle
  Win64 semantics that would need callee/caller agreement and
  no current test exercises any way. Filed for a future tick.
- **Win64 promotion handling**: a user who writes
  `va_arg(ap, char)` reads the low byte of the 8-byte slot. The
  caller — if it's also mdbcc — passes an `int`-sized argument
  per C's default promotion (mdbcc doesn't narrow to `char` at
  the variadic call site), so the low byte IS the int's value
  cast to char. The user gets what C says they get. We don't
  warn on the misuse — same lenient stance as `printf("%d", c)`.
- **`<stdarg.h>` macros vs intrinsics**: the brief suggested
  trying preprocessor macros first. I went straight to codegen
  intrinsics because `va_arg(ap, T)`'s second argument is a
  TYPE, not an expression, and mdbcc's preprocessor has no
  way to express a type-as-argument. Codegen intrinsics also
  give us cleaner diagnostics (the parser can pin "must be a
  parameter name" / "outside a variadic function" instead of
  expanding to a meaningless macro arithmetic expression).

### Honest gaps remaining

- **J-13b**: variadic member functions, variadic constructors,
  variadic + record-return. Test-locked at their rejection
  phrases (Grep-pinned with the v1-scope note).
- **`<stdarg.h>` outside the intrinsic header**: real Borland
  `<stdarg.h>` includes a vendor-specific macro set; an attempt
  to `#include "stdarg.h"` (a quoted user copy) bypasses the
  intrinsic and would fail to parse the macro body. Out of scope
  — every well-formed program writes `<stdarg.h>` system-style.
- **Variadic function-pointer types** (`int (*p)(int, ...)`):
  the `Type::Func` shape has no variadic flag, so a function-
  pointer call through a variadic prototype wouldn't see the
  FP-in-XMM-AND-GPR rule. No test exercises this and the
  function-pointer table machinery would need broader changes.
  Filed for J-13c if a real OWL fixture needs it.

## Tick 66 — 2026-05-23 — J-10b memberwise copy-ctor synthesis

**Goal**: close J-10b. Tick 58 (J-10 v1) added user-defined copy-ctor
invocation on by-value pass/return and registered a defensive
`CodegenError` for "class with class-typed member that has a copy
ctor, but the outer class has no copy ctor" — Grep-pinned phrase
`"memberwise synthesis is deferred to J-10b"`. This tick lifts that
gap: the outer's copy ctor is now SYNTHESISED memberwise, registered
under the canonical `<Tag>::<Tag>` symbol so tick 58 / tick 61
callers (`Sigs::copy_ctor_symbol`) find it transparently.

**Touch surface**: `src/codegen.rs` (pass-1 detection + registration
in place of the defensive guard, +60 LoC; new `build_synth_copy_ctor`
hand-rolling the body, +120 LoC); `tests/cpp_copy_ctor.rs` (5 new
J-10b tests; one tick-58 defensive-rejection test repurposed into a
"compiles cleanly now" lock); this journal.

### Design

The brief explicitly said *"hand-roll the codegen in pass 2 directly
without going through the AST"* if AST changes would balloon the
diff. We took the hand-roll path — no new `Item::Func` synthesis, no
parser participation. The synthesised body lives entirely in
`codegen.rs` as a freestanding x86-64 byte stream, mirroring how
`build_personality_function` (Phase H4a) injects its own function
into `funcs`.

**Pass 1 (`compile_module`)**: walk every record. If the outer has
no copy ctor of its own but contains a class-typed member (peeled
through arrays) with one, push `outer_id` onto a `synth_copy_ctors`
vec. Out-of-scope cases reject loudly per the brief's
"non-goals" section:
- Outer has a base class ⇒ `"synthesized copy ctor with non-trivial
  base class is deferred to J-10b-base"`.
- Outer is polymorphic (has a vtable) ⇒ similar Grep-pinned phrase
  pointing at J-10b-base (the vptr install would duplicate parser-
  injected ctor logic).

For each entry, register the synthesised ctor under `<Tag>::<Tag>`
in `sigs.funcs` with params `[Type::Ptr(Record), Type::Ref(Record)]`
— exactly the shape `copy_ctor_symbol`'s path-2 lookup expects.
This is the single integration point with all of tick 58 / 61 / 62's
machinery — no per-call-site change is required, the lookup
transparently returns the synthesised symbol's mangled name.

**Pass 2 (`build_synth_copy_ctor`)**: emit one `CompiledFn` per
`synth_copy_ctors` entry, BEFORE the personality-function build (the
synthesised ctors are ordinary mdbcc functions with the standard
prologue/epilogue, so the `.pdata` / `.xdata` emission handles them
exactly like a user function).

Body shape:
1. Standard prologue (`push rbp; mov rbp, rsp; sub rsp, 48` — the
   imm32 `sub` is REQUIRED because `pe::read_prolog_alloc` validates
   the exact byte pattern `48 81 EC <imm32>`; the 1-byte `83 EC <i8>`
   short form is rejected).
2. Spill `rcx` (this) and `rdx` (src) to `[rbp-8]` / `[rbp-16]`.
3. For each field, in declaration order:
   - If field's element type (arrays peeled) is a class with a copy
     ctor: emit a call. `lea rcx, [rbp-8] -> mov rcx, [rbp-8]; lea
     rcx, [rcx+field_off]` and similarly for `rdx`, then `call <inner
     ctor>` with the CallSite recorded for the PE writer.
   - Array of class-typed-with-ctor: loop unrolled `count` times,
     stepping by `elem_size`.
   - Anything else: an unrolled byte-copy of `field.size()` bytes
     (the same pattern as `Gen::emit_struct_copy`).
4. Standard epilogue (`leave; ret`).

Each per-field block re-derives `rcx` / `rdx` from the spilled slots
rather than threading them through register saves — keeps every
block self-contained (no inter-field register state assumed), so
adding/reordering fields stays straightforward.

## Tick 69 — 2026-05-23 — J-11b / J-15b: partial-construction unwind

**Goal**: implement the shared cleanup-scope machinery flagged in
tick 59 (J-11b) and tick 60 (J-15b) — the personality function
extension that lets a non-catch scope run cleanup actions during
exception search and resume propagation. Two test-locks to flip:
`tests/cpp_exceptions.rs::t45` (1010 → 1110) and
`tests/cpp_new_array.rs::…_partial_construction_…_leaks` (300 → 303).

**Touch surface**: `src/eh.rs` (CatchPolicy::Cleanup variant +
personality function dispatch path + `EH_SAVE_NAME` global
constant), `src/pe.rs` (build_xdata catch_kind=3 emission),
`src/codegen.rs` (gen_new_array cleanup pad + `Gen::run` ctor
cleanup pad + global reservation), `tests/cpp_new_array.rs` (flip
+ rename test + 2 new), `tests/cpp_exceptions.rs` (flip + rename
t45 + new t46 + widen t27's `.data` budget for the new save area).

### Design — three-piece machinery

1. **`CatchPolicy::Cleanup` variant** in `src/eh.rs`. Carries no
   data — the scope-table entry's existing `try_begin/try_end/
   handler` fields are sufficient.

2. **Personality function** in `src/eh.rs::build_personality_
   function` now takes an `eh_save_global_idx` parameter and gains
   a "cleanup kind" branch at the catch-kind dispatch point: when
   the scope-table entry's `catch_kind == 3`, it
   - skips type matching (any in-range exception triggers);
   - COPIES `ExceptionCode`, `NumberParameters`, `args[0]`, `args
     [1]` from `*ExceptionRecord` into the module-wide
     `.mdbcc_eh_save` global (24 bytes total) — this is the
     load-bearing trick: after `RtlUnwindEx` transfers control,
     the `ExceptionRecord` pointer the personality function held
     points into the now-unwound `RtlDispatchException` frame
     which is reclaimed; the cleanup pad would read garbage if it
     dereferenced. The save area keeps the values stable;
   - calls `RtlUnwindEx` with `ReturnValue = 0` (cleanup pads do
     not read it — the save area is the source of truth).

3. **Cleanup landing pads** — emitted by codegen at the source
   sites:
   - **Array-new (J-15b)** in `gen_new_array`: a per-array
     cleanup scope wraps the ctor loop. The pad reads `[rbp-iter]`
     (count of constructed elements), loops it down to 0 calling
     `T::~T(payload+i*sizeof(T))` (if T has a dtor), then
     `HeapFree(GetProcessHeap(), 0, block)`, then re-raises by
     reading `.mdbcc_eh_save` and calling `RaiseException`.
   - **Derived ctor (J-11b half-step)** in `Gen::run`: when the
     function is `Tag::Tag` for a class whose base has BOTH a
     ctor and a dtor (the gate ensures the parser placed a
     base-ctor call as the FIRST statement of the body), wrap
     the post-first-statement portion of the body in a cleanup
     scope. The pad calls `Base::~Base(this)` and re-raises.

### Why the re-raise pattern (not RtlUnwindEx-resume)

The Microsoft x64 SEH convention for cleanup-then-continue is
`ExceptionCollidedUnwind` + a second `RtlUnwindEx` call with a
different `TargetFrame`. Implementing it correctly requires the
personality function to be re-entrant in a specific way and to
track which scope it was invoked for; the implementation cost is
non-trivial and the search re-walks anyway.

We use the simpler "cleanup pad re-raises the original exception
via `RaiseException`" pattern. The cleanup pad's PC is OUTSIDE
its own scope's `[try_begin, try_end)`, so the re-raise's
search-phase doesn't re-trigger the cleanup; it finds the next
outer scope (the user's `try`/`catch` or another cleanup). This
is wasteful (the search re-walks scope tables) but correct, and
the byte / complexity cost is well under the brief's 300 LoC
budget cap.

### Why a separate `.mdbcc_eh_save` global (vs reusing the ER ptr)

A bug surfaced in initial probe runs: passing the `EXCEPTION_
RECORD*` as `ReturnValue` and reading fields from `*er` in the
cleanup pad gave `e = 3` instead of `e = 99` (the literal in
`throw 99`). The ER pointer references the `RtlDispatch
Exception` stack frame, which the OS reclaims during
`RtlUnwindEx`. Subsequent calls (HeapFree, GetProcessHeap)
overwrite that stack memory before the cleanup pad's re-raise
reads from it.

Fix: a module-wide 24-byte global the personality function
populates BEFORE `RtlUnwindEx`. Layout (locked in
`src/eh.rs::EH_SAVE_NAME` doc):

```
[+0]  u32 code         (ExceptionCode)
[+4]  u32 numparams    (NumberParameters)
[+8]  u64 args[0]      (ExceptionInformation[0])
[+16] u64 args[1]      (ExceptionInformation[1])
```

24 bytes total per module — appears in `.data` for any TU with
try/throw. Adjusted `t27_int_only_throw_program_has_no_class_
eh_overhead`'s budget from `<= 16` to `<= 64`; the lock that
`.mdbcc_eh_buffer` (the class-throw object buffer) is NOT
inflated for int-only programs remains via
`t26_class_throw_inflates_data_section`.

## Tick 70 — 2026-05-23 — J-11b-members: class-typed member subobjects

**Goal**: close J-11b-members. When a ctor throws AFTER one or more
class-typed member subobjects have been fully constructed, each
constructed member's dtor MUST fire on the unwind path (reverse
declaration order, per C++ [class.dtor]/9), then the base dtor (if
any). The base-only case from tick 69 stays correct; the new member
case stacks ON TOP of it.

**Touch surface**: `src/parser.rs` (member-ctor/dtor splicing
helpers + class-finalisation pass `inject_member_ctor_dtor_calls`),
`src/codegen.rs` (cleanup-pad extension with counter-gated per-
member dtor dispatch, `ctor_cleanup_member_dtors` helper,
`maybe_advance_member_counter` helper), `tests/cpp_exceptions.rs`
(t47, t48, t49 — the three behaviour locks).

### Design — counter-gated cleanup pad (mirrors tick 69's array-new)

1. **Parser, post-class-finalisation**. The parser's
   `record_specifier` finalises `records[id].fields` after parsing
   all class members. AT THAT POINT we walk `cxx_funcs` and splice
   into every `Tag::Tag` and `Tag::~Tag` body:
   - Ctor: AFTER the parser-injected `Stmt::SetVptr(id, _)`, insert
     a `this->m.MemberTag()` call (`Expr::MethodCall { recv:
     Member{base: Var("this"), field: m, arrow: true}, name:
     MemberTag, args: [] }`) for each class-typed member with a
     ctor not already in the user's minit list.
   - Dtor: BEFORE the parser-appended base-dtor call (or at end of
     body if no base dtor), insert `MemberTag::~MemberTag(&this->m)`
     for each class-typed member with a dtor, in REVERSE declaration
     order.
   The splice happens in a post-pass because `records[id].fields`
   is empty during member parsing — `ctor_full_body` runs when only
   members 0..K-1 have been seen, so it can't know what's coming.

2. **Codegen, counter slot**. In `Gen::run` for a ctor `Tag::Tag`,
   compute the dtor roster from `records[id].fields` (excluding
   inherited base fields). If the roster is non-empty (and EH is
   active in the module), allocate a frame tmp `counter_slot` and
   initialise to 0 BEFORE try_begin. Build `field_to_counter`
   mapping `field_name → 1-based index`.

3. **Codegen, counter advance**. After EACH ctor-body statement,
   `maybe_advance_member_counter` checks if the statement is a
   `this->m.MemberTag()` MethodCall shape; if so, looks up the
   field in `field_to_counter`, and emits a single
   `mov qword [rbp-counter], imm32` setting the counter to the
   1-based field index.

4. **Codegen, cleanup pad**. Same structure as tick 69's
   `ctor_cleanup_base_dtor` pad, with a prepended chain of member-
   dtor dispatches:
   ```
   for each (offset, dtor) in roster.iter().enumerate().rev():
       cmp qword [rbp-counter], (i+1) as imm32
       jl skip_K
       lea rcx, [rbp-this_off] ; rcx = &this (then load *this)
       mov rcx, [rcx]          ; rcx = this pointer
       add rcx, offset         ; rcx = &this->m
       call MemberTag::~MemberTag
   skip_K:
   ```
   Then the tick-69 base-dtor call (if any), then re-raise via
   `RaiseException` reading from `.mdbcc_eh_save`. The pad's PC is
   OUTSIDE its own scope's `[try_begin, try_end)`, so the re-raise
   doesn't re-trigger the cleanup; search continues to the outer
   try/catch.

### Why ONE scope-table entry (not one per member)

A multi-scope layout (one Cleanup scope per member, each pad
calling only its own dtor and re-raising into the next outer scope)
is brittle: the personality function picks the FIRST matching scope
in the table, so to get dtor ordering N→N-1→...→1 the scopes must
be pushed in REVERSE construction order, and each pad's PC must
sit OUTSIDE all scopes for inner members but INSIDE all scopes for
outer members. The `try_end` boundaries become intricate.

The counter approach (one Cleanup scope, one pad with a linear
chain of conditional dtor calls) is identical to tick 69's array-
new pattern and is robust to ordering changes — the personality
function just sees one scope, runs the pad, and the pad's internal
logic handles all dtors in reverse order regardless of which
member triggered the throw.

### Mixed base + members (t49)

When BOTH a base ctor cleanup (tick 69) and a member cleanup
(tick 70) apply, `cleanup_setup` carries both:
* The cleanup pad emits the member-dtor chain FIRST (counter-
  gated, reverse order).
* Then emits the base-dtor call (tick 69's static `Base::~Base
  (this)`).
* Then the re-raise.

Per C++ standard: member dtors run first (reverse declaration
order), then base dtor. The pad's emission order matches.

having ctors (regardless of base). This collided with J-10b's

`Tag::Tag` directly in `sigs.funcs` with the copy-ctor signature,
and its defensive `debug_assert` fires if a default ctor is

Both are larger surface changes than the v1 brief covers.

## Tick 71 — 2026-05-23 — J-14b virtual member-function pointers

**Goal**: close J-14b — lift tick 62's `&Foo::virtual_method`
rejection. A virtual MFP must dispatch through the receiver's
vtable, not through a baked function address. Keep the existing
8-byte MFP storage (no AST/ABI widening), keep the existing
non-virtual call path byte-identical, and add a tiny per-call
dispatcher that picks the right path at runtime.

**Touch surface**: `src/codegen.rs` (`resolve_member_for_mfp` no
longer rejects virtuals + carries the slot index;
`member_target_symbol` returns `Option<String>` — `None` ⇒
virtual; `Expr::AddressOfMember` codegen emits `mov rax, imm64`
for virtual targets; `gen_member_ptr_call` inserts the runtime
dispatcher); `tests/cpp_mfp.rs` (4 new J-14b tests + flipped the
old rejection test to a success test).

### Investigation (the chosen encoding)

The brief offered two designs:
1. 16-byte MFP (canonical MSVC layout): widen `Type::MemFn::size`
   from 8 to 16, store function address (or stub) + this-adj +
   vtable index.
2. **8-byte MFP with a single-bit virtual marker**, encoded in a
   "definitely-free" bit of the address.

Brief recommended (2) using **bit 0** because PE convention is
16-byte function alignment. **mdbcc does not enforce function
alignment** — `pe::build_text` lays functions back-to-back with
`cursor += f.code.len()`, so bit 0 of an arbitrary function's
address is whatever the previous function's code length parity
left it. STOP-condition triggered for the bit-0 variant.

Pivot: use **bit 63** instead. `IMAGE_BASE = 0x1_4000_0000` and
all functions land below `0x2_0000_0000` (a 33-bit address space
ceiling at v1 program sizes). Bit 63 is guaranteed zero for every
non-virtual address — the canonical-x64 high-half-zero invariant
plus mdbcc's image layout makes this concrete. No alignment
hack, no PE writer change, no AST size change, no `o1_byte_
identity` rebaseline. The cost is one `test rax, rax` + `jns
rel32` + 12 bytes of virtual-path code at every MFP call site
(present iff the function uses `.*` or `->*`; zero footprint
elsewhere).

### Encoding

For `&Class::method`:
- **Non-virtual target**: bytes 0..7 = absolute function address
  (bit 63 = 0). Construction code is unchanged: `lea rax,
  [rip+sym]` via `RipRef::Func`.
- **Virtual target**: bytes 0..7 = `(1u64 << 63) | (vslot * 8)`.
  Construction emits `mov rax, imm64` with the encoded value.
  The vslot is looked up in `records[class_id].vtable` by method
  name — single inheritance keeps slot indices stable, so the
  static slot at construction equals the dynamic slot at call.

For `(obj.*p)(args)` / `(ptr->*p)(args)`:

```
test rax, rax           ; SF = bit 63
jns nonvirt             ; non-virtual: rax is already the fn addr
btr rax, 63             ; clear bit 63 → rax = vtable byte offset
mov r10, [rcx]          ; r10 = vptr (this is at rcx)
mov rax, [r10 + rax]    ; rax = vtable[slot]
nonvirt:
call rax
```

12 bytes of dispatcher (test+jns+btr+mov+mov), 2 bytes of `call`.
RCX (this) is preserved across the dispatcher; R10 is caller-
saved and free. Both paths converge with rax holding the actual
function address — the existing `call rax` is unchanged.

### Code changes

**`resolve_member_for_mfp`** (~20 LoC delta): the virtual-target
rejection is removed; the helper now returns a 4-tuple
`(class_id, ret, params, vslot)` where `vslot: Option<usize>`
indicates virtuality. The slot index is computed from
`records[class_id].vtable.iter().position(|s| s.key == method)`.

**`member_target_symbol`** (~10 LoC delta): returns
`Option<String>` instead of `String`. `None` ⇒ virtual ⇒ caller
must emit the encoded-constant variant, not a `lea`.

**`Expr::AddressOfMember` codegen** (~15 LoC): added a `match`
on the helper's return — `Some(sym)` is the existing `lea rax,
[rip+sym]` path (byte-identical), `None` re-runs
`resolve_member_for_mfp` for the slot and emits `48 B8` (mov
rax, imm64) followed by the 8-byte encoded value.

**`gen_member_ptr_call`** (~8 LoC delta): the dispatcher
sequence is inserted between `self.load_tmp(fp)` and the final
`call rax`. The existing tmp-freeing and stack-arg marshalling
are untouched.

### `Expr::expr_type` for `AddressOfMember`

Updated to take the new 4-tuple and discard the `vslot` — the
**type** of a virtual MFP is the same `Type::MemFn` shape as a
non-virtual one (only the runtime value differs).

### Honest framing

- **Why bit 63 instead of bit 0**: function alignment is not
  enforced in mdbcc's PE writer. Bit 0 of `lea rax,[rip+f]`
  varies with the parity of the previous function's code
  length. Bit 63 is invariant: the image base is well below
  `0x8_0000_0000_0000_0000`, and no realistic v1 program
  approaches the canonical-x64 high-half boundary.
- **`btr rax, 63` vs `shl/shr` round-trip**: `btr` is one
  instruction (5 bytes), the shifts are two (6 bytes). Same
  effect on the encoded value (zeros bit 63, preserves the
  rest); the saved byte is incidental — `btr`'s primary virtue
  is that the intent ("clear bit 63") reads off the source.
- **Single-inheritance slot stability**: an MFP taken on
  `&Base::vmethod` records Base's slot index. When called
  through a Derived `this`, the dispatcher's
  `[r10 + offset]` looks up the slot in **Derived's** vtable —
  but `offset` is Base's slot index, which equals Derived's slot
  index because mdbcc's `rebuild_vtables_for_overloads`
  preserves inherited slot positions (base-first layout).
  Multiple inheritance would break this (`this`-adjustment + a
  per-base vtable region per subobject), but multiple inheritance
  is explicitly out of v1 scope.
- **Pure virtual targets**: an abstract class can never be
  instantiated (existing `is_abstract` check in `New`/local
  decl), so a pure slot can never be dispatched through.
  `&Abstract::pure` itself compiles — the encoded slot index is
  fine — but the call will indirect through a 0 vtable slot and
  fault. Filing as J-14b-pure if it ever matters.
- **Equality of virtual MFPs across hierarchies**:
  `&Base::vmethod == &Derived::vmethod` compares two encoded
  vslot values. For a non-overridden inherited slot in Derived,
  both sides encode the same slot index ⇒ equal. For an
  overridden slot, **also** equal (the slot index doesn't change
  — only the slot's content does). MSVC's behaviour here is
  implementation-defined; mdbcc's "always equal when slot index
  matches" is a reasonable v1 take.
- **No-bit-0 reservation**: bit 0 of the encoded value is part
  of the byte offset (which is always a multiple of 8 ⇒ bit 0
  is naturally 0). If the supervisor's brief wanted bit 0 as
  the marker explicitly, the slot-byte-offset would have to
  shift left by 1 first — but that's purely cosmetic; bit 63
  is the cleaner home given mdbcc's actual address layout.

### Honest gaps remaining

- **MFP comparison `<` / `>`**: undefined behaviour in standard

  but not portable.
- **MFP-to-function-pointer cast**: not supported; the encoded
  value isn't a function address in the virtual case.
- **Cross-translation-unit virtual MFP**: not relevant (mdbcc is

- **Multiple inheritance + virtual MFP**: out of v1 scope; needs

### Why it works (the va_start math)

For `void Logger::log(int n, ...)`, `f.params = [this, n]` and
the variadic flag is true. The prologue spills RCX..R9 into
`[rbp+16..+40]` — RCX (= `this`) at +16, RDX (= `n`) at +24,
R8 (= first variadic) at +32, R9 (= second variadic) at +40.

`va_start(ap, n)` computes:
- `last_index = variadic_named.position("n") = 1` (this=0, n=1)
- `offset = 16 + 8 * (last_index + 1) = 16 + 16 = 32` ✓

The `+1` from `this`'s presence in `variadic_named` exactly
cancels the `+1` shift induced by `this` taking RCX. No new
math, no new ABI shape, no new opcode — just delete the block.

42]` and calls `gen_call_with_lead(&"Logger::log", None, &all)`.
`marshal_args` sees `lead = None`, `base = 0`, and treats `&l` as
the first positional arg (slot 0 → RCX). The variadic-FP-in-
XMM-AND-GPR rule (`callee_variadic = sigs.variadic.contains
("Logger::log")`) fires for any FP arg at slots 1..3 — which
correctly excludes the receiver (pointer) and correctly includes
the first explicit named arg + the first 2 variadic args.
