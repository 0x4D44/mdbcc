# 2026.06.16 — JRN — B-18: Win64 lib producer + RailC Win64 build

## Trigger

Arthur's RailC build failed first with `cannot read library
'…/target/bc45-libs/mdowl.lib'` (libs never built in this checkout), then —
after building them — with `link failed: machine mismatch in mdowl.lib(WINDOW.o):
expected Amd64, got I386`. That second error is exactly **B-18**: `build_bc45_libs`
was hardcoded `-m32`, and RailC's `mdbcc.toml` sets `target = "win64"`.

## What I found (scope was smaller than B-18's text implied)

B-18 described two missing halves. One was already done:

- **Project-driver half — DONE earlier** (`fa69d85`): `overlay_dirs` is a real
  `mdbcc.toml` key, prepended ahead of `include_dirs` in
  `project.rs::build_resolver`. B-18's "src/project.rs has no overlay logic" was
  stale.
- **Lib-producer half — the actual remaining work**: `build_bc45_libs` `-m32`.

Critically, the **`-m64` recipe is already validated end-to-end** by
`tests/railc_source_slice.rs::railc_source_built_dependency_slice_links_win64`
(hard gates O1 import-profile, O3 runtime interaction battery, O5 dialogs, O6
KINGSX pixel-parity). So this was **productization, not discovery** — replicate
that test's recipe in the producer.

The recipe (from the test): compile every TU `-c -m64 -D__WIN32__`; build
`OWL/WINDOW/DISPATCH/DIALOG.CPP` from the patched copies in `wrk_owl_win64/`
instead of the oracle; prepend `wrk_owl_win64/include64` (pointer-width
`WPARAM/LPARAM/LRESULT`) to every TU's include set.

## Decisions

- **Design fork (was open): Option A** — point `build_bc45_libs --target win64`
  at the existing `wrk_owl_win64/` (what the proven test uses). Smallest change;
  Option B (promote to a tracked `overlay/win64/`) is premature with one
  consumer ("don't predict the future"). `wrk_owl_win64/` is already git-tracked.
- **Output layout: `target/bc45-libs/win64/` subdir**, same four lib names.
  Fully isolated object tree / archives / `.fingerprint` from the win32 build,
  so building one never disturbs the other. Chose subdir over `mdowl64.lib`-style
  suffixes to keep the win32/win64 code paths symmetric (same `archive()` names,
  different `out_dir`) and minimise churn. (Open to renaming if Arthur prefers
  the suffix scheme the journal sketched.)
- **Default target stays win32** — additive; existing consumers/`cargo bc45-libs`
  unchanged.

## Changes

- `src/bin/build_bc45_libs.rs`: `Target{Win32,Win64}` enum + `--target` arg
  (default win32); `Layout.target` + `owl_overlay()`/`overlay_inc()`;
  overlay-aware `inc()/sinc()`; `owl_jobs` redirects the 4 patched OWL TUs;
  `compile()` takes the target flag; win64 `out_dir = …/win64`; fingerprint folds
  in the overlay tree. Unit tests for `parse_target` + `Target::flag`.
- `.cargo/config.toml`: `bc45-libs-win64` alias.
- `scripts/build-mdbcc.ps1`: now builds win32 **then** win64.
- `Cargo.toml` 0.6.0 → 0.7.0 (+ `Cargo.lock`).
- `railc/mdbcc.toml` (separate repo): `overlay_dirs = [wrk_owl_win64/include64]`;
  `libs` → `…/bc45-libs/win64/*.lib`.

## Verification

- `cargo bc45-libs-win64` → 4 Amd64 archives in `target/bc45-libs/win64/`
  (owl 106 ok/13 skip, streams 48, rtl 596/31, bids 22/5).
- RailC built via `mdbcc` (`target/release/mdbcc.exe` in `C:\language\railc`):
  "built railc.exe (win64, gui)", **machine 0x8664 / PE32+ / subsystem GUI**,
  12.9 MB.
- **O1 import gate (product exe, parsed import table — not a string grep):**
  imported DLLs = COMDLG32/GDI32/KERNEL32/SHELL32/USER32/WINMM; `USER32!
  Set/GetWindowLongPtrA` present; **no CTL3D32.dll**, **no KERNEL32!VirtualAlloc/
  VirtualFree** (process-heap shim won over the oracle heap members — the one
  risk the slice test doesn't exercise for the full lib). 403 by-name imports.
- Bounded launch crash-smoke: window up after 5 s, no early `0xC0000374`/AV.
- Win32 default path re-run → still produces i386 libs in `target/bc45-libs/`.
- `cargo test --release --lib` 250/250; producer unit tests 7/7.

## Surprises / dead ends

- **Stale-exe red herring**: my first `mdbcc | tail` run read `$?` of `tail`, not
  `mdbcc`, and an old 9.4 MB **I386** `build/railc.exe` was still on disk → PE
  header read as I386/PE32, briefly looked like the build silently produced
  32-bit. Re-running with the real exit code (and deleting the artifact first)
  showed the genuine fresh 12.9 MB Amd64 exe. Lesson: delete the output before a
  "did it rebuild?" check, and never trust `$?` after a pipe.
- **`grep "CTL3D32"` on the exe is a false positive** — RailC has its own CTL3D
  runtime `LoadLibrary` string; only an import-table parse distinguishes a real
  import from a string literal.
