# PLAN OF RECORD — Roadmap to compiling & running Borland OWL apps

Date: 2026-05-17. Status: ACTIVE. Author: roadmap investigation.
Complements scratchpad.md slices 1–15 and HLD Test Oracles V8.

## Arthur's decisions (2026-05-17)
- **D-1 = acquire GENUINE OWL source** (provenance-pinned, like bcc32).
  Real apps compile unmodified; the compiler-conformance bar rises —
  genuine OWL source (not our subset) is the forcing oracle.
- **D-2 = classic OWL 2.5 (BC++ 4.5 era)**.
- **D-2 refinement (roadmap recommendation, flagged for veto):** acquire
  the **32-bit OWL 2.5** (BC++ 4.5 shipped both 16-bit and 32-bit OWL
  2.5). Targeting the **32-bit** variant makes the port a Win32→Win64
  recompile; the 16-bit OWL 2.5 would force a Win16-semantics shim
  (16-bit WPARAM packing, MakeProcInstance, segmented model) — large,
  counter-goal work. Non-template benefit of 2.5 is preserved either
  way. PLAN ASSUMES 32-bit OWL 2.5 unless Arthur directs otherwise.
- **Acceptance-oracle caveat:** bcc32 **5.5.1** is a 5.5-era front-end;
  OWL 2.5 headers are pre-standard 4.5-era C++ and may not parse cleanly
  under 5.5.1. The genuine 4.5 acceptance reference would itself be a
  further acquisition. Mitigation: O3-acceptance may be partial for OWL
  headers; lean on O1 + the real target app running (Phase I) +
  mdbcc-parse of genuine headers as the conformance signal.

## North Star
Take a real legacy Borland C++ **OWL (ObjectWindows Library)** Windows
application's source, compile it with `mdbcc`, and have the resulting
**Win64 PE run on modern Windows 11**.

## Where we are (baseline, verified 2026-05-17)
- Slices 1–14 DONE: C89 + C++ subset + Borland dialect → Win64 PE,
  emitted directly. O1 (88 e2e, authoritative) + O2 (cl) + O3 (bcc32
  5.5.1 accept+behave). Build green, clippy clean.
- PE dynamic section layout fixed & merged to main.
- Slice 15 (16-bit DOS) explicitly out of scope (counter-goal).

## What's missing for OWL (gap analysis)
Critical-path codegen prereqs: (1) >4 args (Win64 stack ABI),
(2) function pointers, (3) virtual functions/vtables/virtual dtors,
(4) multi-DLL Win32 imports + GUI subsystem + WinMain. Then (5) an OWL
runtime, (6) resources (.rc), (7) float/double, (8) C++ maturation
(struct-by-value, exceptions/TXOwl, member-fn overload, array-new),
(9) real-app conformance.

## Strategic decisions (need Arthur)
- **D-1 OWL sourcing:** *reimplement a faithful OWL subset* in our own
  Borland-dialect C++ (own `owl/*.h` matching Borland's public API),
  compiled by mdbcc (RECOMMENDED — matches "reimplement BCC + OWL",
  BCC55 free CLI ships no OWL, scope-controlled) **vs** acquire genuine
  OWL source (max fidelity, far heavier C++/macro stress, provenance).
- **D-2 OWL era:** classic **non-template OWL 2.5 (BC++ 4.5)**
  RECOMMENDED (most legacy apps; defers templates + heavy EH) vs OWL 5
  (templated, BC++ 5.0x).
- **D-3 Oracle for the GUI layer:** OWL behavioural differential is
  unavailable (no Borland OWL toolchain on disk; GUI ≠ stdout). The
  language features *under* OWL stay fully O1/O2/O3-validated; the OWL
  GUI layer gets a new, honestly-weaker oracle O6 (GUI liveness:
  launch → find window by class/title → post WM_CLOSE → assert clean
  exit) + `mdscreensnap` golden + a real target app. brc32/brcc32
  (in BCC55) becomes a genuine *resource* differential reference.

## Phases (each: DESIGN → TDD RED → IMPL (GREEN) → REVIEW → APPLY-FIX;
## O1 stays authoritative & green throughout; journal + commit per phase)

### Phase A — Calling-path foundations: >4 args + function pointers
Hard prereq for every Win32 call/callback. Pure portable C/C++ —
fully O1/O2/O3-validated (bcc32 confirms behaviour).
- Design: Win64 ABI for args 5+ (stack slots, 32B shadow space, 16B
  alignment, caller cleanup); function-pointer types in AST/type
  system; `&func`, call-through-pointer, pointer params/locals/arrays.
- RED: 8-arg arithmetic; fn-pointer array dispatch; callback invoked
  by a helper (qsort-style). GREEN: implement. Differential locks it.
- Risk: ABI edge cases (varargs interaction deferred); alignment bugs.

### Phase B — Virtual functions, vtables, virtual destructors
The single biggest C++ gap; the heart of OWL. Portable C++,
O1/O2/O3-validated (bcc32 validates virtual dispatch).
- Design: vtable layout (we own the ABI — pick Itanium-like, doc it);
  vptr at offset 0 (reconcile with existing single-inh base-at-0);
  virtual call lowering; pure/abstract; virtual dtor + chained
  destruction; vtable → .rdata; ctor/dtor vptr set; override via
  base ptr/ref.
- RED: polymorphic shape area; virtual dtor order; abstract base.
- Risk: interaction with inheritance flattening; dtor/vptr ordering.

### Phase C — Win32 runtime substrate
Generalize PE writer + driver: multi-DLL import directory, GUI
subsystem (2) selected by presence of `WinMain`, WinMain entry stub,
arbitrary imports resolved from a built-in Win32 symbol→DLL table
(minimal intrinsic `<windows.h>`). Console path stays byte-identical
(regression: all O1/O2/O3 unchanged).
- New oracle **O6 (GUI liveness)**: tiny hand-written MessageBoxA app
  → launch → Rust Win32 probe finds/dismisses it → assert clean exit.
- RED: MessageBox app won't build/link → GREEN. Regression: console
  byte-identical.
- Risk: import-directory correctness; subsystem regression; honest
  that O6 is weaker than stdout differential.

### Phase D — Minimal OWL runtime v1 ("Hello OWL window")
First real OWL milestone. Per D-1: reimplement OWL subset.
- Design: TApplication (WinMain glue, message loop, Run +
  InitApplication/InitInstance/InitMainWindow virtuals), TModule,
  TWindow (RegisterClass, CreateWindowEx, static WndProc thunk →
  instance dispatch, virtual HandleMessage/DefWindowProc), TFrameWindow;
  OwlMain. Headers under an mdbcc-provided `owl/` matching Borland's
  public API so real app source is unmodified.
- Oracle: O6 liveness on the OWL hello app + `mdscreensnap` golden;
  all language oracles still green.
- RED: hello-owl source doesn't run → GREEN.
- Risk: WndProc thunk/instance-map design; ABI of our OWL vs codegen.

### Phase E — OWL event handling: response tables + core messages
- Design: DECLARE/DEFINE_RESPONSE_TABLE + EV_* macros lowered to a
  mechanism mdbcc supports (member-fn-ptr table or virtual dispatch —
  decide & doc); message cracking for the common WM_* set; TDC /
  TPaintDC (BeginPaint/EndPaint); default behaviours. Needs member
  function pointers (here or folded into A).
- Oracle: O6 + screenshots; "draw text + menu command + mouse click".
- Risk: macro-heavy headers stress the preprocessor; member-ptr ABI.

### Phase F — Floating point (float/double) + math + printf %f/%g
Big self-contained codegen piece (SSE2 xmm, Win64 FP ABI, conversions,
FP globals/params/returns, printf float specs). Off the
critical path to first window; movable earlier if target app needs it.
- O1/O2/O3-validated (bcc32 validates FP); closes part of printf gap.

### Phase G — Resource compiler (.rc → .rsrc) + dialogs/menus
.rc parser → .res → PE `.rsrc`; OWL TDialog/TMenu + Win32 dialog/menu/
resource APIs. **Real differential available**: brc32/brcc32 (BCC55)
compile the same .rc — compare .res structurally (new oracle arm).
- Oracle: brc32 resource differential + O6 (menu/dialog appears/works).

### Phase H — C++ maturation for real apps
Driven by the target app: struct/class by-value params/returns,
C++ exceptions (TXOwl hierarchy — largest sub-item, may split),
member-function overloading, array-new `new T[n]`/placement new,
operator[]/()/= lowering, block-scope shadowing, the known
global-initializer adjacent-string-concat bug.

### Phase I — Target-app conformance
Acquire 1–2 small genuine legacy OWL apps (provenance-pinned, like
bcc32). Success = compiles + launches + window + basic interaction +
clean exit. Real failures drive any residual gaps. Document fidelity.

## Cross-cutting
- O1 authoritative & green every phase; O2/O3 extended with new
  portable corpus per feature; clippy -D warnings clean; no new crate
  deps unless agreed (iced-x86 dev-dep for O5/v2 already pre-approved);
  journal + atomic commit per phase; scratchpad slice list updated.
- Sequencing: A → B → C → D → E; F and G parallelisable after C;
  H folded in as I demands; I last/continuous.

## Top risks (honest)
1. Scope is very large (OWL is tens of kloc even as a subset; multi-
   month). Mitigation: strict subset driven by ONE concrete target app
   (Phase I pulled in as the forcing function early).
2. No Borland OWL toolchain ⇒ the OWL GUI layer's oracle is weaker
   than the language layer's. Mitigation: keep every language feature
   under OWL on the strong O1/O2/O3 path; O6 + screenshots + real app
   for the GUI layer; brc32 for resources.
3. C++ EH + templates are deep — deferred via the OWL-2.5 choice;
   revisit if a target app needs them.
4. Borland message-dispatch (DDVT/response tables) uses member-fn
   pointers + macros — we control the OWL source so we choose a
   mechanism mdbcc supports while keeping the public macro API.
