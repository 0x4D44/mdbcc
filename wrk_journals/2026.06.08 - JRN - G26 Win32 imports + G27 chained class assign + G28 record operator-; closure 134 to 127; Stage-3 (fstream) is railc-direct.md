## The correction: Stage-3 (ios diamond) IS railc-direct

Chasing the residual TLayout::* (13 symbols), I found they are railc's OWN
TLayout window class — defined in railc **LAYOUT.CPP**, the one railc TU that
fails to compile. Its blocker:

    LAYOUT.CPP:1954  fstream infile;   // "cannot declare a variable of
                                       //  'fstream': virtual-base hierarchy
                                       //  not yet supported"

So **railc itself uses `fstream`** (file input for layout persistence) → it needs
the **ios virtual-base diamond** (istream/ostream : virtual ios; fstream :
iostream). The golden links it (fstream 8, filebuf 13 occurrences). This corrects
the BREAKTHROUGH workflow's "Stage-3 not on the critical path" — that analysis
examined only the 7 railc-direct *ctor* symbols and missed LAYOUT.CPP's fstream.

Stage-3 (task #10) is therefore the single largest remaining closure blocker:
~38 of the 127 (TLayout 13 via LAYOUT.CPP + the ~25 iostream/streambuf/filebuf/
fstreambase residual, all genuine — golden-linked). The doc/view/MDI/OLE files
stay DEAD (G25 dead-strip removed them); Stage-3 is needed ONLY for fstream/ios,
not those.
