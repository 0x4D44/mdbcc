## Why S4 / scope (see HLD)
A minimal OWL app (HELLOAPP 12 LoC / STEP01 23 LoC) uses only SI + a virtual
override + `new` — already supported. Templates/MI/RTTI are needed to compile
the OWL **headers + library** the app pulls in. Scope is set EMPIRICALLY by
compiling the OWL closure (the S3 playbook), not by a speculative general
template engine. Probe (2026-05-29): function/class templates + default args +
`dynamic_cast` + `typeid` are all GAPs; **non-virtual MI already compiles +
runs**. Templates are the long pole.

## Strategy
Monomorphisation (the only sane design; matches mdbcc's no-runtime-generics
model): a template is a recipe; each distinct type-arg set clones the generic
`Function`/`Record`, substitutes the type params, and feeds a concrete entity
into the EXISTING codegen. Staged S4.1→S4.6 (function tmpl → class tmpl →
BIDS headers → MI completion → RTTI → compile `<owl/applicat.h>`).

### S4.2b design — concrete, de-risked (2026-05-29, from reading the parser)
The class parser is the struct/union/class branch of `decl_specifiers`
(`parser.rs:~615`). A class template's pieces are **entangled** across four
parser structures, so the S4.1-style "parse via `external_declaration` then
capture the result" does NOT work cleanly:
  - the **record** is created + pushed at `parser.rs:629` (`records.push`),
    tag registered at `:640`;
  - **member functions** become `cxx_funcs` (mangled into `items` later);
  - **`ClassInfo`** at `self.classes[id]`; the **tag** in `self.tags`.
**Recommended approach:** thread a "parsing-class-template" flag/sink
THROUGH the class parser so that, when set, it captures the record +
member-fn bodies + ClassInfo into a `class_templates` entry and does NOT
register in `records[]`/`tags`/`cxx_funcs`/`items` — keeping the generic out
of every concrete-codegen path.
**Additional real blockers (from `TVectorImpBase`):**
  - **template-parameter base** `: public Alloc` — `parser.rs:667` does
    `self.tags.get("Alloc")` ⇒ "unknown base class". A template-param base
    must resolve to `Type::TemplateParam`; the base subobject is laid out
    only at instantiation.
  - **use-site `<` disambiguation** needs to know the name is a template (so
    `Box<int>` parses as a type-id, not `Box < int`) ⇒ capture MUST precede
    use-site parsing.
  - **member-function instantiation** — each member body is parameterised by
    the class's params; instantiated with the class.
**Staging:** (i) capture simple class templates (no base) + names;
(ii) use-site template-id parsing → instantiate; (iii) record + member-fn
instantiation; (iv) template-param bases; (v) placement-new codegen;
(vi) re-drive classlib→OWL. Multi-tick; warrants fresh context — the
entanglement means a rushed capture risks corrupting the record/tag/
cxx_funcs machinery the 88 SipHash baselines depend on.

### Tick B — `#include "..."` header-names lexed literally (`3c2fc02`)
The TRUE first blocker on `<owl/applicat.h>`: `cannot open include file
'classlibectimp.h'`. Cause: `STREAMBL.H` (in the closure) uses
`#include "classlib\vectimp.h"` (backslash, quoted), and the pp read the
filename from the lexer's escape-decoded `Str` bytes — so `\v` became a vertical
tab (0x0B), corrupting the path. Added a minimal `#include`/`#import`
header-name state machine to the lexer: after `#`+`include`/`import`, a quoted
`"..."` is lexed VERBATIM (no escape decode, no splice), per the C standard.
`<...>` unchanged (forward-slash works; backslash-in-angle = OBSOLETE-only, a
separate gap). Byte-identical (escape-free names lex identically). 3 new pp
tests.

### Tick C — BC++ 4.52 dialect: implicit-int + bool/true/false/mutable (`0748b35`)
Full suite green; clippy clean; 88 SipHash byte-identical; O15 C++-mode
parse-acceptance 79→80 (floor locked).
Probing bottomed out at `classlib/resource.h:23`:
`const DEFAULT_HASH_TABLE_SIZE = 111;` — **pre-standard implicit int**
(`const NAME = 111` ⇒ `const int NAME = 111`). resource.h ← classlib/defs.h ←
*everything*, so this single gap blocked the entire closure. Fixed
`decl_specifiers`: a cv-/storage-qualified declaration with no type names `int`
(gated on `saw_qualifier`, so explicitly-typed decls — the whole 88 corpus — are
byte-identical).

Next bottom-out: `classlib/defs.h:154` `enum TBool { false, true };` under
`#if defined(BI_NO_BOOL)`. `CLASSLIB/COMPILER.H` defines `BI_NO_BOOL` /
`BI_NO_MUTABLE` **unconditionally** — so in the 4.52 dialect `bool`, `true`,
`false`, `mutable` are NOT keywords (the library emulates them:
`enum TBool{false,true}; typedef int bool; #define mutable`). mdbcc had made
them keywords (B-6 synthetic era). Demoted all four to ordinary identifiers —
EXACTLY the `wchar_t` precedent already in the lexer (`typedef ... wchar_t;` in
STDDEF.H). `true`/`false`/`mutable` were inert (zero src usage). `bool` was
load-bearing (B-6 1-byte type) → predefined as a 1-byte `typedef` in
`Parser::new_for` so header-free TUs keep compiling `bool b;`, while a real
`typedef int bool;` overrides it (and the `enum{false,true}` supplies values).
Removed the now-dead `is_bool_kw` path.

**Result:** `classlib/defs.h` now compiles end-to-end (was THE foundational
blocker). The applicat.h closure advances past it into deeper headers
(osl/except.h transitive, shellapi/typeinfo, and the OLE/COM headers the plan
explicitly defers).

## DESIGN SPEC — base-pointer adjustment (the OWL critical-path blocker), ready to implement

The single feature gating the whole OWL header path (`TXBase : xmsg`, and every
exception/class with a non-polymorphic base that carries data). Fully designed
here so the implementation is mechanical. **Chosen model: vptr @ offset 0 +
base-pointer adjustment (Microsoft model)** — NOT vptr-at-end. Rationale: vptr@0
is uniform across the whole hierarchy (a class deriving from TXBase shares the
vptr@0 cleanly), keeps SetVptr + all virtual-dispatch sites UNCHANGED, and
matches how field offsets are already computed. vptr-at-end was rejected: it puts
the vptr mid-object for deeper derivations and would touch ~5 dispatch sites.

### What already works (no change needed)
- **Layout**: `layout(polymorphic=true)` already lays `[vptr@0][base fields @
  ptr_bytes][derived fields]`. Base fields land at `ptr_bytes` — correct.
- **Field access via the derived** (`d.base_field`): uses the shifted offset in
  the merged record — correct.
- **vptr install (SetVptr, codegen.rs:2627) + virtual dispatch (4201, 4295,
  7595, 7685, 7730)**: all `[this+0]` — vptr stays at 0, so UNCHANGED.

### The one new quantity
`Record.base_offset: usize` (add to `src/ast.rs:90`, default 0). It is the offset
of the base subobject within the derived:
`base_offset = ptr_bytes` iff `polymorphic && base_id.is_some() &&
!base.is_polymorphic() && !base.fields.is_empty()`, else `0`. (Equivalently:
`derived_first_base_field.offset - base_first_base_field.offset`; the vptr shift
is the only source, and it's a constant `ptr_bytes` because `ptr_bytes` is a
multiple of every field's alignment.) For poly-from-poly it is 0 (shared vptr).

### The adjustment sites (each: `ptr += cumulative base_offset`)
1. **`record_specifier` (parser.rs ~1101)**: replace the hard error with
   computing `base_offset` and storing it on the Record. (Field offsets already
   right via the existing merge+layout.)
2. **`method_target` (codegen.rs:3973)**: while walking derived→base to find the
   method, ACCUMULATE `base_offset` at each hop. When the method is found in a
   base, the returned `this` must be `recv + Σ base_offset`. Change the return to
   carry the cumulative adjust; the 3 callers (5030, 5334, 9531) emit
   `add rax, adjust` after generating `this_e` (gate on adjust != 0 → existing
   calls byte-identical).
3. **`convert` (codegen.rs:5796)**: an upcast `Derived* → Base*` (related record
   pointers) emits `add rax, Σ base_offset`. This is the implicit upcast at
   assignment / argument / return. (Downcast `Base*→Derived*` subtracts — rare;
   can stay a clean error initially.)
4. **ctor/dtor chaining** (`synthesize_base_chaining` +
   `inject_member_ctor_dtor_calls`, parser.rs): a base ctor/dtor (and a base-
   field member ctor/dtor) receives `this + base_offset`. REQUIRED for xmsg
   (which has ctors) — without it the base ctor writes `str` at the wrong offset.

### Test plan (TDD, all gated → existing suite byte-identical)
- New `cpp_member_parse`/`end_to_end` test: `struct Base{int x; int getx(){return
  x;}}; struct D:public Base{int y; virtual int t(){return x+y;}};` then through a
  `D*`, a `Base*`, exercise `dp->t()` (vptr@0 dispatch), `dp->getx()` (base method,
  method_target adjust), `bp->x` + `bp->getx()` (upcast + base@0). Expect a known
  sum.
- A second test WITH a base ctor (mirrors xmsg) to cover chaining (site 4).
- Then re-drive owldefs.h: `TXBase : xmsg` should lay out + compile.

### Risk / gating
Every site is gated on `base_offset != 0`, which is false for all existing
classes (C code, poly-from-poly, non-poly) → the 88 x64 SipHash baselines and the
vtable tests stay byte-identical. The only new code path is the
poly-from-nonpoly-base-with-data case, which today is a hard error (no passing
test depends on it). The work is ~10 edits; it is a focused, fresh-context task
because a wrong site is a silent miscompile in core method dispatch — exactly
what must not be rushed.

### Implementation note (found while scoping) — two refinements for the next pass
- **method_target this-adjust is caller-free**: rather than changing the return
  tuple + 3 callers, WRAP `this_e` inside `method_target` as
  `(Base*)((char*)this_e + Σbase_offset)` (an `Expr::Cast`+`Binary{Add}` over the
