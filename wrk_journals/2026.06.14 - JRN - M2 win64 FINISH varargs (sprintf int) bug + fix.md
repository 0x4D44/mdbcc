# JRN — M2: win64 FINISH dialog garbage integers — root cause (BC45 RTL stack-walking varargs)

Date: 2026-06-14
Milestone: M2 (FINISH dialog) / a win64 RTL ABI sibling-bug

## Symptom
The native-Win64 FINISH dialog (game-end) OPENS, RENDERS, and CLOSES correctly — the M2 dialog mechanism
(DWL_USER path) works; it's a plain `TDialog` with no custom paint, so the WM_PAINT discriminator lets
`DefDlgProc` paint it. But its integer text is GARBAGE vs the golden:
```
golden : "During your 0 hour shift you achieved: ... 0.00 mins (0 trains) ..."
win64  : "During your 1394768 hour shift ...        ... 0.00 mins (1394880 trains) ..."  (heap-address-like)
```
Floats (`%.2f`) print "0.00"; only the `%d` integers are garbage.

## Root cause (traced, not guessed)
1. A `wsprintf` (USER32) trace inside `TFinish::SetupWindow` read the FIELDS correctly:
   `ShiftLength=0, ArrNum=0, DepNum=0, WorkTime=823`, `TYPESAFE_DOWNCAST(Parent,TLayout)` delta=0. So it is
   NOT the downcast, struct offsets, or the values.
2. Garbage appears only through the C-RTL `sprintf`: `sprintf(t,"%d %d %d",11,22,33)` → `"1394192 0 1394880"`.
3. `tests/win64_varargs_int.rs` proves mdbcc's OWN `va_arg` intrinsic is CORRECT on Win64 (custom variadic
   sums; int-after-double; and the vprintf shape). So the defect is NOT mdbcc codegen — it is the RTL.
4. The RTL printf (`VPRINTER.C`, via `_printf.h`) includes **BC4.52's `<stdarg.h>`**, a 16/32-bit
   STACK-WALKING implementation: `va_start(ap,p)= &p+size`, `va_arg(ap,T)= *(T*)((ap+=size)-size)`. On Win64
   the first four args arrive in REGISTERS, not on the stack after the named params, so `&last+size` points
   at the wrong memory and every `va_arg` reads garbage. (The "0.00" float was a coincidental zero slot.)
   mdbcc's CLI uses `SearchPathResolver`, which finds BC45's `<stdarg.h>` on the `-I` path and compiles its
   macros verbatim.

## Fix — LANDED (two parts)
**Part 1: relax `gen_va_arg`'s `is_variadic` gate** (`src/codegen.rs`, committed `61ba06f`). `va_arg` merely
walks the `va_list` it is handed (`*(T*)ap; ap+=8`), independent of whether the enclosing function is
variadic. The canonical C-library shape is a variadic wrapper that `va_start`s and forwards the `va_list`
to a NON-variadic worker that `va_arg`s it (`vprintf`/`__vprinter`). The old gate wrongly rejected that
worker. `va_start`'s gate (which DOES need the enclosing `...`) is untouched, so
`cpp_variadic::j13_va_arg_outside_variadic_rejected` still passes. New
`tests/win64_varargs_int.rs::win64_va_arg_in_non_variadic_worker_vprintf_shape` validates the conformant
pattern on Win64. Tests: cpp_variadic 33/33, win64_varargs_int 2/2.

**Part 2: a BC45-COMPATIBLE `<stdarg.h>` overlay** (`wrk_owl_win64/include64/STDARG.H`, NEW). The first
attempt — a minimal `typedef char* va_list;` with NO other content — cascaded: it broke
`MATH_COMMON32_REALCVT.C` (home of `_nextreal`, the float va_list advancer), which relies on BC45's `void*`
`va_list` + the `__size` rounding macro and does manual va_list arithmetic. The fix: make the overlay
BC45-compatible — keep `typedef void *va_list`, `__size`, `_va_ptr` (everything BC45's header declares) and
omit ONLY the three `va_start`/`va_arg`/`va_end` MACROS, so those reach the parser as mdbcc's Win64-correct
intrinsics while REALCVT.C's `__size`-based manual advance still compiles AND stays consistent (it advances
by `__size(double)`=8, matching the intrinsic's fixed 8-byte slot). Win64-only (the overlay dir is prepended
only for `-m64`; i386 keeps BC45's correct-for-32-bit macros).

## Result — VALIDATED
- **FINISH dialog now reads `"During your 0 hour shift ... 0.00 mins (0 trains) ... 0.00 mins (0 trains)"`
  — pixel-matching the BC4.5 golden** (was garbage `1394768`/`1394880`).
- **KINGSX layout parity UNCHANGED**: 0 differing px outside the delay-LED region at tick 720 AND 3600
  (`game_parity.ps1` re-run post-fix).
- **Win64 slice O0–O5 GREEN** with the overlay + gate fix (REALCVT.C and the whole RTL compile; no cascade).
- Fixes ALL Win64 RTL integer `printf`/`sprintf`/`vprintf` (and scanf) varargs, not just FINISH — the
  "cookie-class sibling" the GOAL's Key Risks anticipated (BC45's 32-bit stack-based `<stdarg.h>` surfacing
  on Win64), now closed.

## Scope note
This bug affects ALL win64 RTL integer `printf`/`sprintf` output, but in RailC it is mostly confined to
dialog text like FINISH — the KINGSX layout (LED clock, delay boxes) renders via GDI/`wsprintf`-style paths
and is PIXEL-IDENTICAL to the golden (M3/M4). The main, ABOUT, CONFIG surfaces are unaffected.
