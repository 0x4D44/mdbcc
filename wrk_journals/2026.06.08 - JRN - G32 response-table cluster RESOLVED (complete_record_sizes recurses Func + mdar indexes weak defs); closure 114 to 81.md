## The diagnosis (what the symbols actually showed)

mdlink *demangles* for display, so the "bare `TWindow::Find`" unresolveds were
misleading. The real picture, from a COFF symbol-table scan across all 109
mdbcc-built objects:

- **Definitions** were mangled: `@TWindow@Find$qr10TEventInfoppqir4R972r4R974`.
- **References** were the bare internal funcs-key: `TWindow::Find`.

Two independent defects produced this, each fixed below.

### Defect A — `complete_record_sizes` didn't recurse into function types

OWL's `DECLARE_RESPONSE_TABLE` declares (in every TU's class body)
`Find(TEventInfo&, TEqualOperator = 0)` where
`TEqualOperator = bool(*)(TResponseTableEntry<GENERIC>&, TEventInfo&)`.
`DEFINE_RESPONSE_TABLE*` defines `Cls::Find` out-of-line in ONE TU.

In the DEFINING TU the in-class declaration (an extern proto) and the
out-of-line definition have IDENTICAL signatures and MUST dedup
(redeclaration), keeping the name tally at 1 ⇒ non-overloaded ⇒ bare symbol.
They did NOT dedup. Instrumented dump of the two param lists for `TWindow::Find`
in `WINDOW.CPP`:

```
PROTO func-ptr param: Ref(Record { id: 972, size: 0,  align: 1 })   <- decl, mid-class-body
DEF   func-ptr param: Ref(Record { id: 972, size: 16, align: 1 })   <- def, type now complete
```

Same id, same align — only **size** (0 vs 16). `complete_record_sizes` (which
exists precisely to erase this `size:0`-mid-class-body vs `size:16`-complete
skew before the `*p == psig` redeclaration compare) only handled TOP-LEVEL
`Record`/`Ptr`/`Ref`/`Array` — its `_ => t.clone()` arm left records buried
inside a `Type::Func` (the func-ptr param) UNcompleted. So the dedup failed, the
tally hit 2, the definition mangled `@TWindow@Find$q…`, and every referencing TU
(seeing one proto ⇒ tally 1) emitted the bare `TWindow::Find` ⇒ unresolved.

**Fix:** recurse `complete_record_sizes` into `Type::Func` and `Type::MemFn`
(ret + params). The decl and def now match ⇒ tally 1 ⇒ both sides emit the bare
`Cls::Find` ⇒ link. Resolved 29→1 mangling-mismatches; closure **114 → 94**.

### Defect B — `mdar` didn't index WEAK definitions

After Defect A, EVENTHAN.o emitted bare `TEventHandler::Find`/`Dispatch`/
`SearchEntries` (defined) and refs were bare — yet still unresolved. Cause:
mdbcc emits every vague-linkage definition (out-of-line member methods, vtables,
template instantiations) as a **WeakExternal** section-defined symbol so cross-TU
duplicates COMDAT-fold. `mdar` indexed only plain `External` symbols, so
EVENTHAN.o — whose defs are ALL weak — contributed ZERO symbols to the archive
index. mdlink pulls members SOLELY via the index, so it never pulled EVENTHAN.o
and the whole response-table base stayed unresolved. (`@TWindow@Find` had
resolved only because WINDOW.o was pulled for some OTHER indexed symbol.)

**Fix:** `mdar` now indexes `External` **and** `WeakExternal` symbols defined in
a real section (mdlink's pe_writer already treats a weak section-def as a
definition — COMDAT folding). Global first-member-wins dedup keeps the index
lean (a weak symbol defined in N members would otherwise index N times).
Closure **94 → 81**.
