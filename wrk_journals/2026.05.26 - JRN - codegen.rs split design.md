# JRN — codegen.rs split design (S1a)

Subagent design pass, 2026-05-26. Authored before extracting any code,
per the supervisor mandate to "produce a design before touching code".

## Context

- Source: `src/codegen.rs` = 8302 LoC.
- Companion: `src/eh.rs` (642 LoC, already extracted in earlier ticks)
  — sets the precedent. EH constants + scope types + the personality
  function emitter live in eh.rs; the throw/try/rethrow `gen_*` methods
  remain on `impl Gen` in codegen.rs because they reach deep into Gen
  state (slots, temps, scopes, RipRefs).
- Goal: split into `codegen/{expr,stmt,decl,cpp,abi}.rs` + leave
  `codegen.rs` as orchestrator (top-level driver `compile_module`,
  `Module`/`CompiledFn`/`Gen` types).
- Constraint: **zero behavioural change**. All 732 tests green at every
  commit boundary.

| Module | Estimated LoC |
|---|---|

| `codegen/abi.rs` | ~150 |
| `codegen/cpp.rs` | ~1500 |
| `codegen/stmt.rs` | ~1800 (includes EH gen_throw_int, gen_rethrow, gen_try, init lists, big gen_stmt_inner) |
| `codegen/expr.rs` | ~3700 (the giant gen_expr + gen_io_builtin + helpers) |

Total: ~11000 LoC. That's larger than 8302 because each new file adds
its own module-level comments + use statements + visibility shims —
that's expected for a refactor that pierces modules.

Wait, the math says the root will be ~3700 LoC because the Gen new/run
methods alone are ~750 LoC, plus all the primitives (~700 LoC), plus
top-level types (~500 LoC), plus compile_module (~400 LoC), plus free
fn helpers (~400 LoC), plus tests + remaining glue (~1000 LoC). That's
heavy but unavoidable: `Gen::new` and `Gen::run` are the per-function
orchestrators and can't move without dragging in dozens of other things.

## Cross-module dependency graph

```
            codegen.rs (root: Gen, primitives, compile_module)
             |     |     |     |     |
             |     |     |     |     v
             |     |     |     |   abi.rs (constants + classifier)
             |     |     |     |     ^
             |     |     |     |     |
             |     |     |     +-----+----+
             v     |     |                |
         decl.rs  |     v                |
                  |  stmt.rs            cpp.rs
                  |     |  ^             ^  ^
                  |     |  |             |  |
                  v     v  |             |  |
                expr.rs   +-+ <----------+  |
                  ^                         |
                  +----------- < -----------+ (cpp calls expr; expr calls cpp)
```

**Cycle risk**: `cpp.rs` and `expr.rs` cycle:
- `expr.rs::gen_expr` arm for `Expr::MethodCall` calls `cpp.rs::method_target` (resolving methods).
- `cpp.rs::emit_virtual_call` calls `expr.rs::gen_expr` (to evaluate `this` + args).
- `cpp.rs::gen_member_addr` calls `expr.rs::gen_addr`.
- `cpp.rs::has_op_method` is called from expr.rs; its implementation uses `expr_type` which is in expr.rs.

Since Rust modules cannot import each other cyclically through `mod`/`use`, this needs handling. The solution per the eh.rs precedent: all these methods are part of `impl<'s> Gen<'s>`. We can have MULTIPLE `impl Gen` blocks in different files — Rust allows it. Each method is defined ONCE; the call `self.method_target(...)` resolves through `Gen` regardless of which file it's in. No `use` cycle.

The only `use`-level dependency between cpp.rs and expr.rs is for FREE FUNCTIONS (`arg_compat`, `binop_spelling`, `libc_ret`, `type_code`, `overload_symbol`). These are fine: cpp.rs uses `type_code`, `overload_symbol`, `arg_compat` (all in cpp.rs itself); expr.rs uses `binop_spelling`, `libc_ret` (both in expr.rs).

`cpp.rs` and `expr.rs` are linked through `impl Gen` only; no direct cross-imports needed. **CYCLE AVOIDED.**

## Risk areas — functions used widely or with shared mutable state

1. **`gen_expr` (~450 LoC arm dispatch)** calls dozens of other methods. The expr.rs module will use `self.gen_addr`, `self.method_target`, `self.gen_throw_*`, `self.emit_virtual_call`, `self.recv_record_id`, `self.virtual_slot`, etc. — many cross-module. As long as those methods live in `impl Gen<'s>` declared in their respective files, this works.

2. **`expr_type` (~270 LoC)** is in expr.rs and called by EVERY other module. It walks the full Expr AST. Pure read-only on `&self`; no mutability issues.

3. **`gen_stmt_inner` (~420 LoC)** calls `gen_expr`, `gen_addr`, `gen_throw_int`, `gen_throw_class`, `gen_try`, `gen_init_list_into_slot`, lots of primitives. Stays in stmt.rs.

4. **`emit_call` / `marshal_args`** (in expr.rs) is the single chokepoint for direct calls; called from `gen_libc`, `gen_io_builtin`, the `Expr::Call` arm. ~180 LoC.

5. **`run` (~340 LoC)** drives the whole per-function emit. Stays in root since it sequences prologue → body (gen_stmt) → epilogue → cleanup pad emit + EH scope register. It calls `gen_stmt`, `ctor_cleanup_*`, `match_member_ctor_call`, `maybe_advance_member_counter` — the latter all in cpp.rs, accessed through `impl Gen`.

## Extraction order (least-coupled → most-coupled)

1. **`codegen/abi.rs`** — pure constants + one classifier function. No Gen impl methods. Trivial seam. Risk: ~zero.

2. **`codegen/cpp.rs`** — mangling helpers (free fns) + a chunk of `impl Gen` methods. Free fns are independent; methods stay in `impl Gen` (multi-file split).

3. **`codegen/decl.rs`** — `global_image` + maybe one or two `impl Gen` decl-time methods. Small seam.

4. **`codegen/stmt.rs`** — `gen_stmt_inner` + `gen_throw_int` + `gen_rethrow` + `gen_try` + init list helpers. Bigger chunk; calls into cpp.rs through impl Gen.

5. **`codegen/expr.rs`** — `gen_expr` + `gen_io_builtin` + binop machinery + call marshalling + `expr_type`. The largest and most coupled. By the time we get here, everything else is settled — only the root + abi remain for `use` imports.

**Important**: at each extraction, `cargo build --release && cargo clippy --release --all-targets -- -D warnings && cargo test --release` MUST be clean (732 passed, 0 failed, 1 ignored). If anything fails, REVERT and stop.

## Open questions / risks

- **Risk**: `impl Gen` blocks spanning multiple files. Rust allows this
  but it makes "where is this method?" harder for casual readers. The
  eh.rs precedent demonstrates Arthur is comfortable with the split
  pattern; we match it. We document it in each new file's header.

- **Risk**: a method we move turns out to depend on a `pub(super)` /
  `pub(crate)` visibility we haven't applied. Rust will catch this at
  compile time; we add the visibility in the same commit.

- **Risk**: `RecSrc` enum (line 281) — used by `gen_throw_class`
  (cpp.rs) only. We move it to cpp.rs alongside its caller. Keeps it
  out of the root namespace.

- **Risk**: `FmtSpec` + `parse_fmt` (lines 42-138) — used by printf
  machinery only. Could move to expr.rs alongside the printf emitter.
  We do this in the expr.rs extraction.

End of design.
