# 2026.06.17 - JRN - toolchain generality G2 OWL samples

## Context

Continuing the `wrk_docs/2026.06.17 - GOAL - toolchain generality and scale.md`
campaign. The first product probes were the stock BC4.52 OWL `STATICX.CPP` and
`BUTTONX.CPP` examples built as Win64 GUI apps through `mdbcc.toml`, using the
Win64 BC45 dependency libraries under `target/bc45-libs/win64`.

## Findings

- Initial link failed with `no 'WinMain' function defined` even though `mdowl.lib`
  contained `WINMAIN.o`.
- Archive index inspection showed `WinMain -> WINMAIN.o` and `OwlMain -> OWLMAIN.o`.
  The linker only scanned archives for unresolved symbols present in input
  objects; the PE writer's GUI entry stub references `WinMain` later, so the
  archive member was never pulled.
- After fixing archive root seeding, both examples linked, but `owl_static.exe`
  crashed before creating a window with `0xc0000005`.
- Map/disassembly localized the crash to `string::string(const char*)`, called
  with `cp == 1`.
- The bad caller was `TApplication::SetWinMainParams`. Its declaration is static,
  but out-of-line static member definitions were emitted as instance methods with
  an implicit `this`, shifting `(hInstance, hPrevInstance, cmdLine, cmdShow)` by
  one slot. `cmdShow == 1` became the string pointer.

## Changes

- Linker archive scanning now seeds unresolved roots with the eventual entry
  symbol (`main`, `WinMain`, or explicit entry) and treats weak section/absolute
  definitions as definitions.
- Parser now records static member functions separately from instance methods.
- Static member definitions and declarations no longer get an implicit `this`.
- Codegen carries static-method status through overload resolution and method-call
  lowering, so object syntax for a static member does not pass the receiver.
- Added regressions for archive-only GUI `WinMain` and out-of-line static member
  ABI.
- Bumped package version from `0.7.2` to `0.7.3`.
