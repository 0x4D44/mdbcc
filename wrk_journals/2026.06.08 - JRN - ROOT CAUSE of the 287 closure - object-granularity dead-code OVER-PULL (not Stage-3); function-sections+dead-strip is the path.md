# 2026.06.08 — ROOT CAUSE of the 287 closure: object-granularity dead-code OVER-PULL (not Stage-3). Function-sections + linker dead-strip is the path.

Diagnostic arc (no code commit; this redirects the whole remaining plan, so it is
the highest-value output). Mapped all 35 non-compiling OWL files' first-errors,
then traced WHY the reproducible 287-symbol closure exists — against the GOLDEN
as oracle. The answer overturns the "compile 35 OWL files / implement Stage-3"
framing: **most of the 287 is dead code that mdbcc OVER-PULLS and tlink32 prunes.**

## The evidence chain

1. **Golden is tiny.** `wrk_oracle/railc_golden/railc.map`: `_TEXT = 0x2ADBB ≈
   175 KB` of code total. OWL's full code is megabytes. tlink32 pulled only
   railc's LIVE transitive subset from OWLWF.LIB.
2. **railc uses NO doc/view.** `grep` of all railc *.CPP/*.H for
   TDocManager/TDocument/TWindowView/TDocTemplate/DEFINE_DOC/GetDocManager →
   ZERO matches. railc is a plain TApplication + TFrameWindow + TDialog +
   TLayoutWindow app.
3. **Golden contains NO doc/view.** Class-name strings in golden railc.exe:
   `TDocument` = 0, `TView` = 0, `TWindowView` = 0, `TDocManager` = 1 (a lone
   RTTI string, not the framework). vs LIVE: `TApplication` 61, `TFrameWindow`
   43, `TLayout` 42, `TDialog` 30.
4. **My link OVER-PULLS it.** The reproducible 287 contains TDocManager (31
   refs), TDocument (22), TDocTemplate (4), TView (4), TWindowView (6) — ~67
   symbols of a framework the golden doesn't link at all.
5. **The puller is a LIVE object.** `APPLICAT.o` (TApplication, which railc
   references DIRECTLY → always pulled) contains a reference to TDocManager.
   TApplication has doc-manager support methods (SetDocManager/GetDocManager/…)
   that railc never calls — but mdbcc compiles APPLICAT.CPP into ONE coarse
   object holding ALL of TApplication's methods. Pulling the object for
   TApplication's ctor drags in those dead methods → they reference TDocManager
   → DOCMANAG must be defined → it references TDocument/TView/TDocTemplate →
   cascade. The whole dead doc/view framework enters the closure.

## Root cause

**Coarse object granularity → whole-object pull → dead-code over-pull.** mdbcc
emits one `.o` per `.CPP` with every function concatenated into one `.text`. A
COFF/lib link pulls WHOLE objects to satisfy any one symbol, so a live ctor
drags in its object's dead siblings and everything they reference. tlink32 +
OWLWF.LIB avoids this because Borland's static lib is fine-grained (per-function
objects / COMDATs), so tlink32 pulls only the functions actually reached.

## The correct fix (supersedes Stage-3 + the per-file OWL grind for DEAD files)

**Function-level sections + linker dead-strip (GC)** — the standard
`-ffunction-sections` + `--gc-sections` mechanism:
- Codegen: emit each function/method into its own selectable section
  (`.text$<sym>` / COMDAT), not one concatenated `.text`.
- mdlink: build a reachability graph from roots (entry stub + the explicitly-
  listed railc objects' symbols), mark transitively-referenced sections, DROP
  unreachable sections (and their relocations/undefined refs) before closure.

TApplication's dead doc-manager methods get stripped → their TDocManager
references vanish → the entire doc/view (and similarly the dead MDI/OLE/iostream
streaming) framework never enters the closure. This is also REQUIRED for golden
byte-parity later: the golden's code IS the dead-stripped set.
