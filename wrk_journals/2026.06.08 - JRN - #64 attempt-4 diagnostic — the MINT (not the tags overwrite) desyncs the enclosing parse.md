# 2026.06.08 — #64 attempt-4 diagnostic: the MINT itself (not the tags overwrite) desyncs the enclosing class parse

Investigative turn on the #64 nested-class-collision wall (the ~14-file
DECLARE_STREAMER `Streamer` bucket + `Lock`). Attempt-4 was reverted
(working-tree only), but it produced a sharp narrowing of the root cause that
overturns the attempt-2 hypothesis.

## What was tried (attempt 4)

Scoped-key-ONLY registration: mint a fresh record for a colliding nested
class with a scoped tag `Outer::Inner`, register `tags["Outer::Inner"]=id`,
and NEVER touch the flat `tags[Inner]` binding (the attempt-2 hypothesis was
that overwriting it caused the regression). Added a `class_nest` stack
(pushed/popped around the body, since `cur_class` is None during nested
member parsing) to build the scoped name.

## The decisive finding

**It STILL regressed APPLICAT/WINDOW/GAUGE at window.h:409** ("expected a
member name" — a normal method `bool IsWindowEnabled() const;` inside
TWindow's body). Since the flat `tags` binding was never touched, the
attempt-2 hypothesis (overwrite → desync) is WRONG.

**The regression is the MINT itself** — creating a fresh record for the
colliding nested `Streamer`/`Lock` desyncs the ENCLOSING class's member
parse loop, even though the nested body's token consumption should be
identical regardless of which record id it parses into. A fresh EMPTY record
vs the (reuse-path) MERGED record changes something downstream in TWindow's
member parse.

Reuse baseline (current/shipped): APPLICAT compiles THROUGH to codegen and
DEFERS the streamer inline funcs (non-fatal). So #64 is only FATAL where a
streamer method is REACHABLE (BUTTON-style files); it does not block files
that merely include the streamable headers.

## Suspects for the next (debugger-style) arc

The synthesis passes that run at the END of the nested record's
`record_specifier`, on the fresh-vs-merged record, before returning to the
enclosing member loop — any of which may mutate shared parser state
(`cxx_funcs`, `classes`) differently for a fresh empty polymorphic record:
- the polymorphic-default-ctor synthesis (DECLARE_STREAMER's `Streamer` is
  polymorphic — virtual Write/Read — so a SetVptr ctor IS synthesized);
- `synthesize_base_chaining`, `synthesize_ddvt_windowproc`,
  `inject_member_ctor_dtor_calls`.
Concrete next step: instrument `record_specifier` to log `records.len()`
before/after the mint and identify the EXACT TWindow member after the nested
`Streamer` that fails; OR bisect by minting fresh but SKIPPING each synthesis
pass for nested records to isolate which one desyncs.

## Standing conclusion

Four attempts confirm #64 has NO reactive quick fix; it is a dedicated-arc
feature requiring a debugger-level trace of the mint↔enclosing-parse
interaction, then the full scoped-resolution (record + qualified `Outer::
Inner` lookup at the member-def + type sites). The shipped tree keeps the
reuse behavior (byte-identical, regression-free); the 14 reachable-streamer
files remain blocked on this. Recorded so the next arc starts from the
narrowed root cause, not from scratch.
