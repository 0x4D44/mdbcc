## mdar → mdlink proven; two real findings landed/characterized

**Finding 1 (FIXED, committed 855668d): library-member strong-duplicate
folding.** railc + the 3 archives first died on `duplicate symbol
@TRect@Inflate$qii` — Borland ships that strong out-of-line member in BOTH
owl.lib (POINT.CPP) and bids.lib (GEOMETRY.CPP); both members get pulled
(for OTHER symbols). Real linkers fold library duplicates (first wins,
library order); only explicit objects conflict. mdlink now does this
(`LinkOpts::archive_origin`, empty-default byte-identical). 2 new tests
(fold links → 42; explicit conflict still errors). Gate green.

**Finding 2 (CHARACTERIZED): the dominant remaining unresolved is the
OWL→Win32 IMPORT SURFACE.** Post-fold, railc + 3 partial archives links to
~498 unresolved, of which **182 are C++-mangled Win32 GDI/USER APIs**:
`@AngleArc$qp5HDC__…`, `@FillRect$…`, `@CallWindowProcA$…`, `@DestroyWindow$…`
— GDI32/USER32 exports. These are declared `extern "C" WINAPI` (=`__stdcall`)
in WINGDI.H/WINUSER.H; bcc32 emits them as decorated C-linkage imports
resolved via import32.lib. **mdbcc C++-MANGLES them** — so they miss the
linker's exact-name `is_win32_import` table and fall to "unresolved." This
is ONE codegen-linkage recognition issue (honor `extern "C"`/dllimport on
the Win32 API decls → emit `RipRef::Import(name)` instead of a mangled
CallSite), not 182 separate gaps. The +163-imports work fixed the subset
railc calls DIRECTLY; the OWL library bodies call the rest.

The other ~316 unresolved: iostream/streambuf (42 — Stage-3-gated RTL

out-of-line members of the 58 OWL/CLASSLIB files that don't yet compile
