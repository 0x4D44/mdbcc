## M1 objective (from the GOAL doc)

Make OWL's message dispatch **pointer-safe on Win64** so messages whose `lParam` carries a pointer
(`WM_CREATE`/`WM_NCCREATE` `CREATESTRUCTA*`, `WM_GETMINMAXINFO` `MINMAXINFO*`, `WM_NOTIFY`, command routing)
are dispatched **without truncation**, and the main frame window is fully interactive (menus fire, response
tables route).

Known truncation sites (from the wall-1 HLD's "second-stage risk"):
- `SIGNATUR.H:458` `LRESULT_WPARAM_LPARAM_Sig == I32_U_I32_Sig`
- `DISPATCH.H`/`DISPATCH.CPP` `int32` LPARAM dispatchers
- `COMPAT.H` Win16 `uint16`/`uint32` params
- `TWindow::ReceiveMessage`/`HandleMessage` widths

**Acceptance.** A bounded interaction smoke drives the main window (post a menu command / a pointer-bearing
message) and asserts no truncation-class crash (`0xC0000005`) and the expected response; O0–O3 gates stay
green; `railc.res` byte-identical.

**Key constraint (HLD D2).** `WPARAM`/`LPARAM`/`LRESULT` widening must be ABI-coherent across the whole
`-m64` slice or the link breaks (non-virtual cross-TU-inlined `ReceiveMessage`/`HandleMessage` mangling).
The wall-1 overlay deliberately did NOT widen these (only 2 TUs). M1 must widen them slice-wide.

### 2026-06-14 — mdbcc -m64 param codegen (the truncation mechanism)
- (Explore of `src/codegen.rs`) On -m64 the prologue spills R9 (lParam) to its home slot as a **full 8-byte
  store** (`ARG_SPILL[3]` = `mov [rbp+d], r9`, REX.W). BUT when the body reads a `long`-typed `lParam`,
  `load_rax` emits `movsxd rax,[mem]` — reads only the **low 4 bytes** and sign-extends. So **a pointer in a
  32-bit-typed `lParam` is truncated the moment any handler reads it as a variable** (or forwards it to the
  next call). Widening the type makes the read an 8-byte `mov rax,[mem]` → no truncation. Fix confirmed.
- The window appears anyway because OWL recovers `this` via the wall-1 `CreationWindow`/`GWLP_USERDATA`
  path, not by dereferencing `lParam` during creation.

### 2026-06-14 — fix scope (decided)
Coherent slice-wide widening of the dispatch pointer-width types, applied to ALL -m64 TUs via a prepended
overlay INCLUDE dir + a patched `DISPATCH.CPP` (recompiled `DISPATCH.o`), mirroring the wall-1 overlay model:
1. `WINDEF.H`: `WPARAM`→`UINT_PTR`(64), `LPARAM`/`LRESULT`→`LONG_PTR`(64).
2. `owl/DISPATCH.H`: `TAnyDispatcher` + every `*_Dispatch` decl: `int32 lParam`→`LPARAM`, return `int32`→`LRESULT`.
3. `owl/DISPATCH.CPP` (patched copy → `DISPATCH.o`): matching definitions.
4. `owl/SIGNATUR.H`: the lParam/return signature templates: `int32`→`LPARAM`/`LRESULT`.
5. `owl/COMPAT.H`: `TMessage.LParam`→`LPARAM`, `.Result`→`LRESULT` (layout coherence across all TUs).
Mangling coherence (the GOAL's hard constraint): widening the typedefs in WINDEF.H changes the mangled names
of the non-virtual cross-TU `ReceiveMessage`/`HandleMessage` and the dispatch fns *uniformly* across every
-m64 TU (one wiring point: prepend the overlay dir for all -m64 compiles) → the link stays coherent.
**Guard rails** (loud-fail, since the resolver silently stubs a missing overlay header to 32-bit): a sentinel
`#define` in each overlay header + an `#error`/`static_assert(sizeof(LPARAM)==8)` in the patched DISPATCH.CPP
(compiled directly, cannot be stubbed) + a marker symbol for an O2-style "patched object used" check.
**Acceptance probe:** the `wall2_probe.ps1 all` sequence must flip from CRASHED→SURVIVED, folded into the O3 gate.

### 2026-06-14 — MECHANISM resolved (the key enablers)
Three empirical facts (via `bcc -E` + probe compiles) collapse the mechanism risk the wall-1 HLD flagged:
1. **mdbcc typedef redefinition is LAST-WINS** (not an error): `typedef long X; typedef __int64 X;` →
   `sizeof(X)==8`. So I don't need to patch every co-included typedef site — only make the 64-bit one active.
2. **A real OWL TU sees exactly ONE typedef** of each of WPARAM/LPARAM/LRESULT (`typedef UINT WPARAM;` /
   `typedef LONG LPARAM;` / `typedef LONG LRESULT;`) — the include guards suppress the other definition
   sites (WTYPES.H/COMPOBJ.H etc.). So there is a single source of truth to patch.
3. **That site is `WINDEF.H:161-163`** — proven: a prepended overlay `include64/WINDEF.H` with the typedefs
   widened to `UINT_PTR`/`LONG_PTR` flips `sizeof(LPARAM)` to 8 in `#include <owl/window.h>` (clean compile).
**Mechanism (final):** prepend `wrk_owl_win64/include64/` to the `-I` path for ALL `-m64` TUs (one wiring
point in the harness) with the patched `WINDEF.H`. This is the wall-1 HLD's rejected "mechanism C" (full-copy
replacement overlay) — but it's now the RIGHT tool because wall 2 genuinely must *replace* a definition, and
the silent-stub risk is covered by the sentinel `#define MDBCC_WIN64_OVERLAY_WINDEF` + a loud guard.
**Codegen note:** no compiler change — `bcc.exe` already emits a full 8-byte `mov rax,[mem]` for `__int64`
reads. (Also keeps me clear of a concurrent engineer's in-flight `src/` edits.)
**Increment plan:** Step 1 = typedefs only (fixes the unhandled-message→DefWindowProc resize crash, validates
link coherence — the riskiest bit). Step 2 = widen the `int32` dispatch layer for handled pointer-messages.
