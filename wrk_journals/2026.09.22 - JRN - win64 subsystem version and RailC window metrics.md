# 2026-09-22 — Win64 subsystem version and RailC window metrics

## Report

Arthur saw three faults in the mdbcc-built Win64 RailC that the original
Borland build never had: the Arrivals/Departures boards overflow their frames
and draw over the 3D border, the About box puts its two bitmaps in the wrong
places (the DMU is clipped off the right edge), and there is no sound.

## Cause of the first two

mdlink stamped every PE32+ image with OS 6.0 / subsystem 6.0. The PE32 path
already copied tlink32 (OS 1.0 / subsystem 3.10). Windows keys legacy USER
metrics on the subsystem version:

- At 6.0 a window gets the padded Vista frame. RailC's fixed 300x192
  `WS_DLGFRAME` boards lose 10 px of client in each axis (Departures client
  284x153 instead of 294x163), so the eighth row at y=144..161 spills past the
  border line.
- At 6.0 a dialog gets modern font base units. The About box is 524 px wide
  instead of 611, and `TAbout::EvPaint` blits the DMU at a fixed x=450..605.

Proved by patching only those header fields in a copy of the built exe and
measuring client rects and screenshots at 6.0, 4.0 and 3.10. 3.10 matches the
original layout.

## Fix

`src/link/pe_writer.rs::write_pe_from_objects` now stamps `OS_VERSION` (1.0)
and `SUBSYSTEM_VERSION` (3.10) for both targets. The legacy `write_pe` writer
is only reached from unit tests and is unchanged. Guarded by
`tests/pe_layout.rs::win64_images_carry_bc45_subsystem_version`, which went
red on the old writer.

Byte impact: RailC differs from the previous build in exactly three header
bytes (MajorOS 6→1, MajorSubsystem 6→3, MinorSubsystem 0→10). All 88
`o1_byte_identity` fixture hashes moved for the same reason and were
re-blessed in this commit.

Verified end to end: a live Lime Street shift shows all eight rows of both
boards inside their frames, and the About box shows both bitmaps in full.

## Sound: not reproduced as a toolchain fault

An instrumented scratch RailC logged the tick handler during a real shift:
`SoundEnable=1`, game in progress, `FindResource` finds the RCDATA `BEEP`, the
locked pointer starts with `RIFF`, and `sndPlaySoundA(SND_ASYNC|SND_MEMORY)`
returns TRUE on every tick. The `.rsrc` WAV is byte-identical to
`RESOURCE/BEEP.WAV`, and `WINMM.dll!sndPlaySoundA` is imported. A standalone
mdbcc probe playing the same resource with `SND_SYNC` also returns TRUE.

A Core Audio session watcher (IAudioSessionManager2, polled every 100 ms)
saw the RailC process own a session on the default render endpoint, going
Active 36 times in a one-minute shift: one short burst per beep. So the
Win64 exe does render the WAV here. If a player hears nothing, check the
per-exe volume in the Windows Volume Mixer first; Windows remembers it by
exe path.

## Side findings

- A Win64 GUI exe linked with only `mdcw32.lib` (no OWL) crashes 0xC0000005
  before `WinMain` returns, even for `return 42`. It runs with no libs. Filed
  in BUGS.md.
- `Sleep` is unresolved at link: the known LNK-01 import allowlist.
