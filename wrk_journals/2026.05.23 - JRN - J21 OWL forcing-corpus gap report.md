# JRN — J-21 OWL forcing-corpus gap report (tick 53)

## Context

J-21 set out to build a synthetic ~500-LoC OWL idiom corpus (Tier 2 of
the `2026.05.22` queue) to act as a Phase-I forcing function ahead of
real Borland-OWL acquisition. Goal: combine ten cross-cutting C++
features in one TU (class hierarchy + virtuals, response-table
dispatch, custom exception hierarchy, struct-by-value, operator
overloading + trailing-const, array-new with ctor, block-scope
shadowing, member overloading, `operator[]` returning `int&`, and
adjacent string-literal concat) under the existing OWL runtime
(`PROG_D5_HELLO_OWL` / `OWL_RUNTIME_H` in `src/pp.rs`), and assert it
compiles, links, and runs cleanly through the WM_CLOSE teardown chain.

The kitchen-sink TU (`notes/j21_probe.cpp`, 146 LoC) tripped multiple
cross-feature combinations the per-feature test suites did NOT cover.
Bisection (22 `j21_minN.cpp` reductions) localised four distinct gap
clusters; the simplified fixture that DOES compile + run cleanly is
`notes/j21_probe_v2.cpp` (8 of 10 features; sidesteps operator+
returning a class).

## Gaps found

### G-1: inline class member function returning own class by value fails

**Symptom**: codegen error "function `Cls::method`: returning an empty
struct by value is not supported", even when the class has data
members. Out-of-line definitions of the SAME method body work
correctly.

**Minimal reproducer** (`notes/j21_min15.cpp`):
```cpp
class Point { public:
    int x;
    int y;
    Point bump(int v) { Point r; r.x = x + v; r.y = y + v; return r; }
};
int main(void) {
    Point a; a.x = 3; a.y = 4;
    int sx = a.bump(10).x;
    return sx;
}
```

**Observed**: `bcc.exe ... j21_min15.cpp` exits non-zero with
`error: function 'Point::bump': returning an empty struct by value is
not supported`.

**Expected**: compile + run, exit code 13 (3 + 10).

**Out-of-line counter-example** that DOES work (`notes/j21_min17.cpp`):
the IDENTICAL function body moved to `Point Point::bump(int v) {...}`
outside the class compiles and runs cleanly (exit=13).

**Likely root cause**: when an inline member-function body is parsed,
the enclosing class record is only partially populated — its
`fields`/`size` is not yet finalised. The struct-return-by-value path
in `gen_function` sees an empty/zero-sized record and emits the
empty-struct rejection. The out-of-line path runs after the class
declaration completes, so the size is known. Likely interaction with
the class-record finalisation in `src/parser.rs` member-function path
(~line 605 inline / ~line 1361 out-of-line).

**Effort guess**: medium. A defensive "finalise record before
type-checking inline member bodies" pass, or deferring the
empty-struct check to after class finalisation, should be sufficient.
Watch for O1 byte-identity churn (no existing e2e fixture exercises
this combination, so the new path should add bytes only to new tests).

### G-2: `c = a + b;` rejected when `operator+` returns class by value

**Symptom**: parser/codegen rejects assignment from an operator+
return value with `error: expression is not an lvalue`, even though
the LHS `c` is a plain lvalue and the RHS is an rvalue — exactly the
classical "rvalue materialised into LHS" pattern C++ requires.

**Minimal reproducer** (`notes/j21_min20.cpp`):
```cpp
class Point { public:
    int x;
    int y;
    Point operator+(Point& o);
};
Point Point::operator+(Point& o) { Point r; r.x = x + o.x; r.y = y + o.y; return r; }
int main(void) {
    Point a; a.x = 3; a.y = 4;
    Point b; b.x = 5; b.y = 6;
    Point c;
    c = a + b;
    return c.x;
}
```

**Observed**: compile fails with `expression is not an lvalue`.

**Expected**: compile + run, exit 8 (3 + 5).

**Counter-example** (proving the gap is operator-specific, not a
general by-value-method bug): an identical pattern using a plain
out-of-line method works — `c = a.makeFrom(b);` returns Point by
value and assigns into `c` cleanly. Only the operator-overload return
path triggers the rvalue-as-lvalue confusion.

**Likely root cause**: J-1/J-6 work landed operator+ as a method
overload via `resolve_overload`. When `a + b` is lowered to a
synthetic `MethodCall(a, "operator+", [b])` in `gen_expr`, the
`Stmt::Assign` lvalue check on the LHS `c` is fine, but the RHS
expression-type query for an op-overload returning by value falls
through to a path that flags the call expression itself as
"not an lvalue". Probably in `gen_addr` or `expr_type` — the J-6
helper `op_method_return_type` knows about op= return-by-value but
op+ takes a different code path that re-uses the assign-target lvalue
check.

**Effort guess**: small. A targeted fix in the assign arm to allow
rvalue RHS for operator overloads, mirroring the working out-of-line
method path.

### G-3: member access / further use of operator+ return value fails

**Symptom**: `(a + b).x`, `(a + b).x + (a + b).y`, and passing
`a + b` as a function argument all reject with `expression is not an
lvalue` at compile time — OR segfault at runtime if the call site
slips past the parser into codegen.

**Minimal reproducers**:

  Compile-time error (`notes/j21_min19.cpp`):
```cpp
class Point { public:
    int x;
    int y;
    Point operator+(Point& o);
};
Point Point::operator+(Point& o) { Point r; r.x = x + o.x; r.y = y + o.y; return r; }
int main(void) {
    Point a; a.x = 3; a.y = 4;
    Point b; b.x = 5; b.y = 6;
    int sx = (a + b).x;
    return sx;
}
```

  Runtime segfault (`notes/j21_min24.cpp`):
```cpp
class Point { public:
    int x;
    int y;
    Point operator+(Point& o);
};
Point Point::operator+(Point& o) { Point r; r.x = x + o.x; r.y = y + o.y; return r; }
int take(Point p) { return p.x + p.y; }
int main(void) {
    Point a; a.x = 3; a.y = 4;
    Point b; b.x = 5; b.y = 6;
    return take(a + b);
}
```

**Observed**: min19 fails compilation with the lvalue error; min24
compiles but **segfaults** at runtime (STATUS exit 0xC0000005 →
unix-style exit 139).

**Expected**: min19 exit 8 (3 + 5), min24 exit 18 (3+4+5+6).

**Likely root cause**: same as G-2 — the op+ return expression is
not materialised into an addressable temp. For member access on a
struct rvalue, mdbcc's lvalue check fires (matches the H10
review's note that struct-return-by-value paths only support direct
discard or direct return). For passing the rvalue as a function
argument, the argument-marshalling path reads from an unallocated
buffer offset (segfault). Both should be fixed by materialising the
op+ return into a temp slot — same temp-spill pattern as J-7's
anonymous-catch fix in `gen_try`.

**Effort guess**: medium. Materialisation of op-overload struct
rvalues touches `gen_expr` (`Expr::Binop` with op-method dispatch)
and any call/marshalling path that reads a struct value. Cross-cuts
with G-2 — likely the same root fix lands both.

### G-5: explicit operator-name member-call syntax rejected by parser

**Symptom**: `obj.operator+(rhs)` (explicit operator-name as if it were
an ordinary method) fails the parser with `expected a field name`. The
infix form `obj + rhs` works for the int-returning operator+ case (and
is the J-21 fixture's chosen idiom), but the explicit-call form is a
real Borland-OWL idiom (used when overload resolution is ambiguous or
the call site is template-like).

**Minimal reproducer**:
```cpp
class P { public: int v; int operator+(P& o); };
int P::operator+(P& o) { return v + o.v; }
int main(void) {
    P a; a.v = 3;
    P b; b.v = 4;
    return a.operator+(b);
}
```

**Observed**: `notes/j21_probe.cpp:12:16: error: expected a field name`.

**Expected**: exit 7 (3 + 4).

**Likely root cause**: the `.` post-fix-expression arm in `src/parser.rs`
expects `TokenKind::Ident(...)` after the dot. `operator` is recognised
as a `Keyword`, not an `Ident`, so the arm rejects. The fix is to
re-enter the `operator_name()` recogniser when `Keyword::Operator`
follows `.` (or `->`).

**Effort guess**: small. One arm addition in the member-access parser
path, ~10 lines.

**Severity**: MINOR. The infix form is the overwhelming common case; the
J-21 fixture uses it. Explicit form is a nice-to-have for diagnostic
quality when the user really wants to spell out which overload they
mean.

**Workaround in the J-21 fixture**: use the infix form throughout.

### G-4: inline member returning own class via `this` + reference param

**Symptom**: same "expression is not an lvalue" as G-3 fires when an
inline member function uses both `this->field` AND a reference
parameter to construct the return value.

**Minimal reproducer** (`notes/j21_min13.cpp`):
```cpp
class Point { public:
    int x;
    int y;
    Point makeFrom(Point& o) { Point r; r.x = o.x; r.y = o.y; return r; }
};
int main(void) {
    Point a; a.x = 3; a.y = 4;
    Point b;
    b = a.makeFrom(a);
    return b.x;
}
```

**Observed**: compile fails with `expression is not an lvalue`.

**Expected**: compile + run, exit 3.

**Counter-example** (`notes/j21_min18.cpp`): out-of-line definition
of the SAME method body works (exit=3). Note this overlaps with G-1
(inline-vs-outline) — but with a DIFFERENT error message ("not an
lvalue" vs "empty struct"). The error variation suggests the inline
parsing path takes two branches: one for direct `int sx = a.f().x;`
(triggers empty-struct in G-1) and one for `b = a.f();` (triggers
lvalue error here).

**Likely root cause**: probably the same upstream as G-1, surfacing
as a different diagnostic depending on whether the call-site context
needs member access or struct assignment. Same family — inline
member-function body type-checked before class record finalised.

**Effort guess**: medium. Likely closed for free by the G-1 fix.

## What J-21 closed (the wins)

Eight of ten target features combine cleanly under the OWL runtime
(see `notes/j21_probe_v2.cpp` for the working fixture):

1. **Class hierarchy with virtual destructor** — `TXBase`/`TXMyAppError`
   with `virtual ~TXBase()` compiles and dispatches correctly.
2. **Custom exception hierarchy + throw/catch by-reference** — `throw
   TXMyAppError(); catch (TXBase& base)` works; `base.code` reads the
   right field (J-7 + virtual-dtor synergy).
3. **Array-new with ctor + `delete[]`** — `Counter* g = new Counter[3]`
   invokes 3 ctors; `delete[] g` invokes 3 dtors; J-5 overflow guards
   stay dormant (small constant count).
4. **`operator[]` returning `int&`** — `list[0] = 42; printf("%d", list[0])`
   works; the int-reference return path is materialised correctly
   (this is the J-1/J-6 happy path — different from the op+ gap).
5. **Member overloading** — `print(int)` vs `print(char*)` resolve
   via H7 / J-1's mangled names; no overload ambiguity.
6. **Adjacent string-literal concat** — `"Hello, " "OWL!\n"` lexed
   and concatenated (H9 hardening from tick 47 holds).
7. **Block-scope shadowing** — `int idx; { int idx; }` shadowing
   inside member functions resolves correctly (H8 hardening).
8. **Trailing-`const` on member functions** — `int operator+(...) const`
   compiles, mangles to `K` suffix, dispatches (J-1 happy path).

## Shipped in-tree (tick 53)

The J-21 fixture **DID land** as `PROG_J21_OWL_INTEGRATION` in
`tests/gui.rs`, with two tests:

- `j21_owl_integration_structural` (always-on, headless-safe): compiles
  the fixture; asserts subsystem 2, KERNEL32 + USER32 + GDI32
  descriptors, .pdata + .xdata sections present (the EvPaint try/catch
  forces SEH emission), DataDirectory[EXCEPTION] non-zero, .text
  substantial.
- `j21_owl_integration_liveness` (desktop-gated, watchdog-bounded):
  spawns the PE, captures stdout via Stdio::piped, finds the J21 window
  by exact caption, injects one WM_LBUTTONDOWN via SendMessageA, posts
  WM_CLOSE, asserts exit 0 + 12 distinct J21_* sentinel lines in stdout.

Both tests passed first-run. **The fixture includes ALL TEN features**
(working around G-2/G-3 by having operator+ return `int`, which still
exercises trailing-const + H7 binary overload + Point-by-value through
the `point_sum(p)` free function). Response-table dispatch IS in scope
and works correctly — TMyWin's five Ev* virtuals all dispatch through
the if-chain.

The "out of scope" framing in the original draft of this report was
pre-resolution; the resolved fixture exercises:
- Response-table dispatch (PAINT/LBUTTONDOWN/COMMAND/KEYDOWN/DESTROY).
- The 10 cross-feature combinations.
- A throw-from-EvPaint (the try/catch INSIDE EvPaint that catches a
  TXMyAppError as TXBase&) — proved to work without any special-case
  path; the SEH personality function handles cross-feature paths.

Only the **`Point operator+ returning Point`** scenario is parked behind
G-2/G-3.

   `gen_addr` that delegates to `gen_expr` when the binary is an

   `Expr::Call | Expr::MethodCall` arm at `src/codegen.rs:2851`). Then

   empty-struct check to a post-finalisation pass. Probably 1 day.

   member-access parser arm. Small parser tweak.
4. **Re-target the J-21 corpus**: once G-1..G-3 fixes land, switch the
   fixture's `Point::operator+` from `int` to `Point` return to lock
   the cross-feature surface end-to-end.
