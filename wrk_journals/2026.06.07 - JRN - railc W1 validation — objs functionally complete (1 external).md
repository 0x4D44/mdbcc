# 2026.06.07 — railc W1 **validation**: the 21 mdbcc objs are functionally complete

Follow-on to the W1 compile milestone. Validates (not just "compiles clean") that
the 21 mdbcc-built railc objs are CORRECT at the link/symbol level — the GOAL's
"per-TU .obj/symbol differential, early."

## Method

`target/release/mdlink.exe -m32 --subsystem gui -o out.exe wrk_oracle/railc_mdbcc/*.o`
(the 21 mdbcc objs, no libs). mdlink reports ALL unresolved externals in one
batch (mod.rs:82).

## Findings (strong validation)

- **Exactly ONE unresolved external** across all 21 objs:
  `@TStringRef@$bctr$qcui` = `TStringRef::TStringRef(unsigned)` (Borland-mangled).
  Defined in the RTL source `C:/tmp/bc45/SOURCE/RTL/SOURCE/STRING/` (a non-inline
  cw32 function), referenced by 10 TUs.
- **Borland-ABI name mangling**: the external surface is Borland-mangled
  (`@Class@method$qparams`, `$bctr` ctor) — mdbcc's mangling matches Borland's,
  exactly what's needed to link against cw32/owl libs and for self-consistency.
- **Objs are near-self-contained**: RAILC.o is **683 KB** vs the bcc32 golden
  RAILC.obj's **38 KB** — mdbcc emits ALL reachable OWL/RTL inlines+templates
  into each obj (195 distinct `@`-mangled OWL/RTL symbols referenced in RAILC.o
  alone; e.g. `@TWindow@Create` referenced in 15 objs and RESOLVED as an emitted
  inline). Vague-linkage dups are deduped at link (no duplicate-symbol errors).
- **App logic intact (no b12 hollow-exe)**: WinMain is defined in RAILC.o; the
  "deferred 22 inlines" note contains ZERO railc-own functions — all 22 are OWL
  i386-unsupported inlines (global operator new/delete, delete[], placement
  array-new). None are referenced on a reachable path (else they'd be
  unresolved), so they are dead for railc. railc's `new` uses the HeapAlloc path
  (`__imp_HeapAlloc`), not `operator new`, so the deferred operator-new is moot.
- **Imports fully covered**: 28 distinct `__imp_*` across the objs (USER32/GDI32/
  KERNEL32: ShowWindow, BeginPaint/EndPaint, GetDC/ReleaseDC, LineTo/MoveToEx/
  TextOutA, LoadString/Menu/Icon/Cursor/Accelerators, Heap*, etc.) — all in
  mdlink's WIN32_IMPORTS table (else unresolved). CTL3D (Ctl3dRegister/...) and
  other OS calls resolve too (only TStringRef is unresolved).

## Implication

OWL 2.5 is inline-heavy: the OWL/RTL/BIDS code railc actually reaches is almost
entirely header-inline (mdbcc-emitted) — only ONE non-inline RTL function is
referenced. So the path to a RUNNING railc.exe is far shorter than "self-host all
of OWL": provide TStringRef's closure (a small W2 slice) + wire mdlink's `.res`
linking + a GUI WinMain entry. (The emitted OWL-inline codegen's runtime
correctness is the remaining unknown, validated only by RUNNING the exe — the
bisection oracle / W6.)
