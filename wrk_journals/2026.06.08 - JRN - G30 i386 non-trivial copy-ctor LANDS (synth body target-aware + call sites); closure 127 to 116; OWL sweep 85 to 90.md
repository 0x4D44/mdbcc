## The fix (G30, 633fc83)

mdbcc's copy-ctor machinery was **Win64-only at every site**. G30 makes it
target-aware:

1. **`build_synth_copy_ctor` (cpp.rs)** — the implicit copy-ctor BODY. Was
   entirely Win64 (this/src in rcx/rdx, REX.W throughout, RIP-relative vtable).
   Now i386-aware: prologue reads this/src from the stack ([ebp+8]/[ebp+12], no
   spill/shadow); field byte-copy uses ecx/edx (no REX.W); inner member/base
   copy-ctor calls are cdecl (push src+off, push this+off, call, add esp,8); the
   polymorphic vptr install uses an absolute `lea eax,[abs]` + Addr32
   `RipRef::Vtable` (the same reloc `Stmt::SetVptr` uses on i386). Win64 keeps
   the historical bytes verbatim (else branches) → byte-identical.
2. **Decl-init copy-ctor call (codegen.rs ~4424)** — `if Win32` routes through
   `emit_call` (cdecl); Win64 keeps its register hand-roll.
3. **new-expr (`construct_in_place`)** — `new T(t)` copy construction dispatches
   to the copy ctor (`copy_ctor_symbol` Some → real ctor via emit_call; None →
   memcpy for trivially-copyable). Fixes the implicit copy ctor being absent from
   the user-ctor overload set. Byte-identical on Win64.

## Why the earlier partials failed (lesson banked)

Fixing a CALL site without the synth BODY turned an i386 implicit copy from a
clean "no encoder row" defer into a CALL into a Win64-only body → runtime
segfault (silent miscompile). RUN-verification caught it twice; both reverted.
The working fix was ALL sites together, RUN-verified across the matrix.
