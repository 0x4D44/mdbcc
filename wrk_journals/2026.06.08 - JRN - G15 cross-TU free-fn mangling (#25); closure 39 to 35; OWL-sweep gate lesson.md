# 2026.06.08 — G15/G15b: consistent cross-TU free-function mangling (#25); closure 39→35; the OWL-sweep-gate lesson

Continuation of the closure drive. Two committed compiler features close the
long-standing #25 cross-TU mangling inconsistency, plus a hard-won process
lesson. Session arc so far: **railc link closure 343 → 35**, OWL **66 → 82**.

## What #25 was

A non-overloaded FREE function with a cxx-typed parameter (record / ref, or a
pointer/array to one) was emitted under its RAW name on the DEFINITION side
(`SetCreationWindow`), while every cross-TU REFERENCE (extern-proto `force_cpp`,
S1b.7) and bcc32's EXTDEF (o13_12) used the Borland-mangled form
(`@SetCreationWindow$qp7TWindow`). In an all-mdbcc link the two never met —
OWL.CPP's instance-thunk / window helpers, defined raw, were unreferenceable
from WINDOW.CPP's mangled call sites. The dominant remaining symptom that ran
this to ground: railc's 5 OWL-global thunks (CreateInstanceThunk /
FreeInstanceThunk / SetCreationWindow / GetWindowPtr).

## Diagnosis path (recorded — it was long)

1. railc closure showed the thunks unresolved despite OWL.o defining them.
2. `scw.o + OWL.o` (2 objects) RESOLVED them; adding WINDOW.o broke it — first
   read as a "large-object linker bug" (WINDOW.o is 284 KB ≈ 2× others).
3. COFF instrumentation: WINDOW.o references `@SetCreationWindow$qp7TWindow`
   (mangled) while OWL.o + a minimal caller both used `SetCreationWindow` (raw).
   NOT a linker/COFF-size bug — a compiler MANGLING inconsistency.
4. Minimal repro: `void f(Rec*)` defined in TU-A (raw) + `extern void f(Rec*)`
   called in TU-B (mangled `@f$qp3Rec`) → unresolved. Confirmed the rule:
   definition mangles iff `name_counts > 1` (overloaded); reference mangles iff
   any cxx-typed param (`force_cpp`). The comment at codegen.rs:~1268 already
   filed this as #25.

## The fix

- **G15 (009e6e7)**: route a free function (not `::`, not main/WinMain/OwlMain)
  with any cxx-typed param through the SAME single-candidate `overloads` path as
  an overloaded one. The emit pass already mangles `overloads` names
  (records-aware → stable class tag), and same-TU calls resolve via the
  1-element set ⇒ definition, same-TU call, cross-TU reference all agree on
  `@name$q<types>`. Primitive-only free functions stay on the raw `funcs` path ⇒
  88 byte-identity baselines unchanged.
- **G15b (c8bf791)**: G15 regressed the function-as-VALUE paths — a designator
  used by bare name (`ForEach(shutDown)`, `&f`, a callback) only consulted
  `sigs.funcs`, so an in-`overloads` function failed ("no member named" via the
  member fallback). Added `free_fn_value_symbol(name)` (raw for funcs / mangled
  for a single-candidate overload) used in `gen_addr`'s designator arm, plus the
  matching single-overload `Type::Func` branch in `expr_type`'s Var arm.

## THE LESSON (process)

G15 passed the FULL unit suite (1672/0) AND clippy — yet REGRESSED 8 OWL files
(WINDOW/APPLICAT/APPDICT/COMBOBOX/DOCTPL/MDICLIEN/OLEMETA/VBXCTL: OWL 82→74).
The unit suite has no test that passes a cxx-param free function by bare name,
so it was blind to the designator break. **The real gate for a codegen-symbol
change is the OWL compile sweep, not the unit suite.** Going forward: after any
change to mangling / symbol routing / name resolution, run

    for f in C:/tmp/bc45/SOURCE/OWL/*.CPP; do bcc.exe -c -m32 -D__WIN32__ \
        -I C:/tmp/bc45/INCLUDE "$f"; done   # expect OK >= 82

before committing. G15b restored OWL to 82 (identical fail list to pre-G15) and
kept the closure win.
