## B-01 — Win64 pointer comparison is 32-bit

Status: fixed by `1e042a4`.

BUGS.md claim: Win64 pointer comparisons (`p < q`, `p == q`) route through the
32-bit integer-compare path because `gen_binary` widens only `Type::Int{bytes:8}`
for `op64`, not `Type::Ptr`. If two pointer values differ only in the high
32 bits, mdbcc can compare the low halves and return the wrong result.

Working hypothesis: the compare-specific backend already supports 64-bit pointer
operands, but the main binary operation width selector does not route pointer
comparisons through it.

Investigation:

- Added failing regression `tests/win64_pointer_compare.rs`.
- Repro source compares fabricated Win64 pointer values:
  `0x100000001` vs `0x200000001` and `0x100000000` vs `0x200000000`.
  These have identical low 32-bit halves and different high 32-bit halves.
- Pre-fix command:
  `mdtimeout 120 cargo test --test win64_pointer_compare -- --nocapture`
  failed. The generated program returned `10`, which is the `a == b` branch.

Diagnosis:

- `gen_binary` computes `op64` only from `Type::Int{bytes:8}` operands.
- Pointer compare operands reach the generic integer operation path after
  pointer arithmetic is ruled out.
- The non-`op64` path emits `mov ecx,eax` and `cmp eax,ecx`, so the high
  32 bits of each Win64 pointer are discarded before equality/relational
  compare.
- `extend_rax_to_64` and `cmp_set64` already handle pointer-shaped operands,
  so the failure is the width-selection gate, not a missing backend primitive.

Design:

- Minimal root-cause fix: on Win64, route comparison operators involving
  pointer-shaped operands (`Type::Ptr`, and the same machine-word `Type::MemFn`)
  through the existing 64-bit binary-op path.
- Treat pointer-shaped comparisons as unsigned for relational setcc selection.
  This leaves equality unchanged and matches address ordering for pointer values.
- i386 remains byte-path unchanged because `op64` is still target-gated on Win64.

Skeptic vote (2/3 required, 3 max):

- Skeptic A — pass: observed `10` is exactly explained by low-dword equality;
  no other observed fact requires a different root cause.
- Skeptic B — pass: widening all Win64 pointer-shaped comparisons is smaller
  than changing `gen_intop` or adding a pointer-specific compare backend because
  the existing 64-bit path already has the right primitives.
- Skeptic C — concern noted but not blocking: relational comparison on arbitrary
  fabricated pointers is target-probe territory rather than portable C. The
  equality branch alone reproduces the bug without relying on ordering.

Implementation:

- Updated `src/codegen.rs::gen_binary` so `is_compare && Type::Ptr/Type::MemFn`
  participates in both `op64` and unsigned compare selection.
- Added `tests/win64_pointer_compare.rs::pointer_comparisons_observe_high_32_bits`.

## B-02 — `LL`-suffixed `0x80000000..=0xFFFFFFFF` literal types as `int`

Status: fixed by `1cfd816`.

BUGS.md claim: a `long long` / `unsigned long long` suffixed literal in the
32-bit unsigned range but above `i32::MAX` reaches `expr_type` as a bare
`Expr::Int`, and the magnitude rule classifies that range as 32-bit. A 64-bit
operation involving that literal can then sign-extend or wrap the low 32 bits,
e.g. `0xFFFFFFFFULL + 1` yields 0 rather than `0x100000000`.

Investigation so far:

- Lexer preserves suffix flags: `TokenKind::Int { unsigned, longlong, ... }`.
- Parser wraps small `LL` literals (`<= i32::MAX`) in `Expr::Cast` to force
  64-bit type, but skips the wrapper above `i32::MAX`.
- `expr_type(Expr::Int(4294967295))` intentionally returns 32-bit `int` because
  the magnitude rule accepts `i32::MIN..=u32::MAX`.

Reproduction:

- Added `tests/i64_ops.rs::ull_suffix_u32_max_literal_is_64bit`.
  Pre-fix, `mdtimeout 180 cargo test --test i64_ops -- --nocapture` failed with
  left `0`, right `7` for `(0xFFFFFFFFULL + 1ULL) == 0x100000000ULL`.
- Added `tests/i64_ops.rs::ll_suffix_high_u32_literal_is_positive_i64`.
  The first add-based version was a bad oracle because both sides mis-typed the
  same way and passed falsely; replaced it with
  `(0x80000000LL >> 31) == 1LL`, which failed pre-fix with left `0`, right `7`.

Diagnosis:

- The suffix survives lexing, so the lexer is not at fault.
- `Expr::Int` cannot carry a suffix-derived type, so the parser's `Expr::Cast`
  wrapper is the existing type-carrier for `LL` literals.
- The wrapper gate stopped at `i32::MAX`; values in
  `i32::MAX+1..=u32::MAX` therefore reached codegen as a 32-bit signed `int`.
- In mixed 64-bit expressions, `extend_rax_to_64` then sign-extended the low
  dword (`0xFFFFFFFF` -> `-1`, `0x80000000` -> negative), matching both observed
  failures.

Design:

- Keep the global `Expr::Int` magnitude rule unchanged; B-02 is specifically
  about explicit `LL` / `ULL` suffixes.
- Extend the parser wrapper for `longlong && value <= u32::MAX`.
- For values above `i32::MAX`, first tag the inner expression as unsigned
  32-bit, then cast to the requested signed/unsigned 64-bit type. That preserves
  the bit pattern and lets the outer widening zero-extend instead of sign-extend.
- Values above `u32::MAX` still bypass the wrapper and rely on the existing
  64-bit magnitude rule.

Skeptic vote (2/3 required, 3 max):

- Skeptic A — pass: the two failing probes are both explained by the same missing
  suffix type wrapper and later sign-extension; no lexer or emitter hypothesis is
  needed.
- Skeptic B — pass: changing `expr_type`'s global `u32::MAX` rule would affect
  unsuffixed and `U`-only literals, while the parser wrapper fixes the explicit
  suffix bug only.
- Skeptic C — pass with caveat: nested Casts are not pretty, but they reuse the
  repo's existing literal type-carrier and avoid adding a new AST variant for a
  narrow bug.

Implementation:

- Updated `src/parser.rs` so `longlong` literals up to `u32::MAX` are wrapped in
  a 64-bit `Expr::Cast`; the high-u32 range gets an inner unsigned-32 cast.
- Added two B-02 regression cases to `tests/i64_ops.rs`.

Focused validation:

## B-03 — `const_eval` shift folding is signedness-blind

Status: fixed in working tree; commit pending.

BUGS.md claim: runtime/codegen unsigned 64-bit shifts are fixed, but
compile-time constant folding still uses `i64::wrapping_shr`, so an unsigned
constant with bit 63 set folds as an arithmetic shift. Constant contexts such as
array dimensions can therefore reject valid code or compute the wrong value.

Reproduction:

- Added `tests/i64_ops.rs::const_eval_unsigned_u64_shift_is_logical`.
- Pre-fix `mdtimeout 180 cargo test --test i64_ops -- --nocapture` failed at
  compile time: the array bound
  `(0x8000000000000000ULL >> 63) == 1ULL ? 42 : -1` folded to `-1`, producing
  `ParseError { message: "array size must be non-negative" }`.

Diagnosis:

- `const_eval` has only an `i64` value channel and `Expr::Cast` ignored its
  target type, so `BinOp::Shr` always used signed arithmetic `wrapping_shr`.
- The failing literal arrives as a negative `i64` bit pattern for an unsigned
  64-bit value with bit 63 set. Runtime codegen can infer unsigned 64-bit from
  magnitude, but constant folding discarded that signedness before shifting.
- The symptom, trigger, and prior success all fit: runtime `i64_ops` shifts were
  green because `gen_binary` has typed operands; only constant contexts calling
  `const_eval` were wrong.

Design:

- Keep `const_eval`'s public `Option<i64>` surface, but add a local helper that
  infers unsigned integer width from expression shape (`unsigned` casts,
  unsigned-high 64-bit literals, and simple unsigned-producing integer ops).
- For right shift only, use that width to mask the left operand and perform a
  logical shift at 32 or 64 bits. Signed operands keep the existing arithmetic
  shift.
- Do not attempt a full C usual-arithmetic-conversion engine in this patch; the
  bug is specifically unsigned shift folding.

Skeptic vote (2/3 required, 3 max):

- Skeptic A — pass: the failing negative array bound is directly explained by
  arithmetic shift of the unsigned high-bit literal.
- Skeptic B — pass: preserving `const_eval(e) -> Option<i64>` keeps the fix
  narrow; threading a full typed value through every operator would be larger
  than B-03 needs.
- Skeptic C — initially found a real edge: a blanket u64 logical shift would
  mis-fold `((unsigned)-1) >> 31`. Fix adjusted to carry unsigned byte width and
  added a regression for that case.
- Lead follow-up: a first-unsigned-operand shortcut would also mis-fold mixed
  unsigned widths such as `(unsigned)1 + 0x8000000000000000ULL`; helper now keeps
  the widest inferred unsigned operand width.

Implementation:

- Updated `src/parser.rs::const_eval` so `BinOp::Shr` uses logical shift when
  `const_eval_unsigned_bytes(lhs)` returns a width.
- Added `const_eval_unsigned_bytes` to infer unsigned 32/64-bit width locally.
- Added `max_unsigned_bytes` so unsigned-producing binary and conditional
  expressions carry the widest inferred unsigned width.
- Added `tests/i64_ops.rs::const_eval_unsigned_u64_shift_is_logical`.
- Added review-edge regression
  `tests/i64_ops.rs::const_eval_unsigned_32bit_shift_uses_32bit_width`.
- Added mixed-width regression
  `tests/i64_ops.rs::const_eval_unsigned_shift_uses_widest_operand`.

## B-04 — Win64 ref-arg marshalling missed derived-to-base address upcast

Status: fixed in working tree; final validation and commit pending.

BUGS.md claim: the i386 G57/G57b derived-lvalue to base-reference binding fix
was not audited on the Win64 marshal/EH path. Same bug class may pass the
unadjusted most-derived address where a base subobject address is required.

Reproduction:

- Added `tests/win64_ref_base_adjust.rs` with a polymorphic derived class `D`
  over a data-bearing non-polymorphic base `M`. On Win64 the vptr shifts `M` to
  offset 8, so passing `&D` as `M&` makes the callee read vtable bytes as
  `M::v`.
- Pre-fix `mdtimeout 180 cargo test --test win64_ref_base_adjust -- --nocapture`
  failed all three initial cases:
  direct call and `*this` call returned `1073754114`, virtual call returned
  `1073754122`; all expected 42.

Diagnosis:

- `marshal_args_cdecl` already had the G57 conversion after
  `gen_ref_arg_for_param`: compute the source record type and route
  `Derived* -> Base*` through `convert`, which knows static base offsets and
  shared-vbase loads.
- Win64 `marshal_args` only called `gen_ref_arg_for_param` and spilled that
  unadjusted address. The first patch fixed direct calls and the `*this` case,
  proving the immediate root cause.
- The virtual-call regression still failed after that first patch because
  `emit_virtual_call` has its own Win64 register/outgoing-stack loop rather than
  delegating to `marshal_args`. `emit_indirect_call_with_lead` and the Win64
  member-function-pointer call branch had the same by-reference pattern.
- Decl-init and return-reference sites were already routed through `convert`
  in `gen_stmt`, so they were not part of the failing surface.

Design:

- Add a small local helper, `upcast_ref_arg_for_param`, that assumes RAX already
  holds the bound reference address and applies `convert(Derived*, Base*)` only
  when both source expression and parameter are record/reference-shaped.
- Call it immediately after `gen_ref_arg_for_param` in the Win64 by-reference
  argument loops: direct calls (`marshal_args`), virtual calls, function-pointer
  calls, and member-function-pointer calls.
- Leave non-record references, same-class references, UDC temp construction, and
  i386 behavior unchanged. Same-class record refs are a no-op because
  `convert` gates pointer upcasts with `aid != bid`.

## B-05 - i386 intrinsic floating-point varargs

Status: fixed by `8ab1a26`.

Investigation:

- Added two intrinsic `<stdarg.h>` i386 regressions in `tests/i386_run.rs`:
  `i386_intrinsic_va_arg_int_walks_cdecl_stack` and
  `i386_intrinsic_va_arg_double_walks_cdecl_stack`.
- Pre-fix focused repro:
  `mdtimeout 240 cargo test --test i386_run i386_intrinsic_va_arg -- --nocapture`
  failed both tests at compile time with
  `no encoder row for op Mov with operands [Reg(Gpr64), Reg(Gpr64)]`.
- Existing Borland macro stdarg tests still passed, proving the i386 caller
  stack image and in-place named-parameter addressing were already correct.

Diagnosis:

- The parser's intrinsic `va_start`/`va_arg` lowering was Win64-shaped:
  `va_start` used the Win64 home-space formula `rbp + 16 + 8*(idx+1)`, and
  both intrinsics stored the `va_list` pointer through hard-coded 64-bit
  `reg64`/`mem64` moves.
- `va_arg` also advanced every slot by 8 using raw `add rax, 8` and used
  REX-prefixed narrow integer loads, so the i386 path could not even encode the
  intrinsic before reaching the runtime double-walk behavior.
- The reason the bug escaped earlier is that BC45's own `stdarg.h` macro shape
  uses address arithmetic from `&last_named_param`; those tests never exercised
  mdbcc's parser/codegen `VaStart` and `VaArg` nodes.

Design:

- Keep Win64's fixed 8-byte home-space model and existing short `add rax, 8`
  byte sequence.
- For Win32 `va_start`, derive the first unnamed argument from the incoming
  cdecl parameter slot: `&last + cdecl_named_param_bytes(last_type)`.
- For `va_arg`, advance by the target ABI's variadic slot width: Win64 fixed
  8; Win32 8 for floating varargs (`float` promoted to `double`) and otherwise
  the 4-byte-rounded target size.
- Store `va_list` updates through a shared pointer-width helper using existing
  `wreg`/`wmem`, so Win32 emits `eax/ecx` and Win64 emits `rax/rcx`.
- Leave i386 `va_arg(ap, long long)` unsupported with a clear B-06-linked
  error instead of silently pretending the edx:eax pair work exists.

Skeptic vote (2/3 required, 3 max):

- Skeptic A - pass: the compile-time Gpr64 encoder failure is exactly predicted
  by hard-coded Win64 stores in the intrinsic lowering; the macro stdarg tests
  passing rules out caller stack layout as the primary cause.
- Skeptic B - pass: the fix is minimal because it changes only intrinsic
  va-list lowering and reuses existing target-width helpers; cdecl marshalling
  and named-parameter layout are left untouched.
- Skeptic C - markup applied: preserve the existing Win64 `add rax, 8` encoding
  rather than routing it through `emit_add_rax`, which would change the byte
  sequence for unaffected Win64 variadic programs.

Implementation:

- Added `store_rax_word_to_lvalue`, `cdecl_named_param_bytes`,
  `va_arg_advance_bytes`, and `named_param_slot` helpers in `src/codegen.rs`.
- Made `gen_va_start` choose Win64 home-space offset or Win32 cdecl incoming
  offset by target.
- Made `gen_va_arg` use target-aware advancement, pointer-width `va_list`
  stores, target-width scalar loads, and a clear i386 8-byte-integer rejection.
- Added two i386 intrinsic stdarg tests for integer walking and
  `va_arg(ap, double)` followed by an int.

## B-06 - i386 64-bit integer pair arithmetic

Status: fixed by `cde6eef`.

Investigation:

- Added mdbcc-only i386 regressions in `tests/i386_run.rs` because the local
  Borland 4.52 oracle path predates reliable `long long` support.
- Pre-fix focused repro:
  `mdtimeout 240 cargo test --test i386_run i386_u64_ -- --nocapture`
  failed all four original B-06 cases. `x >> 40`, carry into the high dword,
  multiplication high product, and equality with different high dwords all
  returned `7` instead of `42`.
- Extra guards added during implementation cover signed unary negation plus
  arithmetic right shift, truthiness with only EDX set, and increment carry
  from `0xFFFFFFFF` into the high dword.

Diagnosis:

  `gen_intop` path on Win64. Win32 `long long` operands fell through the

  truth testing of `?:` bypassed the truthiness helper.
- The facts fit: i386 already has ABI islands that return 8-byte values in
  EDX:EAX, but expression code never made that the general `long long` result
  contract. Win64 worked because it has a single 64-bit RAX datapath.

- Define the i386 `long long` expression result as EDX:EAX. Keep Win32 pointers
  as EAX only; do not use target-agnostic `Type::size()` where pointer width
  matters.
- Add small pair helpers for spilling/reloading EDX:EAX, literal materialising,
  and sign/zero extension from narrower integer operands.
- Route Win32 binary operations with an 8-byte integer operand to a new i386
  pair op path. Implement add/sub/mul, bitwise ops, shifts, comparisons, unary
  neg/not, increment/decrement carry, assignment/local stores, loads, casts,

- Deliberately reject i386 `long long` division/modulo with a clear error for

  tracked separately if needed.

## B-07 — call argument evaluation order

Investigation:

- Added focused direct-call regressions for Win64 and i386. Both encode a

  evaluated before `a()` while the resulting values are still delivered to

- Pre-fix `mdtimeout 240 cargo test --test calling call_args_evaluate_right_to_left -- --nocapture`
  failed: mdbcc returned `7` instead of `42`.

Diagnosis:

  `slots[i]`/`is_fp[i]` while iterating `i` from `args.len()-1` down to `0`.
- Apply the same pattern to the cloned substantive call paths so B-07 is not
  only fixed for direct calls.

## B-08 - thrown exception object lifetime

Investigation:

- Added focused Win64 exception regressions for thrown-object copy construction,
  synthesized memberwise copy construction, catch fallthrough destruction,
  catch-return destruction, and bare rethrow.
- Pre-fix `mdtimeout 300 cargo test --test cpp_exceptions t21 -- --nocapture`
  confirmed the split:
  - `t21b_throw_class_runs_copy_ctor` FAILS with `41`, expected `42`.
  - `t21c_throw_class_runs_synth_memberwise_copy_ctor` FAILS with `41`,
    expected `42`.
  - `t21d_caught_object_destructs_on_handler_fallthrough` FAILS with `0`,
    expected `1`.
  - `t21e_caught_object_destructs_on_handler_return` FAILS with `1`,
    expected `11`.
  - `t21f_rethrow_does_not_destroy_caught_object_before_outer_catch` PASSES.

Diagnosis:

- Win64 `gen_throw_class` evaluates the thrown object's address, then copies raw
  bytes into `.mdbcc_eh_buffer` with `emit_struct_copy`. That skips user copy
  constructors and synthesized memberwise copy constructors, so owned members
  such as strings retain source/temporary storage instead of constructing a
  stable exception object.
- i386 `gen_throw_class_i386` already uses the intended semantics: direct copy
  constructor if present, else byte-copy the object and run the base copy
  constructor fallback when needed. The Win64 path diverged when class EH was
  added.
- `catch (T& name)` stores the delivered exception-object pointer in the local
  catch slot. The normal destructor tracker assumes a local object lives at the
  slot address, not behind the pointer stored in the slot, so catch fallthrough
  and catch return never destroy the caught exception object.
- The rethrow guard passing pre-fix fits the diagnosis: no destructor was being
  emitted before rethrow, so there is no premature destruction yet.

Design:

- Factor the i386 thrown-object copy semantics into a target-aware helper and use
  it from both i386 and Win64 throw-class lowering.
- For Win64, materialize `&.mdbcc_eh_buffer` in a temp and call the shared copy
  helper before building the `RaiseException` argument array.
- Extend destructor cleanup entries with a `via_ptr` bit. Normal locals keep the
  existing address-of-slot behavior; named Win64 `catch (T& name)` entries load
  `this` from the pointer stored in the catch slot.
- Register a `via_ptr` catch destructor only for named Win64 by-reference class
  catches whose destructor exists. Leave by-pointer, catch-all, i386 catch-side
  destruction, throw operand temporary destruction, and partial-construction
  chains out of scope.

Skeptic review:

- Skeptic A accepts the throw-side diagnosis: both explicit and synthesized copy
  constructor regressions fail by exactly one increment, which raw copy explains

- Skeptic B accepts the catch-side diagnosis: fallthrough and return have
  independent destructor paths, both miss the catch object, and the rethrow case
  confirms the fix must not run cleanup before raising.
- Skeptic C challenges scope: i386 and temporary destruction are related
  lifetime gaps, but not required to explain the observed Win64 OWL corruption

## B-09 - secondary-base dynamic_cast

Investigation:

- Converted the pinned known-gap fixture
  `tests/oracle_s4_classlib.rs::s4_mi_plus_rtti_secondary_base_dynamic_cast`
  from "mdbcc still returns 99" to the bcc32 oracle result `20`.
- Pre-fix `mdtimeout 300 cargo test --test oracle_s4_classlib s4_mi_plus_rtti_secondary_base_dynamic_cast -- --nocapture`
  fails with `left: 99`, `right: 20`.
- The current `dynamic_cast` lowering starts from `[source]->vptr`, walks the
  single descriptor word at `vptr - ptr_width`, and returns the original source
  pointer on success. That fits primary-chain casts because the base subobject is
  at offset 0 in the covered cases.
- Secondary vtables are emitted as synthetic records with `base_id: None`, so a
  `B2*` into a `D : B1, B2` object starts from the synthetic secondary vtable
  and immediately walks to null. Even if it linked to `D`, the success path would
  still need to subtract the secondary-base offset before returning `D*`/`B1*`.

Diagnosis:

- The root cause is missing complete-object RTTI metadata for secondary vtables.
  A secondary vptr describes a subobject (`this == complete + extra_base_offset`)
  but the RTTI prefix only represents primary inheritance (`current vtable ->
  primary base vtable`) and has no way to recover the complete object pointer.
- This explains all observed facts: ordinary primary-chain `dynamic_cast` works,
  secondary-base virtual dispatch works via thunks, but `dynamic_cast` through
  the same secondary vptr returns null because the RTTI walk has no owner link.

Design:

- Extend RTTI-enabled vtable prefixes from one pointer-width word to two while
  preserving the old base-link word at `vptr - ptr_width`:
  - `vptr - 2*ptr_width`: signed adjustment from this vptr's subobject pointer
    back to the complete object (`0` for primary vtables, `-extra_base_offset`
    for secondary vtables).
  - `vptr - ptr_width`: existing base/owner vtable link.
- Emit secondary vtables with `base_id = owner primary record` when the owner
  has a primary vtable, and `this_adjust = -extra_base_offset`.
- Update `dynamic_cast` to load the initial adjustment once from the source
  vtable and add it to the saved source pointer on success. Primary-chain casts
  add zero; secondary-source casts recover the complete/primary pointer.
- Add a static fast path for `dynamic_cast<T*>(p)` when the static source type is
  already `T*` or a statically-known derived-to-base conversion, preserving null
  semantics through the existing `convert` path.

Skeptic review:

- Skeptic A accepts the owner-link requirement: without it the loop cannot leave
  the synthetic secondary vtable, so the observed null result is inevitable.
- Skeptic B accepts the adjustment requirement: linking the secondary vtable to
  `D` alone would make the type test pass but return the `B2` subobject address
  as `D*`/`B1*`, breaking the fixture's virtual calls.
- Skeptic C checks compatibility: keeping the base link at `vptr - ptr_width`
  leaves the existing i386 EH reader and primary-chain RTTI loop intact. Vote:
  2/3 accepted for the prefix-extension fix.

- Changed RTTI-enabled COFF vtable prefixes to carry adjustment plus base/owner
  link; the base link remains immediately before the vtable symbol.
- Taught the direct PE writer to emit and backpatch the same two-word prefix so

- Updated i386 and Win64 `dynamic_cast` lowering to load the initial adjustment

## B-10 - i386 nested try

Investigation:

- `BUGS.md` listed nested `try` as unsupported around `src/codegen.rs:6437`.
- Win64 nested try is no longer reproducible as a bug: existing
  `tests/cpp_exceptions.rs` nested runtime tests pass, including three-level
  and five-level nested cases.
- Added i386 regressions for nested try fallthrough, an inner catch that throws
  to an outer catch, and an inner non-matching catch that must continue search
  at the outer try in the same frame.
- Pre-fix `mdtimeout 300 cargo test --test i386_run i386_nested_try_fallthrough_restores_outer_level -- --nocapture`
  failed at compile time with the explicit nested-try rejection:
  `a try nested inside another try is not yet supported on i386`.

Diagnosis:

- The root cause was the i386 multi-try model storing only one active trylevel
  in the SEH registration record. That is enough for sequential try blocks, but
  cannot represent a nested search stack.
- The old body lowering disarmed the level to `-1` after every try body, so an
  inner try that completed normally would leave the enclosing try inactive.
- The old catch delivery also disarmed to `-1`, so a throw from an inner catch
  body could not be caught by an enclosing try in the same function.
- Finally, the multi handler searched only the current level. If an inner level
  had no matching row, it returned `ContinueSearch` to caller frames instead of
  trying the parent level in the same frame.

Design:

- Extend i386 multi-try scope-table rows from
  `{ level, kind, type_va, pad_va }` to
  `{ level, parent, kind, type_va, pad_va }`.
- Track the compile-time active try level while lowering i386 functions.
  Nested try bodies arm their own level and record the previous level as their
  parent (`u32::MAX` is runtime `-1`).
- Restore the parent trylevel after normal try-body completion and at catch-pad
  entry, before user catch code runs.
- Teach the i386 multi handler to retry the row scan at the recorded parent
  when no row at the current level accepts the exception.

Skeptic review:

- Skeptic A rejects a simple "remove the nested rejection" fix: it would make
  compilation succeed but leave outer try handlers inactive after inner
  fallthrough/catch delivery.
- Skeptic B rejects catch-pad-only restoration: it fixes throws from inner catch
  bodies but not inner no-match propagation, because the runtime handler would
  still stop at the innermost level.
- Skeptic C accepts the parent-row design as minimal: it preserves the existing
  single active word, keeps sequential try parents at `-1`, and changes only the
  multi-try table/handler path. Vote: 2/3 accepted.

Implementation:

- Added parent-level tracking to `Gen` and i386 scope-table emission.
- Removed the explicit nested i386 try rejection.
- Restored parent trylevels on try fallthrough and at catch-pad entry.
- Updated `.mdbcc_seh3_multi_handler` to scan parent levels before continuing
  search outside the frame.

Review:

- Independent self-review checked the i386 handler row offsets, parent fallback
  branch patching, scratch-slot usage below the SEH record, and interaction
  with existing sequential multi-try rows. No B-10 markup was needed.
- The pre-existing unrelated `src/codegen.rs` Win64 outgoing-stack reservation
  hunk remains unstaged for this bug.

- Pre-fix focused regression failed at compile time with the existing nested
  i386 rejection.
- Post-fix focused B-10 regressions passed:

## B-17 - same-named block-scoped statics

Investigation:

- `BUGS.md` pointed at `src/codegen.rs:~1438`. The current code has an

  "same-named block-scoped statics are not yet supported".

- Added Win64 and i386 regressions using sibling blocks:
  `pick(1)` reaches `static int n = 10`, `pick(0)` reaches a distinct
  `static int n = 20`, and repeated calls should return 11, 21, 12, 22 for
  a total of 66.
- Pre-fix both regressions failed with the documented duplicate-static-local
  `CodegenError`.

Diagnosis:

- Static-local storage was keyed as `.slocal.<function>.<source-name>` and
  body lookup used one flat `HashMap<String, String>` populated at function
  start. That design can represent same-named statics in different functions,
  but not same-named declarations in different lexical blocks of one function.
- The facts fit: different functions worked because the function name was part
  of the key; same function/same source name collided during pre-registration;
  and simply removing the guard would still be wrong because flat lookup would
  not know which block's declaration was in scope.

Design:

- Keep pre-registration before pass 2, but key each static-local declaration by
  source location: `.slocal.<fn>.<line>.<col>.<name>`, with matching guard
  symbols for runtime-initialized statics.
- Bind static names at the declaration site into a lexical static-name scope
  parallel to `name_scopes`, and resolve variable names through one
  innermost-out helper that considers automatic and static bindings in the same
  scope order.
- This keeps file-scope globals, static data members, and same-named statics in
  different functions behaviorally unchanged, while making same-function
  block-scoped statics representable.

Skeptic review:

## B-22 - `printf` `+`/space/`#` flags and `%f` precision > 15

Investigation:

- `tests/printf_format.rs` explicitly asserted compile errors for `%+d`,
  `% d`, `%#x`, and `%.16f`.
- `src/codegen.rs` parsed those flags into `FmtSpec`, then rejected
  `spec.plus || spec.space || spec.alt` before dispatch.
- `%f` precision was capped at 15 because the old Win64 path scaled the value
  by `10^prec` into a single integer and `float_token` used a fixed 40-byte
  stack token buffer; the Win32 path also had a fixed 16-byte fraction scratch.

Reproduction:

- Added positive regressions for signed `+`/space flags, alternate hex/octal
  prefixes, `%# .0f` decimal-point forcing (spelled as `%#.0f` in the test),
  and `%.16f`/`%.20f` dyadic values.
- Pre-fix `mdtimeout 300 cargo test --test printf_format -- --nocapture`
  failed exactly on `CodegenError("printf: '+', ' ' and '#' flags not yet supported")`
  and `CodegenError("printf '%f': precision > 15 unsupported ...")`.

Diagnosis:

- The parser was not the fault; it already retained the flags and precision.
- The integer and float emitters only knew how to emit digits plus an optional
  minus sign, so codegen rejected any flag that would need a positive sign,
  space sign, base prefix, or forced decimal point.
- The precision cap was a real safety guard: removing it without resizing the
  buffers or changing the scaled-integer algorithm would either overflow codegen
  arithmetic (`10^20`) or overrun the generated stack token buffer.

- Keep the fast plain `%d`/`%x`/`%f` paths untouched.

  `-`, `+`, space, `0x`, and `0X` as the non-zero-padded prefix.
- For `%f`, size the token and fraction scratch from the requested precision,
  pull fractional digits one at a time on both backends, and emit the `#`
  decimal point before integer digits when precision is zero.
