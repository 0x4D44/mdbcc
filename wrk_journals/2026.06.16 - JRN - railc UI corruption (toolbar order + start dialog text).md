# 2026.06.16 — JRN — RailC UI corruption: toolbar button order + Start dialog text

## Task
Arthur built mdbcc, then built `../railc` (RailC, a Borland C++ 4.5 OWL app) with it,
targeting **win64**. Two visual defects in the running app:

1. **Toolbar buttons in the wrong order / positions** (Image #1).
2. **"Start new" dialog has missing text** (Image #2): only a partial first line
   shows ("A weekday morning in 1994 - 07:00hrs (real" — truncated before "WTT)"),
   and the 2nd/3rd lines are blank.

Goal: investigate root cause(s) in mdbcc and fix; rebuild railc and verify.

## Ground truth gathered (source level)

### Symptom 1 — toolbar (TToolbar / TToolbutton)
- `RAILC.CPP` fills `ToolButtData` (`Toolbuttondata`, in TOOLBUTT.H): parallel arrays
  `int XPos[20]; WORD WParam[20]; long LParam[20]; HWND SentWindow[20],StatWindow[20];
  char UpText[20][100],DownText[20][100];`. On **win64** this struct is ~4520 bytes and
  contains 8-byte HWND members → struct alignment 8.
- `RAILC.CPP:351  new TToolbar(this, 12, ToolButtData, ToolbarBitmaps)` — the whole
  struct is passed **BY VALUE**. TToolbar stores `ButtData = ButtonData` (member copy).
- `TToolbar::SetupWindow` loops i=1..12: `new TToolbutton(this, ButtData.XPos[i], 3, i,
  ButtData.WParam[i], ...)`. The button's **bitmap slice** is `(ButtonNum-1)` where
  `ButtonNum == i` (passed directly, NOT from the struct). Its **screen X** is
  `ButtData.XPos[i]` (from the by-value copy).
- ⇒ If the large by-value struct copy is mis-marshalled on win64, icons (correct, keyed
  on i) land at WRONG X positions → "wrong order". **Prime suspect: Win64 large
  struct-by-value argument passing/copy.**

### Symptom 2 — Start dialog (TStart / TLayout parse)
- `START.CPP` sets three statics from `DisplayHan->StartText[0..2]` (`char
  StartText[3][100]` in LAYOUT.H).
- `LAYOUT.CPP:~2093` parses `[GENERAL]` from the `.RCD` data file using **C++
  iostreams**: `infile.getline(szInput,N)` (ifstream), then
  `istrstream ins(szInput, strlen(szInput)); ins.getline(szInput,N,'='),
  ins.getline(szInput,N,',')`. Values copied via `BoundedCopy` (strncpy wrapper, benign).
- Expected from `KINGSX94.RCD`:
  - `StartText1= A weekday morning in 1994 - 07:00hrs (real WTT)`
  - `StartText2= Prepare to start your 8 hour shift as`
  - `StartText3= duty controller at King's Cross Station`
- Displayed: line1 truncated at "(real", lines 2/3 blank. ⇒ **Prime suspect: mdbcc
  miscompiling the BC4.52 iostream slice** (`istream::getline` ISTGLINE.CPP and/or
  `istrstream`/`strstreambuf` ctor/underflow) — the streams lib is compiled from real
  Borland source (SOURCE/RTL/SOURCE/IOSTREAM).

## ROOT CAUSE — symptom 1 (toolbar)  ✅ FOUND
- Instrumented railc TOOLBUTT/TOOLBAR/RAILC: original `ToolButtData.XPos[4..6]`=58,90,
  114 (correct); after `new TToolbar(this,12,ToolButtData,ToolbarBitmaps)` the copied
  `ButtData.XPos[4]`=garbage, `[5]`=-1.
- Minimal console repro (`wrk_probe/uirepro/tb2_probe.cpp`): passing `bmp=(void*)0x1234`
  as the 4th arg → `ButtData.XPos[4]==0x1234`, `XPos[5]==0`. **The trailing pointer
  arg is written into the struct-copy temp at offset 16.**
- Diagnosis: win64 call marshalling for a **large by-value struct passed by hidden
  pointer, followed by another stack argument** — the struct temp copy OVERLAPS the
  outgoing-argument stack region, so the trailing arg's store (rsp+0x20) lands at
  temp+16. Struct-as-last-arg (tb_probe.cpp) does NOT repro; struct-3rd-of-4 does.
- FIX TARGET: src/codegen.rs call-argument stack layout (allocate struct byval temps
  clear of the outgoing-arg area / order the stores correctly).

## FIX — symptom 1  ✅ DONE
- `src/codegen.rs` ~4030: `outgoing = io_out.max(8*max_stack_args)` omitted the Win64
  0x20 shadow that sits BELOW outgoing stack args. The +32 pad in `frame_fixed`
  normally absorbs the overflow, but an H1 by-value buffer / H2 result buffer placed
  BETWEEN frame_fixed and the outgoing region breaks that adjacency. Precise math:
  outgoing=max(16,8)=16; byval base=rsp+16; trailing arg stored at rsp+0x20=rsp+32 →
  byval offset 16 = XPos[4]. Fix: when `max_stack_args>0 && (by_value_bytes>0 ||
  result_buf_max>0)`, reserve `0x20 + 8*max_stack_args`. Gated so non-byval/non-record
  functions stay byte-identical (O1 contract preserved).
- Verified: minimal repro `tb2_probe.cpp` → 0 mismatches. railc rebuilt (clean source,
  instrumentation removed) → toolbar buttons now 79..343 = XPos 10..274, matching the
  32-bit oracle. Capture `uibug_run/01_main.png` shows the correct continuous toolbar.

## ROOT CAUSE + FIX — symptom 2 (dialog text)  ✅ DONE
- Rebuilding railc / the OWL libs with the codegen fix did NOT help → distinct bug.
- Ground truth (PrintWindow + window-tree enum under PS 5.1):
  - All 3 START statics present, visible, CORRECT text; blackrect (SS_BLACKRECT,
    id -1, (3,19,156,24)) is LAST in z-order (bottom) in BOTH 32-bit oracle and
    64-bit — IDENTICAL z-order, styles (0x50020001 text / 0x50000004 rect), font.
  - Yet on win64 the filled blackrect PAINTS OVER lines 2 & 3 (which sit inside it);
    line 1 (above it) shows. 32-bit renders text-over-panel correctly.
  - Hiding the blackrect → text appears. Giving the blackrect **WS_CLIPSIBLINGS** →
    text appears, panel clipped to thin sunken lines (matches 32-bit). (Probe:
    `dlg_paint_probe.ps1` experiments A–F.)
  - OWL EvPaint trace (`paintlog`): the dialog statics/blackrect do NOT go through
    OWL — they're painted by USER32. The 32-bit build uses standard OWL; win64 uses
    the static-dispatcher OWL (dialog NOT subclassed). With WS_CLIPSIBLINGS absent on
    these controls the OS leaves overlapping-sibling paint order UNDEFINED; 32-bit
    happened to paint favourably, win64 paints the panel last (on top).
- FIX: `wrk_owl_win64/DIALOG.CPP` `TDialog::SetupWindow` — after `TWindow::SetupWindow()`,
  walk the dialog's children (GetWindow GW_CHILD/GW_HWNDNEXT) and OR in WS_CLIPSIBLINGS
  on each. Overlapping controls now render strictly by Z order. Standard dialog hygiene;
  harmless for non-overlapping controls.
- Verified (`verify_probe.ps1`, fixed OWL+railc): START shows all 3 lines; About and
  Config dialogs (group boxes/radios/checkboxes) unchanged; toolbar still correct.
